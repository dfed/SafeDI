# Validation boundaries

Validation is split between the macro and the plugin based on available context:

- **Macro validation** (compile-time, local context only): The macro sees only the single decorated type or extension. Any error that can be determined from local context belongs here — missing `init`/`instantiate()`, invalid parameter combinations (`mockOnly + generateMock`; and, as a warning with a fix-it, `mockOnly + mockAttributes`, which no generated `mock()` reads), mock method signature issues, an optional `@Instantiated` property type (`X?`, `X!`, `Optional<X>`, `Instantiator<X>?`, `Instantiator<X?>`; `InjectableMacro`), a property that is not optional on an erased rename of an optional dependency (`ofType: X?.self` with `erasedToConcreteExistential: true`, which is `nil` where the dependency is; `InjectableMacro`, with a fix-it that adds `?`, except where `onlyIfAvailable` is set, whose own check reports it), and the access levels generated code can never use: `private` or `fileprivate` on the type, its construction initializer, its `instantiate()`, or its hand-written mock method, since generated code is in a file of its own (each with a fix-it that deletes the modifier; `Initializer.isValid` applies the same rule, so an `internal` or `package` initializer is selected for construction). These produce fix-its in the IDE. Whether any other access level suits the module that constructs the type is the tool's to judge (see "Access between modules"). Code generation test fixtures never declare an optional `@Instantiated` property, since the macro rejects one. Generation matches a type's names as `String`s, so the macro (`InstantiableVisitor`) rejects, without a fix-it, two names of one declaration that SafeDI matches by name (dependency labels, alias fulfilling names, and parameter names of initializers, `instantiate(…)`, and hand-written mocks) that are equal as `String`s but differ in UTF-8 bytes, which Swift reads as two names, as well as an `instantiate(…)` dependency parameter named `_`. It rejects two `@Received(fulfilledByDependencyNamed:ofType:)` spellings (`InstantiableMacroRenames.swift`): a rename fulfilled by another rename of the same declaration – only when the two hold in one evaluation of the declaration's `#if` blocks (both outside every block, in one clause, or one in a clause enclosing the other's), since it reads every clause and cannot tell which are active; renames in two clauses of one block, or in two blocks, are left to SafeDITool – with a fix-it that names the property the renames start from and the type the last rename followed reads it as, adding `onlyIfAvailable: true` when a rename on the way is `onlyIfAvailable`, and none where a rename on the way wraps its value or keeps its label, the renames form a cycle, or the declaration would have to be optional and is not; and a rename of a dependency to itself, its label with its type (a fix-it to `@Received`, none when it is also `erasedToConcreteExistential`) or its type, or its type made optional, only if available (a fix-it to `@Received(onlyIfAvailable: true)`, beside the `@Received` macro's fix-it that makes a non-optional type optional; the erased spelling wraps, so it stays). A rename that keeps its label and changes its type retypes the property above it and stays. The warning at a dependency type that names a type nested in the decorated declaration unqualified or through `Self` collects nested types from every `#if` clause and exempts a nested `@Instantiable` type exactly where `TypeDescription.qualifyingInstantiatedType(within:amongInstantiableTypes:)` qualifies it, as SafeDITool does. Its fix-it qualifies with every enclosing type from `context.lexicalContext`, and must also rewrite the same-named parameters of initializers and hand-written mocks and an alias’s `ofType:` argument, or the declaration stops matching its dependencies.
- **Plugin warnings** (build-time, full context): `DependencyTreeGenerator.generateWarnings()` runs after the tree has generated. It reports a `LazilyInstantiated` property that is instantiated whenever the type declaring it is created, because a type created along with that one reads its instance by value. `InstantiationAnalysis` reads the scopes `rootScopeGenerators` built and validated (`validatedScopes`), is type-level, and is memoized per `Scope`: a type’s creation reads what its own required by-value receives and aliases read, plus what its constant children and its instantiated-with-owner lazily instantiated children read, minus every label the type declares. A read of a renamed wrapper's instance is followed through the type's renaming (`propertyRead(by:)`) to the property it renames. An `onlyIfAvailable` receive is deliberately never a reader: whether it reads the instance or is passed `nil` depends on sibling ordering, which only `ScopeGenerator` knows, and a warning about a dependency that is not instantiated would be worse than a missing one.
- **Plugin validation** (build-time, full context): The plugin (`SafeDITool generate`) sees all modules' types. Errors that require cross-type knowledge belong here — unfulfillable dependencies, received dependencies hidden by a closer ancestor's property with the same label (generated code passes dependencies by label), a rename whose `fulfilledByDependencyNamed:` label its own type instantiates or forwards with a type other than its `ofType:` (`renamesContradictingOwnProperties`: the rename refers to that property, so `ofType:` must name its type exactly, optionality included, or a `LazilyInstantiated` property's instance type; recorded in the hidden-label walk and thrown before unfulfillable and hidden properties, which it explains, and checked again in `validateChildrenDoNotRequireEachOther` for the trees of dependencies a mock promotes, which that walk does not reach; both declarations are on one type, but the check stays in the plugin by ruling), dependency cycles, a `@Sendable` builder function that would capture an `Instantiator`, `ErasedInstantiator`, or `LazilyInstantiated` declared outside it (`ScopeGenerator.nonSendableWrapperCaptures`, which walks the generator trees as code generation does, so a dependency passed `nil` is not reported; a receiver is reported once for each chain that reaches it, so the root a diagnostic names never depends on name order), duplicate type declarations, duplicate mock providers, a `mockOnly` hand-written `mock` on a type whose `mock()` is generated, the seam errors (`DependencyTreeGeneratorError.SeamError.Kind`: two receives of one label with different types, a tier that cannot take a required parameter, a hand-written initializer a generated tier would redeclare, a reached seam whose module's `.safedi` names a dependency this run lacks, signatures that do not settle, a seam's tree reaching a declaration its callers cannot see), an `additionalMocksToGenerate` entry of the selected configuration that names no `@Instantiable` type (`SafeDIConfiguration.validateAdditionalMocksToGenerate`, judged against the concrete types mock generation matches entries to, unioned with the `ModuleInfo.instantiableTypeNamesInAnyClause` of this module and its dependent modules, so an entry naming a type declared only in an inactive clause is accepted and its file written without code, as "Conditional compilation" describes; entries of configurations in inactive clauses are planned by `scan` and written without code, never judged), and an entry that names a type whose every map entry is `mockOnly` (`validateAdditionalMocksToGenerate(namingMockOnlyDeclarationsIn:)`: its hand-written mock is its mock; a production declaration a `mockOnly` one merges into, under any key, keeps the entry accepted; it runs before mock generation, so it wins over `handWrittenMockSharesGeneratedMockName` for a fake whose method is named `mock`).
- **Deprecations** (2.3.0, removed in 3.0; decisions 72 and 73). `@Forwarded` on any of the six SafeDI wrappers, optional or not, is a macro warning without a fix-it at the property's type (`InjectableMacro`'s `InjectableDeprecation`, asked of the attribute being expanded so a property is warned about once, and classifying the type with `TypeDescription.propertyType` as the tool does, so a spelling the tool reads as a plain value – `SafeDI.LazilyInstantiated<X>`, a typealias – draws none, a deliberate gap); the tool still accepts and generates the shape, and the fuzzer still draws it: the warning lands at a fixture line, whose messages `warningsOnlyGeneratedCodeDraws` drops. `generate --additional-imported-modules` and a hand-written `--swift-manifest` each give `generate` a location-less `.warning` `SourceDiagnostic`, ahead of the module's other warnings. A manifest is hand-written when it lacks a field `scan` always writes (`SafeDIToolManifest.lacksFieldsScanAlwaysWrites`: `activeCompilationConditions`, `mockScopedFilePaths`, `projectRoot`); one that spells all three cannot be told from `scan`'s and gets no warning, a deliberate gap. Until 3.0 those fields stay optional, so every reader keeps its fallback for a manifest without them.
- **Never a trap on what the macro rejects.** Every build runs `generate` before the compiler expands the macro, so where the tool relies on a macro check to keep it from trapping, input the macro rejects gets a short plain error at the declaration that points at the macro's rule: no fix-it, which the macro keeps for the IDE, and no copy of the macro's validation. `validateDependencyLabelsAreDistinct` is such a check: generation keys a declaration's dependencies by label, so a declaration two of whose dependency labels `String` equates is reported at the later one when a production root's tree (its reachable types), a generated seam's tree (and the foreign seams it calls, checked before any seam signature is computed), or a mock root's tree (the scopes its mock root scope reaches, promoted ones included) builds it – two `instantiate(…)` parameters named `_`, names encoded differently, and one dependency declared in each clause of an `#if` only the compiler decides, which the macro accepts. `validateRenamesAreSpelledAsTheMacroAccepts` runs beside it over the same declarations (`RejectedRename`), and in `mockScopes` before the mock cycle walk, over the declarations that walk reads: the trees of the roots, of the types whose mocks are generated, and of the scopes it follows a required receive to. It rejects a rename fulfilled by the label of another rename of its declaration, by its own label and type, or by its own label with its type, or its type made optional, only if available (not erased) – including, by ruling, a rename of a rename the macro accepts because two `#if` blocks, or two clauses of a block only the compiler decides, hold the links, which SafeDITool's evaluation joins. The ruling keeps one rule for every chain within one declaration, and its error names the label to change. Across clauses only the compiler decides, the shape also does not work: the code generated from every clause's renames can assign one clause's rename from another clause's, a wrong value that compiles. No validation walk meets such a rename, which is why no code follows a chain of aliases within one scope. A declaration no tree reaches traps nowhere, so it is not reported: a shape that works must not become an error. Tests of these errors are the one exception to fixtures the macro accepts.

Two rules of this section, "Reject nonsense shapes" and "The macro prevents; the plugin trusts", are in `CLAUDE.md`, since every change needs them. Access between modules is in `module-membership-and-access.md`.
