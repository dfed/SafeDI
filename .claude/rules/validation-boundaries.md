# Validation boundaries

Validation is split between the macro and the plugin based on available context:

- **Macro validation** (compile-time, local context only): The macro sees only the single decorated type or extension. Any error that can be determined from local context belongs here — missing `init`/`instantiate()`, invalid parameter combinations (`mockOnly + generateMock`; and, as a warning with a fix-it, `mockOnly + mockAttributes`, which no generated `mock()` reads), mock method signature issues, a `@MainActor` initializer that generated code calls without a stated isolation (`InstantiableMacroIsolation.swift`, whose comment gives its gaps), an optional `@Instantiated` property type (`X?`, `X!`, `Optional<X>`, `Instantiator<X>?`, `Instantiator<X?>`; `InjectableMacro`) without `onlyIfAvailable: true`, and with it a type that is not one optional of a type SafeDI creates itself (`X`, `X??`, `Optional<X>`, each with a fix-it to `X?`; a SafeDI wrapper, without one, which a later release may accept), an `@Instantiated` SafeDI wrapper whose built type is another (`LazilyInstantiated<Instantiator<X>>`, no fix-it; `InjectableMacro`), a property that is not optional on an erased rename of an optional dependency (`ofType: X?.self` with `erasedToConcreteExistential: true`, which is `nil` where the dependency is; `InjectableMacro`, with a fix-it that adds `?`, except where `onlyIfAvailable` is set, whose own check reports it), `erasedToConcreteExistential: true` where generated code would call an initializer no type can have (`InjectableMacro`): on an existential spelled with `any` or as a composition (`P & Q`) – the property's type, a rename's type without its optionality, or the type an `@Instantiated` wrapper builds – with a fix-it that removes the argument, and, without one, on a rename into a SafeDI wrapper (whose initializers take a function) of a dependency whose `ofType:` is not spelled as a function type (a property spelled as a bare protocol name is left to the compiler, since the macro cannot tell a protocol from a concrete existential; an `ofType:` naming a typealias of a function type is reported, since the macro reads spellings only, and erasing a function into a wrapper is a nonsense shape), and the access levels generated code can never use: `private` or `fileprivate` on the type, its construction initializer, its `instantiate()`, or its hand-written mock method, since generated code is in a file of its own (each with a fix-it that deletes the modifier; `Initializer.isValid` applies the same rule, so an `internal` or `package` initializer is selected for construction). These produce fix-its in the IDE. Whether any other access level suits the module that constructs the type is the tool's to judge (see "Access between modules"). Code generation test fixtures never declare an optional `@Instantiated` property, since the macro rejects one. Generation matches a type's names as `String`s, so the macro (`InstantiableVisitor`) rejects, without a fix-it, two names of one declaration that SafeDI matches by name (dependency labels, alias fulfilling names, and parameter names of initializers, `instantiate(…)`, and hand-written mocks) that are equal as `String`s but differ in UTF-8 bytes, which Swift reads as two names, as well as an `instantiate(…)` dependency parameter named `_`. It rejects a type name, declared or spelled in the declaration, that begins with a prefix SafeDI reserves for the types it generates ("A type named with a generated type’s prefix is rejected" in `reserved-names-and-spelling.md`). It rejects two `@Received(fulfilledByDependencyNamed:ofType:)` spellings (`InstantiableMacroRenames.swift`): a rename fulfilled by another rename of the same declaration – only when the two hold in one evaluation of the declaration's `#if` blocks (both outside every block, in one clause, or one in a clause enclosing the other's), since it reads every clause and cannot tell which are active; renames in two clauses of one block, or in two blocks, are left to SafeDITool – with a fix-it that names the property the renames start from and the type the last rename followed reads it as, adding `onlyIfAvailable: true` when a rename on the way is `onlyIfAvailable`, and none where a rename on the way wraps its value or keeps its label, the renames form a cycle, or the declaration would have to be optional and is not; and a rename of a dependency to itself, its label with its type (a fix-it to `@Received`, none when it is also `erasedToConcreteExistential`) or its type, or its type made optional, only if available (a fix-it to `@Received(onlyIfAvailable: true)`, beside the `@Received` macro's fix-it that makes a non-optional type optional; the erased spelling wraps, so it stays). A rename that keeps its label and changes its type retypes the property above it and stays. The warning at a dependency type (or an alias’s `ofType:`) that names a type nested in the decorated declaration through `Self` (`Self.Mode`) collects nested types from every `#if` clause; a bare name (`Mode`) gets no warning, because SafeDITool qualifies it (see "Nested-type qualification"), while generated code spells `Self.Mode` as written, in another type’s extension. Its fix-it qualifies with every enclosing type from `context.lexicalContext`, and must also rewrite the same-named parameters of initializers and hand-written mocks and an alias’s `ofType:` argument, or the declaration stops matching its dependencies. An initializer, `instantiate(…)` or mock method that a fix-it adds takes the type's access as far as the macro can see it – in an extension, that of its widest `instantiate(…)`, or else the default of the extension's members – capped by each enclosing type and by each type declared inside the decorated declaration that a parameter names, and spells no modifier where the members beside it have that level without one (`accessModifier(ofDeclarationAddedWithTypeLevel:memberDefaultLevel:members:declaredType:dependencies:)`). The macro cannot see a type declared anywhere else, so a parameter naming a narrower one is left to the compiler, which rejects the added declaration (the Manual leaves this to the compiler's error).
- **Plugin warnings** (build-time, full context): `DependencyTreeGenerator.generateWarnings(validatedScopes:)` runs once the trees are built, and its warnings are returned only when the tree also generates. It reports a `LazilyInstantiated` property that is instantiated whenever the type declaring it is created, because a type created along with that one reads its instance by value. `InstantiationAnalysis` reads the scopes `dependencyTrees(unreadTypeComment:)` built and validated, there, so that `DependencyTrees` carries the warnings and no scope is held through code generation, is type-level, and is memoized per `Scope`: a type’s creation reads what its own required by-value receives and aliases read, plus what its constant children and its instantiated-with-owner lazily instantiated children read, minus every label the type declares. A read of a renamed wrapper's instance is followed through the type's renaming (`propertyRead(by:)`) to the property it renames. An `onlyIfAvailable` receive is deliberately never a reader: whether it reads the instance or is passed `nil` depends on sibling ordering, which only `ScopeGenerator` knows, and a warning about a dependency that is not instantiated would be worse than a missing one.
- **Plugin validation** (build-time, full context): The plugin (`SafeDITool generate`) sees all modules' types. It rejects, before building any tree, each type declared in the module's own files whose name begins with a reserved prefix that the macro does not see, at the name ("A type named with a generated type’s prefix is rejected" in `reserved-names-and-spelling.md`). Errors that require cross-type knowledge belong here — unfulfillable dependencies, received dependencies hidden by a closer ancestor's property with the same label (generated code passes dependencies by label), a label received in a mock's tree – the mocked type's own or a promoted dependency's – in two forms no one declaration provides, one beneath the other or on one type, where both receives are required (`receivedPropertyHiddenInMockTree`; a receive only if available that a required one pins is passed `nil` instead, see `.claude/rules/mock-root-promotion.md`), a label that a type a lazy cycle builds again beneath a declaration of it and the types it builds receive in forms one value cannot carry together (`unpassableCycleLabel`, see `CycleParameter` in `cycle-generation.md`), a rename whose `fulfilledByDependencyNamed:` label its own type instantiates or forwards with a type other than its `ofType:` (`renamesContradictingOwnProperties`: the rename refers to that property, so `ofType:` must name its type exactly, optionality included, or a `LazilyInstantiated` property's instance type; recorded in the hidden-label walk and thrown before unfulfillable and hidden properties, which it explains, and checked again in `validateChildrenDoNotRequireEachOther` for the trees of dependencies a mock promotes, which that walk does not reach; both declarations are on one type, but the check stays in the plugin by ruling), dependency cycles, a hand-written mock a generated mock calls (the mocked type's own, or one a mock tree, or a fill a call in it declares, builds the type with) that takes a parameter without a default value no dependency the declaration has under the build's conditions fulfills (`UnfulfilledMockParameter`, checked per mock root before generation, only where the build compiles the generated mocks – the mock condition is `nil` or active (`ConditionalCompilationEvaluator.compilesGeneratedMocks`), so a release build of a shape whose call is only under `#if DEBUG` builds as before (a debug build that does not report the condition, as SwiftPM's native backend does not report `DEBUG`, gets the compiler's error in the generated mock instead; a fill's call is generated in those builds too, passing such a parameter the value of its own name (`Initializer.createHandWrittenMockArgumentList`), which that debug build compiles only where a value of that name is in scope); `query needs` describes no one build and always checks; a type no mock tree builds with its mock is not reported; each finding once across the mock roots that find it, keyed by its location, type and parameter, and the findings at one location in the mock's parameter order): the macro reads every clause, so it accepts a mock outside an `#if` that takes a dependency only an inactive clause declares, which is reported at the outermost such clause (`Instantiable.dependencyLabelsInUnselectedClauses`, which module info carries, so another module's clause is located in its own file), with no fix-it, naming a default value for the parameter and, only where moving the mock into that clause compiles under every condition (the clause declares each such dependency itself, every other required parameter takes a dependency outside every `#if`, and the type is not `mockOnly`, which would then have no mock), that move; a parameter no clause declares is input the macro rejects, reported plainly at the mock, a `@Sendable` builder function that would capture an `Instantiator`, `ErasedInstantiator`, or `LazilyInstantiated` declared outside it (`ScopeGenerator.nonSendableWrapperCaptures`, which walks the generator trees as code generation does, so a dependency passed `nil` is not reported; a receiver is reported once for each chain that reaches it, so the root a diagnostic names never depends on name order, and each of its errors’ remedies names every type whose declaration a chain captures there, in source order, since each feeds that receive and changing all of them clears every one of its errors), duplicate type declarations among the types the module can name (`types-a-module-cannot-name.md` removes the others first) (`CollectInstantiablesError.duplicate(of:declaredBy:)`: declarations all in one known module are told to keep one, and one declaration that fulfills a type twice to remove the repeat; otherwise SafeDI, which reads only `@Instantiable` declarations here, cannot tell one type of that name from several, so the error offers a rename: when any declaration is an extension or a `fulfillingAdditionalTypes` claim, beside keeping one, naming the modules in sorted order when each is known and first asking any module that repeats the name to fulfill it once; when every declaration is a type of that name and some module is unknown, beside keeping one; when each is a type in a known module and the modules differ, naming them in sorted order and asking for a rename, first to declare the type once in any module that repeats it, and, when each is inside an `#if` only the compiler decides, offering one declaration outside it beside the rename, since SafeDI cannot tell one type split by platform from two unrelated types), duplicate mock providers, a `mockOnly` hand-written `mock` on a type whose `mock()` is generated, the seam errors (`DependencyTreeGeneratorError.SeamError.Kind`: two receives of one label with different types, a tier that cannot take a required parameter, a hand-written initializer a generated tier would redeclare, signatures that do not settle, a seam's tree reaching a declaration or a plain declaration its callers cannot see, a tier wider than a hole's builder; places of one builder that forward different values (`placesForwardOtherValues`), reported at each place that forwards another value than the first by location, naming both, where a place another module's inner seam passes up is located at this module's property through which the tree reaches that seam, since a build never reports in a file another module owns – a plugin check, since the places can be in two modules and `Impl.ForwardedProperties` and `Int` can spell one value, which no single declaration decides), an `additionalMocksToGenerate` entry of the selected configuration that names no `@Instantiable` type (`SafeDIConfiguration.validateAdditionalMocksToGenerate`, judged against the concrete types mock generation matches entries to, unioned with the `ModuleInfo.instantiableTypeNamesInAnyClause` of this module and its dependent modules, so an entry naming a type declared only in an inactive clause is accepted and its file written without code, as "Conditional compilation" describes; entries of configurations in inactive clauses are planned by `scan` and written without code, never judged), and an entry that names a type whose every map entry is `mockOnly` (`validateAdditionalMocksToGenerate(namingMockOnlyDeclarationsIn:)`: its hand-written mock is its mock; a production declaration a `mockOnly` one merges into, under any key, keeps the entry accepted; it runs before mock generation, so it wins over `handWrittenMockSharesGeneratedMockName` for a fake whose method is named `mock`).
- **Deprecations** (2.3.0, removed in 3.0). `@Forwarded` on any of the six SafeDI wrappers, optional or not, is a macro warning without a fix-it at the property's type (`InjectableMacro`'s `InjectableDeprecation`, asked of the attribute being expanded so a property is warned about once, and classifying the type with `TypeDescription.propertyType` as the tool does, so a wrapper spelled with SafeDI's module name, `SafeDI.LazilyInstantiated<X>`, draws it too, and a typealias, which the tool reads as a plain value, draws none, a deliberate gap); the tool still accepts and generates the shape, and the fuzzer still draws it: the warning lands at a fixture line, whose messages `warningsOnlyGeneratedCodeDraws` drops. `generate --additional-imported-modules` and a hand-written `--swift-manifest` each give `generate` a location-less `.warning` `SourceDiagnostic`, ahead of the module's other warnings. A manifest is hand-written when it lacks a field `scan` always writes (`SafeDIToolManifest.lacksFieldsScanAlwaysWrites`: `activeCompilationConditions`, `mockScopedFilePaths`, `projectRoot`); one that spells all three cannot be told from `scan`'s and gets no warning, a deliberate gap. Until 3.0 those fields stay optional, so every reader keeps its fallback for a manifest without them.
- **Never a trap on what the macro rejects.** Every build runs `generate` before the compiler expands the macro, so where the tool relies on a macro check to keep it from trapping, input the macro rejects gets a short plain error at the declaration that points at the macro's rule: no fix-it, which the macro keeps for the IDE, and no copy of the macro's validation. `validateDependencyLabelsAreDistinct` is such a check: generation keys a declaration's dependencies by label, so a declaration two of whose dependency labels `String` equates is reported at the later one when a production root's tree (its reachable types), a generated seam's tree (and the foreign seams it calls, checked before any seam signature is computed), or a mock root's tree (the scopes its mock root scope reaches, promoted ones included) builds it – two `instantiate(…)` parameters named `_`, names encoded differently, and one dependency declared in each clause of an `#if` only the compiler decides, which the macro accepts. `validateRenamesAreSpelledAsTheMacroAccepts` runs beside it over the same declarations (`RejectedRename`), and in `mockScopes` before the mock cycle walk, over the declarations that walk reads: the trees of the roots, of the types whose mocks are generated, and of the scopes it follows a required receive to. It rejects a rename fulfilled by the label of another rename of its declaration, by its own label and type, or by its own label with its type, or its type made optional, only if available (not erased) – including, by ruling, a rename of a rename the macro accepts because two `#if` blocks, or two clauses of a block only the compiler decides, hold the links, which SafeDITool's evaluation joins. The ruling keeps one rule for every chain within one declaration, and its error names the label to change. Across clauses only the compiler decides, the shape also does not work: the code generated from every clause's renames can assign one clause's rename from another clause's, a wrong value that compiles. No validation walk meets such a rename, which is why no code follows a chain of aliases within one scope. A declaration no tree reaches traps nowhere, so it is not reported: a shape that works must not become an error. Tests of these errors are the one exception to fixtures the macro accepts.
- **A tool diagnostic carries at most one fix-it, and only an unambiguous one.** swift-build attaches each `fixit:` line that directly follows a diagnostic (`SourceDiagnostic.FixIt`), and Xcode applies a diagnostic's fix-its as one edit, so two fix-its with different replacements for one range show no Apply button at all; Xcode also drops `note:` lines from build-tool output, so a second candidate cannot ride on a note. Where several repairs are plausible, the message names them and carries no fix-it.
- **An erased instantiator's first generic argument** must be the forwarded properties of the type it builds (`firstGenericMatchesForwardedProperties`). A type with no `@Forwarded` properties is not checked, so a typealias of `Void` only the compiler can see through keeps working. `X.ForwardedProperties` is accepted for any type `X` the fulfiller fulfills, not only its concrete type, so the hand conformance of `X` is trusted as at an `Instantiator<X>` place; a mock does not share this (`mockBuildsFirstGeneric(of:)`, `mock-root-promotion.md`). The check compares through `TypeDescription.withoutSpellingDifferences(qualifiedByModulesNamed:orDeclaringModulesNamed:declaredTypeNames:)`, which sees through only what syntax shows: `Optional<T>`, `Array<T>`, `Dictionary<K, V>`, attribute order, and a qualifier that names `Swift`, the built type's module or, for a seam's fill, whose fulfiller is in another module, the seam's module where it also declares the hole's owner and no seam passes the hole up (`SeamSignature.Hole.declaringModuleNames`), unless a module SafeDI read declares a type of that name at file scope, which hides the one the syntax would mean. The last qualifier is seen through only for a type no other module SafeDI read declares a type of the name of (`DeclaredTypeNames.isDeclared(_:outsideModuleNamed:)`), since generated code spells the bare name in another module than wrote it. Two bare spellings that name different modules' types still match; that is generated code spelling a declaration in another module, a compile error today. It never spells a type. A typealias other than the built type's `ForwardedProperties`, or a type qualified by another module, is rejected with an error that names a spelling that works, since the tool resolves no name. Generated code spells the first generic argument as its declaration does, so a `ForwardedProperties` typealias keeps its spelling: normalizing it to the tuple would spell the built type's forwarded types where their names may resolve to nothing or to another type. So a receive that spells the tuple does not match a declaration that names the typealias.
- **An unfulfilled receive suggests only what it could receive.** Its "Did you mean" near-matches (the same label, or the same type) leave out a property that the closest declaration of its label, of another type, hides (`LabelDeclaration.fulfills(anyOf:)`, which the hidden-receive check reads too), since receiving it is reported as hidden. Where every near-match is hidden, the error suggests declaring the property instead. Wherever the filter drops a near-match, `SafeDIToolCodeGenerationHiddenSuggestionTests` applies what the error then suggests and shows the graph accepted.
- **A hidden receive names every declaration that hides it.** Where declarations of a receive’s label with other types sit at several levels of its chain, the error names each one between the receive and what provides it (the declaration it would resolve to, or, in a mock or a seam, the receive at the root of the walked tree), closest first, with a note at each (`LabelDeclaration.enclosingDeclarations`, read by `HiddenReceivedProperty`), so relabeling what it names leaves no declaration of the label hiding the receive. A declaration above what provides the receive hides nothing and is not named. `SafeDIToolHiddenReceiveDeclarationsTests` holds the shapes, and the remedy oracle applies the advice (`relabelHidingDeclaration`).
- **A mock's `@Sendable` capture check reads what the mock declares.** A wrapper the mock cannot build is the value `mock()` is passed, bound where the type that instantiates it is built (`ScopeGenerator.instantiatedDependenciesNotGenerated`), so `nonSendableWrapperCaptures` judges a `@Sendable` builder function beneath it that reads the wrapper, or the wrapper's instance, as it judges the declaration production builds, and the mock reports production's error, naming that type (`seam-and-mock-contract.md`, rule 7; `SafeDIToolMockSendableBuilderCaptureTests`). It reports it in every build, one that leaves the mock condition inactive included, as it reports every other capture in a mock: the tool cannot tell a release build from a debug build whose integration does not report `DEBUG`, which compiles the mock, and SafeDI has no other code to emit for the capture. A receive no declaration provides is a parameter of `mock()` or an override bound at its root, judged as a value the tree receives from outside it: a promoted sibling of the mocked type that receives another type under a label the mocked type declares included, which production rejects as hidden. `publicMockTierOmissions` enters the same declarations, so a call of another module's public mock whose tier omits a value `mock()` is passed is reported as for a forwarded one; `seamTierOmissions` walks production trees only, which have none.

Two rules of this section, "Reject nonsense shapes" and "The macro prevents; the plugin trusts", are in `CLAUDE.md`, since every change needs them. Access between modules is in `module-membership-and-access.md`.
