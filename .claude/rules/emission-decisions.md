# Decisions made while code is emitted

The emitter is being rewritten in two steps per body: a plan of builder functions and statements that kept code decides, then a spelling of that plan. The rewrite keeps every generated byte only if no output decision is taken while text is written, or from text already written. This file lists every such decision in today's emitter, what it reads, and how it is carried as a fact instead. A new decision that reads emitted text, or is made inside a body emitter, goes in this table, with its port, in the change that adds it.

The audit behind the table searched every emitter file under `Generators/` (`ScopeGenerator`, `PublicMockGeneration`, `PublicMockLevelFunctions`, the `Seam*` files, `GeneratedImportAccess`, `UnreadTypeComment`, `GeneratedCodeText`), `Models/Scope.swift` and `Models/Initializer.swift` for every `.split(`, `components(separatedBy:)`, `.contains("…")`, `hasPrefix` and `hasSuffix`; every `.isEmpty` on emitted text or on an array of emitted lines; every `min()` or `max()` over spelled text; and every branch on a body's generated lines. Diagnostics and access computations are left out: they decide no generated byte.

Errors thrown while text is written (`Initializer.createInitializerArgumentList`'s `unexpectedArgument`) are reported in emission order, the first one the walk reaches; a speculative code task discards its error.

## A caller's argument per form

A seam call's root dispatcher and a public mock call's root level functions hand each value a fill reads of the caller's scope as the caller declares it (an `ArgumentSource`): the label itself, its `instance` where the caller holds it lazily, a wrapper made of the caller's value where the fill reads a `LazilyInstantiated` the caller does not declare (`LazilyInstantiated<X>({ x })`, or `x.map { value in … }` for an optional), or `nil`. Every fill of one call reads the one scope enclosing the call (`Scope.Fill.callerNearestDeclarations`), so the caller's declaration in one form is the same for every fill, and nothing is chosen among spellings: two fills that take one label in different forms are each handed their own form, a form is passed as the declaration where any fill that takes it finds it available, and as `nil` where none does. `SafeDIToolSeamCallerArgumentFormTests` holds those shapes.

## Empty chunks

No body's statements include an empty chunk of text: every child scope a body emits writes at least one line. The only scope that writes nothing is a hole without a site, which exists only in a tree built to compute a seam's signature (`SeamHoles.site(at:)`), and such a tree generates no code. So a constant's body counts its statements without filtering empty strings, as the instantiator and lazy bodies do.

## A level holds its children's code, never a copy of their text

A production body is a plan (`GeneratedCode`): text, pieces written one after another or on lines of their own, a child's code a level indents, and the places of the body's walk (`.place`). Each level holds its children's plans and wraps a child in its indentation without copying it (`.indented`), every scope caches its plan, which every place that builds the scope again shares, and the root's plan is spelled once, where `ScopeGenerator.generateCode(codeGeneration:)` returns the tree's text. Re-indenting a subtree's text at every level above it cost CPU and memory that grew with the tree's size times its depth; the writer (`GeneratedCodeWriter`) keeps each level's line state instead and writes each line once, after the indentation of every level around it, the bytes `GeneratedCodeText.indentingNonEmptyLines` wrote at each level, `"\r\n"` kept inside its line (`GeneratedCodeTests`). A plan can be as deep as the module has types, so the writer keeps a stack of its own rather than recursing, and a level hands its children to `DeferredRelease` when it is released. Code that is not planned yet is hosted as text, flattened where it is read as text: an inlined fill (`inlinedFill`), a seam's root, a mock and the fills a mock's call splices (`mockLoweringFillCode`). A change to how a plan is built or spelled is measured against its base's peak memory on deep inline graphs, such as issue #646's, as well as wide ones: byte-identical output does not show it.

An async function's frame holds a body's values too. A task keeps the frame of each call it is suspended in, and each scope's code is planned on a task of its own (`generator-design.md`, "A generator keeps finished code, never a finished task"), so at the peak of a wide tree every scope holds a `generatePropertyCode` and a `generateProperties` frame at once: on Linux, 1,801 of each at the peak of 600 independent seams built inline, 62 of its 79 MB of heap. A frame holds a slot for each value its function decides or spells, on every branch, and for each function inlined into it, so the ports' plan values, decided inside `generatePropertyCode`, raised that graph's peak memory by 4 to 9%. So both functions only await children's code: what a scope writes around it, and what a body decides of its children, is decided by synchronous functions kept out of them with `@inline(never)` (`propertyCode(around:…)`, `bodyChildren(propertiesGeneratedLater:enclosingFunctionNames:)`); `generatePropertyCode`, whose frame keeps a slot for each of its branches, is never inlined into the `generateCode` frame that every scope awaits each child's code in; and a value either holds across an `await` is one it needs after it. A change to either is measured on a wide graph (the generate benchmark's `E6d` shapes) as well as a deep one.

## Places

A place is a position in a root's tree that the body's ordered walk (ordered children, depth first) reaches. A scope's cached plan is reached once for each place that holds it, so a place is never a scope's or a generator's identity. The emitter marks each place with what the type key reads of it (`PlacePlan.record`); a fill is a place with no record, holding the plan `generateFillCode` returns. A seam's hole site is a place written as text whose record lists every value it reads – the builder struct or level it calls a member of, a run struct, each payload field – the function it declares to build a wrapper (`declaredFunctionNames`), and no binding besides its property, since the payloads bound at its path are places of their own, as a scope's are (`ScopeGenerator.holeSitePlace`; where a loop's box holds them, its text binds them too), or no reads where one is of a struct no binding of the seam's tree types, such as the one a fill is handed; every test checks each record against its text (`HoleSiteRecordObservation.checkingRecords`). The type key lays out a seam's own tree as a root's: the narrowest tier's body, its parameters and builders declared around it (`TypeKeyBody.statements(ofRootBody:outerDeclarations:namesInScope:)`). A call of another module's seam built by value is a text place listing its arguments' reads (`seamCallRecord`); an alias bound to `nil` lists no reads. Text places share only where each read's declaration spells one type exactly (`readsDeclarationOfSameType`). The member calls bound at the top of a `@Sendable` builder function are places too (`ScopeGenerator.memberCallPlaces`), alias records reading the struct the call is made on, so a place built in that function shares as a payload binding does. A loop member's rebinding of another member (`ReceivedBuilderLoops` in `cycle-generation.md`) is a cycle-closing place on that member's builder function (`ScopeGenerator.LoopRebinding`), which the key resolves as Swift resolves the name, so the functions of screens that receive the instantiator a type above declares are laid out once per type, not once per path; where no view of a member that wraps another again stands for several places, the root keeps the path key's body, so a loop the path key writes once keeps its nesting (`loopRebindingBodies`). A member whose own statements call only its siblings’ functions, declared in the body that declares it, with no cycle parameters and no closer beneath its body, is keyed by the kind of each closed-on declaration rather than its path (`closedOnFunctions`), and each of its places’ calls is checked against the siblings of that place’s own parent (`checkCall`, `edgesOfSibling`); without that, each layer’s view would name the layer above it and the views would grow with the depth. A scope the key cannot plan (`isPlannedByTypeKey`: value bindings, a builder loop's box, payloads bound for its members, or a rebinding that is no wrapper made again of a member's own builder function – one of a `__safeDI_<label>_received` function, of a rename, or of the function's own property with its cycle parameters – a fill, and member calls outside the shapes `separatesMemberCalls` admits: a seam call, a cycle-closing scope, a fill's child, a `_received` function) is written per path with the tree around it. A function a seam call declares that captures nothing of the code around it is a root function (`RootFunctionRecord`), which the root declares once, at its top, for every call that declares it (`RootFunctionHoisting`): a dispatcher, and a fill that binds only what its dispatcher hands it (`ScopeGenerator.fillRootFunction`: no builder passed up, no cycle closed on a declaration, no inner scope, every receive a handed field), keyed by its text with the root functions it holds left out, so every copy of a name is one function; a dispatcher whose case reaches an enclosing call's fill calls it by name. A name seen with two keys, inside a `@Sendable` function it cannot be declared in, or calling a name kept in place stays where its call declares it, and the root statement holding it is written with the path key's code while every other statement of the root is still laid out by type (`TypeKeyLayout.keptRootFunctionNames`). A function the root declares is marked `@Sendable` where a `@Sendable` function calls it, a fill that stays in its call included (`ScopeGenerator.fillFunction`). On the erased-screen fixture with cycles this took App from 1,159 functions to 162 at 16 screens, one per screen and builder. A fill that captures the caller's values stays per call. Every such fill, a root function or not, binds its fields and calls a shared body (`sharedFillBodyFunction`), one rule for every fill: the body takes the fields it reads, is named by the hash of its text (the row above), and is a root function, so fills of places at two levels, or of calls at two depths, whose trees write the same text call one function, which the root lays out by type (`TypeKeyBody.statements(ofFunctionBody:…)`, leaving out the root functions the root declares beside it). A body is shared only where a field it binds gives each form the fill reads (`sharesFillBody(handedParameterFields:)`); a fill that reads the caller's wrapper keeps its body, and its dispatchers, in its call: a deliberate gap, a body per call, until a shared body takes the caller's read as a parameter. A mock declares once, before its tree, each body its calls' fills hold that holds no root function and calls none (`declareFillBodies(of:isInsideSendableFunction:)`), and leaves in its fill, as a root does, one reached with two keys or inside a `@Sendable` function it was not written for (`RootFunctionHoisting.recordsDeclarableWhereReached(in:)`). Old and new layouts are compared by diffing `generate`'s output against a build of the base commit, never by an oracle kept in the tree.

## Where the ports live

In `Sources/SafeDICore/Generators/Emission/`:

- a construction's call and an erasure wrap: `ConstructionTarget`, `Expression`;
- a binding's annotation: `BindingDeclaration`, one rule per form;
- where an argument comes from, and a caller's argument per form: `ArgumentSource`, `CallArgument`;
- a builder function's statements, and whether it writes `return`: `BuilderBody`;
- a root's initializer: `RootInitializer`;
- the conditions of a fill's inlining that read no text: `FillInlining`;
- a fill's rebindings of the caller's mock root names: `FillCallerReads.mockRootRebindings(rootBindingNames:)`;
- a loop member's box and `_received` names: `LoopMemberNames`;
- the plan these spell into: `GeneratedCode`, `BuilderFunctionGraph`, `Statement`, `BuilderNode`, and `BuilderKey`, whose `place` is the walk's index.

A mock's builder functions keep their own `return` rule, and the two mock rows above keep their text tests, until the mock body is planned: the mock body is rewritten then, and its configuration structs before it.
