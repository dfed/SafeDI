# Graph fuzzer: known issues

Continues `fuzzer-overview.md`.

`knownIssues` lists every corpus seed that fails today, grouped by shape. One listed shape is intended, under signatures that read the base corpus's value oracle's failures (`valueOracleFixtureRejected`, `mockBuildsOtherValuesThanProduction`): a root's mock rejects, as hidden, an unfulfilled `onlyIfAvailable` receive of a label a closer declaration holds with another type, which production accepts in the same tree, since a mock keeps rejecting a tree that repeats a label along a branch, so its 24 seeds stay listed with no fix to come. A known rejection of the value-oracle fixture, or a known failure of it to compile, masks no later failure of the oracle's chain that the known issue does not document (`GraphFuzzerFinding`), since the wrapper, multi-module and rename oracles still judge the drawn graph, so a seed that also changes under a renaming is listed under an entry with both signatures; no known failure of any kind masks a renamed graph's difference (`GraphFuzzerFinding`), and each one the known issue does not document is a finding of its own (`GraphFuzzerFinding.findings`), with the difference on its line of the report; a rejection is documented only when every error line the tool reports contains one of its rejection signatures' text (`GraphFuzzerFailure.rejectionErrorLines`). `seamKnownIssues` inherits no shape whose every signature reads the base corpus's value oracle (`isBaseCorpusValueOracleShape`), since no other corpus runs that oracle, and inherits none of the seeds of an entry with both signatures below its size (`seamCorpusSeedsOfOtherShapes`). `knownIssues` also lists the graphs whose output changes under a renaming, grouped by what changes, which a signature names exactly (`GraphFuzzerOutcomeDifference.Aspect`), so a graph that shows two is documented only by a shape with both signatures. A generated mock or configuration file's difference is classified from the two outcomes in one place (`aspects(ofCodeInFileNamed:code:otherCode:comparedBy:)`, reading `GraphFuzzerMockDifference`, each outcome's code parsed with SwiftParser): the order of a mock's parameters and fields (`.mockParameterAndFieldOrder`: only the lists the generator sorts by label and then type move, each element whole, and a list that moved must be in that order in each outcome's own naming, within each stretch holding the same elements for a mock's own parameters, whose forwarded, received and uncovered groups the code does not tell apart), or which configuration fields a lazy cycle's mock has (`.mockConfigurationFieldPresence`: a field on one side only, its owner having neither its label nor its type on the other, whose type reaches its owner through the fields of the outcome that lacks it, when the renaming changes the order of two types that decide where `computeCycleEdges` enters the cycle: its owner, its type, those a configuration shows to reach them, and those no configuration names, read from the fixture). Each read of a dropped field that goes with it must be the path its node's place implies; an override it discards hands its builder its construction's arguments, erased as a struct node or a leaf is. Where the two outcomes cannot show a reason exactly, the difference is reported; a file that shows both is both aspects, as two differences. Anything else is `.mockCode` or `.mockConfigurationCode`, which no entry lists: a difference that is neither reason is a finding, and an entry is never widened to swallow one. A listed seed's entry also says what the graph shows: a renamed graph's difference the entry lists and the graph does not show is a finding (`staleRenamedGraphDifference`, a `misfiled` line of the report, since the graph still fails), so the seed moves to the entry that names exactly what it shows. The mechanism's tests use known issues of their own, so they do not depend on the list. Each shape has a one-line reason and its signatures, the ways it is known to fail (`GraphFuzzerKnownIssue.Signature`): a change under a renaming or an oracle's failure, as above, or, on no listed shape today, a fixture the macro rejects, compiler errors containing a given text, compiler warnings in generated code containing a given text, or a compiler crash in a generated mock (Swift 6.2 crashed on a mock shape that Swift 6.4 diagnosed). In the long run, a known seed that fails with one of its shape's signatures runs inside `withKnownIssue`; one that no longer fails is reported as stale, and one that fails any other way is reported as a new failure, so a fix's own pull request shows the entries it makes stale. Each seed is listed once, in increasing order within its shape, below `corpusSeedCount`, which `knownIssues_listEachSeedOnceInIncreasingOrder_belowCorpusSeedCount` checks; `publicMockKnownIssues` is checked so below `publicMockCorpusSeedCount`, and its signatures read a change under a renaming or a public mock oracle's failure (`publicMockBuildsOtherValuesThanKnownRight`; no shape lists `publicMockRejectsGraphKnownRightAccepts` today). To add one, add the seed to its shape's list, or add a shape. Every failure the fuzzer finds becomes a hand-written regression test (reduced to the types that matter, with full `==` output) before its fix, and removing the entry is the last step of the fix. Each also gets a row, with its draw and oracle, in `Tests/GraphFuzzerFindings.md`.
