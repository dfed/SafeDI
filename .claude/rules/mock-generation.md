# Mock generation specifics

- **Share logic between production and mock paths where possible.** Validation, scope population, and other shared concerns should live in common helpers rather than being duplicated between `createTypeDescriptionToScopeMapping` and `createMockTypeDescriptionToScopeMapping`. When adding validation to one path, check whether the other path needs it too.
- **Selected construction initializer.** `InstantiableVisitor.canonicalConstructionInitializer` is the single initializer SafeDI selects for construction (first init that fulfills the type's dependencies). `Instantiable.initializer` is populated from it, and mock generation emits against its signature. Validation that only matters for the path SafeDI uses (e.g., diagnosing `Self.*` in default expressions) should gate on this — walking every entry in `visitor.initializers` false-positives on unused overloads.
- **Two-layer mock return type** (extension-based `customMockName` only). When a `customMock` method returns a type different from `Self` (permitted via `fulfillingAdditionalTypes`), two concerns have to agree:
  1. **Inner closure type** (`MockParameterNode.builderClosureType`) — the type of the override closure stored in the parent's `SafeDIMockConfiguration`. Uses the property type so callers writing overrides match the receiving slot. Fixed in #251.
  2. **Outer `mock()` return type** — the generated `mock()` wrapper must return whatever the user's `customMock` returns. Fixed in #266.

  When touching extension-based types with `customMockName`, confirm both layers. `mockReturnTypeIsCompatible(withPropertyType: concreteInstantiable)` distinguishes genuine hand-written mocks from mockOnly-inherited ones.

  A mock that returns one of the type's additional types builds only properties `mockReturnTypeIsCompatible` accepts, so the type is built with its mock for some properties and with `init` for others, yet mocks generate one `SafeDIMockConfiguration` per concrete type, from the first node that needs it. `generateMockCode` therefore rejects (`validateConfigurationsAreBuiltOneWay`, a `SourceDiagnostic` at `mockDeclarationLocation`) a type whose first mock-built and first `init`-built nodes across all roots, in root order, both read a struct and differ in `MockParameterNode.configurationRequirements` (child properties, default parameters by label and type, builder parameter types). A node beneath a `cycleEdges` edge reads no overrides from its struct (its parent's struct has no field for it), so `collectConfigurationNodesByConstruction` leaves it out, and when the first node of a type is such a node built the other way, the struct is generated from the first node that reads it instead. A node that needs no struct is built from a closure typed by its property, so the shape #419 made compile, a mock that takes nothing, stays accepted, as do a mock with exactly `init`'s parameters and a mock that returns the concrete type. An extension's `instantiate(…)` plays `init`'s part: its default-valued parameters are struct fields (#452), so an `instantiate`-built node can read a struct and conflict too, and the diagnostic names the construction by `MockParameterNode.isExtensionBased`. Never emit a second struct for the same type. The struct's default-valued fields take their defaults from the hand-written mock's parameter of the same label and type (`DefaultParameter.defaultParameters(of:dependencies:)` on `mockInitializer`, matched to the dependencies of the concrete type's entry), whichever node the struct is generated from and even when no property is built with the mock in this module; `init`'s (or `instantiate(…)`'s) default applies only to a field the mock declares no default for, so `configurationRequirements` compares labels and types, never values. A node built with `init` beneath a `cycleEdges` edge, which no override reaches, elides its labeled defaults except those the mock also declares (same label and type), for each of which it passes `<Type>.SafeDIMockConfiguration().<label>` (`callSiteArgumentsForPrunedOverride(handWrittenMockDefaultParameters:)`, `MockContext.handWrittenMockDefaultParameters`), so the default is the mock's, evaluated in the struct, as for every other property of the type. Never inline the mock's default expression at the call site: it can name the type's static members or nested types, which resolve inside the struct (nested in the type's extension) but not in the mock root's extension.
- **Dependencies a hand-written mock is not passed.** A generated mock passes a dependency to the hand-written mock's argument with the same label (`resolveBuilderArguments`, `generateReturnArgumentList`). A mock merged in from a `mockOnly` declaration may have no argument for some of the production declaration's dependencies (`Instantiable.dependenciesNotPassed(to:)`, which never lists a `@Forwarded` one: it is an argument of the type's `Instantiator`). `createMockTypeDescriptionToScopeMapping` gives every property built with that mock a scope whose instantiable declares only the rest (`Scope.dependenciesLeftOut` records what was removed), so the dependency is not built, received, promoted, or offered as an override, and the mock declares no value it never uses. A dependency left out is built after all when the tree of a dependency the mock is passed receives its label, which is known only from the scopes, so the mapping is built again until nothing more is found. A mock that returns one of the type's additional types builds only properties of that type; the others are built with `init` from the complete scope, so one concrete type can have two scopes. The mock root's own instantiable is filtered to the dependencies of its scope, or a dependency its scope does not build would surface as a flat `mock()` parameter.
- **Hand-written `mock` vs. generated `mock()`.** A type whose `mock()` this module generates (`generateMock: true` or `additionalMocksToGenerate`) must not also have a hand-written method named `mock`, wherever it is declared. The macro enforces this within one declaration; `DependencyTreeGenerator.generateMockCode` enforces it across declarations and modules (a `mockOnly` pair) when it creates mock roots, by name only — no signature analysis, because a `mockOnly` extension's mock defaults every parameter, so even "distinguishable" pairs leave `Type.mock()` ambiguous. Do not work around such pairs at the call site (e.g. coerced function references). `Instantiable.mockDeclarationLocation` locates the diagnostic and must travel with `mockInitializer` through every merge.
- Names bound for receivers are tracked by label and then type: the disambiguation maps (`[String: [TypeDescription: String]]`) – `flatParameterDisambiguationMap` for renamed flat parameters, overrides, and sibling bindings, `lazilyInstantiatedBindingNames`, and `uncoveredDependencyNames` – give the name a receive of that label and type is handed.
- A receiver whose label was disambiguated is rebound to the disambiguated name (`emitReceiverBindings`), found by its declared type and then its unwrapped type, since an `onlyIfAvailable` receive of `x: X?` is fulfilled by a disambiguated `x: X`. A receive the node passes `nil` (`MockParameterNode.unavailableProperties`) is not rebound: the name may not be declared yet.
- `TypeDescription.asIdentifier` produces identifier-safe disambiguation suffixes
- `TypeDescription.simplified` strips wrappers for cleaner suffixes, with fallback on collision
- Closure-typed defaults use `@escaping T = default` (not `@autoclosure`). A parameter declared `@escaping` is of a function type, the only kind Swift accepts the attribute on (`DefaultParameter.isDeclaredEscaping`), so a configuration that is not `@Sendable`-typed takes it `@escaping` even when its type is a typealias (`@escaping Handler = {}`); a `@Sendable`-typed one stores such a typealias behind its `@Sendable` autoclosure, as any value, because Swift rejects `@Sendable` on a typealias. SafeDI cannot see that a typealias without `@escaping` is a function type, so a configuration that is not `@Sendable`-typed cannot store a non-escaping one.
- A name a parameter declares `@escaping` is a function type, since Swift accepts the attribute only there (`TypeDescription.nameDeclaredEscaping`), so `init(onTap: @escaping OnTap)` takes `let onTap: OnTap`. Only a bare `@escaping` on a plain or member name matches a property spelled without it: any other attribute or specifier beside it makes another type. Each function generated code declares with a parameter of such a name (a builder function's forwarded and cycle parameters, `mock()`'s forwarded, flat received, and uncovered `@Instantiated` parameters, a public mock's, a seam initializer's) spells it `@escaping`, from `ScopeGenerator.typesDeclaredEscaping`, the names the constructions of its subtree declare so. A subtree's own declarations are enough: a receiver stores what it receives, so its parameter says `@escaping`. The leaf that calls another module's public mock has no scopes for that mock's tree, so `PublicMockCall.typesDeclaredEscaping` hands it those of the mock's parameters that the tree declares so. The leaf that calls a seam has no scopes for the seam's tree either, so `SeamCall.typesDeclaredEscaping` hands it those of the seam's parameters (`SeamSignature.typesDeclaredEscaping`, read from the seam's root generator; part of `settledContent`, and of neither the call shape nor the guard, since a call compiles either way). A seam's `__safeDI_` initializer takes a deferred parameter as an `@autoclosure`, which needs nothing, but the seam's plain initializer takes that value and hands it to the autoclosure, which captures it, so the plain parameter says `@escaping`. A parameter taken by value says so on both initializers, and a hole's scope struct says so for a field its initializer stores by value. `query needs` keeps the bare name, which is what a caller passes.
- **A default-valued `@autoclosure` parameter is evaluated where the mock builds the type.** `DefaultParameter` keeps the declared type (`typeDescription`, `@autoclosure () -> T`), which hand-written-mock default matching and `configurationRequirements` compare, so an `@autoclosure` parameter never matches a plain `T` one, and the value's type (`valueTypeDescription`, `TypeDescription.autoclosureValueType`), which everything else spells. A mock root takes it as `@escaping @autoclosure () -> T` and passes `label()` (`generateReturnArgumentList`); a `SafeDIMockConfiguration` takes it as `@autoclosure @escaping () -> T` (`@Sendable` when the struct is), stores `() -> T`, and every construction site reads `field()` (`resolveBuilderArguments`), so an `Instantiator` evaluates it once per instance, as production does; a builder closure takes `T` (`MockParameterNode.builderParameterTypes`). A public mock takes it as `(() -> T)? = nil` (`DefaultParameter.publicMockForm`), resolved to `{ <default> }` in the declaring module and called where it builds the type, also in a public configuration's construction function. A parameter already `@escaping @autoclosure` is passed the call the same way, which the type wraps again. A throwing `@autoclosure` is not supported: the call has no `try`.
- **Flat parameters default to the mock the tree would build.** A flat `mock()` parameter – a `@Forwarded` property of the mocked type, or a received dependency the mock cannot build (`MockRootParameters.flatReceivedProperties`) – defaults to `<Type>.<mock>()` (`ScopeGenerator.FlatParameterMockDefault`, from `DependencyTreeGenerator.flatParameterMockDefaults(in:emittingModule:)`) when the mock scope map's scope for the parameter's type – the slot, so a forwarded protocol finds the conformer or `mockOnly` fake that holds it, under the map's precedence – has a hand-written mock compatible with that type that takes no required argument, and this module can call it: the `Construction(usesMockMethod: true)` check `inaccessibleConstructions` runs, asked as a predicate, so a mock this module cannot call leaves the parameter required and reports nothing. A public mock applies the same rule, from its declaring module, and takes such a parameter as `T? = nil`, `nil` calling the mock; the guard hashes it like any other default, so a caller that computes the module's predicate otherwise fails at the call. A construction initializer's default for a forwarded label wins. Another module's public mock a tree calls is not hand-written, so no parameter defaults to it. `MockRootParameters` carries the defaults (`forwardedParameterDefaults`, `flatReceivedParameterMockDefaults`), which `generateMockRootCode`, the public mock's plan and findings, and `query needs` all read.
- **Which type a mock builds for `fulfilledByType:`.** `DependencyTreeGenerator.mockScope(instantiating:as:in:)`, passed the dependency's `asInstantiatedType`, decides it, and the mock scope map (`createMockTypeDescriptionToScopeMapping`), the forwarded-property validation of a mock root's children, and public mock holes (`fulfillingMockScope`, through `Hole.instantiatedType`) all read it: the named type's scope, as production builds it, unless the property type's entry is a `mockOnly` declaration of another type (a fake of the protocol wins) or the named type itself (its hand-written mock may return the property type); a `mockOnly` extension of a type with a production declaration is merged into it (`mergedWithMockProvider` keeps `mockOnly` false), so it is that type's mock and does not replace the named type; the property type's entry only when the module sees no declaration of the named type, so a module that inverts the dependency keeps building the property. Received dependencies are unaffected: a receiver matches by its own type.
- **Received erased types.** `generateMockCode`'s `erasedToConcreteTypeMap` lets a mock root promote a received type no `@Instantiable` fulfills (e.g. `AnyService`) by building the concrete type an `@Instantiated(fulfilledByType:, erasedToConcreteExistential: true)` property of that exact property type names, in any module. It is keyed by the full property type, because a receiver matches by type, so an `ErasedInstantiator<(), AnyService>` erasure never counts toward `AnyService`. A type that erasures give more than one concrete type is left out of the map, and its receivers become required flat `mock()` parameters: picking one would depend on dictionary iteration order. Production never consults the map — production receivers get the value from an ancestor.
- **An `@Instantiated` dependency the mock cannot build is still declared.** `Scope.propertiesToDeclare`, which `ScopeGenerator` and the received-property walk (`ScopeDeclarations`) both read, includes `Scope.instantiatedDependenciesNotGenerated`: the type's `@Instantiated` dependencies no scope builds, which `mock()` takes as parameters. A receive of one beneath its type is therefore subtracted there, as production subtracts it, instead of reaching the mock root as a second parameter. Emission hands those receivers the parameter's final name where it enters the type's builder function, or the mocked type's whole tree for its own (`routingReceives(of:toParametersNamed:in:)`, beside `removingRenames`), and a receiver rebinds a parameter named apart. A receiver that is not beneath the type, such as its sibling, receives from above the mocked type and keeps a parameter of its own. A promoted sibling of the mocked type receives the mocked type's own such dependency by value, as its own created properties are one instance, and a receive of its `LazilyInstantiated` is wrapped around the parameter (`lazilyInstantiatedReceivedProperties` admits an instance in `mockedTypeUncoveredProperties`), never taken as a wrapper parameter or override. The instance of a wrapper the mocked type instantiates and the mock cannot build provides only that wrapper (`isProvidedByTreeByValue`): a promoted sibling's receive of the other wrapper kind takes the instance as a parameter or an override, as the mock builds a wrapper of each kind beside one it builds. That asymmetry is production's: a wrapper declaration provides itself and its instance only, so production rejects a receive of the other kind beneath it, and such a receive can only come from another declaration – another instance – while a promoted sibling's same-kind or by-value receive gets the mocked type's own property, as a receive beneath that declaration does. A promoted dependency stands for one built above the mocked type, so `createMockRootScopeGenerator` validates each promoted scope's tree for hidden received dependencies with the walk an additional mock's tree gets, rooted at that scope with its tree's received properties bound, so that the mocked type's own declarations hide nothing in it; a tree that passes is validated once across mock roots (`promotedScopesValidatedForHiddenReceives`), and one that fails is walked by every mock root that promotes it, so the errors reported never depend on the order mock roots are created in. Production never has such a dependency: `validateReachableTypeDescriptions` rejects it before scopes are built.
- **A parameter several types create is documented.** `generateMockRootCode` and each tier of a public mock put a `- Parameter` line above `mock()` for each flat parameter more than one type creates (`UncoveredParameter.sharedValueDocumentation`), listing `creatingTypes`: the mocked type, then its tree depth first, each type's children as it declares them rather than as they are built, each type once. A `@Sendable` autoclosure gets none, since each type calls it and nothing is shared, and neither does a public mock's builder for a hole, which is per site. The parameter's name has no backticks, because Swift's documentation parser reads it as plain text. The line offers only a `mockOnly` fake, the one route true of every listed type: `safeDIOverrides` has no entry for the mocked type or for a type beneath a `cycleEdges` edge, and an override leaves the types beneath the overridden type that receive the dependency holding the parameter. The Manual gives the override route with those limits.
- **What a tree node provides.** One definition decides whether a scope provides a property to the scopes beneath it, so they do not receive it from its ancestors: `ScopeGenerator.provides(_:declaredProperties:forwardedProperties:)`. The scope declares or forwards the exact property, or, for an optional property, its unwrapped form, and a lazily instantiated property is declared (and forwarded) together with the by-value property of its instance (`declaredLazilyInstantiatedInstanceProperty`). `generateMockRootCode` drops a received property from its parameters and overrides only when its tree provides it by that definition, or when a promoted node's optional property is the receive's optional form, since a mock binds a node it builds to a non-optional value. A same-label node of any other type provides nothing: the receive stays a flat parameter or override, named apart from the root's tree bindings by label and type (`user_Draft`). Never match a received property to a tree node by label alone.
- **`onlyIfAvailable` overrides are keyed by label and type.** `generateMockRootCode` makes one `OnlyIfAvailableOverride` per `onlyIfAvailable` received property that no forwarded property or required receive covers and the tree does not provide (the mock root's own `x: X?` is handed a promoted `x: X`), even when a root tree node shares its label with another type: handing that node over is wrong (a promoted `editor: Editor` passed to its own `editor: Draft?`). `onlyIfAvailableOverrides(for:namedAfter:namesInMockScope:reservedNames:)` names the field and the binding by the bare label unless the label is a forwarded, default-valued, or uncovered-`@Instantiated` parameter, a root tree binding name, or another override's label; those are named by `identifierSafeNames` from the optional type (`user_Draft`). A flat received parameter or root alias that shares an override's name is still the one renamed, so mocks without such a clash are unchanged. A renamed override joins the flat renames in the receivers' disambiguation map, and `removingRenames(hiddenByDeclarationsOf:parameters:from:)` drops a rename wherever a nested scope declares or forwards that property (or its non-optional form), so such a receiver resolves to the closest declaration, as in production. The mock root's own renamed receive is rebound to its label at the root scope, unless the root binds that label already (to a node it promotes for another receiver); the root is then passed the renamed binding directly through the return's disambiguation map. Only promotion creates these clashes: when the mocked type's own tree hides the label, `HiddenReceivedProperty` rejects it before generation.
- **Values reaching a `@Sendable` builder function are taken as `@Sendable` autoclosures and called inside it.** A `@Sendable` builder cannot capture a value whose type is not `Sendable`, and SafeDI cannot tell whether a type is, so a labeled default-valued parameter of a type whose `SafeDIMockConfiguration` is `@Sendable`-typed (`MockContext.sendableConfigurationTypeNames`) is stored as `@Sendable () -> T` behind an `@autoclosure` init parameter and read as `field()` at every construction site (`resolveBuilderArguments`), with a closure literal default parenthesized (`(() -> Void)? = ({})`, `autoclosureDefault`), since Swift reads a bare one as the autoclosure itself, and a dependency the mock cannot build that a type inside such a builder instantiates (`UncoveredParameter.isSendableAutoclosure`) is a `@autoclosure @escaping @Sendable () -> T` parameter of `mock()`, read into `__safeDI_<name>` before any builder function and bound as `let <name> = __safeDI_<name>()` at the top of each scope that instantiates it (`sendableAutoclosureBindings`), so the value is created once per construction as in production and the receivers beneath read that binding. Mocks that no `Sendable` wrapper reaches are unchanged. A constant builder function a closer makes `@Sendable` starts the same extractor an instantiator's does.
- When a mockOnly and a non-mockOnly coexist for the same type, `resolveSafeDIFulfilledTypes` merges them. The `(false, true)` and `(true, false)` branches handle opposite processing orders. Any cross-cutting concern (tracking sets, stale clearing) must be applied to both branches or order-dependent bugs will surface only on CI.

Public mocks are in `public-mocks.md`; the mock rules seams share (a module's own configuration, erased renames of optional dependencies) are in `seam-holes.md`.
