# Cycle mechanisms: validation

This file holds the validation half of the table; the mechanisms generation uses are in `cycle-generation.md`.

Multiple cycle-related mechanisms coexist — keep them distinct:

| Name | Scope | Set by / when | Role |
|------|-------|---------------|------|
| `throwIfInvalidCycle` | Shared classifier | Called from `validatePropertiesAreFulfillable` (production, and a mock root whose children require one another) and `validateMockRootScopeForCycles` (mock) | Judges the cycle, not the property that closes it: rejects a cycle closed by a receive, whatever its hops, unless the entry it repeats is an instantiator as declared (see "Received builder loops" below), and a cycle with no deferred hop (an instantiator kind on the segment from the closing property to the stack entry it repeats; a lazy wrapper, validated as its constant, is never one), and accepts every other cycle wherever a tree enters it, so production and mocks agree (those cycles compile as long as pruning breaks the config-struct recursion). Its callers pass the segment as `propertiesInCycle`; the received-property walk always passes a closing receive, so its outcome never reads the hops. A cycle repeats a stack entry built for the same concrete type (two `fulfilledByType:` declarations of one label and protocol are two nodes), and a receive is of a property still being built only when the nearest providing declaration of its label on the path is the entry it matched (`indexOfEntryClosedOn`, `isFulfilledByNearerDeclaration`): a declaration between fulfills it, as the generated code passes it – a cycle-closing declaration, one built for another concrete type, or a property a type between forwards (`A -> Instantiator<B> -> C`, where `B` forwards `a: A` and `C` receives it, hands `C` the forwarded `a`). The walk of received properties from an `onlyIfAvailable` alias's declaring scope has no nearest declarations of that scope, so there every receive of a property being built is judged as being built. Neither stack walk considers an `onlyIfAvailable` dependency, `@Received(onlyIfAvailable: true)` or an `onlyIfAvailable` alias (`Dependency.canCloseDependencyCycle`): generation passes it `nil` while the property it receives is built (`NearestDeclarations.binding(of:)`, which finds a receive unavailable when a form of its label it reads is being built between the label's nearest declaration and the receiver), a constant or a `LazilyInstantiated` (an instantiator is passed itself where every property on the circle is one: see "Received builder loops") — so `a: A?` under the `a: A?` it is built inside gets `nil` as it does under `a: A`, and so does an alias of `a` only if available. Both walks classify the dependency that closes a cycle with `closingReceive(of:in:)`: a required `@Received` dependency is a receive, and so is a required alias, which receives its fulfilling property — unless its scope creates that property, which the alias then refers to. Do not use `Dependency.Source.isReceived` for this; it is `false` for aliases. The classification decides every closer: an instantiation closing a cycle with a deferred hop is accepted whatever its own kind, a receive never is, and a required alias fulfilled by a `LazilyInstantiated` is a receive of the constant it stands for, rejected exactly as its constant twin is. Production's received walk agrees by another route: `Scope.requiredReceivedProperties` lists a required alias's fulfilling property, with `aliasProperty` so the error names the alias, except one the alias's scope always creates (`createdProperties`: instantiated, forwarded or declared by an alias), which requires nothing of an ancestor. No alias renames another alias of its own declaration (`RejectedRename`, in `validation-boundaries.md`), so nothing on this path follows a chain of aliases within one scope. |
| `validateMockRootScopeForCycles` | Mock graph | Called after `@Received` promotion in `createMockRootScopeGenerator` | Walks the post-promotion scope to catch cycles that only surface once received deps are promoted to mock-root children — through an ancestor only. For a type listed only in `additionalMocksToGenerate`, whose tree `validatePropertiesAreFulfillable` checks for hidden properties alone, it is the only cycle check. A promoted received optional property is built as its non-optional value, so a received or aliased dependency matches either form. An `onlyIfAvailable` dependency closes no cycle: an alias of a property still being built is bound to `nil`, which a receive of it reads. |
| `childrenRequiringEachOther` | One scope's instantiated children | Called after `validateMockRootScopeForCycles` on the mock root, and by `validateChildrenDoNotRequireEachOther` | Cheap check, from the cached `collectReceivedProperties`, for children that require one another (C receives B while B's subtree receives C, directly, through an alias the scope declares, as `b: B?` fulfilled by the unwrapped `b: B`, or through an `onlyIfAvailable` alias in the subtree that a receiver requires and that is bound from B), which no ancestor stack shows. An `onlyIfAvailable` alias is a `let` of its label bound from the nearest declaration of its fulfilling property's label, so a receiver that requires it requires that declaration built first: `ReceivedProperties.requiredAliasFulfillingProperties` holds the fulfilling properties a subtree requires through such aliases, which `ScopeDeclarations.requiredAliasFulfillingProperties(childRequiredReceived:childRequiredAliasFulfillingProperties:)` – shared by the walk's `finished` and `requiredReceiver` – collects in one pass (an alias the scope declares is required when a child's tree requires its property, or requires a fulfilling property of the alias's label that the alias provides a form of; no alias of a scope renames another) and prunes by the labels the scope declares or forwards, never by `provides`: the requirement stops at the nearest declaration of its label, whatever form that has. The check names the sibling that declares the label of such a property with a form the alias reads (`ScopeGenerator.provides(_:aFormReadBy:)`), never the child whose tree the requirement comes from, inside which the alias is `nil` since the property is being built. `ScopeGenerator`'s ordering applies the same rule, so a provider that is a sibling emitted after the receiver's tree is a sibling cycle. A child whose tree receives itself through an alias or unwrapped requires itself; one that receives its own property directly is left to the received walk and the ancestor check, which report it. A mock root binds nothing for a property it declares itself, although promotion collects it into `allReceived`. When the chain closes on an alias of the first child, it ends with the child's own property (`@Instantiated a: A -> @Received renamedA: A -> @Received a: A`); each `onlyIfAvailable` alias in the chain adds a sentence suggesting `onlyIfAvailable: true` on the receive (`RequiredOnlyIfAvailableAlias.hint`), as the received walk's diagnostics through such an alias do. Only a cycle with a property on it that is no instantiator is reported: a child that is none, or a rename that erases one, or one only if available of anything but an instantiator a child builds (`valueAliasProperties`). The depth-first search skips a back edge whose cycle holds only instantiators; when it finds no other, each strongly connected component is searched from each value in it, in sibling order, for a path back to it, so a value that shares its children with a cycle of instantiators is still reported, with the chain through the value. On a mock root it gates production's `validatePropertiesAreFulfillable` walk, which reports constant cycles. Running that walk on every mock root would add a received-dependency walk per node of every mock tree; on a real 250-mock-root app the check triggers it zero times. |
| `validateChildrenDoNotRequireEachOther` | Every scope of the production trees, then of each mock tree | After production's `validatePropertiesAreFulfillable` passes, and after the mock root's walk | Reports, as `dependencyReceivedInSameChainItIsInstantiated` at the receiver found by `requiredReceiver` (the first dependency in the last child's tree that requires the closing property; a required `onlyIfAvailable` alias bound from it – one `ScopeDeclarations.requiredOnlyIfAvailableAliases(childRequiredReceived:childRequiredAliasFulfillingProperties:)` lists – is followed to the receiver that requires the alias, whose hint the diagnostic then carries, for each alias in the chain: the children's trees are searched for the alias's property; the search stops beneath a scope that provides the searched property, as the walk prunes, so it always finds a receiver), children that `childrenRequiringEachOther` finds. It catches what the received walk misses: that walk follows a received property to the scope of its type, so it never follows an `Instantiator`, and no walk covers promoted scopes' trees. Running after the walk leaves every diagnostic the walk reports unchanged. `ChildrenRequiringEachOtherValidation.validatedScopes` makes each scope checked once per production pass and once across all mock roots, since which children of a scope require one another depends on the scope's tree alone; on a mock root, the result `childrenRequiringEachOther` computed for the gate is reported directly and only the children's trees are checked again. |
| `stackPropertiesReliedOnByWalkedProperty` | Received walk in `validatePropertiesAreFulfillable` | Filled as each received property's walk returns without throwing | Memo keyed by received property (not scope: another label of the same type can reach an error the first label's walk bailed before). Stores the properties on the stack the walk relied on (bails on cycles that aren't ours, plus those passed up from skipped walks); a later visit skips the property only when its stack contains all of them, so the first error in walk order is unchanged while paths into an unrelated cycle are not re-walked. |
| `isHanded` (handed values) | Received walk in `validatePropertiesAreFulfillable`, per tree | Asked before the walk descends into a received property's scope | The walk does not follow a received property the tree is handed: one no scope in the map instantiates or renames another property to (`propertiesBuiltByAScope`, built lazily), which in a mock's tree the mock root also does not promote, because the root forwards it or `mockCanBuild` says no. Such a value comes from outside the tree (a `@Forwarded` value or a `mock()` parameter), so its type's receives are no part of the tree; a cycle through them is reported where a tree builds that type. Mocks and production follow this one rule (production's map holding only reachable types was a type-level form of it). Which branch applies is the tree's, not the pass's: the validation of mocks (`cyclesOnly`) also walks every production root's tree, and `ValidatedRootScope.isMock` is `false` for every root of the dependency tree, which receives nothing, so its mock (if any) promotes nothing and builds its production tree; the mock branch is for the trees of non-root mocked types only. Otherwise adding one unrelated `generateMock` type to a module, or `generateMock: true` to a root, could reject a production tree the production pass accepted. A mock whose parameter no caller can build is accepted, as production already accepted such a forwarded value. Over-approximates in a mock: a property forwarded inside the tree whose type the mock could build is followed, since the pre-promotion validation does not know whether the mock promotes it. |
| `walkedAliasFulfillingProperties` | Per `validatePropertiesAreFulfillable` call, shared by its trees | Inserted as the property the last alias a required receive needs is bound from is walked where that alias is declared; removed when that walk throws | Memo keyed by `WalkedAliasFulfillingProperty`: that fulfilling property, the properties received through the required aliases, the receive's own first (they start the walk's stack, where a chain bails out), the last alias's declaring stack, and the mock root's forwarded properties, or `nil` for a tree validated as production (they decide where `isHanded` stops). Two aliases of one fulfilling property, or two chains that end in the same alias, walk differently, so a key without the received properties made a tree's rejection depend on which receiver was declared first. |
| Required receives of aliases in `validatePropertiesAreFulfillable` | Per tree walk | Each node resolves its required receives to the nearest alias declaring them (`ReceivableAlias`), every alias included; a property a scope provides shadows the aliases above it | Each `onlyIfAvailable` alias records what it is bound from where it is declared (`ReceivableAlias.binding`, by the rule generation uses: a property its scope provides, else the nearest declaration of the fulfilling property's label when it provides a form the alias reads and is not the declaration the walk descended through, else what a seam or mock root binds; `nil` binds the alias to `nil`). A receiver built inside the last alias's fulfilling property, where that property is the declaring scope's own child the walk descended through, throws `dependencyReceivedInSameChainItIsInstantiated`, a hint per alias; an ancestor still being built or a deeper instance of the label throws nothing, since the alias is then `nil` or bound from another declaration. Where the last alias is bound from a property the tree builds (`.built`), that property is walked as the declaring scope's own required receive (what the walk does for a required alias); a `nil` or handed binding walks nothing, and a required receive of an alias bound to `nil` is passed `nil`. An `onlyIfAvailable` alias of another `onlyIfAvailable` alias is bound from it, so a receive of it requires every alias along any such chain (`ReceivableAlias.fulfillingOnlyIfAvailableAliases`), followed, where the scope declares no property of the fulfilling property's label, through the enclosing scope's alias a receive of it resolves to (`receivableAliases`, whose chain is already resolved). |

## Received builder loops

A receive of an instantiator that is still being built is accepted: the instantiator's builder function rebinds it (see `ReceivedBuilderLoops` in `cycle-generation.md`). One rule, per scope: a cycle of receives among the properties a scope creates is accepted exactly when every property on it is an instantiator (a `LazilyInstantiated` is validated as its constant, so it is never one). Each check that rejected such a receive skips an instantiator entry: `throwIfInvalidCycle`, the received walk's guard on the scope's own property, `optionalReceiveOfPropertyBeingBuilt`, the required receive of an alias whose fulfilling sibling is being built (a non-erasing rename of an instantiator, required or only if available), the receivable set of a child's tree (an instantiator stays receivable in the tree it builds), `insertProperties`' `isBeingBuilt`, and `validateTreeBuiltAgainByCycle`'s being-built throw. `childrenRequiringEachOther` then reports the cycles with a value on them. A tree a mock generates is validated by the same rule – a non-root mock's tree, a root with `generateMock` in the validation of mocks, an additional mock root, `validateMockRootScopeForCycles`, and the mock trees' `childrenRequiringEachOther` – since mock emission rebinds a loop as production does (`cycle-generation.md`). A receive that closes a cycle is therefore always of a value: `invalidCycleError` reports it as `constantDependencyCycleDetected`, and there is no error for a received instantiator closing a cycle.

Key consequence: in an accepted cycle the closing property is an instantiation (never a receive) and some hop is deferred (Instantiator/ErasedInstantiator-typed); the other hops, the closing property among them, may be constants or lazy wrappers (`a: A` -> `b: B` -> `cBuilder: Instantiator<C>` -> `a` is accepted, closed by the constant `a`). A constant or lazy closer calls the enclosing builder function with its cycle parameters (`let a: A = __safeDI_a(…)`, `LazilyInstantiated<A>(__safeDI_a)`) exactly as an instantiator closer hands it to its wrapper, and `computeCycleEdges` may prune an edge a constant closes, which the pruned node's override path handles as it does for an instantiator (one configuration shape whichever root enters the cycle). Generation finds its cycle-closing scope exactly where validation finds the cycle: by the mapped property and the concrete type (`Scope.createScopeGenerator`'s `concreteTypeStack`), so a constant and a lazy wrapper of one label close on each other in either order, and `closedOnDeclaration` names the declaration repeated – the wrapper when the match was its instance entry, with the concrete type – for every lookup keyed by it (`cycleClosedOnDeclarations`, `cycleClosingRedeclaredLabels`, `BuilderFunctionNames.enclosingFunctionNames`, the cycle parameter contexts, the tier omission passes). A key of the property alone let a declaration of the same property built for another type between the closer and the declaration it repeats claim the reference, and the closer called that nearer function. A mock node reads no override of its own where its type, as instantiated and as concrete type, repeats an ancestor's (`MockParameterNode.cycleNodeKey`). Which property closes a cycle depends on where the walk starts: a tree that reaches a cycle from another root can close it on an earlier lazy property than a walk from the cycle's own root, which is why a filler walks each foreign seam with holes from its root (see `seam-holes.md`).

**`LazilyInstantiated` is generated like an `Instantiator` and validated like a constant.** A `LazilyInstantiated` / `SendableLazilyInstantiated` property (`PropertyType.lazilyInstantiated`, `.sendableLazilyInstantiated`) is emitted as a builder function handed to its wrapper, but its instance is created at most once, so it cannot break a cycle. Every property that enters the cycle logic – in `validatePropertiesAreFulfillable` and in `validateMockRootScopeForCycles` – is first mapped through `Property.asValidatedForDependencyCycles`, which turns the wrapper into the constant it stands for. `throwIfInvalidCycle` sees it as a constant hop, and a tree is valid with the wrapper exactly when it is valid with that constant. Never classify these properties as lazy hops: generated code reads `.instance` for every by-value receiver, so a "fully lazy" cycle through them would recurse with no user code involved, creating a fresh wrapper at each level. `PropertyType.isConstant` is `false` for them, because mock generation uses it to mean "bound without a wrapper", so do not call `isConstant` on a property that has not been mapped. Cycle diagnostics show the constants; `lazilyInstantiatedDeclarations` threads the declared wrappers through validation so the message can name them.

**The walk of a tree a cycle builds again stops where nothing the tree reads is new to it.** `validateTreeBuiltAgainByCycle` visits a tree once per path a cycle re-enters it by, which on a dense lazy cycle is exponential. At its start and before each child it pushes, it stops unless the tree reads a label new to it there: one of the new labels, or the label of a new receivable property (`labelsRead(inTreeOf:)`, `treeReadsAnything`). The walk has two judgements, the hidden-label record (`recordHiddenReceives` with its changed context) and the being-built throw, and each fires only for a receive whose own label is new there; what is new only shrinks going down the walk, since a new label is removed where the tree declares it again and a new receivable property is added only by an `onlyIfAvailable` receive of a label already new. So a tree that reads none of them has nothing to report on any path, and skipping it changes no diagnostic and no accepted graph. **Any new judgement in the walk must keep the label it reads in that read set, or the skip silently loses it.** The set holds the label of each `@Received` property and of the property an alias is fulfilled by (not the alias's own label), of every scope reachable through instantiated children, cycle-closing scopes included, since the walk continues through them. Keep the form: skip only (narrowing `TreeBuiltAgain`'s key to labels read, and memoizing the walk, each lost diagnostics on random graphs), and each read set a whole pass from the scope asked about with its own visited set and an explicit stack (a recursive memo in which a scope in progress answers empty records partial answers inside a cycle, and recursion overflows on a deep tree). `SafeDIToolLazyCycleReadLabelTests` has a case per way of reading a label.

**A new label no judgement can fire for counts as read by no tree.** `treeReadsAnything` also ignores the labels of `labelsNoJudgementFiresFor()`, so a flow-scoped value redeclared between screens that receive it, with the type they receive, no longer starts the walk. A label is in the set when every declaration of it in the trees of the roots validated (what `enterDeclarations` enters: each property a scope reached through instantiated children creates, aliases included) is one every read of it accepts by `recordHiddenReceives`' own rule (the property or its unwrapped form, an `onlyIfAvailable` alias's `formsReadByOnlyIfAvailableReceive`, and a lazily instantiated declaration's instance), so no closest declaration hides a read; and when no tree built for a property of the label reads it, so no declaration of it is on the instantiation stack where a required receive of it is walked (every stack entry is an instantiated child whose tree holds the reader). The set reads the scope graph alone, never a walk's outcome, so it is a skip like the one above, computed once per `validatePropertiesAreFulfillable(onRootScopes:)` call and only when a walk first finds a read label new. **Any new judgement in the walk must keep `labelsNoJudgementFiresFor` sound: a label stays out of the set wherever the judgement can fire for it.** The walk stays exponential where a new label can be judged (a declaration of it a read does not accept, or a tree built for it that reads it); a rejected build's chains are one per path, so that path cannot be memoized away.
