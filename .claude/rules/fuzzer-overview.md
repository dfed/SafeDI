# Graph fuzzer

`SafeDIToolGraphFuzzerTests` (support code in `Tests/SafeDIToolTestSupport/GraphFuzzer.swift`) generates random graphs of `final class` `@Instantiable` types from a seed (a quarter of them also with one extension-based type whose `instantiate(…)` has default-valued parameters, decided after the rest of the graph so the other types of a seed's graph do not depend on it), with its own SplitMix64 generator so a seed names the same graph on every machine. The oracle runs each graph through `executeSafeDIToolTest` twice in the test process and accepts only two outcomes: the tool reports an error, or the fixture and the generated code compile (`swiftc -emit-object`, as `verifyGeneratedCodeCompiles` does) and the compile the graph passed reports no warning that only its generated code draws (`warningsOnlyGeneratedCodeDraws`, the verifier's filter). Generated code that does not compile or draws such a warning (`generatedCodeDrawsWarning`), a fixture that does not compile on its own (a fuzzer defect), and two runs that differ are failures; a crash kills the test process. The two runs share the process's hash seed, so the long run also runs the `SafeDITool` executable in two processes for every 50th seed and compares them. The oracle also runs each graph under every `GraphFuzzerRenaming` – reversing the order of its type names, of its labels, of its file names, and of all three at once, each a pure rename of single-digit indices (`i` to `9 - i`, files prefixed `F<99 - rank>_`) – and requires, once the renaming is undone textually, the same verdict, the same diagnostics in any order, and byte-identical generated files (`renamedGraphDiffers`). It compares the suggestions a diagnostic lists ("Did you mean one of …") in any order too: the order inside a message is presentation and changes nothing a user does. It compares the comment naming the types SafeDI counts as `public` because it reads no declaration of them by its count in each module, not by its place: a combined output carries it above its first `public` declaration that names such a type, which name order decides. It catches output that depends on which of several equals SafeDI meets first in name order, which two identical runs cannot see. The reversals keep every type name's `S<seed>_` prefix, which sorts after `ErasedInstantiator<`, `Instantiator<`, and `LazilyInstantiated<` and before the `Sendable` wrappers (a digit sorts before `e`), so no reversal changes whether `x: X` or `x: Instantiator<X>` sorts first. A fifth renaming therefore moves type names across wrapper names (`movesTypeNamesAcrossWrapperNames`): it replaces the prefix's `S` with `A`, which sorts before every wrapper's name, or `Z`, which sorts after every one, chosen per seed by each name's kind and index (`T3`, `AnyT3`, `Value`; a type and its `Protocol` move together), wherever the name appears. A quarter of graphs end with a motif drawn after the graph's own types and before the extension-based type (types 7 to 9, so other graphs draw as before) whose output SafeDI must choose for: a lazy cycle of mocked types, promoted siblings that receive each other only if available, one label received as an instance and as an instantiator, several independently invalid roots, or two types in two files that fulfill one protocol. The four reversals cost about 60% more corpus time, and the move is one more run of the tool per graph. Graphs compile together, kept apart by a per-seed type-name prefix (`S<seed>_`), in one `swiftc` invocation per module role: every graph in one module, with the seam's module of every graph split across modules (`GraphFuzzerModule`), compiles as `FuzzFeature` in package `shop`; then the split graphs' same-package callers (`FuzzApp`, `shop`) and other-package callers (`FuzzOther`, `other`), each against the modules before it, a graph that fails in one module left out of the later ones. Every fuzzer compile passes `-package-name`. A graph's wrappers are all `Sendable`, all not, or – in a quarter of graphs – mixed at random, so a `Sendable` builder's subtree can receive a `LazilyInstantiated` declared outside it; a mixed graph's types are `@unchecked Sendable`, and its types that are not `@Instantiable` (the extended type among them) are `Sendable`, so receiving one by value inside a `@Sendable` builder function is never what fails. The oracle compiles in the Swift 6 language mode, where such a capture is an error rather than a warning. A type no root reaches sometimes receives `items` as a wrapper of the graph's `Value` type, which is not `@Instantiable` and which nothing provides, with the wrapper chosen for each receive, so a mock's tree receives one label as several wrappers its mock cannot build. A type no root reaches also sometimes instantiates a constant of a type that is not `@Instantiable` (`addingDependenciesMocksCannotBuild`), which its mock takes as a parameter, and a pass drawn after every other base pass but one, with its own generator (`addingReceiversOfDependenciesMocksCannotBuild`), now and then gives a type built beneath that owner – one it instantiates, or now and then one that type instantiates – a receive of the constant, required or only if available, which the mock must pass that same parameter (`dependencyMockCannotBuildReceivedBeneathItsOwner`). With a generator of its own, the pass also now and then makes an owner with `generateMock: true` receive a type of the graph that receives the constant by value or as its `LazilyInstantiated` or `SendableLazilyInstantiated`, required or only if available; a mocked owner's mock builds that type beside it and must wrap the parameter it takes rather than take the wrapper (`dependencyMockCannotBuildReceivedLazilyBesideItsMockedOwner`). In a mixed graph the owner now and then lazily instantiates the constant as one wrapper while that type receives the other kind, which the mock must make from an instance it takes (`dependencyMockCannotBuildLazilyInstantiatedReceivedAsOtherKindBesideItsMockedOwner`), and now and then the type instead instantiates a type of the graph under the constant's label above a receiver of the constant, which the tool must reject as hidden. The oracle checks that rule in every accepted graph: a generated `mock()` takes a `LazilyInstantiated` or `SendableLazilyInstantiated` parameter only for a property the mocked type forwards or instantiates (`mockTakesWrapperParameterForReceive`). Types also receive the erased instantiators an ancestor instantiates, with exactly the type it declares, and some forward one. A tenth of graphs end with a chain of aliases through an `onlyIfAvailable` alias (`addingAliasChains`, a pass with its own generator, so every other graph is drawn as before): a second alias, required or `onlyIfAvailable`, of an `onlyIfAvailable` alias a type declares or is given, on a type it instantiates, now and then a third on a type that one instantiates (the macro rejects a rename of another rename of one declaration, so no draw puts two links on one type), and usually a receive of the last on a type beneath it. The second pass never aliases an optional property, so no other graph has such a chain unless `addingSiblingAliasChains`, below, draws one; a receiver that requires the last alias needs every alias created, so the first alias's fulfilling property must be built before it, which the rest of the graph can make a cycle (`aliasOfOnlyIfAvailableAlias`). That pass draws the first alias's source from the properties provided above every path to its host, never one built around it, so it never draws the sibling cycle PRs 472 and 481 fixed. A last pass with its own generator (`addingSiblingAliasChains`, three rolls in ten, about 170 corpus graphs) draws that cycle: a scope – a root, or a type on every path to the chain – instantiates `x: X` as a constant and another type `B` without an instantiator; `B`, or a type a few such steps beneath it that each step dominates, declares an `onlyIfAvailable` alias of `x`, mostly spelled with its optional form (`ofType: X?.self`, `aliasOfOptionalFormOfProperty`); now and then one or two aliases of that alias follow, required or `onlyIfAvailable`, each on a type beneath the one before, so that the chain crosses scopes at every link; usually a type beneath the last alias's type receives it, mostly required, or a required alias of it on a new type beneath does instead; and usually `X` receives `b`, so that `b` must be built before `x` while the chain needs `x` first, which the tool must reject through the chain (`fixture_makesSiblingsTypeReceiveTheOtherSibling_forSeed4224`). A type beneath another is a child it dominates, judged from the declarations rather than from `dominators` (a root now and then declares a property the other roots lack, which the graph's edges do not hold), or, where it has none, which is most often, a new type only it instantiates (`Link0`, `Link1`, …), so a receiver is not rejected merely because another path from a root reaches it without the alias. Without the receive of `b`, the chain must be built after `x`, which the compiled output shows (seeds 731 and 2420, in the smoke batch, whose chains pass through child scopes). One pass more, after `addingReceiversOfDependenciesMocksCannotBuild` and with its own generator (`addingErasedRenamesOfOptionalDependencies`, a quarter of graphs, about 130 corpus graphs), gives a type a root reaches or whose mock is generated an erased rename of an optional property of a type of the graph that is provided above every path to it (`ofType: X?.self, erasedToConcreteExistential: true`), required or now and then `onlyIfAvailable`, and, in about half of those graphs, a receive of it on a type it instantiates: a host that instantiates a type of the graph, when there is one, is chosen seven times in ten, and always gets a receiver (`erasedRenameOfOptionalDependency`; seed 2314, in the smoke batch, renames an optional alias, which a type beneath receives only if available). `aliasProperty` never aliases an optional property and the passes that spell `ofType: X?.self` never erase, so no other pass draws it.

- **Every pull request.** `ci.yml` fuzzes each corpus whole – the base corpus, seeds `0..<corpusSeedCount`, the seam corpus, seeds `0..<seamCorpusSeedCount` drawn with `generateDependencyTree`, and the public mock corpus, seeds `0..<publicMockCorpusSeedCount` drawn with `generateMockPublic` – on every pull request and push to main that changes more than Markdown. "Build and Test on Linux" packages its test bundle; "Fuzz Dependency Graphs on Linux" shards download it and run the long run over parts of a corpus (the matrix names each shard's corpus and features), with batches running concurrently on every core; and "Check Graph Fuzzer Corpus on Linux" combines the shards' reports per corpus, failing when a corpus has no report. A shard fails, naming the seeds in its summary, when a graph fails, a known issue goes stale, the run reports a problem with itself (a changed corpus, an invalid known-issue list, a harness error), the process crashes, or no graph runs. The combine job fails when a shard is missing or reported any of those, when the shards do not cover the corpus exactly once, or when the seeds the tool accepted differ from the pins (`corpusAcceptedSeedCount`, and `corpusAcceptedSeedsSum`, a `GraphFuzzerSeedSetSum` whose parts add up across shards), or when, in the base corpus, the accepted graphs that show a `GraphFuzzerFeature` (read from the emitted source as the smoke batch reads it, whether or not the graph fails as a known issue) differ in number from its pin (`corpusAcceptedFeatureCounts`, which each shard reports and the combine job adds up; a run of the whole corpus checks them itself), or when a complete report names its corpus without that corpus's per-feature counts or the value oracle's inspected count, which every long run writes, so a run that stops writing either line cannot skip its check. The oracle takes any error the tool reports as a valid rejection, so a tool change that makes it accept or reject other graphs must update those pins deliberately. Unit tests leave the siblings of a shape the corpus draws to the corpus, and the per-feature pins are what show the corpus still draws it: a generator or tool change that changes them updates them deliberately, and a feature whose count falls below ten no longer stands in for the unit tests of its shape. A sibling whose defect compiles to a wrong value (a second instance, a farther one, `nil`, or a value where production passes `nil`) is left to the base corpus's value oracle instead, whose `GraphFuzzerValueOracleShape` pins show the corpus still compares pairs whose trees hold its shape, under the same rule of ten; a shape is counted wherever the model finds it in a compared pair's tree, including receivers the comparator never reaches (behind an `ErasedInstantiator`, behind an instantiator with forwarded properties, or an `Instantiator` whose sharing the describer cannot see), so a cut's evidence is its family's mutation run, which shows in how many pinned pairs the comparator detects the defect. The fixed seeds make every failure deterministic, so it belongs to the change that caused it. Measured before the base corpus's value oracle: the shards added about 3¼ minutes after "Build and Test on Linux", cold or warm, since they run its bundle instead of building, and a base shard fuzzed 2500 seeds in about 2¼ minutes before the multi-module property, which adds about a quarter. Each of the four base shards now fuzzes 1250 seeds, multi-module property and value oracle included, in a time not yet measured on CI (the stop rule is 3½ minutes per shard); the seam shard's 1000 and the public mock shard's 1000, 2 to 4 minutes on an eight-core Mac, are not measured on CI either.
- **Ordinary suite.** Compiling generated code is what the fuzzer costs, so the ordinary suite keeps it, for the base and seam corpora, to forty-six small `swiftc` invocations – the base smoke batch, its value comparison (a compile of its one path and a link), the seam smoke batch's three compiles (one per module role) and its value comparison (for each of its three module layouts, a compile of each module and a link of each path), seven from the two compile-failure tests below, one from the one-type probe of `results_reportIntegrationsDiffer…`, nine from the two tests that hand `GraphFuzzerOracle.valueFailures` a seam build passing `nil` and one that does not compile (two comparisons of a compile and a link of each path, and one failing compile), and four from the two tests that hand the base corpus's value oracle a generated mock edited to build a second instance or to pass `nil` (a compile and a link each) – plus the two that compile the SafeDI runtime and the describer once per process, which the comparator's own tests share (the generation tests' own compile verification is apart from these); the public mock corpus's smoke batch (`publicMockSmokeSeeds`: a compile per module role and a value comparison per module layout) and its compile and value self-tests add theirs. It is what `swift test` gives a developer locally. A small fixed batch (`smokeSeeds`, eighteen seeds) must have no failures, exercise every `GraphFuzzerFeature` (detected from the emitted source, and `constantCycleCloser` from the generated code, since which dependency closes a cycle depends on where a tree enters it) in graphs the tool accepts, include both accepted and rejected graphs (at least a quarter of each, rounded down), and compare a root pair and a mirrored pair showing every `GraphFuzzerValueOracleShape` the corpus shows. `compilationFailures_reportEachBrokenGraph_whenGeneratedCodeFailsToTypeCheckOrToLowerOrDrawsWarning` and `compilationFailures_reportWarning_whenGraphCompilesOnItsOwnAfterAnErrorThatNamesNoGraph` hand the oracle broken generated code. `fixture_matchesReferenceHash_forSmokeAndKnownIssueSeeds` pins the generator's output for those seeds, and the long run pins it for the whole corpus (`corpusFixtureHash`). Any generator change changes which graph every seed names, so update both hashes, the accepted-seed pins, the per-feature pins, and the smoke and known-issue seeds in the same change – for every corpus: `corpusFixtureHash`, `smokeAndKnownIssueFixtureHash`, `corpusAcceptedSeedCount`/`corpusAcceptedSeedsSum`, `corpusAcceptedFeatureCounts`, `corpusValueOracleCounts`, `smokeSeeds` and `knownIssues` for the base corpus, with its partition hashes `corpusPartitionHash` and `smokeAndKnownIssuePartitionHash`, and `seamCorpusFixtureHash`, `seamSmokeAndKnownIssueFixtureHash`, `seamCorpusAcceptedSeedCount`/`seamCorpusAcceptedSeedsSum`, `seamCorpusValueOracleInspectedGraphCount`, `seamCorpusOmittedValueGraphCount`, `seamCorpusDrawFeatureCounts`, `seamSmokeSeeds`, and the three lists `seamKnownIssues` is derived from, `seamCorpusSeedsOfOtherShapes` (checked to be a subset of `knownIssues`), `seamCorpusSeedsAddedToInheritedShapes` (checked to hold none of `knownIssues`' seeds) and `labelSortedPassThroughSeeds`, for the seam corpus; and `publicMockCorpusFixtureHash`, `publicMockSmokeAndKnownIssueFixtureHash`, `publicMockCorpusAcceptedSeedCount`/`publicMockCorpusAcceptedSeedsSum`, `publicMockCorpusValueOracleInspectedGraphCount`, `publicMockCorpusOmittedValueGraphCount`, `publicMockCorpusErrorGraphCounts`, `publicMockCorpusDrawFeatureCounts`, `publicMockCorpusOutputFeatureMinimumShares`, `publicMockSmokeSeeds` and `publicMockKnownIssues` for the public mock corpus. That the base corpus is drawn as before with a feature off is pinned by those base hashes, not by a test of the draw.
- **Run a seed.** `SAFEDI_GRAPH_FUZZER_STARTING_SEED=<seed> SAFEDI_GRAPH_FUZZER_ITERATIONS=<count> swift test --traits sourceBuild --filter SafeDIToolGraphFuzzerTests/longRun`, or `SAFEDI_GRAPH_FUZZER_ITERATIONS=corpus` for the whole corpus, which then checks the accepted-seed pins itself; add `SAFEDI_GRAPH_FUZZER_FEATURES=generateDependencyTree` for the seam corpus, or `generateMockPublic` for the public mock corpus (`graph-fuzzer.yml` takes the same as its `features` input). Each failure's issue prints the fixture and the compiler output. `SAFEDI_GRAPH_FUZZER_REPORT=<path>` appends progress to a file. The run also checks that no corpus graph uses a label beginning with `__safeDI_`, the prefix of generated builder functions. To explore graphs beyond the corpus, dispatch `.github/workflows/graph-fuzzer.yml` with another starting seed and count.

  `Scripts/fuzz-corpus.sh` runs the long run this way and prints the shard and corpus pin lines from its report.

- **Known issues.** `knownIssues` lists every corpus seed that fails today, grouped by shape. The corpus first found six shapes, and PR 404 made the tool reject one while PRs 407 and 408 fixed the generated code of the rest. Graphs mixing `Sendable` and non-`Sendable` wrappers found two shapes, both resolved: a type below a `Sendable` builder that receives an `Instantiator` declared outside it, which the tool now rejects as it rejects a captured `LazilyInstantiated`, and a cycle through a `Sendable` builder and an `Instantiator`, whose cycle-closing scope referred to the enclosing builder function that was not `@Sendable` (see `buildsInSendableFunction`). Receiving `items` as several wrappers found two mock shapes, both fixed: a mock wrapped the instance it takes for a required `LazilyInstantiated<Value>?` by its bare label when an `Instantiator<Value>` receive of the label renamed that parameter, and a mock that promotes a received `Instantiator<A>?` read it, still being declared, through an `onlyIfAvailable` alias of `Instantiator<A>` in its own tree. Receives beside a mocked owner of a dependency its mock cannot build found two more: a type that receives a label as one type above a type that receives it as another, where the mock rebinds the first under the label inside the first type's builder function, which the tool now rejects in a promoted dependency's tree as production does (`receivedPropertyHiddenInPromotedTree`) and which is open and listed in the mocked type's own tree; and a required receive in the tree of a dependency the mock promotes that was handed the mocked type's optional `onlyIfAvailable` alias of the property, fixed: the mock binds a root alias whose label a flat received parameter has under a name of its own. Failing a graph whose generated code draws a compiler warning found one more, fixed: a mock promoted the optional form of the mocked type's own alias, which a promoted dependency's tree requires, and built a node and an override that nothing read, since the receiver is handed the alias; promotion now skips a receive the mocked type's own alias provides (`ScopeGenerator.provides`). The base corpus's value oracle found two, under signatures that read its failures (`valueOracleFixtureRejected`, `mockBuildsOtherValuesThanProduction`): a root's mock rejects, as hidden, an unfulfilled `onlyIfAvailable` receive of a label a closer declaration holds with another type, which production accepts in the same tree, open and listed; and a root's mock handed an `onlyIfAvailable` alias that a type built through an instantiator aliases again its override, `nil`, where production creates it from the property it renames, fixed in PR 537. A known rejection of the value-oracle fixture, or a known failure of it to compile, masks no later failure of the oracle's chain that the known issue does not document (`GraphFuzzerFinding`), since the wrapper, multi-module and rename oracles still judge the drawn graph, so a seed that also changes under a renaming is listed under an entry with both signatures; a rejection is documented only when every error line the tool reports contains one of its rejection signatures' text (`GraphFuzzerFailure.rejectionErrorLines`). `seamKnownIssues` inherits no shape whose every signature reads the base corpus's value oracle (`isBaseCorpusValueOracleShape`), since no other corpus runs that oracle, and lists none of the seeds of an entry with both signatures below its size (`seamCorpusSeedsOfOtherShapes`). It lists the graphs whose output changes under a renaming, grouped by what changes (mock code, the mock configuration file). The mechanism's tests use known issues of their own, so they do not depend on the list. Each shape has a one-line reason and its signatures, the ways it is known to fail: compiler errors containing a given text, compiler warnings in generated code containing a given text, or a compiler crash in a generated mock (Swift 6.2 crashed on a mock shape that Swift 6.4 diagnosed). In the long run, a known seed that fails with one of its shape's signatures runs inside `withKnownIssue`; one that no longer fails is reported as stale, and one that fails any other way is reported as a new failure, so a fix's own pull request shows the entries it makes stale. Each seed is listed once, in increasing order within its shape, below `corpusSeedCount`, which `knownIssues_listEachSeedOnceInIncreasingOrder_belowCorpusSeedCount` checks; `publicMockKnownIssues` is checked so below `publicMockCorpusSeedCount`, and its signatures read the public mock oracles' failures (`publicMockRejectsGraphKnownRightAccepts`, `publicMockBuildsOtherValuesThanKnownRight`). To add one, add the seed to its shape's list, or add a shape. Every failure the fuzzer finds becomes a hand-written regression test (reduced to the types that matter, with full `==` output) before its fix, and removing the entry is the last step of the fix.

The rest of the fuzzer's rules: `fuzzer-seam-draws.md` and `fuzzer-seam-oracles.md` (generator features and the seam corpus), `fuzzer-corpora.md` (the multi-module partition, the public mock corpus, modules beneath the seam's module), and `fuzzer-value-oracles.md` (the base corpus value oracle and the differential value comparator).
