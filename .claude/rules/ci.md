# CI

- Every CI job runs on a Linux runner unless it genuinely needs macOS: Xcode or `xcodebuild`, an Apple platform SDK, the Xcode project plugin, or the macOS release binaries and their notarization. Linux runners scale; macOS runners are the scarce resource that pull requests and publishes queue on.
- A short macOS build is a step, with its own `timeout-minutes`, of one of `ci.yml`'s two folded macOS jobs, never a job of its own: a run waits for a macOS runner once per job.
- **A pull request in the middle of a stack builds once on macOS.** Its heavy jobs skip ("Decide Whether This Pull Request Runs the Heavy Jobs"), but "Build for Apple Platforms, DocC and Xcode Projects on Xcode 26" still resolves the package and runs "Build Framework (platform=macOS)", so sources that only Xcode 26's compiler rejects fail on the branch that wrote them. A step added to that job carries `needs.stack-position.outputs.stacked-under == ''` unless the middle of a stack needs it; the record that the tree passed always does.
- A job on a `macos-*` runner states why in a comment in the workflow. macOS jobs run on arm64 images, never on an Intel runner.
- **Manage CI without asking.** macOS runners are few, and every push to a pull request queues a set of macOS jobs. An agent may always cancel a run in flight — one a newer push superseded, one whose result nobody will read, one holding runners a more urgent run waits for — and start it again later. Cancel, never delete: a cancelled run keeps its record and logs. When several agents work at once, the one coordinating them decides which runs hold the runners.
- A job that can hang gets a step-level `timeout-minutes` of about twice its measured duration, with the measurements in a comment beside it; never a per-test timeout, which makes CI flaky: Swift Testing's `.timeLimit` also counts the time a test waits for a thread behind the rest of the suite, and tests that do a fraction of a second of work have waited more than ten minutes on a loaded runner. A test that never ends is stopped by its step's limit, and the log then holds no verdict for it: save the step's log and `Scripts/unfinished-tests.py LOG` names every test that started and did not finish. The Linux test jobs run the test bundle directly, which writes each line as it happens, so a hung test is listed alone. A step that runs `swift test` off a terminal gets the tests' output in blocks and loses the last one when it is stopped, so its list also holds tests that passed; the script says when a log was cut.
- No scheduled or unattended check without a path that turns its findings into fix pull requests.
- New Linux jobs use the container and setup of "Build Tests on Linux" and "Build and Test on Linux" in `ci.yml`, except "Build and Test on Latest Swift" (`swift:latest`), "Lint Swift" (`swift:6.3`, a release build of SwiftFormat), and "Build Release SafeDITool on Linux", which runs `publish.yml`'s Linux build command in `publish.yml`'s container, because publishing 2.3.0-alpha-1 crashed Swift 6.3.3 compiling that release build of code every CI job had passed. "Delete This Run's Scratch Ref" (`verify.yml`, `graph-fuzzer.yml`) has no container: it runs only GitHub's API and git.
- `verify.yml` ("Verify on Linux") runs "Build Tests on Linux"'s build for one branch: `gh workflow run verify.yml --ref <branch> -f filter=<swift test filter>` (empty runs the suite; `-f pins=true` also checks the fuzzer's pins). It restores main's content-stamped build (`.github/scripts/stamp-source-times.sh`) and passed-compile-check caches; keep its container and `RELEASE_SWIFT_TEST_ARGUMENTS` in step with "Build Tests on Linux" and `graph-fuzzer.yml`'s coverage build, which restores its key. `-f mode=fast` needs a filter and builds in debug without coverage, from "Warm the Fast Verify Build Cache"'s cache. `-f mode=function-compile-time` runs only "Check Function Compile Time on Linux"'s build and check ("Verify Function Compile Time on Linux"; keep the two jobs' container, command and check in step) and tests nothing: run it before a pull request that adds or grows a long function under `Sources/SafeDICore` joins a stack, because the limit is about Linux's Swift 6.2 and CI runs on a stack's top only.
- `macos-build-check.yml` builds, by hand, what only a macOS runner builds, with no test run, for a branch that is on no pull request yet: `gh workflow run macos-build-check.yml --ref <branch>`. Its steps are copies of ci.yml’s, which `.github/scripts/check-macos-build-check.py` compares in the run; change a copied step in both. It gates nothing: a pull request runs every macOS job of ci.yml.
- "Check Line Coverage on Linux" is the coverage gate: `Scripts/unexecuted-lines.py` unions the lcov reports the two test jobs upload, counting lines as Codecov does, and fails on any line under `Sources/` or `Plugins/` that no test executes on Linux or macOS, over the whole tree. Every Swift file there is measured or listed as unmeasured, with its reason, in `Scripts/unmeasured-files.txt`. It fails on missing data (a missing, cut-short or other-commit report, an unlisted file no report records, a listed file a report records) and reads nothing from Codecov or the pull request's base. It has no container, since it only reads reports, as "Check Graph Fuzzer Corpus on Linux" does. When a stack lands, only the check on the landing's final commit counts: an intermediate main commit can fail on lines that tests higher in the stack cover.
- A required check that a matrix job reports needs a Linux stand-in that reports the same names when a Markdown-only change skips the job. A skipped job satisfies a required check under its own name, but GitHub evaluates a job's `if:` before expanding its matrix, so a skipped matrix job reports only its unexpanded name. The stand-in takes the job's `name:` and matrix through YAML anchors, runs only when `changes` reports a Markdown-only pull request, and needs no container, since it only reports.
- **What skips the build and test jobs.** "Detect Changed Files" reports `source=false` when every changed file is Markdown other than `Documentation/Manual.md`, or is under `.claude/`; the build and test jobs then skip. A path joins that list only when no job that would skip reads it: three tests read the Manual's code blocks, so it counts as source, and the scripts under `.claude/skills` have their fixture self-tests in "Check Agent Skill Scripts on Linux", which has no `if:` and no container (it needs only Python). A new script under `.claude/skills` with a self-test gets a step there, never in a job that can skip. That job's first step (`.github/scripts/check-skipped-paths.py`) fails when a step of another job, or Swift code under `Sources`, `Plugins` or `Tests`, names a path under `.claude/` outside a comment.
- "Build and Test on Xcode 26" and "Build and Test on Linux" skip each compile check that passed in an earlier run; `.claude/rules/passed-compile-checks.md` says how that cache is keyed and shared. "Build and Test on Latest Swift" never uses it. So under `.recordingIssues` a multi-module test gets no `compilation`; a test that reads it passes `.returningOutcomeOnly`, which always compiles.
- `Examples/Example Package Integration` has spaces in its name so that CI builds a package under a path with spaces. Markdown links to it spell the spaces `%20`, which GitHub renders but md-dead-link-check cannot decode, so `.github/md-dead-link-check.toml` excludes exactly those links and `.github/scripts/check-excluded-markdown-links.py`, a step of "Check Markdown links", checks that each still names a path that exists.
- `ci.yml`'s graph fuzzer jobs ("Fuzz Dependency Graphs on Linux", "Check Graph Fuzzer Corpus on Linux", "Report Changed Lines No Fuzzer Graph Executed on Linux") follow the fuzzer's rules, which load with `graph-fuzzer.yml` and the fuzzer's sources, not with `ci.yml`: before changing one, read `.claude/rules/fuzzer-overview.md` and `.claude/rules/fuzzer-gating-checks.md`.

## Reading the coverage gate's result locally

`Scripts/unexecuted-lines.py` needs both test jobs' reports, so it cannot check a local run. To read a CI run's result locally, download the run's reports (`gh run download RUN -p 'line-coverage-*'`) and run it as the job does, from a checkout of the commit their `commit.txt` names (for a pull request, GitHub's merge commit, which `git fetch origin SHA` fetches); `--self-test DIRECTORY` checks the script against fixtures.
