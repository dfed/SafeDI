# Type requirements query

`SafeDITool query needs <TypeName>… --include <directory>… --module-info <file>…` reports what each named type needs: the modules whose declarations build it and its dependencies in production, its `@Forwarded` parameters, the dependencies no `@Instantiable` declaration fulfills, and what its mock needs. It exists so a focused app can be assembled from exactly the modules one feature needs. It is in beta, and `--help` and the manual say so: it was built ahead of a live use, so its options, text, and JSON may change in any release as real projects adopt it, and the JSON's `formatVersion` is `0` until the format is stable; keep the beta note and the `0` until Dan removes them, and make `1` the first stable format then. `query` is a command group with `needs` as its one subcommand, so further questions (dependents, providers) join as subcommands rather than flags. `--include` is spelled as `generate`'s, and each directory is a module (`IncludedModule`) named after its last path component, or after as many trailing components as tell it apart from the other modules (`Home/Sources`), so a `Modules/<Name>/Sources` layout works without configuration; a Swift file included directly belongs to its directory's module. `--module-info` names `.safedi` files, each a module read with `ModuleInfoFile(moduleInfoDataWithoutView:)`, since the query includes every module it reads and a view grows with the modules beneath (`QueryNeeds.readModuleInfoFiles(at:)` reads each file once, in parallel, and throws the error of the first argument whose file cannot be read) (an unreadable or missing file is `QueryError.moduleInfoNotReadable`, with `BinaryFile.unreadableFileExplanation`), named after the module the file records; two files recording one module are `QueryError.moduleInfoNamedTwice`, and a directory named like a module a file records is `QueryError.modulesShareName`. `ParsedQueryModule` reads either kind: a directory's declarations are attributed to the files found under it, spelled under the `--include` argument; a module info file's to the paths it records (`sourceFilePath`, the declaration and mock declaration locations), spelled as stored, since the writing build's spelling is all the file has. `--active-compilation-conditions` applies only to directories, and `generatedIn` reads a module info file's `configurations`. `QueryCommand.swift` parses each directory module with `parseModule` (the module's own files are its configuration files; `additionalDirectoriesToInclude` is deliberately not followed, since every module is included), rejects a file in two modules, combines the modules' instantiables in module-name order, runs them through `normalizingInstantiableTypes(of:)` and `resolveSafeDIFulfilledTypes(instantiables:)` (`InstantiableResolution.swift`, shared with `generate`, so the query sees the types exactly as `generate` does), and reports the types named in order, each once, from that one read. `DependencyTreeGenerator.requirements(of:)` builds a type's mock root exactly as `generateMockCode` builds the root of a type listed in `additionalMocksToGenerate` — the same `mockScopes(additionalMocksToGenerate:receivedPropertiesCache:)` setup and validation, with the type always listed (the map reads no type named, so one call builds it with the first type and validates each later type's tree alone, `validateListedMockRoot`: every other tree has passed by then, so each type reports what a call that listed it alone reports), the same `mockRootInstantiable(for:scope:)` canonicalization, the same `createMockRoot(for:scope:…)` checks — and reads `ScopeGenerator.mockRootParameters(instantiable:)`, the classification `generateMockRootCode` emits; `generatesMock` only decides whether a hand-written method named `mock` is a collision (`createMockRoot`'s `GeneratedMockReason` is `nil` otherwise, and the root is built with that method). A mock root is a tree in which every dependency the type receives is built beside it, so the tool runs it twice: over the map with every hand-written mock removed (`Instantiable.withoutHandWrittenMock`, `mockOnly` entries dropped) for what the type needs in production, and over every declaration for what the mock needs. Which mock is decided in `query()` from the entry under the type's own key, the one `mockRootInstantiable` builds the root from (`TypeReport.Mock.Kind`): `generated` when a declaration sets `generateMock: true` or an included module's configuration lists the type (`generatedIn` names those modules, and the text says how a project without them generates the mock), `handWritten` when that entry has a hand-written mock, and `wouldBeGenerated` otherwise, so the focused app learns what the `mock()` it would generate needs — `mockOnly` modules included, which the production view strips. A hand-written method named `mock` on another entry for the type (a `mockOnly` extension whose mock returns a protocol, which `resolveSafeDIFulfilledTypes` merges only into that protocol's slot) is neither the root's mock nor compatible with generating one, so the report is `MockReport.none(NoMock)` rather than an error: the production part still prints. The two views are built side by side, as separate generators, and the mock view's result for each type is read before the production view's, so a missing name is reported from the full map, with the types that fulfill that name and the types named most like it (`QueryError.noInstantiableNamed`). Neither part has a walk of its own, so the report cannot disagree with the generated mock; any new kind of `mock()` parameter must be added to `MockRootParameters`, not computed inside `generateMockRootCode` alone. The one input the query lacks is the generating module, which decides which flat parameters default to a hand-written mock (`flatParameterMockDefaults(in:emittingModule:)`): `query()` passes `requirements` the module in `generatedIn` as a `mockEmittingModule` (`ParsedQueryModule.emittingModule(attributionsByFilePath:)`: its name, its package only from a `.safedi` that records one, and the files attributed to it as its own) when exactly one module generates the mock, and `nil` otherwise, which takes every hand-written mock to be callable. So the report and the generated mock still disagree where the query cannot know the answer: a `package` mock of another module when either package is unknown (taken as callable, `packageUnverified`, as `generate` takes it), and a mock that several modules or no module generates. `QueryNeeds.md` states both; no other access shapes the report. The query runs exactly the checks on the path of one root, because it reaches them through `mockScopes` and `createMockRoot`, and none of the passes `generateMockCode` runs over every mock root together after its loop (`validateFills`, which judges fills against the calling module's access, `validateSendableBuildersCaptureNoNonSendableWrapper`, `validateConfigurationsAreBuiltOneWay`): those gate emitting the module's mocks and change nothing in the report, and `generate` reports them with fix-its, so a query that succeeds where `generate` would throw one of them is intended, not drift. The rule for a new check: one that decides whether a single root can be generated goes in `createMockRoot`, so both callers run it; one that needs every root at once goes after the loop, and is not added to the query. The one exception is the access check (`createMockRoot`'s `emittingModule`, see "Access between modules" in `module-membership-and-access.md`): the query reports what a type needs whichever module assembles it, so it has no emitting module, passes none, and checks no access. The public result is `TypeRequirements` (declarations with the file that holds each, erasures with every declaration that makes them, forwarded and required parameters with reasons); `TypeReport` in the tool attributes each file to its module (`FileAttribution`: the module's name, its `--include` or `--module-info` paths as given, and the file spelled under the `--include` argument through `NormalizedFilePath.path(under:spelled:)`, or as a module info file records it) and formats the text; `QueryReport` wraps the types under `formatVersion`, and `QueryErrorReport` prints any error as JSON with a `kind` when `--json` is set. The JSON is a contract documented in `Documentation/QueryNeeds.md`: arrays are always present, optional keys are omitted, every reason has a `reasonKind` beside its sentence, and from `1` on `formatVersion` is raised when a key is renamed, removed, or changes meaning, so a change to the shape is a change to that page and, once the format is stable, a version bump. An erasure is attributed to a module already needed when one declares it, else to the first declaring module by name, with the rest listed beside it: any one declaration suffices, and the choice must not depend on set order.

**Report what a caller writes.** The report gives declared value types and labels as a call site spells them: `service: Service` for a `mock()` parameter the generated code declares `@autoclosure @escaping () -> Service`, since a caller still passes a `Service`. It never surfaces generator mechanics (autoclosures, `__safeDI_` locals, builder functions); hiding them is the design, not a leftover. A seam's own internal mock reports each builder it takes in place of its places' parameters (`MockRootParameters.seamMockBuilders`) as a required parameter under the builder's label, typed as a caller writes it, `() -> T`, with reason `noInstantiableFulfillsType`; `requirements` reads it from there, since it is in no flat list (`SafeDIToolQueryTests`).

**`query graph`** (`QueryGraphCommand.swift`, `Documentation/QueryGraph.md`, `SafeDIToolQueryGraphTests`) is in alpha, `formatVersion` `0`: its options and JSON may change in any release until Dan calls it beta. It reads the modules through `QueryNeeds.readIncludedModules(including:moduleInfo:activeCompilationConditions:)` and `attributionsByFilePath(of:)`, normalizes and resolves as `query needs` does, and exports declarations, never trees: each production declaration once (`mockOnly` left out), its dependencies in declaration order with their `source` (`instantiated`, `received` – an alias is received, with `aliasOf` – or `forwarded`) and an instantiated one's `lifetime`, every type as declared (`type`) and as `TypeDescription.plainType` (`plainType`: the property's, with no optional, wrapper or `any`; an instantiated dependency that spells `fulfilledByType:` also has `fulfilledByType`, its `asInstantiatedType.plainType`), so no consumer parses a spelling, and `fulfillments` keyed by plain type. The graph points both ways: `fulfilledBy` down from an instantiated dependency, `constructedBy` up from the declaration it names, both from the one resolved map. API terms are reused, never invented (Dan's rule): a new field takes a name the Manual or an existing field already uses. `completeness` says how far SafeDI got: `declarations` when resolution fails (no `fulfilledBy`, `constructedBy` or fulfillments), `partialTrees` when every error is a dependency that cannot be fulfilled (`.noInstantiableFound`, `.unfulfillableProperties`), `fulfillment` when the trees are not valid otherwise (no `provenance`, no `isReachedByRoot`), `trees` otherwise; `errors` lists what `generate` reports, the declarations are still written and the command still succeeds. Declarations sort by module, type name, then line, never by file path, so an export from `--include` and one from `.safedi` files order alike. A received dependency's and an alias's `provenance` is read from the trees `generate` builds, never a second implementation of its resolution: `DependencyTreeGenerator.receivedValueSupplies()` validates and builds the roots' trees as `generate` does (`dependencyTrees(unreadTypeComment:)`) over the production declarations, with no seam resolution, so every seam's tree is built inline, and `ScopeGenerator.receivedValueSupplies(ofTreeRootedAt:)` walks each tree as `seamTierOmissions` does: the nearest declaration of each receive's label where its type is constructed, in `orderedChildren` order, `nil` where generation passes `nil` (`unavailableProperties`), with its `ReceivedValueSupply.NilReason` (`noProvidingDeclaration`, or `providerNotYetBuilt` where the nearest provider is built later or is being built around the receiver), a lazy cycle's parameters judged at every call of their function (`OmissionFindings`, whose `passedNothing` records a call that passes `nil`). The walk also returns the types it constructs, which give `isReachedByRoot`; a declaration no root's tree builds has no `provenance`. A provenance entry is the declaration itself, an alias included, so a consumer follows an alias's own `provenance` to what it renames. So the export costs what building the trees costs, without generating code. For `partialTrees`, the query command alone (never `generate`, whose diagnostics stay as they were) builds the trees again of every declaration as written, around the dependencies the error names (`DependencyTreeGenerator.absentDeclarations(ofDependenciesReportedBy:in:)`); nothing is relaxed, because reading a missing dependency as only if available changed what other receives were handed. A type no declaration fulfills gets an absent declaration in the query's own map, a leaf with no dependencies, so the property that instantiates it keeps its label, form, place among its siblings and what it hides; one instantiated only if available stays unmarked, and a receive of it gets `nil` provenance of kind `declarationNotInstantiated`, with `declaredBy` and `label`, in partial and complete trees alike. A receive or alias nothing provides is tolerated where it is declared: `DependencyTreeGenerator.init(…unfulfilledReceiveLocations:)`, which only the query passes, makes `validatePropertiesAreFulfillable` skip those receives where it would record them, so a subtree that holds one can still be remembered as clean, and every other check runs. A tolerated receive still makes its property receivable beneath it (`insertProperties`), so one check reads the marks: `recordHiddenReceives` records no receive whose property has been receivable only since a scope beneath the closest declaration of its label (`receivableDepthByProperty` against `closestDeclarationDepthByLabel`), which only a tolerated receive makes it, since `generate` reports that receive under no fix of the one above; a declaration between the two still hides it, and gives `fulfillment`. `generate` reports the missing types before any receive, so the builds are at most three: as written, around the types, then around the receives that build reports too. The marks (`isUnfulfilled`) are the dependencies `generate` reports plus the receives it reports once the missing types exist, each `errors` entry its own message; any other error at any build gives `fulfillment`, with `generate`'s first error alone and no mark, so the error that decided it can be missing from `errors`. The walk (`ScopeGenerator.receivedValueSupplies(ofTreeRootedAt:unfulfilledReceives:)`) judges a marked receive per place by validation's own test, whether its property is receivable there: where it is not, the receive is `unfulfilled` naming nothing, and an absent declaration of its property, with the instance of a `LazilyInstantiated` one, is in scope beneath it after every real declaration of its label (`VisibleDeclaration.isAbsent`), so a lookup that finds a declaration finds the one it found before and only a lookup that would find none is `unfulfilled`, naming the receive above. Beneath an absent declaration a required receive reads the declaration of exactly its property (`VisibleDeclaration.declares`), as validation judges it, so an optional declaration of the label above the marked receive does not stand in for it. A marked alias stays a declaration, whose own provenance says where it has a value. A receive of a marked instantiated dependency is `unfulfilled` naming it. The walk judges no tree in which a marked receive or its absent declaration meets a parameter of a function a lazy cycle closes on (the receive or one beneath it reads the parameter, or a call beneath it passes it): `receivedValueSupplies()` returns `nil` and the export is `fulfillment` (`graph_reportsNoProvenance_whenUnfulfilledReceiveReadsParameterOfFunctionLazyCycleClosesOn`, `graph_reportsNoProvenance_whenLazyCycleBuiltBeneathUnfulfilledReceiveTakesItsLabelAsParameter`). A partial export keeps each `declaration` handed and each `unfulfilled` value unless the fix declares something nearer, and `QueryGraph.md` lists what it does not know: a missing type's own tree and the type of a value nothing provides are not reached (`isReachedByRoot` is `false` for them), a `nil` can become a declaration, values can be added, and the fix can add errors, hide a declaration, or change a `providerNotYetBuilt`. The fuzzer's query oracle (`fuzzer-query-oracle.md`) checks every accepted one-module graph against the generated code and against its own export with one declaration deleted, and every rejected one-module graph's marks against `generate`'s errors. Build order is not exported: a seam build starts carriers last, and the order can differ between places of a type.
