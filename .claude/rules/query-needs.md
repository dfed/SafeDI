# Type requirements query

`SafeDITool query needs <TypeName>… --include <directory>… --module-info <file>…` reports what each named type needs: the modules whose declarations build it and its dependencies in production, its `@Forwarded` parameters, the dependencies no `@Instantiable` declaration fulfills, and what its mock needs. It exists so a focused app can be assembled from exactly the modules one feature needs. It is in beta, and `--help` and the manual say so: it was built ahead of a live use, so its options, text, and JSON may change in any release as real projects adopt it, and the JSON's `formatVersion` is `0` until the format is stable; keep the beta note and the `0` until Dan removes them, and make `1` the first stable format then. `query` is a command group with `needs` as its one subcommand, so further questions (dependents, providers) join as subcommands rather than flags. `--include` is spelled as `generate`'s, and each directory is a module (`IncludedModule`) named after its last path component, or after as many trailing components as tell it apart from the other modules (`Home/Sources`), so a `Modules/<Name>/Sources` layout works without configuration; a Swift file included directly belongs to its directory's module. `--module-info` names `.safedi` files, each a module read with `ModuleInfoFile(moduleInfoData:)` as `generate` reads a dependent module's, its view ignored, since the query includes every module it reads (an unreadable or missing file is `QueryError.moduleInfoNotReadable`, with `BinaryFile.unreadableFileExplanation`), named after the module the file records; two files recording one module are `QueryError.moduleInfoNamedTwice`, and a directory named like a module a file records is `QueryError.modulesShareName`. `ParsedQueryModule` reads either kind: a directory's declarations are attributed to the files found under it, spelled under the `--include` argument; a module info file's to the paths it records (`sourceFilePath`, the declaration and mock declaration locations), spelled as stored, since the writing build's spelling is all the file has. `--active-compilation-conditions` applies only to directories, and `generatedIn` reads a module info file's `configurations`. `QueryCommand.swift` parses each directory module with `parseModule` (the module's own files are its configuration files; `additionalDirectoriesToInclude` is deliberately not followed, since every module is included), rejects a file in two modules, combines the modules' instantiables in module-name order, runs them through `normalizingInstantiableTypes(of:)` and `resolveSafeDIFulfilledTypes(instantiables:)` (`InstantiableResolution.swift`, shared with `generate`, so the query sees the types exactly as `generate` does), and reports the types named in order, each once, from that one read. `DependencyTreeGenerator.requirements(forTypeNamed:generatesMock:mockEmittingModule:)` builds a type's mock root exactly as `generateMockCode` builds the root of a type listed in `additionalMocksToGenerate` — the same `mockScopes(additionalMocksToGenerate:receivedPropertiesCache:)` setup and validation, with the type always listed, the same `mockRootInstantiable(for:scope:)` canonicalization, the same `createMockRoot(for:scope:…)` checks — and reads `ScopeGenerator.mockRootParameters(instantiable:)`, the classification `generateMockRootCode` emits; `generatesMock` only decides whether a hand-written method named `mock` is a collision (`createMockRoot`'s `GeneratedMockReason` is `nil` otherwise, and the root is built with that method). A mock root is a tree in which every dependency the type receives is built beside it, so the tool runs it twice: over the map with every hand-written mock removed (`Instantiable.withoutHandWrittenMock`, `mockOnly` entries dropped) for what the type needs in production, and over every declaration for what the mock needs. Which mock is decided in `query()` from the entry under the type's own key, the one `mockRootInstantiable` builds the root from (`TypeReport.Mock.Kind`): `generated` when a declaration sets `generateMock: true` or an included module's configuration lists the type (`generatedIn` names those modules, and the text says how a project without them generates the mock), `handWritten` when that entry has a hand-written mock, and `wouldBeGenerated` otherwise, so the focused app learns what the `mock()` it would generate needs — `mockOnly` modules included, which the production view strips. A hand-written method named `mock` on another entry for the type (a `mockOnly` extension whose mock returns a protocol, which `resolveSafeDIFulfilledTypes` merges only into that protocol's slot) is neither the root's mock nor compatible with generating one, so the report is `MockReport.none(NoMock)` rather than an error: the production part still prints. The mock view is computed before the production view, so a missing name is reported from the full map, with the types that fulfill that name and the types named most like it (`QueryError.noInstantiableNamed`). Neither part has a walk of its own, so the report cannot disagree with the generated mock; any new kind of `mock()` parameter must be added to `MockRootParameters`, not computed inside `generateMockRootCode` alone. The one input the query lacks is the generating module, which decides which flat parameters default to a hand-written mock (`flatParameterMockDefaults(in:emittingModule:)`): `query()` passes `requirements` the module in `generatedIn` as a `mockEmittingModule` (`ParsedQueryModule.emittingModule(attributionsByFilePath:)`: its name, its package only from a `.safedi` that records one, and the files attributed to it as its own) when exactly one module generates the mock, and `nil` otherwise, which takes every hand-written mock to be callable. So the report and the generated mock still disagree where the query cannot know the answer: a `package` mock of another module when either package is unknown (taken as callable, `packageUnverified`, as `generate` takes it), and a mock that several modules or no module generates. `QueryNeeds.md` states both; no other access shapes the report. The query runs exactly the checks on the path of one root, because it reaches them through `mockScopes` and `createMockRoot`, and none of the passes `generateMockCode` runs over every mock root together after its loop (`validateSendableBuildersCaptureNoNonSendableWrapper`, `validateConfigurationsAreBuiltOneWay`): those gate emitting the module's mocks and change nothing in the report, and `generate` reports them with fix-its, so a query that succeeds where `generate` would throw one of them is intended, not drift. The rule for a new check: one that decides whether a single root can be generated goes in `createMockRoot`, so both callers run it; one that needs every root at once goes after the loop, and is not added to the query. The one exception is the access check (`createMockRoot`'s `emittingModule`, see "Access between modules" in `module-membership-and-access.md`): the query reports what a type needs whichever module assembles it, so it has no emitting module, passes none, and checks no access. The public result is `TypeRequirements` (declarations with the file that holds each, erasures with every declaration that makes them, forwarded and required parameters with reasons); `TypeReport` in the tool attributes each file to its module (`FileAttribution`: the module's name, its `--include` or `--module-info` paths as given, and the file spelled under the `--include` argument through `NormalizedFilePath.path(under:spelled:)`, or as a module info file records it) and formats the text; `QueryReport` wraps the types under `formatVersion`, and `QueryErrorReport` prints any error as JSON with a `kind` when `--json` is set. The JSON is a contract documented in `Documentation/QueryNeeds.md`: arrays are always present, optional keys are omitted, every reason has a `reasonKind` beside its sentence, and from `1` on `formatVersion` is raised when a key is renamed, removed, or changes meaning, so a change to the shape is a change to that page and, once the format is stable, a version bump. An erasure is attributed to a module already needed when one declares it, else to the first declaring module by name, with the rest listed beside it: any one declaration suffices, and the choice must not depend on set order.
