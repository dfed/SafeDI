# Remedy oracle

Every error SafeDI reports names its fix. The remedy oracle (`Tests/SafeDIToolTestSupport/GraphFuzzerRemedies.swift`) follows that advice on the graphs the base corpus rejects, about half of it, which no other oracle judges beyond determinism and renaming: for each error of the families it reads (the three users see most, a mock parameter an inactive `#if` clause declares, a type two declarations fulfill, an `@Instantiated` type no declaration fulfills, a capture a `@Sendable` function cannot make, and in the seam corpus a seam's label collision), it applies the remedy the error states to the graph's declarations, runs the tool again, and requires that no error is left at the declaration the error was at (`GraphFuzzerToolRuns.remedyFailure`, `remedyLeavesErrorAtSite`). An error elsewhere is allowed: a remedy can expose an error the tool's walk stopped before, or change what another type receives. It runs only the tool, never the compiler, so it adds about one tool run per remedied site, and a few more where it forwards a receive.

- **Which graphs.** A rejected base or seam corpus graph, in one module or split across modules (`GraphFuzzerOracle.remedyRuns(of:outcome:)`, `GraphFuzzerRemedies.reads(_:)`): every family. A remedy edits a split graph's files in place, so the remedied graph keeps its module map and runs through the `.moduleInfo` flow as the corpus's first run does; the SwiftPM plugin's scan flow is the multi-module oracle's to compare, not re-run per remedy. An edit may be in another module than the error, as a root in `FuzzApp` declaring what a receive in `FuzzFeature` needs. No public mock corpus graph is read. The seam corpus inherits the base corpus's remedy shapes (`isBaseCorpusValueOracleShape` excludes only the value oracle's), less the seeds its own draw changes (`seamCorpusSeedsOfOtherShapes`), and lists its own. The seam corpus does not judge the advice to add `onlyIfAvailable: true` to a required receive of an optional (`receiveOnlyIfAvailable`, `instantiateOnRootAndReceiveOnlyIfAvailable`), since that receive is not a shape anyone writes; such a site counts as unremedied. The base corpus judges it until its draws stop drawing the receive (plan I6). The long run reports a `remedies` line for both corpora.
- **What it reads.** An error's site is the property declaration its location names, as a file, the `final class` around that line, and the property's label (`GraphFuzzerRemedy.Site`), so a remedy that adds or removes lines elsewhere in the file moves no site. An error at a declaration's `@Instantiable` line, where a type two declarations fulfill is reported, has that declaration as its site, with the fulfilled type as its label. An error at a seam's `@Instantiable` line that its tree receives one label in forms its initializer cannot take as one parameter has the seam as its site, with the label, whatever remedy it states, so the error a remedy leaves is at the same site (`Files.seamSite(of:)`). An error at an `#if` clause, which is where a mock parameter of an inactive clause is reported, has the dependency its message names as its site, so the error is at the same site after an edit moves the clause. All the errors at a site must state the same remedy, or, for a receive no type in its chain fulfills, the same declaration on their own roots, which every named root then gets; a site whose errors state other remedies gets none.
- **The remedies** (`GraphFuzzerRemedyKind`), each read from the error's text (`GraphFuzzerRemedies.StatedRemedy`):
  - an unfulfilled receive's "Declare `@Instantiated let x: X` on `Root` …": `Root` declares it (`instantiateOnRoot`), and where the hint goes on "and add `onlyIfAvailable: true` to this property’s `@Received`", for a required receive of `x: X?`, the receive gets it too (`instantiateOnRootAndReceiveOnlyIfAvailable`);
  - "Did you mean to decorate this property with `@Received(onlyIfAvailable: true)`?": the bare `@Received` gets it (`receiveOnlyIfAvailable`);
  - "Did you mean `y: Y`?" and "Did you mean one of …?": the bare `@Received` takes each suggestion's label and type in turn, a remedy each (`receiveSuggestedProperty`);
  - a cycle's "Change … to an instantiator.": the dependency at the site, which closes the cycle, becomes `Instantiator<T>`, `ErasedInstantiator<(), AnyT>` for an erased one, `Sendable` when its lazy wrapper was (`instantiateAsInstantiator`);
  - a receive of a property still being built, or an unfulfilled receive whose declaration would be ("Declaring `@Instantiated let x: X` would close a dependency cycle …"), "Remove this @Received property, or receive it with `onlyIfAvailable: true` and an optional type": two remedies, the removal (`removeReceive`) and the optional receive (`receiveOptionallyIfAvailable`);
  - an unfulfilled receive's "Declare `@Forwarded let x: X` on a type below `Root` in the chain, and pass the value to the `Instantiator` that builds that type", for a type with `@Forwarded` properties or one no declaration fulfills: the receiver forwards the property (`forwardReceive`). What built the receiver as a constant, or through an erased instantiator that took nothing, then reports the declaration that builds it ("Declare it as `Instantiator<T>`.", "Declare it as `ErasedInstantiator<X, AnyT>`."), which the remedy applies too, a run for each set of declarations the run before states: each root reports its first error only, so three roots that build the receiver take three runs, and six is the limit (`followingForwardedReceive`, `maximumForwardedReceiveFollowingRunCount`). A forwarded property has no receive left for an error to be at, so the verdict also requires that no such error about a builder of the receiver, new since the remedy, is left (`errorsIntroducedByForwarding`). The oracle cannot judge the other half of the advice, the hand-written `instantiate(…)` call that passes the value: no fixture calls one;
  - "Found multiple @Instantiable types or extensions that fulfill `P`. … keep one, and remove `P` from the others’ `fulfillingAdditionalTypes`": each declaration that reports it keeps the type in turn, a remedy each, and every other declaration loses the argument (`keepOneFulfiller`);
  - "No @Instantiable type or extension fulfills `X` … Decorate `X`, or an extension of it, with @Instantiable": the empty class the fixture declares gets the attribute, and the conformance and public initializer the macro then requires (`decorateType`);
  - a receive inside a `@Sendable` function of a wrapper that is not `Sendable`, "Declare `x` on `T`, and this property, as `SendableInstantiator<X>` to fix." and its form without "and this property": the named declaration, and the receive where the error says so, take the wrapper it spells; "Declare `x` as `W` where it is declared and where it is received as `V`", which a mock's tree that receives the property from outside reports: every property of that label and type takes it, in every type of the graph, which is more than the error's chain where another branch declares the same (`declareAsSendableWrapper`);
  - a seam whose tree receives one label in forms of one type, "Receive `x` the same way in every type of the tree, or declare it on `Seam` as the form that provides the others: `@Received let x: X`.": the seam declares that property, in place of its own of that label where it has one (`declareProvidingFormOnSeam`). The error's forms must each be received as an adopter would: one that is optional is received only if available, since a required receive of an optional is not a shape anyone writes, so an error that names such a form, or a form the oracle cannot find on the type the error names, gets no remedy and counts as unremedied. "Receive `x` the same way in every type of the tree." alone states no edit the oracle can make;
  - a receive a closer declaration of its label hides, "`T` declares `x: Y` with the same label, … Give `x: Y` on `T` a different label to fix.": that declaration on `T` takes the label `xRelabeled` (`relabelHidingDeclaration`). A hidden receive that is a required optional gets no remedy and counts as unremedied, as above, and so does a label an alias renames with `fulfilledByDependencyNamed:`, whose rename the relabel would leave behind. The error in a mock's tree, "Receive … under different labels", states an edit of the receive, which the oracle does not make;
  - a hand-written mock's parameter whose dependency only an inactive clause declares, "Give the parameter a default value, or move the `mock` method inside `#if X`.": the parameter gets a call of its type's initializer as its default (`defaultMockParameter`), and, where the error offers the move, the mock's `#if DEBUG` block moves to the end of the clause the error is at (`moveMockIntoClause`).
- **The mock parameter draw.** No graph drew that error, so `addingGuardedMockParameterShapes` draws it in one base corpus graph of fifty, from a stream of its own after every other pass: `Guarded` declares `guardedValue`, instantiated or received, inside one of four clause forms no build of the fuzzer selects (`#if`, `#else`, `#elseif`, and a nested block, where the error offers no move), and its mock takes it; a mocked `GuardedHost` builds `Guarded` with its `mock`, or `Guarded`, mocked itself, names `customMock`. Only a build that compiles the generated mocks reports the error, so the tool is told `DEBUG` is active for a graph that draws the shape, in one module and split across modules (`GraphFuzzerFixture.activeCompilationConditions`), and for no other graph. These are the first graphs the fuzzer runs with conditions, and they show the two multi-module flows emitting other compile-time assertions, a known issue (`compileTimeAssertionsDifferBetweenIntegrationsReason`). The tool rejects every such graph, about half of them with another error first, so the base corpus pins how many it rejects with the error (`corpusErrorGraphCounts`, on the report's `errors base` line), which a production error does not hide.
- **What it leaves out.** Advice it cannot apply as stated: an erased instantiator's "naming the type it builds" (the macro rejects a declaration that names none), a `@Sendable` capture of a property an alias also receives (the alias names its type in `ofType:`, and its own property and the aliases of it are typed after it), a missing type the fixture does not declare as an empty class on one line, a cycle an alias received only if available closes, a suggestion or receive on an alias, a property the type already declares under the new label, a root declared by an extension. The long run's report counts these sites (`unremedied=` on its `remedies` line), and with them each error of a family the oracle reads at a line it cannot place: a declaration that is no `final class`'s, or an attribute on two lines.
- **How it edits.** On the fixture's text, as the fuzzer writes a type (`GraphFuzzerRemedies.Files`): property lines `@Attribute let label: Type` in a `final class`'s body and a one-line initializer that takes each property in order, before its default-valued parameters, and assigns each. An edit rewrites the initializer and its body with the properties, so the remedied graph stays one the macro accepts.
- **Pins and tests.** The long run reports `remedies <corpus> <kind>=<judged>/<failed>,… unremedied=<n>`, which no pin checks. `smokeSeeds_applyRemedies_inGraphsTheToolRejects` pins the kinds the smoke batch applies (`smokeRemedyKinds`). `SafeDIToolGraphFuzzerRemedyTests` holds a handwritten graph for every kind, each written as the fuzzer writes one, with its remedied file in full and no error left at its site, and the oracle's verdict on a remedy that leaves one.
- **A finding** is advice that does not fix its error, or trades it for another at the same declaration. It is a defect of the diagnostic, not of generated code: record it as a known issue with `.remedyLeavesErrorAtSite(_:containing:)`, a signature for each remedy kind that shows the shape, each naming the error the remedy leaves, which tells the shapes of one kind apart (every remedy line of the failure must match one of the entry's signatures, `GraphFuzzerFailure.remedyFailures`), with its minimal graph in the entry's reason and as a test in `SafeDIToolGraphFuzzerRemedyTests` that expects the advice to work inside `withKnownIssue`, and fix the diagnostic in a change of its own. Eight shapes are recorded today: advice to declare a `Sendable` wrapper that names one root and the receive where another root declares the property, or another type receives it, as the wrapper that is not `Sendable` (`remedySendableWrapperNamesOneDeclarationReason`, whose fix names every declaration); advice inside a `@Sendable` builder to receive or declare what it cannot capture, or to relabel the declaration that hides it; advice to receive only if available, or a suggested property, beneath a type that declares the label with another type, where the receive is then hidden; a suggestion whose receive closes a cycle; suggestions that alternate between two paths to one receiver, since each error reports one; advice to declare on a root whose own properties the declared tree receives and require the declaration; advice to relabel the closest of several declarations that hide a receive, since the error names only that one (`remedyHiddenByEachDeclarationAlongTheChainReason`, whose fix names every one along the chain); and, in the seam corpus, advice to declare on a seam the wrapper that provides a label's other forms, which nothing that builds the seam declares, so the receive is unfulfilled or closes a cycle (`remedySeamProvidingWrapperUndeclaredReason`).
