# Graph fuzzer: comparing output with the pull request's base

A rewrite proves it changes no output by comparing against the tool built from the commit beneath it, never by keeping the code it replaces in the tree behind a switch: each pull request deletes what it replaces, and git holds the old code.

- **What runs.** `ci.yml`'s "Build the Base SafeDITool on Linux" builds `SafeDITool` (release, `--product SafeDITool`, as "Check Generate Time on Linux" builds it) at the first parent of the merge commit the run checks out, the tip of the branch beneath a stacked pull request or of main as it was when GitHub made that merge, and uploads the binary. It does not build `github.event.pull_request.base.sha`: when the base branch moves just before a run is queued, the event can name the older tip while the merge holds the newer one, and the comparison then reports what landed on the base as the pull request's change; the job prints a notice naming both commits when they differ. "Check Graph Fuzzer Corpus on Linux" fails, naming both, when the commit the base tool was built from is not the first parent of the merge commit it checks out, so a comparison with another commit never passes or fails by luck; it also prints the comparison's summary into its log. It caches the binary alone, keyed by the base's tree hashes of `Sources`, `Package.swift` and `Package.resolved` and a hash of `swift --version`, and also looks for the tool "Check Generate Time on Linux" saved for that commit on main. It runs only for a pull request that changes more than Markdown. Each fuzzer shard then runs `SafeDIToolBaseComparisonTests/longRun` over its own seeds, with the base's tool and the bundle's (`SAFEDI_BASE_COMPARISON_BASE_TOOL`, `…_HEAD_TOOL`, `…_FEATURES`, `…_STARTING_SEED`, `…_ITERATIONS`, `…_REPORT`), and uploads `base-comparison.txt` with its report. "Check Graph Fuzzer Corpus on Linux" judges them (`combine-base-comparison-reports.py`).
- **What it compares** (`GraphFuzzerBaseComparison`, `Tests/SafeDIToolTestSupport/GraphFuzzerBaseComparison.swift`). Both tools run as processes with the same arguments over the same fixture files, one after the other in the same directories, so no path needs reducing: each step's exit status, standard error and standard output, and the bytes of every file the steps write – generated files, `.safedi` files, and the manifest `scan` writes. The scan cache is left out. A graph in one module runs as the SwiftPM plugin runs the tool (`scan` with every file mock-scoped, then `generate --swift-manifest`); a graph split across modules (`GraphFuzzerFixture.modules`, the seam and public mock corpora's roles) runs as Bazel's rule does, one `generate --combined-output --module-info-output --module-name [--package-name] [--dependent-module-info-file-path]` per module in dependency order, listing what the fuzzer's module-info flow lists, stopping at the first module rejected. The base corpus's `GraphFuzzerPartition` is not run per module.
- **Verdict.** A pull request whose description holds the line `Generated output: unchanged` fails on any difference, on a graph the comparison could not judge, on a shard without a complete report, on shards that do not judge each corpus's seeds exactly once (each report names its seeds and its corpus's size, and its compared and unjudged graphs must add up to its seeds), and on a base tool that did not build. The job reads the description as it is when the job runs, through GitHub's API, so editing the line in starts no run but a re-run of "Check Graph Fuzzer Corpus on Linux" judges it. Any other pull request may change output on purpose: the summary lists the graphs that differ, with their first difference, and the check passes. The long run itself fails only when it compared fewer seeds than it was given or a configuration input is missing.
- **Harness problems.** A tool that rejects its command line (exit status 64, ArgumentParser's) makes the graph a problem, not a difference: a base older than an option the harness passes, or the reverse.
- **Line counts.** The base tool's job prints the generator's lines of code (Swift under `Sources/SafeDICore/Generators`, blank and comment-only lines left out, `count-generator-lines.sh`) at the base and the head. It is information and gates nothing: a rewrite may grow where that makes it easier to reason about.
- **Tests.** `SafeDIToolBaseComparisonTests` runs the built tool against itself over graphs of every corpus and both flows (no difference, and `.safedi`, generated and manifest files compared), a base that rejects its arguments (a problem), a head that prints more to standard error or standard output (a difference per step) or appends to its combined output (a file difference), and each kind of difference between hand-written records.
