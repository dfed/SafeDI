# CI's cache of passed compile checks

"Build and Test on Xcode 26" and "Build and Test on Linux" skip each compile check that passed in an earlier run: `SAFEDI_COMPILE_CHECK_PASSED_CACHE` names a file of passed checks' keys (`PassedCompileCheckCache.swift`), cached under `.github/scripts/compile-check-identity.sh`'s hash of what compiles them, which covers SafeDICore only as the macro target compiles it (`Package.swift`'s `exclude`), so a generator change compiles again only the checks whose generated code it changes; a new input to whether a check compiles goes into that script or the key. Each key also carries what compiles the check, as the test process itself finds it (`CompileCheckBuild`): the compiler and SDK, the bytes of the SafeDI module it loads, and the dependency versions the build recorded (`workspace-state.json`, which a job that tests another job's build carries in its bundle). The macro plugin's bytes are not hashed, since two builds of the same sources differ; its sources are in the script's hash. Deliberately not in the key: the compiler that built the plugin (CI builds it with the one that compiles the checks), and how old the plugin is within the configuration directory the verifier chose, whose name the key does carry. Where the build cannot be described (no `workspace-state.json` above the plugin, as in Xcode's derived data), checks compile without a key and the process's last line counts them. So no workflow file is hashed: a workflow edit keeps every passed check unless it changes one of those, and nobody has to know which workflow lines matter. `share-compile-checks.yml` adds each finished CI or Verify run's passed checks to a per-identity list saved as main's cache, which every run on every branch also restores; a run uploads only the checks its own test processes passed (`passed-in-run-<run>.txt`), never what its job restored; as a `workflow_run` workflow it runs from main's copy only, and after a pull request's run it may not save a cache, so that list holds only what main's runs and Verify runs passed. `restore-shared-compile-checks` therefore also reads the lists the newest runs of the job's identity uploaded as artifacts (`restore-from-artifacts.js`; the artifact's name ends with the identity, so one request lists them): only from this repository's own runs of `ci.yml` and `verify.yml`, never a fork's, only lines that are keys; whatever it cannot read is a warning and compiles. A workflow's token may make 1,000 requests an hour for the whole repository, so the script reads at most the newest fifteen, none that the restored list already holds (`artifacts-read.txt`), and nothing when few requests are left; its last line counts its requests. Its job needs `actions: read`. Removing a check that should not have passed means deleting those artifacts as well as the caches, or changing `v1` in all three names (`share-compile-checks.yml` gives the commands). The list trusts every branch of this repository, so the identity also hashes the two actions that restore and upload the checks, with the restore action's script, and the identity script. A cache restores only where the compression matches, so the Linux list is saved from the test jobs' container (gzip) and the macOS list from a Linux runner without one (zstd, as the macOS job): change a test job's container or runner and that workflow together.

## What the value comparison's programs printed

The differential value comparator compiles, links and runs one program per path of each batch of graphs, through no compile check. `DifferentialValueOutputMemo` keeps what each program that exited with status 0 printed, one file per key in `value-outputs` beside the file of passed checks, so the job's cache of that directory carries it and the same identity names it. A later program with that key compiles and runs nothing, on any branch whose job reads it (below).

- **Only output is kept.** The judgment, exemptions and retention verdicts are computed from the output on every run, so a change to them needs no key. A program that fails to compile, link or run, or that a time limit stops, is never kept.
- **The key is the program, not a graph.** A batch links several graphs into one executable, whose modules share static state, so the key covers the whole batch: every file, each module's layout and conditions, and `main.swift`, which spells the probes, samples, limits and retention.
- **The key hashes what decides the output beyond the program**: the describer's text, the bytes of the comparator's, the compile helper's, the memo's and the passed-check cache's source files, the runtime's sources, a release's macros tool, the loader's environment variables (`LD_LIBRARY_PATH`, `LD_PRELOAD`, `DYLD_*`), and `CompileCheckBuild`'s description. A new input to what a program prints goes into `harnessDescription` or the key.
- **What it cannot see** is a program whose output differs between two runs of the same bytes. "Build and Test on Latest Swift" and the graph fuzzer's shards set no `SAFEDI_COMPILE_CHECK_PASSED_CACHE`, so they compile and run every program on every run.
- **An output that spells a fixture root or a UUID is not kept**, since the key rewrites both and the next run would read this run's paths. A write that fails keeps nothing and fails no test. The tally line counts both.
- **A pass near a limit is kept**, as a passed compile check is: a probe that finished just under its time limit is read at once on a slower runner that might have stopped it.
- **This checkout's macro plugin is covered only by CI's identity**, which names the cache directory. Someone who sets the variable by hand and edits `Sources/SafeDIMacros` empties the directory.
- **A process that cannot read the harness's sources** (a test bundle run away from its checkout) runs every program and keeps none.
- **A test that counts the executables a comparison compiles** passes `memo: nil`.
- **Outputs reach other branches as passes do, through artifacts only.** A process lists the keys it wrote and the keys it read or wrote beside the directory (`value-outputs-written-in-run-<run>.txt`, `value-outputs-used-in-run-<run>.txt`). `upload-passed-compile-checks` puts the outputs it wrote, never a restored one, in the run's artifact under `value-outputs/`, and `restore-from-artifacts.js` adds each output of the newest artifacts of the job's identity that the directory lacks. What makes a stale hit impossible is the pair: the file's name is the program's key (`build`: compiler, SDK, SafeDI module bytes, dependency versions; `harness`: describer, the four harness sources, runtime sources, a release's macros tool, loader variables; each module's name, package, dependencies, conditions, mock condition and normalized files; `main.swift`; the executable's name), and the artifact's identity covers the one input the key leaves out, this checkout's macro plugin, with the manifest, test arguments, compiler and the sharing actions. `share-compile-checks.yml` adds no outputs to main's shared list: that list is saved again whenever it grows, which outputs would make it do on nearly every run, by megabytes, in the cache quota the build caches need.
- **A branch's cache keeps only what its run used.** The restore adds other runs' outputs to the directory, so before a job saves its cache `.github/scripts/keep-value-outputs-used-in-run.sh` deletes every output the run neither read nor wrote, and the whole directory when it used none. Verify's groups each do so and hand their outputs to the job that saves the run's cache. An output dropped this way is read again from its artifact while that is among the newest, and compiled otherwise; a filtered run keeps only its own tests' outputs.
