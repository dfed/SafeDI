# Reserved names, nested types, and spelling

- **Names generated code introduces are reserved** (`ReservedName`, the one place they are spelled: `ScopeGenerator` emits them from its constants, and the macro checks against them). A seam's generated enums (`SafeDIScope_<Stem>`, `SafeDISendableScope_<Stem>`), the enums nested by type in a plain root (`<Type>_Scope`, the type as the seam's module spells it), and payload structs (`<case>_Values`, `<label>_Values` nested by type) take a trailing `_` where a field's type would resolve to the struct; every type nested in a root nested by type also takes `_` while a case, another generated type, or any type spelled inside the root has its name (`scopeEnumsByType`); a wrapping case's payload is bound in the seam's body as `__safeDI_<stem>Values_<label>`; a stem is the instantiated type's `simplified.asIdentifier`, its label lowered at the leading capitals. Generated bodies declare builder functions `__safeDI_<label>` (and `@Sendable`-extracted locals `__safeDI_<label>__…`) next to the `let <label>` they build, and a seam initializer only generated code calls labels its parameters `__safeDI_<label>` (`ReservedName.seamGeneratedOnlyArgumentLabel(of:)`, joined through `spelledAsJoinedIdentifier`, so a keyword needs no backticks and a raw identifier keeps them); the prefix keeps them out of the namespace of user labels, and it stays: any other scheme is more collision-prone and rewrites every generated file. Three kinds of exact name are reserved too, because generated code puts them in a scope with user names and cannot rename them: `safeDIOverrides` (the `mock()` parameter callers spell, which a mock parameter of that label redeclares and a body binding hides), `safeDIBuilder` (the property and initializer parameter of every `SafeDIMockConfiguration`, which a configured type's instantiated or default-parameter label redeclares, and the `if let safeDIBuilder` override binding in each construction expression, which therefore never shadows an argument), and the wrapper types generated code constructs by name (`Instantiator<T>(…)` and the other five, `Property.PropertyType.wrapperTypeName`), which a binding of that name hides. The macro tests pin that each is rejected; the evidence that each collides is in PR 410's description, because a fixture that declares one is macro-invalid and so cannot be a pipeline test. `SafeDIToolReservedNameTests` shows, with macro-valid fixtures, that the other names generated code introduces do not collide, which is what stops anyone reserving more than is needed: the `instance` closure parameter, and the generated members `SafeDIOverrides`, `SafeDIMockConfiguration`, `ForwardedProperties`, and `mock`, which a same-named property does not redeclare and which generated code never names where a binding could hide them. A new generated identifier in a scope with user names must be added to `ReservedName`, with such a test. The `@Instantiable` macro rejects every name it can see that generated code binds or refers to: property labels and `fulfilledByDependencyNamed:` names (`InstantiableVisitor`), the names of `instantiate(…)` parameters without a default value (also the visitor), and the argument labels of labeled, default-valued, non-dependency parameters of the construction initializer, `instantiate(…)` methods, and mock methods, which a mock root takes as `mock()` parameters (`validateReservedParameterLabels`, the same parameters `validateDefaultExpressions` checks). The property macros do not check, so nothing is reported twice. Only a prefixed parameter label gets a fix-it (rename the argument label to the label without the prefix, keep the parameter's name): renaming a dependency can change which dependency it fulfills or receives, because SafeDI matches by label, with no error, and an exactly reserved label has no evident replacement. `generate` does not check: SafeDI is upgraded per project at once, so every module's names have passed the macro.
- **Nested-type qualification.** `normalizingInstantiableTypes(of:plainTypeDeclarations:)` qualifies every type a declaration spells – each dependency's property type and alias `ofType:` type, every argument of its initializer, other initializers, and hand-written mock (dependency or default-valued alike, each by itself, so a dependency's argument is qualified as its property), and the mock's return type – in two steps. First `TypeDescription.qualifyingInstantiatedType(within:amongInstantiableTypes:searchingTypesEnclosingIt:namesOfNestedInstantiableTypes:)` qualifies the type `asInstantiatedType` returns (`Instantiator<Service>?` → `Instantiator<Feature.Service>?`, `LazilyInstantiated<any Service>` → `LazilyInstantiated<any Feature.Service>`, so a by-value receiver of `any Service`, qualified the same way, still matches `lazilyInstantiatedInstanceType`), choosing the most qualified of `nestedOptions` that an `@Instantiable` fulfills, so a nested type wins over a top-level type of the same name, as the compiler resolves it; `fulfilledByType:` gets only this step, restricted, on an extension-based declaration, to the extended type's own nested types and the name as written. Then `TypeAccessProof.NestedTypeQualifier` nests each outermost name the type spells, anywhere in it (generic arguments, closures, tuples, optionals), as Swift resolves it where the declaration is written: the most qualified option of `nestedOptions` that is an instantiable type or a plain declaration (`PlainTypeDeclaration`) the declaration's module can name, else the name as written; a declaration another module nests in a type whose name the mentioning module itself declares is no option, since the module's own type shadows the other's (`PlainTypeDeclarations.candidates`). A member of an extension-based declaration is written at file scope, so only the extended type's own nested types are options there, in both steps; `fulfillingAdditionalTypes:` is written outside the type, so it is qualified within the type enclosing it, and on an extension by neither step. The generated code is outside the declaration – another type's tree, a mock or `SafeDIMockConfiguration` in an extension of the nested type, a seam's initializer, a public mock's module-level configuration – and there `Mode`, declared in `Feature` beside `Feature.Child`, does not resolve; so every generator reads the qualified types and qualifies nothing itself. A module keeps the plain declarations nested in the outermost type enclosing each `@Instantiable` type of any clause and those its declarations mention (`keptPlainTypeNames(of:)`), so every run that reads the type's file, and every `.safedi`, holds what the qualifier reads. A declaration SafeDI knows no module of counts as the mentioning declaration's module's (normalization runs before the run knows its own files). Most names name no nested type, so the qualifier searches a name's options only when a nested instantiable type or a nested plain declaration a mention can find has that name (`namesOfNestedTypes`, backticks dropped), or when the enclosing type's outermost name is a module's, whose top-level declarations a mention spelled with it names; the instantiated-type step likewise searches the nested options only for a name a nested instantiable type has. Any new way `PlainTypeDeclarations.candidates` can find a declaration must keep that check a superset of it. Both steps return `nil` when they change nothing, and normalization keeps a dependency, argument or type they leave unchanged rather than rebuilding it. A type inherited from a superclass or a protocol, and a default *expression* (`= Mode.fast`, copied as written into the type's extension), are not qualified, and where an inherited nested type shadows one of the enclosing types', the qualified type is the enclosing type's and the generated code does not compile. Unqualified, `mockReturnTypeIsCompatible` fails against `Feature.Consumer`, and the hand-written mock is silently skipped; doing it while normalizing, before `resolveSafeDIFulfilledTypes`, keeps `mockInitializer`, `mockReturnType` and `mockDeclarationLocation` together through both mockOnly merge branches, and makes a provider and a receiver that spell one type differently (`Grandchild.NestedType` and, inside `Grandchild`, `NestedType`) match. `replacingInstantiatedType` walks the same path through a type as `asInstantiatedType`: both read `TypeDescription.builtGeneric`, which names the built generic of each wrapper and whether its own instantiated type is read through it (`LazilyInstantiated`, whose generic may be `any Service`), so a new wrapper type is added there once.
- **Identifier spelling.** Labels and parameter names are stored in `spelledAsIdentifier` spelling: backticks only where Swift requires them to declare or name a value. Every call-site label goes through `spelledAsArgumentLabel`. Every name joined from a label (`__safeDI_` + label, `label_lazilyInstantiated`, sibling, alias, and override-local suffixes) goes through `spelledAsJoinedIdentifier`. Tuple element labels follow the same spelling. A new emission site that interpolates a label directly compiles for every label the fuzzer draws and breaks only for a keyword or a raw identifier, which the fuzzer never draws, so only a keyword-label test catches it.
- **`TypeDescription ==`/`hash` ignore `any` at every depth.** `any P` equals `P`, `(any P)?` equals `P?`, `Instantiator<any P>` equals `Instantiator<P>`, and `(any P).Type` is treated as `P.Protocol` (not `P.Type`, which is `any P.Type`). `some P` stays distinct. Sets and dictionaries keyed by `TypeDescription` or `Property` therefore merge the two spellings, keeping whichever was inserted first, while `asSource`/`asIdentifier` keep each declaration's own spelling. `<` compares the spelling without `any` first, then the full spelling as a deterministic tiebreak, so two spellings of one type are equal under `==` but ordered under `<` (determinism was chosen over the Comparable contract). Any new map or set keyed by a type's spelling string (`asSource`) instead of `TypeDescription` must normalize `any` the same way, or it will miss matches `==` makes.

## Types the expression parser cannot read

`TypeDescription` keeps everything a type's spelling carries, so `asSource` gives back a type Swift reads as the same one: a closure's `throws(E)` (`thrownType`; `==` and `hash` read `throws(any Error)` as `throws`, as Swift does), a variadic parameter (`.variadic`), an attribute's qualifier and arguments, as text without the `@` (`Space.Act`, `convention(c)`), a specifier that follows the attributes (`lateSpecifiers`, kept in `specifiers`, which `asSource` spells first because Swift reads `nonisolated(nonsending)` only there), and a value generic argument (`.unknown`). Swift's expression parser does not read `nonisolated(nonsending)` in a generic argument (6.4 reports "consecutive statements on a line"), so a wrapper of such a type is constructed by its bare name under a type annotation (`spelledForConstruction`, `isConstructedByAnnotation`).
