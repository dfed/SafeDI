# Mock root promotion and parameter naming

- Extension-based `@Instantiable` types use `static func instantiate(...)` instead of `init(...)`. Their `@Instantiated` dependencies are constructed by the parent scope. Each `instantiate` parameter without a default value is a `@Received` dependency (`InstantiableVisitor`), named by its inner name, which the macro rejects when it is `_` (Swift lets two parameters share only that name, and generation keys a type's dependencies by name); a default-valued one is not a dependency, exactly as a default-valued non-dependency `init` parameter: the production call leaves it out, a generated mock offers it as an override, and the macro gives `instantiate` the checks an initializer's default-valued parameters get (`InstantiableVisitor.instantiateFunctions`).
- When a received dependency is promoted to root scope, the producer branch must capture the root-bound value — not reconstruct the type.
- `collectReceivedProperties` returns as `onlyIfAvailable` only properties that every receiver receives only if available. A property one receiver requires and another receives `onlyIfAvailable` is required — the collision is real, because an `onlyIfAvailable` alias's fulfilling property is non-optional (`@Received(fulfilledByDependencyNamed: "x", ofType: X.self, onlyIfAvailable: true)` yields `x: X`). Treating such a property as only-if-available skips its promotion, and the required receiver is handed `X?`. `createMockRootScopeGenerator` applies the same rule across the root's tree and the promoted scopes' trees, and `ScopeGenerator.onlyIfAvailableUnwrappedReceivedProperties` applies it to each subtree, so sibling ordering and mock parameters agree with promotion.
- A received constant whose type has `@Forwarded` properties is never promoted (`mockCanBuild`): the mock has no values to forward, so the dependency stays received and `mock()` takes it as a flat parameter, as production never `@Instantiated`s such a constant. The promotion loop and the worklist that collects promoted scopes' received properties both apply the check; a worklist that walked an unpromoted scope would promote its received dependencies into unused `SafeDIOverrides` entries.
- The mock root's own aliases are bound in the mock body's top-level scope, next to the dependencies promoted to the root and the `onlyIfAvailable` override bindings — production never puts them together, because it builds a type's aliases inside the scope that builds the type. `renamingAliases` binds an alias whose label one of those top-level bindings already uses as `<label>_<simplified type's asIdentifier>`, and the rename joins the tree's disambiguation map (receivers rebind it to the label) and the return-argument map. Only a binding redeclares: an alias whose label matches a flat parameter shadows it legally and keeps its name.
- A mock root can list the same property twice: promotion collects a promoted scope's received properties without subtracting what the root already instantiates. `orderedPropertiesToGenerate` emits only the first child for each property; emitting both produces two identically-labeled siblings, which sibling disambiguation renames to the same `label_Type_` name — an invalid redeclaration and a duplicate `SafeDIOverrides` field. What the calls of other modules' public mocks in a promoted scope's tree pass, or build when passed `nil`, is the exception: such a call takes the optional form of what it is passed, which no child of the mocked type's own matches by property, so `createMockRootScopeGenerator` leaves out of those sets what the mocked type declares, by the rules the received-property walk's `record` applies at every scope (`ScopeDeclarations.providesWhatPublicMockCallPasses` and `providesWhatPublicMockCallBuildsWhenNil`); otherwise the mock builds a second instance for the call, or a public mock takes it as a parameter.
- **Each form of one label is promoted on its own.** `createMockRootScopeGenerator` promotes every received property the mock can build as its own sibling, keyed by the exact property: `x: X`, `x: Instantiator<X>` and `x: ErasedInstantiator<(), AnyX>` become three siblings, which sibling disambiguation names apart (`x_X`, `x_Instantiator__X`, `x_AnyX`), each bound to the receivers of its form. A `@Forwarded` or default-valued parameter of `mock()` keeps its label, so it takes part in the mock root's sibling disambiguation without being renamed (`disambiguatePropertyLabels(besideParametersKeepingTheirLabels:)`, computed once as `MockRootParameters.rootLabelMap`): a promoted dependency under its label is named apart (`x_Instantiator__X`, `user_Draft`) instead of hiding it from the mocked type. It skips only an optional property whose non-optional form it promotes (that node binds a non-optional value, which the optional receive is handed) and the by-value form of a promoted `LazilyInstantiated`, optional or not. Never deduplicate promotions by `asInstantiatedType`: keeping one form by spelling order made the `mock()` signature, and whether a graph is accepted, depend on how the type's name sorts against `Instantiator<`. Promoted siblings, one form each, follow `inOrderTheMockTreeFirstReceives` (below), which meets each form where a receiver of it is declared. `Property.precedesInMockOrder` – label, then `PropertyType` order, then type – orders the flat received parameters and the `onlyIfAvailable` overrides, so one label's forms are listed by form there, whatever the type is named. `generateMockRootCode` decides whether the tree provides a received `LazilyInstantiated` – or its instance – with `isProvidedByTree`, never by label: an `Instantiator` node under the same label provides neither, so the mock takes the instance by value and wraps it. The mock never builds a node for the instance beside a received wrapper (the wrapper is promoted instead; see `lazily-instantiated.md`), but a promoted wrapper of the other kind declares the instance too: a `SendableLazilyInstantiated<X>` the tree requires provides `x: X` to an `onlyIfAvailable` `x: LazilyInstantiated<X>?` receive, which cannot be wrapped from it, since the tree declares it after the wrappers, so that receive keeps its override (`isProvidedByTree($0.asValidatedForDependencyCycles)`). The old key also promoted `x: (any P)?` over `x: any P`, because `(` sorts first, and the receiver of `x: any P` read the node before its declaration.
- Promoted dependencies are siblings at the mock root, and an `onlyIfAvailable` receive deep in one sibling's subtree resolves against another sibling by Swift lexical scope. Availability therefore depends on emission order: an `onlyIfAvailable` receiver may only see siblings emitted before its subtree. The promoted siblings follow the mock root's own children in the order the mock's tree first receives them, never in label order: `inOrderTheMockTreeFirstReceives` walks the root's own dependencies in declaration order, then each instantiated child's tree depth first, then the trees of the scopes the mock builds for required receives, which mirror the promotion worklist, and last the trees of the fills the calls of other modules' public mocks it met pass, so every promoted sibling is met. `orderedPropertiesToGenerate` takes that as its base order, so when two promoted siblings receive each other only if available, the one received later is emitted first and passed `nil`, as production builds the property declared later first; validation walks the same `mockRootScope`, so one order decides both the generated mock and the error a mock root reports. Any new emission path must thread `propertiesGeneratedLater` (production `generateCode`, mock `collectMockParameterTree`, both through `orderedChildren`) and pass `nil` for receives in it, or it will reference a `let` before its declaration. An `onlyIfAvailable` alias is always declared, `nil` where its fulfilling property is unavailable, so a receiver beneath reads it, never an enclosing property of its label, and it counts as generated before its later siblings. Availability is judged by one function for production, mocks and the functions lazy cycles close on: `NearestDeclarations.binding(of:)` in `Scope.createScopeGenerator`, after the scope's own created properties, reads the nearest declaration of the label (a mock root's bound properties and its own declarations joined, a seam's parameters, a cycle function's parameters, or the nearest scope's declarations, each hiding every declaration farther up) and finds the property unavailable when that declaration provides no form the receive reads, or a form it reads is being built between it and the receiver. A receiver built inside the ancestor it receives, or built as the property it receives (a type built by `xBuilder` receiving `xBuilder?`), gets `nil` too: `ScopeGeneratorUnderConstruction` records every form of the scope's own property as being built (`NearestDeclarations.build(_:)`) before it judges the scope's dependencies, until a scope nearer the receiver declares the label again – one that closes a cycle, or one built for another concrete type – whose declaration is what the receive is passed, as validation's `isFulfilledByNearerDeclaration` judges it, in production and mock generation alike, and its `binding(of:)` reads a property the scope creates itself first (`Scope.createdBinding(of:)`), which shadows the one being built. The test compile verifier compiles each test's fixtures and generated code to an object file (`-emit-object`, whole-module), so it reports SIL diagnostics as well as type errors: a nested function capturing a later local ("closure captures before it is declared") and `self` used before `self.init` in a production `init()` fail the test. `-typecheck` would miss both. It defines `DEBUG`, the test's conditions, and the module's `mockConditionalCompilation`, so generated mocks are compiled too. It also fails a test when the compiler reports a warning in a generated file, or at a fixture's line that a `#sourceLocation` directive in a generated file attributes generated code to, unless it reports the same warning in a fixture (generated code repeats the fixture's imports): a build that treats warnings as errors fails on a warning in generated code, which its author cannot edit.
- An `onlyIfAvailable` receive that is unavailable is passed `nil`, so it must not count as a provider below it. `validatePropertiesAreFulfillable` adds a scope's `onlyIfAvailable` received properties to its children's `receivableProperties` only when it or its unwrapped form is receivable at the scope and neither is still being built (`insertProperties`; in a mock, only a property still being built is unavailable); otherwise a required `x: X?` beneath one passes validation and the generated code names an undeclared or not-yet-declared `x`. A required receive that can resolve only to its non-optional form while that is still being built (`user: User?` under `user: User`, or in the type `user` builds) is a cycle, in production and mock validation alike, since no mock parameter can stand in for it: it is reported with the diagnostic the non-optional receive gets from the cycle walks, which match only exact properties — `dependencyReceivedInSameChainItIsInstantiated` when the receiving scope is built for the property, `throwIfInvalidCycle` for an ancestor — and only after those walks, so a graph they reject keeps its diagnostic. "Not @Instantiated or @Forwarded in chain" is only for a property nothing in the chain creates. A required `x: X?` that resolves to a sibling `x: X` — through an available `onlyIfAvailable` receive above it, or in a mock — orders that sibling first (`orderedPropertiesToGenerate` matches required received properties by their unwrapped form too), except beneath a scope that forwards `x: X`, which fulfills it, so that scope's `requiredReceivedProperties` leaves it out. Validation does not follow a required optional receive into its unwrapped type's scope, so a cycle through one (`x` requires the receiver's ancestor) is not reported and fails to compile, as it did before.
- A forwarded `x: X` fulfills every receive of `x: X?` beneath it, and an alias a type declares of its own forwarded property binds to that property, so neither is received from an ancestor. `ScopeGenerator.init` (`isReceivedFromAncestors` and the own-dependency loop), `DependencyTreeGenerator.walkReceivedProperties`, mock promotion, and the mock root's flat parameters all apply this, matching an optional receive by its unwrapped form. A check of the exact property alone promotes a second instance of the forwarded value, surfaces an unused `mock()` parameter, or passes `nil` for the forwarded value. Provenance decides whether two forms of a label are one instance in a mock: a property the tree creates is the instance of a `LazilyInstantiated` of its label, while a forwarded property comes from outside the tree and is never the source of another form of its label. So `createMockRootScopeGenerator` builds a promoted `x: LazilyInstantiated<X>` beside a forwarded `x: X` on its own (`x_LazilyInstantiated__X`) and does not let a required receive of the instance that the forwarded property fulfills promote the wrapper; `mockRootParameters` gives the instance of a wrapper beside a forwarded property that it does not build a parameter or override of its own (`lazilyInstantiatedPropertyByInstanceBesideForwardedProperty`), named after the wrapper, classified by the wrapper's receives, and kept out of the rename maps the forwarded property's receivers read; and the mocked type's own `@Instantiated x: X` is rebuilt as the `x: LazilyInstantiated<X>` its tree receives, whose instance `generateReturnArgumentList` passes the mocked type. A renamed form is passed to its receiver under the label inside the receiver's builder function, so `forwardedPropertyHiddenInPromotedTree` rejects a receive of the forwarded property beneath one, as production rejects the pair under any root; a `LazilyInstantiated` the mock does not build is passed by name and hides nothing.
- `orderedPropertiesToGenerate` holds `onlyIfAvailable` receives unwrapped, so it matches them against siblings by the sibling's unwrapped property, and it orders every `onlyIfAvailable` alias after its fulfilling sibling before any other `onlyIfAvailable` receive. A sibling whose tree receives the alias only if available is then generated with the alias unavailable (it is passed `nil`). An `onlyIfAvailable` alias reads its fulfilling property or that property's optional form (`Property.formsReadByOnlyIfAvailableReceive`), so a scope that declares or forwards either form is the alias's source and receives nothing of the label from above (`providesAFormReadByOnlyIfAvailableReceive`, in `ScopeGenerator` and `ScopeDeclarations` alike).
- The disambiguation maps flow through sibling accumulation and parent-to-child descent. Siblings at one level share one map (`combinedDisambiguationMap`, which `mergeSiblingDisambiguations` fills); only the descent into a node's builder function changes it: `removingRenames` prunes the renames the node's declarations and forwarded parameters hide, and `routingReceives(of:toParametersNamed:in:)` routes receives of the node's uncovered `@Instantiated` dependencies to their `mock()` parameters, as `generateMockRootCode` does over the mocked type's whole tree for its own. A change on the sibling path hands a sibling the instantiating type's parameter, where production hands it a value from above. Which receives a scope subtracts is decided once, by `Scope.propertiesToDeclare` (with `instantiatedDependenciesNotGenerated`), which `ScopeGenerator` and `ScopeDeclarations` both read; a second computation lets the mock tree and the received-property walk disagree about what reaches the mock root.
- `resolveSafeDIFulfilledTypes` can produce multiple map entries with the same `concreteInstantiable` under different keys (e.g., a merged entry under `MyService` and an unmerged entry under `ServiceProtocol`). These entries may have different mock info. The mock scope map uses scope-reuse by `concreteInstantiable` and a deterministic sort to handle this.
- `mockInitializer` on an `Instantiable` can be inherited from a mockOnly merge — it doesn't always mean the type declared its own mock. `generateMock` is never inherited. Use `mockReturnTypeIsCompatible(withPropertyType: concreteInstantiable)` to distinguish genuine hand-written mocks from inherited ones.
