# Mock root promotion and parameter naming

- Extension-based `@Instantiable` types use `static func instantiate(...)` instead of `init(...)`. Their `@Instantiated` dependencies are constructed by the parent scope. Each `instantiate` parameter without a default value is a `@Received` dependency (`InstantiableVisitor`), named by its inner name, which the macro rejects when it is `_` (Swift lets two parameters share only that name, and generation keys a type's dependencies by name); a default-valued one is not a dependency, exactly as a default-valued non-dependency `init` parameter: the production call leaves it out, a generated mock offers it as an override, and the macro gives `instantiate` the checks an initializer's default-valued parameters get (`InstantiableVisitor.instantiateFunctions`).
- When a received dependency is promoted to root scope, the producer branch must capture the root-bound value — not reconstruct the type.
- **A promoted member of a loop of builders that nothing outside its loop reads has no binding.** `A` receives `bBuilder` and `B`'s tree requires `aBuilder`, so `A.mock()` promotes both, as a loop (`ReceivedBuilderLoops` in `cycle-generation.md`), and only `__safeDI_bBuilder`'s rebinding reads `aBuilder`: a `let aBuilder` would be unused, which Swift reports. `ScopeGenerator.loopMembersReadOnlyInsideTheirLoop` finds such members on a mock root: neither among the mocked type's received or instantiated dependencies (by exact property where a child has it, otherwise by unwrapped property, so of a label promoted in two forms the construction reads only the form it names), nor depended on by a child outside its loop or by a rename the root declares, whose binding reads the member's. Only a generated child counts: a mock root lists a property again where a promoted scope receives one it instantiates (`A` instantiates `bBuilder`, which `X`, in promoted `xBuilder`'s tree, receives back), and only the first child listing a property is generated, so the second listing reads nothing. The member's function is declared, which the loop's wrappers hand, and its `SafeDIOverrides` entry stays, since the function reads it. A production scope's children are its type's own properties, which its initializer reads, so this arises only on a mock root.
- `collectReceivedProperties` returns as `onlyIfAvailable` only properties that every receiver receives only if available. A property one receiver requires and another receives `onlyIfAvailable` is required — the collision is real, because an `onlyIfAvailable` alias's fulfilling property is non-optional (`@Received(fulfilledByDependencyNamed: "x", ofType: X.self, onlyIfAvailable: true)` yields `x: X`). Treating such a property as only-if-available skips its promotion, and the required receiver is handed `X?`. `createMockRootScopeGenerator` applies the same rule across the root's tree and the promoted scopes' trees, and `ScopeGenerator.onlyIfAvailableUnwrappedReceivedProperties` applies it to each subtree, so sibling ordering and mock parameters agree with promotion.
- A received constant whose type has `@Forwarded` properties is never promoted (`mockCanBuild`): the mock has no values to forward, so the dependency stays received and `mock()` takes it as a flat parameter, as production never `@Instantiated`s such a constant. The promotion loop and the worklist that collects promoted scopes' received properties both apply the check; a worklist that walked an unpromoted scope would promote its received dependencies into unused `SafeDIOverrides` entries.
- A received erased instantiator is promoted only when its first generic argument names `X.ForwardedProperties`, is the type of the only `@Forwarded` property, or is a tuple of them whose every element's type is one bare name (`Property.mockBuildsFirstGeneric(of:)`, which `mockCanBuild` reads). Production accepts any tuple of them, and `X.ForwardedProperties` for any type `X` the fulfiller fulfills (`firstGenericMatchesForwardedProperties`); a mock that receives `ErasedInstantiator<Panel.ForwardedProperties, Panel>` filled by `DefaultPanel` takes it as a `mock()` parameter too. The gap is deliberate: a mock takes a received `ErasedInstantiator<(count: Int?, names: [String]), Child>` as a `mock()` parameter, because building it would remove the parameter that callers of the mock pass and bring `Child`'s tree into the mock, whose cycles, hidden labels, and access no tree had to pass, so a graph that worked would stop generating.
- The mock root's own aliases are bound in the mock body's top-level scope, next to the dependencies promoted to the root and the `onlyIfAvailable` override bindings — production never puts them together, because it builds a type's aliases inside the scope that builds the type. `renamingAliases` binds an alias whose label one of those top-level bindings already uses as `<label>_<simplified type's asIdentifier>`, and the rename joins the tree's disambiguation map (receivers rebind it to the label) and the return-argument map. It renames, the same way, an alias whose label a flat received parameter has: such a parameter is received by a promoted dependency's tree in a form the alias does not provide (an optional alias beside a required non-optional receive, or another type), so the alias's binding, though legal Swift, would hide it from those receivers. Renaming the alias rather than the parameter keeps `mock()`'s signature. A public mock that would rename a site of a hole (`MockTreeNames.rootHoleSiteProperties`) so is rejected, whatever other place it has (`publicMockHoleSiteBoundApartFinding`, `SafeDIToolPublicMockHoleBoundApartTests`, `SafeDIToolPublicMockHoleLabelTests`), so `renamingAliases` never renames a site: the mock hands its builders the mocked type's values by label and would hold two under the site's, which another place's builder, or the site's own where the mocked type builds a child that receives the site's value, would be handed. A site bound apart with no receive of its label, because the label equals a name SafeDI generates (a sibling or flat parameter named apart, a `LazilyInstantiated` wrapper's binding), is rejected too, at the hole's declaration with no note, by an error that names the generated value (`holeSiteBoundApartFromGeneratedName`). Which sites are bound apart is decided once, by `mockRootTopLevelNames`, which `generateMockRootCode` and the check both read. An internal or listed mock takes the dependency as a parameter under its label and has no site, so it accepts the shape: a deliberate gap, commented at both sites. An alias provides a receive in a promoted tree by `ScopeGenerator.provides` (its exact property, or the unwrapped form of an optional receive); `createMockRootScopeGenerator` promotes nothing for such a receive, or the mock builds a node and an override nothing reads.
- A mock root can list the same property twice: promotion collects a promoted scope's received properties without subtracting what the root already instantiates. `orderedPropertiesToGenerate` emits only the first child for each property; emitting both produces two identically-labeled siblings, which sibling disambiguation renames to the same `label_Type_` name — an invalid redeclaration and a duplicate `SafeDIOverrides` field. What the calls of other modules' public mocks in a promoted scope's tree pass, or build when passed `nil`, is the exception: such a call takes the optional form of what it is passed, which no child of the mocked type's own matches by property, so `createMockRootScopeGenerator` leaves out of those sets what the mocked type declares, by the rules the received-property walk's `record` applies at every scope (`ScopeDeclarations.providesWhatPublicMockCallPasses` and `providesWhatPublicMockCallBuildsWhenNil`); otherwise the mock builds a second instance for the call, or a public mock takes it as a parameter.
- **Each form of one label is promoted on its own.** `createMockRootScopeGenerator` promotes every received property the mock can build as its own sibling, keyed by the exact property: `x: X`, `x: Instantiator<X>` and `x: ErasedInstantiator<(), AnyX>` become three siblings, which sibling disambiguation names apart (`x_X`, `x_Instantiator__X`, `x_AnyX`), each bound to the receivers of its form. A `@Forwarded` or default-valued parameter of `mock()` keeps its label, so it takes part in the mock root's sibling disambiguation without being renamed (`disambiguatePropertyLabels(besideParametersKeepingTheirLabels:)`, computed once as `MockRootParameters.rootLabelMap`): a promoted dependency under its label is named apart (`x_Instantiator__X`, `user_Draft`) instead of hiding it from the mocked type. It skips only an optional property whose non-optional form it promotes (that node binds a non-optional value, which the optional receive is handed) and the by-value form of a promoted `LazilyInstantiated`, optional or not. Never deduplicate promotions by `asInstantiatedType`: keeping one form by spelling order made the `mock()` signature, and whether a graph is accepted, depend on how the type's name sorts against `Instantiator<`. Promoted siblings, one form each, follow `inOrderTheMockTreeFirstReceives` (below), which meets each form where a receiver of it is declared. `Property.precedesInMockOrder` – label, then `PropertyType` order, then type – orders the flat received parameters and the `onlyIfAvailable` overrides, so one label's forms are listed by form there, whatever the type is named. `generateMockRootCode` decides whether the tree provides a received `LazilyInstantiated` – or its instance – with `isProvidedByTree`, never by label: an `Instantiator` node under the same label provides neither, so the mock takes the instance by value and wraps it. The mock never builds a node for the instance beside a received wrapper (the wrapper is promoted instead; see `lazily-instantiated.md`), but a promoted wrapper of the other kind declares the instance too: a `SendableLazilyInstantiated<X>` the tree requires provides `x: X` to an `onlyIfAvailable` `x: LazilyInstantiated<X>?` receive, which cannot be wrapped from it, since the tree declares it after the wrappers, so that receive keeps its override (`isProvidedByTree($0.asValidatedForDependencyCycles)`). A requirement of the instance promotes no wrapper of another kind than a required non-optional wrapper of that instance (`createMockRootScopeGenerator`'s `requiredWrappersByInstanceProperty`): that wrapper provides the instance, as the one declaration production reads does, so a receive only if available of the other kind is not handed a wrapper the mock makes for it, and, where the required wrapper pins it (`MockReceivesPassedNil`), is passed `nil`, as production passes it.
- Promoted dependencies are siblings at the mock root, and an `onlyIfAvailable` receive deep in one sibling's subtree resolves against another sibling by Swift lexical scope. Availability therefore depends on emission order: an `onlyIfAvailable` receiver may only see siblings emitted before its subtree. The promoted siblings follow the mock root's own children in the order the mock's tree first receives them, never in label order: `inOrderTheMockTreeFirstReceives` walks the root's own dependencies in declaration order, then each instantiated child's tree depth first, then the trees of the scopes the mock builds for required receives, which mirror the promotion worklist, and last the trees of the fills the calls of other modules' public mocks it met pass, so every promoted sibling is met. `orderedPropertiesToGenerate` takes that as its base order, so when two promoted siblings receive each other only if available, the one received later is emitted first and passed `nil`, as production builds the property declared later first; validation walks the same `mockRootScope`, so one order decides both the generated mock and the error a mock root reports. Any new emission path must thread `propertiesGeneratedLater` (production `generateCode`, the mock's lowering `treeNames(of:readsFills:)`, both through `orderedChildren`) and pass `nil` for receives in it, or it will reference a `let` before its declaration. An `onlyIfAvailable` alias is always declared, `nil` where its fulfilling property is unavailable, so a receiver beneath reads it, never an enclosing property of its label, and it counts as generated before its later siblings. Availability is judged by one function for production, mocks and the functions lazy cycles close on: `NearestDeclarations.resolvingBinding(of:)` in `Scope.createScopeGenerator`, after the scope's own created properties, reads the nearest declaration of the label (a mock root's bound properties and its own declarations joined, a seam's parameters, a cycle function's parameters, or the nearest scope's declarations, each hiding every declaration farther up) and finds the property unavailable when that declaration provides no form the receive reads, or a form it reads is being built between it and the receiver. A receiver built inside the ancestor it receives, or built as the property it receives (a type built by `xBuilder` receiving `xBuilder?`), gets `nil` too: `ScopeGeneratorUnderConstruction` records every form of the scope's own property as being built (`NearestDeclarations.build(_:)`) before it judges the scope's dependencies, until a scope nearer the receiver declares the label again – one that closes a cycle, or one built for another concrete type – whose declaration is what the receive is passed, as validation's `isFulfilledByNearerDeclaration` judges it, in production and mock generation alike, and its `binding(of:)` reads a property the scope creates itself first (`ScopeRecord.createdBinding(of:)`), which shadows the one being built. The test compile verifier compiles each test's fixtures and generated code to an object file (`-emit-object`, whole-module), so it reports SIL diagnostics as well as type errors: a nested function capturing a later local ("closure captures before it is declared") and `self` used before `self.init` in a production `init()` fail the test. `-typecheck` would miss both. It defines `DEBUG`, the test's conditions, and the module's `mockConditionalCompilation`, so generated mocks are compiled too. It also fails a test when the compiler reports a warning in a generated file, or at a fixture's line that a `#sourceLocation` directive in a generated file attributes generated code to, unless it reports the same warning in a fixture (generated code repeats the fixture's imports): a build that treats warnings as errors fails on a warning in generated code, which its author cannot edit.
- An `onlyIfAvailable` receive that is unavailable is passed `nil`, so it must not count as a provider below it. `validatePropertiesAreFulfillable` adds a scope's `onlyIfAvailable` received properties to its children's `receivableProperties` only when it or its unwrapped form is receivable at the scope and neither is still being built (`insertProperties`; in a mock, only a property still being built is unavailable); otherwise a required `x: X?` beneath one passes validation and the generated code names an undeclared or not-yet-declared `x`. A required `x: X?` that only a non-optional `x: X` fulfills is an unsupported shape (`test-design.md`, "Unsupported shapes"): no check reports it while that `x` is still being built. "Not @Instantiated or @Forwarded in chain" is only for a property nothing in the chain creates. A mock of a supported shape still resolves one: where production fulfills a required `x: X?` with a forwarded optional and the mocked type's tree also requires `x: X`, the mock promotes one `x: X` for both forms, and `siblingGraph` orders that sibling before the receivers of `x: X?` (`ScopeGenerator.unwrappedOptionalRequiredReceivedProperties`; `SafeDIToolMockGenerationTests`' `mock_buildsPromoted…ProductionForwardsBesideNonOptionalForm` cells, by value, through a wrapper and through the mocked type's rename `ofType: X?.self`), except beneath a scope that forwards `x: X`, which fulfills it, so that scope's `requiredReceivedProperties` leaves it out. Validation does not follow a required optional receive into its unwrapped type's scope, so a cycle through one (`x` requires the receiver's ancestor) is not reported and fails to compile.
- A forwarded `x: X` fulfills every receive of `x: X?` beneath it, and an alias a type declares of its own forwarded property binds to that property, so neither is received from an ancestor. `ScopeGenerator.init` (`isReceivedFromAncestors` and the own-dependency loop), `DependencyTreeGenerator.walkReceivedProperties`, mock promotion, and the mock root's flat parameters all apply this, matching an optional receive by its unwrapped form. A check of the exact property alone promotes a second instance of the forwarded value, surfaces an unused `mock()` parameter, or passes `nil` for the forwarded value. Provenance decides whether two forms of a label are one instance in a mock: a property the tree creates is the instance of a `LazilyInstantiated` of its label, while a forwarded property comes from outside the tree and is never the source of another form of its label. So `createMockRootScopeGenerator` builds a promoted `x: LazilyInstantiated<X>` beside a forwarded `x: X` on its own (`x_LazilyInstantiated__X`) and does not let a required receive of the instance that the forwarded property fulfills promote the wrapper; `mockRootParameters` gives the instance of a wrapper beside a forwarded property that it does not build a parameter or override of its own (`lazilyInstantiatedPropertyByInstanceBesideForwardedProperty`), named after the wrapper, classified by the wrapper's receives, and kept out of the rename maps the forwarded property's receivers read; and the mocked type's own `@Instantiated x: X` is rebuilt as the `x: LazilyInstantiated<X>` its tree receives, whose instance `generateReturnArgumentList` passes the mocked type. A renamed form is passed to its receiver under the label inside the receiver's builder function, so `forwardedPropertyHiddenInPromotedTree` rejects a receive of the forwarded property beneath one, as production rejects the pair under any root; a `LazilyInstantiated` the mock does not build is passed by name and hides nothing. `DependencyTreeGenerator.receivesPassedNilInMockTree` walks every other such pair in the mocked type's own tree and in a promoted dependency's tree, which production builds above the mocked type, walking the own tree first and then the promoted trees, each depth first in declaration order, up to a type that declares the label, beneath which that tree's own validation applies. A required receive pins the declaration every receive of its label there resolves to to its type. So it rejects (`receivedPropertyHiddenInMockTree`) a required receive beneath a type there that requires the label, or after a required receive of it on its own type (reported at the later declaration), in a form no one declaration provides with it (`oneDeclarationFulfills`: the same property, its optional form, or a `LazilyInstantiated` and its instance; `HidingReceive.isRequired`: not `onlyIfAvailable`, for a receive and an alias alike), comparing the closest type above that receives the label and the type's earlier receives first, then every required receive above, so a receive only if available between the two hides neither: production cannot build the pair. A receive only if available that a required receive above it, on its type, or beneath it pins to a form it cannot read is always passed `nil` in production, so the mock passes it `nil` and offers it nothing: the walk returns, by label and by the concrete type that declares them, those a required receive on their own type or beneath it pins, which are pinned wherever their type is built (`MockReceivesPassedNil.pinnedWhereverBuilt`), and only the label of those a required receive above pins (`labelsPinnedFromAbove`), since that pins a place, not a type; `NearestDeclarations.binding(_:passingNilTo:)` holds them in the mock root's bindings, which a declaration nearer the receiver hides, `ScopeGeneratorUnderConstruction` makes each unavailable, and `ScopeGenerator` (`receivesPassedNil`, and an alias's `fulfillingPropertyIsPassedNil`) counts it as receiving nothing from above, so the mock root binds and offers the form only where another receive reads it, and passes the mocked type's own such receive `nil` (`generateReturnArgumentList`). Each scope of the generated tree records what its type's required receives of such a label read in the root's binding of the label, while that binding is the nearest declaration (`NearestDeclarations.recordRequiredReceives(of:)`), and a receive only if available beneath is passed `nil` where one of them pins it (`resolvingPassesNil(to:receivedBy:on:)`), so a type the mock's trees build twice, pinned in one place and not in the other, is passed `nil` in the one and reads the mock's binding in the other, as in production. The mocked type's own required receives are recorded for its own children only: a promoted dependency's tree is built above the mocked type (`MockReceivesPassedNil.promotedProperties`). Two `onlyIfAvailable` receives are accepted and pin nothing, because production fulfills each in some placement and the mock offers each its own override, the surface two sibling receivers of the label get; a receive only if available beside a required receive in another type's subtree, which the walk does not compare, keeps its override too. An alias receives its fulfilling property's label (`propertyReceivedFromAbove`), unless its own type declares that label, which the alias then renames, except an alias that keeps the label it retypes. It rejects the pair whichever form the mock names apart and at every depth, so whether a mock is accepted never depends on its binding names. A label repeated along one branch is not encouraged, but the rule rejects only what would not compile or would mislead, and a mock misleads when it stands for a type production can build beneath no declaration or offers a value for a receive production always passes `nil`; a shape that compiles and matches production needs no generator support beyond what it has.
- `orderedPropertiesToGenerate` holds `onlyIfAvailable` receives unwrapped, so it matches them against siblings by the sibling's unwrapped property, and it orders every `onlyIfAvailable` alias after its fulfilling sibling before any other `onlyIfAvailable` receive. A sibling whose tree receives the alias only if available is then generated with the alias unavailable (it is passed `nil`). An `onlyIfAvailable` alias reads its fulfilling property or that property's optional form (`Property.formsReadByOnlyIfAvailableReceive`), so a scope that declares or forwards either form is the alias's source and receives nothing of the label from above (`providesAFormReadByOnlyIfAvailableReceive`, in `ScopeGenerator` and `ScopeDeclarations` alike).
- The disambiguation maps flow through sibling accumulation and parent-to-child descent. Siblings at one level share one map; only the descent into a node's builder function changes it: `removingRenames` prunes the renames the node's declarations and forwarded parameters hide, and `routingReceives(of:toParametersNamed:in:)` routes receives of the node's uncovered `@Instantiated` dependencies to their `mock()` parameters, as `generateMockRootCode` does over the mocked type's whole tree for its own. A change on the sibling path hands a sibling the instantiating type's parameter, where production hands it a value from above. Which receives a scope subtracts is decided once, by `Scope.propertiesToDeclare` (with `instantiatedDependenciesNotGenerated`), which `ScopeGenerator` and `ScopeDeclarations` both read; a second computation lets the mock tree and the received-property walk disagree about what reaches the mock root.
- `resolveSafeDIFulfilledTypes` can produce multiple map entries with the same `concreteInstantiable` under different keys (e.g., a merged entry under `MyService` and an unmerged entry under `ServiceProtocol`). These entries may have different mock info. The mock scope map uses scope-reuse by `concreteInstantiable` and a deterministic sort to handle this.
- `mockInitializer` on an `Instantiable` can be inherited from a mockOnly merge — it doesn't always mean the type declared its own mock. `generateMock` is never inherited. Use `mockReturnTypeIsCompatible(withPropertyType: concreteInstantiable)` to distinguish genuine hand-written mocks from inherited ones.
