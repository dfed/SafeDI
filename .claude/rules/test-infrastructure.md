# Test targets, fixtures and paths

- **`SafeDITool`'s tests span five test targets.** A release whole-module compile grows faster than its module's line count, so one module of every `SafeDITool` test was the longest step of CI's build; five modules compile in parallel. `SafeDIToolTests` tests the tool itself (scan, generate, configuration, conditional compilation, module info, query, paths, caches, spelling); `SafeDIToolDependencyTreeTests` production code generation (`SafeDIToolCodeGeneration*`, `SafeDIToolDependencyTreeGenerationTests`, and the `LazilyInstantiated`, deferred-cycle, lazy-cycle, forwarded-tuple, `Sendable` builder and `onlyIfAvailable` rename tests); `SafeDIToolMockTests` mock generation (`SafeDIToolMock*`, `SafeDIToolPublicMock*`, `SafeDIToolFlatMockParameterDefaultTests`, `SafeDIToolNestedTypeMockTests`); `SafeDIToolSeamTests` seams and access (`SafeDIToolSeam*`, `SafeDIToolAccessEnforcementTests`, `SafeDIToolUnreadTypeAccessTests`); `SafeDIToolFuzzerTests` the graph fuzzer's suites and `DifferentialValueComparatorTests`. A new test file goes in the target whose subject it tests. The helpers they share (`executeSafeDIToolTest`, the compile verifier, the graph fuzzer, the comparator) live in `Tests/SafeDIToolTestSupport`, a regular target that declares no tests and that no product lists, because Xcode 26 rejects a test target that depends on another test target (Xcode 27 accepts one). A package that depends on SafeDI never builds it, and Xcode's `SafeDI-Package` scheme builds only products, but a plain `swift build` of this package builds it, in release without `-enable-testing`, so the helpers import `SafeDIToolLibrary` without `@testable`, through the declarations the library makes `public` for them (no product lists the library, so `public` exposes nothing outside SafeDI's own targets; `package` would need a package name, which the `SafeDIGenerator` plugin, compiling `PluginTargetGraph.swift` through a symbolic link, does not have). A helper that needs another declaration of the library makes it `public` too. Every test file reaches it with `@testable import SafeDIToolTestSupport`, and the tool with `@testable import SafeDIToolLibrary`. SwiftPM compiles a regular target for the package's `platforms`, not for the host as it compiles a test target, so a helper that uses newer API than the package's `platforms` is marked `@available(macOS 13.0, iOS 16.0, tvOS 16.0, watchOS 9.0, *)`, as are the helpers that use it. SwiftPM's native build system (CI's) links every test target into one `SafeDIPackageTests.xctest`, so CI, coverage, and the fuzzer shards' `--filter 'SafeDIToolGraphFuzzerTests/longRun'` see one bundle as before; Swift Build builds one bundle per test target, as it did before the split.
- **Test fixture file naming controls processing order.** Files parse in parallel, so completion order is random; `ModuleInfo(_:)` therefore orders a module's file scans by path, so its instantiables are in source file path order, keeping each file's top-to-bottom declaration order, and its imports and mock imports are sorted and deduplicated, so the `.safedi` file `generate` writes is the same bytes every run; upstream `.safedi` module info is already in that order, and `loadSafeDIModuleInfo` returns the dependent modules in the path order of their `.safedi` files, whatever order the caller lists them in or the parallel reads finish in, so the combined list `resolveSafeDIFulfilledTypes` sees is deterministic without a second sort. `executeSafeDIToolTest` names fixture files by extracting the type name from `@Instantiable` in the source content, so those names decide the order. When testing ordering-sensitive behavior (e.g., which of the two mockOnly merge branches runs), pick names that sort the way you need, and be aware that an `extension MyService` file falls back to `"File"`. A configuration-only snippet also falls back to `File.swift`, so it exercises `parseModule`'s fallback path; pass `swiftFileContentByFilePath` (e.g. `["SafeDIConfiguration.swift": …]`) to name a fixture explicitly when the file name matters. A single-module test writes a `.safedi` only when it names its module (`moduleMembershipArguments` with `--module-name`), and a multi-module fixture that `omitsModuleName` writes none, so no other module may depend on it.
- **Tests never write to the system temporary directory.** macOS empties `$TMPDIR` at startup before login, and the millions of entries killed test runs left there twice kept a Mac at the Apple logo for hours. Take every temporary path from `TestTemporaryDirectory` (`Tests/SafeDIToolTestSupport/TestTemporaryDirectory.swift`): `root` or `uniquePath(prefix:pathExtension:)`, one directory per test process in the user's caches directory (`$SAFEDI_TEST_TEMPORARY_DIRECTORY` overrides it, and must itself lie outside `$TMPDIR`: expectation recording refuses a directory inside the system temporary directory, so the tests of `ExpectationRecordingTests` that record fail under one), outside the checkout because fixtures inside the working directory would be read as part of the project. Give a process a test launches `TestTemporaryDirectory.environment(withTemporaryDirectory:)`, as `runProcess` does.
- **Tests must not depend on where the checkout lives.** The suite runs from checkouts under `/Users`, under `/tmp` (reached as `/private/tmp`), and through other symbolic links. Build an expected path by the rule the contract under "File path spelling" gives its consumer — for example the project root as the test handed it to `scan`, made absolute, joined with the file's path inside it, for `additionalInputFiles` — never from `currentDirectoryPath` or `NSTemporaryDirectory()` compared with a normalized path, and test a symbolic link by creating one, as `SafeDIToolPathSpellingTests` does. Under a plugin invocation that reports the fixture directory resolved, `generate()`'s diagnostics are at `NormalizedFilePath(fixtures.compilerPath(of:)).path`, and what `run()` prints is at `compilerPath(of:)` (see "File path spelling").
- **The compile verifier compiles to an object file and fails on a warning in generated code.** The test compile verifier (`SafeDICompileVerifier.swift`) compiles each test's fixtures and generated code to an object file (`-emit-object`, whole-module), so it reports SIL diagnostics as well as type errors: a nested function capturing a later local ("closure captures before it is declared") and `self` used before `self.init` in a production `init()` fail the test. `-typecheck` would miss both. It defines `DEBUG`, the test's conditions, and the module's `mockConditionalCompilation`, so generated mocks are compiled too. It also fails a test when the compiler reports a warning in a generated file, or at a fixture's line that a `#sourceLocation` directive in a generated file attributes generated code to, unless it reports the same warning in a fixture (generated code repeats the fixture's imports): a build that treats warnings as errors fails on a warning in generated code, which its author cannot edit. Every compile check and every graph fuzzer compile enables the `ExistentialAny` upcoming feature (`existentialAnyFeature` in `SafeDICompileVerifier.swift`). A warning in generated code is excused only when the module's own fixture draws the same message, or, for a missing `any` alone, the fixture of a module it imports (`warnings(_:excludingExistentialAnyMessagesIn:)`), since generated code copies the spellings of the declarations it reads and of nothing else; so a generated spelling that drops an `any` the fixture spells fails its test or its graph (`SafeDIToolMockExistentialAnyTests`, `SafeDIToolCompileVerifierTests`).
