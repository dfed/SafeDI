# Cycle mechanisms: generation

This file holds the mechanisms generation uses; the validation half of the table is in `cycle-validation.md`.

Multiple cycle-related mechanisms coexist — keep them distinct:

| Name | Scope | Set by / when | Role |
|------|-------|---------------|------|
| `isPropertyCycle` on a scope/node | Per-root, syntactic | `Scope.createScopeGenerator` when a property, as cycle validation sees it, repeats an entry of the ancestor stack built for the same concrete type | Terminates infinite descent during a single root's walk; differs between roots for the same underlying cycle. |
| `cycleEdges` (set of `CycleEdge`) | Global | `DependencyTreeGenerator.computeCycleEdges`, alphabetical-DFS feedback arc set | Chooses a single back-edge per cycle consistently across all roots — required because shared `SafeDIMockConfiguration` structs must have one shape. Consumed by struct generation AND override-path navigation in mock bodies. Each root returns the nodes of the types its tree configures (`collectConfigurationTypes`); `generateMockCode` keeps the first root's node for each type, in alphabetical root order, and only then generates that struct (`ScopeGenerator.generateConfigurationStruct`), so no root generates a struct that is thrown away. |
| `buildsInSendableFunction` on a `ScopeGenerator` | Per scope, from its subtree | `ScopeGenerator.init`, from `cycleClosedOnDeclarationsReferencedFromSendableFunction` | A builder function is `@Sendable` when its property is a `Sendable` wrapper, or when a cycle-closing scope refers to it from inside a `@Sendable` builder function that does not enclose it (A → `SendableInstantiator<B>` → B → `Instantiator<A>`): that function captures it. A builder made `@Sendable` this way holds its subtree's references too, so the builders they name are marked in turn. Production generation, mock generation (decorator, `SendableOverrideExtractor`, `requiresSendable`), and `nonSendableWrapperCaptures` all read it. |
| Soft `onlyIfAvailable` edges in `orderedPropertiesToGenerate` | Per scope, siblings | `ScopeGenerator.orderedPropertiesToGenerate` | A required receive of a sibling always orders it first; an `onlyIfAvailable` receive does only when that does not close a sibling cycle. A child's receive of a sibling is `onlyIfAvailable` only when every receiver in the child's subtree receives it `onlyIfAvailable` (`onlyIfAvailableUnwrappedReceivedProperties`). When it would, the receiver's subtree is generated with that sibling in `propertiesGeneratedLater` and gets `nil`, matching production's "not available" semantics. Not an error. Every `onlyIfAvailable` alias waits, as a soft edge, on the sibling that declares its fulfilling property's label with a form it reads. One that a receiver in the subtree requires (`requiredOnlyIfAvailableAliasProperties`: a child's tree requires its property, or a fulfilling property of its label it provides a form of – `isRequiredByChild`; an `onlyIfAvailable` alias's generator lists nothing, and no alias of a scope renames another, so one pass finds the set) waits on that sibling as a hard edge, as a required alias does, and where no sibling declares the label, `requiredAliasFulfillingProperties` carries the fulfilling property up, pruned by the labels each scope declares or forwards, until the nearest declaration of its label orders it before the branch, also through a lazy cycle's parameters (`CycleParameter.requiredAliasFulfillingForms`). A child's own property is never such an edge: inside its tree the alias is `nil`. The sibling cycle check mirrors this (`ScopeDeclarations.requiredAliasFulfillingProperties`), and a provider that cannot be built first is a sibling cycle, which `childrenRequiringEachOther` reports. These sets only order children: they never make a mock parameter, a seam parameter or a cycle parameter required. The required edges are found by looking each child's received, unwrapped optional required, and alias-fulfilling properties up in a map from sibling property to index, or by testing each sibling when the child receives at least as many properties as there are siblings; either way the set is what testing every sibling pair gives, without the quadratic cost on a mock root's many children. The soft edges are still added by walking siblings in order, which the result depends on. |
| `CycleParameter` (parameters of a function a lazy cycle closes on) | Per closed-on scope, per tree | `ScopeGenerator.init` finds them bottom-up (`foundCycleParameters`, from `cycleClosingRedeclaredLabels`); `Scope.createScopeGenerator` creates the tree again while any scope finds other parameters than it was created with | A cycle-closing scope of any kind (`isPropertyCycle`: constant, lazy wrapper or instantiator) calls the builder function of the scope it closes on, so the type it builds again receives each label from the nearest declaration on its own path, as every `@Received` property does. Each label the closed-on function's body receives from above it that a scope between it and one of its cycle-closing scopes declares (instantiated, aliased or forwarded, or as a parameter of its own builder function) is a parameter of the function, typed by the form the body receives that provides every other form (made optional when nothing requires it), or, where a receiver requires the label, by the required form that provides every other required form, which each call's nearest declaration provides, so a form the body receives only if available that it does not provide is passed `nil` in the body where no declaration that provides the required forms could provide it too (`B` requires `x: X` and its sibling `C` receives `x: Y?` only if available: the parameter is `x: X` and `C` gets `nil`), in the order a walk of the body first meets a receive of each label (`inOrderTheBodyFirstReceives`, which records that first receive as the parameter's `receiver`, and, where it meets the label at a scope closing the cycle on the same function – one that repeats the function's declaration, in either form, lazily instantiated or constant – keeps the receiver that scope was given, since a chain through that scope would grow with each pass and the parameters would never settle; a scope of the function's property that closes on a function built for another concrete type keeps its receiver too, a deliberate gap that changes only diagnostic text), never in label order, which the rename oracle would catch; the closed-on property's own label is none, since every call is made inside a tree that builds a declaration of it, so it is always `nil`; nor is any label the closed-on scope itself declares or forwards, since its own declaration is the nearest inside the function; a label no one parameter can pass – a required form beside a form the parameter cannot carry that a declaration providing the required form could provide too, as `B` requiring `x: X` and `C` receiving `x: LazilyInstantiated<X>?` only if available, which a call whose nearest declaration is `x: LazilyInstantiated<X>` would hand a value (rejected even where every declaration the calls see is a plain `x: X`, which the parameter cannot tell, so a later fix stays additive), or every form received only if available and no one parameter providing them all, as `B` receiving `x: X?` and `C` receiving `x: Instantiator<X>?`, or `x: LazilyInstantiated<X>` beside `x: X?`, whose parameter, made optional, offers no instance (a mock reports a receive beneath a declaration that does not provide it as hidden first, so only the shapes one declaration can provide reach a mock) – is the error `unpassableCycleLabel` (`UnpassableCycleLabel`, carried up the tree as `unpassableCycleLabelsInTree` and thrown by `validateCycleLabelsArePassable`, one error per label, for the production roots and in `createMockRoot`, so `reportingAll(of:)` reports a label two mock roots share once), at the label's first receive in the body, with a note at the declaration between that comes first in source order (`CycleParameter.Redeclaration`, which `cycleClosingRedeclaredLabels` carries for each label), since the type a cycle builds again would otherwise read the label from above the function. The scope declaring the function passes the binding in scope there – in a mock, its parameter or override, and `nil` for a label only calls of other modules' public mocks receive that the mock leaves out (`receivedOnlyByPublicMockCallsLeftOut`), as production passes `nil` where nothing above provides a receive only if available (`NearestDeclarations.binding(of:)`); each cycle-closing scope counts the parameters' forms among its receives (so its siblings order around it) and passes its nearest declaration, judged by the same function: the property, its instance, or `nil` when it is received only if available and the declaration is of another form, is still being built around the cycle-closing scope, or is generated after it. Inside the function the parameters hide every other declaration of their labels, as forwarded properties do: each replaces its label in `NearestDeclarations` for the body and for the scope's own receives and aliases (lazily instantiated instance sets likewise), so a receive there only if available of a form a nearer declaration does not provide, or of a label a scope in the body is built as, is passed `nil`, and an `onlyIfAvailable` alias of a parameter's label is bound from the parameter, with the parameter's optionality. A parameter required only through an `onlyIfAvailable` alias is optional (`CycleParameter.isRequired` reads `requiredForms` alone): its `requiredAliasFulfillingForms` only order the declarations where the function is called. Mocks emit the same parameters and arguments (`mockCycleParameterArguments`), with the renames the parameters hide removed inside the function. `validateTreeBuiltAgainByCycle` walks the tree built again at each cycle-closing scope with the cycle-closing scope's own context – the declarations between that bind the parameters (`newLabels`, until the tree declares a label again) and the properties receivable there that were not where the tree was first built (`newReceivableProperties`, from `ScopeToValidate.receivableDepthByProperty`) – threaded as the walk of a tree threads its own (`enterDeclarations`, `insertProperties`), and continues through every cycle-closing scope it meets whose context is new, memoized by the cycle-closing scope's parent, its property and that context (`TreeBuiltAgain`), so nested cycles end. It applies the hidden-label rule of every other path through the same check (`recordHiddenReceives`, with the changed context so the first build's judgments are not reported twice): a receive hidden by a new declaration is the hidden-label error where a scope above provides it, required or only if available; a receive hidden by the tree's own declaration, as on its first build, is the error where only a scope between provides it, which the first build passed `nil`; a receive only if available that nothing above provides is passed `nil`; and a required receive whose new nearest declaration is still being built is the dependency cycle error. A tree without such a redeclaration is created once and generates as before. A pass changes a scope's parameters only through what the cycle-closing scopes nested in its function passed in the pass before, so the passes end once each nesting depth has settled. Only the first pass starts each generator's code as it creates the generator, since nearly every tree takes one pass; a later pass collects its generators, and once the passes end the last pass's are started, since nothing reads the code of a pass that is not the last. `nonSendableWrapperCaptures` judges a parameter's label at the calls, never in the body: it counts each argument a call passes non-`nil` – the call of the scope declaring the function and of each cycle-closing scope – as a read at the calling scope, inside the scope's own `Sendable` wrapper closure when it has one, reported at the parameter's `receiver`, so a non-`Sendable` wrapper declared outside that closure, or outside a `@Sendable` builder function between the scope and the declaration, is the capture error, as the same receive outside a cycle is; the body reads the parameter, declared inside the function, which only a `@Sendable` builder function inside the body captures. `seamTierOmissions` and `publicMockTierOmissions` judge the label at the calls too (`OmissionFindings`): a call in the body of a seam's tier or of a public mock that omits a parameter's value is reported at the declaration each call of the function passes that provides it – the declaring scope's, unless it passes `nil`, and each cycle-closing scope's – and a call that passes a parameter of a function, its own or an enclosing one's, is judged by that function's calls in turn. |
| `cycleClosedOnDeclarations` and builder function names | Per generated body, per root | `ScopeGenerator.init` (bottom-up), then `ScopeGenerator.builderFunctionNames(for:enclosingFunctionNames:)` for each body, in production `generateProperties` and mock `generateMockBodyBindings` alike | A cycle-closing scope of any kind (`isPropertyCycle`: constant, lazy wrapper or instantiator) declares no builder function: it refers by name to the enclosing `__safeDI_<label>` function built for the declaration it repeats. Swift resolves that name to the innermost function of that name in scope, and a local function is in scope throughout its body (a later sibling included), so a builder function with the same name in any body between the two would shadow it: one for another property of the label, or one for a declaration of the same property built for another concrete type. `cycleClosedOnDeclarations` carries each closer's `closedOnDeclaration` – the declaration it repeats (`ScopeGenerator.BuiltDeclaration`: the property, the wrapper for a constant that repeats a lazy declaration's instance, and the concrete type it is built for) – up to the scope it closes on, which claims it only where its own `declaration` (property and concrete type) equals it; a body whose children carry one renames its function of that name `__safeDI_<label>_<built type's asIdentifier>` (underscores appended on collision), and `BuilderFunctionNames.enclosingFunctionNames` carries the names of referenced functions not named `__safeDI_<label>` (renamed, or sibling-disambiguated at a mock root) down to the closers. Bodies with no such clash keep their names, so their output is unchanged; the production cache key includes the names. |

## Eager instances at a lazy cycle's calls

A deliberate gap, to be fixed: where a call of the builder function a lazy cycle closes on passes a parameter taken by value from a `LazilyInstantiated` declaration, it passes the wrapper's `instance` (`cycleParameterArguments`, and `mockCycleParameterArguments` for mocks). So the instance is created when the function is called, eagerly, not when a receiver in the function's body first reads it, as the Manual's `LazilyInstantiated` section promises, and it is created even when nothing reads it. Every receiver gets the same instance it would if the read were lazy; only when the initializer runs, and whether it runs, differ. The per-type builders planned after 2.3.0 give each provided form its own function, which moves the creation back to the first read; that change is a defect fix. Until then, do not change this timing piecemeal, and do not add a test that pins it.

## How a `@Sendable` local function is spelled

Every `@Sendable` local function generated code declares – a builder function, a hole's wrapper function, a fill's stages, a dispatcher, in production, seams and mocks alike – starts with `ScopeGenerator.sendableFunctionDecorator`, `@Sendable nonisolated `, in every module. In a module whose declarations default to the main actor, a local function in a context on the main actor (an initializer or `mock()` of a type nothing else isolates, or of a type declared `@MainActor` or bound to it through `generatedInitializerAttributes` or `mockAttributes`) is on the main actor too, `@Sendable` or not, and the compiler rejects a synchronous `@Sendable` one there. Everywhere else a synchronous `@Sendable` local function is nonisolated already, so the keyword changes nothing (`SafeDIToolSendableBuilderDefaultIsolationTests`, `SafeDIToolSeamDefaultIsolationTests`). A new kind of `@Sendable` local function uses the constant, and a parser of generated code that matches such a function (the graph fuzzer's) matches the whole decorator.

## Walks

- **No synchronous recursion per level of a tree.** A dependency tree, a chain of received dependencies, a chain of siblings that require one another, and a mock parameter tree can each be as deep as the module has types, while `generate` and the tests run on concurrency threads, whose stack is half a megabyte on Apple platforms (a debug frame of the old instantiation walk took 40 KB, so a chain of 13 overflowed). Walk them with an explicit stack that keeps the recursive visiting order, so every diagnostic and memo is unchanged (the walks of `DependencyTreeGenerator`, `Scope.createScopeGenerator`, `ScopeGenerator.orderedPropertyToGenerateIndices`), or recurse through `async` functions, whose frames the task allocates (`ScopeGenerator`'s tree walks, the mock emitter `generateMockBodyBindings`, and the mock tree walks). An object that owns the next level of a tree hands what it owns to `DeferredRelease` in its `deinit` (`Scope`, `ScopeGenerator`, `MockTreeItems`); a new owning link needs the same, or releasing a deep tree nests a deinitializer per level. `SafeDIToolDeepTreeTests` builds chains deeper than any recursion could go.
- A memoized walk with a cycle sentinel must not cache a result that took nothing from a scope still being walked: that result is wrong from any other entry point, and which entry point walks first can follow set order. `collectReceivedProperties` keeps such results only until the scope they lack finishes its walk.

## Property kinds and erasure

- **`erasedToConcreteExistential: true` is orthogonal to the property's `PropertyType`.** The flag controls whether SafeDI wraps the concrete in the property's existential type at the call site; it does not determine whether the property itself is constant or lazy. The four combinations:

  | Decorator + property | `Property.PropertyType` | `isConstant` | Can be the deferred hop? |
  |----------------------|-------------------------|--------------|------------------------------|
  | `@Instantiated let x: Concrete` | `.constant` | `true` | No. |
  | `@Instantiated let x: Instantiator<T>` | `.instantiator` | `false` | Yes. |
  | `@Instantiated(erasedToConcreteExistential: true) let x: AnyProto` | `.constant` | `true` | No. |
  | `@Instantiated(erasedToConcreteExistential: true) let x: ErasedInstantiator<A, AnyP>` | `.erasedInstantiator` | `false` | Yes. |

  Any kind can close an accepted cycle and sit on a pruned back-edge; the hop that defers it is what the column says, and the erasure flag says nothing about either.
