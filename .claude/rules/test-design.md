# Designing a change's tests

Review findings cluster in the neighbors of a fix, not in the shape it was written for, so a change's tests are designed before its code.

- **Write the shape matrix first.** For each rule a change adds or fixes, list its neighbor shapes as failing tests before writing code: declaration order (before, after, inside its own tree); a type reached under two parents, only one of which provides the label; required, optional and `onlyIfAvailable` on the receive and on the owner; wrapper kind and what the caller holds (the instance, the wrapper, the other wrapper); its own property versus the tree's; each position across a module boundary (the boundary type itself, beneath it, inside a fill) under both kinds of integration (the SwiftPM plugin's scan, and `generate` per module as Bazel and Tuist run it); and how each property's type is spelled (plain, closure, `@Sendable` closure, optional closure, tuple, `any P`, nested, generic, typealias, another module's). Argue an impossible cell in a line.
- **Handwritten tests cover each rule's primary shape:** diagnostic text, location and fix-it; one full generated-output pin per rule; a failing-first regression test for every bug a review or the fuzzer finds; and configurations the fuzzer does not draw.
- **Siblings along an axis go to the fuzzer** when a draw reaches the axis with a pinned count and an oracle would fail on the defect the cell guards; a draw alone is not enough. When no draw reaches it yet, extend the fuzzer (`fuzzer-corpora.md`) rather than writing sibling unit tests, and say in the pull request why any sibling stays handwritten.
- **A new feature gets a differential oracle** that compares its output with a path whose output is known right: a seam against its inline build, a public mock against the internal mock, builder parameters against the same type built inline. A seam or public mock feature also gets a retention check against the inline build (`seam-and-mock-contract.md`, rule 3).
- **Regenerate expectations a change alters with `Scripts/regenerate-expectations.py`**, never by pasting actual output. The hook is `Tests/SafeDIToolTestSupport/ExpectationRecording.swift`: with `SAFEDI_TEST_RECORD_DIRECTORY` naming a directory outside the checkout and the system temporary directory, `executeSafeDIToolTest` and `executeSafeDIToolMultiModuleTest` record every output, and the exact-match assertion helpers every mismatch, with run paths replaced by placeholders; without it they record nothing, and recording never changes what a test compares. Record twice over the same `Tests/`: on the old generator (the commit that adds the change's failing tests) and on the new one, running `--write-manifest` after each (`SAFEDI_SKIP_COMPILE_CHECK=1` may skip compiles). Apply with the change's rules file, which predicts its renames and rewrites. Read every unexplained residual diff, every manual item, the changed outputs no literal matched, the compile-skipped list and the sample of explained literals in the report, update the manual and unmatched ones by hand, then run the tests with the variable unset, so compile verification checks the new expectations. The script's help gives the commands and the rules format. It rewrites only a literal that equals a whole output, in the test that recorded it (found by the location of the test the record carries when the call goes through a helper function): an expectation assembled from fragments, an assertion wrapper's parameter, `assertThrowsError(containing:)` and the query helpers are left to a person.
- **Expected output draws no warning SafeDI could foresee**, such as an unused binding: adopters build with warnings as errors and cannot edit generated code. When reviewing an expected string by hand, look for warnings as well as errors.
- **Expected output is written out.** A test compares a generated file with one string literal that spells the whole file, at the comparison. Only a value an argument of the test decides (the comment an integration puts on a seam call, a tier's access modifier), or a path the checkout decides (built as CLAUDE.md's "Tests must not depend on where the checkout lives" says), is interpolated, at its place in that literal and nowhere else. A value SafeDI computes, such as a seam's guard hash, is spelled in the literal, never passed in. A test that assembles expected text from fragments, or in a helper function that builds more than the one argument-decided value, breaks this rule: no tool can tell which part of the output each piece stands for, so every generator change is then made in that test by hand. A count or filtered lines may stand in for the whole file only for an output of thousands of lines, with a comment saying so; a test whose subject is a count or a size asserts it.
