# Designing a change's tests

Review findings cluster in the neighbors of a fix, not in the shape it was written for, so a change's tests are designed before its code.

- **Write the shape matrix first.** For each rule a change adds or fixes, list its neighbor shapes as failing tests before writing code: declaration order (before, after, inside its own tree); a type reached under two parents, only one of which provides the label; required, optional and `onlyIfAvailable` on the receive and on the owner; wrapper kind and what the caller holds (the instance, the wrapper, the other wrapper); its own property versus the tree's; each position across a module boundary (the boundary type itself, beneath it, inside a fill) under both kinds of integration (the SwiftPM plugin's scan, and `generate` per module as Bazel and Tuist run it); and how each property's type is spelled (plain, closure, `@Sendable` closure, optional closure, tuple, `any P`, nested, generic, typealias, another module's). Argue an impossible cell in a line.
- **Handwritten tests cover each rule's primary shape:** diagnostic text, location and fix-it; one full generated-output pin per rule; a failing-first regression test for every bug a review or the fuzzer finds; and configurations the fuzzer does not draw.
- **Siblings along an axis go to the fuzzer** when a draw reaches the axis with a pinned count and an oracle would fail on the defect the cell guards; a draw alone is not enough. When no draw reaches it yet, extend the fuzzer (`fuzzer-corpora.md`) rather than writing sibling unit tests, and say in the pull request why any sibling stays handwritten.
- **A new feature gets a differential oracle** that compares its output with a path whose output is known right: a seam against its inline build, a public mock against the internal mock, builder parameters against the same type built inline. A seam or public mock feature also gets a retention check against the inline build (`seam-and-mock-contract.md`, rule 3).
- **A claim about what a comparison checks names the test that fails without it.** Wherever a comment, a rule or a pull request says a comparison or an oracle checks something, or forgives a difference because something else catches it, it names the test or the seed that fails when the claim is made false: the check removed, or the forgiven difference made in the generator by hand. A normalization that hid swapped values, and a reordering forgiven because "the renamed graph is compiled", which it never was, were each found by a reviewer reading the diff, rounds after the code was written. For a new oracle this is `fuzzer-corpora.md`'s "A new oracle shows it fires".
- **Three forms of test pass with their change reverted,** so none is a change's only test. A test that compares generated output with generated output under another setting (memo on and off, plan on and off) is equal when the change does nothing: beside it, assert that the change applied, as a count of what was reused or shared. A change that makes work cheaper is pinned by a count of that work (elements written, places built, passes run), never by its unchanged result or by a time. A fix for a defect only a release build or a newer compiler shows names the CI job that builds that way and runs the fixed path, since a debug test cannot fail on it.
- **Regenerate expectations a change alters with the `regenerate-expectations` skill** (`.claude/skills/regenerate-expectations/SKILL.md`), never by pasting actual output: record what the tests compare on the old and on the new generator, apply with a rules file that predicts the change, read every item the report lists, and run the tests again so compile verification checks the new expectations. A tool only agents run is a skill in `.claude/skills/<name>/`; `regenerate-expectations` rewrites the test expectations a change alters (its SKILL.md says how). Then read the rewritten expectations by class with `review-expectation-diffs`, which accepts the forms an approved-differences file lists and shows each new form once, with its count.
- **Unsupported shapes get no test or draw.** A dependency declared implicitly unwrapped (`x: X!`, received, renamed, forwarded or instantiated) and a required `@Received let x: X?` that only a non-optional `x: X` fulfills (through an only-if-available receive above it, or in a mock whose production tree fulfills it with no optional declaration) are neither supported nor rejected: SafeDI may generate anything for them, including code that does not compile, and no handling, test, cell or fuzzer draw keeps them working. A test whose subject is another rule uses a real shape instead: `@Received(onlyIfAvailable: true) let x: X?`, or `x: X`. Kept: a required receive of `x: X?` that an optional declaration fulfills (a forwarded optional, a rename `ofType: X?.self`), with its mock, which promotes one `x: X` for it and a required `x: X` elsewhere in the tree and builds that `x` first (`mock-root-promotion.md`); a seam remedy that names no providing form for a required `x: X?` beside a wrapper (`LabelCollisionRemedy.receiveTheSameWay`), since the wrapper's instance is non-optional; a `!` inside a generic argument of a spelled type (`fulfilledByType: "Box<(any Q & P)!>"`), which is no `X!` dependency; the diagnostics that steer the unsupported forms to a real one, the macro's error for an `@Instantiated` optional or implicitly unwrapped property, and `TypeDescription.implicitlyUnwrappedOptional`, since `!` still parses inside a spelled type. A fuzzer failure that reduces to one of these shapes changes the draw, never the generator.
- **Instantiated only if available: where the property is `nil`.** A property nothing fulfills (`DependencyTreeGenerator.instantiates(_:)`) is `nil` in a root’s tree (`unavailableDependency(_:)`; a hole without a place where the module holds a seam, `SeamHoles.takesBuilders`). A seam takes a builder returning the optional, its stem ending `Optional` and named apart before a required builder’s (`stems(of:)`), which a root that cannot fill it fills with `nil`; a seam of a module SafeDI knows no name of takes no builder, so the property is `nil` there too (`populatePropertiesToGenerate`). A mock keeps it a declaration (`unavailableDependency(_:)`), bound where production binds `nil`, from an override that defaults to `nil` (`MockRootParameters.unavailableDependencyOverrideProperties`): one per label and type, a `SafeDIOverrides` entry of an internal mock, so `query needs` requires nothing; where only a `mockOnly` declaration fulfills the type, the mock builds that fake. Never lower it as a receive, which would read the declarations above its type. The base corpus draws both halves (`addingDependencyInstantiatedOnlyIfAvailable`). Deliberate gaps of an internal mock, commented at `mockRootParameters` and the node’s binding: it stays `nil` inside a `@Sendable` builder function, which could not capture the override, and where `mock()` already takes a value of the label and type, which is another declaration’s. A public mock’s is a hole instead (`createMockTypeDescriptionToScopeMapping`: an only-if-available dependency nothing fulfills that `canBeHole` accepts), inside a `@Sendable` builder function too: its stem ends `Optional`, its builder returns the optional and defaults to `{ nil }` (`PublicMockParameter.DefaultKind.nilBuilder`; on `__safeDI_mock`, `.init(__safeDI_noScope: { nil })`), so it takes no override, and a calling mock fills each place with a type its module sees, as inline builds it there, taking the optional builder of `calling-mock-hole-builders.md`, or, seeing none, passes up a builder that defaults to `{ nil }` (`PassedUpBuilder.defaultExpression`). `SafeDIToolCallingMockInstantiatedOnlyIfAvailableTests` compares each cell’s values with the mocks built inline in one module.
- **Expected output draws no warning SafeDI could foresee**, such as an unused binding: adopters build with warnings as errors and cannot edit generated code. When reviewing an expected string by hand, look for warnings as well as errors.
- **Expected output is written out.** A test compares a generated file with one string literal that spells the whole file, at the comparison. Only a value an argument of the test decides (the comment an integration puts on a seam call, a tier's access modifier), or a path the checkout decides (built as `test-infrastructure.md`'s "Tests must not depend on where the checkout lives" says), is interpolated, at its place in that literal and nowhere else. A value SafeDI computes, such as a seam's guard hash, is spelled in the literal, never passed in. A test that assembles expected text from fragments, or in a helper function that builds more than the one argument-decided value, breaks this rule: no tool can tell which part of the output each piece stands for, so every generator change is then made in that test by hand. A count or filtered lines may stand in for the whole file only for an output of thousands of lines, with a comment saying so; a test whose subject is a count or a size asserts it.
- **Run only what you edited until it passes; then the whole suite once.** While fixing tests or their expectations, run the suites you touched: `SAFEDI_SKIP_COMPILE_CHECK=1 TMPDIR=~/Library/Caches/SafeDITests/swiftpm swift test --traits sourceBuild --filter 'SuiteOne|SuiteTwo'` (a regular expression over `Target.Suite/test`; `TMPDIR` as "Build & Test" in `CLAUDE.md` says). After an incremental build, fourteen suites of 891 tests ran in 18 seconds, against 3.5 to 5 minutes for the suite; a slice that ran the suite after each of a dozen fixes waited 40 minutes for them. `SAFEDI_SKIP_COMPILE_CHECK=1` leaves out compiling the generated code, so it is for this loop only, and a test that needs the compile, such as a value oracle's or the comparator's, passes under it without checking anything: leave it unset when editing those. When the filtered run passes, run the whole suite once without it, as "Build & Test" in `CLAUDE.md` says, before handing back.
