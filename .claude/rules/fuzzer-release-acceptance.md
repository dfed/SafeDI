# Graph fuzzer: release acceptance

SafeDI measures breaking changes from its last stable release (`releases-and-packaging.md`). Release acceptance checks that for the base corpus: every graph the older release accepts must still be accepted, compile cleanly and build the same values. The harness is `GraphFuzzerReleaseAcceptance` (`Tests/SafeDIToolTestSupport/GraphFuzzerReleaseAcceptance.swift`), its tests and long run `SafeDIToolReleaseAcceptanceTests` (`Tests/SafeDIToolFuzzerTests`).

- **Both sides.** Each seed's graph is the base corpus's, drawn by this tree's generator storing every parameter (`GraphFuzzerGenerator.fixture(forSeed:storingEveryParameter: true)`), so the comparator can judge it. This tree runs in the test process as the corpus runs (`GraphFuzzerOracle.toolOutcome(of:)`, `scan` then `generate --swift-manifest`); the older release runs through its built `SafeDITool` as its SwiftPM plugin runs it (`scan` over a CSV of the fixture's files, every file mock-scoped, then `generate` with the manifest), never through its test suite, which writes into the system temporary directory. Each side's generated files compile with the fixture against that side's runtime and macros: the runtime the value comparator compiles from the release's `Sources/SafeDI` (`DifferentialValueOracle.runtimeArtifacts(for:)`), with the release's `SafeDIMacros-tool`. The older release is a parameter (`GraphFuzzerRelease`: its name, tool and `DifferentialValueRuntimeSource`), so a later release candidate can be compared with a beta the same way.
- **Classes**, first match in this order (`GraphFuzzerReleaseAcceptance.classify`):
  - A, the older release rejects the graph: its tool reports an error (`tool`), its macros reject the fixture, an error located in a fixture file (`macro`), or its generated code does not compile (`compile`). A graph the older release rejects cannot be a break.
  - C, this tree's tool rejects it.
  - D, this tree's generated code, or the fixture under its macros, does not compile.
  - E, this tree's generated code draws a warning, by message, that the older release's does not; generated code a `#sourceLocation` directive attributes to a fixture's line counts as generated (the compile spells those directives under a directory of its own, `GraphFuzzerReleaseCompilation.sourceLocationDirectoryName`, and prefixes each fixture file's name, so no two paths share a `#fileID`).
  - F, a probe both releases generate builds other values (`DifferentialValueOracle.compare`, this tree as the feature path, the older release as the known-right path); B, every probe agrees. The probes are each root and each generated mock without a required parameter (`differentialValueProbes(generatedFiles:)`); a probe only one release generates is skipped and counted by which (`GraphFuzzerReleaseProbeSkip`). Each instantiator with forwarded properties is called with the base corpus value oracle's samples (`GraphFuzzerSampleValues`).
  - X, the comparator could not describe a path: a harness failure, never a verdict.
- **Annotations**, which break nothing: `new-source-diagnostic`, a warning about the fixture this tree's tool or macros report and the older release's do not (a deprecation is one); `shared-generated-warning`, a warning both releases' generated code draws.
- **Listed seeds.** A break (C, D, E or F) fails the run unless `listedSeedsByRelease` lists the seed under the older release with that class: a known break, a release-noted behavior change, or an exemption, a defect of the older release this tree fixed. A listed seed of another class fails as stale. Against 2.2.0 the known breaks are #649's (an instantiator received only if available inside its own loop of instantiators is that instantiator, where 2.2.0 passed `nil`, and each receiver holds a wrapper of its own), class F: the graphs whose values differ and whose generated code shows a loop through received instantiators (`buildersReceivingEachOther` and its siblings among `GraphFuzzerFeature`). Each other listed 2.2.0 seed was reduced and bisected to the pull request its reason names, and ruled a change of 2.2.0 behavior that was wrong or surprising: #533, #571 and #572 (class F, the nearest declaration in a cycle), #593 and #597 (class C, a label received in two forms along a mock's tree), and #649's `@Sendable` loop rejection (class C). There are no exemptions.
- **What it does not compare.** 2.2.0 rejects a correct forwarded tuple as an erased instantiator's first generic argument and suggests the identical spelling as the fix (fixed since, by comparing the spellings without their differences), so about a quarter of the base graphs this tree accepts, every one drawing `addingForwardedTuples`' tree, are class A against 2.2.0 and are not compared. That is the verdict, not a gap to close: a graph 2.2.0 rejects cannot break. Neither are the seam and public mock corpora, whose features 2.2.0 lacks, nor what the comparator does not see (`fuzzer-value-oracles.md`). A unit test cannot run the older release, so the executable side is exercised only by the dispatched run: a broken runner makes every graph class A, which the compared-graph floor fails.
- **Tests.** The unit suite judges this tree against itself over seeds 0 to 3 (no break, three graphs compared), one hand-written graph whose two generated files pass one value differently (exactly that difference, class F), and the classifier once per class, rejection reason and annotation, from hand-written runs. The hand mutation that passes `nil` for every receive only if available fails seed 24 by value (F) and seeds 1, 107 and 114 by a new generated warning (E) over seeds 0 to 199.
- **Running it.** `graph-fuzzer.yml` with `release_acceptance` (the other inputs ignored): one job builds 2.2.0's tool and macros, at the commit its tag names, and packages them with its `Sources/SafeDI`, cached under a key that names the release, the commit, the runner's operating system, the container and a hash of `swift --version`; one builds this commit's test bundle; four shards of 1250 seeds run the long run (`SAFEDI_RELEASE_ACCEPTANCE_RELEASE`, `…_TOOL`, `…_MACROS_TOOL`, `…_RUNTIME_SOURCES`, `…_REPORT`, `…_SHARD`); and "Check Release Acceptance on Linux" combines their reports (`combine-release-acceptance-reports.py`). A requested run with a missing input fails rather than skips, a shard without a complete report fails, and the combine job fails on a missing shard, seeds not covered exactly once, a failure, a stale seed, a problem, or fewer graphs compared by value than `COMPARED_GRAPH_FLOOR`. Run it on dispatch and before each release candidate; it is no required check, since it runs only when dispatched. Locally, set the variables above (the shard optional) and run `swift test --traits sourceBuild --filter SafeDIToolReleaseAcceptanceTests/longRun`.
- **Pins.** The compared-graph floor and the listed seeds are derived from a dispatched run, never edited by hand to make a run pass: a new break is attributed (release-noted, or an older release's defect) or fixed.
