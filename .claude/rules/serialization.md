# Serialization

`scan`'s cache (`<manifest>.safediScanCache`, a `CachedScannedModuleInfo`) and `.safedi` module info files (a `ModuleInfoFile`: the module's own declarations under a non-optional module name, and its `view` – `ModuleInfoView`, `ViewedModuleIdentity`, `ViewedModule` – of the modules it depends on) are written in SafeDITool's own binary format, by hand rather than through `Codable` (`BinaryCoding.swift`, `BinaryCodableModels.swift`, `BinaryFile.swift`, all in `SafeDIToolLibrary`, never `SafeDICore`). These files are **regenerated every build** — there is no cross-version deserialization. Do not add backward-compatibility decoding logic. A header (magic, format version, schema fingerprint, body length, checksum) rejects any other file: an unreadable scan cache is a cache miss and a fresh parse, and an unreadable `.safedi` is an error naming the file. `BinaryFile.schemaDescription` and `BinaryLayout.description` spell every stored type and field type with `String(reflecting:)`, so the module names `SafeDIToolLibrary` and `SafeDICore` are part of `schemaFingerprint`: every build of the tool must name its modules that way (the SwiftPM targets, the prebuilt binaries, and `module_name` on the Bazel `swift_library` rules of `SafeDICore` and `SafeDIToolLibrary`), or its `.safedi` files are unreadable to the others, and no test catches it, because `swift test` cannot see a Bazel build. The plugin-read `SafeDIToolManifest` stays JSON. `generate` writes `--combined-output` and `--module-info-output` only when their bytes change (`Data.writeIfChanged(toPath:)`), and the `.safedi` last, after every validation, so a failed run publishes none: Bazel removes an action's outputs before it runs, so every Bazel run writes them, and Xcode's script dependency analysis compares a script's inputs with its last run's, so an unwritten output does not rerun the script forever (captured 2026-11-04 in DAN-2's design, T4b/T4d).

When a stored type changes, keep its coder in step:
- Each `BinarySchemaMember` writes its fields in initializer order and reads them back through that initializer, with each field's type choosing how it is read. A field whose type is not `BinaryCodable` fails to compile; so does an enum case the writer's exhaustive `switch` does not handle, and a tag the reader's `switch` does not handle.
- `binaryLayout` is what `BinaryFile.schemaFingerprint` covers: for a struct, each field it writes, in write order, as a `BinaryLayoutField` whose key path fixes the field's type, plus `unwrittenProperties`, the stored properties not written under their own name (`Dependency.asInstantiatedType`, `UnorderedEquatingCollection.set`, `Instantiable.instantiableTypes`, written as `concreteInstantiable` and `additionalInstantiables`, and `Property`'s stored hash, which is never written because hashing is seeded per process: a decoded `Property` goes through `Property.init(label:typeDescription:)`, which computes it again); for an enum, each tag's associated values, in declaration order, which is also the order written and read. A file written by a SafeDITool whose types write other fields, fields of other types, or the same fields in another order is therefore never read. `SafeDIToolBinaryFileTests` compares each struct's layout against `Mirror`, so a new stored property fails until it is listed, written, and read, and writes each field and associated value in turn with a value distinct from the rest (`BinarySample`), so a layout whose order or types differ from what the coder writes and reads fails too. A new stored type must join `BinaryFile.schemaMembers` and conform to `BinarySample` in the tests.
- A `BinaryReader` reads type descriptions nested at most `BinaryReader.maximumNestingDepth` (128) deep, so the writer notes a deeper one and `BinaryFile` refuses to write a file that holds it, naming the instantiable whose declaration names it, or the outermost type of a plain type declaration (`BinaryFileWriteError`): `scan` then writes no cache, and `generate` fails rather than write a `.safedi` dependents cannot read. Do not describe the deep type itself in such an error: spelling a type recurses as deeply as it nests, which exhausts a task's stack in a debug build.
- `executeSafeDIToolTest` checks, for every fixture that runs scan, that the cache reads back exactly what scan wrote (`reflectedDescription`, which sees private fields and spellings `==` ignores, and compares strings by their UTF-8 bytes, because `String`'s `==` calls canonically equivalent spellings equal while Swift compares identifiers byte for byte; the writer's string table keys strings by those bytes for the same reason), so a field the coder drops fails whichever tests give it a value.
- `Codable` conformances stay: the `dump` subcommand prints either file as JSON through them.
