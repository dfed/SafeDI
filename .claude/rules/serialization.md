# Serialization

`scan`'s cache (`<manifest>.safediScanCache`, a `CachedScannedModuleInfo`) and `.safedi` module info files (a `ModuleInfoFile`: the module's own declarations under a non-optional module name, the signatures its run computed of the seams it declares and the plans of the public mocks it declares (`seamSignatures`, `publicMockPlans`, see `seams.md`), and its `view` – `ModuleInfoView`, `ViewedModuleIdentity`, `ViewedModule` – of the modules it depends on) are written in SafeDITool's own binary format, by hand rather than through `Codable` (`BinaryCoding.swift`, `BinaryCodableModels.swift`, `BinaryFile.swift`, all in `SafeDIToolLibrary`, never `SafeDICore`). These files are **regenerated every build** — there is no cross-version deserialization. Do not add backward-compatibility decoding logic. A header (magic, format version, schema fingerprint, body length, checksum) rejects any other file: an unreadable scan cache is a cache miss and a fresh parse, and an unreadable `.safedi` is an error naming the file. `BinaryFile.schemaDescription` and `BinaryLayout.description` spell every stored type and field type with `String(reflecting:)`, and `schemaFingerprint` is the checksum of that description, checked in as a constant rather than computed at run time: reflecting on a type scans the runtime's protocol conformance tables, which cost about 170M instructions, most of a small module's `generate` under Bazel or Tuist. `SafeDIToolBinaryFileTests.schemaFingerprint_isChecksumOfSchemaDescription` recomputes it and, when a layout changes, fails with the new value to check in. So every build of the tool writes the same fingerprint, whatever its build system names its modules. The plugin-read `SafeDIToolManifest` stays JSON. `generate` writes `--combined-output` and `--module-info-output` only when their bytes change (`Data.writeIfChanged(toPath:)`), and the `.safedi` last, after every validation, so a failed run publishes none: Bazel removes an action's outputs before it runs, so every Bazel run writes them, and Xcode's script dependency analysis compares a script's inputs with its last run's, so an unwritten output does not rerun the script forever (captured 2026-11-04 in DAN-2's design, T4b/T4d).

What reruns after a change (the Manual leaves this out as performance detail): every `safedi_compile` action has the whole `SafeDIInfo.transitive_module_infos` depset among its inputs and names, with `--unused-inputs-list-output`, those it did not open as its `unused_inputs_list`, so under Bazel's local action cache a change to a module's declarations reruns the actions of the modules that list it and of those that opened it (a module with a root or seam whose trees reach a type nothing it lists declares), while a disk or remote cache, which keys on every declared input, reruns every module above it; an action whose outputs come out byte-identical reruns nothing after it. Tuist's script reruns when one of its target's Swift files or one of the `.safedi` files it reads changes, so a change in a module reruns the scripts of the modules that list it, and recompiles only the modules whose `SafeDIGenerated.swift` changed. Under either, a change to a declaration in a module that declares a seam or public mock, or in a module such a module reads, changes the `.safedi` of that module and of every module above it, since each carries those declarations in its view, and can change the generated calls of what they compute.

**A view that refers to modules.** Under `--module-info-views-refer-to-modules`, which the Bazel rule passes, a file stores `ModuleInfoFile.ownEntryChecksum` (the checksum of its position-free `ownEntry` without its seam signatures and public mock plans, `ViewedModule.checksum`, which says why that is sound; written right after `moduleName`) and its view lists each module it carries as a `ViewedModuleReference` (name and that checksum) in place of a `ViewedModule` copy. `ModuleReferenceResolver` turns references back into entries before anything reads a view: from a given file's own entry, or else from the file among `--transitive-module-info-file-path`'s that describes the module, found by reading only each file's first fields (`ModuleInfoFile.Head`, which neither checks the body's checksum nor decodes the string table) and then reading that file whole without its view. A reference no file resolves is `UnresolvableModuleReferenceError`; one whose checksum differs from the file's is `ModuleInfoDisagreementError`. The checksum has no positions, so a position-only edit leaves every referring file byte-identical. Tuist and custom builds that list modules keep copies, since a reader there may not be given the referenced files.

**Positions stored apart.** Under `--module-info-positions-in-own-file`, which the Bazel rule passes, a `.safedi` keeps each declaration location's file path and its rank among the module's distinct locations in that file (`Dependency.DeclarationLocation.order`, from 1), which orders locations as their lines and columns do, and writes the lines and columns to `Name.safedipositions` beside it (`ModulePositions.swift`: magic, the 8-byte checksum of the module info file's body, then the points, each `column << 1 | moved` and, when moved, the zigzag line difference from the location before, a range's end measured from its start). The main file spells a ranked location by parity (`-2 * order` before its line and column where it keeps them, `-2 * order + 1` alone where it stores them elsewhere), so a normal file's bytes are unchanged. An aliased `@Received`'s location is kept in the main file, since generated code prints its line (`AliasDeclarationReferences`). Nothing a run generates, and nothing that decides whether it succeeds, reads a line or column: every comparison of locations of one file orders by rank (`Dependency.DeclarationLocation.<`). A location read without its positions file has no line and column (`lineAndColumn` is `nil`), so only `SourceDiagnostic`, `AliasDeclarationReferences` and the query reports read one; a run whose error or warning prints such a location, or a fix-it whose range is stored elsewhere (`SourceDiagnostic.printsPositionStoredElsewhere`, which any new diagnostic that prints another module's line in its text must answer for too), runs again reading every positions file (`ModulePositionsReading`, `Generate.Output.readPositionsFilesInSecondRun`) and returns or throws what that run does. That run computes the stored seam signatures and plans where the first discarded them, so a failing build runs at most once more than with positions inline; an error located only in the module's own files, and an error not located in source, run once. A positions file missing, of another body, or of another count is a plain error naming both files, after the run's own diagnostics, only where a diagnostic of that run still prints a location of that module without its line; otherwise the run reports what it would have. `query` and `dump` read the positions file beside the `.safedi` they name and leave out the lines it would give where it is missing or does not pair. Ranks order and equate only locations of one module info file: a source file compiled into two modules is ranked in each separately, and comparing their ranks says nothing; no successful run is known to, since each type is declared by one module. Each positions file a run did not open is listed in `--unused-inputs-list-output`. Under Bazel's local action cache a line moved in a module, past no other declaration and no alias, changes only its positions file, so no action above reruns; a disk or remote cache keys on every declared input, positions files included. The multi-module harness runs every Bazel-flow module once more over split files and requires the same code, warnings and errors (`SplitPositionsRun`); the base corpus's `addingReadersOfRenamedLazyInstance` draws a warning whose choice of reader is decided by rank in a lower module's file.

When a stored type changes, keep its coder in step:
- Each `BinarySchemaMember` writes its fields in initializer order and reads them back through that initializer, with each field's type choosing how it is read. A field whose type is not `BinaryCodable` fails to compile; so does an enum case the writer's exhaustive `switch` does not handle, and a tag the reader's `switch` does not handle.
- `binaryLayout` is what `BinaryFile.schemaFingerprint` covers: for a struct, each field it writes, in write order, as a `BinaryLayoutField` whose key path fixes the field's type, plus `unwrittenProperties`, the stored properties not written under their own name (`Dependency.asInstantiatedType`, `UnorderedEquatingCollection.set`, `Instantiable.instantiableTypes`, written as `concreteInstantiable` and `additionalInstantiables`, and `Property`'s stored hash, which is never written because hashing is seeded per process: a decoded `Property` goes through `Property.init(label:typeDescription:)`, which computes it again); for an enum, each tag's associated values, in declaration order, which is also the order written and read. A file written by a SafeDITool whose types write other fields, fields of other types, or the same fields in another order is therefore never read. `SafeDIToolBinaryFileTests` compares each struct's layout against `Mirror`, so a new stored property fails until it is listed, written, and read, and writes each field and associated value in turn with a value distinct from the rest (`BinarySample`), so a layout whose order or types differ from what the coder writes and reads fails too. A new stored type must join `BinaryFile.schemaMembers` and conform to `BinarySample` in the tests. Any change to a layout then updates `BinaryFile.schemaFingerprint` to the value that test reports.
- A `BinaryReader` reads type descriptions nested at most `BinaryReader.maximumNestingDepth` (32) deep, since a debug build's read takes about 4.4 KB of stack per level and must fit in half of a concurrency thread's 512 KB (`read_fitsInHalfOfConcurrencyThreadStack_whenTypeNestsAsDeeplyAsSafeDIReads`), so the writer notes a deeper one and `BinaryFile` refuses to write a file that holds it, naming the instantiable whose declaration names it, or the outermost type of a plain type declaration (`BinaryFileWriteError`): `scan` then writes no cache, and `generate` fails rather than write a `.safedi` dependents cannot read. Do not describe the deep type itself in such an error: spelling a type recurses as deeply as it nests, which exhausts a task's stack in a debug build.
- `executeSafeDIToolTest` checks, for every fixture that runs scan, that the cache reads back exactly what scan wrote (`reflectedDescription`, which sees private fields and spellings `==` ignores, and compares strings by their UTF-8 bytes, because `String`'s `==` calls canonically equivalent spellings equal while Swift compares identifiers byte for byte; the writer's string table keys strings by those bytes for the same reason), so a field the coder drops fails whichever tests give it a value.
- A field a file repeats at many places, each a long collection, is written as `BinaryShared`: its first write writes the value, and every later write of an equal value only a reference, which the reader resolves to the same storage. `UncarriedDeclaration.placesInTree` needs it: every declaration beside one tree lists all of the tree's places, as many as its paths, so a deep hole graph's `.safedi` grew to 49 MB and took longer to write and read than its signature took to compute. The writer finds a shared value by its type and the bytes it writes with each string spelled where it is named (`BinaryWriter.writingStringsInline()`, `SharedValueIndicesByBytes`), since two values read back the same exactly when those bytes are the same. It also remembers each storage it wrote or found equal, and refers a later write of that storage to the same index without writing it again to compare: a module's view holds each value once per file it was read from, so the lifelike App's `.safedi` serialized 76,000 values for comparison and took 60% of its run.
- A module info's seam signatures (`ModuleInfoFile.seamSignatures`, `ViewedModule.seamSignatures`), and its public mock plans (`publicMockPlans`) alike, are written as `BinarySharingSignatureValues`: inside them, each type description, hole field (`SeamSignature.Hole.Field`) and uncarried declaration's reason (`UncarriedDeclaration.Reason`), at its outermost level, is written once and referenced afterwards (`writeSharedByBytes`), keyed by the bytes it writes, since `TypeDescription`'s `==` ignores `any`. Inside a value written in full, nothing is shared, so a value's bytes never depend on what was written before it. A signature names its seam's type and a few others at dozens of places, and repeats each field of a scope at every hole and route step that binds it: sharing types took E6d-600's Feature from 324 KB to 271 KB, and sharing fields and reasons took P2-200's Feat from 8.6 MB to 2.4 MB. A new type that a signature repeats joins them by writing and reading itself as `TypeDescription`, `Field` and `Reason` do; one whose values rarely repeat costs a hash of its bytes per write for nothing. Declarations outside the signatures are written as before. The writer finds what it wrote before without writing it again wherever the value in memory says so: a string by the two words that hold it, and a type description by the words of its enum case (`StringRepresentation`, `ValueRepresentation`, tables of `TableByWords`, which hash no bytes), and only a value held in other storage is written out and found by its bytes, which are compared against the bytes kept of each shared value, with no key built per write. The lifelike App’s file is 3.9 million values that name 2,959 strings and a few thousand types, and writing it took 1.1 s before this and 0.3 s after. The reader does the same from its side: a shared value is kept in a `SharedValueBox` of its own type, a `Property` inside a signature is found by its string’s index and its type’s reference, and a list inside a signature whose reading added no shared value is handed back, storage and all, when the same bytes come again, without being read (`readSharingStorageOfRepeats(_:)`), which took a quarter off the peak memory of the App’s `generate`. None of this changes a byte of a file: a change here is checked by comparing every `.safedi` and generated file of the benchmark shapes with the base tool’s. `Scripts/generate-time-check.py` fails a change that doubles any module's `.safedi` file on its shapes.
- A list a signature or a plan holds once per place, and that differs little from another place's, is written as a difference (`BinaryWriter.writeDifference(of:in:)`, read by `readDifference(in:)`, format version 4): the places of one type each list the declarations bound before them (`Hole.fields`, `EnumPlace.values`, `ScopeEnum.Values.fields`) and those bound after them (`Hole.uncarriedDeclarations`, `ScopeEnum.Values.labelsBoundLater`), so N places wrote N × N entries, and a public mock plan of 80 builders was 124 KB where it is now 34 KB. Each kind of list has a `BinaryDifferenceSlot`: the three lists of fields, which hold the same list for one place, share one. A list is written as how many lists back in its slot the list it differs from is, how many elements it keeps from that list's start and end, and the elements between in full; the list it differs from is the first list written of the same elements, where there is one, and otherwise the best of three (the last, the longest that starts with its first element, the longest that ends with its last), since places are written in label order; it is written whole where that is no longer. The reader hands back the storage of a list that is the whole of another, and of a list written whole whose bytes it read before, so equal lists are one storage once read, as they were when each was written whole; only the labels a case binds later, kept as a set, are held a second time while a module's signatures are read. A list read as a difference reserves its count before it is filled: grown as it was read, each held up to twice its elements, and the 150-screen App's `generate` 12 MB more. Elements are the same when the writer wrote them as the same bytes, so the reader gets what a list written whole gives, whatever the elements are; each element is written once, in place, and only its bytes are compared and moved (writing each a second time to compare made E24-fill's `generate` 4.8 times as long). `UncarriedDeclaration.builtAfter` names the place itself, so those lists are written without it (the declaration's one coder, told to leave it out) and it follows as runs of equal values, which the reader sets in the list it read, in place where nothing else holds it (`readDifference(in:readingElement:readingSuffix:applying:)`): a declaration is some 460 bytes, and holding each list once without `builtAfter` and once with it took 20 MB more of that App's peak. The same declarations built after the same places are one storage. Only where `sharesSignatureValues` holds: inside a value shared by bytes a list is written whole, since such a value's bytes may not depend on what was written before. A list the reader hands back for repeated bytes (`readSharingStorageOfRepeats(_:)`) is never one that holds a difference, whose bytes mean what the lists before them say. A new per-place list joins by taking a slot; a list whose elements differ at every place (an element that names the place) gains nothing until what differs is written apart, as `builtAfter` is. `SafeDIToolBinaryFileTests` reads back 3,000 drawn lists, a declaration distinct in each field in turn and a twelve-builder plan field by field, and fails when a plan's bytes grow faster than its builders. A run that throws after reading a stored block computes everything again, so a block that never decoded would change no output: a run's output holds what such a discarded run threw (`Generate.Output.errorOfDiscardedRunThatReadStoredBlocks`), and both test harnesses, the graph fuzzer's runs among them, fail on one, and on a written file whose signatures or plans decode to values the tool writes as other bytes (`StoredBlockDecodeChecks`); `StoredBlockDecodeObservation` tells a test that cuts a block short which block threw. The harness reads the output and sets no task-local value of its own: one more `TaskLocal.withValue` around `generate()` there made the tests' release build abort on Linux with Swift 6.2 ("freed pointer was not the last allocation"). A new stored block joins by a case of `StoredBlockDecodeObservation.Block`.
- A seam's signature holds its place graph by case (`SeamSignature.places`, whose coders are in `BinaryCodableSeamPlaces.swift`) and, while it still holds a hole per site, the case of each hole (`caseIndexByHole`). A public mock's plan holds the same two (`StoredPublicMockPlan.places` and `caseIndexByHole`), written between its enums and its receivers. The graph is written as its levels, then its cases, then the levels' lists of declarations (`Places.declarationLists`, one for every level of one build of a type whichever property its route goes on through, so a type with forty places writes forty declarations, not sixteen hundred), each record in the order its initializer takes its fields; a record with two or more optional or Boolean fields writes them as field flags, as a struct outside signatures does. A list most levels, cases or children hold empty (a level's cycle re-entries, fill stack, path and parents, a case's lists from calls and fills, a child's `receivesOnlyIfAvailable` and `carriers`) is one more of those flags, and is written only when it holds an element (`BinaryWriter.writeAbsentWhenEmpty(_:flaggedIn:)`, a `BinaryLayoutField(_:absentWhenEmpty:)`, which the schema description states): the root level of a seam with one place wrote six counts of zero. Nothing in it is per site, so it grows with the seam's types and their properties, never with the paths that reach a place: ten layers of six screens, each instantiating a type only the app fulfills, are 29,524 places and a graph of 33 KB. A place a call passes up is a reference to the case of the seam it came from (`CalledCase`), never a copy of that seam's levels, so a file does not grow with the modules beneath it. The multi-module test harness reads each file a run wrote and compares every seam's graph and every public mock's, stored property by stored property with a source position counted as absent, with the graph the run computed (`StoredPlaceGraphChecks`, from `ModuleInfoFile.seamSignaturesReadBack` and `publicMockPlansReadBack`, and `Generate.Output.seamSignaturesWrittenToModuleInfo` and `publicMockPlansWrittenToModuleInfo`): what the oracles check of a computed graph then holds of the graph a module above decodes. Nothing turns it off.
- **A stored signature holds only what a call of the seam reads.** What only the seam's own generation reads, as its call routes, is a member of `ScopeGenerator.SeamRoot` without a default.
- Outside seam signatures, a struct with two or more optional or Boolean fields that a file holds many of writes them as one varint of flags before its fields (`BinaryFieldFlags`, `writesFieldFlags`, which the schema description states): one bit per field in write order, an optional's presence or a Boolean's value, and an optional's value only when present. Its coder opens with `startFields()` and ends with `finishFields(_:startingAt:)`, writes such a field through `fieldFlags.append` or `writeOptional(_:flaggedIn:)`, and reads it back through `readFieldFlags()`, `next()` and `readOptional(flaggedIn:)`, ending with `finish()`, which rejects a flag no field read. The tests write each struct's samples the same way (`writeFieldSamples`), so a flag read out of order fails `binaryLayout_matchesBytesEachCachedStructWritesAndReads_whenEachFieldInTurnHoldsADistinctValue`. A struct with one such field gains nothing and writes it as before, as do the files' top-level structs. Inside seam signatures one struct does the same, a hole's field (`SeamSignature.Hole.Field`), whose four optionals and four Booleans took eight bytes of each field a signature writes in full: a signature writes every distinct field once, and a seam with one place writes two that differ in one Boolean.
- `Codable` conformances stay: the `dump` subcommand prints either file as JSON through them.
- Scan's cache holds the module's declarations of reserved type names (`CachedScannedModuleInfo.reservedTypeNameDeclarations`, and each `FileScan`'s own), which only the module's own `generate` reports. `.safedi` files do not carry them: they are not part of `ModuleInfo`, so a dependent's inputs are the same bytes whether or not the module declares one.
