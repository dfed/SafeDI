# Serialization

`scan`'s cache (`<manifest>.safediScanCache`, a `CachedScannedModuleInfo`) and `.safedi` module info files (a `ModuleInfoFile`: the module's own declarations under a non-optional module name, the signatures its run computed of the seams it declares (`seamSignatures`, see `seams.md`), and its `view` – `ModuleInfoView`, `ViewedModuleIdentity`, `ViewedModule` – of the modules it depends on) are written in SafeDITool's own binary format, by hand rather than through `Codable` (`BinaryCoding.swift`, `BinaryCodableModels.swift`, `BinaryFile.swift`, all in `SafeDIToolLibrary`, never `SafeDICore`). These files are **regenerated every build** — there is no cross-version deserialization. Do not add backward-compatibility decoding logic. A header (magic, format version, schema fingerprint, body length, checksum) rejects any other file: an unreadable scan cache is a cache miss and a fresh parse, and an unreadable `.safedi` is an error naming the file. `BinaryFile.schemaDescription` and `BinaryLayout.description` spell every stored type and field type with `String(reflecting:)`, and `schemaFingerprint` is the checksum of that description, checked in as a constant rather than computed at run time: reflecting on a type scans the runtime's protocol conformance tables, which cost about 170M instructions, most of a small module's `generate` under Bazel or Tuist. `SafeDIToolBinaryFileTests.schemaFingerprint_isChecksumOfSchemaDescription` recomputes it and, when a layout changes, fails with the new value to check in. So every build of the tool writes the same fingerprint, whatever its build system names its modules. The plugin-read `SafeDIToolManifest` stays JSON. `generate` writes `--combined-output` and `--module-info-output` only when their bytes change (`Data.writeIfChanged(toPath:)`), and the `.safedi` last, after every validation, so a failed run publishes none: Bazel removes an action's outputs before it runs, so every Bazel run writes them, and Xcode's script dependency analysis compares a script's inputs with its last run's, so an unwritten output does not rerun the script forever (captured 2026-11-04 in DAN-2's design, T4b/T4d).

What reruns after a change (the Manual leaves this out as performance detail): every `safedi_compile` action has the whole `SafeDIInfo.transitive_module_infos` depset among its inputs and names, with `--unused-inputs-list-output`, those it did not open as its `unused_inputs_list`, so under Bazel's local action cache a change to a module's declarations reruns the actions of the modules that list it and of those that opened it (a module with a root or seam whose trees reach a type nothing it lists declares), while a disk or remote cache, which keys on every declared input, reruns every module above it; an action whose outputs come out byte-identical reruns nothing after it. Tuist's script reruns when one of its target's Swift files or one of the `.safedi` files it reads changes, so a change in a module reruns the scripts of the modules that list it, and recompiles only the modules whose `SafeDIGenerated.swift` changed. Under either, a change to a declaration in a module that declares a seam or public mock, or in a module such a module reads, changes the `.safedi` of that module and of every module above it, since each carries those declarations in its view, and can change the generated calls of what they compute.

**A view that refers to modules.** Under `--module-info-views-refer-to-modules`, which the Bazel rule passes, a file stores `ModuleInfoFile.ownEntryChecksum` (the checksum of its position-free `ownEntry` without its seam signatures, `ViewedModule.checksum`, which says why that is sound; written right after `moduleName`) and its view lists each module it carries as a `ViewedModuleReference` (name and that checksum) in place of a `ViewedModule` copy. `ModuleReferenceResolver` turns references back into entries before anything reads a view: from a given file's own entry, or else from the file among `--transitive-module-info-file-path`'s that describes the module, found by reading only each file's first fields (`ModuleInfoFile.Head`, which neither checks the body's checksum nor decodes the string table) and then reading that file whole without its view. A reference no file resolves is `UnresolvableModuleReferenceError`; one whose checksum differs from the file's is `ModuleInfoDisagreementError`. The checksum has no positions, so a position-only edit leaves every referring file byte-identical. Tuist and custom builds that list modules keep copies, since a reader there may not be given the referenced files.

When a stored type changes, keep its coder in step:
- Each `BinarySchemaMember` writes its fields in initializer order and reads them back through that initializer, with each field's type choosing how it is read. A field whose type is not `BinaryCodable` fails to compile; so does an enum case the writer's exhaustive `switch` does not handle, and a tag the reader's `switch` does not handle.
- `binaryLayout` is what `BinaryFile.schemaFingerprint` covers: for a struct, each field it writes, in write order, as a `BinaryLayoutField` whose key path fixes the field's type, plus `unwrittenProperties`, the stored properties not written under their own name (`Dependency.asInstantiatedType`, `UnorderedEquatingCollection.set`, `Instantiable.instantiableTypes`, written as `concreteInstantiable` and `additionalInstantiables`, and `Property`'s stored hash, which is never written because hashing is seeded per process: a decoded `Property` goes through `Property.init(label:typeDescription:)`, which computes it again); for an enum, each tag's associated values, in declaration order, which is also the order written and read. A file written by a SafeDITool whose types write other fields, fields of other types, or the same fields in another order is therefore never read. `SafeDIToolBinaryFileTests` compares each struct's layout against `Mirror`, so a new stored property fails until it is listed, written, and read, and writes each field and associated value in turn with a value distinct from the rest (`BinarySample`), so a layout whose order or types differ from what the coder writes and reads fails too. A new stored type must join `BinaryFile.schemaMembers` and conform to `BinarySample` in the tests. Any change to a layout then updates `BinaryFile.schemaFingerprint` to the value that test reports.
- A `BinaryReader` reads type descriptions nested at most `BinaryReader.maximumNestingDepth` (32) deep, since a debug build's read takes about 4.4 KB of stack per level and must fit in half of a concurrency thread's 512 KB (`read_fitsInHalfOfConcurrencyThreadStack_whenTypeNestsAsDeeplyAsSafeDIReads`), so the writer notes a deeper one and `BinaryFile` refuses to write a file that holds it, naming the instantiable whose declaration names it, or the outermost type of a plain type declaration (`BinaryFileWriteError`): `scan` then writes no cache, and `generate` fails rather than write a `.safedi` dependents cannot read. Do not describe the deep type itself in such an error: spelling a type recurses as deeply as it nests, which exhausts a task's stack in a debug build.
- `executeSafeDIToolTest` checks, for every fixture that runs scan, that the cache reads back exactly what scan wrote (`reflectedDescription`, which sees private fields and spellings `==` ignores, and compares strings by their UTF-8 bytes, because `String`'s `==` calls canonically equivalent spellings equal while Swift compares identifiers byte for byte; the writer's string table keys strings by those bytes for the same reason), so a field the coder drops fails whichever tests give it a value.
- A field a file repeats at many places, each a long collection, is written as `BinaryShared`: its first write writes the value, and every later write of an equal value only a reference, which the reader resolves to the same storage. `UncarriedDeclaration.placesInTree` needs it: every declaration beside one tree lists all of the tree's places, as many as its paths, so a deep hole graph's `.safedi` grew to 49 MB and took longer to write and read than its signature took to compute. The writer hashes a shared value by its count and end elements, since hashing each element costs what writing it did.
- A module info's seam signatures (`ModuleInfoFile.seamSignatures`, `ViewedModule.seamSignatures`) are written as `BinarySharingSignatureValues`: inside them, each type description, hole field (`SeamSignature.Hole.Field`) and uncarried declaration's reason (`UncarriedDeclaration.Reason`), at its outermost level, is written once and referenced afterwards (`writeSharedByBytes`), keyed by the bytes it writes, since `TypeDescription`'s `==` ignores `any`. Inside a value written in full, nothing is shared, so a value's bytes never depend on what was written before it. A signature names its seam's type and a few others at dozens of places, and repeats each field of a scope at every hole and route step that binds it: sharing types took E6d-600's Feature from 324 KB to 271 KB, and sharing fields and reasons took P2-200's Feat from 8.6 MB to 2.4 MB. A new type that a signature repeats joins them by writing and reading itself as `TypeDescription`, `Field` and `Reason` do; one whose values rarely repeat costs a hash of its bytes per write for nothing. Declarations outside the signatures are written as before. `Scripts/generate-time-check.py` fails a change that doubles any module's `.safedi` file on its shapes.
- Outside seam signatures, a struct with two or more optional or Boolean fields that a file holds many of writes them as one varint of flags before its fields (`BinaryFieldFlags`, `writesFieldFlags`, which the schema description states): one bit per field in write order, an optional's presence or a Boolean's value, and an optional's value only when present. Its coder opens with `startFields()` and ends with `finishFields(_:startingAt:)`, writes such a field through `fieldFlags.append` or `writeOptional(_:flaggedIn:)`, and reads it back through `readFieldFlags()`, `next()` and `readOptional(flaggedIn:)`, ending with `finish()`, which rejects a flag no field read. The tests write each struct's samples the same way (`writeFieldSamples`), so a flag read out of order fails `binaryLayout_matchesBytesEachCachedStructWritesAndReads_whenEachFieldInTurnHoldsADistinctValue`. A struct with one such field gains nothing and writes it as before, as do the files' top-level structs.
- `Codable` conformances stay: the `dump` subcommand prints either file as JSON through them.
- Scan's cache holds the module's declarations of reserved type names (`CachedScannedModuleInfo.reservedTypeNameDeclarations`, and each `FileScan`'s own), which only the module's own `generate` reports. `.safedi` files do not carry them: they are not part of `ModuleInfo`, so a dependent's inputs are the same bytes whether or not the module declares one.
