# `LazilyInstantiated`

- **A `LazilyInstantiated` property declares two receivable properties.** `x: LazilyInstantiated<X>` can be received as itself or by value as `x: X`. Which declarations offer the by-value form is decided in one place: `Dependency.lazilyInstantiatedInstanceProperty` (and `Scope.PropertyToGenerate.lazilyInstantiatedInstanceProperty`, `ScopeGenerator.declaredLazilyInstantiatedInstanceProperty`). An `@Instantiated` property always does, because the generated wrapper is never optional. A `@Forwarded` or aliased one is bound with its declared type, so it does only when that type is not optional. A received one never does. `Scope.createdProperties` and `properties`, `ScopeGenerator.propertiesToDeclare` and its forwarded subtraction, sibling ordering, mock promotion (`collectReceivedProperties`), and the `@Instantiable` macro's check that a root's aliases are fulfilled on the root (`InstantiableMacro`, through `Dependency.receivableProperties`) all go through those accessors; do not re-derive the form from a `Property` alone. A by-value receiver is passed `x.instance`: `Scope.createScopeGenerator` threads `lazilyInstantiatedInstanceProperties` – the by-value properties that are in scope only through a wrapper – down to initializer argument lists, aliases, and mock nodes. A nearer declaration with the same label removes a property from that set, exactly as the nearer `let` shadows the wrapper in the generated Swift; an alias that keeps the label it retypes is looked up in the inherited set, because it is not in scope where its own value is read. `Scope.providedProperties`, validation’s `childReceivableProperties`, and the `propertiesToDeclare(in:)` and `forwardedProperties(in:)` helpers hold both forms too, and hidden-label validation accepts a by-value receive whose closest declaration of the label is the wrapper (`LabelDeclaration.lazilyInstantiatedInstanceProperty`). An `onlyIfAvailable` alias is the nearest declaration of its label, `nil` included, so nothing farther up – an instance included – stands in for it. A wrapper whose instance type is optional (`LazilyInstantiated<X?>`) offers no by-value form, wherever it is declared. `Instantiable.forwardedReceivableProperties` and `DependencyTreeGenerator.propertiesToDeclare(in:)` are the only places that list a type's forwarded and declared properties with their by-value forms; use them rather than filtering `dependencies` again. `orderedPropertiesToGenerate`'s `siblingIndexByProperty` maps each lazily instantiated sibling's by-value property to that sibling too, unless another sibling declares that property itself, and the pairwise fallback applies the same rule so that both paths build the same set.
- **Validation maps a wrapper to the constant with the same optionality.** `Property.asValidatedForDependencyCycles` turns `x: LazilyInstantiated<X>?` into `x: X?`, not `x: X`: an `onlyIfAvailable` receive of the wrapper inside the tree it builds must not equal the stack entry, or a tree the constant twin accepts (the receiver is passed `nil`) is rejected as a cycle. `TypeDescription.lazilyInstantiatedInstanceType` is the generic argument as spelled (`any Service`), which is what a by-value receiver must match; `asInstantiatedType` normalizes it for the scope lookup. Validation’s instantiation stacks (`propertyStack`, `instantiationStack`, `ReceivableAlias.lastAliasDeclaringInstantiationStack`) hold the mapped constants, while `receivableProperties`, `createdProperties`, `providedProperties` and `boundProperties` hold properties as declared, plus the by-value form of each wrapper. Map a declared property before comparing it with a stack, and never before looking it up in one of those sets. Generation differs: `NearestDeclarations.build(_:)` records every form the wrapper being built provides – the wrapper, its by-value form, and their optional forms (`CycleParameter.forms(providedBy:)`) – so `NearestDeclarations.binding(of:)` passes `nil` for an `onlyIfAvailable` receive of either form inside the tree the wrapper builds, in production and mock generation alike.
- **A mock's parameters for receives never mention `LazilyInstantiated`.** Adopting it on an owner must not change the generated `mock()` of an unchanged receiver. (A wrapper the mocked type forwards, or that a type in its tree instantiates and the mock cannot build, is a parameter of the wrapper's type, or beneath a `Sendable` wrapper a `@Sendable` autoclosure returning it: see "An `@Instantiated` dependency the mock cannot build is still declared" in `mock-generation.md`.) `createMockRootScopeGenerator` treats a dependency received both ways as one: it promotes the wrapper once whenever any receiver requires the wrapper or its instance, optional or not, and skips the by-value form and its optional form, also when the mock root declares the wrapper itself, and counts neither among the properties the mock is passed (`mockParameters`, which `childrenRequiringEachOther` takes as forwarded, so an `onlyIfAvailable` alias of either would count as always created). A required `x: LazilyInstantiated<X>`, or a required `x: X` or `x: X?` that no forwarded property fulfills (see `mock-root-promotion.md`), promotes `x: LazilyInstantiated<X>`; a required `x: LazilyInstantiated<X>?` beside none of them is promoted as itself, like any optional form whose non-optional form nothing requires. An `onlyIfAvailable` receive of the wrapper is then passed the node the mock builds, so no entry for the dependency is typed `LazilyInstantiated`; only a receive of the other wrapper kind, beside a promoted one, still is (see `mock-root-promotion.md`). A dependency the mock cannot build is classified in `generateMockRootCode` by its by-value form (`receivedParameterProperties`), so it is a `T` parameter or a `T?` override; the mock then binds `<label>_lazilyInstantiated` and passes that name to the types that receive the wrapper, and to aliases of it (`lazilyInstantiatedBindingNames`, threaded beside the flat-parameter rename map; the root's own receive goes through `returnDisambiguationMap`). `removingRenames(hiddenByDeclarationsOf:parameters:from:)` prunes `lazilyInstantiatedBindingNames` wherever it prunes that map, so a receiver below a nested scope that declares the wrapper – an `@Instantiated` child, an alias, or a builder's forwarded parameter – is passed that closest declaration, as in production. It is never rebound under the dependency's label: only one of the two bindings that share that label is renamed, so a rebinding inside a builder function would hide the instance parameter from the by-value receivers built there, which have no rename of their own to rebind. A by-value receiver of a wrapper renamed by sibling disambiguation rebinds the wrapper under its label, and an alias of its instance reads `.instance` from the renamed binding directly (`disambiguatedLazilyInstantiatedBinding`). `erasedToConcreteTypeMap` is keyed by both forms' types, and promotion falls back from a wrapper to the erasure of its instance (`concreteTypeErased(to:)`), so the wrapper is buildable whenever its instance is — also when the wrapper is optional, or when only a constant declares the erasure — and `mockReturnTypeIsCompatible` is asked about the instance type. `mockCanBuild` treats a lazily instantiated property as it does a constant: a mock has no values to forward, so it cannot lazily instantiate a type with `@Forwarded` properties, and `mock()` takes that dependency’s instance. A forwarded lazily instantiated property fulfills receives of itself, of its optional form, and of its instance beneath the mock root (`isFulfilledByForwardedProperty`), so neither `lazilyInstantiatedReceivedProperties` nor the by-value parameter set includes them; mapping such a receive to its by-value form first would lose that the wrapper is forwarded, and the mock would take a second value and ignore the forwarded one.
