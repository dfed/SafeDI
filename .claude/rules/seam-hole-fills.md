# Seams: fills that receive a building instantiator

Continues `seam-holes.md`.

- **A fill's receive of an instantiator the seam's tree is building is an error, never `nil`.** Inline, a type in a fill's tree that receives the hole's own property, or the property of a scope on the site's path or a member of its loop of builders, where that property is an instantiator, closes a loop of instantiators (`ReceivedBuilderLoops` in `cycle-generation.md`) and gets a wrapper made again of a builder function the seam's initializer declares; the seam's module does not see the receive, so it can rebind nothing for it. `fields(of:)` marks such a declaration `UncarriedDeclaration.Reason.instantiatorBuildingSite`, and `findingsOfFill` reports a receive of it, required or only if available, as `FillFinding.Kind.receivesInstantiatorBuildingSite`, whose remedy is to instantiate it above the seam and receive it in the seam's tree, so the caller holds it. The finding stands in the rare shape where inline passes `nil`, a loop whose component holds a value after the second pass (`aBuilder`'s tree requires a value `V`, which requires `cBuilder`, whose `C` receives `aBuilder` only if available); the message says such a fill "can get" an instantiator of its own, not "would". An instantiator the seam builds after the site, such as a second hole whose implementation receives the first back, stays `declarationBoundAfterSite`, whose message offers the same remedy for an instantiator. A fill's own generator finds no loops (`ScopeGenerator.init`, `fill != nil`): its one child is the filled property, and a receive of it is this finding.
- **A place a caller fills inside a fill built again is held to the visible build's rule.** Where a call inside a fill of a seam call builds the filled seam again and passes the fill on (`declarationBoundOnPathToReenteringCall` in `seam-holes.md`), a place inside that fill that the calling seam's module cannot fill, its own or one a seam called inside the fill passes up, at any depth, is filled by a caller, whose fill the visible build's check never sees. So the calling seam records on the place, in a list of its own (`SeamSignature.Hole.reenteringCallDeclarations`, `DependencyTreeGenerator.unreadableInsideFills(_:placeFields:fillingModule:)`), every path's declaration of each label whose read the visible build would reject there as this error: the filled place holds no field, cycle re-entry or uncarried declaration of it, no called copy's hole leaves it uncarried, no scope from the fill's root down to the place declares it, and, for a passed-up place, the place holds no field of it, which the visible build's fill of that place binds. Where a called copy leaves such a label uncarried (`FillReentryHidings.calledCopyDeclarations`), the place joins that copy's declarations to its own uncarried ones, so the caller reports the visible build's `declarationBoundAfterSite`; the caller checks those after its field branch, so with a field of the label above the seam call it accepts what the visible build rejects, and it names only the first copy of a label, a gap the 2.3.1 rework closes with the rest. Each entry carries what the message prints (the declaration, the path's place, the call, the place built again and its seam's module, the module that fills it), never a whole `Hole`; a copy a seam passes up keeps every entry, beside `SiteAdditions`, which keeps only the first declaration of a label. The caller's `checkReceive` tests the list right after `cycleReentryDeclarations` and before the field branch, for required and only-if-available reads alike, and reports one finding per place built again with the visible build's text. A field of the label bound above the seam call does not lift it: a deliberate loss of a shape that builds correctly with a caller's fill, kept so both builds reject one shape with one remedy, until the 2.3.1 rework that hands each route its own value lifts it in both (both code sites say so). The remedies follow the reader, and each, applied as written, gives a graph both builds accept with inline's values (`SafeDIToolSeamReenteredFillTests`' `generate_buildsInlineValues_…` cells): for a reader only if available, `@Received(onlyIfAvailable: true) let x: X?` on the seam built again; for a required one, `@Received let x: X` there with `x` declared on every route to it (the seam's module cannot see past its own callers, so where nothing above declares `x` the hole build reports the unfulfilled receive the one-module build does), or both receives only if available; and, for either, a type that fulfills the place in the seam's module, which then builds the place's whole tree.
