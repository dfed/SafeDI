# File paths

- **Generated code names no file or line.** An aliased `@Received(fulfilledByDependencyNamed:ofType:)` assignment ends in `// Declared as Type.label` in every integration (`DependencyTreeGenerator.aliasedDependency(_:fulfilledBy:erasedToConcreteExistential:onlyIfAvailable:declaredBy:)`, `ScopeGenerator.referencingDeclaration(of:by:)`): the declaring type spelled as generated code spells it, nested qualification kept, then the alias's label. A path or a line in generated code would differ between integrations, move with every edit above the declaration, and, as a `#sourceLocation` directive, make the compiler warn wherever its spelling of a file differs from the build system's. Tuist shares its build cache across machines, so nothing generated for a Tuist build, nor its `.safedi`, may hold an absolute path.
- **A diagnostic about another module's declaration reads its file again.** `DiagnosticLocator` reads the file at the path the `.safedi` records and, where that is relative and does not open, under the directory each of the run's input files resolves under (`resolvedRoot(ofRelativePath:)`, the input's `realpath(3)` without the input's own relative path, in the inputs' sorted order), since a sandboxed Bazel action's inputs are symbolic links into the execution root that holds every module's files; the access check's `isReadableFile` reads it the same way. The diagnostic still prints the recorded path.
- **File path spelling.** `Sources/SafeDICore/Utilities/FilePathSpelling.swift` is the only place a path is normalized or resolved, or made relative to a directory; the SafeDIGenerator plugin compiles it, and `OutputFileNaming.swift`, through symbolic links. `PathSpellingCallTests.sources_normalizeAndResolvePathsOnlyInFilePathSpelling` (in the plugin test target, which can strip comments and strings) fails if code under `Sources` or `Plugins` outside that file calls `standardizedFileURL`, `.standardized`, `standardize()`, `standardizingPath`, `resolvingSymlinksInPath`, `canonicalPathKey`, `destinationOfSymbolicLink`, or `realpath`; it does not detect a path made relative by hand. A comparison is sound only when both sides were spelled by one rule. `NormalizedFilePath` is absolute, without `.`/`..`/repeated `/`, and, on Apple platforms, without the `/private` Foundation drops from a path that names an existing file under `/private/tmp`, `/private/var`, or `/private/etc` (a path to no file keeps it); it resolves no other symbolic link. `ProjectFilePaths` resolves the reported project root once per run and spells each path inside the project under the resolved root as a `ProjectFilePath` (`projectFilePath(of:)`), which only it can create; every comparison that must agree — the "already an input" exclusion, mock-scoped and configuration-file matching, scan's stamps, and the cache-freshness check — takes `ProjectFilePath`s, because the inputs and `--mock-scoped-files` arrive under the root as the build system reported it while `additionalDirectoriesToInclude` is found from the working directory, which `getcwd(3)` reports resolved (and Foundation's directory enumerator on Apple platforms returns resolved paths). So `scan` is handed the reported root as `--project-root`, and `generate --output-directory`, when it scans for itself, takes the same option: without it `generate` takes its working directory, which is resolved, and a target whose files are reported through a symbolic link finds none of them among the CSV's, generating none of its roots and mocks. The SafeDIGenerator plugin's `PluginScanner` fallbacks, for packages and for Xcode projects, have `generate` scan for itself and pass it the same root they hand `scan` elsewhere, which every release from 2.3.0-alpha-2 on accepts. Never resolve per file: scan's freshness check is stat-only for speed. `ProjectFileSet` answers whether a path as a declaration records it names one of a set of files (the module's own, for `isOwnFile`), spelling the path only when its last component is one of the files' names, or `.`, `..` or empty, since spelling changes a path's directories alone. Each consumer gets one spelling. The manifest's file names (roots, mocks, configurations, `mockScopedFilePaths`) and scan's cache name a file relative to the resolved root when it lies inside it, else by its normalized path (`manifestPath(of:)`), and module info names files as the parse did (scan's cache names, or the CSV's spelling on a fresh parse). `projectRoot` is the reported root made absolute against the working directory, without a trailing `/`, and not normalized (`reportedProjectRoot`). What the build system, the compiler, or an IDE matches as a string — `additionalInputFiles`, which the plugin declares as build inputs, and the file paths `run()` prints in diagnostics — is that root joined with the file's path inside it (`buildSystemPath(of:)`), the spelling the build system already uses for the project's other files; a file outside the project gets its normalized path. Without a manifest's project root, those are the paths as handed under `--compiler-receives-input-paths-unchanged`, which is also how the compiler prints its own diagnostics (under Bazel, relative to the execution root, while the working directory is the action's sandbox, which Bazel deletes). Without the flag either, `run()` prints a diagnostic's path made absolute against the working directory and normalized. `Generate.BuildSystemFilePaths` is that one decision, which `run()` reads. A diagnostic `generate()` returns names its file as it was handed to the parser: under a plugin, when `generate` reads scan's cache, the path scan parsed the file under (`ProjectFilePath.path`, normalized under the resolved root), and otherwise, without a manifest or when `generate` parses afresh, the path as the input CSV spells it. Only `run()` respells it, as the build system does (`Generate.BuildLog`). Output paths keep the spelling the plugin passed; `generate`'s check that no two manifest outputs name one file compares them as `OutputFilePath`s (`OutputFilePaths.outputFilePath(of:)`): the output's directory resolved with `realpath(3)`, once per spelling of the directory, joined with its name, or its normalized path when the directory does not exist, compared ignoring letter case and Unicode normalization (`CaseInsensitiveFileName`, under which `OutputFileNaming.swift` also names outputs apart on every platform, so that macOS's default volume, which ignores letter case, holds each output as its own file). Scan's cache records `additionalDirectoriesToInclude` as scan found them, relative to the working directory, so `generate` finds the same files. SwiftPM and Xcode report resolved roots; reported links come from scripts and other integrations.
