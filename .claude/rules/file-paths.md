# File paths

- **`#sourceLocation` paths are compared as strings.** The compiler groups every path a module uses – each source file as it was handed to the compiler, and each `#sourceLocation` file – by file name, and warns at a directive whose file name maps to more than one path (a build error under warnings as errors). It does not resolve relative paths or symbolic links. `AliasDeclarationReferences` emits a directive for an alias only when `generate` knows the compiler’s spelling: a plugin manifest’s `projectRoot` (`ProjectFilePaths.buildSystemPath(of:)`), unless the root is spelled differently from its `realpath(3)` resolution (`ProjectFilePaths.reportsResolvedProjectRoot`, from the one resolution `ProjectFilePaths` makes per run) – Xcode reports a package under `/tmp` as `/tmp/…` and hands the compiler `/private/tmp/…`, and a manifest from `scan` holds no second spelling that would reveal it – or `--compiler-receives-input-paths-unchanged` (passed by the Bazel rule). It still omits one whose file name another directive’s file or one of the module’s own files shares (`--mock-scoped-files` when `generate` scans for itself, the manifest’s `mockScopedFilePaths` otherwise, every input file under the flag), which covers a module file known under two spellings such as Xcode’s `/tmp/…` against the working directory’s `/private/tmp/…`. Every other alias gets a trailing `// Declared at <path>:<line>` comment with the path as the integration handed it (project-root-relative under a plugin). Tuist shares its build cache across machines, so nothing generated for a Tuist build, nor its `.safedi`, may hold an absolute path: its script hands `generate` `$SRCROOT`-relative paths and gets comments. Never spell a directive path with `NormalizedFilePath`, which drops a leading `/private` the compiler keeps. The examples treat warnings as errors and each declares an aliased `@Received` in its root module, so CI catches a wrong spelling.
- **File path spelling.** `Sources/SafeDICore/Utilities/FilePathSpelling.swift` is the only place a path is normalized or resolved, or made relative to a directory; the SafeDIGenerator plugin compiles it, and `OutputFileNaming.swift`, through symbolic links. `PathSpellingCallTests.sources_normalizeAndResolvePathsOnlyInFilePathSpelling` (in the plugin test target, which can strip comments and strings) fails if code under `Sources` or `Plugins` outside that file calls `standardizedFileURL`, `.standardized`, `standardize()`, `standardizingPath`, `resolvingSymlinksInPath`, `canonicalPathKey`, `destinationOfSymbolicLink`, or `realpath`; it does not detect a path made relative by hand. A comparison is sound only when both sides were spelled by one rule. `NormalizedFilePath` is absolute, without `.`/`..`/repeated `/`, and, on Apple platforms, without the `/private` Foundation drops from a path that names an existing file under `/private/tmp`, `/private/var`, or `/private/etc` (a path to no file keeps it); it resolves no other symbolic link. `ProjectFilePaths` resolves the reported project root once per run and spells each path inside the project under the resolved root as a `ProjectFilePath` (`projectFilePath(of:)`), which only it can create; every comparison that must agree — the "already an input" exclusion, mock-scoped and configuration-file matching, scan's stamps, and the cache-freshness check — takes `ProjectFilePath`s, because the inputs and `--mock-scoped-files` arrive under the root as the build system reported it while `additionalDirectoriesToInclude` is found from the working directory, which `getcwd(3)` reports resolved (and Foundation's directory enumerator on Apple platforms returns resolved paths). So `scan` is handed the reported root as `--project-root`, and `generate --output-directory`, when it scans for itself, takes the same option: without it `generate` takes its working directory, which is resolved, and a target whose files are reported through a symbolic link finds none of them among the CSV's, generating none of its roots and mocks. The SafeDIGenerator plugin's `PluginScanner` fallbacks, for packages and for Xcode projects, have `generate` scan for itself and pass it the same root they hand `scan` elsewhere, which every release from 2.3.0-alpha-2 on accepts. Never resolve per file: scan's freshness check is stat-only for speed. Each consumer gets one spelling. The manifest's file names (roots, mocks, configurations, `mockScopedFilePaths`) and scan's cache name a file relative to the resolved root when it lies inside it, else by its normalized path (`manifestPath(of:)`), and module info names files as the parse did (scan's cache names, or the CSV's spelling on a fresh parse). `projectRoot` is the reported root made absolute against the working directory, without a trailing `/`, and not normalized (`reportedProjectRoot`). What the build system, the compiler, or an IDE matches as a string — `additionalInputFiles`, which the plugin declares as build inputs, `#sourceLocation` paths, and the file paths `run()` prints in diagnostics — is that root joined with the file's path inside it (`buildSystemPath(of:)`), the spelling the build system already uses for the project's other files; a file outside the project gets its normalized path. Without a manifest's project root, those are the paths as handed under `--compiler-receives-input-paths-unchanged`, which is also how the compiler prints its own diagnostics (under Bazel, relative to the execution root, while the working directory is the action's sandbox, which Bazel deletes). Without the flag either, `run()` prints a diagnostic's path made absolute against the working directory and normalized. `Generate.BuildSystemFilePaths` is that one decision, which `run()` and `#sourceLocation` paths both read. A diagnostic `generate()` returns names its file as it was handed to the parser: under a plugin, when `generate` reads scan's cache, the path scan parsed the file under (`ProjectFilePath.path`, normalized under the resolved root), and otherwise, without a manifest or when `generate` parses afresh, the path as the input CSV spells it. Only `run()` respells it, as the build system does (`Generate.BuildLog`). Output paths keep the spelling the plugin passed; `generate`'s check that no two manifest outputs name one file compares them as `OutputFilePath`s (`OutputFilePaths.outputFilePath(of:)`): the output's directory resolved with `realpath(3)`, once per spelling of the directory, joined with its name, or its normalized path when the directory does not exist, compared ignoring letter case and Unicode normalization (`CaseInsensitiveFileName`, under which `OutputFileNaming.swift` also names outputs apart on every platform, so that macOS's default volume, which ignores letter case, holds each output as its own file). Scan's cache records `additionalDirectoriesToInclude` as scan found them, relative to the working directory, so `generate` finds the same files. `// Declared at` comments use the manifest name. SwiftPM and Xcode report resolved roots; reported links come from scripts and other integrations.
