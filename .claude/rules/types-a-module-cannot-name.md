# Types a module cannot name

`resolveSafeDIFulfilledTypes` keys declarations by name, so two declarations of one name would collide; `distinguishingTypesUnnameable(from:among:plainTypeDeclarations:modulesRead:)` (`InstantiableResolution.swift`) runs first, at the run's own view (`normalizedInstantiables`) and at each per-module view (`visibleDeclarations(ofModuleNamed:)`, `callersVisibleInstantiables`), each with that view's module as the viewer. It runs after normalization, since a mention of a nested type equals the key it names only once qualified. It touches only a type two or more production declarations fulfill, which throws today, so nothing that builds can change. For each such name, a declaration the viewer cannot name – its effective access (`AccessLevel.effective(ofTypeDeclaredBy:)`, capped by the plain declaration its own module records of the name, which bounds an extension's type and a `fulfillingAdditionalTypes` name narrower than its claimant) does not reach the viewer by `TypeAccessProof.ModuleReach` – fulfills it as `TypeDescription.qualified(byModuleNamed:)` spells it (`ModA.Store`, with `Instantiable.declaredName` holding `Store`, which `ExtendedTypeDeclarations`' lookups and the access error's phrases read). Only the declaring module's own mentions are spelled that way (`claimMentioned`): its own declaration of the name shadows every import, so its meaning is certain whatever else it reads; it leaves the name whole when the module can name a second fulfiller meaning the same, or the name may mean more than one declaration SafeDI records there. SafeDI cannot tell what any other module means by the name: a module can read one SafeDI reads nothing of (a fetched package, a library built without SafeDI, Foundation), and which modules each file imports decides. So a declaration of another module that spells the name, where that module may name a declaration told apart (`mayName`, by `TypeAccessProof.MentionMeaning`: its own declaration shadows every other; otherwise a declaration `package` or wider it can name or SafeDI cannot tell it cannot, `moduleNamesItMayMean`), leaves the name whole, the duplicate error: a rejection has a remedy, a wrong spelling does not compile. A module SafeDI knows cannot name it – `internal`, `package` across a known boundary, its own declaration of the name, under the target graph a module it does not depend on – keeps its mention as written; a module of a run given module info files that does not list the declaring module may import it beneath one it lists, so keeps the name whole. Mentions are the types `Instantiable.typesMembersSpell` names, and a `mockOnly` declaration's types. The viewer's own mentions are unchanged, so a bare `Store` in the app is the type it can name. The spelling is what a reader sees and what generated code would say, and no generated code spells it: the viewer cannot name the type, so a construction of one reaches the access error. A sibling of the declaring module's package that mentions the name is therefore the duplicate error; letting it build needs each file's imports, no record SafeDI keeps, and would turn an error into a build.

A `fulfillingAdditionalTypes` claim names a type apart from the declaration that claims it. When the claimant is hidden and the claimed name is one the viewer can write (a `public` protocol, or a name no module SafeDI reads declares, as a protocol of the standard library), the claim is distinguished as above, but a mention keeps its spelling, since `Logger` means the one protocol wherever it is written: a `@Forwarded` or `@Received` type, a parameter or an alias stays `Logger`, and only a dependency of the claimant's module that instantiates the name is fulfilled by the distinguished name (`.instantiated(fulfillingTypeDescription: ModA.Logger, …)`, `Instantiable.distinguished(asFulfilling:replacingMentions:fulfillingInstantiationsOf:)`), which generated code never spells: the seam that holds it is a leaf. Another module's dependency that instantiates the name, or its `mockOnly` declaration of the claimant's own type (`moduleNamesThatMayMean(_:claimedAs:)`; one of another type provides that type's mock), leaves the name whole where that module may mean what the claim claims and may construct the claimant. What a claim means is that rule applied in the claimant's module (`modulesMeant(by:in:)`), and the viewer can write the claimed name when the claim means nothing SafeDI records or what the viewer means by the name.

A name stays whole, and so stays the duplicate error, when: two declarations remain the viewer can name; the viewer's name is unknown (the Xcode project plugin), since `viewer.moduleName` is `nil`; a declaration the viewer cannot name is a seam or has a public mock, because `SeamResolution.foreignSeams`, `foreignDeclarationsSeenByModule` and `seamRoots` key those by the type each module sees, so one key would hold two modules' signatures; the spelling is another type's key; the claim is not a named type (`qualified` returns `nil`); a hidden declaration is a claim and the viewer can name another declaration that means a different type by the name (an app's own `Store` beside a hidden claim of `Base`'s `public` `Store`), since a third module's mention of the protocol, left as written, would resolve to that other declaration; or another module may mean a declaration told apart, or the declaring module cannot settle what it means (above). The duplicate error says the rule (`nameRule`, with the seam clause when a seam or public mock is among them).

An access error about a construction of a distinguished type leads with the remedy that keeps it out of this module (a public mock of its seam, or a seam), since widening both types would make them compete, and offers no fix-it (`constructedTypeDeclaredName`). `query needs` takes no viewer: it has no emitting module, and `--include` directories record no package, so such types stay the duplicate error there.
