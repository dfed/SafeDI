# Module membership and access between modules

## Module membership

`generate` records, outside the visitors so scan's cache never holds it, the module and package that declare each `@Instantiable` (`Instantiable.moduleName`, `packageName`, and `mockDeclarationModuleName`/`mockDeclarationPackageName`, which travel with `mockInitializer` through `mergedWithMockProvider` and are cleared by `withoutHandWrittenMock`), and the module it generates code for (`ModuleInfo.moduleName`, `packageName`, `dependencyModuleNames`, the module's direct dependencies and any modules beneath them its run read). `ModuleMembership` (`ModuleMembership.swift`) decides them, and `ModuleInfo.declared(by:dependingOn:)` applies them once the module, additional directories included, is assembled, before normalization and before `--module-info-output` is written; nil means unknown, never "this module". Three sources are independent. Own files: a run per module (Bazel, Tuist) passes `--module-name` and `--package-name`, which, when either is given, describe every input file (CSV and `--include`) and no other, so an `additionalDirectoriesToInclude` file has no module; otherwise a run with a manifest reads the target graph (below); otherwise own files have no module. Dependencies: the modules the `--dependent-module-info-file-path` files record (sorted, without duplicates; a file that records none adds nothing), whichever way own files were attributed, joined with the planned target's dependencies when the target graph was read; the files' names are the direct dependencies Bazel's `deps` and Tuist's `dependencies:` list, with, in a module that reads them, the modules `--transitive-module-info-file-path` names, and cannot drift from the files. A dependent `.safedi` carries what its producer recorded. The target graph, which a run with a manifest reads when neither option is given, is the file the SafeDIGenerator plugin writes beside its CSV (`<CSV path>.targets.json`, `PluginTargetGraph`, `Sources/SafeDIToolLibrary/PluginTargetGraph.swift`, which the plugin compiles through a symbolic link, so the plugin encodes and the tool decodes one declaration; written by `writeTargetGraph`): the planned target and every target of `sourceModuleRecursiveDependencies` (the CSV's targets, the SafeDI path dependency and the leaked swift-syntax `VersionMarkerModules` included), each with SwiftPM's package identity (the `Package.id` of the package that declares it, found by walking `context.package` and its dependencies; `-package-name` carries it C99-mangled: `swift-syntax` becomes `swift_syntax`), its Swift files spelled by the same code that spells the CSV (`inputSwiftFilePaths(of:relativeTo:)`), and its direct dependencies' module names, sorted. The plugin API cannot tell whether a dependency target applies SafeDI's plugin (every target's `pluginGeneratedSources` is empty), so the graph does not say. Both of the plugin's `generate` forms read it: the manifest form (`<csv> --swift-manifest`), and the fallback form (`<csv> --output-directory … --mock-scoped-files …`, which scans for itself with the working directory as its project root and runs on every cold Swift Build build and every Xcode build of a package). A file belongs to the target that lists it, matched exactly: a fresh parse names a file by its CSV entry, and scan's cache names it relative to the package directory, or normalized outside it, which is how the plugin spells the entry, so no path is spelled again (targets that split one directory with `sources:`, or nest, are told apart, and the fallback form's working-directory root changes nothing); a file no target lists, or two targets list, has no module. The Xcode project plugin writes no graph and passes neither option, so membership is unknown there, as it is for a hand-written manifest: an Xcode project target is an ordinary run without a module name, by ruling, since the plugin cannot say which module declares a file `additionalDirectoriesToInclude` adds. `generate` drops every import of the module it generates code for (`module.moduleName`) from the imports it hands `DependencyTreeGenerator`, `additionalImportedModules` included, since a file read from a module above can import this one and the compiler warns at an import of the module it compiles (`#ModuleSelfImport`); the `.safedi` keeps them, since a module that reads it imports this one rightly. A run that names no module keeps them, so an Xcode project target that reads such a file gets that warning, as in 2.2.0: a foreseeable warning accepted by ruling for a shape no adopter has, which the Manual's "Limits of the Xcode project plugin" states. `query` records every declaration of an included module as that module's (`IncludedModule.name`, or the module name a `.safedi` records), with the package a `.safedi` records and none for a directory (`readIncludedModules()`); it checks no access, and its report still names modules as `IncludedModule` does. An `IncludedModule` name can be several path components (`Home/Sources`) and need not be the compiler's, so nothing may compare a module name `query` records with one a build recorded: the enforcement reads it only to group a query's declarations by module.

## Access between modules

- **Access between modules** (build-time, `SafeDITool generate`): every construction `generate` emits must compile in the module it emits it in (the `emittingModule`: `ModuleInfo.moduleName`/`packageName`, the module's own files – the manifest's `mockScopedFilePaths`, or else the input files (CSV and `--include`), never a file reached through `additionalDirectoriesToInclude` – and whether a recorded file can be read). A construction is a production root or a type its tree instantiates – the fill of a seam call included, the fulfilling type and its tree, reached at the call's reference location – built with its initializer or `instantiate()`, a type a mock builds, with its hand-written mock where `mockReturnTypeIsCompatible` says the mock builds it with that, and a mock root. A flat `mock()` parameter defaults to a hand-written mock only where that construction passes the check (`flatParameterMockDefaults(in:emittingModule:)`), so a default is never reported. The declarations it relies on (`Instantiable.accessNeeds(constructingWithMockMethod:)`) – the types enclosing the type in its file, the type, and the method, each with the level it has by itself, or an extension a declaration that spells no modifier takes its level from, and, for a type an extension declares – one declared inside it, or the type of an `@Instantiable` extension – the declaration of the extended type in the extension's module and those enclosing it in its file (`extendedTypeAccessNeeds`, which `Construction` stores, so the check reads the same needs, as does `constructsOnlyPublicDeclarations`): its own `@Instantiable` declaration, or else its plain declaration (`PlainTypeDeclaration`, which `FileVisitor` records for every `struct`, `class`, `actor`, `enum`, `protocol` and `typealias`, in the `#if` clauses it scans and directly inside extensions), which `ModuleInfo.plainTypeDeclarations` carries attributed to modules as instantiables are, and `ExtendedTypeDeclarations` looks up by module name and the type's spelling without backticks (`TypeDescription.plainDeclarationKey`, by which `TypeAccessProof` looks plain declarations up too), preferring those in the extension's file and otherwise those visible outside their file, and of several, which clauses of a platform block declare, the narrowest, first in source order on a tie (`PlainTypeDeclaration.isVisibleOutsideItsFile`; a `private` or `fileprivate` type of another file is never the extended type, which an imported type of its name can be); and, when that declaration is itself inside an extension, the declarations that bound the types that extension declares, found the same way from the declaration's file, and on, outermost first (`ExtendedTypeDeclarations.accessNeeds(boundingTypesAnExtensionOf:declaresInModuleNamed:fromFileAt:)`; a type the extension's module does not declare ends the walk and is left to the compiler, since a namesake in another module could fail a construction that compiles) – must each satisfy `AccessLevel.required(toConstructFrom:declaredIn:isOwnFile:)`: `internal` for a declaration in an own file or the same module, `package` within one package, `public` across packages – two named modules with different packages, or one of which SafeDI is told no package of (decision 64: a named module not told its package has none, and the error's fix for a `package` declaration also says to pass the package, `ModuleIdentity.passingPackageRemedy(forModulesNamed:)`, as the seam and public-mock omission errors do for a parameter whose tier is `package`) – and `packageUnverified` (`package` accepted, with no annotation) only where a module name is unknown on either side and the two packages are not both known. So SafeDI checks package membership wherever it knows both modules' names, and assumes it only where it does not. A module whose name is unknown assumes `package` and builds another module's tree inline rather than calling a tier or a public mock; from outside that package the generated code does not compile (row 4b's B4.10b, M8.35b): a stated limit, never pinned. Effective access (`AccessReachability.swift`): a declaration's spelled level, or, when it spells none and is directly inside an extension, the extension's (`fileprivate` for `private`), capped by each enclosing type; a member defaults to `internal` in a type whatever its level and to its extension's level in an extension (`AccessDeclaration.isExtension`); an extension caps nothing, spelled or not, as in Swift, which only warns at a member more permissive than its extension, so the type an extension-based `@Instantiable` declares is taken to be `open` (its own access is unknown) and its methods have the levels they have by themselves. A failure is `inaccessibleConstructions`, one error per declaration to widen, in source order, once however many constructions, roots, or mock roots need it (`InaccessibleConstruction.merging`, which keeps the construction with the earliest reference, then the one whose type is declared first, so an error at a reference names the type that reference constructs and root order changes nothing); in a mock's tree the error names the mock (`InaccessibleConstruction.mockRoot`; of two mocks that reach one declaration through one reference, the one declared first), and the fix also suggests a public mock of the outermost type another module declares on the path, one with neither a hand-written nor a public mock and not an extension's (`Construction.publicMockCandidate`) – declaring it `public` too when it is narrower, and saying, for a seam, that mocks build a seam's tree inline: at the declaration with one fix-it (replace the modifier, or insert one where the declaration begins) when its file can be read, else at the first reference in source order in this module, naming the declaring module. A production construction's fix also offers a seam (`InaccessibleConstruction.SeamRemedy`): its candidate is the outermost type on a path from the root, the constructed type included, that a module SafeDI knows, other than this one, declares, and the walk keeps it only when every path to the construction has the same one and the candidate's module reads every type on each path from the candidate to the construction, the construction's own type included (`SeamCandidateOnPaths`, which only narrows, so the walk revisits a scope whenever it changes, as for an earlier reference); a seam whose module SafeDI knows, a leaf, and an extension-based type instantiate nothing, so none is ever another construction's candidate, and a seam call's fill starts a path of its own, whose candidate is the fill's type (`SeamCandidateOnPaths.agreed(nil).extended(to:childIsCandidate:candidatesModuleReads:)`); no candidate above the seam reaches it, since a type above it declared a seam passes the builder up to this module whenever its own module cannot see the fulfilling type. The initializer generated for the candidate has its widest tier at the candidate type's access and calls every initializer of the tree inside the candidate's module, the candidate's own included, taking a pass-through at the access of the types it names, capped at the candidate's type, so the remedy is withheld (`seamRemedy(offeredBy:toWiden:declaredIn:extendedTypes:)`) only for what a call of a seam leaf reads – the candidate's type, its enclosing types, and the type an extension declaring it extends (`seamLeafAccessNeeds(of:)`, `extendedTypeAccessNeeds(of:in:)`, which `Construction.accessNeeds` reads for a seam leaf) –, for every declaration when the candidate builds no tree (`buildsTree(_:)`, which also decides that SafeDI generates the seam no initializer, so a leaf's own construction offers none), and for a declaration the candidate's module cannot reach. A module reads the modules whose declarations its own run of `generate` reads, as `seamResolution` computes a seam's signature from them (`EmittingModule.moduleNamesReadByRunOfModule`, `Generate.moduleNamesRead(byRunOfModuleNamed:dependencyModuleNamesByModuleName:membership:)`): itself and, under Bazel's or Tuist's invocation, the modules its module info names as read (those it depends on directly and those it read from beneath), or, under the plugin's target graph, every module it depends on, directly or not. A run under Bazel, Tuist or a custom script is given the `.safedi` of each module it depends on – each module whose types its own source or the code generated for its roots and mocks uses, so a module with a root is given every module beneath it (Manual, "Which modules to list"), and a type its trees reach in a module it is not given fails a root's tree and becomes a parameter of a mock – and never one only for another module's seam or public mock. The Bazel rule collects that closure itself: `SafeDIInfo.transitive_module_infos` is a depset built as rules_swift builds `SwiftInfo.transitive_modules`, every `safedi_compile` action has all of it as inputs, and passes it, flattened only at execution through an `Args` object, with `--transitive-module-info-file-path`. Dependency trees alone ask for a module beneath (`ModulesBeneathSelection`): `generate` reads every module beneath that declares a type a tree needs and nothing read declares, and a module read this way behaves as if it were listed. A root's tree that needs a type nothing read declares does not build, so a read for it can only fix the build or report what a complete list reports. A seam's tree takes such a type as a builder (a hole), so a read does what listing the module does: the seam builds the type and its initializer stops taking that builder, or the run reports the duplicate. The selection has no gates: two declarations of one type, from any two modules read, are the ordinary duplicate error. The generated code imports each module read this way (`importsOfModulesReadFromBeneath`), since the files that import it can be in a module no tree needs; a listed module's imports stay what the files read import. A mock asks for nothing, because it takes what it cannot build as a parameter, a valid state that a read could turn into a failure in as many ways as `generate` can reject a mock; a mock builds what the list and the modules read for the trees declare. `generate` opens the file only when the module declares a root or a seam (a module with neither does not open it, and the roots of the modules it lists start no walk, because listing a module changes the signature of a mock that reaches it, so the set must not reach a module with no tree), and then only when a walk over its own declarations and those of the files `--dependent-module-info-file-path` lists, from its own trees and the roots of every module it reads, reaches a type none of them declares, so a module whose list leaves nothing open pays nothing. At a seam another module generates, the walk goes through that seam's tree over the declarations that module read (from the files and their views). A type that module does not read is a hole, a need of this run unless a seam between its tree and the hole fills it (that seam's module reads a type that fulfills it; the walk then goes on through that fill's tree). The run needs what fills the hole and, since the generator reaches a fill only through the declarations the run read, every type on a route from its tree to the hole on which no seam fills it, so it reads each module beneath that declares one. It reads each file without its view (`ModuleInfoFile(moduleInfoDataWithoutView:)`, since a view grows with the modules beneath), and reads whole every module that declares a production declaration of such a type, combined with the listed files in path order (`moduleInfoFilesIncludingThoseBeneath`). It works in rounds: a whole walk over what has been read names the files it wants, which are then read together. So a module beneath that no tree needs is never read: it is never a duplicate and never enters the module's `dependencyModuleNames` or view (a seam module above it leaves a no-tree module that lists it unchanged), and a module is read whole or not at all, because a dependent computes a seam's signature from the whole of each module in `dependencyModuleNames`. Tuist passes no such option and lists the closure, and a custom script does either: each `.safedi` carries, in `ModuleInfoFile.view`, the module graph of its closure (`ViewedModuleIdentity`: names, packages, dependencies, mock conditions) and, without positions (`withoutPositions()`), the declarations and imports of each module in the closure that declares a seam or public mock and of their direct dependencies (`ViewedModule`), so a run given the modules it depends on computes any reached seam's or public mock's signature without the modules beneath them; the view never fulfills a type of this run's own trees (`typeDescriptionToFulfillingInstantiableMap` holds the given files' declarations and the module's own only), and an error about a type only a view declares names the module it reaches it through (`DependencyTreeGenerator.ViewDeclaringModule`). Positions are stripped so a position-only edit leaves every dependent's `.safedi` byte-identical, while `sourceFilePath` and `AccessDeclaration.spellsAccessModifier` – a stored fact, not `modifierRange != nil` – stay, because a signature's tiers and proof read them. Every `.safedi` names its module (`--module-info-output` requires `--module-name`, and `safedi_compile.module_name` is mandatory); the generated file imports the view entries' imports too, and `GeneratedImportAccess.WrittenLevels` attributes through them by module and path. Its imports decide nothing: a module imported but not read is one whose `@Instantiable` declarations its run does not see (a transitive dependency under Bazel), so the seam would take a builder for the type and this module would fill it; a type whose module SafeDI does not know, or an implementation that a module depending on the candidate's provides, is read by no other module. A required parameter narrower than the candidate's type is then the declared seam's `tierOmitsRequiredParameter` in its own module, never an error at the declaration the remedy was offered for. An error merging several constructions offers the remedy only when all offer the same; a mock builds every tree inline, so its errors offer none. In a production tree of a module SafeDI cannot name (a run given no module name, a target the Xcode project plugin builds among them), the outermost seam another module declares that the tree builds inline (no `seamCall`) on the earliest path to an inaccessible construction (the seam's own construction counts) also gets one error at its earliest reference (`InaccessibleConstruction.InlineSeam`, reported by `sourceDiagnosticGroups(of:)`), which says why the tree is built inline, names the first declaration in source order to widen, of a type other than the seam where there is one, and leads with making the tree's types and initializers `package`, or `public` across packages, as the error at each declaration does, then how SafeDI comes to know the seam's module under the only runs that report it, those that name no module (the Xcode project plugin: a local Swift package; a run by hand: the seam's module's info, written with `--module-name`, which a run that names no module reads and calls the seam through). Production runs it in `rootScopesThisModuleGenerates`, before any generator exists, since creating one starts generating code; a module generates only the roots its own files declare (decision 79): a root declared outside them is never generated or checked there (`rootsOfOtherModules`), and its file holds the header and a comment naming the declaring module, when SafeDI knows it, and saying to add the SafeDI plugin to the target that declares the root, or nothing when the root has no dependencies, since its own module generates no `init()` for it either. The consumer still validates that root's tree with the rest, as it always has. Mocks run it in `createMockRoot`. Nothing runs when every declaration any generated code could construct is `public` or `open` (`constructsOnlyPublicDeclarations`). The Xcode project plugin is a lesser integration by ruling: SafeDI knows no module there, so seams across targets (built inline there), holes in a seam's tree (an error there; a public mock's hole builders work) and generated calls of public mocks are unsupported, and the Manual's "Limits of the Xcode project plugin" is the one place that says so; `generate` cannot tell it from any other run without a module name, so no diagnostic or comment names it (`EmittingModule` knows a module name or not); a change that adds Xcode support is taken only when it costs the other integrations nothing.

## Pitfalls

- The input CSV written by plugins includes ALL swift files (target + dependencies). Mock scoping requires passing `mockScopedSwiftFiles` separately — only the target's own files.
- **An import added for a fulfiller answers to files SafeDI does not read** (`FulfillerImports`). A generated file gains the import of a module its trees build a type of for a property that does not name it, of the module of a `mockOnly` declaration another module's mock merges in, of a type a flat `mock()` parameter defaults to, and of the type an `additionalMocksToGenerate` entry names, unless a whole-module import of that module or an import of that type by itself, through any module, is already there (a merged mock's module needs the whole-module import, since an import of the type does not bring in its method). Only then does `generate` read the module's own files, each once and in parallel, the first time a generated file would gain such an import apart from a type of the module that shadows the fulfiller, which only the read can find, so a module whose own types shadow every fulfiller reads them all and gains nothing (`ownFiles(at:conditionalCompilation:)`, `FulfillerImports.OwnFiles`, which holds what every later question needs and depends on no order; the build systems declare them inputs): the compiler compares imports across every file of a module, so the added import spells a level where any own file imports that module below `public` (an unleveled import is ambiguous beside it; a `public` import elsewhere asks for none; only this import is affected, not the file's other imports) and is `@_implementationOnly` where any own file's is, the two together when an own file's import is both, and no import is added for a type the module itself declares where other files can see it, since that type shadows every import.
- **Which module declares a file is not "own" versus "other".** The SwiftPM plugin's CSV also lists files of no target of the package being built – every source of the SafeDI path dependency, and swift-syntax checkout files nested under `Sources/VersionMarkerModules/`, which slip past the `checkouts` check – so membership comes only from `PluginTargetGraph`, which lists those targets too, and is `nil` (unknown) for any file no target lists, never this module. The graph lists each target's files spelled by the code that spells the CSV, so `generate` matches a declaration's file by exact string and never compares spellings: change one spelling and the other in `inputSwiftFilePaths(of:relativeTo:)` together. The plugin declares the CSV and the sidecar as inputs of its `generate` command and writes each only when what it holds changes (`writeIfChanged(_:to:)`), so a change to the targets that changes no Swift file reruns `generate`, and a plan that changes nothing does not. The sidecar is written in the package path of `SafeDIGenerateDependencyTree.swift` only: the Xcode project plugin has no package information, so its runs know no module, and a SafeDITool older than the sidecar ignores it. A sidecar that exists but does not decode is an error (`UnreadableTargetGraphError`), not a silent unknown.
- **Generated imports spell the access level each file needs** (SE-0409; `GeneratedImportAccess`). Without `InternalImportsByDefault` an import with no level is `public` and the compiler rejects it as ambiguous beside another file's import of the same module below `public`; with it, such an import is `internal`, too narrow for a `public` declaration naming the module's types; and an unused `public` or `package` import warns. SafeDI cannot see the feature, so each generated file decides each import's level from its own code: when no own file of the module spells a level on an import, none is spelled (the old output, byte for byte); otherwise `public` when a `public` or `@usableFromInline` declaration of the file names a type the module may declare, or the import is `@_exported`; else `package` when a `package` declaration does (behind `#if hasFeature(InternalImportsByDefault)` when the own files import that module at no level below `public`, since a `package` import would make one of their unleveled imports ambiguous); else `internal` when the own files import the module below `public`; else no level. Generated mocks and public-mock configurations compile only where the mock condition is active, and an unused `public` or `package` import warns in every build where it is not (a Release build), so a level only mock code needs is spelled under the condition, with the level the rest of the file needs in `#else` (`#if DEBUG` / `public import X` / `#else` / `internal import X` / `#endif`, `GeneratedImportAccess.Spelling.underMockCondition`): a mock file's code is all under it, and a file holding a module's whole output hands its dependency-tree code and mock code apart (`DependencyTreeGenerator.GeneratedFileContent.dependencyTreeAndMock`); mocks generated without a condition, and an `@_exported` import, which does not warn unused, need no guard. `ImportStatement` records `accessLevel` and, only when it spells one, `sourceFilePath` (set by `FileScan.relocated(to:)` and `withImports(evaluatedWith:)`), so `generate` takes the module's own levels apart from those of a dependency's file (`GeneratedImportAccess.WrittenLevels`, by the `isOwnFile` the access check uses), which the SwiftPM plugin's CSV holds too and which say nothing of the module's own imports. The header is made per file from the file's body (`DependencyTreeGenerator.fileHeader(for:)`), which is parsed only when the module spells levels and the body spells `public`, `package` or `@usableFromInline`; a type is attributed to the modules that declare it as SafeDI read them (an extension's `@Instantiable` declares none, and a declaration of a module SafeDI does not know attributes nothing), to SafeDI for its wrappers (`WellKnownTypeNames`), to no module for the standard library's types, to a module a qualified spelling names, and otherwise to Foundation for its well-known types, to every module the own files import at the declaration's level or wider, and, unless it is one of Foundation's well-known types, to every module that a dependency's file declaring an `@Instantiable` that names it (in a dependency or an initializer parameter) imports at `package` or wider, since a seam or public mock names types its tree receives from other modules – an over-approximation the Manual states. A fixture that spells an import's level spells its own `import SafeDI` (`VerificationCompilerSettings(prependsSafeDIImport: false)`), and `SafeDIToolImportAccessLevelTests` compiles each cell with and without `InternalImportsByDefault`, and each cell whose public mock needs a `public` import in a release build too (`ModuleFixture(isReleaseConfiguration: true)`); a public mock that names no imported type gets no such import, so a release build cannot warn at it, and its cell compiles in debug only.
