# Graph fuzzer: drawing a change, running seeds, the multi-module partition and the public mock corpus

- **Drawing a change.** The fuzzer finds defects only in shapes it draws, and only once the draw runs under the code. So, as TDD asks of unit tests:
  - **A new shape gets a draw in the same PR.** A change that makes the generator accept or emit a shape it did not adds a draw for it in the PR that holds that code – never in an earlier PR, where the generator does not yet accept or emit the shape, so the draw cannot be checked, nor on a parallel branch, where no oracle runs under the code. The draw takes a stream of its own (a pass with its own generator, or a mask like `seamRandomSeedMask`), so every graph without it is drawn as before, and it must produce graphs the tool accepts.
  - **A fix adds a roll.** A fixed generator defect gets a roll – a new draw or a widened one – whose graph reproduces it: with the fix reverted, an oracle fails on a named seed, and with the fix it passes; the PR names the seed. A defect the fuzzer found has its seed already; one a reviewer or a hand probe found does not, and its neighbors (the same fix's lazy form, its alias form) are where the next one hides. The hand-written regression test still comes first.
  - **A new oracle shows it fires.** Its PR names a hand mutation – a deliberate break of the generator, such as reverting a fix or reading another level – and the seed that fails under it. An oracle that has never failed may be unable to.
  - **Floors beside the pins.** A new draw feature checks a floor on the graphs of it the tool accepts, and a new oracle a floor on the graphs it judges: ten, below which a feature no longer stands in for unit tests (`fuzzer-overview.md`). Exact pins are copied from CI's output, so a zero pins like any other count; a floor fails. A draw whose rolls the tool mostly rejects says why in the PR.
  - **No global off switch.** An oracle skips only seeds it names, each with its reason, as known issues do; never every graph behind a flag, a constant or a feature check. An oracle turned off to land a draw hides the defects the draw was for.
  - **Coverage at hand-back.** Before handing back a generator change, run the coverage report ("Coverage of a change", below) and give each run it lists its one-line disposition. It is advisory: a run may stay undrawn with a reason.
  - **When no draw can reach a shape, say why** in the PR: the macro rejects it, the corpus cannot compile its spelling, or an oracle's scope leaves it out. Hand-written tests cover it.

  Keep it in proportion. A small fix in code the corpus already draws needs only its reproducing roll. Docs, diagnostic wording, tests and CI need nothing.

- **Run a seed.** `SAFEDI_GRAPH_FUZZER_STARTING_SEED=<seed> SAFEDI_GRAPH_FUZZER_ITERATIONS=<count> swift test --traits sourceBuild --filter SafeDIToolGraphFuzzerTests/longRun`, or `SAFEDI_GRAPH_FUZZER_ITERATIONS=corpus` for the whole corpus, which then checks the accepted-seed pins itself; add `SAFEDI_GRAPH_FUZZER_FEATURES=generateDependencyTree` for the seam corpus, or `generateMockPublic` for the public mock corpus (`graph-fuzzer.yml` takes the same as its `features` input). Each failure's issue prints the fixture and the compiler output. `SAFEDI_GRAPH_FUZZER_REPORT=<path>` appends progress to a file. The run also checks that no corpus graph uses a label beginning with `__safeDI_`, the prefix of generated builder functions. To explore graphs beyond the corpus, dispatch `.github/workflows/graph-fuzzer.yml` with another starting seed and count; its `shards` input splits the run across jobs (`SAFEDI_GRAPH_FUZZER_SHARD=<index>/<count>`), four by default for the seam corpus.

  `Scripts/fuzz-corpus.sh` does this and prints the pin lines; `--seeds 98,311` runs listed seeds in one process.

- **Coverage of a change.** Before handing back work that changes `Sources/SafeDICore` or `Sources/SafeDIToolLibrary`, push it under a branch name and run the `pre-review` skill, which dispatches this run and prints its report in its block. The run is `gh workflow run verify.yml --ref <the branch> -f pins=true -f base=<the commit it builds on>`, which tests the commit from the same build (`graph-fuzzer.yml -f coverage=true` fuzzes alone; `base` defaults to the merge base with main, and the report lists what the branch's commit changed since its merge base with `base`). The run builds the commit the branch held when it was dispatched, so a later push changes nothing; keep the branch until the run finishes. In about 47 minutes from a cold build (run 43774444496: 25.5 building, about 10 waiting for runners, since `pins` adds 13 jobs beside the 7 test groups; `graph-fuzzer.yml` alone took 13 from a saved build, 43762600658), it builds that commit for coverage, runs the unit suite and ci.yml's corpus shards, checks the pins (the `apply-fuzzer-pins` skill writes moved ones), and "Report Changed Lines No Fuzzer Graph Executed on Linux" lists, in its summary and `fuzzer-coverage` artifact, each changed line no corpus graph executed, in numbered runs, split line by line into those a unit test reaches and those nothing reaches. Give every run a one-line disposition: `R<n>: draw added` (dispatch again to confirm), `R<n>: rejected-graph draw added`, or `R<n>: no graph can reach, because …`. The report says what it cannot: a line it does not list was executed by some graph, perhaps a rejected one or one an oracle skips, so not necessarily judged, and a deleted line, a wrong value on executed lines, or an untaken `??` or ternary arm within an executed line (the export has no branch records) never shows. It names a shard that left no profile or no report, since a crashed or timed-out shard's lines would be listed (each workflow's `EXPECTED_SHARDS` names its fuzzer matrix, and the report fails when another shard reports), and counts rather than lists changed default values of stored properties that neither the corpus nor the unit suite ran. ci.yml makes the same report on every pull request and push to main, against the merge base with main, so a stack's top pull request lists every slice's lines; `Scripts/fuzzer-coverage-report.sh RUN [BASE]` reports a run's artifact against another base.

- **Multi-module partition.** The oracle also runs every graph that declares no seam and no public mock – each of the base corpus's – split across modules through both multi-module integrations of `executeSafeDIToolMultiModuleTest`, `.moduleInfo` (Bazel's flow: `generate --combined-output --module-info-output --compiler-receives-input-paths-unchanged --module-name --package-name` per module, reading the listed dependencies' `.safedi`; Tuist's differs only by omitting that flag) and `.swiftPackagePlugin` (the SwiftPM plugin's: one CSV per module holding its files and its transitive dependencies' files, the module's own mock-scoped, with the target graph beside it, `scan` while planning and then `generate` with the manifest, one file per root and per mock), without compiling, and requires the same results (`integrationsDiffer`). `GraphFuzzerPartition` (`Tests/SafeDIToolTestSupport/GraphFuzzerMultiModule.swift`) is a pure function of the graph – it draws nothing from the seed, so `corpusFixtureHash` and the accepted-seed pins are unchanged by it, and `smokeAndKnownIssuePartitionHash` and `corpusPartitionHash` pin the partition itself, so a change to it is deliberate (they move with the generator and the known-issue list as well, as the fixture hashes do). The partition projects the fixture's files first (`projectedFiles(of:)`): the helper types `Value` and `Unbuildable<n>`, which the generator declares in `Root0`'s file, move into a file of their own (`S<seed>_Helpers.swift`, named explicitly), since left there every type of `Root0`'s tree that names them, with the files between, would share `Root0`'s component, so `Root0` could never be split from a type of its tree that forwards `lazyValue`; the helper file is visited first, so it is the first component and always lands in `Alpha`. Each file refers to the types it names (instantiated, received, forwarded, aliased, erased to, named by `fulfilledByType:`, the graph's `Value` and protocol types, the extended class), each name is declared in one file, and Tarjan's algorithm over that reference graph, visiting the helper file first and then the files in order, lists each strongly connected component after every component it refers to (the helper file, which refers to nothing, is the first component; a lazy cycle through instantiators is one component, so its types share a module; a root's component follows those of the types its tree names; the roots are the first files, so the types no root's file refers to, directly or through other files, are visited after them and their components follow the roots', and a root need not be in the last module). The components are dealt out, contiguously in that order, to `Alpha`, `Beta`, `Gamma`, `Delta` – as many as `GraphFuzzerHash` of the fixture's text chooses, one to four, so single-module graphs stay in the corpus – so every reference points into the same or an earlier module. The two integrations combine declarations in different orders: `generate` lists the dependencies' `.safedi` files, read in path order, before the module's own declarations, while the plugin parses every module's files in path order (`Sources/<Module>/…`), the module's own among them; `Delta` sorts before `Gamma`, so in a four-module graph whose `Delta` depends on `Gamma` (otherwise `Gamma`'s files are not in `Delta`'s CSV and its `.safedi` is not read) the plugin combines `Delta`'s own declarations before `Gamma`'s where the module-info integration combines them after – kept deliberately, since a real package's module directories sort arbitrarily against a Bazel build's `.safedi` paths, so those graphs, 518 of the corpus's 5000 (the long run counts them as `delta-depends-on-gamma` on its `partitions` report line), check that nothing SafeDI generates or reports depends on that order (the corpus passing with it is the evidence). A module's `dependencies` are every module whose declarations its `generate` must read, the modules its files refer to and, through them, theirs: what a Bazel user lists in `safedi_compile`'s `deps`, since a `.safedi` holds only its own module's declarations, so a tree reaching a declaration two modules down needs that module listed (`multiModuleTest_throwsErrorForGrandparentDeclaration_whenModuleInfoListsOnlyTheDirectDependency`); the plugin lists the transitive closure's files itself, so both integrations read the same declarations. Every other file keeps its name and content; `Root0`'s loses only the helper declarations; each gets an `import` line per module it refers to before it, and the module, package and helper file names hold no digit but the seed's, so the renamings leave them alone. The property compares module by module in dependency order (`GraphFuzzerMultiModuleOutcome.difference`): a module both generate must have the same generated units, each byte for byte, the combined file's imports in every one of the plugin's files (the plugin's dependency-tree and mock files import what each kind needs, which differs only through `#if`-guarded imports, which no fuzzer graph has), and the same warnings; a module the module-info integration rejects must be rejected with the same diagnostics, in any order, by the plugin. A unit is one generated extension, keyed as the plugin names the file it writes (`<Type>+SafeDI.swift`, `<Type>+SafeDIMock.swift`, `<Type>+SafeDIMockConfiguration.swift` for a `SafeDIMockConfiguration` struct wherever the plugin places it), with the `#if` the mock condition wraps it in, and with every path under the fixture root reduced to `<fixture-directory>/…` (`GraphFuzzerGeneratedModule`): the combined file's joined bodies and the plugin's per-file outputs reduce to the same units, and a `#sourceLocation` directive differs between the integrations only in the fixture root's spelling (the plugin's resolved root against the CSV's path under `--compiler-receives-input-paths-unchanged`). Two differences are the integrations' own. One needs no normalization: the plugin's `scan` plans a dependency-tree file for every root in its CSV, so a consumer writes a file for each dependency's root, which holds a comment and no code, so no unit, and the outcomes compare as written. The other is normalized rather than reported: the plugin adds a build command only for a module whose manifest plans an output, so a module runs `generate` under it only when its own files declare a mock, or its own or its dependencies' files declare a root (`scan` plans every root in the CSV), and a defect its declarations alone reveal (two types fulfilling one protocol, seed 20) is reported where the first module that depends on it generates, or nowhere – the property expects those diagnostics there, requires that the module-info integration generated nothing for a module the plugin skips, and takes an unreported defect as the plugin's design; when the plugin first rejects a module that does not depend on the skipped one, nothing is compared, because `.moduleInfo` stopped at the skipped module and never ran that one. It runs in the smoke batch, which must split graphs into one, two, and three or more modules and reject some split ones, and over the corpus in the long run, whose report counts the graphs at each module count (`partitions`) and notes each differing graph (`multimodule`). Measured: the plain run adds about a quarter of the long run's CPU time (500 seeds: 290 s to 359 s of CPU), so only the graph as generated is split (`GraphFuzzerOracle.multiModuleRenamings`): each of the five renamings would add as much again. The seam and public mock corpora are not partitioned: a graph of theirs that is split across modules is split by roles of its own (`GraphFuzzerModule`), which the partition does not model, and runs through `.moduleInfo` alone.
- **Twins over a shared screen.** A base and seam corpus pass after `addingScreensLaidOutFromPerTypePlan`, on a stream of its own (`twinRandomSeedMask`, four graphs in a hundred of the base corpus and ten of the seam corpus's), `addingTwinsOverSharedScreen`, draws one label declared by value on one type and as a `LazilyInstantiated` (in half the `Sendable` graphs a `SendableLazilyInstantiated`) on another, inside a cycle: `TwinRoot`, or in the seam corpus `TwinSeam` beneath it, builds `TwinFirst` by value or through an instantiator and now and then opens `TwinSecond`; each declares `twinModel` in one of the two forms and builds `TwinScreen`, which receives it, required or only if available, and now and then builds `TwinPanel`, which receives it too; `TwinModel` opens `TwinSecond`, so the cycle closes on whichever twin a path built first. Two rolls of their own have both parents declare `twinTheme`, which `TwinModel` receives: by value on both (`themeInSameForm`, t8 of the cycles lane's replay), or by value on `TwinFirst` and as the lazy wrapper on `TwinSecond` (`themeInMixedForms`, in every graph but one in five whose lazy twin is a `SendableLazilyInstantiated`, counted apart since the read is then inside its `@Sendable` builder; the twin whose parent holds the theme by value calls the function the other closes on with `SendableLazilyInstantiated<TwinTheme> { twinTheme }`, which the query oracle reads as the value it holds). The public mock corpus draws the same tree beneath `TwinHome`, a `.public` type with an `internal` initializer that a mocked consumer builds (`drawTwinsPublicMock`, `fuzzer-public-mock-corpus.md`). Each shape is a `TwinShape`: the seam and public mock corpora count them as draw features (`twinsOverSharedScreen…`, `twinsPublicMock…`), drawn and accepted, the base corpus as `GraphFuzzerFeature`s (`twinsOverSharedScreen…`, in `corpusAcceptedFeatureCounts`, smoke seeds 2186 and 2449 showing them), and `SafeDIToolGraphFuzzerTwinDrawTests` pins the base corpus's drawn counts and runs, in the ordinary suite, seeds that together draw every shape, asserting each accepted and, in the base corpus, the plan seeing the twin (`PlanBodiesObservation`); the value oracles judge them as every graph.
- **Public mock corpus.** The `generateMockPublic` feature's draw, oracles, pins and known issues are in `fuzzer-public-mock-corpus.md`.
- **Keyword labels.** No other draw labels a property as a keyword, so two draws do, each on a stream of its own and after every other draw: in the seam corpus, `labelingHoleOwnersAsKeywords` (`keywordLabelRandom`, two graphs with a hole in five) labels the seam's property that builds `HoleOwner` at its first site `Type`, `Protocol`, `Self`, `init` or `default`, a level of the hole's builders, a member of its builder struct where the hole type takes one, and a field of the seam's overrides where it is mocked (`holeOwnerLabeledAsKeyword`), and, on a roll of its own, `holeServiceLazy` `Type` or `Protocol` where a `SendableLazilyInstantiated` holds it, a case of the `@Sendable` enum that carries no values (`holeSendablePlaceLabeledAsKeyword`); in the public mock corpus, `drawKeywordLabeledPublicMock` (`publicMockKeywordLabelRandomSeedMask`, three graphs in ten) gives `KeywordHome`'s public overrides, `KeywordHolder`'s module-level configuration, `KeywordApp`'s internal overrides and, two draws in five, `KeywordLocal`'s internal configuration keyword members (`keywordLabeledPublicMock…`). Neither draws `self`, which the fixtures' initializers would take as a parameter that hides the instance they assign to; the unit tests cover it. The scope-declaration oracles compare a case's name with a property's label without backticks, and the in-seam leak's known-issue signatures name the keyword-labeled owner's path as they name `holeOwnerBuilder`.
- **Modules beneath the seam's module** are in `fuzzer-seam-dependencies.md`.

## A run prints the pins it derives

"Check Graph Fuzzer Corpus on Linux" and "Check Graph Fuzzer Corpus for Coverage on Linux" run `.github/scripts/report-graph-fuzzer-pins.sh` after the combine step, whether it passed or failed. It runs `.github/scripts/analyze-graph-fuzzer-pins.py` over the shards' reports and prints its report and its `pins.json` to the job's log and summary, so deriving a change's pins needs no artifact download: the `apply-fuzzer-pins` skill reads a saved copy of that log.

- The step reports and never judges. The combine step is the check; a fault in the analysis is a warning, never a failed job.
- A pull request's run builds the merge with its base, so the step asks GitHub whether that base was an ancestor of the head and states `validForHead` as `true`, `false` or `unknown`. Only `true` is applied.
- The pins block is the last thing the step prints, without the analysis's `observed` values, in lines of 2,000 characters with a digest, so a log read from its end holds it and a log cut short is refused.
- The analysis's self-test ("Check Line Coverage on Linux" runs it) analyzes a recorded run kept compressed in `.github/scripts/fixtures/`: its 22 shard reports, its context, and the combine script and test sources of the commit it built. It expects exactly the section (a) and `pins.json` recorded for that run, so it checks the analysis's rules and never moves when the repository's pins move.
- A shard report line that starts with a new word is added to the analysis's `KNOWN_WORDS` in the change that adds the line. Until then the analysis lists every such line as unparsed and `apply-fuzzer-pins` refuses the run's pins, since its sums may be partial.
- The analysis reads the Swift constants of the commit's own test sources. A pin kept in a new shape (a new file outside `Tests/SafeDIToolFuzzerTests/SafeDIToolGraphFuzzerTests.swift` and `Tests/SafeDIToolTestSupport/GraphFuzzer*.swift`, or a constant built in a way the analysis does not read) is taught to the analysis in the change that adds it, with a second recorded run that holds the new shape.
