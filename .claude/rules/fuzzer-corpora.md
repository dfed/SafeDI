# Graph fuzzer: the multi-module partition and the public mock corpus

- **Multi-module partition.** The oracle also runs every graph that declares no seam and no public mock – each of the base corpus's – split across modules through both multi-module integrations of `executeSafeDIToolMultiModuleTest`, `.moduleInfo` (Bazel's flow: `generate --combined-output --module-info-output --compiler-receives-input-paths-unchanged --module-name --package-name` per module, reading the listed dependencies' `.safedi`; Tuist's differs only by omitting that flag) and `.swiftPackagePlugin` (the SwiftPM plugin's: one CSV per module holding its files and its transitive dependencies' files, the module's own mock-scoped, with the target graph beside it, `scan` while planning and then `generate` with the manifest, one file per root and per mock), without compiling, and requires the same results (`integrationsDiffer`). `GraphFuzzerPartition` (`Tests/SafeDIToolTestSupport/GraphFuzzerMultiModule.swift`) is a pure function of the graph – it draws nothing from the seed, so `corpusFixtureHash` and the accepted-seed pins are unchanged by it, and `smokeAndKnownIssuePartitionHash` and `corpusPartitionHash` pin the partition itself, so a change to it is deliberate (they move with the generator and the known-issue list as well, as the fixture hashes do). The partition projects the fixture's files first (`projectedFiles(of:)`): the helper types `Value` and `Unbuildable<n>`, which the generator declares in `Root0`'s file, move into a file of their own (`S<seed>_Helpers.swift`, named explicitly), since left there every type of `Root0`'s tree that names them, with the files between, would share `Root0`'s component, so `Root0` could never be split from a type of its tree that forwards `lazyValue`; the helper file is visited first, so it is the first component and always lands in `Alpha`. Each file refers to the types it names (instantiated, received, forwarded, aliased, erased to, named by `fulfilledByType:`, the graph's `Value` and protocol types, the extended class), each name is declared in one file, and Tarjan's algorithm over that reference graph, visiting the helper file first and then the files in order, lists each strongly connected component after every component it refers to (the helper file, which refers to nothing, is the first component; a lazy cycle through instantiators is one component, so its types share a module; a root's component follows those of the types its tree names; the roots are the first files, so the types no root's file refers to, directly or through other files, are visited after them and their components follow the roots', and a root need not be in the last module). The components are dealt out, contiguously in that order, to `Alpha`, `Beta`, `Gamma`, `Delta` – as many as `GraphFuzzerHash` of the fixture's text chooses, one to four, so single-module graphs stay in the corpus (1320, 1200, 1270 and 1210 of the 5000 graphs get one to four) – so every reference points into the same or an earlier module. The two integrations combine declarations in different orders: `generate` lists the dependencies' `.safedi` files, read in path order, before the module's own declarations, while the plugin parses every module's files in path order (`Sources/<Module>/…`), the module's own among them; `Delta` sorts before `Gamma`, so in a four-module graph whose `Delta` depends on `Gamma` (otherwise `Gamma`'s files are not in `Delta`'s CSV and its `.safedi` is not read) the plugin combines `Delta`'s own declarations before `Gamma`'s where the module-info integration combines them after – kept deliberately, since a real package's module directories sort arbitrarily against a Bazel build's `.safedi` paths, so those graphs, 535 of the corpus's 5000 (the long run counts them as `delta-depends-on-gamma` on its `partitions` report line), check that nothing SafeDI generates or reports depends on that order (the corpus passing with it is the evidence). A module's `dependencies` are every module whose declarations its `generate` must read, the modules its files refer to and, through them, theirs: what a Bazel user lists in `safedi_compile`'s `deps`, since a `.safedi` holds only its own module's declarations, so a tree reaching a declaration two modules down needs that module listed (`multiModuleTest_throwsErrorForGrandparentDeclaration_whenModuleInfoListsOnlyTheDirectDependency`); the plugin lists the transitive closure's files itself, so both integrations read the same declarations. Every other file keeps its name and content; `Root0`'s loses only the helper declarations; each gets an `import` line per module it refers to before it, and the module, package and helper file names hold no digit but the seed's, so the renamings leave them alone. The property compares module by module in dependency order (`GraphFuzzerMultiModuleOutcome.difference`): a module both generate must have the same generated units, each byte for byte, the combined file's imports in every one of the plugin's files (the plugin's dependency-tree and mock files import what each kind needs, which differs only through `#if`-guarded imports, which no fuzzer graph has), and the same warnings; a module the module-info integration rejects must be rejected with the same diagnostics, in any order, by the plugin. A unit is one generated extension, keyed as the plugin names the file it writes (`<Type>+SafeDI.swift`, `<Type>+SafeDIMock.swift`, `<Type>+SafeDIMockConfiguration.swift` for a `SafeDIMockConfiguration` struct wherever the plugin places it), with the `#if` the mock condition wraps it in, and with every path under the fixture root reduced to `<fixture-directory>/…` (`GraphFuzzerGeneratedModule`): the combined file's joined bodies and the plugin's per-file outputs reduce to the same units, and a `#sourceLocation` directive differs between the integrations only in the fixture root's spelling (the plugin's resolved root against the CSV's path under `--compiler-receives-input-paths-unchanged`). Two differences are the integrations' own. One needs no normalization: the plugin's `scan` plans a dependency-tree file for every root in its CSV, so a consumer writes a file for each dependency's root, which holds a comment and no code, so no unit, and the outcomes compare as written. The other is normalized rather than reported: the plugin adds a build command only for a module whose manifest plans an output, so a module runs `generate` under it only when its own files declare a mock, or its own or its dependencies' files declare a root (`scan` plans every root in the CSV), and a defect its declarations alone reveal (two types fulfilling one protocol, seed 20) is reported where the first module that depends on it generates, or nowhere – the property expects those diagnostics there, requires that the module-info integration generated nothing for a module the plugin skips, and takes an unreported defect as the plugin's design; when the plugin first rejects a module that does not depend on the skipped one, nothing is compared, because `.moduleInfo` stopped at the skipped module and never ran that one. It runs in the smoke batch, which must split graphs into one, two, and three or more modules and reject some split ones, and over the corpus in the long run, whose report counts the graphs at each module count (`partitions`) and notes each differing graph (`multimodule`). Measured: the plain run adds about a quarter of the long run's CPU time (500 seeds: 290 s to 359 s of CPU), so only the graph as generated is split (`GraphFuzzerOracle.multiModuleRenamings`): each of the five renamings would add as much again. The seam and public mock corpora are not partitioned: a graph of theirs that is split across modules is split by roles of its own (`GraphFuzzerModule`), which the partition does not model, and runs through `.moduleInfo` alone.
- **Public mock corpus.** The `generateMockPublic` generator feature draws a graph of its own (`GraphFuzzerPublicMockDraw`, `Tests/SafeDIToolTestSupport/GraphFuzzerPublicMocks.swift`) in place of the base graph, from streams of its own (`publicMockRandomSeedMask`; and `publicMockNamespaceRandomSeedMask`, which declares `Space` in a file of its own that holds no SafeDI marker half the time and `Dock` `package` three times in ten and `public` inside a platform-conditioned `#if` block seven times in twenty (`dockInsidePlatformBlock`), which SafeDI reads exactly, as outside every block, so a holder in an unspelled extension of a `public` `Dock` is `public` and only a `package` `Dock` makes the public tier omit it; and `publicMockUnreadTypeRandomSeedMask`, which gives a leaf's child, three times in twenty, an only-if-available receive of a type no declaration SafeDI reads declares – a `StaticString`, its array or a tuple holding it, or `Unicode.Scalar` – which the public tier takes and the comment of a run without a target graph names: `unreadParameterType`, output `unreadTypeComment`), so the base and seam corpora are drawn as before and every finding is the feature's: a declaring module (`FuzzFeature`, package `shop`) with one to three types declared `generateMock: .public` (`T0`–`T2`) and their children (`T3`–`T5`), and a consumer in the same package (`T7` in `FuzzApp`), in another package (`T8` in `FuzzOther`), or both, each mocked, now and then `.public` itself, receiving or instantiating a leaf – or two leaves that receive a package dependency the other package cannot name (M8.9b) – and now and then building it inside a `Sendable` wrapper's type (`T9`, in graphs whose types are all `Sendable`). Indexed names and `t<index>` labels let the reversals act; each file names its module, and a file that declares no `@Instantiable` type, or a `SafeDIConfiguration.swift` in a directory of its own (so a renaming that prefixes file names keeps the name the tool reads), names itself on its second line (`GraphFuzzerFixture.fileNameMarker`). a holder of what the leaf's tree receives only if available, of a public type in an unspelled extension of `Dock`, a namespace declared `public`, three times in ten `package` (a consumer in another package then holds none, since its declaration could not name one), and in seven of twenty `public` inside a platform-conditioned `#if` block, which SafeDI reads exactly, so only a `package` `Dock` makes the public tier omit the holder, which a consumer instantiates, receives, holds lazily, builds under the `Sendable` wrapper, or declares before or after the leaf, now and then receiving the leaf only if available in turn; `mockConditionalCompilation: nil` in one module; and, on the spelling stream, a value `spelled<index>` in nine of R15's ten spellings (another module's type needs a module below the declaring one, which the draw lacks) as the leaf's forwarded, required or only-if-available property, its non-optional or optional default, its child's default, or a value every consumer forwards, the types it names proven `public` by an initializer no tree reaches (`SpellProver`, as `BadgeHolder` proves `Badge`), so that it reaches the public tier. On the erasure stream a consumer instantiates a leaf through an erasure (G1: M8.19, M8.20b) – a constant `AnyT<index>`, an `ErasedInstantiator`, or, where nothing its tree is handed from outside a `@Sendable` builder keeps it from compiling, a `SendableErasedInstantiator` – the leaf conforming to a protocol its module declares and the eraser a public struct that stores what it erases, so the value differential sees through it. On the hole stream (R7) a `.public` type `T6` instantiates a hole – a type no declaration of its module fulfills, proven `public` by `HoleProver` – on itself or on `HoleHost` beneath an `Instantiator`, a `LazilyInstantiated`, or a `Sendable` wrapper, declared as a class, as `Instantiator<Hole>`, as `any HoleProtocol`, or as an erasure of `HoleFill` (a constant or an `ErasedInstantiator`), now and then after a `package` and a public value its scope struct holds; a hand-written caller in a consumer module calls its public mock with a builder that ignores its scope (`publicMockCallerMarker`, which `GraphFuzzerOracle.addingPublicMockCallers` turns into a generated file the compile checks); and, while `drawsHoleConsumers` is on, consumers reach `T6`, one consumer module per graph declaring the type that fills the hole – reading nothing, a field of the scope struct, a value no field holds (so the caller passes the builder up), or closing a fully lazy cycle back through the fill with `Instantiator<T6>`. Each graph also runs as its known-right path (`GraphFuzzerGenerator.knownRightPublicMockFixture(forSeed:)`: every declaration `public`, every `.public` mock `true`, so every consumer inlines), held in `GraphFuzzerToolRuns.knownRightOutcome`. Section 6's output features are `GraphFuzzerPublicMockOutputFeature`, read from accepted graphs' generated code; the long run reports each count and the graphs each public mock error rejects, and checks the pinned minimum shares (`publicMockCorpusOutputFeatureMinimumShares`, the floor of each share the corpus run observed, for each feature the generated code shows), which the combine job adds up across shards. `publicMockKnownIssues` lists the label order of a `.public` consumer's surfaced parameters (`.mockParameterAndFieldOrder`), one of the base corpus's shapes – which back-edge of a lazy cycle loses its override (`.mockConfigurationFieldPresence`: one field of a configuration struct present under one naming and absent under another), in a consumer that builds a `.public` type's tree inline with a fill that closes a lazy cycle through it – and a value that two public mocks each build, which the stated divergence's exemption does not derive; the order of a module's configurations is not listed, here or in `seamKnownIssues`, since a generated file that differs only in the order of its extensions and public configurations counts as equal, across `#if` blocks of exactly one condition too. - **Modules beneath the seam's module.** In the seam and public mock corpora, `GraphFuzzerSeamDependencyDraw` (`Tests/SafeDIToolTestSupport/GraphFuzzerSeamDependencies.swift`) draws, after every other pass and from streams of its own (`seamRandomSeedMask`, `publicMockRandomSeedMask`), so that a graph without it is the graph it was, the modules beneath a split graph's seam's module that only `.safedi` views carry to its callers under the module-info flow: `FuzzSession` (`GraphFuzzerModule.seamDependency`), which only the seam's module lists, `FuzzCore` (package `core`), which only `FuzzSession` lists, and `FuzzBase` (package `base`), which only `FuzzCore` lists; callers still list the seam's module alone. In three eligible graphs in ten, half the declarations of the seam's module that can move go into `FuzzSession` (`destinations(of:typeNamePrefix:random:)`): a declaration moves only when it spells `public` or `package` on everything another module of its package needs, names only what moves with it, and no caller, configuration, hand-written caller comment, caller's mock, or caller's inline build of a seam or public mock it can construct names or builds it (`Analysis`: `pinnedNames`, `inlineNames`), since under the module-info flow a caller reads no type a view alone carries while the plugin flow reads every module beneath it; a declaration never moves two modules down, since the seam's module builds its seams' and public mocks' trees and lists only `FuzzSession`. Two in ten eligible graphs gain a chain (`chainPercent`): a seam the callers call and no mock builds, or a `.public` leaf a consumer calls and cannot construct (its initializer `internal`, or `package` and reached only from `FuzzOther`), instantiates `ChainLink` (`FuzzSession`), which instantiates `ChainBase` (`FuzzCore`) – seams in the seam corpus, public mocks with an `internal` initializer in the public mock corpus – which instantiates `ChainLeaf` (`FuzzBase`), whose tree receives `ChainToken` only if available; its bottom level reads a module the level above does not list, the shape of cell 5b, whose defect (a nested public mock plan computed from the calling module's filtered map) the drawn chains report as `integrationsDisagree` when its fix is removed, while a chain one module shorter passes with or without it. The inline build and the known-right path list every module a module depends on (`toolOutcome(of:listsTransitiveDependencies:)`), as 2.2.0 asked, since they build what a seam or public mock would have; the flows' comparison ignores a module whose output is imports alone (`integrationComparedBlocks(of:)`); compiles search every module beneath one (`GraphFuzzerModule.transitiveDependencies`, `DifferentialValuePath.moduleNames(dependedOnBy:)`); and the creation stamps' counter is declared in the lowest module, which the rendering that stores every parameter imports in every module above it. `seamDependency` and `seamDependencyChain` are draw features of both corpora (`GraphFuzzerSeamDependencyDraw.drawn(in:)`), each in the smoke batches (seeds 153 and 163, and 98 and 208).
