# Generator design

- **No feature that can crash an accepted tree.** If static analysis cannot rule out that an accepted tree plus ordinary user code crashes, hangs or recurses at runtime because of a feature, the feature is disqualified; removing a trap does not satisfy this. Misuse inside a user's own initializer (reading the `LazilyInstantiated` being created) is the user's: it behaves like the Swift feature it mirrors, never a trap.
- **Build type spellings through `TypeDescription`.** Generated code computes type names and call targets with `TypeDescription` (`asSource`, `asInstantiatedTypeSpelledAsDeclared`), never by joining strings such as a type name, `"."` and a method name, which loses generics, nesting and module qualification.
- **Spell an existential with its `any`.** Swift 6 adopters enable the `ExistentialAny` upcoming feature, under which a protocol spelled as a type without `any` warns, and they build with warnings as errors. `asInstantiatedType` drops `any` (it names the type a scope builds, for maps and comparisons), so code that declares a value of the built type spells `asInstantiatedTypeSpelledAsDeclared`, which keeps `any P` and spells an opaque parameter's `some P` as `any P`. A spelling the person wrote without `any` is copied as written: the warning is then their code's too. `==` reads `any P` and `P` as one type, so where two declarations spell one value apart, a set keeps whichever it met first. A dependency the mocked type receives, directly or through an alias, its mock binds in the mocked type's own spelling, in every form it does not build itself: a promoted dependency's override and binding, a flat `mock()` parameter, an `onlyIfAvailable` override or parameter, and a `LazilyInstantiated` of it (`ScopeGenerator.MockedTypeSpellings`). An alias spells the dependency as its property's type does, where that type is the one `ofType:` names, and never as `ofType:` does: `Service.self` is an expression, which the feature does not flag. A direct receive decides over an alias, whichever the type declares first (`SafeDIToolMockExistentialAnyTests`). Every other value – one the mocked type does not receive, and a seam's pass-through – takes the most explicit of its receivers' spellings over all its forms (`ValueSpellings`, `TypeDescription.mostExplicitSpelling(among:)`), an alias's receive spelled as its property is, so a receive by value and a `LazilyInstantiated` of one dependency are spelled one way: every set of received properties keeps the more explicit spelling on each merge (`insertKeepingMostExplicitSpelling(_:)`), so neither a walk's order nor a set's decides (`SafeDIToolMockExistentialAnyTests`, `SafeDIToolSeamExistentialSpellingTests`). One deliberate gap, commented at its sites: the override closure of a type the mock builds, and the bindings of its arguments in that type's builder function, take that type's initializer's parameters as declared (`MockLowering.ConstantNode.builderClosureType`, `emitReceiverBindings`), since an argument reads the nearest declaration of its label, which a type between it and the mock root can spell its own way. Every compile check and every graph fuzzer compile enables the feature, and a generated spelling that drops an `any` the fixture spells fails its test or its graph (`test-infrastructure.md`).
- **No hand-kept list of system frameworks.** Where logic or wording must tell system modules from the user's, use a signal SafeDI has (the modules it read, or was given module info for), or drop the feature. A curated list is always incomplete and goes stale with every SDK.
- **Runtime speed of generated code over compile time.** Generated trees run in adopters' apps; compile time costs only developers, and release compile time matters least. Never make a tree slower in order to compile faster (heap-allocated payloads) without a runtime measurement beside the compile numbers, and rank compile-cost work by debug builds. A small constant cost per tree build, such as one allocation per seam, is fine: trees are not built in tight loops. Seams alone never inline local functions (`LocalFunctionInlining`).
- **A cost every build pays needs the case's frequency.** More `generate` time is paid by every user on every build; a rare compile error with a documented fix is paid once by the few who hit it. Measure how often the case occurs in a real app before trading API, capability or build time for it, and keep it documented when it is rare, fails at compile time (never with a wrong value) and has an easy fix. Where SafeDI cannot see something (isolation, another module's sources), a documented opt-in or spelling comes before generator work. Erasure (`fulfilledByType:`, `erasedToConcreteExistential:`, `ErasedInstantiator`) is first-class: a real app's tree that does not use it yet is no evidence a shape is rare.
- **Measure the compile cost of a change to generated code.** Before review of a change that alters what seams, public mocks or builders emit, run `Scripts/compile-time-check.py BASE_TOOL HEAD_TOOL BUILD DIRECTORY --base-build BASE_BUILD` with tools built from the change and from the commit it is based on: it generates wide graphs (40 and 200 screens) with each tool and fails when a module's generated lines grow by a quarter or `swiftc`'s CPU time on it by half. A change that grows either on purpose says so, with the table, in its pull request. CI times no compile: "Check Generate Time on Linux" runs the script's self-test and its `--lines` mode, which reports a module's generated lines more than 5% from `Scripts/compile-time-baseline.txt` (a warning, `--warn-only`, until the generator's output settles; then a failure). A change that alters generated output rewrites the file with `--write-baseline` from its own tool, in a commit of its own, and says why in a comment above each moved number.
- **No function the compiler takes long over.** "Check Function Compile Time on Linux" (`Scripts/function-compile-time-check.py`) fails when one function of SafeDICore takes over 10 s in the optimizer or 5 s in the type checker in a release build: the optimizer's cost grows faster than a function's length. Split the function (a block of a long initializer into a private static function, a long joined expression into sequential appends); never turn the optimizer off for it, since the generator's hot path runs through such code. `Scripts/function-compile-time-waivers.txt` lists the functions known to be over, each with a ceiling and what removes it; never add a line for new code.
- **`generate` time grows with the code it generates.** A step that runs once per place, fill, builder or scope must not build or scan a collection holding every place's, fill's or name's entries: build it once and share it (`GenerationWork.Shared`), or ask each set in turn (`NamesConsultedInTurn`) instead of joining them. Each such step counts its work where each taker takes what it consults (`GenerationWork.taking(_:by:)`): a plain collection counts every element, so rebuilding or scanning it for each taker counts that work whatever the step reports. `SafeDIToolSeamGenerationWorkTests` fails when a counted step's work grows more than 1.1 times as fast as the paths to the places of shape E: its places in the seam's own tree, in the fills of a seam it calls at each path, and there with every path opening types of its own, so that the names grow with the paths. A new step of that kind is counted there too. The observer is task-local, and every task that emits a scope's code inherits it, so it sees every step; `identifierSafeNames` counts only for a seam's signature. Two sites still do such work, uncounted: a call walks the enums of the inner seams on each of its places' routes, once for each place (`InnerScopeReaders.labelsSomeInnerRouteLacks(of:)`), so its work grows with its places times the inner seams' places; and a call nested in a fill of another call copies the enclosing calls' fill map and fill names.
- **Benchmarks are lifelike.** A synthetic module takes its shape from a real app's measured statistics: module count and sizes, the share of files with `#if` and mock text, where `#SafeDIConfiguration` lives, received-chain depth and fan-out. Never copy a private app's source into the repository, a fixture or the fuzzer's seeds; reproduce its shape with invented names.
- **Generated code captures only what it reads.** A generated closure, `@Sendable` or not, never captures a value nothing in it reads; that failure is SafeDI's (`seam-and-mock-contract.md`, "No retain cycles"). A non-`Sendable` value the user's own declarations capture is the user's, left to the compiler.
- **Parallel generator work reads only `Sendable` values.** No `@unchecked Sendable`, `nonisolated(unsafe)`, or lock-wrapped sharing of a mutable reference type in the generator: build immutable value snapshots (structs of what each task needs, keyed by index) once, serially, and keep `Scope` and the other classes actor-isolated or task-local. If that needs a type that does too much split in two, split it. `SourceRuleTests` fails on either under `Sources` and `Plugins` (`uncheckedConcurrency`, `source-rules.md`), and only a waiver citing Dan's OK for that one site admits one.
- **Text transforms at every node go over bytes.** A tree has a node per path, so a transform of generated text that runs at every node (re-indenting a subtree, spelling an override path) goes over UTF-8 bytes through `GeneratedCodeText` rather than splitting into `Character`s or rewriting through Foundation, and returns the same bytes as the expression it replaces, which `GeneratedCodeTextTests` checks on every string of a few tokens; where it deliberately differs, because the old expression wrote code that did not compile, a test there spells the case out.
- **Share work by construction.** Work that several places, types or roots would repeat belongs to an object that owns its result: a view computed once per type or per context and handed to every taker (as `GenerationWork.Shared` hands a collection built once), or a node of the tree that holds its own state. It is never a skip flag or a memo table that a walk consults on its way: such a walk does the right work only when every path through it remembers to ask, its result depends on which caller arrived first, and the unshared path stays in the tree beside the shared one. Each such object states what memory it holds and for how long, in a comment at its declaration, since an object that outlives its last taker costs every build. Four deliberate exceptions, each stated at its site: a cache read only to word an error report; a set of the nodes one building walk has already seen, which dies with that walk; a seam walk whose result depends on the path that reached it, so that no one result can be owned (`receivers(in:)`'s set of projected frames, `ReceiversVisit`); and a pass over a whole tree that looks for cycles.
- **One driver builds each layer once.** `DependencyTreeGenerator.generate(_:)` is the one call that generates a module: it validates and builds the trees of the roots and seams once, which their code, their warnings and the DOT graph read, and then the mocks, and returns all four. No stored property of an actor is a memo whose computation awaits: once a memo filled by check-then-set awaits between the two, two callers both compute and the later wins, and a stored in-flight task is banned (below). A value computed once is a local of the driver, or of the one entry-point call that needs it (`fileHeaders(for:)` reads the module's own files at most once, `requirements(of:)` builds each view's mock scope map once, for every type `query needs` asks about, and keeps nothing after it returns), handed down as a parameter; a module whose public mocks a run calls computes every plan the run asks of it in one call (`publicMockPlans(ofOwnTypes:)`), which the caller keeps in `PublicMockPlans`. `SourceRuleTests`' `ActorStateRuleCheck` (`source-rules.md`) cannot see an `async` function that calls a synchronous one that sets a property, so `SafeDIToolGenerationLayerTests` counts each layer (`GenerationLayerObservation`): each declaration map's seam signatures and each root's tree once per run, the access proof of the run's own declarations at most once per run (the public mock context and the module's own seam signatures share it through `ownAccessProof()`, built when first read, so a module with neither builds none), and each module's mock scopes once for its mocks, once for the plans of its own public mocks where it compares them with its callers' view (a run that writes a `.safedi` stores each plan from the mock root it generated the mock from), and once for every plan a calling run computes of it, which a run under module info reads from the module's `.safedi` instead (`SafeDIToolGenerationLayerTests`' `generate_buildsNoOtherModulesMockScopes_whenModuleInfosCarryPublicMockPlans`).
- **A generator keeps finished code, never a finished task.** A Swift task keeps the memory its async frames took until the task is released, so a cache of a scope's code holds the code's plan once it is generated and drops the task (`ScopeGenerator.generateCode`); a scope's code starts on a task created when the scope above asks for it, and no scope starts its code before then. A production root's body, and a seam's root body in its own module where the module plans no more trees than that bound (each tree is planned on a task of its own, so more trees already fill the processors), asks for its children's code at once, a task each with at most `ConcurrentChildCode.maximumChildrenAtOnce` in flight (a measured constant, not the processor count, since each plan in flight holds its frames), and writes it in the order of its children, never in the order the tasks finish (`ScopeGenerator.appendConcurrentChildCode(to:codeGeneration:leadingMemberWhitespace:fillPlaceBindings:)`); every body beneath, and a mock's, asks one child after another, since planning every body's children at once cost more processor time than it saved. Every task planning a scope holds `generatePropertyCode`'s async frame and those of the bodies it awaits, so the work those functions do around an `await` that is not itself awaited goes in a function of its own marked `@inline(never)`, and a body awaits each child in its own frame, with no function between. A function's initial async context size is in its async function pointer (symbol suffix `Tu`). `SafeDIToolCodeTaskTests` counts the code tasks still held once a tree's code is generated (`HeldCodeTasks`) and the children a body plans at once (`ConcurrentChildCode`); neither is a `GenerationWork` step, whose every step must grow with a seam's paths.
- **A shared generator is built as each place would build it.** `Scope.createScopeGenerator` reuses a generator between places whose key and read log match (`construction-memo.md`). A new input to a place's build, a new read of the context above it, or a new field a generator stores goes into the memo's key, its log, or its exclusions, and onto that file's list, in the same change; a new argument of `generatePropertyCode` goes into `UnavailablePropertiesCacheKey`.

## Mock generation flow

Mock generation follows this pipeline:

1. **`generateMockCode`** builds the mock scope map via `createMockTypeDescriptionToScopeMapping` (includes ALL types, not just reachable from roots)
2. For each type with `generateMock: true`, **`createMockRootScopeGenerator`** promotes `@Received` dependencies to root-level children (except those `mockCanBuild` rejects and those one of the mocked type's own aliases provides), in the order the mock's tree first receives them (`inOrderTheMockTreeFirstReceives`), and validates for cycles
3. **`ScopeGenerator.lowerMockRoot(context:)`** builds the mock: `treeNames(of:readsFills:)` walks the tree once, recording each property node (`MockTreeNames.propertyNodes`, which `query needs`, promotion and the public mock plan read); `mockRootParameters(instantiable:mockDefaults:treeNames:)` classifies the flat parameters, through the one static classification over `MockRootParameterInputs` (`mockRootParameters(instantiable:mockDefaults:treeNames:inputs:)`, and `lowerRootSignature(of:flatParameterMockDefaults:tree:inputs:)` beside it), which the generator fills from itself (`mockRootParameterInputs(of:)`); `lowerMockRootWithTree(of:context:)` writes `SafeDIOverrides`, `mock()` and its body. Where a test sets `MockTreeNamesObservation.observer`, `lowerMockRoot(context:worldRoot:promotion:)` compares the tree's names, read without fills, with those the root's per-type world answers (`MockTreeNamesFromWorld`, which visits each declaration once per inside-`@Sendable` state, with a visited set on a cycle, and refuses a root with a twin on a cycle, a `Sendable` wrapper on a cycle, a dependency a declaration on a cycle may hide that its bounds do not settle, a mock that passes `nil` to a receive a required one pins (`MockReceivesPassedNil`, which `createMockRootScopeGenerator` reports with what its root binds through `MockTreeNamesObservation.recordsMockRootPromotion`), a call, a fill, a hole or a public mock, and a received property the root binds in no spelling (`spelling`)), and, where the world answers, compares the generator's `MockRootParameterInputs` and its children in build order with the world's root row, its received properties spelled as the root binds them (`rootInputs(of:spelledAs:)`), and the generator's `mock()` signature with the one `lowerRootSignature(of:flatParameterMockDefaults:tree:inputs:)` lowers from the world's names and inputs, field by field; `mock()` still reads the tree's, and `SAFEDI_MOCK_TREE_NAMES_REPORT` names a file a sweep of a suite appends each root's outcome to (`MockTreeNamesChecks`)
4. Only where a test observes node records, `lowerMockRootWithTree` makes an internal mock root's too (`ScopeGenerator.nodeRecordsMockStatements(of:worldRoot:bindsOnlyNodes:sendableConfigurationTypeNames:rootNames:outerDeclarations:)`) and, where the test sets `NodeRecordsObservation.laysOutMockRoots`, lays its nodes out from them: each function takes its node's overrides as `safeDIOverrides` (`SafeDIToolNodeRecordsMockRootTests`), and a node whose construction takes a default-valued parameter is built in a function that reads the field from its configuration, but for a configuration of the `Sendable` form, whose root keeps the walk (`NodeRecords+MockDefaultValuedParameter.swift`). A function on a cycle of the root's world, or between two places of one configuration that a cycle joins, also takes the places entered above it as `__safeDI_entered`, a value of a struct `mock()` declares, and reads its configuration of the place a function above it entered where there is one, as the walk reads the override of the nearest place on the path (`NodeRecords+MockCycle.swift`, `SafeDIToolNodeRecordsMockCycleTests`).

The production code path (`generatePropertyCode` with `.dependencyTree`) and mock path (`.mock`) share the same `ScopeGenerator` but diverge at `generatePropertyCode`. Mock fields (`mockInitializer`, `mockReturnType`, `customMockName`) are only accessed in mock code paths — never in production paths.

## Determinism in the generator

`CLAUDE.md`'s "Determinism" states the principle; these are the places in the generator where it has gone wrong.

- `Property.<` sort uses type as tiebreaker (not just label) for stable ordering.
- `typeDescriptionToFulfillingInstantiableMap` is a dictionary — iterating `.values` has non-deterministic order. Any code that reduces, sorts, or builds state from `.values` must produce the same result regardless of iteration order. CI runs the suite 5 times on Linux, each in a process of its own, specifically to catch non-determinism: once in "Build and Test on Linux" and four more in the "Repeat Tests on Linux (pass N)" jobs, which run the same bundle without compile verification.
- A loop over a `Set<Scope>` may build state, but anything it reports — an error, a match — must be chosen by a deterministic key (as `createTypeDescriptionToScopeMapping` does for `@Forwarded` errors), not by which element the loop reached first. `validatePropertiesAreFulfillable` and the mock roots in `generateMockCode` visit trees in type order, but which errors are reported, and in what order, is decided by source location (next bullet), never by that visiting order.
- **Diagnostics are chosen by source location, never by name order.** Every root (production, `generateMock` type, mock root, mock root's child trees) reports the first error its own walk finds, and `DependencyTreeGeneratorError.reportingAll(of:)` joins them in source order (`SourceDiagnostic.joiningInSourceOrder`), so renaming a type never changes which error appears or where. Two rules keep that true: a memo shared across roots (`ChildrenRequiringEachOtherValidation.validatedScopes`, `walkedAliasFulfillingProperties`) keeps only walks that completed — an entry from a walk that threw must be dropped, or a later root would skip the work and the reported set would depend on root order; and where one of several candidates must be picked (which promoted child a mock root validates first, which received property names a sibling, which reader a warning names), pick by declaration location or declaration order (`inOrderTheMockTreeFirstReceives` orders a mock root's promoted children by where its tree first receives them, for generation and validation alike), not by label or type-name order. The rename-invariance fuzzer oracle checks this class end to end.
