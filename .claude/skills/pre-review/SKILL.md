# Run what a branch owes before review

`pre-review.py`, beside this file, runs what a reviewer would otherwise find a round later, and prints a block that names the head it ran on. Run it from the repository root, in the background, on the head you are about to hand back; `S` below is `.claude/skills/pre-review/pre-review.py`. Its `--help` is the full contract.

1. Commit everything and push the head under a branch name. `python3 -I S [BASE]` then runs `./CLI/lint.sh --check` and the `verify-touched` skill on this machine, in a worktree of its own at that head (kept under the caches directory, so its build stays warm and you may keep working in the checkout; a run removes the worktrees of checkouts whose folders are gone), and, when the change touches the sources, the fuzzer, or the workflows and scripts that run it, dispatches `verify.yml` with `pins=true` and `base=` the commit it measures from, and waits for the run. `BASE` is what the branch is measured from (default `origin/main`); in a stack, name the branch below, never one that holds this head. The corpora never run on this machine. On a machine that queues heavy work, pass `--runner COMMAND` or set `SAFEDI_VERIFY_RUNNER`: lint and the suites both run behind it. The block does not cover unit-test coverage of the changed lines: "Check Agent Skill Scripts on Linux" is that gate, and `--coverage` adds `Scripts/changed-line-coverage.sh` as a step when you want it before CI.
2. With `--no-wait` it returns as soon as the run is dispatched; `python3 -I S --report` prints the block again with the run's result, and asks GitHub for the overlap list again only when the run's state changed or the list is five minutes old (one minute when it was not checked or left a branch unread), so a waiter may call it each minute. `--pins-run ID` takes a Verify run already dispatched with pins on this head. On a machine without `gh`, dispatch the run another way and pass its id on a machine that has it. A machine with one waiter for every GitHub run names it in `SAFEDI_PRE_REVIEW_WAIT`; the script gives it the run's id in place of asking GitHub each minute.
3. Put the block in the hand-back, whole, and answer each list above its `result:` line: for each call that sorts or picks by a label, a name or a position, why that order is allowed ("What may follow names" in `CLAUDE.md`); for each added test of a choice or an order, how many candidates it has (twenty or more, or a permutation of six); for each run of changed lines no corpus graph executed, its disposition ("Coverage of a change" in `.claude/rules/fuzzer-corpora.md`); for each file the change shares with another open pull request or lane branch, that this branch is stacked on that one, or why it need not be (two changes that each owe a pins run share the fuzzer's pins: the pull requests that do are listed too, and the lane branches counted). An instruction file the change edits that the block lists as at or near its limit is trimmed or split before review, not answered. The first list sees calls only: an order inherited from a loop over a list already in label order is still yours to look for.
4. When the work has a brief with a shape matrix, add `--matrix BRIEF --hand-back DRAFT`: the block then lists each cell (a table row whose first column is a number such as `6.11`) that the draft does not account for. Name the cell, or a range such as `6.1–6.4`, at the start of a line, a list item or a clause after a semicolon, or after the word "cell", and right after it its test in backticks, its seed, or `unchanged`, `stopped` or `not done`.

Before every push that starts CI, run `python3 -I S --pre-push [BASE]` first: lint, then side by side the changed-line coverage script over the whole suite (generated code not compiled), with every line the change did not touch that a test ran on `BASE` and none runs now (the base is measured once per machine and kept; each such line fails the check, and since CI also counts the other platform, push over one only by saying in the pull request why that platform executes it), and CI's release build of the tool, which fails on a compiler warning under `Sources/` or `Plugins/`. It takes minutes, asks GitHub nothing, pushes nothing and starts no run, and prints a "Pre-push block" that names the head and the toolchain that compiled it. A pass is of that toolchain only: CI builds with Swift 6.2, Xcode 26 and Swift 6.3, so code a newer compiler accepts can still fail there. It is not the pre-review block. While writing a change, `python3 -I S --changed-lines [BASE]` runs the coverage script alone in the same worktree, so both use one warm build.

A block is of one head. Reviewing a hand-back, compare the block's `head:` with the commit under review and run `--report` on that commit when in doubt: a hand-back with no block, a block of another head, or one that says `NOT READY` goes back before it is read.

After changing the script, run `python3 -I S --self-test`. "Check Agent Skill Scripts on Linux" runs the same.
