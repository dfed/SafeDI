### Harness (`spike/per-type-seam/`)

- `common/Harness.swift`: every fixture type is a `public final class` holding a `Tracker`, which numbers the instances of its type, logs what each instance received (`Live#2(cache: Cache#2)`), and keeps a live count per type. `Registry.printAlive` prints every type with a live instance.
- `common/typegen.py` writes the fixture types (`*.swift.txt`, regenerated by each `run.sh`).
- `common/build.zsh VARIANT Onone|O [flags]` runs `SafeDITool generate` per module exactly as `Scripts/multi-module-repro.sh` does (for `tool` modules), or takes hand-written generated code (`hand` modules), and compiles every module with the repro's `swiftc` line plus `-warnings-as-errors` and `-Onone`/`-O`, then links and runs. Output goes to `~/.cache/per-type-seam-spike`, outside the checkout.
- `common/run-fixture.zsh` builds each variant at `-Onone` and `-O`, stores the trace in `<fixture>/results/<variant>-<opt>.txt` (or the compiler's or tool's error in `.error.txt`), compares each byte for byte with inline's `-Onone` trace, and builds every (d) once more with `-enable-library-evolution -emit-module-interface -verify-emitted-module-interface` (SafeDI and the fixture modules; the executable is left out, since top-level code has no interface).
- Each trace ends with the frees: what is alive after everything is dropped, and after holding one value (a step, a retried checkout) and dropping the rest. A trace that equals inline's byte for byte means values **and** frees equal inline's.
- The calling module's code under the leak fix is hand-written once per fixture (and candidate) and shared by (c) and (d), so "callers compile unchanged" is checked by construction: (c) and (d) compile the same `App` sources, including `Callers.swift`, which calls the readable initializer (`Home { … }`, `Home(apiBuilder: …)`).
- `run-all.sh` reruns everything.

## What worked and what broke (so far)

- Worked: everything a person writes stays as the leak fix leaves it while the body becomes one function per type, in every fixture so far.
- Broke: candidate A, as soon as a value bound between the root and a reopened level is read below it (`F2/mark`).
- The brief's word "reopening property" is not defined for `next`, where inline closes the cycle at `Screen.stepBuilder`, not at `next`; I read it as the property whose type is already on the path (`Step.next` reopens `Screen`), which is how the brief's F2 sketch uses it.

## Rules needed so far

- **Key**: the concrete type (F1's `Avatar` at two places, F6's `T` and `Screen` at a plain and a `@Sendable` place).
- **Placement**: before the first statement that reaches it, in the initializer's body; a function a loop reaches is declared before the functions that call it, and Swift's local functions allow the mutual recursion (F2).
- **Parameters**: the type's level struct, always first; a forwarded value (`cart` in F4); a declaration the same at every call is captured (the root struct in F2 (d) A).
- **Which struct**: the type's own level struct in its family; for a type built in both families with a member that reopens it, also the `@Sendable` family's struct of the type (F6 (ii)).
- **Loop re-entry**: the call at the reopening property hands the reopened type's function the struct its own member returns (candidate B). Under A it can only take the root member's, which loses values (F2 `mark`).
