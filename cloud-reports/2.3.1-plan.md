## 1. Summary

- **Shape.** Five stages, stacked on top of the 2.3.0 stack the moment its seven slices are complete (2.3.1-STACKS-ON-2.3.0). Stage 0 starts now and touches no `Sources/`. Then: the base stack (scripted split, the filed issues, the reserved-name diagnostic); the output-neutral emitter rewrite (byte-identical); the per-type reshape (output changes); W1 with D1's value; the release checks.
- **The one design idea that makes the sequencing cheap.** The new emitter builds a function graph whose functions are keyed. With the key set to *the path*, every function has one place and the output is today's per-path text, byte for byte. That is the output-neutral rewrite. With the key set to *the type* (type, provided form, and how each read resolves), the same graph shares functions. That is the reshape. The per-type production spike observed exactly this: "a tree in which every key has one place is byte-identical, by construction". So the reshape is a key change plus its rules, and the per-path key stays available as a test-only differential oracle for one release, instead of a second emitter kept alive.
- **Size.** About 120–180 lane-hours in all, of which 44–64 are on the critical path (26–38 if slice 1's observed 0.6 factor holds). Five CI cycles, one per stack. With three to four lanes running, that is roughly 4–7 working days of wall clock from the moment the 2.3.0 stack is complete. This is longer than the lead's "3–5 days of lane time" (2.3.1-STACKS-ON-2.3.0); section 7 says where the difference is.
- **What lands.** The generator at about 14,000–15,500 code lines (the clean-slate estimate for the planned steps), #646 fixed, #718–#720 fixed, W1, W4, the two-type loop, the self-loop and D1's value accepted, V3 a correct value, large seams linear, and generated code faster than 2.2.0 on the benchmark.

## 3. The emitter design in brief

The design note (N6) writes this out in full before E1 starts. These points are settled by spikes and rulings, and the note does not reopen them.

1. **One function graph for production, seams and mocks.** Nodes are builder functions; an edge is a call. Each node has a key, a placement (the lowest body every call passes through, before the first statement that reaches a call), and parameters in a fixed order: the level struct for each hole family it leads to, the values its place forwards, then each received value that is not the same declaration at every call. A value the same at every call is captured. Mutual recursion needs nothing more, because Swift local functions in one block may call one another.
2. **Keys.** Path mode: the key includes the path, so every node has one place, and the output is today's. Type mode: the concrete type, the provided form, and for each read, the declaration it resolves to, `nil`, or "passed". The mock key adds "reads a configuration". One `BuilderKey` type serves production and mocks (simplification C4).
3. **One argument source** (C2): captured, `nil`, parameter, or lazy instance, with one spelling function. One construction-call function and one wrapper-binding function (B2, B3) serve every site.
4. **Names** come from the body-wide `GeneratedNameAllocator`: the first-reached place's label stem, claimed, never a type name. This keeps check 2's shape-stability rule (no member, `_Values` or function name contains a type name) and needs no nested-type spelling. Generated-only names, so this is the plan's call, not a card.
5. **Order is deterministic.** Functions are declared in first-reach order from the tree. Siblings keep today's order, with W1 gap 1's single exception.
6. **Seams:** a loop re-entry hands the reopened type's function the struct its own member returns (candidate B). One function per family where a type is built in both (spike 2's d2). A type with no properties that forwards nothing is built in place.
7. **Mocks:** configuration is a parameter, not a capture; nested configurations live in the enum box (`__safeDI_Nested` behind an indirect enum, same field name, type and access). Public mocks keep their signature, tiers, guard and callers' view. Never shared: whatever the mock-overrides spike's rule 3 lists until a draw shows the shared form is right for it.
8. **New files.** The new emitter is written as small files from the start (NO-STANDALONE-FILE-SPLIT); the old emitter's code is deleted in the PR that replaces it.

## 9. Decisions

**For Dan:**

1. **What "faster than 2.2.0" is measured on.** Recommendation: every shape in N1 that 2.2.0 can build, with median of five, generated-module compile at `-O` and `-Onone`, runtime per value, and `generate` instructions, each at or under 2.2.0; seams and public mocks at or under the 2.3.0 head. The ruling names runtime and compile time on "the lifelike benchmark"; N1 is my proposal for what that benchmark contains, and #646 puts `generate` time in by the issues rule.
2. **Whether about 12,000 lines is a 2.3.1 goal.** The planned steps land near 14,000–15,500. Reaching about 12,000 needs one tree model shared by validation, seams and mocks, which is on no plan and touches which error is reported. Recommendation: not in 2.3.1; reassess after 2.3.1 with the split files in hand.
3. **The `@Sendable` family sentence** (spike 2, question 3): one function per family where a type is built in both (d2), which mirrors the builder struct's families one to one. Recommendation: d2. Needed before R2a. It changes nothing a person writes and keeps seams and production alike, so the lead may judge it decided under standing rule 1.

**For the lead:**

4. **The path key as the oracle** (accepted by the lead, recorded as an amendment). EMITTER-REWRITE-SEQUENCING says "today's emitter as oracle". This plan deletes today's emitter as each byte-identical PR replaces it, because the zero-diff gate already proves it equal, and keeps the path key as the reshape's differential for one release (removed in 2.4.0). Same safety, and one emitter, not two, during the reshape.
5. **"The two shapes that depend on a name or a label"**: the lead reads them as D16 and D5 (not a recorded ruling). R2a verifies each on main with the rename-invariance oracle and gates on its seeds (section 4).
6. **E6 is conditional** (accepted). If N1 shows `generate` faster than 2.2.0 outside emission everywhere, E6 is dropped.

## 10. What would make this wrong

- **N2 fails.** Public mocks then keep per-path bodies, R3 shrinks to the cycle parameter, and #646's mock variant may miss the ship bar. That would come back to Dan as an exception or a later 2.3.x.
- **Byte-identical turns out to be hard in one corner** (E4's mock body is the most likely). No byte diff ships in stack B on a lane's own decision: the PR keeps today's code for that corner, still covered, lists it under Found and not fixed with R3 as its plan, or gets the lead's sign-off for a reviewed diff (design note section 8). Never for E1–E3 or E5.
- **The reshape is slower to compile on some real shape.** Spike 2's L shape and the per-type production spike say no, but April's per-type attempt was compile-neutral and was removed. N1 runs before stack C lands.
- **A late 2.3.0 fix** restacks everything; the split script and stacked lanes keep that to a rerun.
