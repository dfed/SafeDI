## 1. What the rewrite replaces and what it keeps

**Replaced:** the text assembly in `generatePropertyCode` (SG:5042–5399) and its helpers (`instantiatorDeclaration`, `instantiatorExpression`, `loopRebindingDeclaration`, the constant/instantiator/lazy branches, the alias text), the per-body name assignment (`builderFunctionNames(for:enclosingFunctionNames:)` SG:4919–4955, `identifierSafeNames` SG:8757–8785), the mock body emitter (`generateMockBodyBindings`, `generateInstantiatorBinding`, the constant-node builder branch, loop member emission), and the seam body's place, fill and level-function text.

**Kept, unchanged in behavior:** scope building (`Scope.createScopeGenerator`), every validation walk, `ScopeGenerator.init`'s bottom-up facts (moved into a facts value by E1), sibling order (`computeOrderedPropertyToGenerateIndices` SG:3639–3732 and `siblingGraph` SG:3759–3892), availability (`unavailableProperties(isGeneratedBefore:…)` SG:4316, `propertiesGeneratedLater(thanChildAt:)` SG:4209), cycle parameters (`foundCycleParameters`, `cycleClosedOnDeclarations`), `ReceivedBuilderLoops`, `buildsInSendableFunction` (SG:176–197), `computeCycleEdges`, the mock promotion and parameter tree, signatures, guards, `.safedi` files and diagnostics. The emitter reads these; it does not recompute them.

That split is the reason the rewrite can be byte-identical, once one correction is made: today several output decisions are taken during emission, some from emitted text. Section 1.1 lists them; E1 moves each into facts before any spelling changes, so that afterwards every decision that changes output is made by kept code and the new emitter only spells it.

## 2. The function graph

The emitter works in two steps per generated body (a root's `init()`, a seam initializer, a `mock()`):

1. **Plan.** Walk the `ScopeGenerator` tree once, in the order generation walks it today (ordered children, depth first), and build a `BuilderFunctionGraph`: a node per builder function, a binding per `let`, and the order of statements per body.
2. **Spell.** Render the plan to text with one spelling function per statement kind.

### 2.1 Nodes

A `BuilderNode` is one local function SafeDI writes:

| Field | Meaning | Today's source |
|---|---|---|
| `key: BuilderKey` | What makes two places the same function (section 3) | none (one function per place) |
| `built: ConstructionTarget` | `.initializer(Concrete)`, `.instantiate(Concrete)`, `.mock(Concrete, name)`, `.fill(…)` | `instantiationDeclaration` SG:5124–5132 |
| `returnType` | The concrete type returned | the three branches' `-> Concrete` |
| `isSendable` | Writes `@Sendable ` | Path mode: `buildsInSendableFunction` (four spellings today, SG:5205, 5308, 5349) and the `_received` rule (SG:5247). Type mode: computed after placement (section 4) |
| `parameters: [BuilderParameter]` | In order: level structs (seams, mocks), forwarded properties sorted as today (SG:5162), cycle parameters in `inOrderTheBodyFirstReceives` order, then (type key only) passed reads | `initializerFunctionParameters` (four calls today) |
| `body: [Statement]` | Rebindings, guard lines, child bindings, the return | `generateProperties` SG:4538–4706 |
| `placement` | The body the function is declared in, and the statement it precedes | implicit today: the binding that uses it |
| `name` | Claimed from the body's allocator (section 5) | `functionName(toBuild:)` and the renames |

### 2.2 Statements

Every line a body writes is one of these, each with one spelling function:

- `.function(BuilderNode)`: the `func` block. The templates write a trailing blank line, but see 2.2.1.
- `.binding(label, annotation?, Expression, lineEnd?)`: `let x[: T] = …`, with an optional trailing comment (`constructionLineEnd`, SG:5145).
- `.alias(label, AliasValue, reference)`: today's `aliasDeclaration` plus `referencingDeclaration` (the `#sourceLocation` or `// Declared at` form, SG:5950–5965).
- `.rebinding(label, annotation?, Expression)`: a loop member's rebinding, annotated by `instantiatorDeclaration`'s rule (SG:4768–4772, 4808–4813).
- `.guardLine(…, lineEnd?)` (the seam call's comment, SG:5151), `.valuesBinding(…)`: seam and mock only.
- `.return(Expression, isImplicit)`: instantiator and lazy functions write a bare expression when the function's statement array is empty, counted with guard lines included (SG:5216, 5326); constants filter empty strings and always write `return` (SG:5358, 5379); `_received` has its own rule (SG:5250). Path mode carries the three rules by name.
- The root's `self.init(argumentList)`.

#### 2.2.1 Whitespace

The private `generateCode` prefixes each line with the child's leading whitespace and splits on `"\n"` with empty lines omitted (SG:2135–2141), and every child is generated with non-empty leading whitespace, so the templates' blank lines after a function (SG:5217–5219, 5251–5253, 5380–5382) and a childless function's empty body line never reach output (expected output: `Tests/SafeDIToolDependencyTreeTests/SafeDIToolCodeGenerationTests.swift:936–940`). The spelling step does the same: indent per nesting level and drop empty lines, except at the sites that do not split today, which keep their empty lines: `prepareFillCode`'s `leadingMemberWhitespace: ""` (SG:3578–3582), `indented`, `inlinedFill` and the fill body (SG:4714, 4741, 5676). E2's gate catches a missed site.

An `Expression` is a construction call (`ConstructionTarget` plus arguments), a wrapper (`Instantiator`, `ErasedInstantiator`, `SendableInstantiator`, `LazilyInstantiated`, the `Sendable` lazy wrapper) around a function reference or a closure calling one, an erasure wrap, or a reference. This replaces three hand-spelled templates (SG:4777–4803, 5284–5298, 5389–5395) with one spelling of each part.

### 2.3 Argument sources (simplification C2)

Every argument SafeDI passes comes from one enum, spelled in one function:

```
enum ArgumentSource {
	case binding(label), lazyInstance(label), nil, parameter(label)
	case forwardedSpread(label, isOnly, spreadName)   // "$0", or a fill's forwarded parameter name (SG:5164)
	case builderArgument(…), holeArgument(…)          // seam calls (builderCallArguments, holeArgumentValuesByLabel: SG:5098, 5135–5137)
	case autoclosureCall(label)                       // a seam alias's fulfillingExpression (SG:5425)
	case configurationField(path, label)              // a mock's field() and SafeDIMockConfiguration().<label> arguments
	case passedWrapper(label)                         // type mode: the wrapper, read `.instance` at the first read (section 4)

```

A rebinding's cycle arguments (`label: label`, SG:5185) are `.binding`. Today's initializer and cycle sources map onto it one to one: `createInitializerArgumentList` (`Models/Initializer.swift:263–282`: `label: nil`, `label: inner.instance`, `label: inner`), `cycleParameterArguments` (SG:4506–4521), `forwardedArguments(of:spreading:)` (SG:4746–4755: `label: $0` or `label: $0.label`), and the mock's `mockCycleParameterArguments` (SG:9837) and dependency arguments. In path mode each source is today's; in type mode a read that differs between places becomes `.parameter` (section 3).

## 3. Keys

```
struct BuilderKey: Hashable, Sendable {
	let built: ConstructionTarget         // concrete type and how it is constructed
	let form: ProvidedForm                 // constant, instantiator kind, lazy kind, erased-to type
	let reads: [FreeRead]                  // the body's free reads, in first-read order
	let family: Family                     // plain or @Sendable, in production too (see below)
	let configuration: ConfigurationRead?  // mocks: which configuration path, or "a parameter"
	let place: PlaceIdentity?              // path mode only
}
struct FreeRead { let property: Property; let outcome: ReadOutcome }  // keyed by property (label and form), never by label
enum ReadOutcome { case captured(BindingInstance), nil, passed, passedWrapper }
```

- **Free reads only.** A read is in the key only if the node's own body does not bind it. A body may read two forms of one label (`cycle-generation.md`: rebound properties are keyed by property, never by label; a mock root promotes each form on its own), so reads are keyed by `Property`.
- **`BindingInstance`** is the binding statement in this root's plan (the `ScopeGenerator` node that binds it), not the type-level `Scope`: two builds of `P`, each binding its own `x`, are two instances.
- **Forms.** A by-value read of a wrapper's instance is `.passedWrapper` when passed: the call hands the wrapper and the body reads `.instance` at its first read, so sharing never moves an instance's creation earlier (the eager-instance gap in `cycle-generation.md` must not spread).
- **Family in production.** A place inside a `@Sendable` builder and a place outside it never share a node: the production key carries the family, as seams do (d2). Without it a shared function placed at the root would be captured by a `@Sendable` builder below it, which SG:172–175 says forces `@Sendable`. Any remaining `@Sendable` need (a cycle closer referring across a `@Sendable` function to a node it is not inside) is computed after placement as a worklist, transitively, as `buildsInSendableFunction` does today.

- **Path mode** sets `place` to the scope's identity in this root's tree, so every key is unique and the graph has one node per place: today's output. The same mode keeps two facts per-place that type mode would merge: names (each place keeps today's name) and placement (each function sits immediately before the binding that uses it, today's position).
- **Type mode** sets `place` to `nil`. Two places share a node when built, form, reads, family and configuration agree. `DeclarationIdentity` is the declaring scope plus property (never the label), so renames and coinciding labels cannot merge different values (contract rule 6). `ReadOutcome.passed` is how a cycle or a `nil`-versus-value difference becomes a parameter, as the per-type production spike's cyclic stage does.
- **The fixed point (type mode).** Capture or pass depends on placement, and placement depends on the classes, so the order is stated:
  1. Partition places by `built`, `form`, `family`, `configuration` and the *set of free-read properties* (no outcomes yet). `cycleClosedOnDeclarations` names the declaration each closer repeats, so cycle members start in the right classes.
  2. Refine each class by the classes of the nodes its places call, until no class splits (the per-type production spike's bisimulation, on nodes, not text).
  3. Place each class (section 4) and set each read's outcome: `.captured(b)` where every place resolves it to the same binding instance `b` declared and visible before the placement; `.nil` where every place passes `nil`; otherwise `.passed` or `.passedWrapper`.
  4. Split any class whose places now disagree on a non-passed outcome or whose callees' classes changed, and repeat from 2.

  It terminates: each round only splits classes, and the number of places is finite. Placement only moves down when a class splits, so a capture never becomes invisible after it was checked in the same round.
- **Determinism.** Every iteration over nodes, classes, representatives, parameter unions and placement ties is by first-reach index. No dictionary or set of keys is iterated (`Scope` hashes by object identity).
- **One key type** serves production, seams and mocks (simplification C4). Mocks add `configuration`; the mock-overrides spike's key (concrete type, instantiated type, erasure, mock-or-init, extension-based, sorted forwarded properties, reads a configuration) is the same fields under these names.

## 4. Placement and parameters (type mode)

These are the per-type spikes' rules, unchanged:

- **Placement:** the lowest body every call passes through, before the first statement that reaches a call. Functions a loop reaches are declared before their callers; mutual recursion between local functions in one block needs nothing more.
- **Parameters, in order:** the level struct for each hole family the node leads to (seams; mocks with W1); forwarded values; each read whose outcome differs between places (`.passed`); a builder parameter is optional where any place reads it optionally.
- **Captures:** a read every place resolves to one declaration visible and declared before the block is captured. A value bound once above every place (the root's pass-through) is captured, not passed.
- **In place:** a *constant* whose function would have no statement but its return is constructed inline (today's elision, SG:5358, which includes constants that take received arguments; the seam spike's Stage 2 leaves are the no-argument case). Instantiator and lazy forms always get a named function: anonymous closures there hit swiftlang/swift#75003 (SG:5370–5371).
- **Lazy cycles:** a closing call hands the `LazilyInstantiated` wrapper, and the function reads `instance` where its body first reads it. This is the defect fix in `cycle-generation.md`'s "Eager instances at a lazy cycle's calls"; it needs one node per provided form, which the key already has. Path mode keeps today's eager `instance` argument.
- **Captures only what it reads** (`generator-design.md`): a function captures nothing its body does not read, so a shared function's body may need fewer captures than any one place's text had.

## 5. Names

- **Today** production has an allocator only for `_received` names in bodies with loops (SG:4585), seeded with a specific set (SG:5006–5014): the enclosing functions and fills referenced beneath, `namesBoundBySeam`, this body's builder functions, and each member's children's default names and `_received` names whether or not those exist. Mocks use one allocator per scope (SG:9209, 10033), and `SendableOverrideExtractor` reserves and claims override locals in emission-walk order and hands names back to later siblings (SG:9196–9204). Path mode ports each of these as a named policy with its exact seeds and claim order; the extractor is E4's.
- **Path mode** claims today's names in today's order, so it must reproduce `builderFunctionNames(for:enclosingFunctionNames:)` exactly: `__safeDI_<label>` (`ReservedName.builderFunctionNamePrefix`, `spelledAsJoinedIdentifier`), renamed to `__safeDI_<label>_<suffix>` with the suffix from `identifierSafeNames`' candidate order (simplified instantiated, instantiated, declared type's `asIdentifier`) only where a child references a function of that name (`functionNamesReferenced(beneath:)`), underscores appended on collision. E2 ports this as the path-mode naming policy, not as general allocator behavior.
- **Type mode** names a node from the label of its first-reached place, claimed: `__safeDI_<label>`, underscores appended on collision. No type name enters a function name, member or `_Values` field (check 2's shape-stability rule), so no nested-type or reserved-name spelling is needed. Determinism: first-reach order over ordered children is a function of the tree, which contract rule 6 and the rename-invariance oracle already require to ignore names.
- Every new fixed word is a `ReservedName` entry (`SourceRuleTests` fails on a `__safeDI_` literal elsewhere).

## 6. Order of statements

- Children keep today's order (`orderedChildren`, SG:4256–4308), including loop units and the seam carriers' "start last" (SG:3694–3701), which W1's gap 1 narrows to "only when its fill reads a sibling declared after it" (2-3-1-CREATION-ORDER).
- In path mode each function precedes its binding, as today. In type mode a shared function moves to its placement; bindings keep their order. So construction order is unchanged by the reshape: only where a function's text sits moves.
- Loop units emit as today, which differs by emitter. Production interleaves per member: function, `_received` function, binding, with only the seam payload bindings hoisted to the first member (SG:4576–4582, 4656, 5254–5262). A mock emits every member's prelude, then every function, then every binding (`InstantiatorBindingLines`).

## 7. Seams and mocks on the graph

**Seams (E3, R2a).** The seam's initializer is a body like a root's, whose nodes may take level structs. Fills, level functions in the calling module, `_Values` structs and the builder struct's members are statements of the calling module's or seam module's bodies, written by the same spelling functions. Rules from the per-type seam spike, all decided: one member per property leading to a place (candidate B: a loop's reopening property hands the reopened type's function the struct its own member returns); one function per family where a type is built in both (d2, pending Dan's wording); parameters in section 4's order. W1's stage structs and the dispatcher fixed point are calling-module statements on the same graph. E3's mapping table is written against slice 7's head, since slices 2–7 replace today's enum form (`FillDispatcher`, `RoutePlan`, `InnerScopeReaders`).

**Mocks (E4, R3).** A mock body is a body whose nodes read a configuration. The hook: each place has a `ConfigurationRead` (its path through `safeDIOverrides`, or `nil` for a reopened level), and its binding passes that configuration to the node, so path mode spells today's override reads and type mode passes the configuration as a parameter. Flat parameters, promotion, the parameter tree, `SafeDIOverrides` and configuration structs stay kept code; E4 replaces only the body. Configuration storage moves to the enum box in R3 (`__safeDI_Nested` behind an indirect enum, field name, type and access unchanged), not in E4, because it changes output. Never shared in R3 until a draw shows the shared form is right: the mock-overrides spike's list (subtrees with a cycle flag, `@Sendable` builders or configurations that require `Sendable`, loops of builders, scope payloads, fills, calls of public mocks, `onlyIfAvailable` aliases or unavailable receives, `LazilyInstantiated` instances), with public mocks added only if N2 says yes. N2's answer may change this paragraph; E4 starts after it.

## 8. How each PR proves itself

- **E1–E5 (path mode):** zero expectation file changes, every fuzzer pin unchanged, and the fuzzer coverage report shows no changed generator line unexecuted by a corpus graph. A changed byte is a defect in the rewrite. Each PR deletes the code it replaces.
- **R1–R3 (type mode):** expectations regenerated by tool, never by hand; whole-literal pins for each rule (one shared type, a cycle, a cycle with path values, a passed label, an optional parameter, a lazy closing call, a seam loop re-entry, a shared mock builder with two configurations); new oracle: each tree builds each key in one function; differential: on every corpus and a long run, path mode and type mode give equal values and equal retention (`DifferentialValueComparator`, retention judging on). The path key stays a test-only option for one release (the lead's amendment), removed in 2.4.0.
- **Cost:** N1's benchmark after E2 (no worse than the 2.3.0 head) and after each R PR (faster than 2.2.0 where 2.2.0 has the shape).

## 9. Open points

For the lead, before E1:

1. **Speculative generation.** Today every root's tree starts `generateCode()` speculatively with an empty cache key (`Scope.swift:1306–1321`), and parents that ask with other names or availability miss the cache (SG:3590–3596, 2106–2126). The plan step replaces per-child text generation, so the cache keys on nothing the graph needs. Proposal: drop the speculative text cache in E2 and plan each root once; measure `generate` time with N1 before and after (simplification C7 says measure, do not tune). If it is slower, plan children in parallel by subtree, from `Sendable` snapshots (`generator-design.md`).
2. **The `_received` decorator rule** is settled in section 2.4 (one rule, one named case). In type mode its places share a family by the key, so no place of a shared `_received` function needs a different decorator.
3. **Elision** is settled in section 4: constants only.
4. **Fills cross emitters.** `prepareFillCode` and `fillCode` (SG:3577–3588) cache fills by `propertiesGeneratedLater`, and mock bodies consume production-emitted fill strings (SG:9897). So E2 keeps a string interface for fills (an adapter that spells a fill's plan to today's text); E3 moves fills onto the graph against slice 7's head, and E4 switches the mock side to nodes. Proposal: accept that ordering rather than moving fills as one piece in E2, which would make E2 depend on slice 7's seam form.
5. **Production `@Sendable` sharing** (review question): this note splits production nodes by family, so `Logger` under the root and `Logger` under a `SendableInstantiator` stay two functions. The alternative, one `@Sendable` function used by both, is d1's production analogue; it changes nothing a person writes, but the d2 choice keeps seams and production alike.
