# SafeDI 2.3.1

2.3.1 makes per-module builds of seams much faster, fixes generated mocks that built a different value than production or did not compile, gives errors advice that holds, and lets Bazel skip SafeDI actions an edit beneath them cannot change. It also adds `SafeDITool query graph`, an alpha JSON export of the dependency graph.

## Upgrading from 2.3.0

Regenerate every module with 2.3.1 at once, as every SafeDI upgrade requires. No flag is removed or renamed, and the SwiftPM plugin, the Xcode project plugin and the Tuist plugin need no change. Most projects need no edit. Check these:

1. **A mock that calls another module’s public mock may now report an access error.** Where a place of that public mock is filled with a type your module cannot construct, such as an `internal` type of another module of your package, or a `package` type of another package, 2.3.0 accepted your mock and gave its `mock()` a required builder for the place, while your production tree reported the access error. 2.3.1 reports the same error for the mock, at the same declaration, with a fix-it that widens it (`package` within a package, `public` across packages). Apply the fix-it; it also lets your production tree build. Where only a hand-written `mock()` is out of reach, the error names that `mock()` instead. A build that does not activate the mock condition (`DEBUG` by default) reports nothing new. (#881)
2. **One builder label changes back.** If a seam or public mock has holes of both `Service` and `ServiceSendable`, 2.3.0 labeled `Service`’s builder `service_ServiceBuilder:`. 2.3.1 labels it `serviceBuilder:` again, so rename that argument in calls you wrote. (#880)
3. **`.safedi` files change format.** A `.safedi` file written by 2.3.0 is reported as unreadable by 2.3.1 (“A different version of SafeDI most likely wrote this file…”). Bazel, Tuist and builds that run `generate --module-info-output` regenerate every module’s file in the same build, so this shows only if modules are generated with two SafeDI versions. The SwiftPM plugin’s scan cache rebuilds itself. (#890, #902, #904, #934)
4. **Bazel: nothing to change if you use SafeDI’s `safedi_compile` rule.** It now passes two new flags and an `unused_inputs_list`; see [Build integrations](#build-integrations). A rule of your own keeps working without them. (#894, #904)
5. **An override for a value your mock’s tree requires can become `@Sendable`.** Suppose your mock calls another module’s public mock whose tree receives a `SendableLazilyInstantiated` only if available, and your mock’s own tree requires that value’s instance. 2.3.0 took an override of `(() -> Filter)?` and passed the call `nil`. 2.3.1 builds one `SendableLazilyInstantiated` and passes it to the call too, as the same mock built inline in one module does, so the override becomes `filter: (@Sendable () -> Filter)? = nil`. Make an override closure you pass there `@Sendable`: one that captures a value that is not `Sendable` no longer compiles. (#882)
6. **A few mocks build different values**, each now the value production builds. A test that asserted 2.3.0’s value changes. See [Generated mocks](#generated-mocks). (#865, #892)

## New

- **An internal mock can set what its calls of another module’s public mock receive only if available.** Where a type in the called public mock’s tree receives a value only if available and nothing in your tree provides it, your mock’s `SafeDIOverrides` gains an entry for it that defaults to `nil`, such as `Screen.mock(safeDIOverrides: .init(filter: ProbeFilter()))`. 2.3.0 always passed `nil`. A mock called as before builds what it built before, except in the shape Upgrading item 5 describes. Types listed in `additionalMocksToGenerate` get the entry too. (#882)
- **`SafeDITool query graph` (alpha)** exports a set of modules’ `@Instantiable` declarations as one JSON document, so a tool or a coding agent can answer its own questions about the graph: who uses a type, what a type depends on, which type fulfills a protocol. It reads modules as `query needs` does and resolves types as `generate` does. Each received dependency lists the declarations whose value generated code hands it, and whether some build hands it `nil`, read from the same trees `generate` builds. `--output` writes the file only when its bytes change. The command is alpha: its options and JSON (`formatVersion` 0) can change in any release. See [`Documentation/QueryGraph.md`](https://github.com/dfed/SafeDI/blob/2.3.1/Documentation/QueryGraph.md). (#913, #926)

## Fixes

### Generated mocks

- **A mock reports the access errors its production twin reports** ([#849](https://github.com/dfed/SafeDI/issues/849)). A generated mock whose tree calls another module’s public mock now fills each of its places as production does. Where a fill constructs a type the mock’s module cannot reach, it reports production’s error, naming the mock, rather than asking the test for a builder whose value production could never build. Upgrading item 1 describes the change. (#881)
- **A mock whose tree receives one label as both a `LazilyInstantiated` and a `SendableLazilyInstantiated` compiles.** Where a third type received that label by value and was declared first, the generated `mock()` read one wrapper before declaring it. It now declares every wrapper first. (#889)
- A mock now passes `nil`, as production does, to a receive only if available of the other `LazilyInstantiated` kind beside a required wrapper of the same instance; 2.3.0’s mock handed it a wrapper of its own. (#892)
- **A type built again by a cycle inside a mock reads the nearest wrapper’s instance**, as production does. Where a mock’s tree received a label as both wrapper kinds and a type beneath declared it again, 2.3.0’s mock read its own top-level instance and left the nearer binding unused, which a build that treats warnings as errors rejects. (#865)

### Generated code

- **A hole type’s builder label no longer follows an unrelated type’s name.** Adding a place of `ServiceSendable` beside one of `Service` renamed `Service`’s builder from `serviceBuilder:` to `service_ServiceBuilder:` in a seam’s initializers and a public mock’s `mock()`. Now only `ServiceSendable`’s builder is named apart. Upgrading item 2 describes the change. (#880)
- **Generated code calls only the entry point generated code is meant to call.** In 2.3.0, a public mock without a builder struct was called from other modules’ generated code through its `mock()`, and a wider tier forwarded to the narrower tier’s `mock()`. Every tier now declares `__safeDI_mock(…)` with `mock()`’s parameters, documented “Only code SafeDI generates calls this function,” and all generated calls go through it. Rebuild the module that declares a public mock before the modules that call it, as regenerating already does. Calls you write, and every value, are unchanged. (#859)

### Documentation

- `generate --help` now says that every module’s run passes `--module-info-output`, a module that declares a root included, and that `--dot-file-output` draws the trees of a module’s roots and seams in any module. The Manual lists the Linux directories of the artifact bundle. (#906)

## Diagnostics

### Changed messages

Errors whose advice led straight to another error now check the advice against your graph first (#858):

- A root that declares what its tree’s receivers require: the error now says that declaration would close a dependency cycle, and gives the cycle error’s two remedies (remove the receive, or receive it with `onlyIfAvailable: true` and an optional type), instead of advising the declaration.
- A receive inside a `@Sendable` builder names the `Sendable` form first and declaring the property inside the function second, each only where it validates.
- A suggestion whose required receive would close a cycle in a mock now suggests `@Received(onlyIfAvailable: true)` with an optional type.
- Advice to declare a property on a root, or on another type in the chain, also names the declarations a mock’s tree would hide it behind, to relabel.
- A seam whose wrapper-only receive no caller declares now advises the form its tree requires, such as `@Received let user: User`.

An input file `generate` or `query` cannot read is reported the same way on every run. The error names the file and gives a fixed reason: `Could not read the Swift file at '<path>': No file exists at that path.`, `The file is not UTF-8 text.`, or `The path names a directory, or a file SafeDI may not open.`, and likewise for a `.safedi` file. Of several unreadable files, `generate` reports the first in path order. 2.3.0 printed Foundation’s own error, whose details came in a different order each run, left out the path of a file that is not UTF-8, and reported whichever parallel read failed first. (#910)

## Build integrations

- **Bazel reruns a module’s SafeDI action only when a `.safedi` file it read changes.** `generate` takes a new option, `--unused-inputs-list-output`, which writes the `.safedi` files `--transitive-module-info-file-path` listed that the run never opened, and `safedi_compile` hands that file to Bazel as `unused_inputs_list`. A module with no root or seam opens none of them. On a 61-module harness, one edit in a bottom-layer module reran 40 SafeDI actions with 2.3.0, and reruns 5 with 2.3.1. Only Bazel’s local action cache benefits: a disk or remote cache still keys on every declared input. (#894)
- **A Bazel module’s `.safedi` file refers to the modules beneath it rather than copying them.** `generate` takes a new option, `--module-info-views-refer-to-modules`, which `safedi_compile` now passes. With it, a module’s file holds each module beneath it as a name and a checksum, and a run resolves those references from the files `--transitive-module-info-file-path` lists. A reference no listed file resolves is an error that suggests passing the transitive list or building without the flag. (#904)

## Performance

Generated code is byte-identical to 2.3.0’s for everything in this section, except where the Fixes above change it.

- A module that declares seams now stores their signatures in its `.safedi` file, so the modules that depend on it no longer recompute them: their `generate` runs 1.5 to 2.1× faster than in 2.3.0 on our seam benchmarks (#890, #902, #934).
- Those `.safedi` files are larger than in 2.3.0: 6.1 MB in total on our largest seam benchmark, against 156 KB. Hashing and caching them added no measurable time to a Bazel action in our measurements. We’re continuing to reduce their size.
- **A module that declares seams generates faster.** Its seam signatures are computed in time linear in its seams, where 2.3.0’s grew with their square, and each declaration’s access is proved once per run, shared by its seams and public mocks. On our benchmarks of 10, 50 and 100 seam modules, per-module generation of the whole app takes 0.71 to 0.88× 2.3.0’s time. (#869, #917, #928)
- **Per-module generation reads the modules beneath once**, and skips encoding module info it does not compare and the teardown at exit. On a chain of 200 modules, per-module generation takes 0.80× 2.3.0’s time, and its peak memory falls from 499 MB to 96 MB. (#887, #893)
- **`scan` is faster on large graphs.** On our benchmarks of 200 or more types, it takes 0.61 to 0.88× 2.3.0’s wall time. This is the first step of the SwiftPM plugin’s build. (#883, #899)
- **`generate` uses less memory and CPU on trees without seams.** Validation reads less per scope and skips a subtree it already walked clean, and production code is built once per scope and written once, at the end, in time linear in its size at any depth. On every one of our benchmarks without seams, `generate`’s peak heap is 0.08 to 0.78× 2.3.0’s and its CPU time 0.03 to 0.74×. (#856, #879, #888, #895, #896, #897, #907, #914, #919, #924)
