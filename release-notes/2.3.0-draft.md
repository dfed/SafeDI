## What’s new

### Generate a dependency tree per module: seams

A root’s generated `init()` builds the whole tree in the root’s module, so every type in the tree must be visible there, and any change recompiles the tree there. Decorate a type at a module’s boundary, such as a feature’s entry point, with `@Instantiable(generateDependencyTree: true)`, and its own module generates its tree as an initializer. Every other tree calls that initializer and treats the type, a seam, as a leaf, so a change inside the seam’s tree recompiles only its module and the generated calls (#525).

- **One initializer per access level.** The initializer takes what the tree needs from outside, each parameter as visible as the types it names, so a seam has one initializer per access level among its parameters. A wider one passes `nil` for the parameters it omits. The types the tree builds keep their own access (#525, #527, #640).
- **Values stay lazy.** A value the seam passes into its tree is created when the tree first reads it, as it is when the tree is built inline (#578, #583).
- **Calls are checked.** A guard enum beside the initializers makes a stale generated call a compile error. Generated code calls an initializer whose labels start with `__safeDI_`. To call a seam from code you write, set `#SafeDIConfiguration(generatePlainDependencyTreeInitializers: true)` in its module, and SafeDI also generates an initializer with readable labels, which takes every parameter as a plain value and keeps nothing of the caller (#615, #631). No parameter has a default, so a hand-written call stops compiling when the seam’s tree starts to receive another dependency (#561).
- **Holes: implementations can live above the feature.** A seam’s tree can instantiate a type no declaration its module can see fulfills, such as a protocol only the app implements. The seam then takes one builder per such type, labeled after what it builds (`userServiceBuilder`), and hands it an enum of the places that want a value, nested by type, with the values in scope at each place. The builder returns the plain value, and the seam wraps it where the property is an `Instantiator` or `LazilyInstantiated`. A module that can see an implementation fills the builder in the code it generates; a seam that cannot passes it up to its caller. `{ _ in DefaultUserService() }` fills every place (#528, #627, #628, #690, #691). ⟦PLACEHOLDER: leak-fix slices 1–7 may change how builders are labeled, passed and held. Slice 1 (#731) is drafted under “Leak fix” below; reconcile this bullet when the stack lands.⟧
- Errors at a seam, and the trees a seam builds differently from an inline build, are listed in the Manual’s “Where a seam differs from building its tree inline”.

Under the Xcode project plugin, which names no module, seams are built inline.

### Public mocks

`@Instantiable(generateMock: .public)` generates a `public` `mock()` that tests and previews in other modules, of this package or another, can call. A mock another module generates calls it wherever it cannot build the type’s tree itself. `generateMock` takes a `MockGeneration`: `.none`, `.internal` or `.public`; `true` and `false` still mean `.internal` and `.none`. Like a seam, a public mock has one `mock()` per access level among its parameters, and takes a builder for each type its module cannot build (#530, #629, #692, #696, #707). A public mock compiles in a module whose declarations default to the main actor (#641).

### Types and initializers can be `package` or `internal`

`@Instantiable` types, their initializers, `instantiate(…)` methods and hand-written mocks no longer need to be `public`. Each needs only the access of the code that builds it: any level but `private` and `fileprivate` in its own module, `package` in another module of its package, and `public` across packages. The macro rejects only `private` and `fileprivate`, and `generate` reports each declaration that must widen, once, with a fix-it (#509, #534, #569, #575). A project whose types are all `public` generates the same code as before.

- `package` access needs every module of a package compiled with the same package name. SwiftPM passes it. Under Tuist, set `SWIFT_PACKAGE_NAME`; under Bazel, `package_name` on `safedi_swift_library`; in a custom build, `generate --package-name` (#567, #574, #647).
- A type SafeDI reads no declaration of, such as a system framework’s, counts as `public` (#541).
- Generated imports spell the access level their declarations need, so a module that imports `Foundation` below `public`, or turns on `InternalImportsByDefault`, compiles (#551).
- The macro’s fix-its that add an initializer, `instantiate()` or a mock method give it the access the type needs instead of always `public` (#552).

### Attributes on generated initializers

`generatedInitializerAttributes:` puts attributes on a root’s generated `init()`, and on every initializer generated for a seam; `generatedAttributes:` applies to both the initializers and the mock. For example, `@Instantiable(isRoot: true, generatedInitializerAttributes: "@MainActor")` (#510). In a module whose declarations default to the main actor, give each type that conforms only to `Instantiable` `generatedAttributes: "@MainActor"` (#664).

### Loops through received instantiators

A type can receive an instantiator declared above it even when that instantiator builds the receiver, or a type above it. Two screens can open each other without either instantiating the other: their parent declares an `Instantiator` for each, and each screen receives the other’s. Among the properties one type creates, a cycle of receives is accepted when every property on it is an instantiator, at any depth, with `Instantiator`, `ErasedInstantiator` and their `Sendable` twins, through `fulfilledByType` and renames. Generated mocks build these loops as production does, and seams carry them (#649, #650, #651).

### Dependency cycles through an instantiator anywhere along them

A dependency cycle is accepted when any dependency along it is an instantiator, from whichever type a tree enters it. A root holding `a: A`, where `A` builds `B`, `B` holds `cBuilder: Instantiator<C>`, and `C` builds `A`, used to be rejected, though a root holding `cBuilder` built. The error for a cycle with no instantiator names every dependency on it (#571).

### `Builder` type aliases

`Instantiator<T>.Builder`, `SendableInstantiator<T>.Builder`, `ErasedInstantiator<ForwardedProperties, Instantiable>.Builder` and `SendableErasedInstantiator<ForwardedProperties, Instantiable>.Builder` name the closure each wrapper is created with, so code can spell it, for example where a builder forwards a value that is itself a closure (#712).

### Generated mocks

- A `mock()` parameter for a forwarded value, or for a received value only an `Instantiator` can build, defaults to the hand-written mock SafeDI would build its type with, a protocol’s `mockOnly` fake included, when that mock takes no required argument and the module can call it (#570).
- A `mock()` parameter handed to several types that each create that dependency says so in its documentation comment (#614).

### Bazel, Tuist and custom builds

- **Bazel.** `safedi_swift_library` collects the SafeDI modules beneath a module, so a module that declares a root lists only the modules it depends on directly in `safedi_deps`. Complete lists keep working (#610).
- **Calling another module’s seam or public mock** needs only the modules you import listed. A module still lists each module whose types its own roots and mocks build (#577, #581).
- **Two modules can each keep an `@Instantiable` type of one name** that a module using both cannot name, such as two `internal` `Store`s. An app that reaches both through seams builds. The error for two declarations of one name now names the modules, and its remedy fits the shape (#618, #622).
- `generate` rewrites its combined output and `.safedi` file only when their contents change (#577).

### `query needs` (beta)

- The report lists each flat `mock()` parameter’s default, and the JSON adds `defaultExpression` to `unfulfilledDependencies` (#570).
- A `--module-info` module is named after the module its file records; two files recording one module, or a directory named like one, are an error (#577).

## Performance

⟦PLACEHOLDER: `scan` and `generate` wall time and instructions against 2.2.0 on the 15-module, 3,100-file fixture shaped after a production app, release builds, measured after the leak stack lands.⟧

- The macro plugin compiles only the parts of `SafeDICore` the macros use. A release build of the macro module takes about 88% fewer compiler instructions, and the plugin binary is about 20% smaller (#635).
- `scan` spells and stamps a module’s input paths concurrently and reuses what the parse already computed (#680). Writing and reading `.safedi` files and the scan cache no longer reflects over their types at run time, which was most of a small module’s `generate` under Bazel or Tuist (#668).
- `generate` qualifies nested types, checks parameter-name encodings, and builds mocks with fewer copies and repeated walks (#596, #663, #665, #681).

## Fixes

### Lazy cycles

- A type built again through a lazy instantiator cycle receives each property from the nearest declaration above it, as the Manual’s rule says. 2.2.0 passed the declaration above the cycle, skipping a nearer one, or passed `nil` (#533). Where the type built again receives the label in two forms that no one declaration provides, it gets the required form’s nearest declaration, and a shape no one value can carry is an error (#639).
- A type that receives, only if available, an instantiator its builder’s own scope declares is passed that instantiator at every depth of the cycle. 2.2.0 passed `nil` below the first (#572).
- A dependency with the same label and type as a declaration above it, but fulfilled by another type, builds the type it names. 2.2.0 took it for a cycle: a `flowBuilder` fulfilled by `SettingsFlow` inside `LoggedInFlow` built another `LoggedInFlow`, and any other form was rejected (#571).
- A type that receives the label of an instantiator closing a cycle is passed that instantiator from every entry point. 2.2.0 rejected it or passed `nil` (#571).
- A type built inside a dependency it receives, beneath a type forwarding that dependency, is passed the forwarded value, or `nil` when the receive is only if available. 2.2.0 rejected it as a cycle (#571).

### Renamed dependencies

- A rename with `erasedToConcreteExistential: true` of an optional dependency (`ofType: Secret?.self`), required or `onlyIfAvailable`, builds the erased value only when the dependency is present: `(token as Secret?).map { AnyAuth($0) }`. 2.2.0 generated `AnyAuth(token)`, which did not compile with an optional `token` (#572, #579). See Breaking changes.
- In a dependency tree, a type that requires an `onlyIfAvailable` rename is passed `nil` where nothing holds the rename’s dependency, or where that dependency is an ancestor still being built. 2.2.0 rejected both (#572).

### Generated mocks

- A generated mock builds the type an `@Instantiated(fulfilledByType:)` property names, as the app does, even when another type lists the property’s type in `fulfillingAdditionalTypes`. It used to build that other type, or use its merged `mockOnly` mock. A `mockOnly` fake of the property’s type still replaces the named type (#590). See Breaking changes.
- A generated mock compiles when one of the mocked type’s renames has a label that a dependency the mock builds receives as another type. The rename used to hide the `mock()` parameter for that receive. The mock no longer builds a dependency one of the mocked type’s own renames already provides, which drew an unused-value warning (#594). See Breaking changes.
- A generated mock of a type whose initializer, `instantiate(…)` or hand-written mock has a labeled, default-valued `@autoclosure` parameter compiles, and evaluates the value where it builds the type (#595).
- A generated mock compiles when a type in its tree has a default-valued `@escaping` parameter whose type is a typealias of a function type, such as `onTap: @escaping Handler = {}` (#542).
- A mock that takes two received closures of one label names a `nonisolated(nonsending)` closure’s parameter with identifier characters only, so it compiles (#678).
- A mock whose `@Sendable` builder reads overrides whose labels join with underscores to one name compiles (#679).

### Generated code

- An `@Instantiable` nested in a namespace that names one of the namespace’s types unqualified generates code that compiles. It used to fail with “cannot find type”, or name a top-level type of the same name. A receive spelled `NestedType` inside `Grandchild` matches a forwarded `Grandchild.NestedType`; it used to be an error (#585).
- A generated file imports the module that declares a type it builds for a property of another type, through `fulfilledByType:` with `erasedToConcreteExistential: true` or through `fulfillingAdditionalTypes`, when no file of the module imports it. It used to fail with `cannot find 'DefaultThing' in scope` (#617).
- SafeDI keeps every part of a type that its spelling carries, so generated code that did not compile for such types compiles, and declarations that do not match get a SafeDI error instead of a compiler error in generated code (#605).
- An `ErasedInstantiator` whose first generic argument is the tuple of the built type’s forwarded properties works when an element’s type is more than one bare name, and that argument may spell each type any way that syntax alone shows is the same type (#604, #606).
- The macro accepts an `@escaping` initializer parameter whose type is a typealias of a closure (`init(onTap: @escaping OnTap)`), and an initializer parameter declared `@Sendable @escaping` matches a `@Sendable` closure property (#557, #616).
- `#if` around a plain type declaration resolves as `#if` around `@Instantiable` content does (#555).

### Build integration

- **Bazel.** Diagnostics name each file as the path Bazel handed SafeDITool, which editors and rules_xcodeproj open, instead of a path inside the deleted sandbox (#536). `bazel run @safedi//bazel:safeditool` accepts relative paths (#560). SafeDI depends on the Bazel Central Registry’s `swift-syntax` and `swift-argument-parser` (#599).
- **Tuist.** The plugin loads by commit, as the Manual now shows: no Tuist version loads it by tag (#556). `-D` flags in `OTHER_SWIFT_FLAGS` count as active compilation conditions (#560). A project in a subdirectory of the workspace finds `SafeDITool` (#553).
- **Xcode.** **Safedi Release Install** (`safedi-release-install`) checks the `SafeDITool` it downloads against a SHA-256 pinned in SafeDI. A corrupted or replaced download is deleted and the command fails with both hashes; running it again retries (#600).

## Diagnostics

- Errors name their fix in the reader’s build: the root, unfulfilled-type, duplicate and unfulfilled-receive errors (#557); the access errors, which lead with the package-name remedy and name each integration’s setting (#647, #673); the error for a type nothing fulfills, which names no imported module (#672); the hidden-receive error in a mock, which names both receives (#671); and the errors whose advice used to produce another error (#608, #687).
- The macro warns about `mockAttributes` on a `mockOnly` declaration (#557).
- The macro no longer warns about a bare nested type name in a dependency’s type, which SafeDI now qualifies. It still warns, with a fix-it, about a nested type spelled through `Self` (#589).
- Every apostrophe SafeDI emits is ’ (U+2019) (#698). A script that matches SafeDI’s text needs updating.

### Deprecations

Each still works, now warns, and is removed or becomes an error in SafeDI 3.0 (#558):

- `@Forwarded` on an `Instantiator`, `SendableInstantiator`, `ErasedInstantiator`, `SendableErasedInstantiator`, `LazilyInstantiated` or `SendableLazilyInstantiated`. Declare the wrapper `@Instantiated` and forward what the type it builds needs, receive it from an ancestor that declares it, or forward the value it builds.
- `generate --additional-imported-modules`. Use `#SafeDIConfiguration(additionalImportedModules:)`.
- A manifest passed to `generate --swift-manifest` that lacks the fields `scan` always writes. Run `scan` first, or use `--output-directory` or `--combined-output`.

## Errors SafeDI now reports

Each of these graphs generated code that did not compile wherever a tree built it, or built a value no tree can build:

- `erasedToConcreteExistential: true` on an `any` or composition existential, or on the type a SafeDI wrapper builds, with a fix-it that removes the argument; and an erased rename into a SafeDI wrapper of a dependency that is not a function (#592). See Breaking changes.
- An `async` or `throws` hand-written mock method, with a fix-it that removes the specifiers. A generated mock calls a hand-written mock synchronously (#509).
- A rename of another rename on the same type, a rename of a dependency to itself, and a chain of renames formed by `#if` clauses active together (#563). See Breaking changes.

## Breaking changes

1. **A root’s `init()` is generated only in its own module.** A target generates `init()` only for the roots its own files declare. In 2.2.0, a target whose plugin read another module’s root also generated that root’s `init()`. If you call a root’s `init()` from another target, add the SafeDI plugin to the target that declares the root (#564).
2. **Renames of renames.** The macro rejects a property renamed from another rename on the same type, which 2.2.0 documented and built, with a fix-it that renames the start of the chain. On an optional rename of an only-if-available rename, the fix-it gives `nil` where the start is unavailable, even where an ancestor declares the middle label, which the chain used to read. The macro also rejects a property renamed from itself, such as `@Received(fulfilledByDependencyNamed: "x", ofType: X.self, onlyIfAvailable: true) let x: X?`; apply the fix-it. `generate` rejects a chain of renames formed by `#if` blocks active together, which could build a wrong value; give the first rename another label (#563).
3. **`mockOnly` types in `additionalMocksToGenerate`.** Listing a type whose only declarations are `mockOnly` is an error. Remove the entry and call the fake’s own method, or name that method `mock` (#557).
4. **`onlyIfAvailable` renames are always bound.** An `onlyIfAvailable` rename whose dependency cannot be built first is `nil` for the type that declares it and every type below it. 2.2.0 let it fall through to an enclosing property of the same name. In a dependency tree, a dependency received only if available inside the property it is built from is `nil`, even beside a farther optional declaration of its name, which 2.2.0 passed. A type built as a rename’s dependency that requires that rename is a dependency-cycle error, also under an enclosing property of the rename’s name (#572).
5. **Erased renames of optional dependencies are optional.** A rename with `erasedToConcreteExistential: true` whose `ofType:` is optional must declare an optional property, and the macro’s fix-it adds the `?`. 2.2.0 accepted a non-optional property, which compiled only where the dependency happened to be bound to a non-optional value. Declare the property optional, or name the non-optional dependency in `ofType:` (#579).
6. **A label received in two forms along a mock’s tree.** A generated mock reports the hidden-label error production reports when its tree receives one label in two forms, one beneath the other with no declaration of the label in between, and either receive is required: in the tree of a dependency the mock builds beside the mocked type (#593), and in the mocked type’s own tree (#597). In 2.2.0 such a mock either did not compile, or compiled for a tree no production root can build, or offered an override for a value production always passes `nil`; in some of these shapes 2.2.0’s mock passed a built value where production passes `nil`. Receive the two forms under different labels.
7. **Generated mock signatures.**
   - The `SafeDIOverrides` entry of an `@Instantiated(fulfilledByType:)` property whose type another type also fulfills configures the named type: `filter: AppFilter.SafeDIMockConfiguration`, was `CoreFilter.SafeDIMockConfiguration`. Update an override that configured the other type’s construction (#590).
   - A mock no longer has a `SafeDIOverrides` entry for a dependency one of the mocked type’s own renames provides. Setting it never had an effect; delete the argument (#594).
8. **Instantiators received in loops.** An instantiator received with `onlyIfAvailable: true` inside the tree it builds, or from an instantiator beside it that receives it back, is that instantiator instead of `nil`, and so is a rename of one. Two types that receive one instantiator this way no longer hold the same wrapper object; each builds the same thing. One such receive is an error: a `SendableInstantiator` whose tree receives, only if available, a non-`Sendable` instantiator whose tree requires the `Sendable` one back. The same receive outside a loop was already that error. Declare the other instantiator as its `Sendable` twin, or remove the receive, which has only ever been `nil` (#649).
9. **`erasedToConcreteExistential` where no erasing initializer exists.** The `@Instantiated` and `@Received` macros report `erasedToConcreteExistential: true` on an `any` or composition existential, or on the type a SafeDI wrapper builds, and an erased rename into a SafeDI wrapper of a dependency that is not a function. These compiled only where no tree built the property. Remove the argument, or erase where the wrapper is instantiated with `@Instantiated(fulfilledByType:erasedToConcreteExistential:)` (#592).
10. **`async` and `throws` hand-written mocks.** The macro rejects them, with a fix-it. They compiled only where no generated mock called them (#509).
11. **Custom Bazel and Tuist setups.**
    - A `safedi_compile` you declare yourself needs `module_name` (`safedi_swift_library` sets it), and `generate --module-info-output` requires `--module-name` (#504, #577).
    - Under Tuist, only where a target’s module name differs from its `module:` argument: `SafeDI.preCompileScript(dependencies:)` names each dependency by its module name (`PRODUCT_MODULE_NAME`). Update such `dependencies:` entries (#577).

A graph SafeDI now rejects did not compile before, except the shapes in items 2, 3, 5, 6, 8, 9 and 10.

## Upgrading

### From 2.2.0

- **Root `init()` across targets.** If another target calls a root’s `init()`, apply the plugin to the root’s own target (item 1):

  ```diff
   .target(
       name: "Feature",
       dependencies: ["SafeDI"],
  +    plugins: [.plugin(name: "SafeDIGenerator", package: "SafeDI")]
   ),
  ```
- **Macro errors.** Items 2, 3, 5, 9 and 10 are reported by the macro as you type, each with a fix-it where one is safe.
- **Mock call sites.** Where a `SafeDIOverrides` entry changed type or went away (item 7), the compiler points at each call site.
- **Deprecation warnings.** A build that treats warnings as errors fails on the three deprecations until each is replaced.
- **Diagnostic text changed.** A script that matches SafeDI’s error or warning text needs updating.
