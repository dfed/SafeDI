# SafeDI — Claude Code Guidelines

## Documentation

The core documentation is `Documentation/Manual.md`. Read it before making changes to understand SafeDI's API, macros, configuration options, and mock generation. The manual is the source of truth for user-facing behavior — if you change behavior, update the manual.

## Build & Test

```bash
swift build --traits sourceBuild   # Build all targets
swift test --traits sourceBuild    # Run all tests
./CLI/lint.sh                      # SwiftFormat — must pass before every push
swift test --traits sourceBuild --enable-code-coverage  # Coverage report
```

The `sourceBuild` trait is required for local development to compile SafeDITool from source. Without it, the plugin uses the prebuilt binary from the artifact bundle.

Always lint before pushing. Always run the full test suite after changes — don't rely on filtered runs alone.

### CI

- Every CI job runs on a Linux runner unless it genuinely needs macOS: Xcode or `xcodebuild`, an Apple platform SDK, the Xcode project plugin, or the macOS release binaries and their notarization. Linux runners scale; macOS runners are the scarce resource that pull requests and publishes queue on.
- A job on a `macos-*` runner states why in a comment in the workflow.
- New Linux jobs use the same container and setup as the existing Linux test job ("Build and Test on Linux" in `ci.yml`).

## Architecture

SafeDI is a compile-time dependency injection framework for Swift. It uses Swift macros (`@Instantiable`, `@Instantiated`, `@Received`, `@Forwarded`) to declare dependency graphs, then generates initializer code and mock methods via a build tool plugin.

### Key modules

| Module | Role |
|--------|------|
| `SafeDICore` | Models (`TypeDescription`, `Property`, `Instantiable`, `Dependency`), visitors (`FileVisitor`, `InstantiableVisitor`), generators (`ScopeGenerator`, `DependencyTreeGenerator`) |
| `SafeDIMacros` | Swift macro implementations (`@Instantiable`, `@Received`, etc.) |
| `SafeDITool` | CLI entry point with `scan` and `generate` subcommands — scans Swift files for `@Instantiable` types, builds dependency tree, generates output |
| Plugins (`SafeDIGenerator`) | SPM build tool plugin that wires the tool into the build |

### Code generation flow

1. **Plugin** writes CSV of swift files → runs `SafeDITool scan` to build manifest → runs `SafeDITool generate` to produce code
2. **`SafeDITool generate`** parses all files via `FileVisitor` → builds `DependencyTreeGenerator` → generates per-root code + mock code
3. **DependencyTreeGenerator** creates `ScopeGenerator` trees → each generates its code via `generatePropertyCode`
4. **Mock generation** (`generateMockCode`) creates `mock()` static methods with `@autoclosure @escaping` parameters, `T? = nil` subtree parameters, and `MockContext` for disambiguation

### Conditional compilation

`FileVisitor` takes a `ConditionalCompilationEvaluator`; `InstantiableVisitor` takes a `ConditionalCompilationHandling`, which the macro sets to `.scanAllClauses` (the compiler already picked the active clause) and `FileVisitor` sets to `.evaluate(evaluator)`. The evaluator treats the supplied `activeCompilationConditions` as complete (a bare condition not in the set is inactive), scans every clause of platform-conditioned blocks (`os()`, `canImport()`, …), and evaluates mock-only content (`SafeDIContentDetector`) as if `mockConditionalCompilation` were active. A guarded initializer counts as SafeDI content only when `ConstructionInitializerCandidates` finds some evaluation could select it for construction — it must be able to fulfill the dependencies (bounded below by those outside every `#if` and above by those in every clause) and must not follow an unguarded initializer that fulfills them in every evaluation; initializers in `@Instantiable` extensions never count. Each evaluation that decides a block guarding SafeDI content is a `ConditionalCompilationDecision`; `generate` prepends `ConditionalCompilationDecision.compileTimeAssertions` (`#if …` / `#error`) to every generated file so the compiler rejects code generated under a condition it evaluates differently. There is no "unknown condition" state and no error at generate time: the compile-time assertion is the fail-closed mechanism. `parseModule` first parses the module's own files (`configurationFilePaths`) named `SafeDIConfiguration.swift`, chosen by path alone, and walks them to find the module's `#SafeDIConfiguration`: `SafeDIContentDetector` classifies a configuration as production content, so its `#if` blocks never depend on `mockConditionalCompilation`. The configuration found there builds the module's evaluator, every other file is read, parsed, and walked once with it, and the `SafeDIConfiguration.swift` trees are walked again from memory only when the mock condition is not the default. When no `SafeDIConfiguration.swift` holds a configuration (the fallback), every file is walked with the supplied conditions and the default `DEBUG` mock condition, which finds a configuration elsewhere; if it names another mock condition, every file that declared SafeDI content is read, parsed, and walked again — no text heuristic picks a subset. `SafeDIConfiguration.placementWarning` reports exactly that case (configuration outside `SafeDIConfiguration.swift` with a non-default mock condition) as a `SourceDiagnostic` with `.warning` severity located at the invocation (`SafeDIConfiguration.declarationLocation`, which travels in module info and scan's cache). `SafeDIConfiguration.unreadableAdditionalDirectoryWarnings` likewise warns, at the invocation, about each `additionalDirectoriesToInclude` entry of the selected configuration from which no Swift file can be read (nothing at its path, or a non-Swift file; an empty directory is fine). It judges `ParsedModule.additionalDirectories`, the `AdditionalDirectory` entries paired with the path they resolved to: scan's cache stores scan's resolution (against scan's working directory, which its freshness check also enumerates), and a fresh parse uses this run's. It is a warning, not an error, because `scan` reads every configuration's directories in every clause and a directory may exist only on some platforms. `generate` returns warnings instead of throwing them and `run()` prints them; `scan` never warns, so a build warns once per `generate`. Every syntax tree but those of `SafeDIConfiguration.swift` files is released as soon as it is walked, so memory scales with concurrency rather than module size. `scan` and `generate` both go through it, and it rejects more than one configuration in scope. `scan` records its project root in the manifest so `generate` matches configuration files by the same resolved paths.

Build tool plugins cannot read the conditions the compiler receives while they plan the build, so the `SafeDIGenerator` plugin also passes `generate` the literal arguments `--build-setting-active-compilation-conditions=[${SWIFT_ACTIVE_COMPILATION_CONDITIONS}]` and `--build-setting-other-swift-flags=[${OTHER_SWIFT_FLAGS}]` (`BuildSettingCompilationConditions`). Swift Build (Xcode and SwiftPM's `swiftbuild` backend) expands them when the command runs, and Xcode project builds expand them through the shell script that runs the command; SwiftPM's native backend passes them through literally. When both arrive expanded, their conditions plus the `-D` flags in `OTHER_SWIFT_FLAGS` *replace* the command-line and manifest conditions (Xcode reports a package's debug-configuration defines to plugins in Release too, so a union would be wrong); otherwise `generate` falls back to them. The plugin passes the options to every SafeDITool it runs, including the prebuilt binary pinned in `Package.swift` (Swift 6.2 sometimes hands the plugin that one even with the `sourceBuild` trait) and the `.safedi/` download named by `safeDIVersion` in `Plugins/Shared.swift`, so those must never name a release older than 2.1.0-rc-3, the first to accept them. Which files exist — roots, `generateMock: true` types, `additionalMocksToGenerate` entries, `#SafeDIConfiguration` files — is still decided by `scan` at planning time, but independently of any condition: `scan` plans an output for each such declaration in every clause of every `#if` block (`OutputFileDeclarations`, which `SafeDIContentDetector` collects during the walk of each block it already makes and `FileVisitor` adds for the clauses it scans), and treats the files in every configuration's `additionalDirectoriesToInclude` as inputs, parsing those only an inactive configuration lists solely to plan their roots. `generate` writes every planned output, without code (only the header and its compile-time assertions) when the declaration is inactive under its conditions, and generates the additional mocks only of the configuration it selects. It still rejects with a `ManifestError` a declaration whose file the manifest does not list (the manifest's `mockScopedFilePaths` lets it check mocks and configurations), which with superset planning means the file changed after `scan` or the manifest is hand-written. It also rejects a manifest in which two outputs name one file, which only a hand-written manifest can do: `scan` lists each additional mock once, however many times a configuration lists it. The `PluginScanner` fallback ignores `#if` and unions every configuration's arrays, so it plans the same superset. Because a cached file scan may declare a configuration in an inactive clause, `generate` parses the module afresh when a stale file declares a configuration in any clause, not just an active one; and when it parses `additionalDirectoriesToInclude` afresh it names those files as the manifest does, so their roots match its entries.

Because `generate` usually has more conditions than `scan` (always `SWIFT_PACKAGE`, `DEBUG` in debug), scan's cache keeps per-file results keyed by what each file consulted. `ScannableClauses.consultedConditions` records every bare condition a clause selection depended on (minus the mock condition for mock-only blocks, which is forced active); `FileVisitor` and `InstantiableVisitor` accumulate them only for blocks whose selection can change what they report: blocks with SafeDI content, blocks with syntax errors, and (separately, as `importOnlyConsultedCompilationConditions` with `importSegments` holding the block source) blocks that guard only imports. `FileVisitor` also collects `mockImports`: each block guarding only imports is selected again as a block guarding mock-only declarations is, and `importOnlyConsultedCompilationConditions` covers both selections. Generated mock files, `SafeDIMockConfiguration.swift`, the mock half of `--combined-output`, and module info carry `mockImports`; dependency-tree files keep `imports`, so `#if DEBUG import A #else import B #endif` still gives production code `import B`. `CachedScannedModuleInfo` (see Serialization) stores the files that consulted nothing as one `ModuleInfo` and the rest as `CachedFileScan`s; `generate` walks a file again only when a condition it consulted changed value, re-evaluates only its import segments when only those changed, and parses the whole module afresh when a walked-again file declared a configuration. Any new state a visitor collects from inside an `#if` block must either be covered by `consultedCompilationConditions` or be provably independent of the selection, or the cache becomes unsound.

### Mock generation flow

Mock generation follows this pipeline:

1. **`generateMockCode`** builds the mock scope map via `createMockTypeDescriptionToScopeMapping` (includes ALL types, not just reachable from roots)
2. For each type with `generateMock: true`, **`createMockRootScopeGenerator`** promotes `@Received` dependencies to root-level children (except those `mockCanBuild` rejects) and validates for cycles
3. **`ScopeGenerator.generateMockRootCode`** builds the mock method:
   - Calls `collectMockParameterTree` to walk the dependency tree and build `MockParameterNode` trees
   - Collects flat parameters: `@Forwarded` deps, uncovered `@Instantiated` deps, `@Received` deps not in the tree
   - Generates `SafeDIOverrides` struct (if tree children exist) and the `mock()` method signature and body

The production code path (`generatePropertyCode` with `.dependencyTree`) and mock path (`.mock`) share the same `ScopeGenerator` but diverge at `generatePropertyCode`. Mock fields (`mockInitializer`, `mockReturnType`, `customMockName`) are only accessed in mock code paths — never in production paths.

### Cycle mechanisms

Multiple cycle-related mechanisms coexist — keep them distinct:

| Name | Scope | Set by / when | Role |
|------|-------|---------------|------|
| `isPropertyCycle` on a scope/node | Per-root, syntactic | `Scope.createScopeGenerator` when a property label repeats in the ancestor stack | Terminates infinite descent during a single root's walk; differs between roots for the same underlying cycle. |
| `cycleEdges` (set of `CycleEdge`) | Global | `DependencyTreeGenerator.computeCycleEdges`, alphabetical-DFS feedback arc set | Chooses a single back-edge per cycle consistently across all roots — required because shared `SafeDIMockConfiguration` structs must have one shape. Consumed by struct generation AND override-path navigation in mock bodies. Each root returns the nodes of the types its tree configures (`collectConfigurationTypes`); `generateMockCode` keeps the first root's node for each type, in alphabetical root order, and only then generates that struct (`ScopeGenerator.generateConfigurationStruct`), so no root generates a struct that is thrown away. |
| `throwIfInvalidCycle` | Shared classifier | Called from `validatePropertiesAreFulfillable` (production, and a mock root whose children require one another) and `validateMockRootScopeForCycles` (mock) | Rejects constant + partially-lazy + received-lazy cycles. Accepts fully-lazy non-received cycles (those compile as long as pruning breaks the config-struct recursion). Neither stack walk considers an `onlyIfAvailable` dependency, `@Received(onlyIfAvailable: true)` or an `onlyIfAvailable` alias (`Dependency.canCloseDependencyCycle`): generation passes it `nil` while the property it receives is built (`isPropertyUnavailable`, which in a mock matches the property still being built exactly or by its non-optional form), whatever kind of property that is — constant, `LazilyInstantiated`, or `Instantiator` — so `a: A?` under the `a: A?` it is built inside gets `nil` as it does under `a: A`, and so does an alias of `a` only if available. Both walks classify the dependency that closes a cycle with `closingReceive(of:in:)`: a required `@Received` dependency is a receive, and so is a required alias, which receives its fulfilling property — unless its scope creates that property, which the alias then refers to. Do not use `Dependency.Source.isReceived` for this; it is `false` for aliases. The classification matters only for a non-constant property: a required alias fulfilled by a `LazilyInstantiated` is mapped to the constant it stands for and rejected as a constant cycle, exactly as its constant twin is. Production's received walk agrees by another route: `Scope.requiredReceivedProperties` lists a required alias's fulfilling property, with `aliasProperty` so the error names the alias, except one the alias's scope always creates (`unconditionallyCreatedProperties`: instantiated, forwarded, or a required alias), which requires nothing of an ancestor. An alias of an `onlyIfAvailable` alias on the same scope stays listed, so the required-alias check can see whether that alias is created. A scope closing a property cycle (`isPropertyCycle`) generates none of its dependencies, so `ScopeGenerator` does not count an alias of another of its type's aliases as received there (`cycleClosingAliasProperties`); otherwise the cycle-closing scope is ordered after the alias it renames, which is ordered after the cycle-closing scope, and a chain of aliases is emitted before what it renames. |
| `validateMockRootScopeForCycles` | Mock graph | Called after `@Received` promotion in `createMockRootScopeGenerator` | Walks the post-promotion scope to catch cycles that only surface once received deps are promoted to mock-root children — through an ancestor only. For a type listed only in `additionalMocksToGenerate`, whose tree `validatePropertiesAreFulfillable` checks for hidden properties alone, it is the only cycle check. |
| `childrenRequiringEachOther` | One scope's instantiated children | Called after `validateMockRootScopeForCycles` on the mock root, and by `validateChildrenDoNotRequireEachOther` | Cheap check, from the cached `collectReceivedProperties`, for children that require one another (C receives B while B's subtree receives C, directly, through any chain of aliases the scope declares, by requiring an `onlyIfAvailable` alias of B — `requiredAliasFulfilling` — or as `b: B?` fulfilled by the unwrapped `b: B` when a receiver requires it), which no ancestor stack shows. A child whose tree receives itself through an alias or unwrapped requires itself; one that receives its own property directly is left to the received walk and the ancestor check, which report it. An `onlyIfAvailable` alias the scope declares links its receiver to B as a required one does, because a receiver that requires it has it created after B (`requiredOnlyIfAvailableAliasProperties`), unless an enclosing scope provides its property (or unwrapped form) or the mock binds it: the receiver is then handed that property, as `isProvidedByEnclosingScope` has generation do. A mock root binds nothing for a property it declares itself, although promotion collects it into `allReceived`. When the chain closes on an alias of the first child, it ends with the child's own property (`@Instantiated a: A -> @Received renamedA: A -> @Received a: A`); each `onlyIfAvailable` alias in the chain adds a sentence suggesting `onlyIfAvailable: true` on the receive (`RequiredOnlyIfAvailableAlias.hint`), as the received walk's diagnostics through such an alias do. Property types do not matter: an `Instantiator` captures what its tree receives when it is created, so two sibling `Instantiator`s that receive each other cannot be ordered either. On a mock root it gates production's `validatePropertiesAreFulfillable` walk, which reports constant cycles. Running that walk on every mock root would add a received-dependency walk per node of every mock tree; on a real 250-mock-root app the check triggers it zero times. |
| `validateChildrenDoNotRequireEachOther` | Every scope of the production trees, then of each mock tree | After production's `validatePropertiesAreFulfillable` passes, and after the mock root's walk | Reports, as `aliasedDependenciesFulfillOneAnother` at the alias that closes the cycle, aliases of one scope that are fulfilled by one another (`aliasesFulfillingOneAnother`; the macro cannot see which `#if` clauses are active, so this is not a macro check), then, as `dependencyReceivedInSameChainItIsInstantiated` at the receiver found by `requiredReceiver`, children that `childrenRequiringEachOther` finds. It catches what the received walk misses: that walk follows a received property to the scope of its type, so it never follows an `Instantiator`, and no walk covers promoted scopes' trees. Running after the walk leaves every diagnostic the walk reports unchanged. `ChildrenRequiringEachOtherValidation` threads which `onlyIfAvailable` alias properties enclosing scopes provide (restricted to the properties of the module's `onlyIfAvailable` aliases, so nearly always empty) and keys `validatedScopes` by scope and that set, which makes each scope checked once per production pass and once across all mock roots for each such set; on a mock root, the result `childrenRequiringEachOther` computed for the gate is reported directly and only the children's trees are checked again. |
| `stackPropertiesReliedOnByWalkedProperty` | Received walk in `validatePropertiesAreFulfillable` | Filled as each received property's walk returns without throwing | Memo keyed by received property (not scope: another label of the same type can reach an error the first label's walk bailed before). Stores the properties on the stack the walk relied on (bails on cycles that aren't ours, plus those passed up from skipped walks); a later visit skips the property only when its stack contains all of them, so the first error in walk order is unchanged while paths into an unrelated cycle are not re-walked. |
| Soft `onlyIfAvailable` edges in `orderedPropertiesToGenerate` | Per scope, siblings | `ScopeGenerator.orderedPropertiesToGenerate` | A required receive of a sibling always orders it first; an `onlyIfAvailable` receive does only when that does not close a sibling cycle. A child's receive of a sibling is `onlyIfAvailable` only when every receiver in the child's subtree receives it `onlyIfAvailable` (`onlyIfAvailableUnwrappedReceivedProperties`). When it would, the receiver's subtree is generated with that sibling in `propertiesGeneratedLater` and gets `nil`, matching production's "not available" semantics. Not an error. An `onlyIfAvailable` alias that a receiver in the subtree requires, where no enclosing scope provides the alias's property (`requiredOnlyIfAvailableAliasProperties`, from each alias's `onlyIfAvailableAliasFulfillingProperty`), is built after its fulfilling sibling, as a required alias is, and `requiredAliasFulfillingProperties` carries that need up so ancestors build the fulfilling property before the branch; a sibling receiving the alias only if available then waits on it only when that does not close a cycle. An `onlyIfAvailable` alias that an enclosing scope also provides and that is never created (its fulfilling property is in `unavailableOptionalProperties`, `uncreatedAliasPropertyProvidedByEnclosingScope`) puts its own property in `requiredAliasFulfillingProperties` when a receiver below requires it, so the enclosing provider is built first, and hardened if it is itself an `onlyIfAvailable` alias; that set matches a sibling declared under the property's non-optional form too. These sets only order children: they never make a mock parameter required. The required edges are found by looking each child's received, unwrapped optional required, and alias-fulfilling properties up in a map from sibling property to index, or by testing each sibling when the child receives at least as many properties as there are siblings; either way the set is what testing every sibling pair gives, without the quadratic cost on a mock root's many children. The soft edges are still added by walking siblings in order, which the result depends on. |
| Required receives of aliases in `validatePropertiesAreFulfillable` | Per tree walk | Each node resolves its required receives to the nearest alias declaring them (`ReceivableAlias`); an `onlyIfAvailable` alias whose property an enclosing scope also provides, or a mock root binds (`boundProperties`), is skipped, and a property a scope provides shadows the aliases above it, except such a skipped alias whose fulfilling property is not provided, which is never created | A receiver built inside an alias's fulfilling property throws `dependencyReceivedInSameChainItIsInstantiated` (any alias). For an `onlyIfAvailable` alias whose fulfilling property is available, the fulfilling property is walked as the declaring scope's own required receive (what the walk does for a required alias), skipped when a root declares the alias, as for a required alias. One whose fulfilling property is unavailable is unfulfillable (`UnfulfillableProperty.uncreatedAlias`), reported only when not `cyclesOnly`: a mock takes the fulfilling property as an optional parameter. |
| `cycleClosingProperties` and builder function names | Per generated body, per root | `ScopeGenerator.init` (bottom-up), then `ScopeGenerator.builderFunctionNames(for:enclosingFunctionNames:)` for each body, in production `generateProperties` and mock `generateMockBodyBindings` alike | A cycle-closing scope (`isPropertyCycle`) declares no builder function: it refers by name to the enclosing `__safeDI_<label>` function built for its property (label and type). Swift resolves that name to the innermost function of that name in scope, and a local function is in scope throughout its body (a later sibling included), so a builder function for another property with the same name in any body between the two would shadow it. `cycleClosingProperties` carries each closer's property up to the scope it closes on; a body whose children carry one renames its function of that name `__safeDI_<label>_<built type's asIdentifier>` (underscores appended on collision), and `BuilderFunctionNames.enclosingFunctionNames` carries the names of referenced functions not named `__safeDI_<label>` (renamed, or sibling-disambiguated at a mock root) down to the closers. Bodies with no such clash keep their names, so their output is unchanged; the production cache key includes the names. |

Key consequence: if `throwIfInvalidCycle` accepts a cycle, every hop in it is non-constant (Instantiator/ErasedInstantiator-typed). Any code that assumes "a cycle node reached through a constant-typed property" is reasoning about something impossible.

**`LazilyInstantiated` is generated like an `Instantiator` and validated like a constant.** A `LazilyInstantiated` / `SendableLazilyInstantiated` property (`PropertyType.lazilyInstantiated`, `.sendableLazilyInstantiated`) is emitted as a builder function handed to its wrapper, but its instance is created at most once, so it cannot break a cycle. Every property that enters the cycle logic – in `validatePropertiesAreFulfillable` and in `validateMockRootScopeForCycles` – is first mapped through `Property.asValidatedForDependencyCycles`, which turns the wrapper into the constant it stands for. `throwIfInvalidCycle` is unchanged, and a tree is valid with the wrapper exactly when it is valid with that constant. Never classify these properties as lazy hops: generated code reads `.instance` for every by-value receiver, so a "fully lazy" cycle through them would recurse with no user code involved, creating a fresh wrapper at each level. `PropertyType.isConstant` is `false` for them, because mock generation uses it to mean "bound without a wrapper", so do not call `isConstant` on a property that has not been mapped. Cycle diagnostics show the constants; `lazilyInstantiatedDeclarations` threads the declared wrappers through validation so the message can name them.

### Mock generation specifics

- **Share logic between production and mock paths where possible.** Validation, scope population, and other shared concerns should live in common helpers rather than being duplicated between `createTypeDescriptionToScopeMapping` and `createMockTypeDescriptionToScopeMapping`. When adding validation to one path, check whether the other path needs it too.
- **Selected construction initializer.** `InstantiableVisitor.canonicalConstructionInitializer` is the single initializer SafeDI selects for construction (first init that fulfills the type's dependencies). `Instantiable.initializer` is populated from it, and mock generation emits against its signature. Validation that only matters for the path SafeDI uses (e.g., diagnosing `Self.*` in default expressions) should gate on this — walking every entry in `visitor.initializers` false-positives on unused overloads.
- **Two-layer mock return type** (extension-based `customMockName` only). When a `customMock` method returns a type different from `Self` (permitted via `fulfillingAdditionalTypes`), two concerns have to agree:
  1. **Inner closure type** (`MockParameterNode.builderClosureType`) — the type of the override closure stored in the parent's `SafeDIMockConfiguration`. Uses the property type so callers writing overrides match the receiving slot. Fixed in #251.
  2. **Outer `mock()` return type** — the generated `mock()` wrapper must return whatever the user's `customMock` returns. Fixed in #266.

  When touching extension-based types with `customMockName`, confirm both layers. `mockReturnTypeIsCompatible(withPropertyType: concreteInstantiable)` distinguishes genuine hand-written mocks from mockOnly-inherited ones.

  A mock that returns one of the type's additional types builds only properties `mockReturnTypeIsCompatible` accepts, so the type is built with its mock for some properties and with `init` for others, yet mocks generate one `SafeDIMockConfiguration` per concrete type, from the first node that needs it. `generateMockCode` therefore rejects (`validateConfigurationsAreBuiltOneWay`, a `SourceDiagnostic` at `mockDeclarationLocation`) a type whose first mock-built and first `init`-built nodes across all roots, in root order, both read a struct and differ in `MockParameterNode.configurationRequirements` (child properties, default parameters by label and type, builder parameter types). A node beneath a `cycleEdges` edge reads no overrides from its struct (its parent's struct has no field for it), so `collectConfigurationNodesByConstruction` leaves it out, and when the first node of a type is such a node built the other way, the struct is generated from the first node that reads it instead. A node that needs no struct is built from a closure typed by its property, so the shape #419 made compile, a mock that takes nothing, stays accepted, as do a mock with exactly `init`'s parameters and a mock that returns the concrete type. An extension's `instantiate(…)` plays `init`'s part: its default-valued parameters are struct fields (#452), so an `instantiate`-built node can read a struct and conflict too, and the diagnostic names the construction by `MockParameterNode.isExtensionBased`. Never emit a second struct for the same type. The struct's default-valued fields take their defaults from the hand-written mock's parameter of the same label and type (`DefaultParameter.defaultParameters(of:dependencies:)` on `mockInitializer`, matched to the dependencies of the concrete type's entry), whichever node the struct is generated from and even when no property is built with the mock in this module; `init`'s (or `instantiate(…)`'s) default applies only to a field the mock declares no default for, so `configurationRequirements` compares labels and types, never values. A node built with `init` beneath a `cycleEdges` edge, which no override reaches, elides its labeled defaults except those the mock also declares (same label and type), for each of which it passes `<Type>.SafeDIMockConfiguration().<label>` (`callSiteArgumentsForPrunedOverride(handWrittenMockDefaultParameters:)`, `MockContext.handWrittenMockDefaultParameters`), so the default is the mock's, evaluated in the struct, as for every other property of the type. Never inline the mock's default expression at the call site: it can name the type's static members or nested types, which resolve inside the struct (nested in the type's extension) but not in the mock root's extension.
- **Dependencies a hand-written mock is not passed.** A generated mock passes a dependency to the hand-written mock's argument with the same label (`resolveBuilderArguments`, `generateReturnArgumentList`). A mock merged in from a `mockOnly` declaration may have no argument for some of the production declaration's dependencies (`Instantiable.dependenciesNotPassed(to:)`, which never lists a `@Forwarded` one: it is an argument of the type's `Instantiator`). `createMockTypeDescriptionToScopeMapping` gives every property built with that mock a scope whose instantiable declares only the rest (`Scope.dependenciesLeftOut` records what was removed), so the dependency is not built, received, promoted, or offered as an override, and the mock declares no value it never uses. A dependency left out is built after all when the tree of a dependency the mock is passed receives its label, which is known only from the scopes, so the mapping is built again until nothing more is found. A mock that returns one of the type's additional types builds only properties of that type; the others are built with `init` from the complete scope, so one concrete type can have two scopes. The mock root's own instantiable is filtered to the dependencies of its scope, or a dependency its scope does not build would surface as a flat `mock()` parameter.
- **Hand-written `mock` vs. generated `mock()`.** A type whose `mock()` this module generates (`generateMock: true` or `additionalMocksToGenerate`) must not also have a hand-written method named `mock`, wherever it is declared. The macro enforces this within one declaration; `DependencyTreeGenerator.generateMockCode` enforces it across declarations and modules (a `mockOnly` pair) when it creates mock roots, by name only — no signature analysis, because a `mockOnly` extension's mock defaults every parameter, so even "distinguishable" pairs leave `Type.mock()` ambiguous. Do not work around such pairs at the call site (e.g. coerced function references). `Instantiable.mockDeclarationLocation` locates the diagnostic and must travel with `mockInitializer` through every merge.
- `MockParameterIdentifier` (propertyLabel + sourceType) is the key type for tracking parameters throughout mock gen
- `resolvedParameters` tracks which deps are already bound — prevents duplicate bindings across scopes
- `parameterLabelMap` maps identifiers to disambiguated parameter names
- A receiver whose label was disambiguated is rebound to the disambiguated name (`emitReceiverBindings`), found by its declared type and then its unwrapped type, since an `onlyIfAvailable` receive of `x: X?` is fulfilled by a disambiguated `x: X`. A receive the node passes `nil` (`MockParameterNode.unavailableProperties`) is not rebound: the name may not be declared yet.
- `TypeDescription.asIdentifier` produces identifier-safe disambiguation suffixes
- `TypeDescription.simplified` strips wrappers for cleaner suffixes, with fallback on collision
- Closure-typed defaults use `@escaping T = default` (not `@autoclosure`)
- `#SafeDIConfiguration` is always read from the current module only, never dependent modules
- **Received erased types.** `generateMockCode`'s `erasedToConcreteTypeMap` lets a mock root promote a received type no `@Instantiable` fulfills (e.g. `AnyService`) by building the concrete type an `@Instantiated(fulfilledByType:, erasedToConcreteExistential: true)` property of that exact property type names, in any module. It is keyed by the full property type, because a receiver matches by type, so an `ErasedInstantiator<(), AnyService>` erasure never counts toward `AnyService`. A type that erasures give more than one concrete type is left out of the map, and its receivers become required flat `mock()` parameters: picking one would depend on dictionary iteration order. Production never consults the map — production receivers get the value from an ancestor.
- **What a tree node provides.** One definition decides whether a scope provides a property to the scopes beneath it, so they do not receive it from its ancestors: `ScopeGenerator.provides(_:declaredProperties:forwardedProperties:)`. The scope declares or forwards the exact property, or, for an optional property, its unwrapped form, and a lazily instantiated property is declared (and forwarded) together with the by-value property of its instance (`declaredLazilyInstantiatedInstanceProperty`). `generateMockRootCode` drops a received property from its parameters and overrides only when its tree provides it by that definition, or when a promoted node's optional property is the receive's optional form, since a mock binds a node it builds to a non-optional value. A same-label node of any other type provides nothing: the receive stays a flat parameter or override, named apart from the root's tree bindings by label and type (`user_Draft`). Never match a received property to a tree node by label alone.
- **`onlyIfAvailable` overrides are keyed by label and type.** `generateMockRootCode` makes one `OnlyIfAvailableOverride` per `onlyIfAvailable` received property that no forwarded property or required receive covers and the tree does not provide (the mock root's own `x: X?` is handed a promoted `x: X`), even when a root tree node shares its label with another type: handing that node over is wrong (a promoted `editor: Editor` passed to its own `editor: Draft?`). `onlyIfAvailableOverrides(for:namesInMockScope:reservedNames:)` names the field and the binding by the bare label unless the label is a forwarded, default-valued, or uncovered-`@Instantiated` parameter, a root tree binding name, or another override's label; those are named by `identifierSafeNames` from the optional type (`user_Draft`). A flat received parameter or root alias that shares an override's name is still the one renamed, so mocks without such a clash are unchanged. A renamed override joins the flat renames in the receivers' disambiguation map, and `removingRenames(hiddenByDeclarationsOf:parameters:from:)` drops a rename wherever a nested scope declares or forwards that property (or its non-optional form), so such a receiver resolves to the closest declaration, as in production. The mock root's own renamed receive is rebound to its label at the root scope, unless the root binds that label already (to a node it promotes for another receiver); the root is then passed the renamed binding directly through the return's disambiguation map. Only promotion creates these clashes: when the mocked type's own tree hides the label, `HiddenReceivedProperty` rejects it before generation.
- When a mockOnly and a non-mockOnly coexist for the same type, `resolveSafeDIFulfilledTypes` merges them. The `(false, true)` and `(true, false)` branches handle opposite processing orders. Any cross-cutting concern (tracking sets, stale clearing) must be applied to both branches or order-dependent bugs will surface only on CI.

### Validation boundaries

Validation is split between the macro and the plugin based on available context:

- **Macro validation** (compile-time, local context only): The macro sees only the single decorated type or extension. Any error that can be determined from local context belongs here — missing `init`/`instantiate()`, invalid parameter combinations (`mockOnly + generateMock`), mock method signature issues, access control. These produce fix-its in the IDE.
- **Plugin warnings** (build-time, full context): `DependencyTreeGenerator.generateWarnings()` runs after the tree has generated. It reports a `LazilyInstantiated` property that is instantiated whenever the type declaring it is created, because a type created along with that one reads its instance by value. `InstantiationAnalysis` reads the scopes `rootScopeGenerators` built and validated (`validatedScopes`), is type-level, and is memoized per `Scope`: a type’s creation reads what its own required by-value receives and aliases read, plus what its constant children and its instantiated-with-owner lazily instantiated children read, minus every label the type declares. A read of a renamed wrapper's instance is followed through every renaming the type declares (`propertyRead(by:)`) back to the property it starts from. An `onlyIfAvailable` receive is deliberately never a reader: whether it reads the instance or is passed `nil` depends on sibling ordering, which only `ScopeGenerator` knows, and a warning about a dependency that is not instantiated would be worse than a missing one.
- **Plugin validation** (build-time, full context): The plugin (`SafeDITool generate`) sees all modules' types. Errors that require cross-type knowledge belong here — unfulfillable dependencies, received dependencies hidden by a closer ancestor's property with the same label (generated code passes dependencies by label), dependency cycles, a `@Sendable` builder function that would capture an `Instantiator`, `ErasedInstantiator`, or `LazilyInstantiated` declared outside it (`ScopeGenerator.nonSendableWrapperCaptures`, which walks the generator trees as code generation does, so a dependency passed `nil` is not reported; a receiver is reported once for each chain that reaches it, so the root a diagnostic names never depends on name order), duplicate type declarations, duplicate mock providers, a `mockOnly` hand-written `mock` on a type whose `mock()` is generated, an `additionalMocksToGenerate` entry of the selected configuration that names no `@Instantiable` type (`SafeDIConfiguration.validateAdditionalMocksToGenerate`, judged against the concrete types mock generation matches entries to; entries of configurations in inactive clauses are planned by `scan` and written without code, never judged).

### Serialization

`scan`'s cache (`<manifest>.safediScanCache`, a `CachedScannedModuleInfo`) and `.safedi` module info files (a `ModuleInfo`) are written in SafeDITool's own binary format, by hand rather than through `Codable` (`BinaryCoding.swift`, `BinaryCodableModels.swift`, `BinaryFile.swift`, all in `SafeDITool`, never `SafeDICore`). These files are **regenerated every build** — there is no cross-version deserialization. Do not add backward-compatibility decoding logic. A header (magic, format version, schema fingerprint, body length, checksum) rejects any other file: an unreadable scan cache is a cache miss and a fresh parse, and an unreadable `.safedi` is an error naming the file. The plugin-read `SafeDIToolManifest` stays JSON.

When a stored type changes, keep its coder in step:
- Each `BinarySchemaMember` writes its fields in initializer order and reads them back through that initializer, with each field's type choosing how it is read. A field whose type is not `BinaryCodable` fails to compile; so does an enum case the writer's exhaustive `switch` does not handle, and a tag the reader's `switch` does not handle.
- `binaryLayout` is what `BinaryFile.schemaFingerprint` covers: for a struct, each field it writes, in write order, as a `BinaryLayoutField` whose key path fixes the field's type, plus `unwrittenProperties`, the stored properties not written under their own name (`Dependency.asInstantiatedType`, `UnorderedEquatingCollection.set`, `Instantiable.instantiableTypes`, written as `concreteInstantiable` and `additionalInstantiables`, and `Property`'s stored hash, which is never written because hashing is seeded per process: a decoded `Property` goes through `Property.init(label:typeDescription:)`, which computes it again); for an enum, each tag's associated values, in declaration order, which is also the order written and read. A file written by a SafeDITool whose types write other fields, fields of other types, or the same fields in another order is therefore never read. `SafeDIToolBinaryFileTests` compares each struct's layout against `Mirror`, so a new stored property fails until it is listed, written, and read, and writes each field and associated value in turn with a value distinct from the rest (`BinarySample`), so a layout whose order or types differ from what the coder writes and reads fails too. A new stored type must join `BinaryFile.schemaMembers` and conform to `BinarySample` in the tests.
- A `BinaryReader` reads type descriptions nested at most `BinaryReader.maximumNestingDepth` (128) deep, so the writer notes a deeper one and `BinaryFile` refuses to write a file that holds it, naming the instantiable whose declaration names it (`BinaryFileWriteError`): `scan` then writes no cache, and `generate` fails rather than write a `.safedi` dependents cannot read. Do not describe the deep type itself in such an error: spelling a type recurses as deeply as it nests, which exhausts a task's stack in a debug build.
- `executeSafeDIToolTest` checks, for every fixture that runs scan, that the cache reads back exactly what scan wrote (`reflectedDescription`, which sees private fields and spellings `==` ignores, and compares strings by their UTF-8 bytes, because `String`'s `==` calls canonically equivalent spellings equal while Swift compares identifiers byte for byte; the writer's string table keys strings by those bytes for the same reason), so a field the coder drops fails whichever tests give it a value.
- `Codable` conformances stay: the `dump` subcommand prints either file as JSON through them.

## Determinism

Everything SafeDI produces must be identical on every run over the same inputs: generated code, diagnostics (their text, their order, and which one is reported first), fix-its, output file names, and the bytes of manifests, `.safedi` files and caches.

- Swift seeds hashing per process, and `Scope` hashes by object identity, so the order of a `Set` or `Dictionary` changes between runs — for scopes, even under a fixed hash seed. A task group's results arrive in completion order. None of these orders may reach output.
- When code chooses among candidates or emits a list, use declaration order, source path order, or a sorted order. Never use first-found or last-write-wins over an unordered collection.
- When a choice is genuinely ambiguous, report an error or apply a stated tie-break. Do not pick silently.
- Sorting only on the failure path is fine, and keeps the success path cheap: visit everything, and keep the candidate that sorts first only when there is something to report.
- A test of choice-making code needs enough candidates that a wrong order fails on nearly every run: twenty or more, or a permutation of six. A fixture with one candidate cannot catch this class of bug.

## Code Style

- **No abbreviations.** Use `dependency` not `dep`, `parameter` not `param`, `declaration` not `decl`. Everywhere: variables, functions, tests, comments, commits.
- **No `default` or `case _` in switch statements when all cases are knowable.** Enumerate all cases explicitly for compile-time safety.
- **Use `for ... where` for simple boolean filters** instead of `guard ... else { continue }` inside the loop body.
- **Use `guard` for early exits**, not `if condition { continue/return }`.
- **No early return from bare `if`.** If an `if` branch returns, the non-returning path must be in an explicit `else` clause. Never fall through after `if { return }`.
- **Test names follow `method_expectation_conditionUnderTest`** pattern (e.g., `mock_disambiguatesAllParameters_whenThreeChildrenShareSameLabel`).

## Testing Philosophy

- **TDD**: Write failing tests first, then fix.
- **One behavior per test method.** Each test verifies one behavior, but may use multiple assertions to fully validate it (e.g., checking both the count and content of output). Do not test unrelated behaviors in the same method.
- **No tautological tests.** Tests must exercise real code paths with real input. Never use test helpers that rewrite input before processing — the test content should be exactly what production code would see. Tests should verify input code → output code.
- **Test through the pipeline**, not direct model construction. Mock tests use `executeSafeDIToolTest` which parses real Swift source through the full visitor → generator pipeline.
- **Full `==` output comparison.** Never use `.contains()` for mock output. Compare the complete expected string.
- **Verify updated test expectations compile.** When updating expected output in generator tests, review the new expected code to confirm it would compile as valid Swift. Check that variable references resolve to the correct scope, types match (no optional where non-optional expected), and all referenced variables have bindings. Do not blindly update expected output to match actual — the actual output may itself be buggy.
- **Code generation tests should only test paths where the macro would not emit an error.** Test inputs must be valid under `@Instantiable` macro validation — every `mockOnly: true` type needs a `mock()` method (or `customMockName` method), mock method names on the same type must not collide (and a `mockOnly` mock paired with a generated mock must use `customMockName`, or generation errors), and production types need `init` or `instantiate()`.
- **Test titles must be observably verified.** When a test title says "prefers X over Y", the assertion must verify X is used — not just that the test doesn't crash. Add a parent type with `generateMock: true` that instantiates the type under test, and assert the full mock output shows X's method name.
- **If code can't be covered by a test with real parsed input, remove the code.** Dead branches and defensive fallbacks for structurally unreachable paths should not exist.
- **"Structurally unreachable" claims need a failing test.** Before removing defensive branches on the grounds that they can't be reached, write a test that tries to reach them with valid input. If the test can't be written, cite the specific rejection (file:line) and the input shape it rejects — a structural argument alone is not evidence. Structural arguments are easy to get wrong: e.g., `erasedToConcreteExistential: true` does NOT imply a constant property type, so "erased + cycle is rejected as constant" was wrong and cost a round trip when the branches had to be restored.
- **Test fixture file naming controls processing order.** Files parse in parallel, so completion order is random; `ModuleInfo(_:)` therefore orders a module's file scans by path, so its instantiables are in source file path order, keeping each file's top-to-bottom declaration order, and its imports and mock imports are sorted and deduplicated, so the `.safedi` file `generate` writes is the same bytes every run; upstream `.safedi` module info is already in that order, and `loadSafeDIModuleInfo` returns the dependent modules in the path order of their `.safedi` files, whatever order the caller lists them in or the parallel reads finish in, so the combined list `resolveSafeDIFulfilledTypes` sees is deterministic without a second sort. `executeSafeDIToolTest` names fixture files by extracting the type name from `@Instantiable` in the source content, so those names decide the order. When testing ordering-sensitive behavior (e.g., which of the two mockOnly merge branches runs), pick names that sort the way you need, and be aware that an `extension MyService` file falls back to `"File"`. A configuration-only snippet also falls back to `File.swift`, so it exercises `parseModule`'s fallback path; pass `swiftFileContentByFilePath` (e.g. `["SafeDIConfiguration.swift": …]`) to name a fixture explicitly when the file name matters.
- **Tests must not depend on where the checkout lives.** The suite runs from checkouts under `/Users`, under `/tmp` (reached as `/private/tmp`), and through other symbolic links. Build an expected path by the rule the contract under "File path spelling" gives its consumer — for example the project root as the test handed it to `scan`, made absolute, joined with the file's path inside it, for `additionalInputFiles` — never from `currentDirectoryPath` or `NSTemporaryDirectory()` compared with a normalized path, and test a symbolic link by creating one, as `SafeDIToolPathSpellingTests` does.

## Graph fuzzer

`SafeDIToolGraphFuzzerTests` (support code in `Tests/SafeDIToolTests/Helpers/GraphFuzzer.swift`) generates random graphs of `final class` `@Instantiable` types from a seed (a quarter of them also with one extension-based type whose `instantiate(…)` has default-valued parameters, decided after the rest of the graph so the other types of a seed's graph do not depend on it), with its own SplitMix64 generator so a seed names the same graph on every machine. The oracle runs each graph through `executeSafeDIToolTest` twice in the test process and accepts only two outcomes: the tool reports an error, or the fixture and the generated code compile (`swiftc -emit-object`, as `verifyGeneratedCodeCompiles` does). Generated code that does not compile, a fixture that does not compile on its own (a fuzzer defect), and two runs that differ are failures; a crash kills the test process. The two runs share the process's hash seed, so the long run also runs the `SafeDITool` executable in two processes for every 50th seed and compares them. Graphs compile together in one `swiftc` invocation, kept apart by a per-seed type-name prefix (`S<seed>_`). A graph's wrappers are all `Sendable`, all not, or – in a quarter of graphs – mixed at random, so a `Sendable` builder's subtree can receive a `LazilyInstantiated` declared outside it; a mixed graph's types are `@unchecked Sendable`, and its types that are not `@Instantiable` (the extended type among them) are `Sendable`, so receiving one by value inside a `@Sendable` builder function is never what fails. The oracle compiles in the Swift 6 language mode, where such a capture is an error rather than a warning. A type no root reaches sometimes receives `items` as a wrapper of the graph's `Value` type, which is not `@Instantiable` and which nothing provides, with the wrapper chosen for each receive, so a mock's tree receives one label as several wrappers its mock cannot build.

- **Every pull request.** `ci.yml` fuzzes the whole corpus, seeds `0..<corpusSeedCount`, on every pull request and push to main that changes more than Markdown. "Build and Test on Linux" packages its test bundle; "Fuzz Dependency Graphs on Linux" shards download it and run the long run over parts of the corpus, with batches running concurrently on every core; and "Check Graph Fuzzer Corpus on Linux" combines the shards' reports. A shard fails, naming the seeds in its summary, when a graph fails, a known issue goes stale, the run reports a problem with itself (a changed corpus, an invalid known-issue list, a harness error), the process crashes, or no graph runs. The combine job fails when a shard is missing or reported any of those, when the shards do not cover the corpus exactly once, or when the seeds the tool accepted differ from the pins (`corpusAcceptedSeedCount`, and `corpusAcceptedSeedsSum`, a `GraphFuzzerSeedSetSum` whose parts add up across shards). The oracle takes any error the tool reports as a valid rejection, so a tool change that makes it accept or reject other graphs must update those pins deliberately. The fixed seeds make every failure deterministic, so it belongs to the change that caused it. Measured: the shards add about 3¼ minutes after "Build and Test on Linux", cold or warm, since they run its bundle instead of building; each fuzzes 2500 seeds in about 2¼ minutes.
- **Ordinary suite.** Compiling generated code is what the fuzzer costs, so the ordinary suite keeps it to four small `swiftc` invocations and is what `swift test` gives a developer locally. A small fixed batch (`smokeSeeds`, five seeds) must have no failures, exercise every `GraphFuzzerFeature` (detected from the emitted source) in graphs the tool accepts, and include both accepted and rejected graphs. `compilationFailures_reportEachBrokenGraph_whenGeneratedCodeFailsToTypeCheckOrToLower` hands the oracle broken generated code. `fixture_matchesReferenceHash_forSmokeAndKnownIssueSeeds` pins the generator's output for those seeds, and the long run pins it for the whole corpus (`corpusFixtureHash`). Any generator change changes which graph every seed names, so update both hashes, the accepted-seed pins, and the smoke and known-issue seeds in the same change.
- **Run a seed.** `SAFEDI_GRAPH_FUZZER_STARTING_SEED=<seed> SAFEDI_GRAPH_FUZZER_ITERATIONS=<count> swift test --traits sourceBuild --filter SafeDIToolGraphFuzzerTests/longRun`, or `SAFEDI_GRAPH_FUZZER_ITERATIONS=corpus` for the whole corpus, which then checks the accepted-seed pins itself. Each failure's issue prints the fixture and the compiler output. `SAFEDI_GRAPH_FUZZER_REPORT=<path>` appends progress to a file. The run also checks that no corpus graph uses a label beginning with `__safeDI_`, the prefix of generated builder functions. To explore graphs beyond the corpus, dispatch `.github/workflows/graph-fuzzer.yml` with another starting seed and count.
- **Known issues.** `knownIssues` lists every corpus seed that fails today, grouped by shape. The corpus first found six shapes, and PR 404 made the tool reject one while PRs 407 and 408 fixed the generated code of the rest. It lists one shape that graphs mixing `Sendable` and non-`Sendable` wrappers found: a cycle through a `Sendable` builder and an `Instantiator`, whose cycle-closing scope refers to the enclosing builder function that is not `@Sendable`. (They also found a type below a `Sendable` builder that receives an `Instantiator` declared outside it, which the tool now rejects as it rejects a captured `LazilyInstantiated`.) Receiving `items` as several wrappers found two mock shapes: a mock wraps the instance it takes for a required `LazilyInstantiated<Value>?` by its bare label when an `Instantiator<Value>` receive of the label renamed that parameter, and a mock that promotes a received `Instantiator<A>?` reads it, still being declared, through an `onlyIfAvailable` alias of `Instantiator<A>` in its own tree. The mechanism's tests use known issues of their own, so they do not depend on the list. Each shape has a one-line reason and its signatures, the ways it is known to fail: compiler errors containing a given text, or a compiler crash in a generated mock (Swift 6.2 crashed on a mock shape that Swift 6.4 diagnosed). In the long run, a known seed that fails with one of its shape's signatures runs inside `withKnownIssue`; one that no longer fails is reported as stale, and one that fails any other way is reported as a new failure, so a fix's own pull request shows the entries it makes stale. Each seed is listed once, in increasing order within its shape, below `corpusSeedCount`, which `knownIssues_listEachSeedOnceInIncreasingOrder_belowCorpusSeedCount` checks. To add one, add the seed to its shape's list, or add a shape. Every failure the fuzzer finds becomes a hand-written regression test (reduced to the types that matter, with full `==` output) before its fix, and removing the entry is the last step of the fix.

## Common Pitfalls

- The input CSV written by plugins includes ALL swift files (target + dependencies). Mock scoping requires passing `mockScopedSwiftFiles` separately — only the target's own files.
- **Names generated code introduces are reserved** (`ReservedName`, the one place they are spelled: `ScopeGenerator` emits them from its constants, and the macro checks against them). Generated bodies declare builder functions `__safeDI_<label>` (and `@Sendable`-extracted locals `__safeDI_<label>__…`) next to the `let <label>` they build; the prefix keeps them out of the namespace of user labels, and it stays: any other scheme is more collision-prone and rewrites every generated file. Three kinds of exact name are reserved too, because generated code puts them in a scope with user names and cannot rename them: `safeDIOverrides` (the `mock()` parameter callers spell, which a mock parameter of that label redeclares and a body binding hides), `safeDIBuilder` (the property and initializer parameter of every `SafeDIMockConfiguration`, which a configured type's instantiated or default-parameter label redeclares, and the `if let safeDIBuilder` override binding in each construction expression, which therefore never shadows an argument), and the wrapper types generated code constructs by name (`Instantiator<T>(…)` and the other five, `Property.PropertyType.wrapperTypeName`), which a binding of that name hides. The macro tests pin that each is rejected; the evidence that each collides is in PR 410's description, because a fixture that declares one is macro-invalid and so cannot be a pipeline test. `SafeDIToolReservedNameTests` shows, with macro-valid fixtures, that the other names generated code introduces do not collide, which is what stops anyone reserving more than is needed: the `instance` closure parameter, and the generated members `SafeDIOverrides`, `SafeDIMockConfiguration`, `ForwardedProperties`, and `mock`, which a same-named property does not redeclare and which generated code never names where a binding could hide them. A new generated identifier in a scope with user names must be added to `ReservedName`, with such a test. The `@Instantiable` macro rejects every name it can see that generated code binds or refers to: property labels and `fulfilledByDependencyNamed:` names (`InstantiableVisitor`), the names of `instantiate(…)` parameters without a default value (also the visitor), and the argument labels of labeled, default-valued, non-dependency parameters of the construction initializer, `instantiate(…)` methods, and mock methods, which a mock root takes as `mock()` parameters (`validateReservedParameterLabels`, the same parameters `validateDefaultExpressions` checks). The property macros do not check, so nothing is reported twice. Only a prefixed parameter label gets a fix-it (rename the argument label to the label without the prefix, keep the parameter's name): renaming a dependency can change which dependency it fulfills or receives, because SafeDI matches by label, with no error, and an exactly reserved label has no evident replacement. `generate` does not check: SafeDI is upgraded per project at once, so every module's names have passed the macro.
- **Nested-type qualification.** `generate` qualifies each dependency's property type, `fulfilledByType:` type, and alias `ofType:` type with `TypeDescription.qualifyingInstantiatedType(within:amongInstantiableTypes:)`, and maps the initializer's arguments by the qualified property types. It qualifies only the type `asInstantiatedType` returns (`Instantiator<Service>?` → `Instantiator<Feature.Service>?`, `LazilyInstantiated<any Service>` → `LazilyInstantiated<any Feature.Service>`, so a by-value receiver of `any Service`, qualified the same way, still matches `lazilyInstantiatedInstanceType`), choosing the most qualified of `nestedOptions` that an `@Instantiable` fulfills, so a nested type wins over a top-level type of the same name, as the compiler resolves it. It also qualifies a hand-written mock's return type (`mockReturnType`, which the macro requires to be `Self` or the declaration's unqualified name, so a nested type's mock returns `Consumer`, not `Feature.Consumer`) and each of its arguments' types (`mockInitializer`), each type by itself rather than through the dependency map, because a `mockOnly` declaration has no dependencies and its mock is matched to those of the declaration it merges into. Doing it while normalizing, before `resolveSafeDIFulfilledTypes`, keeps `mockInitializer`, `mockReturnType` and `mockDeclarationLocation` together through both mockOnly merge branches. Unqualified, `mockReturnTypeIsCompatible` fails against `Feature.Consumer`, and the hand-written mock is silently skipped. Other generic arguments (an `ErasedInstantiator`'s forwarded properties) and non-instantiable types are not qualified. `replacingInstantiatedType` walks the same path through a type as `asInstantiatedType`: both read `TypeDescription.builtGeneric`, which names the built generic of each wrapper and whether its own instantiated type is read through it (`LazilyInstantiated`, whose generic may be `any Service`), so a new wrapper type is added there once.
- `Property.<` sort uses type as tiebreaker (not just label) for stable ordering.
- Extension-based `@Instantiable` types use `static func instantiate(...)` instead of `init(...)`. Their `@Instantiated` dependencies are constructed by the parent scope. Each `instantiate` parameter without a default value is a `@Received` dependency (`InstantiableVisitor`); a default-valued one is not a dependency, exactly as a default-valued non-dependency `init` parameter: the production call leaves it out, a generated mock offers it as an override, and the macro gives `instantiate` the checks an initializer's default-valued parameters get (`InstantiableVisitor.instantiateFunctions`).
- When a received dependency is promoted to root scope, the producer branch must capture the root-bound value — not reconstruct the type.
- `collectReceivedProperties` returns as `onlyIfAvailable` only properties that every receiver receives only if available. A property one receiver requires and another receives `onlyIfAvailable` is required — the collision is real, because an `onlyIfAvailable` alias's fulfilling property is non-optional (`@Received(fulfilledByDependencyNamed: "x", ofType: X.self, onlyIfAvailable: true)` yields `x: X`). Treating such a property as only-if-available skips its promotion, and the required receiver is handed `X?`. `createMockRootScopeGenerator` applies the same rule across the root's tree and the promoted scopes' trees, and `ScopeGenerator.onlyIfAvailableUnwrappedReceivedProperties` applies it to each subtree, so sibling ordering and mock parameters agree with promotion.
- A received constant whose type has `@Forwarded` properties is never promoted (`mockCanBuild`): the mock has no values to forward, so the dependency stays received and `mock()` takes it as a flat parameter, as production never `@Instantiated`s such a constant. The promotion loop and the worklist that collects promoted scopes' received properties both apply the check; a worklist that walked an unpromoted scope would promote its received dependencies into unused `SafeDIOverrides` entries.
- The mock root's own aliases are bound in the mock body's top-level scope, next to the dependencies promoted to the root and the `onlyIfAvailable` override bindings — production never puts them together, because it builds a type's aliases inside the scope that builds the type. `renamingAliases` binds an alias whose label one of those top-level bindings already uses as `<label>_<simplified type's asIdentifier>`, and the rename joins the tree's disambiguation map (receivers rebind it to the label) and the return-argument map. Only a binding redeclares: an alias whose label matches a flat parameter shadows it legally and keeps its name.
- A mock root can list the same property twice: promotion collects a promoted scope's received properties without subtracting what the root already instantiates. `orderedPropertiesToGenerate` emits only the first child for each property; emitting both produces two identically-labeled siblings, which sibling disambiguation renames to the same `label_Type_` name — an invalid redeclaration and a duplicate `SafeDIOverrides` field.
- Promoted dependencies are siblings at the mock root, and an `onlyIfAvailable` receive deep in one sibling's subtree resolves against another sibling by Swift lexical scope. Availability therefore depends on emission order: an `onlyIfAvailable` receiver may only see siblings emitted before its subtree. Any new emission path must thread `propertiesGeneratedLater` (production `generateCode`, mock `collectMockParameterTree`, both through `orderedChildren`) and pass `nil` for receives in it, or it will reference a `let` before its declaration. `orderedChildren` also adds each `onlyIfAvailable` alias a scope does not create, so a receiver of the alias gets `nil` rather than an undeclared name — but only when no enclosing scope provides the same property (`Scope.createScopeGenerator`'s `isProvidedByEnclosingScope`, mirroring production availability: created by an ancestor, exactly or in unwrapped form, and not on the property stack). Otherwise the receiver resolves to the enclosing property by Swift lexical scope, as it always has; an enclosing provider that is itself unavailable already arrives in `propertiesGeneratedLater`. A mock root counts every received property it binds as provided. Such an alias also does not count as generated before its later siblings (`propertiesAlreadyGeneratedAtThisScope`). A receiver that requires such an alias is never in that position: ordering builds the alias's fulfilling property first, and validation rejects the tree where that cannot work. Validation and ordering use the same enclosing-provider rule, so a required receive of an alias an enclosing scope also provides is left to resolve to that provider. A receiver built inside the ancestor it receives, or built as the property it receives (a type built by `xBuilder` receiving `xBuilder?`), gets `nil` too: `Scope.createScopeGenerator`'s `isPropertyUnavailable` checks the property stack including the scope's own property (`childPropertyStack`), in production and mock generation alike, unless the scope creates the property itself, which shadows the one being built. The test compile verifier compiles each test's fixtures and generated code to an object file (`-emit-object`, whole-module), so it reports SIL diagnostics as well as type errors: a nested function capturing a later local ("closure captures before it is declared") and `self` used before `self.init` in a production `init()` fail the test. `-typecheck` would miss both. It defines `DEBUG`, the test's conditions, and the module's `mockConditionalCompilation`, so generated mocks are compiled too. It also fails a test when the compiler reports a warning in a generated file, unless it reports the same warning in a fixture (generated code repeats the fixture's imports): a build that treats warnings as errors fails on a warning in generated code, which its author cannot edit.
- An `onlyIfAvailable` receive that is unavailable is passed `nil`, so it must not count as a provider below it. `validatePropertiesAreFulfillable` adds a scope's `onlyIfAvailable` received properties to its children's `receivableProperties` only when they are available by `isPropertyUnavailable`'s rule (in a mock, only a property still being built is unavailable); otherwise a required `x: X?` beneath one passes validation and the generated code names an undeclared or not-yet-declared `x`. A required receive that can resolve only to its non-optional form while that is still being built (`user: User?` under `user: User`, or in the type `user` builds) is a cycle, in production and mock validation alike, since no mock parameter can stand in for it: it is reported with the diagnostic the non-optional receive gets from the cycle walks, which match only exact properties — `dependencyReceivedInSameChainItIsInstantiated` when the receiving scope is built for the property, `throwIfInvalidCycle` for an ancestor — and only after those walks, so a graph they reject keeps its diagnostic. "Not @Instantiated or @Forwarded in chain" is only for a property nothing in the chain creates. A required `x: X?` that resolves to a sibling `x: X` — through an available `onlyIfAvailable` receive above it, or in a mock — orders that sibling first (`orderedPropertiesToGenerate` matches required received properties by their unwrapped form too), except beneath a scope that forwards `x: X`, which fulfills it, so that scope's `requiredReceivedProperties` leaves it out. Validation does not follow a required optional receive into its unwrapped type's scope, so a cycle through one (`x` requires the receiver's ancestor) is not reported and fails to compile, as it did before.
- A forwarded `x: X` fulfills every receive of `x: X?` beneath it, and an alias a type declares of its own forwarded property binds to that property, so neither is received from an ancestor. `ScopeGenerator.init` (`isReceivedFromAncestors` and the own-dependency loop), `DependencyTreeGenerator.walkReceivedProperties`, mock promotion, and the mock root's flat parameters all apply this, matching an optional receive by its unwrapped form. A check of the exact property alone promotes a second instance of the forwarded value, surfaces an unused `mock()` parameter, or passes `nil` for the forwarded value.
- `orderedPropertiesToGenerate` holds `onlyIfAvailable` receives unwrapped, so it matches them against siblings by the sibling's unwrapped property, and it orders every `onlyIfAvailable` alias after its fulfilling sibling before any other `onlyIfAvailable` receive. A sibling whose tree receives the alias only if available is then generated with the alias unavailable (it is passed `nil`), instead of the alias going uncreated while its own type is passed its undeclared name.
- `resolvedParameters` flows through sibling accumulation AND parent-to-child descent. Both paths must be consistent.
- **`#sourceLocation` paths are compared as strings.** The compiler groups every path a module uses – each source file as it was handed to the compiler, and each `#sourceLocation` file – by file name, and warns at a directive whose file name maps to more than one path (a build error under warnings as errors). It does not resolve relative paths or symbolic links. `AliasDeclarationReferences` emits a directive for an alias only when `generate` knows the compiler’s spelling: a plugin manifest’s `projectRoot` (`ProjectFilePaths.buildSystemPath(of:)`), unless the root is spelled differently from its `realpath(3)` resolution (`ProjectFilePaths.reportsResolvedProjectRoot`, from the one resolution `ProjectFilePaths` makes per run) – Xcode reports a package under `/tmp` as `/tmp/…` and hands the compiler `/private/tmp/…`, and a manifest from `scan` holds no second spelling that would reveal it – or `--compiler-receives-input-paths-unchanged` (passed by the Bazel rule). It still omits one whose file name another directive’s file or one of the module’s own files shares (`--mock-scoped-files` when `generate` scans for itself, the manifest’s `mockScopedFilePaths` otherwise, every input file under the flag), which covers a module file known under two spellings such as Xcode’s `/tmp/…` against the working directory’s `/private/tmp/…`. Every other alias gets a trailing `// Declared at <path>:<line>` comment with the path as the integration handed it (project-root-relative under a plugin). Tuist shares its build cache across machines, so nothing generated for a Tuist build, nor its `.safedi`, may hold an absolute path: its script hands `generate` `$SRCROOT`-relative paths and gets comments. Never spell a directive path with `NormalizedFilePath`, which drops a leading `/private` the compiler keeps. The examples treat warnings as errors and each declares an aliased `@Received` in its root module, so CI catches a wrong spelling.
- **File path spelling.** `Sources/SafeDICore/Utilities/FilePathSpelling.swift` is the only place a path is normalized or resolved, or made relative to a directory; the SafeDIGenerator plugin compiles it, and `OutputFileNaming.swift`, through symbolic links. `PathSpellingCallTests.sources_normalizeAndResolvePathsOnlyInFilePathSpelling` (in the plugin test target, which can strip comments and strings) fails if code under `Sources` or `Plugins` outside that file calls `standardizedFileURL`, `.standardized`, `standardize()`, `standardizingPath`, `resolvingSymlinksInPath`, `canonicalPathKey`, `destinationOfSymbolicLink`, or `realpath`; it does not detect a path made relative by hand. A comparison is sound only when both sides were spelled by one rule. `NormalizedFilePath` is absolute, without `.`/`..`/repeated `/`, and, on Apple platforms, without the `/private` Foundation drops from a path that names an existing file under `/private/tmp`, `/private/var`, or `/private/etc` (a path to no file keeps it); it resolves no other symbolic link. `ProjectFilePaths` resolves the reported project root once per run and spells each path inside the project under the resolved root as a `ProjectFilePath` (`projectFilePath(of:)`), which only it can create; every comparison that must agree — the "already an input" exclusion, mock-scoped and configuration-file matching, scan's stamps, and the cache-freshness check — takes `ProjectFilePath`s, because the inputs and `--mock-scoped-files` arrive under the root as the build system reported it while `additionalDirectoriesToInclude` is found from the working directory, which `getcwd(3)` reports resolved (and Foundation's directory enumerator on Apple platforms returns resolved paths). Never resolve per file: scan's freshness check is stat-only for speed. Each consumer gets one spelling. The manifest's file names (roots, mocks, configurations, `mockScopedFilePaths`) and scan's cache name a file relative to the resolved root when it lies inside it, else by its normalized path (`manifestPath(of:)`), and module info names files as the parse did (scan's cache names, or the CSV's spelling on a fresh parse). `projectRoot` is the reported root made absolute against the working directory, without a trailing `/`, and not normalized (`reportedProjectRoot`). What the build system, the compiler, or an IDE matches as a string — `additionalInputFiles`, which the plugin declares as build inputs, `#sourceLocation` paths, and the file paths `run()` prints in diagnostics — is that root joined with the file's path inside it (`buildSystemPath(of:)`), the spelling the build system already uses for the project's other files; a file outside the project gets its normalized path. Output paths keep the spelling the plugin passed. Scan's cache records `additionalDirectoriesToInclude` as scan found them, relative to the working directory, so `generate` finds the same files. `// Declared at` comments use the manifest name. SwiftPM and Xcode report resolved roots; reported links come from scripts and other integrations.
- `typeDescriptionToFulfillingInstantiableMap` is a dictionary — iterating `.values` has non-deterministic order. Any code that reduces, sorts, or builds state from `.values` must produce the same result regardless of iteration order. CI runs tests 5 times specifically to catch non-determinism.
- `Scope` hashes by object identity, so a `Set` of scopes iterates in an order that changes from run to run even under a fixed hash seed. Validation that throws at the first error must visit trees in a sorted order: `validatePropertiesAreFulfillable(typeDescriptionToScopeMap:cyclesOnly:)` visits roots, then the other types whose mocks are generated, each in type order; the mock roots in `generateMockCode` are visited in type order too.
- `Scope` hashes by object identity, so a `Set<Scope>` iterates in an order that changes from run to run even under a fixed hash seed. A loop over one may build state, but anything it reports — the first error, the first match — must be chosen by a deterministic key (as `createTypeDescriptionToScopeMapping` does for `@Forwarded` errors), not by which element the loop reached first.
- A memoized walk with a cycle sentinel must not cache a result that took nothing from a scope still being walked: that result is wrong from any other entry point, and which entry point walks first can follow set order. `collectReceivedProperties` keeps such results only until the scope they lack finishes its walk.
- `resolveSafeDIFulfilledTypes` can produce multiple map entries with the same `concreteInstantiable` under different keys (e.g., a merged entry under `MyService` and an unmerged entry under `ServiceProtocol`). These entries may have different mock info. The mock scope map uses scope-reuse by `concreteInstantiable` and a deterministic sort to handle this.
- `mockInitializer` on an `Instantiable` can be inherited from a mockOnly merge — it doesn't always mean the type declared its own mock. `generateMock` is never inherited. Use `mockReturnTypeIsCompatible(withPropertyType: concreteInstantiable)` to distinguish genuine hand-written mocks from inherited ones.
- **A `LazilyInstantiated` property declares two receivable properties.** `x: LazilyInstantiated<X>` can be received as itself or by value as `x: X`. Which declarations offer the by-value form is decided in one place: `Dependency.lazilyInstantiatedInstanceProperty` (and `Scope.PropertyToGenerate.lazilyInstantiatedInstanceProperty`, `ScopeGenerator.declaredLazilyInstantiatedInstanceProperty`). An `@Instantiated` property always does, because the generated wrapper is never optional. A `@Forwarded` or aliased one is bound with its declared type, so it does only when that type is not optional. A received one never does. `Scope.createdProperties` and `properties`, `ScopeGenerator.propertiesToDeclare` and its forwarded subtraction, sibling ordering, and mock promotion (`collectReceivedProperties`) all go through those accessors; do not re-derive the form from a `Property` alone. A by-value receiver is passed `x.instance`: `Scope.createScopeGenerator` threads `lazilyInstantiatedInstanceProperties` – the by-value properties that are in scope only through a wrapper – down to initializer argument lists, aliases, and mock nodes. A nearer declaration with the same label removes a property from that set, exactly as the nearer `let` shadows the wrapper in the generated Swift; an alias that keeps the label it retypes is looked up in the inherited set, because it is not in scope where its own value is read. `Scope.providedProperties`, validation’s `childReceivableProperties`, and the `propertiesToDeclare(in:)` and `forwardedProperties(in:)` helpers hold both forms too, and hidden-label validation accepts a by-value receive whose closest declaration of the label is the wrapper (`LabelDeclaration.lazilyInstantiatedInstanceProperty`). The instance never stands in for an `onlyIfAvailable` alias that is not created: reading it takes the wrapper, which the alias’s label hides. `Scope.createScopeGenerator`’s `isProvidedByEnclosingScope` and validation’s `isAliasPropertyProvidedByEnclosingScope` both leave it out, so a receiver below such an alias is passed `nil`, or is unfulfillable when it requires the property. A wrapper whose instance type is optional (`LazilyInstantiated<X?>`) offers no by-value form, wherever it is declared. `Instantiable.forwardedReceivableProperties` and `DependencyTreeGenerator.propertiesToDeclare(in:)` are the only places that list a type's forwarded and declared properties with their by-value forms; use them rather than filtering `dependencies` again. `orderedPropertiesToGenerate`'s `siblingIndexByProperty` maps each lazily instantiated sibling's by-value property to that sibling too, unless another sibling declares that property itself, and the pairwise fallback applies the same rule so that both paths build the same set.
- **Validation maps a wrapper to the constant with the same optionality.** `Property.asValidatedForDependencyCycles` turns `x: LazilyInstantiated<X>?` into `x: X?`, not `x: X`: an `onlyIfAvailable` receive of the wrapper inside the tree it builds must not equal the stack entry, or a tree the constant twin accepts (the receiver is passed `nil`) is rejected as a cycle. `TypeDescription.lazilyInstantiatedInstanceType` is the generic argument as spelled (`any Service`), which is what a by-value receiver must match; `asInstantiatedType` normalizes it for the scope lookup. Validation’s instantiation stacks (`propertyStack`, `instantiationStack`, `ReceivableAlias.declaringInstantiationStack`) hold the mapped constants, while `receivableProperties`, `createdProperties`, `providedProperties` and `boundProperties` hold properties as declared, plus the by-value form of each wrapper. Map a declared property before comparing it with a stack, and never before looking it up in one of those sets. Generation differs: `Scope.createScopeGenerator`’s `childPropertyStack` keeps the declared wrapper and adds its by-value form, so `isPropertyUnavailable` passes `nil` for an `onlyIfAvailable` receive of either form inside the tree the wrapper builds, in production and mock generation alike.
- **A mock's parameters never mention `LazilyInstantiated`.** Adopting it on an owner must not change the generated `mock()` of an unchanged receiver. `createMockRootScopeGenerator` treats a dependency received both ways as one: it promotes the wrapper once when any receiver requires either form, and skips the by-value form, also when the mock root declares the wrapper itself. A dependency the mock cannot build is classified in `generateMockRootCode` by its by-value form (`receivedParameterProperties`), so it is a `T` parameter or a `T?` override; the mock then binds `<label>_lazilyInstantiated` and passes that name to the types that receive the wrapper, and to aliases of it (`lazilyInstantiatedBindingNames`, threaded beside the flat-parameter rename map; the root's own receive goes through `returnDisambiguationMap`). `removingRenames(hiddenByDeclarationsOf:parameters:from:)` prunes `lazilyInstantiatedBindingNames` wherever it prunes that map, so a receiver below a nested scope that declares the wrapper – an `@Instantiated` child, an alias, or a builder's forwarded parameter – is passed that closest declaration, as in production. It is never rebound under the dependency's label: only one of the two bindings that share that label is renamed, so a rebinding inside a builder function would hide the instance parameter from the by-value receivers built there, which have no rename of their own to rebind. A by-value receiver of a wrapper renamed by sibling disambiguation rebinds the wrapper under its label, and an alias of its instance reads `.instance` from the renamed binding directly (`disambiguatedLazilyInstantiatedBinding`). `erasedToConcreteTypeMap` is keyed by both forms' types, and promotion falls back from a wrapper to the erasure of its instance (`concreteTypeErased(to:)`), so the wrapper is buildable whenever its instance is — also when the wrapper is optional, or when only a constant declares the erasure — and `mockReturnTypeIsCompatible` is asked about the instance type. `mockCanBuild` treats a lazily instantiated property as it does a constant: a mock has no values to forward, so it cannot lazily instantiate a type with `@Forwarded` properties, and `mock()` takes that dependency’s instance. A forwarded lazily instantiated property fulfills receives of itself, of its optional form, and of its instance beneath the mock root (`isFulfilledByForwardedProperty`), so neither `lazilyInstantiatedReceivedProperties` nor the by-value parameter set includes them; mapping such a receive to its by-value form first would lose that the wrapper is forwarded, and the mock would take a second value and ignore the forwarded one.
- **`TypeDescription ==`/`hash` ignore `any` at every depth.** `any P` equals `P`, `(any P)?` equals `P?`, `Instantiator<any P>` equals `Instantiator<P>`, and `(any P).Type` is treated as `P.Protocol` (not `P.Type`, which is `any P.Type`). `some P` stays distinct. Sets and dictionaries keyed by `TypeDescription` or `Property` therefore merge the two spellings, keeping whichever was inserted first, while `asSource`/`asIdentifier` keep each declaration's own spelling. `<` compares the spelling without `any` first, then the full spelling as a deterministic tiebreak, so two spellings of one type are equal under `==` but ordered under `<` (determinism was chosen over the Comparable contract). Any new map or set keyed by a type's spelling string (`asSource`) instead of `TypeDescription` must normalize `any` the same way, or it will miss matches `==` makes.
- **`erasedToConcreteExistential: true` is orthogonal to the property's `PropertyType`.** The flag controls whether SafeDI wraps the concrete in the property's existential type at the call site; it does not determine whether the property itself is constant or lazy. The four combinations:

  | Decorator + property | `Property.PropertyType` | `isConstant` | Can be in an accepted cycle? |
  |----------------------|-------------------------|--------------|------------------------------|
  | `@Instantiated let x: Concrete` | `.constant` | `true` | No — `throwIfInvalidCycle` rejects. |
  | `@Instantiated let x: Instantiator<T>` | `.instantiator` | `false` | Yes. |
  | `@Instantiated(erasedToConcreteExistential: true) let x: AnyProto` | `.constant` | `true` | No — `throwIfInvalidCycle` rejects. |
  | `@Instantiated(erasedToConcreteExistential: true) let x: ErasedInstantiator<A, AnyP>` | `.erasedInstantiator` | `false` | Yes. |

  When reasoning about whether an erased node can appear on a pruned back-edge, check `propertyType.isConstant` — don't short-circuit on the erasure flag.
