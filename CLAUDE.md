# SafeDI — Claude Code Guidelines

## Documentation

The core documentation is `Documentation/Manual.md`. Read it before making changes to understand SafeDI's API, macros, configuration options, and mock generation. The manual is the source of truth for user-facing behavior — if you change behavior, update the manual. Each topic has one home section, which the others link to rather than restate. Tests read parts of it by position. Two tests take the Swift code blocks of "Generating a dependency tree per module" up to the section's first line that begins with `#`, its first subheading: one expects exactly six, takes the first as its fixture, and compares the second with the code generated for that fixture and the third with the call a root in another module generates for it; the other compares the fifth and sixth with the code its own builder fixture generates. A third takes the two Swift code blocks of "Adopting SafeDI in a large codebase" and the first of "Calling a public mock from another module", each section up to its next heading, as the files of modules `Feed`, `App` and a module of another package, and compiles them. The graph fuzzer's known issues cite the first two shapes of the section's list of ways a seam differs from building its tree inline.

Always lint before pushing. Always run the full test suite after changes — don't rely on filtered runs alone.

**Run an integration before describing it.** A claim about what SwiftPM, Xcode, Bazel or Tuist passes the tool cites a captured build or a harness case.

### CI

- Every CI job runs on a Linux runner unless it genuinely needs macOS: Xcode or `xcodebuild`, an Apple platform SDK, the Xcode project plugin, or the macOS release binaries and their notarization. Linux runners scale; macOS runners are the scarce resource that pull requests and publishes queue on.
- A job on a `macos-*` runner states why in a comment in the workflow.
- New Linux jobs use the same container and setup as the existing Linux test job ("Build and Test on Linux" in `ci.yml`), except "Build Release SafeDITool on Linux", which runs `publish.yml`'s Linux build command in `publish.yml`'s container, because publishing 2.3.0-alpha-1 crashed Swift 6.3.3 compiling that release build of code every CI job had passed.
- A required check that a matrix job reports needs a Linux stand-in that reports the same names when a Markdown-only change skips the job. A skipped job satisfies a required check under its own name, but GitHub evaluates a job's `if:` before expanding its matrix, so a skipped matrix job reports only its unexpanded name. The stand-in takes the job's `name:` and matrix through YAML anchors, runs only when `changes` reports a Markdown-only pull request, and needs no container, since it only reports (as "xcodebuild-markdown-only" does for "xcodebuild").
- `Examples/Example Package Integration` has spaces in its name so that CI builds a package under a path with spaces. Markdown links to it spell the spaces `%20`, which GitHub renders but md-dead-link-check cannot decode, so `.github/md-dead-link-check.toml` excludes exactly those links and `.github/scripts/check-excluded-markdown-links.py`, a step of "Check Markdown links", checks that each still names a path that exists.

## Architecture

SafeDI is a compile-time dependency injection framework for Swift. It uses Swift macros (`@Instantiable`, `@Instantiated`, `@Received`, `@Forwarded`) to declare dependency graphs, then generates initializer code and mock methods via a build tool plugin.

### Key modules

| Module | Role |
|--------|------|
| `SafeDICore` | Models (`TypeDescription`, `Property`, `Instantiable`, `Dependency`), visitors (`FileVisitor`, `InstantiableVisitor`), generators (`ScopeGenerator`, `DependencyTreeGenerator`) |
| `SafeDIMacros` | Swift macro implementations (`@Instantiable`, `@Received`, etc.) |
| `SafeDITool` | CLI entry point with `scan`, `generate`, `query`, and `dump` subcommands — scans Swift files for `@Instantiable` types, builds dependency tree, generates output; `query` reports what one type needs |
| Plugins (`SafeDIGenerator`) | SPM build tool plugin that wires the tool into the build |

### Code generation flow

1. **Plugin** writes CSV of swift files → runs `SafeDITool scan` to build manifest → runs `SafeDITool generate` to produce code. The Bazel rule (`bazel/safedi.bzl`) and the Tuist plugin (`TuistPlugins/SafeDITuist`) run no `scan`: each runs `generate --combined-output --module-info-output` once per module, passing the `.safedi` files of the modules it lists as dependencies.
2. **`SafeDITool generate`** parses all files via `FileVisitor` → builds `DependencyTreeGenerator` → generates per-root code + mock code
3. **DependencyTreeGenerator** creates `ScopeGenerator` trees → each generates its code via `generatePropertyCode`. A seam (`@Instantiable(generateDependencyTree: true)`) is a root of its own module's generation (`generateSeamRootCode`, an initializer per access tier plus a guard enum) and a leaf of every other tree, which calls that initializer; see the seam paragraph under Common Pitfalls.
4. **Mock generation** (`generateMockCode`) creates `mock()` static methods with `@autoclosure @escaping` parameters, `T? = nil` subtree parameters, and `MockContext` for disambiguation

`generate` records, outside the visitors so scan's cache never holds it, the module and package that declare each `@Instantiable` (`Instantiable.moduleName`, `packageName`, and `mockDeclarationModuleName`/`mockDeclarationPackageName`, which travel with `mockInitializer` through `mergedWithMockProvider` and are cleared by `withoutHandWrittenMock`), and the module it generates code for (`ModuleInfo.moduleName`, `packageName`, `dependencyModuleNames`, the module's direct dependencies). `ModuleMembership` (`ModuleMembership.swift`) decides them, and `ModuleInfo.declared(by:dependingOn:)` applies them once the module, additional directories included, is assembled, before normalization and before `--module-info-output` is written; nil means unknown, never "this module". Three sources are independent. Own files: a run per module (Bazel, Tuist) passes `--module-name` and `--package-name`, which, when either is given, describe every input file (CSV and `--include`) and no other, so an `additionalDirectoriesToInclude` file has no module; otherwise a run with a manifest reads the target graph (below); otherwise own files have no module. Dependencies: the modules the `--dependent-module-info-file-path` files record (sorted, without duplicates; a file that records none adds nothing), whichever way own files were attributed, joined with the planned target's dependencies when the target graph was read; the files' names are the direct dependencies Bazel's `deps` and Tuist's `dependencies:` list and cannot drift from the files. A dependent `.safedi` carries what its producer recorded. The target graph, which a run with a manifest reads when neither option is given, is the file the SafeDIGenerator plugin writes beside its CSV (`<CSV path>.targets.json`, `PluginTargetGraph`, `Sources/SafeDITool/PluginTargetGraph.swift`, which the plugin compiles through a symbolic link, so the plugin encodes and the tool decodes one declaration; written by `writeTargetGraph`): the planned target and every target of `sourceModuleRecursiveDependencies` (the CSV's targets, the SafeDI path dependency and the leaked swift-syntax `VersionMarkerModules` included), each with SwiftPM's package identity (the `Package.id` of the package that declares it, found by walking `context.package` and its dependencies; `-package-name` carries it C99-mangled: `swift-syntax` becomes `swift_syntax`), its Swift files spelled by the same code that spells the CSV (`inputSwiftFilePaths(of:relativeTo:)`), and its direct dependencies' module names, sorted. The plugin API cannot tell whether a dependency target applies SafeDI's plugin (every target's `pluginGeneratedSources` is empty), so the graph does not say. Both of the plugin's `generate` forms read it: the manifest form (`<csv> --swift-manifest`), and the fallback form (`<csv> --output-directory … --mock-scoped-files …`, which scans for itself with the working directory as its project root and runs on every cold Swift Build build and every Xcode build of a package). A file belongs to the target that lists it, matched exactly: a fresh parse names a file by its CSV entry, and scan's cache names it relative to the package directory, or normalized outside it, which is how the plugin spells the entry, so no path is spelled again (targets that split one directory with `sources:`, or nest, are told apart, and the fallback form's working-directory root changes nothing); a file no target lists, or two targets list, has no module. The Xcode project plugin writes no graph and passes neither option, so membership is unknown there, as it is for a hand-written manifest: an Xcode project target is an ordinary run without a module name, by ruling, since the plugin cannot say which module declares a file `additionalDirectoriesToInclude` adds. `generate` drops every import of the module it generates code for (`module.moduleName`) from the imports it hands `DependencyTreeGenerator`, `additionalImportedModules` included, since a file read from a module above can import this one and the compiler warns at an import of the module it compiles (`#ModuleSelfImport`); the `.safedi` keeps them, since a module that reads it imports this one rightly. A run that names no module keeps them, so an Xcode project target that reads such a file gets that warning, as in 2.2.0: a foreseeable warning accepted by ruling for a shape no adopter has, which the Manual's "Limits of the Xcode project plugin" states. `query` records every declaration of an included module as that module's (`IncludedModule.name`, or the module name a `.safedi` records), with the package a `.safedi` records and none for a directory (`readIncludedModules()`); it checks no access, and its report still names modules as `IncludedModule` does. An `IncludedModule` name can be several path components (`Home/Sources`) and need not be the compiler's, so nothing may compare a module name `query` records with one a build recorded: the enforcement reads it only to group a query's declarations by module.

### Conditional compilation

`FileVisitor` takes a `ConditionalCompilationEvaluator`; `InstantiableVisitor` takes a `ConditionalCompilationHandling`, which the macro sets to `.scanAllClauses` (the compiler already picked the active clause) and `FileVisitor` sets to `.evaluate(evaluator)`. The evaluator treats the supplied `activeCompilationConditions` as complete (a bare condition not in the set is inactive), scans every clause of platform-conditioned blocks (`os()`, `canImport()`, …), and evaluates mock-only content (`SafeDIContentDetector`) as if `mockConditionalCompilation` were active. A guarded initializer counts as SafeDI content only when `ConstructionInitializerCandidates` finds some evaluation could select it for construction — it must be able to fulfill the dependencies (bounded below by those outside every `#if` and above by those in every clause) and must not follow an unguarded initializer that fulfills them in every evaluation; initializers in `@Instantiable` extensions never count. Each evaluation that decides a block guarding SafeDI content is a `ConditionalCompilationDecision`; `generate` prepends `ConditionalCompilationDecision.compileTimeAssertions` (`#if …` / `#error`) to every generated file so the compiler rejects code generated under a condition it evaluates differently. There is no "unknown condition" state and no error at generate time: the compile-time assertion is the fail-closed mechanism. `parseModule` first parses the module's own files (`configurationFilePaths`) named `SafeDIConfiguration.swift`, chosen by path alone, and walks them to find the module's `#SafeDIConfiguration`: `SafeDIContentDetector` classifies a configuration as production content, so its `#if` blocks never depend on `mockConditionalCompilation`. The configuration found there builds the module's evaluator, every other file is read, parsed, and walked once with it, and the `SafeDIConfiguration.swift` trees are walked again from memory only when the mock condition is not the default. When no `SafeDIConfiguration.swift` holds a configuration (the fallback), every file is walked with the supplied conditions and the default `DEBUG` mock condition, which finds a configuration elsewhere; if it names another mock condition, every file that declared SafeDI content is read, parsed, and walked again — no text heuristic picks a subset. `SafeDIConfiguration.placementWarning` reports exactly that case (configuration outside `SafeDIConfiguration.swift` with a non-default mock condition) as a `SourceDiagnostic` with `.warning` severity located at the invocation (`SafeDIConfiguration.declarationLocation`, which travels in module info and scan's cache). `SafeDIConfiguration.unreadableAdditionalDirectoryWarnings` likewise warns, at the invocation, about each `additionalDirectoriesToInclude` entry of the selected configuration from which no Swift file can be read (nothing at its path, or a non-Swift file; an empty directory is fine). It judges `ParsedModule.additionalDirectories`, the `AdditionalDirectory` entries paired with the path they resolved to: scan's cache stores scan's resolution (against scan's working directory, which its freshness check also enumerates), and a fresh parse uses this run's. It is a warning, not an error, because `scan` reads every configuration's directories in every clause and a directory may exist only on some platforms. `generate` returns warnings instead of throwing them and `run()` prints them; `scan` never warns, so a build warns once per `generate`. Every syntax tree but those of `SafeDIConfiguration.swift` files is released as soon as it is walked, so memory scales with concurrency rather than module size. A file whose text holds no marker is not parsed, but it can declare a plain type whose declaration SafeDI reads: one an extension extends (a namespace enum in a file of its own), whose access bounds what the extension declares, and one a declaration's dependencies or members mention (a protocol a seam's hole is typed by), whose access proves a generated parameter that names it. So the read that finds no marker also collects each name that follows `enum`, `struct`, `class`, `actor`, `protocol` or `typealias` and whitespace (`TypeDeclarationWords.namesFollowingKeywords`, a superset the parse decides: a word, or what a backtick and the closing backtick on its line enclose, a backticked keyword introducing nothing and a backtick without a closing one on its line an ordinary byte; a name behind a comment is left to the compiler), and `parseModule` then parses only the skipped files that may declare a type of a kept name (`keptPlainTypeNames(of:)`, every name spelled without backticks, as `GuardedPlainTypeNames.DeclaredType` and the keep filter spell theirs, since Swift reads `` `Token` `` and `Token` as one name): the outermost name of each type an extension that is or holds an `@Instantiable` extends (`OutputFileDeclarations.extendedTypeNames`, recorded in every clause, so those never depend on conditions), the outermost name of each `@Instantiable` type and every name between it and the type's own, in any clause (a namespace an extension declaring the type extends can itself be declared inside an extension, in a file that shows only the namespace's own name), and every name of each type a declaration's dependency (an alias's fulfilling property included, whose type a seam's generated initializer can take), initializer or `instantiate(…)` argument, or hand-written mock argument mentions (`mentionedTypeNames(of:)`: the outermost and each nested one, since a file that declares `Space.Inner.Config` inside `extension Space.Inner` shows only `Config` after a keyword, and the second is the type's in a mention a module's name qualifies), which come from the declarations these conditions select. Reading the skipped files a second time instead cost the lifelike benchmark's `scan` 20%. Such a file contributes its `plainTypeDeclarations` alone, in the clauses the conditions select, consults the conditions of the blocks that declare one in any clause, and is cached and stamped as every input is; `generate` parses such a file again, rather than skipping it, when a condition it consulted changed value. `parseModule` keeps only the plain declarations whose outermost type has a kept name, since no other bounds or proves anything, and `generate`'s refresh of a condition-sensitive file keeps those of the names scan kept (`CachedScannedModuleInfo.keptPlainTypeNames`, or `additionalKeptPlainTypeNames` for a file `additionalDirectoriesToInclude` adds); a refresh after which the module's declarations mention other names than scan's did, in either direction, parses the module afresh, since scan kept, and asserted, by the names it saw; the names of top-level `@Instantiable` types are left out of that comparison, since their own declarations prove them, except a name that a kept plain declaration under a block with decisions shares (`FileScan.keptGuardedPlainTypeNames`, such as a nested type of that name), since a mention of it decides whether that block's decisions are asserted. A run that writes a `.safedi` without a target graph (`--module-info-output` and no `--swift-manifest`: Bazel, Tuist) cannot tell which of the module's types the modules reading it will mention, so it also parses each skipped file whose text holds the word `package`, whatever names the search found in it (`TypeDeclarationWords.mayDeclareTypeOtherModulesCanName`: every declaration only another module of the package can name holds it, on itself, on a type enclosing it, or on the extension it is directly inside, wherever comments put it), and keeps every plain declaration whose `levelBeforeExtendedTypeCap` is `package` (`keepsTypeDeclarationsOtherModulesCanName`). It keeps no other `public` or `open` declaration: under decision 54 a type no declaration SafeDI reads declares counts as `public`, so the record proves nothing its absence would not, and only the comment that names such types (`UnreadTypeComment`) loses the name of a cross-module `public` type, which it then lists. `scan` and `generate` both go through it, and it rejects more than one configuration in scope. `scan` records its project root in the manifest so `generate` matches configuration files by the same resolved paths.

Build tool plugins cannot read the conditions the compiler receives while they plan the build, so the `SafeDIGenerator` plugin also passes `generate` the literal arguments `--build-setting-active-compilation-conditions=[${SWIFT_ACTIVE_COMPILATION_CONDITIONS}]` and `--build-setting-other-swift-flags=[${OTHER_SWIFT_FLAGS}]` (`BuildSettingCompilationConditions`). Swift Build (Xcode and SwiftPM's `swiftbuild` backend) expands them when the command runs, and Xcode project builds expand them through the shell script that runs the command; SwiftPM's native backend passes them through literally. When both arrive expanded, their conditions plus the `-D` flags in `OTHER_SWIFT_FLAGS` *replace* the command-line and manifest conditions (Xcode reports a package's debug-configuration defines to plugins in Release too, so a union would be wrong); otherwise `generate` falls back to them. The plugin passes its options to every SafeDITool it runs, including the prebuilt binary pinned in `Package.swift` (Swift 6.2 sometimes hands the plugin that one even with the `sourceBuild` trait) and the `.safedi/` download named by `safeDIVersion` in `Plugins/Shared.swift`, so it passes `generate` only options the pinned release accepts: an option the plugin is to pass ships in a release first, and the plugin passes it once that release is pinned. The `SafeDITuist` script passes the same two options, which its shell expands, when the pinned binary's `generate --help` advertises them, and `SWIFT_ACTIVE_COMPILATION_CONDITIONS` alone through `--active-compilation-conditions` otherwise. Which files exist — roots, `generateDependencyTree: true` types among the module's own files (`declaresDependencyTreeType`, named together with the root files in one `outputFileNames(forFilesAt:)` call, since uniqueness is per call), `generateMock: true` types, `additionalMocksToGenerate` entries, `#SafeDIConfiguration` files — is still decided by `scan` at planning time, but independently of any condition: `scan` plans an output for each such declaration in every clause of every `#if` block (`OutputFileDeclarations`, which `SafeDIContentDetector` collects during the walk of each block it already makes and `FileVisitor` adds for the clauses it scans), and treats the files in every configuration's `additionalDirectoriesToInclude` as inputs, parsing those only an inactive configuration lists solely to plan their roots. `generate` writes every planned output, without code (only the header and its compile-time assertions) when the declaration is inactive under its conditions, and generates the additional mocks only of the configuration it selects. It still rejects with a `ManifestError` a declaration whose file the manifest does not list (the manifest's `mockScopedFilePaths` lets it check mocks and configurations), which with superset planning means the file changed after `scan` or the manifest is hand-written. It also rejects a manifest in which two outputs name one file, which only a hand-written manifest can do: `scan` lists each additional mock once, however many times a configuration lists it. The `PluginScanner` fallback ignores `#if` and unions every configuration's arrays, so it plans the same superset. Because a cached file scan may declare a configuration in an inactive clause, `generate` parses the module afresh when a stale file declares a configuration in any clause, not just an active one; and when it parses `additionalDirectoriesToInclude` afresh it names those files as the manifest does, so their roots match its entries.

Because `generate` usually has more conditions than `scan` (always `SWIFT_PACKAGE`, `DEBUG` in debug), scan's cache keeps per-file results keyed by what each file consulted. `ScannableClauses.consultedConditions` records every bare condition a clause selection depended on (minus the mock condition for mock-only blocks, which is forced active); `FileVisitor` and `InstantiableVisitor` accumulate them only for blocks whose selection can change what they report: blocks with SafeDI content, blocks with syntax errors, and (separately, as `importOnlyConsultedCompilationConditions` with `importSegments` holding the block source) blocks that guard only imports. `FileVisitor` also collects `mockImports`: each block guarding only imports is selected again as a block guarding mock-only declarations is, and `importOnlyConsultedCompilationConditions` covers both selections. Generated mock files, `SafeDIMockConfiguration.swift`, the mock half of `--combined-output`, and module info carry `mockImports`; dependency-tree files keep `imports`, so `#if DEBUG import A #else import B #endif` still gives production code `import B`. `CachedScannedModuleInfo` (see Serialization) stores the files that consulted nothing as one `ModuleInfo` and the rest as `CachedFileScan`s; `generate` walks a file again only when a condition it consulted changed value, re-evaluates only its import segments when only those changed, and parses the whole module afresh when a walked-again file declared a configuration. Any new state a visitor collects from inside an `#if` block must either be covered by `consultedCompilationConditions` or be provably independent of the selection, or the cache becomes unsound. `OutputFileDeclarations.instantiableTypeNames`, and `ModuleInfo.instantiableTypeNamesInAnyClause`, which unions them and which scan's cache and `.safedi` carry, are such independent state: `SafeDIContentDetector` records the type of every `@Instantiable` in every clause of each block `FileVisitor` reaches, naming nested types from the enclosing type `FileVisitor` hands it, and `FileVisitor` adds the declarations outside every block, so any evaluator records the same names; `generate` uses them to tell an `additionalMocksToGenerate` entry that names a declaration these conditions leave inactive, whose file it writes without code, from one that names no type. `Instantiable.isInsideCompilerDecidedBlock` is independent state too: `FileVisitor` sets it from whether an enclosing `#if` block names a condition only the compiler decides (`IfConfigDeclSyntax.namesConditionOnlyTheCompilerDecides`, a call or a `$` flag, syntax alone), so any evaluator that reaches the declaration records the same value; module info carries it, and `foundDuplicateInstantiable` words its remedy for duplicates that all have it. Plain type declarations (`PlainTypeDeclaration`) follow the selection, as `@Instantiable` content does: `FileVisitor` records them from the clauses it scans – those the reported conditions select, and every clause of a platform-conditioned block – and evaluates a block that guards nothing else SafeDI reads but declares one in any clause as a production block (`SafeDIContentDetector` returns each type it declares in any clause, `PlainTypeNamesInAnyClause`: its own name, its outermost name and its level); a block that also guards mock-only declarations keeps the forced selection for its mock-only content, and for its plain declarations reads the mock condition as a platform condition: `FileVisitor.recordPlainTypeDeclarationsWhereMockConditionIsInactive` also records the plain declarations of the clauses `ConditionalCompilationEvaluator.whereMockConditionIsInactive` selects (the reported conditions without the mock condition, which it neither consults nor reports a decision about) that the forced selection does not, and of the blocks nested in them, where the walk passes each clause, so a type counts as the narrowest level either selection declares it at and a seam's generated initializer, which compiles where the condition is inactive, has one signature in debug and release. No decision about the mock condition is asserted; the decisions of that selection about other conditions are kept with the block's plain type names, and those of its nested plain-only blocks with theirs (`plainTypeDeclarationDecisions`), so they are consulted and asserted only when the module keeps such a declaration, as any plain-only block's are. A condition that joins the mock condition with another flag (`#if DEBUG || STAGING`) therefore follows that flag's reported value where the mock condition is inactive, unasserted, since a decision that mentions the mock condition is dropped; a misreport fails at the generated code with the compiler's access error. A type declared only where the mock condition is active counts as declared, as a type declared once does; another file's `#if !DEBUG` declaration of it is an ordinary block. Such a block's decisions and consulted conditions are not the file's: they travel with its declared types (`FileVisitor.plainTypeDeclarationDecisions`, `GuardedPlainTypeNames`) until the module decides what it keeps. `FileScan.keepingPlainTypeDeclarations(ofTypesWithin:keepingThoseOtherModulesPackageCanName:isInReadingModule:)` keeps the records whose outermost name the module keeps (`KeptPlainTypeNames.outermostTypeNames`), or, on the writer path, `package` ones; adds to `consultedCompilationConditions` the conditions of each block that declares such a type in any clause, which decide what the file contributes, and of no other; and asserts, among `conditionalCompilationDecisions`, the decisions of a block only where a read the access check makes can resolve to a declaration it holds (`KeptPlainTypeNames.assertsDecisions(about:isInReadingModule:)`): the type's own name is one a declaration mentions, or its outermost name is one an `@Instantiable` extension extends, and the reading module can name it – the module's own file's declaration, or another module's `package`-or-wider one, since another module's narrower declaration is that module's run to assert – or, on the writer path, it is `package`. So a `#if DEBUG struct` nothing mentions, a type nested in an `@Instantiable` type that nothing names, and a dependency's `internal` namesake of a type a mention names assert nothing. The cache stays sound because nothing a dropped block holds reaches the output, and the dropped set depends only on the kept names, which `generate` compares: scan's cache stores the module's kept names (`CachedScannedModuleInfo.keptPlainTypeNames`) and those of the files `additionalDirectoriesToInclude` adds (`additionalKeptPlainTypeNames`, the module's with theirs) apart, a module file walked again with `parseSwiftFilesDeclaringTypes` keeps by the module's and an added file by the union, as a fresh parse does, and `generate` parses afresh whenever the module's declarations, once walked again, mention other types than scan's did, in either direction, other than top-level `@Instantiable` types whose name no kept plain declaration under a block with decisions shares (`refreshed(_:from:…:mentionedByModuleInfo:…)`). A marker-free file walked again is parsed again too. `Instantiable.otherInitializers` is such state too: `InstantiableVisitor` collects a seam's initializers other than the canonical one from every clause of every member `#if` block (`initializersInEveryClause`), since the generated initializer is unconditional and one it would redeclare in any clause is a redeclaration, so scan's cache of it is sound whatever `generate`'s conditions.

### Type requirements query

`SafeDITool query needs <TypeName>… --include <directory>… --module-info <file>…` reports what each named type needs: the modules whose declarations build it and its dependencies in production, its `@Forwarded` parameters, the dependencies no `@Instantiable` declaration fulfills, and what its mock needs. It exists so a focused app can be assembled from exactly the modules one feature needs. It is in beta, and `--help` and the manual say so: it was built ahead of a live use, so its options, text, and JSON may change in any release as real projects adopt it, and the JSON's `formatVersion` is `0` until the format is stable; keep the beta note and the `0` until Dan removes them, and make `1` the first stable format then. `query` is a command group with `needs` as its one subcommand, so further questions (dependents, providers) join as subcommands rather than flags. `--include` is spelled as `generate`'s, and each directory is a module (`IncludedModule`) named after its last path component, or after as many trailing components as tell it apart from the other modules (`Home/Sources`), so a `Modules/<Name>/Sources` layout works without configuration; a Swift file included directly belongs to its directory's module. `--module-info` names `.safedi` files, each a module read with `ModuleInfoFile(moduleInfoData:)` as `generate` reads a dependent module's, its view ignored, since the query includes every module it reads (an unreadable or missing file is `QueryError.moduleInfoNotReadable`, with `BinaryFile.unreadableFileExplanation`), named after the module the file records; two files recording one module are `QueryError.moduleInfoNamedTwice`, and a directory named like a module a file records is `QueryError.modulesShareName`. `ParsedQueryModule` reads either kind: a directory's declarations are attributed to the files found under it, spelled under the `--include` argument; a module info file's to the paths it records (`sourceFilePath`, the declaration and mock declaration locations), spelled as stored, since the writing build's spelling is all the file has. `--active-compilation-conditions` applies only to directories, and `generatedIn` reads a module info file's `configurations`. `QueryCommand.swift` parses each directory module with `parseModule` (the module's own files are its configuration files; `additionalDirectoriesToInclude` is deliberately not followed, since every module is included), rejects a file in two modules, combines the modules' instantiables in module-name order, runs them through `normalizingInstantiableTypes(of:)` and `resolveSafeDIFulfilledTypes(instantiables:)` (`InstantiableResolution.swift`, shared with `generate`, so the query sees the types exactly as `generate` does), and reports the types named in order, each once, from that one read. `DependencyTreeGenerator.requirements(forTypeNamed:generatesMock:mockEmittingModule:)` builds a type's mock root exactly as `generateMockCode` builds the root of a type listed in `additionalMocksToGenerate` — the same `mockScopes(additionalMocksToGenerate:receivedPropertiesCache:)` setup and validation, with the type always listed, the same `mockRootInstantiable(for:scope:)` canonicalization, the same `createMockRoot(for:scope:…)` checks — and reads `ScopeGenerator.mockRootParameters(instantiable:)`, the classification `generateMockRootCode` emits; `generatesMock` only decides whether a hand-written method named `mock` is a collision (`createMockRoot`'s `GeneratedMockReason` is `nil` otherwise, and the root is built with that method). A mock root is a tree in which every dependency the type receives is built beside it, so the tool runs it twice: over the map with every hand-written mock removed (`Instantiable.withoutHandWrittenMock`, `mockOnly` entries dropped) for what the type needs in production, and over every declaration for what the mock needs. Which mock is decided in `query()` from the entry under the type's own key, the one `mockRootInstantiable` builds the root from (`TypeReport.Mock.Kind`): `generated` when a declaration sets `generateMock: true` or an included module's configuration lists the type (`generatedIn` names those modules, and the text says how a project without them generates the mock), `handWritten` when that entry has a hand-written mock, and `wouldBeGenerated` otherwise, so the focused app learns what the `mock()` it would generate needs — `mockOnly` modules included, which the production view strips. A hand-written method named `mock` on another entry for the type (a `mockOnly` extension whose mock returns a protocol, which `resolveSafeDIFulfilledTypes` merges only into that protocol's slot) is neither the root's mock nor compatible with generating one, so the report is `MockReport.none(NoMock)` rather than an error: the production part still prints. The mock view is computed before the production view, so a missing name is reported from the full map, with the types that fulfill that name and the types named most like it (`QueryError.noInstantiableNamed`). Neither part has a walk of its own, so the report cannot disagree with the generated mock; any new kind of `mock()` parameter must be added to `MockRootParameters`, not computed inside `generateMockRootCode` alone. The one input the query lacks is the generating module, which decides which flat parameters default to a hand-written mock (`flatParameterMockDefaults(in:emittingModule:)`): `query()` passes `requirements` the module in `generatedIn` as a `mockEmittingModule` (`ParsedQueryModule.emittingModule(attributionsByFilePath:)`: its name, its package only from a `.safedi` that records one, and the files attributed to it as its own) when exactly one module generates the mock, and `nil` otherwise, which takes every hand-written mock to be callable. So the report and the generated mock still disagree where the query cannot know the answer: a `package` mock of another module when either package is unknown (taken as callable, `packageUnverified`, as `generate` takes it), and a mock that several modules or no module generates. `QueryNeeds.md` states both; no other access shapes the report. The query runs exactly the checks on the path of one root, because it reaches them through `mockScopes` and `createMockRoot`, and none of the passes `generateMockCode` runs over every mock root together after its loop (`validateSendableBuildersCaptureNoNonSendableWrapper`, `validateConfigurationsAreBuiltOneWay`): those gate emitting the module's mocks and change nothing in the report, and `generate` reports them with fix-its, so a query that succeeds where `generate` would throw one of them is intended, not drift. The rule for a new check: one that decides whether a single root can be generated goes in `createMockRoot`, so both callers run it; one that needs every root at once goes after the loop, and is not added to the query. The one exception is the access check (`createMockRoot`'s `emittingModule`, see "Validation boundaries"): the query reports what a type needs whichever module assembles it, so it has no emitting module, passes none, and checks no access. The public result is `TypeRequirements` (declarations with the file that holds each, erasures with every declaration that makes them, forwarded and required parameters with reasons); `TypeReport` in the tool attributes each file to its module (`FileAttribution`: the module's name, its `--include` or `--module-info` paths as given, and the file spelled under the `--include` argument through `NormalizedFilePath.path(under:spelled:)`, or as a module info file records it) and formats the text; `QueryReport` wraps the types under `formatVersion`, and `QueryErrorReport` prints any error as JSON with a `kind` when `--json` is set. The JSON is a contract documented in `Documentation/QueryNeeds.md`: arrays are always present, optional keys are omitted, every reason has a `reasonKind` beside its sentence, and from `1` on `formatVersion` is raised when a key is renamed, removed, or changes meaning, so a change to the shape is a change to that page and, once the format is stable, a version bump. An erasure is attributed to a module already needed when one declares it, else to the first declaring module by name, with the rest listed beside it: any one declaration suffices, and the choice must not depend on set order.

### Mock generation flow

Mock generation follows this pipeline:

1. **`generateMockCode`** builds the mock scope map via `createMockTypeDescriptionToScopeMapping` (includes ALL types, not just reachable from roots)
2. For each type with `generateMock: true`, **`createMockRootScopeGenerator`** promotes `@Received` dependencies to root-level children (except those `mockCanBuild` rejects), in the order the mock's tree first receives them (`inOrderTheMockTreeFirstReceives`), and validates for cycles
3. **`ScopeGenerator.generateMockRootCode`** builds the mock method:
   - Calls `collectMockParameterTree` to walk the dependency tree and build `MockParameterNode` trees
   - Collects flat parameters: `@Forwarded` deps, uncovered `@Instantiated` deps, `@Received` deps not in the tree
   - Generates `SafeDIOverrides` struct (if tree children exist) and the `mock()` method signature and body

The production code path (`generatePropertyCode` with `.dependencyTree`) and mock path (`.mock`) share the same `ScopeGenerator` but diverge at `generatePropertyCode`. Mock fields (`mockInitializer`, `mockReturnType`, `customMockName`) are only accessed in mock code paths — never in production paths.

### Cycle mechanisms

Multiple cycle-related mechanisms coexist — keep them distinct:

| Name | Scope | Set by / when | Role |
|------|-------|---------------|------|
| `isPropertyCycle` on a scope/node | Per-root, syntactic | `Scope.createScopeGenerator` when a property, as cycle validation sees it, repeats an entry of the ancestor stack built for the same concrete type | Terminates infinite descent during a single root's walk; differs between roots for the same underlying cycle. |
| `cycleEdges` (set of `CycleEdge`) | Global | `DependencyTreeGenerator.computeCycleEdges`, alphabetical-DFS feedback arc set | Chooses a single back-edge per cycle consistently across all roots — required because shared `SafeDIMockConfiguration` structs must have one shape. Consumed by struct generation AND override-path navigation in mock bodies. Each root returns the nodes of the types its tree configures (`collectConfigurationTypes`); `generateMockCode` keeps the first root's node for each type, in alphabetical root order, and only then generates that struct (`ScopeGenerator.generateConfigurationStruct`), so no root generates a struct that is thrown away. |
| `throwIfInvalidCycle` | Shared classifier | Called from `validatePropertiesAreFulfillable` (production, and a mock root whose children require one another) and `validateMockRootScopeForCycles` (mock) | Judges the cycle, not the property that closes it: rejects a cycle closed by a receive, whatever its hops, and a cycle with no deferred hop (an instantiator kind on the segment from the closing property to the stack entry it repeats; a lazy wrapper, validated as its constant, is never one), and accepts every other cycle wherever a tree enters it, so production and mocks agree (those cycles compile as long as pruning breaks the config-struct recursion). Its callers pass the segment as `propertiesInCycle`; the received-property walk always passes a closing receive, so its outcome never reads the hops. A cycle repeats a stack entry built for the same concrete type (two `fulfilledByType:` declarations of one label and protocol are two nodes), and a receive is of a property still being built only when the nearest providing declaration of its label on the path is the entry it matched (`indexOfEntryClosedOn`, `isFulfilledByNearerDeclaration`): a declaration between fulfills it, as the generated code passes it – a cycle-closing declaration, one built for another concrete type, or a property a type between forwards (`A -> Instantiator<B> -> C`, where `B` forwards `a: A` and `C` receives it, hands `C` the forwarded `a`). The walk of received properties from an `onlyIfAvailable` alias's declaring scope has no nearest declarations of that scope, so there every receive of a property being built is judged as being built. Neither stack walk considers an `onlyIfAvailable` dependency, `@Received(onlyIfAvailable: true)` or an `onlyIfAvailable` alias (`Dependency.canCloseDependencyCycle`): generation passes it `nil` while the property it receives is built (`NearestDeclarations.binding(of:)`, which finds a receive unavailable when a form of its label it reads is being built between the label's nearest declaration and the receiver), whatever kind of property that is — constant, `LazilyInstantiated`, or `Instantiator` — so `a: A?` under the `a: A?` it is built inside gets `nil` as it does under `a: A`, and so does an alias of `a` only if available. Both walks classify the dependency that closes a cycle with `closingReceive(of:in:)`: a required `@Received` dependency is a receive, and so is a required alias, which receives its fulfilling property — unless its scope creates that property, which the alias then refers to. Do not use `Dependency.Source.isReceived` for this; it is `false` for aliases. The classification decides every closer: an instantiation closing a cycle with a deferred hop is accepted whatever its own kind, a receive never is, and a required alias fulfilled by a `LazilyInstantiated` is a receive of the constant it stands for, rejected exactly as its constant twin is. Production's received walk agrees by another route: `Scope.requiredReceivedProperties` lists a required alias's fulfilling property, with `aliasProperty` so the error names the alias, except one the alias's scope always creates (`unconditionallyCreatedProperties`: instantiated or forwarded), which requires nothing of an ancestor. No alias renames another alias of its own declaration (`RejectedRename`, below), so nothing on this path follows a chain of aliases within one scope. |
| `validateMockRootScopeForCycles` | Mock graph | Called after `@Received` promotion in `createMockRootScopeGenerator` | Walks the post-promotion scope to catch cycles that only surface once received deps are promoted to mock-root children — through an ancestor only. For a type listed only in `additionalMocksToGenerate`, whose tree `validatePropertiesAreFulfillable` checks for hidden properties alone, it is the only cycle check. A promoted received optional property is built as its non-optional value, so a received or aliased dependency matches either form. An `onlyIfAvailable` dependency closes no cycle: an alias of a property still being built is bound to `nil`, which a receive of it reads. |
| `childrenRequiringEachOther` | One scope's instantiated children | Called after `validateMockRootScopeForCycles` on the mock root, and by `validateChildrenDoNotRequireEachOther` | Cheap check, from the cached `collectReceivedProperties`, for children that require one another (C receives B while B's subtree receives C, directly, through an alias the scope declares, as `b: B?` fulfilled by the unwrapped `b: B`, or through an `onlyIfAvailable` alias in the subtree that a receiver requires and that is bound from B), which no ancestor stack shows. An `onlyIfAvailable` alias is a `let` of its label bound from the nearest declaration of its fulfilling property's label, so a receiver that requires it requires that declaration built first: `ReceivedProperties.requiredAliasFulfillingProperties` holds the fulfilling properties a subtree requires through such aliases, which `ScopeDeclarations.requiredAliasFulfillingProperties(childRequiredReceived:childRequiredAliasFulfillingProperties:)` – shared by the walk's `finished` and `requiredReceiver` – collects in one pass (an alias the scope declares is required when a child's tree requires its property, or requires a fulfilling property of the alias's label that the alias provides a form of; no alias of a scope renames another) and prunes by the labels the scope declares or forwards, never by `provides`: the requirement stops at the nearest declaration of its label, whatever form that has. A child whose tree receives itself through an alias or unwrapped requires itself; one that receives its own property directly is left to the received walk and the ancestor check, which report it. A mock root binds nothing for a property it declares itself, although promotion collects it into `allReceived`. When the chain closes on an alias of the first child, it ends with the child's own property (`@Instantiated a: A -> @Received renamedA: A -> @Received a: A`); each `onlyIfAvailable` alias in the chain adds a sentence suggesting `onlyIfAvailable: true` on the receive (`RequiredOnlyIfAvailableAlias.hint`), as the received walk's diagnostics through such an alias do. On a mock root it gates production's `validatePropertiesAreFulfillable` walk, which reports constant cycles. Running that walk on every mock root would add a received-dependency walk per node of every mock tree; on a real 250-mock-root app the check triggers it zero times. |
| `validateChildrenDoNotRequireEachOther` | Every scope of the production trees, then of each mock tree | After production's `validatePropertiesAreFulfillable` passes, and after the mock root's walk | Reports, as `dependencyReceivedInSameChainItIsInstantiated` at the receiver found by `requiredReceiver` (the first dependency in the last child's tree that requires the closing property; a required `onlyIfAvailable` alias bound from it – one `ScopeDeclarations.requiredOnlyIfAvailableAliases(childRequiredReceived:childRequiredAliasFulfillingProperties:)` lists – is followed to the receiver that requires the alias, whose hint the diagnostic then carries, for each alias in the chain: the children's trees are searched for the alias's property; the search stops beneath a scope that provides the searched property, as the walk prunes, so it always finds a receiver), children that `childrenRequiringEachOther` finds. It catches what the received walk misses: that walk follows a received property to the scope of its type, so it never follows an `Instantiator`, and no walk covers promoted scopes' trees. Running after the walk leaves every diagnostic the walk reports unchanged. `ChildrenRequiringEachOtherValidation.validatedScopes` makes each scope checked once per production pass and once across all mock roots, since which children of a scope require one another depends on the scope's tree alone; on a mock root, the result `childrenRequiringEachOther` computed for the gate is reported directly and only the children's trees are checked again. |
| `stackPropertiesReliedOnByWalkedProperty` | Received walk in `validatePropertiesAreFulfillable` | Filled as each received property's walk returns without throwing | Memo keyed by received property (not scope: another label of the same type can reach an error the first label's walk bailed before). Stores the properties on the stack the walk relied on (bails on cycles that aren't ours, plus those passed up from skipped walks); a later visit skips the property only when its stack contains all of them, so the first error in walk order is unchanged while paths into an unrelated cycle are not re-walked. |
| `isHanded` (handed values) | Received walk in `validatePropertiesAreFulfillable`, per tree | Asked before the walk descends into a received property's scope | The walk does not follow a received property the tree is handed: one no scope in the map instantiates or renames another property to (`propertiesBuiltByAScope`, built lazily), which in a mock's tree the mock root also does not promote, because the root forwards it or `mockCanBuild` says no. Such a value comes from outside the tree (a `@Forwarded` value or a `mock()` parameter), so its type's receives are no part of the tree; a cycle through them is reported where a tree builds that type. Mocks and production follow this one rule (production's map holding only reachable types was a type-level form of it). Which branch applies is the tree's, not the pass's: the validation of mocks (`cyclesOnly`) also walks every production root's tree, and `ValidatedRootScope.isMock` is `false` for every root of the dependency tree, which receives nothing, so its mock (if any) promotes nothing and builds its production tree; the mock branch is for the trees of non-root mocked types only. Over-approximates in a mock: a property forwarded inside the tree whose type the mock could build is followed, since the pre-promotion validation does not know whether the mock promotes it. |

| `buildsInSendableFunction` on a `ScopeGenerator` | Per scope, from its subtree | `ScopeGenerator.init`, from `cycleClosedOnDeclarationsReferencedFromSendableFunction` | A builder function is `@Sendable` when its property is a `Sendable` wrapper, or when a cycle-closing scope refers to it from inside a `@Sendable` builder function that does not enclose it (A → `SendableInstantiator<B>` → B → `Instantiator<A>`): that function captures it. | `cycleClosedOnDeclarations` and builder function names | Per generated body, per root | `ScopeGenerator.init` (bottom-up), then `ScopeGenerator.builderFunctionNames(for:enclosingFunctionNames:)` for each body, in production `generateProperties` and mock `generateMockBodyBindings` alike | A cycle-closing scope of any kind (`isPropertyCycle`: constant, lazy wrapper or instantiator) declares no builder function: it refers by name to the enclosing `__safeDI_<label>` function built for the declaration it repeats. Swift resolves that name to the innermost function of that name in scope, and a local function is in scope throughout its body (a later sibling included), so a builder function with the same name in any body between the two would shadow it: one for another property of the label, or one for a declaration of the same property built for another concrete type. `cycleClosedOnDeclarations` carries each closer's `closedOnDeclaration` – the declaration it repeats (`ScopeGenerator.BuiltDeclaration`: the property, the wrapper for a constant that repeats a lazy declaration's instance, and the concrete type it is built for) – up to the scope it closes on, which claims it only where its own `declaration` (property and concrete type) equals it; a body whose children carry one renames its function of that name `__safeDI_<label>_<built type's asIdentifier>` (underscores appended on collision), and `BuilderFunctionNames.enclosingFunctionNames` carries the names of referenced functions not named `__safeDI_<label>` (renamed, or sibling-disambiguated at a mock root) down to the closers. Bodies with no such clash keep their names, so their output is unchanged; the production cache key includes the names. |

Key consequence: in an accepted cycle the closing property is an instantiation (never a receive) and some hop is deferred (Instantiator/ErasedInstantiator-typed); the other hops, the closing property among them, may be constants or lazy wrappers (`a: A` -> `b: B` -> `cBuilder: Instantiator<C>` -> `a` is accepted, closed by the constant `a`). A constant or lazy closer calls the enclosing builder function with its cycle parameters (`let a: A = __safeDI_a(…)`, `LazilyInstantiated<A>(__safeDI_a)`) exactly as an instantiator closer hands it to its wrapper, and `computeCycleEdges` may prune an edge a constant closes, which the pruned node's override path handles as it does for an instantiator (one configuration shape whichever root enters the cycle). Generation finds its cycle-closing scope exactly where validation finds the cycle: by the mapped property and the concrete type (`Scope.createScopeGenerator`'s `concreteTypeStack`), so a constant and a lazy wrapper of one label close on each other in either order, and `closedOnDeclaration` names the declaration repeated – the wrapper when the match was its instance entry, with the concrete type – for every lookup keyed by it (`cycleClosedOnDeclarations`, `cycleClosingRedeclaredLabels`, `BuilderFunctionNames.enclosingFunctionNames`, the cycle parameter contexts, the tier omission passes). A key of the property alone let a declaration of the same property built for another type between the closer and the declaration it repeats claim the reference, and the closer called that nearer function. A mock node reads no override of its own where its type, as instantiated and as concrete type, repeats an ancestor's (`MockParameterNode.cycleNodeKey`). Which property closes a cycle depends on where the walk starts: a tree that reaches a cycle from another root can close it on an earlier lazy property than a walk from the cycle's own root, which is why a filler walks each foreign seam with holes from its root (below).

**`LazilyInstantiated` is generated like an `Instantiator` and validated like a constant.** A `LazilyInstantiated` / `SendableLazilyInstantiated` property (`PropertyType.lazilyInstantiated`, `.sendableLazilyInstantiated`) is emitted as a builder function handed to its wrapper, but its instance is created at most once, so it cannot break a cycle. Every property that enters the cycle logic – in `validatePropertiesAreFulfillable` and in `validateMockRootScopeForCycles` – is first mapped through `Property.asValidatedForDependencyCycles`, which turns the wrapper into the constant it stands for. `throwIfInvalidCycle` sees it as a constant hop, and a tree is valid with the wrapper exactly when it is valid with that constant. Never classify these properties as lazy hops: generated code reads `.instance` for every by-value receiver, so a "fully lazy" cycle through them would recurse with no user code involved, creating a fresh wrapper at each level. `PropertyType.isConstant` is `false` for them, because mock generation uses it to mean "bound without a wrapper", so do not call `isConstant` on a property that has not been mapped. Cycle diagnostics show the constants; `lazilyInstantiatedDeclarations` threads the declared wrappers through validation so the message can name them.

### Mock generation specifics

- **Share logic between production and mock paths where possible.** Validation, scope population, and other shared concerns should live in common helpers rather than being duplicated between `createTypeDescriptionToScopeMapping` and `createMockTypeDescriptionToScopeMapping`. When adding validation to one path, check whether the other path needs it too.
- **Selected construction initializer.** `InstantiableVisitor.canonicalConstructionInitializer` is the single initializer SafeDI selects for construction (first init that fulfills the type's dependencies). `Instantiable.initializer` is populated from it, and mock generation emits against its signature. Validation that only matters for the path SafeDI uses (e.g., diagnosing `Self.*` in default expressions) should gate on this — walking every entry in `visitor.initializers` false-positives on unused overloads.
- **Two-layer mock return type** (extension-based `customMockName` only). When a `customMock` method returns a type different from `Self` (permitted via `fulfillingAdditionalTypes`), two concerns have to agree:
  1. **Inner closure type** (`MockParameterNode.builderClosureType`) — the type of the override closure stored in the parent's `SafeDIMockConfiguration`. Uses the property type so callers writing overrides match the receiving slot. Fixed in #251.
  2. **Outer `mock()` return type** — the generated `mock()` wrapper must return whatever the user's `customMock` returns. Fixed in #266.

  When touching extension-based types with `customMockName`, confirm both layers. `mockReturnTypeIsCompatible(withPropertyType: concreteInstantiable)` distinguishes genuine hand-written mocks from mockOnly-inherited ones.

  A mock that returns one of the type's additional types builds only properties `mockReturnTypeIsCompatible` accepts, so the type is built with its mock for some properties and with `init` for others, yet mocks generate one `SafeDIMockConfiguration` per concrete type, from the first node that needs it. `generateMockCode` therefore rejects (`validateConfigurationsAreBuiltOneWay`, a `SourceDiagnostic` at `mockDeclarationLocation`) a type whose first mock-built and first `init`-built nodes across all roots, in root order, both read a struct and differ in `MockParameterNode.configurationRequirements` (child properties, default parameters by label and type, builder parameter types). A node beneath a `cycleEdges` edge reads no overrides from its struct (its parent's struct has no field for it), so `collectConfigurationNodesByConstruction` leaves it out, and when the first node of a type is such a node built the other way, the struct is generated from the first node that reads it instead. A node that needs no struct is built from a closure typed by its property, so the shape #419 made compile, a mock that takes nothing, stays accepted, as do a mock with exactly `init`'s parameters and a mock that returns the concrete type. An extension's `instantiate(…)` plays `init`'s part: its default-valued parameters are struct fields (#452), so an `instantiate`-built node can read a struct and conflict too, and the diagnostic names the construction by `MockParameterNode.isExtensionBased`. Never emit a second struct for the same type. The struct's default-valued fields take their defaults from the hand-written mock's parameter of the same label and type (`DefaultParameter.defaultParameters(of:dependencies:)` on `mockInitializer`, matched to the dependencies of the concrete type's entry), whichever node the struct is generated from and even when no property is built with the mock in this module; `init`'s (or `instantiate(…)`'s) default applies only to a field the mock declares no default for, so `configurationRequirements` compares labels and types, never values. A node built with `init` beneath a `cycleEdges` edge, which no override reaches, elides its labeled defaults except those the mock also declares (same label and type), for each of which it passes `<Type>.SafeDIMockConfiguration().<label>` (`callSiteArgumentsForPrunedOverride(handWrittenMockDefaultParameters:)`, `MockContext.handWrittenMockDefaultParameters`), so the default is the mock's, evaluated in the struct, as for every other property of the type. Never inline the mock's default expression at the call site: it can name the type's static members or nested types, which resolve inside the struct (nested in the type's extension) but not in the mock root's extension.
- **Dependencies a hand-written mock is not passed.** A generated mock passes a dependency to the hand-written mock's argument with the same label (`resolveBuilderArguments`, `generateReturnArgumentList`). A mock merged in from a `mockOnly` declaration may have no argument for some of the production declaration's dependencies (`Instantiable.dependenciesNotPassed(to:)`, which never lists a `@Forwarded` one: it is an argument of the type's `Instantiator`). `createMockTypeDescriptionToScopeMapping` gives every property built with that mock a scope whose instantiable declares only the rest (`Scope.dependenciesLeftOut` records what was removed), so the dependency is not built, received, promoted, or offered as an override, and the mock declares no value it never uses. A dependency left out is built after all when the tree of a dependency the mock is passed receives its label, which is known only from the scopes, so the mapping is built again until nothing more is found. A mock that returns one of the type's additional types builds only properties of that type; the others are built with `init` from the complete scope, so one concrete type can have two scopes. The mock root's own instantiable is filtered to the dependencies of its scope, or a dependency its scope does not build would surface as a flat `mock()` parameter.
- **Hand-written `mock` vs. generated `mock()`.** A type whose `mock()` this module generates (`generateMock: true` or `additionalMocksToGenerate`) must not also have a hand-written method named `mock`, wherever it is declared. The macro enforces this within one declaration; `DependencyTreeGenerator.generateMockCode` enforces it across declarations and modules (a `mockOnly` pair) when it creates mock roots, by name only — no signature analysis, because a `mockOnly` extension's mock defaults every parameter, so even "distinguishable" pairs leave `Type.mock()` ambiguous. Do not work around such pairs at the call site (e.g. coerced function references). `Instantiable.mockDeclarationLocation` locates the diagnostic and must travel with `mockInitializer` through every merge.
- Names bound for receivers are tracked by label and then type: the disambiguation maps (`[String: [TypeDescription: String]]`) – `flatParameterDisambiguationMap` for renamed flat parameters, overrides, and sibling bindings, `lazilyInstantiatedBindingNames`, and `uncoveredDependencyNames` – give the name a receive of that label and type is handed.
- A receiver whose label was disambiguated is rebound to the disambiguated name (`emitReceiverBindings`), found by its declared type and then its unwrapped type, since an `onlyIfAvailable` receive of `x: X?` is fulfilled by a disambiguated `x: X`. A receive the node passes `nil` (`MockParameterNode.unavailableProperties`) is not rebound: the name may not be declared yet.
- **Public mocks (`generateMock: .public`).** `Instantiable.generateMock` is a `MockGeneration` (`.none`, `.internal`, `.public`; the macro reads a boolean literal as `.internal` or `.none`), with the argument's range in `mockGenerationArgumentRange`, where every public mock diagnostic points. The declaring module generates one through the internal mock's path, branched where they differ (`generateMockRootCode`'s `publicMock`, `generateMockBodyBindings`' `PublicMockEmission`), so an internal mock's output is byte-identical with no public mock in the module; the public parts live in `PublicMockGeneration.swift`. A parameter's and a member's access is `TypeAccessProof`'s, read through one `PublicMockContext` per module with the mocked type's module and each label's receivers' modules admitted. Whether a public mock can be generated (a narrower enclosing type, or a narrower declaration of the type an enclosing extension extends, read from `extendedTypeAccessNeeds` as constructions read it; a narrower type itself, which the macro rejects, reported plainly at the declaration; a required parameter no `public` tier can take) is decided for one root by `ScopeGenerator.publicMockFindings`, which `generateMockCode` and the query both run. A configured type in a public mock's tree is built by a construction function in its own extension (`__safeDI_init`/`__safeDI_mock`), which mirrors `Initializer.spelledIsolation`, from one module-level configuration per type shared by the module's public mocks; never nest a public configuration in the configured type's extension, where two modules that declare one make its name ambiguous. A consumer in another module calls the public mock of a type it cannot build inline (`publicMockCalls(in:)`: the type's mock tree has an inaccessible construction, other modules' `.public` types in it left out), through a leaf scope (`Scope.publicMockCall`, `publicMockLeafInstantiable`) that declares the mock's whole signature, which the consumer computes as the declaring module did, with a `DependencyTreeGenerator` over that module's visible declarations (`SeamResolution.foreignPublicMocks`, `publicMockPlan(ofOwnType:)`): the reached tier's received parameters as receives (`T? = nil` ones only if available) and the parameters it omits, and a public mock's no-tier parameters, as receives only if available, which order the leaf and reach the trees that call it as inline receivers would. Only-if-available receives only leaves make are never mock parameters or overrides (`receivedOnlyByPublicMockCalls`; a leaf passes them where the tree provides them, as production would, `NearestDeclarations.binding(of:)`), except on a `.public` consumer, which takes those a call passes as its own `T? = nil` parameters (`passedByPublicMockCalls`), a call inside a fill included: `collectReceivedProperties` walks a leaf's fills after its children and keeps what their calls pass that the fill's fields do not provide (`ScopeGenerator.fieldForms(of:)`, which the fill's generator declares), so the mock binds every parameter the generator surfaces, and `inOrderTheMockTreeFirstReceives` walks the fills it met last, so a dependency built when passed `nil` that only a call inside a fill receives is promoted and ordered. `publicMockTierOmissions` (modeled on `seamTierOmissions`), the mock-condition agreement and the by-name check run over every mock root before any code is generated. A public mock's root built with a hole (an `@Instantiated` property nothing the module sees fulfills) takes a builder for it, through the seams' hole machinery ("Seams: holes, builders, fills"): the public mock's map is built with `buildsHoles` (`MockScopes.publicMockTypeDescriptionToScopeMap`, `forMockRoot`), `holes(of:…scopeTypeNamePrefix: "SafeDIMockScope")` reads the root's generator, and each site is a `MockAliasNode.holeSite`. A caller fills a builder only where `holesFilled(byCallsOf:in:)` finds the fulfilling declaration's tree reads nothing but the struct's fields and the builders the caller fills, every construction in it reachable: the fulfilling scope is the one the inline mock would build the hole's property with (`fulfillingMockScope(of:in:)`, from the mock scope map, so a hand-written mock or a `mockOnly` fake that alone fulfills the hole fills it), judged with `isMock: true`. The leaf scope's `holeArguments` then hold the fill, which `ScopeGenerator.prepareFillCode(propertiesGeneratedLater:)` generates with production emission before the mock's emission, with the `propertiesGeneratedLater` of the body of the calling node's builder function (`MockParameterNode.fillPropertiesGeneratedLater`), as production generates a seam call's fills, so a receive inside it of a sibling the caller builds after the call is passed `nil`, every scope of its tree built as the inline mock builds it – with its hand-written mock where `mockReturnTypeIsCompatible` says the mock builds it (`buildsWithHandWrittenMocks` in `Scope.createScopeGenerator`, `ScopeGenerator.constructsWithHandWrittenMock`) – and no override reaches it; a call inside it passes the enclosing fill. A node that calls another module's public mock and fills a builder is built in a builder function of its own, as a seam call is in production, with its fills and guard inside it (`callPreamble(of:indent:)`), so two calls of one mock, or a fill and a `.public` caller's own builder of one label, never share a scope; a fill is named after the parameter it fills (`SeamSignature.Hole.takenUnder(parameterName:)`) and matched to it by its site, never by builder label, and a required parameter the declaring module named apart is a dependency of the leaf under that name (`publicMockCalls(in:)`). Every other builder is passed up as a received dependency of the leaf, which a `.public` caller takes on the hole's tier (`passedUpHolesByBuilder`, ordered by builder property). A leaf passes `<label>.instance` for a by-value parameter whenever the calling tree holds a wrapper of the label – promoted or instantiated – as `dependencyArgument` reads it, and as a leaf inside a fill does, which production emission builds; availability is decided from the same declarations (the wrapper's nearest declaration binds its by-value form, `CycleParameter.forms(providedBy:)`, read by `NearestDeclarations.binding(of:)`). A dependency a called public mock builds when passed `nil` is promoted at the caller's root, as the inline mock promotes it, wherever the caller can construct it (`builtWhenNilByPublicMockCalls`, M8.8b), so every call – each one an `Instantiator` makes included – is passed one instance; a lazily instantiated one is promoted as the wrapper the called mock builds (`PublicMockParameter.builtWrapper`), whose instance each call is passed. A `mock()` bound to a global actor (`Instantiable.generatedMockIsGlobalActorIsolated`, from `declarationIsolation` and `mockAttributes`) takes the type's own optional-typed defaults as parameters with providers of its isolation, never as `SafeDIOverrides` fields, whose nonisolated initializer cannot call them. SafeDI cannot see isolation a type takes from a conformance or a superclass, which is the user's opt-in through `mockAttributes` (decision 53): every other public mock keeps those defaults as fields with `nonisolated` providers, above which a generated comment names the opt-in. A module that declares a public mock computes it again over its callers' view (`callersViewFinding(of:)`), as `computeSeamRoots` does for seams.
- `TypeDescription.asIdentifier` produces identifier-safe disambiguation suffixes
- `TypeDescription.simplified` strips wrappers for cleaner suffixes, with fallback on collision
- Closure-typed defaults use `@escaping T = default` (not `@autoclosure`). A parameter declared `@escaping` is of a function type, the only kind Swift accepts the attribute on (`DefaultParameter.isDeclaredEscaping`), so a configuration that is not `@Sendable`-typed takes it `@escaping` even when its type is a typealias (`@escaping Handler = {}`); a `@Sendable`-typed one stores such a typealias behind its `@Sendable` autoclosure, as any value, because Swift rejects `@Sendable` on a typealias. SafeDI cannot see that a typealias without `@escaping` is a function type, so a configuration that is not `@Sendable`-typed cannot store a non-escaping one.
- The configuration that governs a module's own generation (imports, directories, additional mocks, its mock condition) comes only from that module. A dependency module's configuration is read only for its `mockConditionalCompilation`, to check a call of its seam or public mock (`GenerateCommand.seamResolution`, `publicMockUnderOtherMockCondition`; see the Seams entry).
- **Flat parameters default to the mock the tree would build.** A flat `mock()` parameter – a `@Forwarded` property of the mocked type, or a received dependency the mock cannot build (`MockRootParameters.flatReceivedProperties`) – defaults to `<Type>.<mock>()` (`ScopeGenerator.FlatParameterMockDefault`, from `DependencyTreeGenerator.flatParameterMockDefaults(in:emittingModule:)`) when the mock scope map's scope for the parameter's type – the slot, so a forwarded protocol finds the conformer or `mockOnly` fake that holds it, under the map's precedence – has a hand-written mock compatible with that type that takes no required argument, and this module can call it: the `Construction(usesMockMethod: true)` check `inaccessibleConstructions` runs, asked as a predicate, so a mock this module cannot call leaves the parameter required and reports nothing. A public mock applies the same rule, from its declaring module, and takes such a parameter as `T? = nil`, `nil` calling the mock; the guard hashes it like any other default, so a caller that computes the module's predicate otherwise fails at the call. A construction initializer's default for a forwarded label wins. Another module's public mock a tree calls is not hand-written, so no parameter defaults to it. `MockRootParameters` carries the defaults (`forwardedParameterDefaults`, `flatReceivedParameterMockDefaults`), which `generateMockRootCode`, the public mock's plan and findings, and `query needs` all read.
- **An erased rename of an optional dependency is mapped.** `ScopeGenerator.aliasValue` binds an alias with `erasedToConcreteExistential: true` to `(x as X?).map { AnyX($0) }` whenever its `ofType:` is optional or its binding may be (`fulfillingValueMayBeOptional`), required or `onlyIfAvailable`, and it is the one site production, mocks, and seams share. Never decide the wrapping from the binding alone: a required rename of `x: X?` reads a forwarded optional, a mock's optional parameter or override, or the non-optional value a promoted node or a lexically enclosing `let` holds, and the mapped expression compiles over each.
- **Received erased types.** `generateMockCode`'s `erasedToConcreteTypeMap` lets a mock root promote a received type no `@Instantiable` fulfills (e.g. `AnyService`) by building the concrete type an `@Instantiated(fulfilledByType:, erasedToConcreteExistential: true)` property of that exact property type names, in any module. It is keyed by the full property type, because a receiver matches by type, so an `ErasedInstantiator<(), AnyService>` erasure never counts toward `AnyService`. A type that erasures give more than one concrete type is left out of the map, and its receivers become required flat `mock()` parameters: picking one would depend on dictionary iteration order. Production never consults the map — production receivers get the value from an ancestor.
- **An `@Instantiated` dependency the mock cannot build is still declared.** `Scope.propertiesToDeclare`, which `ScopeGenerator` and the received-property walk (`ScopeDeclarations`) both read, includes `Scope.instantiatedDependenciesNotGenerated`: the type's `@Instantiated` dependencies no scope builds, which `mock()` takes as parameters. A receive of one beneath its type is therefore subtracted there, as production subtracts it, instead of reaching the mock root as a second parameter. Emission hands those receivers the parameter's final name where it enters the type's builder function, or the mocked type's whole tree for its own (`routingReceives(of:toParametersNamed:in:)`, beside `removingRenames`), and a receiver rebinds a parameter named apart. A receiver that is not beneath the type, such as its sibling, receives from above the mocked type and keeps a parameter of its own. A promoted sibling of the mocked type receives the mocked type's own such dependency by value, as its own created properties are one instance, and a receive of its `LazilyInstantiated` is wrapped around the parameter (`lazilyInstantiatedReceivedProperties` admits an instance in `mockedTypeUncoveredProperties`), never taken as a wrapper parameter or override. The instance of a wrapper the mocked type instantiates and the mock cannot build provides only that wrapper (`isProvidedByTreeByValue`): a promoted sibling's receive of the other wrapper kind takes the instance as a parameter or an override, as the mock builds a wrapper of each kind beside one it builds. That asymmetry is production's: a wrapper declaration provides itself and its instance only, so production rejects a receive of the other kind beneath it, and such a receive can only come from another declaration – another instance – while a promoted sibling's same-kind or by-value receive gets the mocked type's own property, as a receive beneath that declaration does. A promoted dependency stands for one built above the mocked type, so `createMockRootScopeGenerator` validates each promoted scope's tree for hidden received dependencies with the walk an additional mock's tree gets, rooted at that scope with its tree's received properties bound, so that the mocked type's own declarations hide nothing in it; a tree that passes is validated once across mock roots (`promotedScopesValidatedForHiddenReceives`), and one that fails is walked by every mock root that promotes it, so the errors reported never depend on the order mock roots are created in. Production never has such a dependency: `validateReachableTypeDescriptions` rejects it before scopes are built.
- **What a tree node provides.** One definition decides whether a scope provides a property to the scopes beneath it, so they do not receive it from its ancestors: `ScopeGenerator.provides(_:declaredProperties:forwardedProperties:)`. The scope declares or forwards the exact property, or, for an optional property, its unwrapped form, and a lazily instantiated property is declared (and forwarded) together with the by-value property of its instance (`declaredLazilyInstantiatedInstanceProperty`). `generateMockRootCode` drops a received property from its parameters and overrides only when its tree provides it by that definition, or when a promoted node's optional property is the receive's optional form, since a mock binds a node it builds to a non-optional value. A same-label node of any other type provides nothing: the receive stays a flat parameter or override, named apart from the root's tree bindings by label and type (`user_Draft`). Never match a received property to a tree node by label alone.
- **`onlyIfAvailable` overrides are keyed by label and type.** `generateMockRootCode` makes one `OnlyIfAvailableOverride` per `onlyIfAvailable` received property that no forwarded property or required receive covers and the tree does not provide (the mock root's own `x: X?` is handed a promoted `x: X`), even when a root tree node shares its label with another type: handing that node over is wrong (a promoted `editor: Editor` passed to its own `editor: Draft?`). `onlyIfAvailableOverrides(for:namedAfter:namesInMockScope:reservedNames:)` names the field and the binding by the bare label unless the label is a forwarded, default-valued, or uncovered-`@Instantiated` parameter, a root tree binding name, or another override's label; those are named by `identifierSafeNames` from the optional type (`user_Draft`). A flat received parameter or root alias that shares an override's name is still the one renamed, so mocks without such a clash are unchanged. A renamed override joins the flat renames in the receivers' disambiguation map, and `removingRenames(hiddenByDeclarationsOf:parameters:from:)` drops a rename wherever a nested scope declares or forwards that property (or its non-optional form), so such a receiver resolves to the closest declaration, as in production. The mock root's own renamed receive is rebound to its label at the root scope, unless the root binds that label already (to a node it promotes for another receiver); the root is then passed the renamed binding directly through the return's disambiguation map. Only promotion creates these clashes: when the mocked type's own tree hides the label, `HiddenReceivedProperty` rejects it before generation.
- **Values reaching a `@Sendable` builder function are taken as `@Sendable` autoclosures and called inside it.** A `@Sendable` builder cannot capture a value whose type is not `Sendable`, and SafeDI cannot tell whether a type is, so a labeled default-valued parameter of a type whose `SafeDIMockConfiguration` is `@Sendable`-typed (`MockContext.sendableConfigurationTypeNames`) is stored as `@Sendable () -> T` behind an `@autoclosure` init parameter and read as `field()` at every construction site (`resolveBuilderArguments`), with a closure literal default parenthesized (`(() -> Void)? = ({})`, `autoclosureDefault`), since Swift reads a bare one as the autoclosure itself, and a dependency the mock cannot build that a type inside such a builder instantiates (`UncoveredParameter.isSendableAutoclosure`) is a `@autoclosure @escaping @Sendable () -> T` parameter of `mock()`, read into `__safeDI_<name>` before any builder function and bound as `let <name> = __safeDI_<name>()` at the top of each scope that instantiates it (`sendableAutoclosureBindings`), so the value is created once per construction as in production and the receivers beneath read that binding. Mocks that no `Sendable` wrapper reaches are unchanged. A constant builder function a closer makes `@Sendable` starts the same extractor an instantiator's does.
- When a mockOnly and a non-mockOnly coexist for the same type, `resolveSafeDIFulfilledTypes` merges them. The `(false, true)` and `(true, false)` branches handle opposite processing orders. Any cross-cutting concern (tracking sets, stale clearing) must be applied to both branches or order-dependent bugs will surface only on CI.

### Validation boundaries

Validation is split between the macro and the plugin based on available context:

- **Macro validation** (compile-time, local context only): The macro sees only the single decorated type or extension. Any error that can be determined from local context belongs here — missing `init`/`instantiate()`, invalid parameter combinations (`mockOnly + generateMock`; and, as a warning with a fix-it, `mockOnly + mockAttributes`, which no generated `mock()` reads), mock method signature issues, an optional `@Instantiated` property type (`X?`, `X!`, `Optional<X>`, `Instantiator<X>?`, `Instantiator<X?>`; `InjectableMacro`), a property that is not optional on an erased rename of an optional dependency (`ofType: X?.self` with `erasedToConcreteExistential: true`, which is `nil` where the dependency is; `InjectableMacro`, with a fix-it that adds `?`, except where `onlyIfAvailable` is set, whose own check reports it), and the access levels generated code can never use: `private` or `fileprivate` on the type, its construction initializer, its `instantiate()`, or its hand-written mock method, since generated code is in a file of its own (each with a fix-it that deletes the modifier; `Initializer.isValid` applies the same rule, so an `internal` or `package` initializer is selected for construction). These produce fix-its in the IDE. Whether any other access level suits the module that constructs the type is the tool's to judge (see "Access between modules"). Code generation test fixtures never declare an optional `@Instantiated` property, since the macro rejects one. Generation matches a type's names as `String`s, so the macro (`InstantiableVisitor`) rejects, without a fix-it, two names of one declaration that SafeDI matches by name (dependency labels, alias fulfilling names, and parameter names of initializers, `instantiate(…)`, and hand-written mocks) that are equal as `String`s but differ in UTF-8 bytes, which Swift reads as two names, as well as an `instantiate(…)` dependency parameter named `_`. It rejects two `@Received(fulfilledByDependencyNamed:ofType:)` spellings (`InstantiableMacroRenames.swift`): a rename fulfilled by another rename of the same declaration – only when the two hold in one evaluation of the declaration's `#if` blocks (both outside every block, in one clause, or one in a clause enclosing the other's), since it reads every clause and cannot tell which are active; renames in two clauses of one block, or in two blocks, are left to SafeDITool – with a fix-it that names the property the renames start from and the type the last rename followed reads it as, adding `onlyIfAvailable: true` when a rename on the way is `onlyIfAvailable`, and none where a rename on the way wraps its value or keeps its label, the renames form a cycle, or the declaration would have to be optional and is not; and a rename of a dependency to itself, its label with its type (a fix-it to `@Received`, none when it is also `erasedToConcreteExistential`) or its type, or its type made optional, only if available (a fix-it to `@Received(onlyIfAvailable: true)`, beside the `@Received` macro's fix-it that makes a non-optional type optional; the erased spelling wraps, so it stays). A rename that keeps its label and changes its type retypes the property above it and stays. The warning at a dependency type that names a type nested in the decorated declaration unqualified or through `Self` collects nested types from every `#if` clause and exempts a nested `@Instantiable` type exactly where `TypeDescription.qualifyingInstantiatedType(within:amongInstantiableTypes:)` qualifies it, as SafeDITool does. Its fix-it qualifies with every enclosing type from `context.lexicalContext`, and must also rewrite the same-named parameters of initializers and hand-written mocks and an alias’s `ofType:` argument, or the declaration stops matching its dependencies.
- **Plugin warnings** (build-time, full context): `DependencyTreeGenerator.generateWarnings()` runs after the tree has generated. It reports a `LazilyInstantiated` property that is instantiated whenever the type declaring it is created, because a type created along with that one reads its instance by value. `InstantiationAnalysis` reads the scopes `rootScopeGenerators` built and validated (`validatedScopes`), is type-level, and is memoized per `Scope`: a type’s creation reads what its own required by-value receives and aliases read, plus what its constant children and its instantiated-with-owner lazily instantiated children read, minus every label the type declares. A read of a renamed wrapper's instance is followed through the type's renaming (`propertyRead(by:)`) to the property it renames. An `onlyIfAvailable` receive is deliberately never a reader: whether it reads the instance or is passed `nil` depends on sibling ordering, which only `ScopeGenerator` knows, and a warning about a dependency that is not instantiated would be worse than a missing one.
- **Plugin validation** (build-time, full context): The plugin (`SafeDITool generate`) sees all modules' types. Errors that require cross-type knowledge belong here — unfulfillable dependencies, received dependencies hidden by a closer ancestor's property with the same label (generated code passes dependencies by label), a rename whose `fulfilledByDependencyNamed:` label its own type instantiates or forwards with a type other than its `ofType:` (`renamesContradictingOwnProperties`: the rename refers to that property, so `ofType:` must name its type exactly, optionality included, or a `LazilyInstantiated` property's instance type; recorded in the hidden-label walk and thrown before unfulfillable and hidden properties, which it explains, and checked again in `validateChildrenDoNotRequireEachOther` for the trees of dependencies a mock promotes, which that walk does not reach; both declarations are on one type, but the check stays in the plugin by ruling), dependency cycles, a `@Sendable` builder function that would capture an `Instantiator`, `ErasedInstantiator`, or `LazilyInstantiated` declared outside it (`ScopeGenerator.nonSendableWrapperCaptures`, which walks the generator trees as code generation does, so a dependency passed `nil` is not reported; a receiver is reported once for each chain that reaches it, so the root a diagnostic names never depends on name order), duplicate type declarations, duplicate mock providers, a `mockOnly` hand-written `mock` on a type whose `mock()` is generated, the seam errors (`DependencyTreeGeneratorError.SeamError.Kind`: two receives of one label with different types, a tier that cannot take a required parameter, a hand-written initializer a generated tier would redeclare, a reached seam whose module's `.safedi` names a dependency this run lacks, signatures that do not settle, a seam's tree reaching a declaration its callers cannot see), an `additionalMocksToGenerate` entry of the selected configuration that names no `@Instantiable` type (`SafeDIConfiguration.validateAdditionalMocksToGenerate`, judged against the concrete types mock generation matches entries to, unioned with the `ModuleInfo.instantiableTypeNamesInAnyClause` of this module and its dependent modules, so an entry naming a type declared only in an inactive clause is accepted and its file written without code, as "Conditional compilation" describes; entries of configurations in inactive clauses are planned by `scan` and written without code, never judged), and an entry that names a type whose every map entry is `mockOnly` (`validateAdditionalMocksToGenerate(namingMockOnlyDeclarationsIn:)`: its hand-written mock is its mock; a production declaration a `mockOnly` one merges into, under any key, keeps the entry accepted; it runs before mock generation, so it wins over `handWrittenMockSharesGeneratedMockName` for a fake whose method is named `mock`).
- **Access between modules** (build-time, `SafeDITool generate`): every construction `generate` emits must compile in the module it emits it in (the `emittingModule`: `ModuleInfo.moduleName`/`packageName`, the module's own files – the manifest's `mockScopedFilePaths`, or else the input files (CSV and `--include`), never a file reached through `additionalDirectoriesToInclude` – and whether a recorded file can be read). A construction is a production root or a type its tree instantiates – the fill of a seam call included, the fulfilling type and its tree, reached at the call's reference location – built with its initializer or `instantiate()`, a type a mock builds, with its hand-written mock where `mockReturnTypeIsCompatible` says the mock builds it with that, and a mock root. A flat `mock()` parameter defaults to a hand-written mock only where that construction passes the check (`flatParameterMockDefaults(in:emittingModule:)`), so a default is never reported. Until 3.0 those fields stay optional, so every reader keeps its fallback for a manifest without them.
- **Reject nonsense shapes.** A shape only a confused user would write gets an error, never generator support.
- **The macro prevents; the plugin trusts.** A shape decidable from one declaration gets a macro diagnostic (the rename check under "Plugin validation" stays in the plugin by ruling), and the tool never re-checks what the macro rejects. Where it relies on a macro check to keep from trapping, it reports a plain error instead, as the next rule describes.
- **Never a trap on what the macro rejects.** Every build runs `generate` before the compiler expands the macro, so where the tool relies on a macro check to keep it from trapping, input the macro rejects gets a short plain error at the declaration that points at the macro's rule: no fix-it, which the macro keeps for the IDE, and no copy of the macro's validation. `validateDependencyLabelsAreDistinct` is such a check: generation keys a declaration's dependencies by label, so a declaration two of whose dependency labels `String` equates is reported at the later one when a production root's tree (its reachable types), a generated seam's tree (and the foreign seams it calls, checked before any seam signature is computed), or a mock root's tree (the scopes its mock root scope reaches, promoted ones included) builds it – two `instantiate(…)` parameters named `_`, names encoded differently, and one dependency declared in each clause of an `#if` only the compiler decides, which the macro accepts. `validateRenamesAreSpelledAsTheMacroAccepts` runs beside it over the same declarations (`RejectedRename`), and in `mockScopes` before the mock cycle walk, over the declarations that walk reads: the trees of the roots, of the types whose mocks are generated, and of the scopes it follows a required receive to. It rejects a rename fulfilled by the label of another rename of its declaration, by its own label and type, or by its own label with its type, or its type made optional, only if available (not erased) – including, by ruling, a rename of a rename the macro accepts because two `#if` blocks, or two clauses of a block only the compiler decides, hold the links, which SafeDITool's evaluation joins. The ruling keeps one rule for every chain within one declaration, and its error names the label to change. Across clauses only the compiler decides, the shape also does not work: the code generated from every clause's renames can assign one clause's rename from another clause's, a wrong value that compiles. No validation walk meets such a rename, which is why no code follows a chain of aliases within one scope. A declaration no tree reaches traps nowhere, so it is not reported: a shape that works must not become an error. Tests of these errors are the one exception to fixtures the macro accepts.

### Serialization

`scan`'s cache (`<manifest>.safediScanCache`, a `CachedScannedModuleInfo`) and `.safedi` module info files (a `ModuleInfoFile`: the module's own declarations under a non-optional module name, and its `view` – `ModuleInfoView`, `ViewedModuleIdentity`, `ViewedModule` – of the modules it depends on) are written in SafeDITool's own binary format, by hand rather than through `Codable` (`BinaryCoding.swift`, `BinaryCodableModels.swift`, `BinaryFile.swift`, all in `SafeDITool`, never `SafeDICore`). These files are **regenerated every build** — there is no cross-version deserialization. Do not add backward-compatibility decoding logic. A header (magic, format version, schema fingerprint, body length, checksum) rejects any other file: an unreadable scan cache is a cache miss and a fresh parse, and an unreadable `.safedi` is an error naming the file. `BinaryFile.schemaDescription` and `BinaryLayout.description` spell every stored type and field type with `String(reflecting:)`, so the module names `SafeDITool` and `SafeDICore` are part of `schemaFingerprint`: every build of the tool must name its modules that way (the SwiftPM targets, the prebuilt binaries, and `module_name` on the Bazel `swift_binary` and `swift_library`), or its `.safedi` files are unreadable to the others, and no test catches it, because `swift test` cannot see a Bazel build. The plugin-read `SafeDIToolManifest` stays JSON. `generate` writes `--combined-output` and `--module-info-output` only when their bytes change (`Data.writeIfChanged(toPath:)`), and the `.safedi` last, after every validation, so a failed run publishes none: Bazel removes an action's outputs before it runs, so every Bazel run writes them, and Xcode's script dependency analysis compares a script's inputs with its last run's, so an unwritten output does not rerun the script forever (captured 2026-11-04 in DAN-2's design, T4b/T4d).

When a stored type changes, keep its coder in step:
- Each `BinarySchemaMember` writes its fields in initializer order and reads them back through that initializer, with each field's type choosing how it is read. A field whose type is not `BinaryCodable` fails to compile; so does an enum case the writer's exhaustive `switch` does not handle, and a tag the reader's `switch` does not handle.
- `binaryLayout` is what `BinaryFile.schemaFingerprint` covers: for a struct, each field it writes, in write order, as a `BinaryLayoutField` whose key path fixes the field's type, plus `unwrittenProperties`, the stored properties not written under their own name (`Dependency.asInstantiatedType`, `UnorderedEquatingCollection.set`, `Instantiable.instantiableTypes`, written as `concreteInstantiable` and `additionalInstantiables`, and `Property`'s stored hash, which is never written because hashing is seeded per process: a decoded `Property` goes through `Property.init(label:typeDescription:)`, which computes it again); for an enum, each tag's associated values, in declaration order, which is also the order written and read. A file written by a SafeDITool whose types write other fields, fields of other types, or the same fields in another order is therefore never read. `SafeDIToolBinaryFileTests` compares each struct's layout against `Mirror`, so a new stored property fails until it is listed, written, and read, and writes each field and associated value in turn with a value distinct from the rest (`BinarySample`), so a layout whose order or types differ from what the coder writes and reads fails too. A new stored type must join `BinaryFile.schemaMembers` and conform to `BinarySample` in the tests.
- A `BinaryReader` reads type descriptions nested at most `BinaryReader.maximumNestingDepth` (128) deep, so the writer notes a deeper one and `BinaryFile` refuses to write a file that holds it, naming the instantiable whose declaration names it, or the outermost type of a plain type declaration (`BinaryFileWriteError`): `scan` then writes no cache, and `generate` fails rather than write a `.safedi` dependents cannot read. Do not describe the deep type itself in such an error: spelling a type recurses as deeply as it nests, which exhausts a task's stack in a debug build.
- `executeSafeDIToolTest` checks, for every fixture that runs scan, that the cache reads back exactly what scan wrote (`reflectedDescription`, which sees private fields and spellings `==` ignores, and compares strings by their UTF-8 bytes, because `String`'s `==` calls canonically equivalent spellings equal while Swift compares identifiers byte for byte; the writer's string table keys strings by those bytes for the same reason), so a field the coder drops fails whichever tests give it a value.
- `Codable` conformances stay: the `dump` subcommand prints either file as JSON through them.

## Determinism

Everything SafeDI produces must be identical on every run over the same inputs: generated code, diagnostics (their text, their order, and which one is reported first), fix-its, output file names, and the bytes of manifests, `.safedi` files and caches.

- Swift seeds hashing per process, and `Scope` hashes by object identity, so the order of a `Set` or `Dictionary` changes between runs — for scopes, even under a fixed hash seed. A task group's results arrive in completion order. None of these orders may reach output.
- When code chooses among candidates or emits a list, use declaration order, source path order, or a sorted order. Never use first-found or last-write-wins over an unordered collection.
- When a choice is genuinely ambiguous, report an error or apply a stated tie-break. Do not pick silently.
- Sorting only on the failure path is fine, and keeps the success path cheap: visit everything, and keep the candidate that sorts first only when there is something to report.
- A test of choice-making code needs enough candidates that a wrong order fails on nearly every run: twenty or more, or a permutation of six. A fixture with one candidate cannot catch this class of bug.

## Code Style

- **Compare for meaning through a projection.** A comparison for meaning (settling, the callers' view, a guard hash) uses an explicit projection, never the synthesized `==` or hash of a type that carries diagnostic payload.
- **No abbreviations.** Use `dependency` not `dep`, `parameter` not `param`, `declaration` not `decl`. Everywhere: variables, functions, tests, comments, commits.
- **No `default` or `case _` in switch statements when all cases are knowable.** Enumerate all cases explicitly for compile-time safety.
- **Use `for ... where` for simple boolean filters** instead of `guard ... else { continue }` inside the loop body.
- **Use `guard` for early exits**, not `if condition { continue/return }`.
- **No early return from bare `if`.** If an `if` branch returns, the non-returning path must be in an explicit `else` clause. Never fall through after `if { return }`.
- **Test names follow `method_expectation_conditionUnderTest`** pattern (e.g., `mock_disambiguatesAllParameters_whenThreeChildrenShareSameLabel`).
- **No traps in shipped code.** A validated tree, and the code generated from it, never crash. Code under `Sources` and `Plugins` uses none of the traps `SourceRuleTests` (below) fails on, except at a site whose waiver states the invariant that keeps it from trapping on any input, including input the macro rejects ("Never a trap on what the macro rejects").
- **`SourceRuleTests` enforces source rules.** It fails on a trap in `Sources` or `Plugins` (a force unwrap, in an expression or a key path, an implicitly unwrapped optional or `init!`, `unsafelyUnwrapped`, `try!`, `as!`, `fatalError`, `precondition`, `preconditionFailure`, `assert`, `assertionFailure`, `Dictionary(uniqueKeysWithValues:)`, `Dictionary(dictionaryLiteral:)`, or a dictionary literal whose keys are not distinct literals), on `try?` under `Sources/SafeDICore/Generators`, on `__safeDI_` in a literal in `Sources` outside `ReservedName.swift`, on a lone backtick literal in `Sources` outside `IdentifierSpellingExtensions.swift`, and on an error type declared under `Sources/SafeDICore` that `ErrorReportingSite.byErrorType` does not list with the code that reports it. A safe site is waived by a comment on its line or on the lines just above it, `// safedi-source-rule: allow <rule> — <the invariant that makes it safe>`; a waiver that names no rule, gives no reason, or waives no site fails the test.
- **No new `@unchecked Sendable`.** The compiler proves the concurrency safety of SafeDI's own code (`Sources` and `Plugins`; a test fixture's types are input); disentangle the state instead. Only a tiny low-level primitive may be unchecked.
- **An actor's `lazy var` initializer reaches nothing isolated through a closure.** In an actor, a `lazy var` whose initializer contains a closure or a local function that calls an isolated method or reads an isolated property fails to compile with Xcode 26's Swift 6.2 ("actor-isolated default value in a actor-isolated context"), although Linux's Swift 6.2 and Swift 6.4 accept it. Keep the value in a stored optional instead, filled on first use by an isolated method that returns it.
- **Build long arrays and strings with sequential appends.** A long expression that joins arrays or strings with `+` and contains ternaries makes Linux's Swift 6.2 time out type-checking it. Declare a `var` and append each part, with an `if` where a ternary chose a part.

## Testing Philosophy

- **TDD**: Write failing tests first, then fix.
- **One behavior per test method.** Each test verifies one behavior, but may use multiple assertions to fully validate it (e.g., checking both the count and content of output). Do not test unrelated behaviors in the same method.
- **No tautological tests.** Tests must exercise real code paths with real input. Never use test helpers that rewrite input before processing — the test content should be exactly what production code would see. Tests should verify input code → output code.
- **Test through the pipeline**, not direct model construction. Mock tests use `executeSafeDIToolTest` which parses real Swift source through the full visitor → generator pipeline.
- **Full `==` output comparison.** Never use `.contains()` for mock output. Compare the complete expected string.
- **Verify updated test expectations compile.** When updating expected output in generator tests, review the new expected code to confirm it would compile as valid Swift. Check that variable references resolve to the correct scope, types match (no optional where non-optional expected), and all referenced variables have bindings. Do not blindly update expected output to match actual — the actual output may itself be buggy.
- **Code generation tests should only test paths where the macro would not emit an error**, except tests of the plain errors "Never a trap on what the macro rejects" describes. Test inputs must be valid under `@Instantiable` macro validation — every `mockOnly: true` type needs a `mock()` method (or `customMockName` method), mock method names on the same type must not collide (and a `mockOnly` mock paired with a generated mock must use `customMockName`, or generation errors), and production types need `init` or `instantiate()`.
- **Test titles must be observably verified.** When a test title says "prefers X over Y", the assertion must verify X is used — not just that the test doesn't crash. Add a parent type with `generateMock: true` that instantiates the type under test, and assert the full mock output shows X's method name.
- **If code can't be covered by a test with real parsed input, remove the code.** Dead branches and defensive fallbacks for structurally unreachable paths should not exist.
- **"Structurally unreachable" claims need a failing test.** Before removing defensive branches on the grounds that they can't be reached, write a test that tries to reach them with valid input. If the test can't be written, cite the specific rejection (file:line) and the input shape it rejects — a structural argument alone is not evidence. Structural arguments are easy to get wrong: e.g., `erasedToConcreteExistential: true` does NOT imply a constant property type, so "erased + cycle is rejected as constant" was wrong and cost a round trip when the branches had to be restored.
- **Document a deliberate gap; don't pin it.** A deliberate difference between sibling code paths gets a comment at both sites and a rule in this file, not a test that pins the non-behavior.
- **Test fixture file naming controls processing order.** Files parse in parallel, so completion order is random; `ModuleInfo(_:)` therefore orders a module's file scans by path, so its instantiables are in source file path order, keeping each file's top-to-bottom declaration order, and its imports and mock imports are sorted and deduplicated, so the `.safedi` file `generate` writes is the same bytes every run; upstream `.safedi` module info is already in that order, and `loadSafeDIModuleInfo` returns the dependent modules in the path order of their `.safedi` files, whatever order the caller lists them in or the parallel reads finish in, so the combined list `resolveSafeDIFulfilledTypes` sees is deterministic without a second sort. `executeSafeDIToolTest` names fixture files by extracting the type name from `@Instantiable` in the source content, so those names decide the order. When testing ordering-sensitive behavior (e.g., which of the two mockOnly merge branches runs), pick names that sort the way you need, and be aware that an `extension MyService` file falls back to `"File"`. A configuration-only snippet also falls back to `File.swift`, so it exercises `parseModule`'s fallback path; pass `swiftFileContentByFilePath` (e.g. `["SafeDIConfiguration.swift": …]`) to name a fixture explicitly when the file name matters. A single-module test writes a `.safedi` only when it names its module (`moduleMembershipArguments` with `--module-name`), and a multi-module fixture that `omitsModuleName` writes none, so no other module may depend on it.
- **Tests must not depend on where the checkout lives.** The suite runs from checkouts under `/Users`, under `/tmp` (reached as `/private/tmp`), and through other symbolic links. Build an expected path by the rule the contract under "File path spelling" gives its consumer — for example the project root as the test handed it to `scan`, made absolute, joined with the file's path inside it, for `additionalInputFiles` — never from `currentDirectoryPath` or `NSTemporaryDirectory()` compared with a normalized path, and test a symbolic link by creating one, as `SafeDIToolPathSpellingTests` does. Under a plugin invocation that reports the fixture directory resolved, `generate()`'s diagnostics are at `NormalizedFilePath(fixtures.compilerPath(of:)).path`, and what `run()` prints is at `compilerPath(of:)` (see "File path spelling").

## Graph fuzzer

`SafeDIToolGraphFuzzerTests` (support code in `Tests/SafeDIToolTests/Helpers/GraphFuzzer.swift`) generates random graphs of `final class` `@Instantiable` types from a seed (a quarter of them also with one extension-based type whose `instantiate(…)` has default-valued parameters, decided after the rest of the graph so the other types of a seed's graph do not depend on it), with its own SplitMix64 generator so a seed names the same graph on every machine. The oracle runs each graph through `executeSafeDIToolTest` twice in the test process and accepts only two outcomes: the tool reports an error, or the fixture and the generated code compile (`swiftc -emit-object`, as `verifyGeneratedCodeCompiles` does) and the compile the graph passed reports no warning that only its generated code draws (`warningsOnlyGeneratedCodeDraws`, the verifier's filter). Generated code that does not compile or draws such a warning (`generatedCodeDrawsWarning`), a fixture that does not compile on its own (a fuzzer defect), and two runs that differ are failures; a crash kills the test process. The two runs share the process's hash seed, so the long run also runs the `SafeDITool` executable in two processes for every 50th seed and compares them. The oracle also runs each graph under every `GraphFuzzerRenaming` – reversing the order of its type names, of its labels, of its file names, and of all three at once, each a pure rename of single-digit indices (`i` to `9 - i`, files prefixed `F<99 - rank>_`) – and requires, once the renaming is undone textually, the same verdict, the same diagnostics in any order, and byte-identical generated files (`renamedGraphDiffers`). It compares the suggestions a diagnostic lists ("Did you mean one of …") in any order too: the order inside a message is presentation and changes nothing a user does. It compares the comment naming the types SafeDI counts as `public` because it reads no declaration of them by its count in each module, not by its place: a combined output carries it above its first `public` declaration that names such a type, which name order decides. It catches output that depends on which of several equals SafeDI meets first in name order, which two identical runs cannot see. The reversals keep every type name's `S<seed>_` prefix, which sorts after `ErasedInstantiator<`, `Instantiator<`, and `LazilyInstantiated<` and before the `Sendable` wrappers (a digit sorts before `e`), so no reversal changes whether `x: X` or `x: Instantiator<X>` sorts first. A fifth renaming therefore moves type names across wrapper names (`movesTypeNamesAcrossWrapperNames`): it replaces the prefix's `S` with `A`, which sorts before every wrapper's name, or `Z`, which sorts after every one, chosen per seed by each name's kind and index (`T3`, `AnyT3`, `Value`; a type and its `Protocol` move together), wherever the name appears. A quarter of graphs end with a motif drawn after the graph's own types and before the extension-based type (types 7 to 9, so other graphs draw as before) whose output SafeDI must choose for: a lazy cycle of mocked types, promoted siblings that receive each other only if available, one label received as an instance and as an instantiator, several independently invalid roots, or two types in two files that fulfill one protocol. The four reversals cost about 60% more corpus time, and the move is one more run of the tool per graph. Graphs compile together, kept apart by a per-seed type-name prefix (`S<seed>_`), in one `swiftc` invocation per module role: every graph in one module, with the seam's module of every graph split across modules (`GraphFuzzerModule`), compiles as `FuzzFeature` in package `shop`; then the split graphs' same-package callers (`FuzzApp`, `shop`) and other-package callers (`FuzzOther`, `other`), each against the modules before it, a graph that fails in one module left out of the later ones. Every fuzzer compile passes `-package-name`. A graph's wrappers are all `Sendable`, all not, or – in a quarter of graphs – mixed at random, so a `Sendable` builder's subtree can receive a `LazilyInstantiated` declared outside it; a mixed graph's types are `@unchecked Sendable`, and its types that are not `@Instantiable` (the extended type among them) are `Sendable`, so receiving one by value inside a `@Sendable` builder function is never what fails. The oracle compiles in the Swift 6 language mode, where such a capture is an error rather than a warning. A type no root reaches sometimes receives `items` as a wrapper of the graph's `Value` type, which is not `@Instantiable` and which nothing provides, with the wrapper chosen for each receive, so a mock's tree receives one label as several wrappers its mock cannot build. A type no root reaches also sometimes instantiates a constant of a type that is not `@Instantiable` (`addingDependenciesMocksCannotBuild`), which its mock takes as a parameter, and a pass drawn after every other base pass but one, with its own generator (`addingReceiversOfDependenciesMocksCannotBuild`), now and then gives a type built beneath that owner – one it instantiates, or now and then one that type instantiates – a receive of the constant, required or only if available, which the mock must pass that same parameter (`dependencyMockCannotBuildReceivedBeneathItsOwner`). With a generator of its own, the pass also now and then makes an owner with `generateMock: true` receive a type of the graph that receives the constant by value or as its `LazilyInstantiated` or `SendableLazilyInstantiated`, required or only if available; a mocked owner's mock builds that type beside it and must wrap the parameter it takes rather than take the wrapper (`dependencyMockCannotBuildReceivedLazilyBesideItsMockedOwner`). In a mixed graph the owner now and then lazily instantiates the constant as one wrapper while that type receives the other kind, which the mock must make from an instance it takes (`dependencyMockCannotBuildLazilyInstantiatedReceivedAsOtherKindBesideItsMockedOwner`), and now and then the type instead instantiates a type of the graph under the constant's label above a receiver of the constant, which the tool must reject as hidden. The oracle checks that rule in every accepted graph: a generated `mock()` takes a `LazilyInstantiated` or `SendableLazilyInstantiated` parameter only for a property the mocked type forwards or instantiates (`mockTakesWrapperParameterForReceive`). Types also receive the erased instantiators an ancestor instantiates, with exactly the type it declares, and some forward one. A tenth of graphs end with a chain of aliases through an `onlyIfAvailable` alias (`addingAliasChains`, a pass with its own generator, so every other graph is drawn as before): a second alias, required or `onlyIfAvailable`, of an `onlyIfAvailable` alias a type declares or is given, on a type it instantiates, now and then a third on a type that one instantiates (the macro rejects a rename of another rename of one declaration, so no draw puts two links on one type), and usually a receive of the last on a type beneath it. The second pass never aliases an optional property, so no other graph has such a chain unless `addingSiblingAliasChains`, below, draws one; a receiver that requires the last alias needs every alias created, so the first alias's fulfilling property must be built before it, which the rest of the graph can make a cycle (`aliasOfOnlyIfAvailableAlias`). That pass draws the first alias's source from the properties provided above every path to its host, never one built around it, so it never draws the sibling cycle PRs 472 and 481 fixed. A last pass with its own generator (`addingSiblingAliasChains`, three rolls in ten, about 170 corpus graphs) draws that cycle: a scope – a root, or a type on every path to the chain – instantiates `x: X` as a constant and another type `B` without an instantiator; `B`, or a type a few such steps beneath it that each step dominates, declares an `onlyIfAvailable` alias of `x`, mostly spelled with its optional form (`ofType: X?.self`, `aliasOfOptionalFormOfProperty`); now and then one or two aliases of that alias follow, required or `onlyIfAvailable`, each on a type beneath the one before, so that the chain crosses scopes at every link; usually a type beneath the last alias's type receives it, mostly required, or a required alias of it on a new type beneath does instead; and usually `X` receives `b`, so that `b` must be built before `x` while the chain needs `x` first, which the tool must reject through the chain (`fixture_makesSiblingsTypeReceiveTheOtherSibling_forSeed4224`). A type beneath another is a child it dominates, judged from the declarations rather than from `dominators` (a root now and then declares a property the other roots lack, which the graph's edges do not hold), or, where it has none, which is most often, a new type only it instantiates (`Link0`, `Link1`, …), so a receiver is not rejected merely because another path from a root reaches it without the alias. Without the receive of `b`, the chain must be built after `x`, which the compiled output shows (seeds 731 and 2420, in the smoke batch, whose chains pass through child scopes). One pass more, after `addingReceiversOfDependenciesMocksCannotBuild` and with its own generator (`addingErasedRenamesOfOptionalDependencies`, a quarter of graphs, about 130 corpus graphs), gives a type a root reaches or whose mock is generated an erased rename of an optional property of a type of the graph that is provided above every path to it (`ofType: X?.self, erasedToConcreteExistential: true`), required or now and then `onlyIfAvailable`, and, in about half of those graphs, a receive of it on a type it instantiates: a host that instantiates a type of the graph, when there is one, is chosen seven times in ten, and always gets a receiver (`erasedRenameOfOptionalDependency`; seed 2314, in the smoke batch, renames an optional alias, which a type beneath receives only if available). `aliasProperty` never aliases an optional property and the passes that spell `ofType: X?.self` never erase, so no other pass draws it.

- **Every pull request.** `ci.yml` fuzzes each corpus whole – the base corpus, seeds `0..<corpusSeedCount`, the seam corpus, seeds `0..<seamCorpusSeedCount` drawn with `generateDependencyTree`, and the public mock corpus, seeds `0..<publicMockCorpusSeedCount` drawn with `generateMockPublic` – on every pull request and push to main that changes more than Markdown. "Build and Test on Linux" packages its test bundle; "Fuzz Dependency Graphs on Linux" shards download it and run the long run over parts of a corpus (the matrix names each shard's corpus and features), with batches running concurrently on every core; and "Check Graph Fuzzer Corpus on Linux" combines the shards' reports per corpus, failing when a corpus has no report. A shard fails, naming the seeds in its summary, when a graph fails, a known issue goes stale, the run reports a problem with itself (a changed corpus, an invalid known-issue list, a harness error), the process crashes, or no graph runs. The combine job fails when a shard is missing or reported any of those, when the shards do not cover the corpus exactly once, or when the seeds the tool accepted differ from the pins (`corpusAcceptedSeedCount`, and `corpusAcceptedSeedsSum`, a `GraphFuzzerSeedSetSum` whose parts add up across shards), or when, in the base corpus, the accepted graphs that show a `GraphFuzzerFeature` (read from the emitted source as the smoke batch reads it, whether or not the graph fails as a known issue) differ in number from its pin (`corpusAcceptedFeatureCounts`, which each shard reports and the combine job adds up; a run of the whole corpus checks them itself), or when a complete report names its corpus without that corpus's per-feature counts or the value oracle's inspected count, which every long run writes, so a run that stops writing either line cannot skip its check. The oracle takes any error the tool reports as a valid rejection, so a tool change that makes it accept or reject other graphs must update those pins deliberately. Unit tests leave the siblings of a shape the corpus draws to the corpus, and the per-feature pins are what show the corpus still draws it: a generator or tool change that changes them updates them deliberately, and a feature whose count falls below ten no longer stands in for the unit tests of its shape. A sibling whose defect compiles to a wrong value (a second instance, a farther one, `nil`, or a value where production passes `nil`) is left to the base corpus's value oracle instead, whose `GraphFuzzerValueOracleShape` pins show the corpus still compares pairs whose trees hold its shape, under the same rule of ten; a shape is counted wherever the model finds it in a compared pair's tree, including receivers the comparator never reaches (behind an `ErasedInstantiator`, behind an instantiator with forwarded properties, or an `Instantiator` whose sharing the describer cannot see), so a cut's evidence is its family's mutation run, which shows in how many pinned pairs the comparator detects the defect. The fixed seeds make every failure deterministic, so it belongs to the change that caused it. Measured before the base corpus's value oracle: the shards added about 3¼ minutes after "Build and Test on Linux", cold or warm, since they run its bundle instead of building, and a base shard fuzzed 2500 seeds in about 2¼ minutes before the multi-module property, which adds about a quarter. Each of the four base shards now fuzzes 1250 seeds, multi-module property and value oracle included, in a time not yet measured on CI (the stop rule is 3½ minutes per shard); the seam shard's 1000 and the public mock shard's 1000, 2 to 4 minutes on an eight-core Mac, are not measured on CI either.

It is what `swift test` gives a developer locally. - **Multi-module partition.** The oracle also runs every graph that declares no seam and no public mock – each of the base corpus's – split across modules through both multi-module integrations of `executeSafeDIToolMultiModuleTest`, `.moduleInfo` (Bazel's flow: `generate --combined-output --module-info-output --compiler-receives-input-paths-unchanged --module-name --package-name` per module, reading the listed dependencies' `.safedi`; Tuist's differs only by omitting that flag) and `.swiftPackagePlugin` (the SwiftPM plugin's: one CSV per module holding its files and its transitive dependencies' files, the module's own mock-scoped, with the target graph beside it, `scan` while planning and then `generate` with the manifest, one file per root and per mock), without compiling, and requires the same results (`integrationsDiffer`). `GraphFuzzerPartition` (`Tests/SafeDIToolTests/Helpers/GraphFuzzerMultiModule.swift`) is a pure function of the graph – it draws nothing from the seed, so `corpusFixtureHash` and the accepted-seed pins are unchanged by it, and `smokeAndKnownIssuePartitionHash` and `corpusPartitionHash` pin the partition itself, so a change to it is deliberate (they move with the generator and the known-issue list as well, as the fixture hashes do). The partition projects the fixture's files first (`projectedFiles(of:)`): the helper types `Value` and `Unbuildable<n>`, which the generator declares in `Root0`'s file, move into a file of their own (`S<seed>_Helpers.swift`, named explicitly), since left there every type of `Root0`'s tree that names them, with the files between, would share `Root0`'s component, so `Root0` could never be split from a type of its tree that forwards `lazyValue`; the helper file is visited first, so it is the first component and always lands in `Alpha`. Each file refers to the types it names (instantiated, received, forwarded, aliased, erased to, named by `fulfilledByType:`, the graph's `Value` and protocol types, the extended class), each name is declared in one file, and Tarjan's algorithm over that reference graph, visiting the helper file first and then the files in order, lists each strongly connected component after every component it refers to (the helper file, which refers to nothing, is the first component; a lazy cycle through instantiators is one component, so its types share a module; a root's component follows those of the types its tree names; the roots are the first files, so the types no root's file refers to, directly or through other files, are visited after them and their components follow the roots', and a root need not be in the last module). The components are dealt out, contiguously in that order, to `Alpha`, `Beta`, `Gamma`, `Delta` – as many as `GraphFuzzerHash` of the fixture's text chooses, one to four, so single-module graphs stay in the corpus (1319, 1214, 1262 and 1205 of the 5000 graphs get one to four) – so every reference points into the same or an earlier module. The two integrations combine declarations in different orders: `generate` lists the dependencies' `.safedi` files, read in path order, before the module's own declarations, while the plugin parses every module's files in path order (`Sources/<Module>/…`), the module's own among them; `Delta` sorts before `Gamma`, so in a four-module graph whose `Delta` depends on `Gamma` (otherwise `Gamma`'s files are not in `Delta`'s CSV and its `.safedi` is not read) the plugin combines `Delta`'s own declarations before `Gamma`'s where the module-info integration combines them after – kept deliberately, since a real package's module directories sort arbitrarily against a Bazel build's `.safedi` paths, so those graphs, 532 of the corpus's 5000 (the long run counts them as `delta-depends-on-gamma` on its `partitions` report line), check that nothing SafeDI generates or reports depends on that order (the corpus passing with it is the evidence). A module's `dependencies` are every module whose declarations its `generate` must read, the modules its files refer to and, through them, theirs: what a Bazel user lists in `safedi_compile`'s `deps`, since a `.safedi` holds only its own module's declarations, so a tree reaching a declaration two modules down needs that module listed (`multiModuleTest_throwsErrorForGrandparentDeclaration_whenModuleInfoListsOnlyTheDirectDependency`); the plugin lists the transitive closure's files itself, so both integrations read the same declarations. Every other file keeps its name and content; `Root0`'s loses only the helper declarations; each gets an `import` line per module it refers to before it, and the module, package and helper file names hold no digit but the seed's, so the renamings leave them alone. The property compares module by module in dependency order (`GraphFuzzerMultiModuleOutcome.difference`): a module both generate must have the same generated units, each byte for byte, the combined file's imports in every one of the plugin's files (the plugin's dependency-tree and mock files import what each kind needs, which differs only through `#if`-guarded imports, which no fuzzer graph has), and the same warnings; a module the module-info integration rejects must be rejected with the same diagnostics, in any order, by the plugin. A unit is one generated extension, keyed as the plugin names the file it writes (`<Type>+SafeDI.swift`, `<Type>+SafeDIMock.swift`, `<Type>+SafeDIMockConfiguration.swift` for a `SafeDIMockConfiguration` struct wherever the plugin places it), with the `#if` the mock condition wraps it in, and with every path under the fixture root reduced to `<fixture-directory>/…` (`GraphFuzzerGeneratedModule`): the combined file's joined bodies and the plugin's per-file outputs reduce to the same units, and a `#sourceLocation` directive differs between the integrations only in the fixture root's spelling (the plugin's resolved root against the CSV's path under `--compiler-receives-input-paths-unchanged`). Two differences are the integrations' own. One needs no normalization: the plugin's `scan` plans a dependency-tree file for every root in its CSV, so a consumer writes a file for each dependency's root, which holds a comment and no code, so no unit, and the outcomes compare as written. The other is normalized rather than reported: the plugin adds a build command only for a module whose manifest plans an output, so a module runs `generate` under it only when its own files declare a mock, or its own or its dependencies' files declare a root (`scan` plans every root in the CSV), and a defect its declarations alone reveal (two types fulfilling one protocol, seed 20) is reported where the first module that depends on it generates, or nowhere – the property expects those diagnostics there, requires that the module-info integration generated nothing for a module the plugin skips, and takes an unreported defect as the plugin's design; when the plugin first rejects a module that does not depend on the skipped one, nothing is compared, because `.moduleInfo` stopped at the skipped module and never ran that one. It runs in the smoke batch, which must split graphs into one, two, and three or more modules and reject some split ones, and over the corpus in the long run, whose report counts the graphs at each module count (`partitions`) and notes each differing graph (`multimodule`). Measured: the plain run adds about a quarter of the long run's CPU time (500 seeds: 290 s to 359 s of CPU), so only the graph as generated is split (`GraphFuzzerOracle.multiModuleRenamings`): each of the five renamings would add as much again. The seam and public mock corpora are not partitioned: a graph of theirs that is split across modules is split by roles of its own (`GraphFuzzerModule`), which the partition does not model, and runs through `.moduleInfo` alone.

## Common Pitfalls

- The input CSV written by plugins includes ALL swift files (target + dependencies). Mock scoping requires passing `mockScopedSwiftFiles` separately — only the target's own files.
- **Which module declares a file is not "own" versus "other".** The SwiftPM plugin's CSV also lists files of no target of the package being built – every source of the SafeDI path dependency, and swift-syntax checkout files nested under `Sources/VersionMarkerModules/`, which slip past the `checkouts` check – so membership comes only from `PluginTargetGraph`, which lists those targets too, and is `nil` (unknown) for any file no target lists, never this module. The graph lists each target's files spelled by the code that spells the CSV, so `generate` matches a declaration's file by exact string and never compares spellings: change one spelling and the other in `inputSwiftFilePaths(of:relativeTo:)` together. The plugin declares the CSV and the sidecar as inputs of its `generate` command and writes each only when what it holds changes (`writeIfChanged(_:to:)`), so a change to the targets that changes no Swift file reruns `generate`, and a plan that changes nothing does not. The sidecar is written in the package path of `SafeDIGenerateDependencyTree.swift` only: the Xcode project plugin has no package information, so its runs know no module, and a SafeDITool older than the sidecar ignores it. A sidecar that exists but does not decode is an error (`UnreadableTargetGraphError`), not a silent unknown.
- **Attributes for generated declarations are resolved once.** The `@Instantiable` macro has two overloads: one takes `generatedInitializerAttributes:` and `mockAttributes:`, the other `generatedAttributes:` (no default, which is what selects it), so no declaration spells `generatedAttributes` beside either. `InstantiableVisitor` resolves them into `Instantiable.generatedInitializerAttributes` and `Instantiable.mockAttributes` (`generatedAttributes` when given, else the specific argument), and generators read only those fields, never the macro's arguments. Each is written verbatim before its generated declaration's modifiers, on the same line (`@MainActor public convenience init()`, `@MainActor static func mock(`); a new kind of generated initializer reads `generatedInitializerAttributes`, and a new kind of generated mock `mockAttributes`. A `mockOnly` declaration merged into a production declaration contributes neither: `mergedWithMockProvider` copies only the hand-written mock's fields.
- **Names generated code introduces are reserved** (`ReservedName`, the one place they are spelled: `ScopeGenerator` emits them from its constants, and the macro checks against them). Generated bodies declare builder functions `__safeDI_<label>` (and `@Sendable`-extracted locals `__safeDI_<label>__…`) next to the `let <label>` they build; the prefix keeps them out of the namespace of user labels, and it stays: any other scheme is more collision-prone and rewrites every generated file. Three kinds of exact name are reserved too, because generated code puts them in a scope with user names and cannot rename them: `safeDIOverrides` (the `mock()` parameter callers spell, which a mock parameter of that label redeclares and a body binding hides), `safeDIBuilder` (the property and initializer parameter of every `SafeDIMockConfiguration`, which a configured type's instantiated or default-parameter label redeclares, and the `if let safeDIBuilder` override binding in each construction expression, which therefore never shadows an argument), and the wrapper types generated code constructs by name (`Instantiator<T>(…)` and the other five, `Property.PropertyType.wrapperTypeName`), which a binding of that name hides. The macro tests pin that each is rejected; the evidence that each collides is in PR 410's description, because a fixture that declares one is macro-invalid and so cannot be a pipeline test. `SafeDIToolReservedNameTests` shows, with macro-valid fixtures, that the other names generated code introduces do not collide, which is what stops anyone reserving more than is needed: the `instance` closure parameter, and the generated members `SafeDIOverrides`, `SafeDIMockConfiguration`, `ForwardedProperties`, and `mock`, which a same-named property does not redeclare and which generated code never names where a binding could hide them. A new generated identifier in a scope with user names must be added to `ReservedName`, with such a test. The `@Instantiable` macro rejects every name it can see that generated code binds or refers to: property labels and `fulfilledByDependencyNamed:` names (`InstantiableVisitor`), the names of `instantiate(…)` parameters without a default value (also the visitor), and the argument labels of labeled, default-valued, non-dependency parameters of the construction initializer, `instantiate(…)` methods, and mock methods, which a mock root takes as `mock()` parameters (`validateReservedParameterLabels`, the same parameters `validateDefaultExpressions` checks). The property macros do not check, so nothing is reported twice. Only a prefixed parameter label gets a fix-it (rename the argument label to the label without the prefix, keep the parameter's name): renaming a dependency can change which dependency it fulfills or receives, because SafeDI matches by label, with no error, and an exactly reserved label has no evident replacement. `generate` does not check: SafeDI is upgraded per project at once, so every module's names have passed the macro.
- **Nested-type qualification.** `generate` qualifies each dependency's property type, `fulfilledByType:` type, and alias `ofType:` type with `TypeDescription.qualifyingInstantiatedType(within:amongInstantiableTypes:)`, and maps the initializer's arguments by the qualified property types. It qualifies only the type `asInstantiatedType` returns (`Instantiator<Service>?` → `Instantiator<Feature.Service>?`, `LazilyInstantiated<any Service>` → `LazilyInstantiated<any Feature.Service>`, so a by-value receiver of `any Service`, qualified the same way, still matches `lazilyInstantiatedInstanceType`), choosing the most qualified of `nestedOptions` that an `@Instantiable` fulfills, so a nested type wins over a top-level type of the same name, as the compiler resolves it. It also qualifies a hand-written mock's return type (`mockReturnType`, which the macro requires to be `Self` or the declaration's unqualified name, so a nested type's mock returns `Consumer`, not `Feature.Consumer`) and each of its arguments' types (`mockInitializer`), each type by itself rather than through the dependency map, because a `mockOnly` declaration has no dependencies and its mock is matched to those of the declaration it merges into. Doing it while normalizing, before `resolveSafeDIFulfilledTypes`, keeps `mockInitializer`, `mockReturnType` and `mockDeclarationLocation` together through both mockOnly merge branches. Unqualified, `mockReturnTypeIsCompatible` fails against `Feature.Consumer`, and the hand-written mock is silently skipped. Other generic arguments (an `ErasedInstantiator`'s forwarded properties) and non-instantiable types are not qualified. `replacingInstantiatedType` walks the same path through a type as `asInstantiatedType`: both read `TypeDescription.builtGeneric`, which names the built generic of each wrapper and whether its own instantiated type is read through it (`LazilyInstantiated`, whose generic may be `any Service`), so a new wrapper type is added there once.

- **Generated imports spell the access level each file needs** (SE-0409; `GeneratedImportAccess`). The header is made per file from the file's body (`DependencyTreeGenerator.fileHeader(for:)`), which is parsed only when the module spells levels and the body spells `public`, `package` or `@usableFromInline`; a type is attributed to the modules that declare it as SafeDI read them (an extension's `@Instantiable` declares none, and a declaration of a module SafeDI does not know attributes nothing), to SafeDI for its wrappers (`WellKnownTypeNames`), to no module for the standard library's types, to a module a qualified spelling names, and otherwise to Foundation for its well-known types, to every module the own files import at the declaration's level or wider, and, unless it is one of Foundation's well-known types, to every module that a dependency's file declaring an `@Instantiable` that names it (in a dependency or an initializer parameter) imports at `package` or wider, since a seam or public mock names types its tree receives from other modules – an over-approximation the Manual states. A fixture that spells an import's level spells its own `import SafeDI` (`VerificationCompilerSettings(prependsSafeDIImport: false)`), and `SafeDIToolImportAccessLevelTests` compiles each cell with and without `InternalImportsByDefault`, and each cell whose public mock needs a `public` import in a release build too (`ModuleFixture(isReleaseConfiguration: true)`); a public mock that names no imported type gets no such import, so a release build cannot warn at it, and its cell compiles in debug only.
- **`#sourceLocation` paths are compared as strings.** The compiler groups every path a module uses – each source file as it was handed to the compiler, and each `#sourceLocation` file – by file name, and warns at a directive whose file name maps to more than one path (a build error under warnings as errors). It does not resolve relative paths or symbolic links. `AliasDeclarationReferences` emits a directive for an alias only when `generate` knows the compiler’s spelling: a plugin manifest’s `projectRoot` (`ProjectFilePaths.buildSystemPath(of:)`), unless the root is spelled differently from its `realpath(3)` resolution (`ProjectFilePaths.reportsResolvedProjectRoot`, from the one resolution `ProjectFilePaths` makes per run) – Xcode reports a package under `/tmp` as `/tmp/…` and hands the compiler `/private/tmp/…`, and a manifest from `scan` holds no second spelling that would reveal it – or `--compiler-receives-input-paths-unchanged` (passed by the Bazel rule). It still omits one whose file name another directive’s file or one of the module’s own files shares (`--mock-scoped-files` when `generate` scans for itself, the manifest’s `mockScopedFilePaths` otherwise, every input file under the flag), which covers a module file known under two spellings such as Xcode’s `/tmp/…` against the working directory’s `/private/tmp/…`. Every other alias gets a trailing `// Declared at <path>:<line>` comment with the path as the integration handed it (project-root-relative under a plugin). Tuist shares its build cache across machines, so nothing generated for a Tuist build, nor its `.safedi`, may hold an absolute path: its script hands `generate` `$SRCROOT`-relative paths and gets comments. Never spell a directive path with `NormalizedFilePath`, which drops a leading `/private` the compiler keeps. The examples treat warnings as errors and each declares an aliased `@Received` in its root module, so CI catches a wrong spelling.
- **File path spelling.** `Sources/SafeDICore/Utilities/FilePathSpelling.swift` is the only place a path is normalized or resolved, or made relative to a directory; the SafeDIGenerator plugin compiles it, and `OutputFileNaming.swift`, through symbolic links. `PathSpellingCallTests.sources_normalizeAndResolvePathsOnlyInFilePathSpelling` (in the plugin test target, which can strip comments and strings) fails if code under `Sources` or `Plugins` outside that file calls `standardizedFileURL`, `.standardized`, `standardize()`, `standardizingPath`, `resolvingSymlinksInPath`, `canonicalPathKey`, `destinationOfSymbolicLink`, or `realpath`; it does not detect a path made relative by hand. A comparison is sound only when both sides were spelled by one rule. `NormalizedFilePath` is absolute, without `.`/`..`/repeated `/`, and, on Apple platforms, without the `/private` Foundation drops from a path that names an existing file under `/private/tmp`, `/private/var`, or `/private/etc` (a path to no file keeps it); it resolves no other symbolic link. `ProjectFilePaths` resolves the reported project root once per run and spells each path inside the project under the resolved root as a `ProjectFilePath` (`projectFilePath(of:)`), which only it can create; every comparison that must agree — the "already an input" exclusion, mock-scoped and configuration-file matching, scan's stamps, and the cache-freshness check — takes `ProjectFilePath`s, because the inputs and `--mock-scoped-files` arrive under the root as the build system reported it while `additionalDirectoriesToInclude` is found from the working directory, which `getcwd(3)` reports resolved (and Foundation's directory enumerator on Apple platforms returns resolved paths). So `scan` is handed the reported root as `--project-root`, and `generate --output-directory`, when it scans for itself, takes the same option: without it `generate` takes its working directory, which is resolved, and a target whose files are reported through a symbolic link finds none of them among the CSV's, generating none of its roots and mocks. The Xcode project plugin's fallback, which has `generate` scan for itself, does not pass it yet, so that case is not fixed there: the fallback runs the SafeDITool pinned in `Package.swift`, 2.3.0-alpha-1 rejects the option, and the plugin passes it once the pinned binary accepts it. Never resolve per file: scan's freshness check is stat-only for speed. Each consumer gets one spelling. The manifest's file names (roots, mocks, configurations, `mockScopedFilePaths`) and scan's cache name a file relative to the resolved root when it lies inside it, else by its normalized path (`manifestPath(of:)`), and module info names files as the parse did (scan's cache names, or the CSV's spelling on a fresh parse). `projectRoot` is the reported root made absolute against the working directory, without a trailing `/`, and not normalized (`reportedProjectRoot`). What the build system, the compiler, or an IDE matches as a string — `additionalInputFiles`, which the plugin declares as build inputs, `#sourceLocation` paths, and the file paths `run()` prints in diagnostics — is that root joined with the file's path inside it (`buildSystemPath(of:)`), the spelling the build system already uses for the project's other files; a file outside the project gets its normalized path. Without a manifest's project root, those are the paths as handed under `--compiler-receives-input-paths-unchanged`, which is also how the compiler prints its own diagnostics (under Bazel, relative to the execution root, while the working directory is the action's sandbox, which Bazel deletes). Without the flag either, `run()` prints a diagnostic's path made absolute against the working directory and normalized. `Generate.BuildSystemFilePaths` is that one decision, which `run()` and `#sourceLocation` paths both read. A diagnostic `generate()` returns names its file as it was handed to the parser: under a plugin, when `generate` reads scan's cache, the path scan parsed the file under (`ProjectFilePath.path`, normalized under the resolved root), and otherwise, without a manifest or when `generate` parses afresh, the path as the input CSV spells it. Only `run()` respells it, as the build system does (`Generate.BuildLog`). Output paths keep the spelling the plugin passed; `generate`'s check that no two manifest outputs name one file compares them as `OutputFilePath`s (`OutputFilePaths.outputFilePath(of:)`): the output's directory resolved with `realpath(3)`, once per spelling of the directory, joined with its name, or its normalized path when the directory does not exist, compared ignoring letter case and Unicode normalization (`CaseInsensitiveFileName`, under which `OutputFileNaming.swift` also names outputs apart on every platform, so that macOS's default volume, which ignores letter case, holds each output as its own file). Scan's cache records `additionalDirectoriesToInclude` as scan found them, relative to the working directory, so `generate` finds the same files. `// Declared at` comments use the manifest name. SwiftPM and Xcode report resolved roots; reported links come from scripts and other integrations.
- `typeDescriptionToFulfillingInstantiableMap` is a dictionary — iterating `.values` has non-deterministic order. Any code that reduces, sorts, or builds state from `.values` must produce the same result regardless of iteration order. CI runs tests 5 times specifically to catch non-determinism.
- `Scope` hashes by object identity, so a `Set` of scopes iterates in an order that changes from run to run even under a fixed hash seed. Validation that throws at the first error must visit trees in a sorted order: `validatePropertiesAreFulfillable(typeDescriptionToScopeMap:cyclesOnly:)` visits roots, then the other types whose mocks are generated, each in type order; the mock roots in `generateMockCode` are visited in type order too.
- `Scope` hashes by object identity, so a `Set<Scope>` iterates in an order that changes from run to run even under a fixed hash seed. A loop over one may build state, but anything it reports — the first error, the first match — must be chosen by a deterministic key (as `createTypeDescriptionToScopeMapping` does for `@Forwarded` errors), not by which element the loop reached first.
- A memoized walk with a cycle sentinel must not cache a result that took nothing from a scope still being walked: that result is wrong from any other entry point, and which entry point walks first can follow set order. `collectReceivedProperties` keeps such results only until the scope they lack finishes its walk.
- `resolveSafeDIFulfilledTypes` can produce multiple map entries with the same `concreteInstantiable` under different keys (e.g., a merged entry under `MyService` and an unmerged entry under `ServiceProtocol`). These entries may have different mock info. The mock scope map uses scope-reuse by `concreteInstantiable` and a deterministic sort to handle this.
- `mockInitializer` on an `Instantiable` can be inherited from a mockOnly merge — it doesn't always mean the type declared its own mock. `generateMock` is never inherited. Use `mockReturnTypeIsCompatible(withPropertyType: concreteInstantiable)` to distinguish genuine hand-written mocks from inherited ones.
- **A `LazilyInstantiated` property declares two receivable properties.** `x: LazilyInstantiated<X>` can be received as itself or by value as `x: X`. Which declarations offer the by-value form is decided in one place: `Dependency.lazilyInstantiatedInstanceProperty` (and `Scope.PropertyToGenerate.lazilyInstantiatedInstanceProperty`, `ScopeGenerator.declaredLazilyInstantiatedInstanceProperty`). An `@Instantiated` property always does, because the generated wrapper is never optional. A `@Forwarded` or aliased one is bound with its declared type, so it does only when that type is not optional. A received one never does. `Scope.createdProperties` and `properties`, `ScopeGenerator.propertiesToDeclare` and its forwarded subtraction, sibling ordering, mock promotion (`collectReceivedProperties`), and the `@Instantiable` macro's check that a root's aliases are fulfilled on the root (`InstantiableMacro`, through `Dependency.receivableProperties`) all go through those accessors; do not re-derive the form from a `Property` alone. A by-value receiver is passed `x.instance`: `Scope.createScopeGenerator` threads `lazilyInstantiatedInstanceProperties` – the by-value properties that are in scope only through a wrapper – down to initializer argument lists, aliases, and mock nodes. A nearer declaration with the same label removes a property from that set, exactly as the nearer `let` shadows the wrapper in the generated Swift; an alias that keeps the label it retypes is looked up in the inherited set, because it is not in scope where its own value is read. `Scope.providedProperties`, validation’s `childReceivableProperties`, and the `propertiesToDeclare(in:)` and `forwardedProperties(in:)` helpers hold both forms too, and hidden-label validation accepts a by-value receive whose closest declaration of the label is the wrapper (`LabelDeclaration.lazilyInstantiatedInstanceProperty`). An `onlyIfAvailable` alias is the nearest declaration of its label, `nil` included, so nothing farther up – an instance included – stands in for it. A wrapper whose instance type is optional (`LazilyInstantiated<X?>`) offers no by-value form, wherever it is declared. `Instantiable.forwardedReceivableProperties` and `DependencyTreeGenerator.propertiesToDeclare(in:)` are the only places that list a type's forwarded and declared properties with their by-value forms; use them rather than filtering `dependencies` again. `orderedPropertiesToGenerate`'s `siblingIndexByProperty` maps each lazily instantiated sibling's by-value property to that sibling too, unless another sibling declares that property itself, and the pairwise fallback applies the same rule so that both paths build the same set.
- **Validation maps a wrapper to the constant with the same optionality.** `Property.asValidatedForDependencyCycles` turns `x: LazilyInstantiated<X>?` into `x: X?`, not `x: X`: an `onlyIfAvailable` receive of the wrapper inside the tree it builds must not equal the stack entry, or a tree the constant twin accepts (the receiver is passed `nil`) is rejected as a cycle. `TypeDescription.lazilyInstantiatedInstanceType` is the generic argument as spelled (`any Service`), which is what a by-value receiver must match; `asInstantiatedType` normalizes it for the scope lookup. Validation’s instantiation stacks (`propertyStack`, `instantiationStack`, `ReceivableAlias.declaringInstantiationStack`) hold the mapped constants, while `receivableProperties`, `createdProperties`, `providedProperties` and `boundProperties` hold properties as declared, plus the by-value form of each wrapper. Map a declared property before comparing it with a stack, and never before looking it up in one of those sets. Generation differs: `NearestDeclarations.build(_:)` records every form the wrapper being built provides – the wrapper, its by-value form, and their optional forms (`CycleParameter.forms(providedBy:)`) – so `NearestDeclarations.binding(of:)` passes `nil` for an `onlyIfAvailable` receive of either form inside the tree the wrapper builds, in production and mock generation alike.
- **A mock's parameters never mention `LazilyInstantiated`.** Adopting it on an owner must not change the generated `mock()` of an unchanged receiver. `createMockRootScopeGenerator` treats a dependency received both ways as one: it promotes the wrapper once whenever any receiver requires the wrapper or its instance, optional or not, and skips the by-value form and its optional form, also when the mock root declares the wrapper itself, and counts neither among the properties the mock is passed (`mockParameters`, which `childrenRequiringEachOther` takes as forwarded, so an `onlyIfAvailable` alias of either would count as always created). A required `x: LazilyInstantiated<X>`, or a required `x: X` or `x: X?` that no forwarded property fulfills (above), promotes `x: LazilyInstantiated<X>`; a required `x: LazilyInstantiated<X>?` beside none of them is promoted as itself, like any optional form whose non-optional form nothing requires. An `onlyIfAvailable` receive of the wrapper is then passed the node the mock builds, so no entry for the dependency is typed `LazilyInstantiated`; only a receive of the other wrapper kind, beside a promoted one, still is (above). A dependency the mock cannot build is classified in `generateMockRootCode` by its by-value form (`receivedParameterProperties`), so it is a `T` parameter or a `T?` override; the mock then binds `<label>_lazilyInstantiated` and passes that name to the types that receive the wrapper, and to aliases of it (`lazilyInstantiatedBindingNames`, threaded beside the flat-parameter rename map; the root's own receive goes through `returnDisambiguationMap`). `removingRenames(hiddenByDeclarationsOf:parameters:from:)` prunes `lazilyInstantiatedBindingNames` wherever it prunes that map, so a receiver below a nested scope that declares the wrapper – an `@Instantiated` child, an alias, or a builder's forwarded parameter – is passed that closest declaration, as in production. It is never rebound under the dependency's label: only one of the two bindings that share that label is renamed, so a rebinding inside a builder function would hide the instance parameter from the by-value receivers built there, which have no rename of their own to rebind. A by-value receiver of a wrapper renamed by sibling disambiguation rebinds the wrapper under its label, and an alias of its instance reads `.instance` from the renamed binding directly (`disambiguatedLazilyInstantiatedBinding`). `erasedToConcreteTypeMap` is keyed by both forms' types, and promotion falls back from a wrapper to the erasure of its instance (`concreteTypeErased(to:)`), so the wrapper is buildable whenever its instance is — also when the wrapper is optional, or when only a constant declares the erasure — and `mockReturnTypeIsCompatible` is asked about the instance type. `mockCanBuild` treats a lazily instantiated property as it does a constant: a mock has no values to forward, so it cannot lazily instantiate a type with `@Forwarded` properties, and `mock()` takes that dependency’s instance. A forwarded lazily instantiated property fulfills receives of itself, of its optional form, and of its instance beneath the mock root (`isFulfilledByForwardedProperty`), so neither `lazilyInstantiatedReceivedProperties` nor the by-value parameter set includes them; mapping such a receive to its by-value form first would lose that the wrapper is forwarded, and the mock would take a second value and ignore the forwarded one.
- **`TypeDescription ==`/`hash` ignore `any` at every depth.** `any P` equals `P`, `(any P)?` equals `P?`, `Instantiator<any P>` equals `Instantiator<P>`, and `(any P).Type` is treated as `P.Protocol` (not `P.Type`, which is `any P.Type`). `some P` stays distinct. Sets and dictionaries keyed by `TypeDescription` or `Property` therefore merge the two spellings, keeping whichever was inserted first, while `asSource`/`asIdentifier` keep each declaration's own spelling. `<` compares the spelling without `any` first, then the full spelling as a deterministic tiebreak, so two spellings of one type are equal under `==` but ordered under `<` (determinism was chosen over the Comparable contract). Any new map or set keyed by a type's spelling string (`asSource`) instead of `TypeDescription` must normalize `any` the same way, or it will miss matches `==` makes.
- **Diagnostics are chosen by source location, never by name order.** Every root (production, `generateMock` type, mock root, mock root's child trees) reports the first error its own walk finds, and `DependencyTreeGeneratorError.reportingAll(of:)` joins them in source order (`SourceDiagnostic.joiningInSourceOrder`), so renaming a type never changes which error appears or where. Two rules keep that true: a memo shared across roots (`ChildrenRequiringEachOtherValidation.validatedScopes`, `walkedAliasFulfillingProperties`) keeps only walks that completed — an entry from a walk that threw must be dropped, or a later root would skip the work and the reported set would depend on root order; and where one of several candidates must be picked (which promoted child a mock root validates first, which received property names a sibling, which reader a warning names), pick by declaration location or declaration order (`inOrderTheMockTreeFirstReceives` orders a mock root's promoted children by where its tree first receives them, for generation and validation alike), not by label or type-name order. The rename-invariance fuzzer oracle (#464) checks this class end to end.
- **`erasedToConcreteExistential: true` is orthogonal to the property's `PropertyType`.** The flag controls whether SafeDI wraps the concrete in the property's existential type at the call site; it does not determine whether the property itself is constant or lazy. The four combinations:

  | Decorator + property | `Property.PropertyType` | `isConstant` | Can be the deferred hop? |
  |----------------------|-------------------------|--------------|------------------------------|
  | `@Instantiated let x: Concrete` | `.constant` | `true` | No. |
  | `@Instantiated let x: Instantiator<T>` | `.instantiator` | `false` | Yes. |
  | `@Instantiated(erasedToConcreteExistential: true) let x: AnyProto` | `.constant` | `true` | No. |
  | `@Instantiated(erasedToConcreteExistential: true) let x: ErasedInstantiator<A, AnyP>` | `.erasedInstantiator` | `false` | Yes. |

  Any kind can close an accepted cycle and sit on a pruned back-edge; the hop that defers it is what the column says, and the erasure flag says nothing about either.
