# SafeDI — Claude Code Guidelines

## Documentation

The core documentation is `Documentation/Manual.md`. Read it before making changes to understand SafeDI's API, macros, configuration options, and mock generation. The manual is the source of truth for user-facing behavior — if you change behavior, update the manual. Each topic has one home section, which the others link to rather than restate. Tests read parts of it by position. Two tests take the Swift code blocks of "Generating a dependency tree per module" up to the section's first line that begins with `#`, its first subheading: one expects exactly six, takes the first as its fixture, and compares the second with the code generated for that fixture and the third with the call a root in another module generates for it; the other compares the fifth and sixth with the code its own builder fixture generates. The graph fuzzer's known issues cite the first two shapes of the section's list of ways a seam differs from building its tree inline.

### CI

- Every CI job runs on a Linux runner unless it genuinely needs macOS: Xcode or `xcodebuild`, an Apple platform SDK, the Xcode project plugin, or the macOS release binaries and their notarization. Linux runners scale; macOS runners are the scarce resource that pull requests and publishes queue on.
- A job on a `macos-*` runner states why in a comment in the workflow.
- New Linux jobs use the same container and setup as the existing Linux test job ("Build and Test on Linux" in `ci.yml`).
- A required check that a matrix job reports needs a Linux stand-in that reports the same names when a Markdown-only change skips the job. A skipped job satisfies a required check under its own name, but GitHub evaluates a job's `if:` before expanding its matrix, so a skipped matrix job reports only its unexpanded name. The stand-in takes the job's `name:` and matrix through YAML anchors, runs only when `changes` reports a Markdown-only pull request, and needs no container, since it only reports (as "xcodebuild-markdown-only" does for "xcodebuild").
- `Examples/Example Package Integration` has spaces in its name so that CI builds a package under a path with spaces. Markdown links to it spell the spaces `%20`, which GitHub renders but md-dead-link-check cannot decode, so `.github/md-dead-link-check.toml` excludes exactly those links and `.github/scripts/check-excluded-markdown-links.py`, a step of "Check Markdown links", checks that each still names a path that exists.

## Architecture

SafeDI is a compile-time dependency injection framework for Swift. It uses Swift macros (`@Instantiable`, `@Instantiated`, `@Received`, `@Forwarded`) to declare dependency graphs, then generates initializer code and mock methods via a build tool plugin.

### Key modules

| Module | Role |
|--------|------|
| `SafeDICore` | Models (`TypeDescription`, `Property`, `Instantiable`, `Dependency`), visitors (`FileVisitor`, `InstantiableVisitor`), generators (`ScopeGenerator`, `DependencyTreeGenerator`) |
| `SafeDIMacros` | Swift macro implementations (`@Instantiable`, `@Received`, etc.) |
| `SafeDITool` | CLI entry point with `scan`, `generate`, `query`, and `dump` subcommands — scans Swift files for `@Instantiable` types, builds dependency tree, generates output; `query` reports what one type needs |
| Plugins (`SafeDIGenerator`) | SPM build tool plugin that wires the tool into the build |

### Code generation flow

1. **Plugin** writes CSV of swift files → runs `SafeDITool scan` to build manifest → runs `SafeDITool generate` to produce code. The Bazel rule (`bazel/safedi.bzl`) and the Tuist plugin (`TuistPlugins/SafeDITuist`) run no `scan`: each runs `generate --combined-output --module-info-output` once per module, passing the `.safedi` files of the modules it lists as dependencies.
2. **`SafeDITool generate`** parses all files via `FileVisitor` → builds `DependencyTreeGenerator` → generates per-root code + mock code
3. **DependencyTreeGenerator** creates `ScopeGenerator` trees → each generates its code via `generatePropertyCode`. A seam (`@Instantiable(generateDependencyTree: true)`) is a root of its own module's generation (`generateSeamRootCode`, an initializer per access tier plus a guard enum) and a leaf of every other tree, which calls that initializer; see the seam paragraph under Common Pitfalls.
4. **Mock generation** (`generateMockCode`) creates `mock()` static methods with `@autoclosure @escaping` parameters, `T? = nil` subtree parameters, and `MockContext` for disambiguation

`generate` records, outside the visitors so scan's cache never holds it, the module and package that declare each `@Instantiable` (`Instantiable.moduleName`, `packageName`, and `mockDeclarationModuleName`/`mockDeclarationPackageName`, which travel with `mockInitializer` through `mergedWithMockProvider` and are cleared by `withoutHandWrittenMock`), and the module it generates code for (`ModuleInfo.moduleName`, `packageName`, `dependencyModuleNames`, the module's direct dependencies). `ModuleMembership` (`ModuleMembership.swift`) decides them, and `ModuleInfo.declared(by:dependingOn:)` applies them once the module, additional directories included, is assembled, before normalization and before `--module-info-output` is written; nil means unknown, never "this module". Three sources are independent. Own files: a run per module (Bazel, Tuist) passes `--module-name` and `--package-name`, which, when either is given, describe every input file (CSV and `--include`) and no other, so an `additionalDirectoriesToInclude` file has no module; otherwise a run with a manifest reads the target graph (below); otherwise own files have no module. Dependencies: the modules the `--dependent-module-info-file-path` files record (sorted, without duplicates; a file that records none adds nothing), whichever way own files were attributed, joined with the planned target's dependencies when the target graph was read; the files' names are the direct dependencies Bazel's `deps` and Tuist's `dependencies:` list and cannot drift from the files. A dependent `.safedi` carries what its producer recorded. The target graph, which a run with a manifest reads when neither option is given, is the file the SafeDIGenerator plugin writes beside its CSV (`<CSV path>.targets.json`, `PluginTargetGraph`, `Sources/SafeDITool/PluginTargetGraph.swift`, which the plugin compiles through a symbolic link, so the plugin encodes and the tool decodes one declaration; written by `writeTargetGraph`): the planned target and every target of `sourceModuleRecursiveDependencies` (the CSV's targets, the SafeDI path dependency and the leaked swift-syntax `VersionMarkerModules` included), each with SwiftPM's package identity (the `Package.id` of the package that declares it, found by walking `context.package` and its dependencies; `-package-name` carries it C99-mangled: `swift-syntax` becomes `swift_syntax`), its Swift files spelled by the same code that spells the CSV (`inputSwiftFilePaths(of:relativeTo:)`), and its direct dependencies' module names, sorted. The plugin API cannot tell whether a dependency target applies SafeDI's plugin (every target's `pluginGeneratedSources` is empty), so the graph does not say. Both of the plugin's `generate` forms read it: the manifest form (`<csv> --swift-manifest`), and the fallback form (`<csv> --output-directory … --mock-scoped-files …`, which scans for itself with the working directory as its project root and runs on every cold Swift Build build and every Xcode build of a package). A file belongs to the target that lists it, matched exactly: a fresh parse names a file by its CSV entry, and scan's cache names it relative to the package directory, or normalized outside it, which is how the plugin spells the entry, so no path is spelled again (targets that split one directory with `sources:`, or nest, are told apart, and the fallback form's working-directory root changes nothing); a file no target lists, or two targets list, has no module. The Xcode project plugin writes no graph and passes no option, so membership is unknown there, as it is for a hand-written manifest. `query` records every declaration of an included module as that module's (`IncludedModule.name`, or the module name a `.safedi` records), with the package a `.safedi` records and none for a directory (`readIncludedModules()`); it checks no access, and its report still names modules as `IncludedModule` does. An `IncludedModule` name can be several path components (`Home/Sources`) and need not be the compiler's, so nothing may compare a module name `query` records with one a build recorded: the enforcement reads it only to group a query's declarations by module.

### Conditional compilation

`FileVisitor` takes a `ConditionalCompilationEvaluator`; `InstantiableVisitor` takes a `ConditionalCompilationHandling`, which the macro sets to `.scanAllClauses` (the compiler already picked the active clause) and `FileVisitor` sets to `.evaluate(evaluator)`. The evaluator treats the supplied `activeCompilationConditions` as complete (a bare condition not in the set is inactive), scans every clause of platform-conditioned blocks (`os()`, `canImport()`, …), and evaluates mock-only content (`SafeDIContentDetector`) as if `mockConditionalCompilation` were active. A guarded initializer counts as SafeDI content only when `ConstructionInitializerCandidates` finds some evaluation could select it for construction — it must be able to fulfill the dependencies (bounded below by those outside every `#if` and above by those in every clause) and must not follow an unguarded initializer that fulfills them in every evaluation; initializers in `@Instantiable` extensions never count. Each evaluation that decides a block guarding SafeDI content is a `ConditionalCompilationDecision`; `generate` prepends `ConditionalCompilationDecision.compileTimeAssertions` (`#if …` / `#error`) to every generated file so the compiler rejects code generated under a condition it evaluates differently. There is no "unknown condition" state and no error at generate time: the compile-time assertion is the fail-closed mechanism. `parseModule` first parses the module's own files (`configurationFilePaths`) named `SafeDIConfiguration.swift`, chosen by path alone, and walks them to find the module's `#SafeDIConfiguration`: `SafeDIContentDetector` classifies a configuration as production content, so its `#if` blocks never depend on `mockConditionalCompilation`. The configuration found there builds the module's evaluator, every other file is read, parsed, and walked once with it, and the `SafeDIConfiguration.swift` trees are walked again from memory only when the mock condition is not the default. When no `SafeDIConfiguration.swift` holds a configuration (the fallback), every file is walked with the supplied conditions and the default `DEBUG` mock condition, which finds a configuration elsewhere; if it names another mock condition, every file that declared SafeDI content is read, parsed, and walked again — no text heuristic picks a subset. `SafeDIConfiguration.placementWarning` reports exactly that case (configuration outside `SafeDIConfiguration.swift` with a non-default mock condition) as a `SourceDiagnostic` with `.warning` severity located at the invocation (`SafeDIConfiguration.declarationLocation`, which travels in module info and scan's cache). `SafeDIConfiguration.unreadableAdditionalDirectoryWarnings` likewise warns, at the invocation, about each `additionalDirectoriesToInclude` entry of the selected configuration from which no Swift file can be read (nothing at its path, or a non-Swift file; an empty directory is fine). It judges `ParsedModule.additionalDirectories`, the `AdditionalDirectory` entries paired with the path they resolved to: scan's cache stores scan's resolution (against scan's working directory, which its freshness check also enumerates), and a fresh parse uses this run's. It is a warning, not an error, because `scan` reads every configuration's directories in every clause and a directory may exist only on some platforms. `generate` returns warnings instead of throwing them and `run()` prints them; `scan` never warns, so a build warns once per `generate`. Every syntax tree but those of `SafeDIConfiguration.swift` files is released as soon as it is walked, so memory scales with concurrency rather than module size. A file whose text holds no marker is not parsed, but it can declare the plain type an extension extends (a namespace enum in a file of its own), whose access bounds what the extension declares. So the read that finds no marker also collects each word that follows `enum`, `struct`, `class` or `actor` and whitespace (`wordsFollowingTypeDeclarationKeywords`, a superset the parse decides; another spelling, such as backticks, is left to the compiler), and `parseModule` then parses only the skipped files that may declare a type an extension that is or holds an `@Instantiable` extends (`OutputFileDeclarations.extendedTypeNames`, the outermost name of each, recorded in every clause, so the files found never depend on conditions). Reading the skipped files a second time instead cost the lifelike benchmark's `scan` 20%. Such a file contributes its `plainTypeDeclarations` alone, consults no condition, and is cached and stamped as every input is. `parseModule` keeps only the plain declarations whose outermost type is among those names, since no other bounds anything, and `generate`'s refresh of a condition-sensitive file keeps the ones scan cached, which no condition changes. `scan` and `generate` both go through it, and it rejects more than one configuration in scope. `scan` records its project root in the manifest so `generate` matches configuration files by the same resolved paths.

Build tool plugins cannot read the conditions the compiler receives while they plan the build, so the `SafeDIGenerator` plugin also passes `generate` the literal arguments `--build-setting-active-compilation-conditions=[${SWIFT_ACTIVE_COMPILATION_CONDITIONS}]` and `--build-setting-other-swift-flags=[${OTHER_SWIFT_FLAGS}]` (`BuildSettingCompilationConditions`). Swift Build (Xcode and SwiftPM's `swiftbuild` backend) expands them when the command runs, and Xcode project builds expand them through the shell script that runs the command; SwiftPM's native backend passes them through literally. When both arrive expanded, their conditions plus the `-D` flags in `OTHER_SWIFT_FLAGS` *replace* the command-line and manifest conditions (Xcode reports a package's debug-configuration defines to plugins in Release too, so a union would be wrong); otherwise `generate` falls back to them. The plugin passes the options to every SafeDITool it runs, including the prebuilt binary pinned in `Package.swift` (Swift 6.2 sometimes hands the plugin that one even with the `sourceBuild` trait) and the `.safedi/` download named by `safeDIVersion` in `Plugins/Shared.swift`, so those must never name a release older than 2.1.0-rc-3, the first to accept them. Which files exist — roots, `generateDependencyTree: true` types among the module's own files (`declaresDependencyTreeType`, named together with the root files in one `outputFileNames(forFilesAt:)` call, since uniqueness is per call), `generateMock: true` types, `additionalMocksToGenerate` entries, `#SafeDIConfiguration` files — is still decided by `scan` at planning time, but independently of any condition: `scan` plans an output for each such declaration in every clause of every `#if` block (`OutputFileDeclarations`, which `SafeDIContentDetector` collects during the walk of each block it already makes and `FileVisitor` adds for the clauses it scans), and treats the files in every configuration's `additionalDirectoriesToInclude` as inputs, parsing those only an inactive configuration lists solely to plan their roots. `generate` writes every planned output, without code (only the header and its compile-time assertions) when the declaration is inactive under its conditions, and generates the additional mocks only of the configuration it selects. It still rejects with a `ManifestError` a declaration whose file the manifest does not list (the manifest's `mockScopedFilePaths` lets it check mocks and configurations), which with superset planning means the file changed after `scan` or the manifest is hand-written. It also rejects a manifest in which two outputs name one file, which only a hand-written manifest can do: `scan` lists each additional mock once, however many times a configuration lists it. The `PluginScanner` fallback ignores `#if` and unions every configuration's arrays, so it plans the same superset. Because a cached file scan may declare a configuration in an inactive clause, `generate` parses the module afresh when a stale file declares a configuration in any clause, not just an active one; and when it parses `additionalDirectoriesToInclude` afresh it names those files as the manifest does, so their roots match its entries.

Because `generate` usually has more conditions than `scan` (always `SWIFT_PACKAGE`, `DEBUG` in debug), scan's cache keeps per-file results keyed by what each file consulted. `ScannableClauses.consultedConditions` records every bare condition a clause selection depended on (minus the mock condition for mock-only blocks, which is forced active); `FileVisitor` and `InstantiableVisitor` accumulate them only for blocks whose selection can change what they report: blocks with SafeDI content, blocks with syntax errors, and (separately, as `importOnlyConsultedCompilationConditions` with `importSegments` holding the block source) blocks that guard only imports. `FileVisitor` also collects `mockImports`: each block guarding only imports is selected again as a block guarding mock-only declarations is, and `importOnlyConsultedCompilationConditions` covers both selections. Generated mock files, `SafeDIMockConfiguration.swift`, the mock half of `--combined-output`, and module info carry `mockImports`; dependency-tree files keep `imports`, so `#if DEBUG import A #else import B #endif` still gives production code `import B`. `CachedScannedModuleInfo` (see Serialization) stores the files that consulted nothing as one `ModuleInfo` and the rest as `CachedFileScan`s; `generate` walks a file again only when a condition it consulted changed value, re-evaluates only its import segments when only those changed, and parses the whole module afresh when a walked-again file declared a configuration. Any new state a visitor collects from inside an `#if` block must either be covered by `consultedCompilationConditions` or be provably independent of the selection, or the cache becomes unsound. `OutputFileDeclarations.instantiableTypeNames`, and `ModuleInfo.instantiableTypeNamesInAnyClause`, which unions them and which scan's cache and `.safedi` carry, are such independent state: `SafeDIContentDetector` records the type of every `@Instantiable` in every clause of each block `FileVisitor` reaches, naming nested types from the enclosing type `FileVisitor` hands it, and `FileVisitor` adds the declarations outside every block, so any evaluator records the same names; `generate` uses them to tell an `additionalMocksToGenerate` entry that names a declaration these conditions leave inactive, whose file it writes without code, from one that names no type. `Instantiable.otherInitializers` is such state too: `InstantiableVisitor` collects a seam's initializers other than the canonical one from every clause of every member `#if` block (`initializersInEveryClause`), since the generated initializer is unconditional and one it would redeclare in any clause is a redeclaration, so scan's cache of it is sound whatever `generate`'s conditions.

### Type requirements query

`SafeDITool query needs <TypeName>… --include <directory>… --module-info <file>…` reports what each named type needs: the modules whose declarations build it and its dependencies in production, its `@Forwarded` parameters, the dependencies no `@Instantiable` declaration fulfills, and what its mock needs. It exists so a focused app can be assembled from exactly the modules one feature needs. It is in beta, and `--help` and the manual say so: it was built ahead of a live use, so its options, text, and JSON may change in any release as real projects adopt it, and the JSON's `formatVersion` is `0` until the format is stable; keep the beta note and the `0` until Dan removes them, and make `1` the first stable format then. `query` is a command group with `needs` as its one subcommand, so further questions (dependents, providers) join as subcommands rather than flags. `--include` is spelled as `generate`'s, and each directory is a module (`IncludedModule`) named after its last path component, or after as many trailing components as tell it apart from the other modules (`Home/Sources`), so a `Modules/<Name>/Sources` layout works without configuration; a Swift file included directly belongs to its directory's module. `--module-info` names `.safedi` files, each a module read with `ModuleInfo(moduleInfoData:)` as `generate` reads a dependent module's (an unreadable or missing file is `QueryError.moduleInfoNotReadable`, with `BinaryFile.unreadableFileExplanation`), named after the file without `.safedi` and without the `_safedi` the Bazel macro appends (`IncludedModule.moduleName(ofModuleInfoFileNamed:)`), under the same suffix rule as directories, with the file name as spelled as the fallback when a directory's path reads the same (`Home` and `Home.safedi`), which is also what keeps the suffix loop finite. `ParsedQueryModule` reads either kind: a directory's declarations are attributed to the files found under it, spelled under the `--include` argument; a module info file's to the paths it records (`sourceFilePath`, the declaration and mock declaration locations), spelled as stored, since the writing build's spelling is all the file has. `--active-compilation-conditions` applies only to directories, and `generatedIn` reads a module info file's `configurations`. `QueryCommand.swift` parses each directory module with `parseModule` (the module's own files are its configuration files; `additionalDirectoriesToInclude` is deliberately not followed, since every module is included), rejects a file in two modules, combines the modules' instantiables in module-name order, runs them through `normalizingInstantiableTypes(of:)` and `resolveSafeDIFulfilledTypes(instantiables:)` (`InstantiableResolution.swift`, shared with `generate`, so the query sees the types exactly as `generate` does), and reports the types named in order, each once, from that one read. `DependencyTreeGenerator.requirements(forTypeNamed:generatesMock:)` builds a type's mock root exactly as `generateMockCode` builds the root of a type listed in `additionalMocksToGenerate` — the same `mockScopes(additionalMocksToGenerate:receivedPropertiesCache:)` setup and validation, with the type always listed, the same `mockRootInstantiable(for:scope:)` canonicalization, the same `createMockRoot(for:scope:…)` checks — and reads `ScopeGenerator.mockRootParameters(instantiable:)`, the classification `generateMockRootCode` emits; `generatesMock` only decides whether a hand-written method named `mock` is a collision (`createMockRoot`'s `GeneratedMockReason` is `nil` otherwise, and the root is built with that method). A mock root is a tree in which every dependency the type receives is built beside it, so the tool runs it twice: over the map with every hand-written mock removed (`Instantiable.withoutHandWrittenMock`, `mockOnly` entries dropped) for what the type needs in production, and over every declaration for what the mock needs. Which mock is decided in `query()` from the entry under the type's own key, the one `mockRootInstantiable` builds the root from (`TypeReport.Mock.Kind`): `generated` when a declaration sets `generateMock: true` or an included module's configuration lists the type (`generatedIn` names those modules, and the text says how a project without them generates the mock), `handWritten` when that entry has a hand-written mock, and `wouldBeGenerated` otherwise, so the focused app learns what the `mock()` it would generate needs — `mockOnly` modules included, which the production view strips. A hand-written method named `mock` on another entry for the type (a `mockOnly` extension whose mock returns a protocol, which `resolveSafeDIFulfilledTypes` merges only into that protocol's slot) is neither the root's mock nor compatible with generating one, so the report is `MockReport.none(NoMock)` rather than an error: the production part still prints. The mock view is computed before the production view, so a missing name is reported from the full map, with the types that fulfill that name and the types named most like it (`QueryError.noInstantiableNamed`). Neither part has a walk of its own, so the report cannot disagree with the generated mock; any new kind of `mock()` parameter must be added to `MockRootParameters`, not computed inside `generateMockRootCode` alone. The query runs exactly the checks on the path of one root, because it reaches them through `mockScopes` and `createMockRoot`, and none of the passes `generateMockCode` runs over every mock root together after its loop (`validateSendableBuildersCaptureNoNonSendableWrapper`, `validateConfigurationsAreBuiltOneWay`): those gate emitting the module's mocks and change nothing in the report, and `generate` reports them with fix-its, so a query that succeeds where `generate` would throw one of them is intended, not drift. The rule for a new check: one that decides whether a single root can be generated goes in `createMockRoot`, so both callers run it; one that needs every root at once goes after the loop, and is not added to the query. The one exception is the access check (`createMockRoot`'s `emittingModule`, see "Validation boundaries"): the query reports what a type needs whichever module assembles it, so it has no emitting module, passes none, and checks no access. The public result is `TypeRequirements` (declarations with the file that holds each, erasures with every declaration that makes them, forwarded and required parameters with reasons); `TypeReport` in the tool attributes each file to its module (`FileAttribution`: the module's name, its `--include` or `--module-info` paths as given, and the file spelled under the `--include` argument through `NormalizedFilePath.path(under:spelled:)`, or as a module info file records it) and formats the text; `QueryReport` wraps the types under `formatVersion`, and `QueryErrorReport` prints any error as JSON with a `kind` when `--json` is set. The JSON is a contract documented in `Documentation/QueryNeeds.md`: arrays are always present, optional keys are omitted, every reason has a `reasonKind` beside its sentence, and from `1` on `formatVersion` is raised when a key is renamed, removed, or changes meaning, so a change to the shape is a change to that page and, once the format is stable, a version bump. An erasure is attributed to a module already needed when one declares it, else to the first declaring module by name, with the rest listed beside it: any one declaration suffices, and the choice must not depend on set order.

### Mock generation flow

Mock generation follows this pipeline:

1. **`generateMockCode`** builds the mock scope map via `createMockTypeDescriptionToScopeMapping` (includes ALL types, not just reachable from roots)
2. For each type with `generateMock: true`, **`createMockRootScopeGenerator`** promotes `@Received` dependencies to root-level children (except those `mockCanBuild` rejects), in the order the mock's tree first receives them (`inOrderTheMockTreeFirstReceives`), and validates for cycles
3. **`ScopeGenerator.generateMockRootCode`** builds the mock method:
   - Calls `collectMockParameterTree` to walk the dependency tree and build `MockParameterNode` trees
   - Collects flat parameters: `@Forwarded` deps, uncovered `@Instantiated` deps, `@Received` deps not in the tree
   - Generates `SafeDIOverrides` struct (if tree children exist) and the `mock()` method signature and body

The production code path (`generatePropertyCode` with `.dependencyTree`) and mock path (`.mock`) share the same `ScopeGenerator` but diverge at `generatePropertyCode`. Mock fields (`mockInitializer`, `mockReturnType`, `customMockName`) are only accessed in mock code paths — never in production paths.

### Cycle mechanisms

Multiple cycle-related mechanisms coexist — keep them distinct:

| Name | Scope | Set by / when | Role |
|------|-------|---------------|------|
| `isPropertyCycle` on a scope/node | Per-root, syntactic | `Scope.createScopeGenerator` when a property label repeats in the ancestor stack | Terminates infinite descent during a single root's walk; differs between roots for the same underlying cycle. |
| `cycleEdges` (set of `CycleEdge`) | Global | `DependencyTreeGenerator.computeCycleEdges`, alphabetical-DFS feedback arc set | Chooses a single back-edge per cycle consistently across all roots — required because shared `SafeDIMockConfiguration` structs must have one shape. Consumed by struct generation AND override-path navigation in mock bodies. Each root returns the nodes of the types its tree configures (`collectConfigurationTypes`); `generateMockCode` keeps the first root's node for each type, in alphabetical root order, and only then generates that struct (`ScopeGenerator.generateConfigurationStruct`), so no root generates a struct that is thrown away. |
| `throwIfInvalidCycle` | Shared classifier | Called from `validatePropertiesAreFulfillable` (production, and a mock root whose children require one another) and `validateMockRootScopeForCycles` (mock) | Judges the property that closes a cycle: rejects one that is constant (or lazily instantiated, validated as its constant) or a receive, and accepts one that is a non-received instantiator, whatever the hops before it are (those cycles compile as long as pruning breaks the config-struct recursion). Neither stack walk considers an `onlyIfAvailable` dependency, `@Received(onlyIfAvailable: true)` or an `onlyIfAvailable` alias (`Dependency.canCloseDependencyCycle`): generation passes it `nil` while the property it receives is built (`isPropertyUnavailable`, which in a mock matches the property still being built exactly or by its non-optional form), whatever kind of property that is — constant, `LazilyInstantiated`, or `Instantiator` — so `a: A?` under the `a: A?` it is built inside gets `nil` as it does under `a: A`, and so does an alias of `a` only if available. Both walks classify the dependency that closes a cycle with `closingReceive(of:in:)`: a required `@Received` dependency is a receive, and so is a required alias, which receives its fulfilling property — unless its scope creates that property, which the alias then refers to. Do not use `Dependency.Source.isReceived` for this; it is `false` for aliases. The classification matters only for a non-constant property: a required alias fulfilled by a `LazilyInstantiated` is mapped to the constant it stands for and rejected as a constant cycle, exactly as its constant twin is. Production's received walk agrees by another route: `Scope.requiredReceivedProperties` lists a required alias's fulfilling property, with `aliasProperty` so the error names the alias, except one the alias's scope always creates (`unconditionallyCreatedProperties`: instantiated, forwarded, or a required alias), which requires nothing of an ancestor. An alias of an `onlyIfAvailable` alias on the same scope stays listed, so the required-alias check can see whether that alias is created. A scope closing a property cycle (`isPropertyCycle`) generates none of its dependencies, so `ScopeGenerator` does not count an alias of another of its type's aliases as received there (`cycleClosingAliasProperties`); otherwise the cycle-closing scope is ordered after the alias it renames, which is ordered after the cycle-closing scope, and a chain of aliases is emitted before what it renames. |
| `validateMockRootScopeForCycles` | Mock graph | Called after `@Received` promotion in `createMockRootScopeGenerator` | Walks the post-promotion scope to catch cycles that only surface once received deps are promoted to mock-root children — through an ancestor only. For a type listed only in `additionalMocksToGenerate`, whose tree `validatePropertiesAreFulfillable` checks for hidden properties alone, it is the only cycle check. A promoted received optional property is built as its non-optional value, so a received or aliased dependency matches either form. ### Mock generation specifics

- **Share logic between production and mock paths where possible.** Validation, scope population, and other shared concerns should live in common helpers rather than being duplicated between `createTypeDescriptionToScopeMapping` and `createMockTypeDescriptionToScopeMapping`. When adding validation to one path, check whether the other path needs it too.
- **Selected construction initializer.** `InstantiableVisitor.canonicalConstructionInitializer` is the single initializer SafeDI selects for construction (first init that fulfills the type's dependencies). `Instantiable.initializer` is populated from it, and mock generation emits against its signature. Validation that only matters for the path SafeDI uses (e.g., diagnosing `Self.*` in default expressions) should gate on this — walking every entry in `visitor.initializers` false-positives on unused overloads.
- **Two-layer mock return type** (extension-based `customMockName` only). When a `customMock` method returns a type different from `Self` (permitted via `fulfillingAdditionalTypes`), two concerns have to agree:
  1. **Inner closure type** (`MockParameterNode.builderClosureType`) — the type of the override closure stored in the parent's `SafeDIMockConfiguration`. Uses the property type so callers writing overrides match the receiving slot. Fixed in #251.
  2. **Outer `mock()` return type** — the generated `mock()` wrapper must return whatever the user's `customMock` returns. Fixed in #266.

  When touching extension-based types with `customMockName`, confirm both layers. `mockReturnTypeIsCompatible(withPropertyType: concreteInstantiable)` distinguishes genuine hand-written mocks from mockOnly-inherited ones.

  A mock that returns one of the type's additional types builds only properties `mockReturnTypeIsCompatible` accepts, so the type is built with its mock for some properties and with `init` for others, yet mocks generate one `SafeDIMockConfiguration` per concrete type, from the first node that needs it. `generateMockCode` therefore rejects (`validateConfigurationsAreBuiltOneWay`, a `SourceDiagnostic` at `mockDeclarationLocation`) a type whose first mock-built and first `init`-built nodes across all roots, in root order, both read a struct and differ in `MockParameterNode.configurationRequirements` (child properties, default parameters by label and type, builder parameter types). A node beneath a `cycleEdges` edge reads no overrides from its struct (its parent's struct has no field for it), so `collectConfigurationNodesByConstruction` leaves it out, and when the first node of a type is such a node built the other way, the struct is generated from the first node that reads it instead. A node that needs no struct is built from a closure typed by its property, so the shape #419 made compile, a mock that takes nothing, stays accepted, as do a mock with exactly `init`'s parameters and a mock that returns the concrete type. An extension's `instantiate(…)` plays `init`'s part: its default-valued parameters are struct fields (#452), so an `instantiate`-built node can read a struct and conflict too, and the diagnostic names the construction by `MockParameterNode.isExtensionBased`. Never emit a second struct for the same type. The struct's default-valued fields take their defaults from the hand-written mock's parameter of the same label and type (`DefaultParameter.defaultParameters(of:dependencies:)` on `mockInitializer`, matched to the dependencies of the concrete type's entry), whichever node the struct is generated from and even when no property is built with the mock in this module; `init`'s (or `instantiate(…)`'s) default applies only to a field the mock declares no default for, so `configurationRequirements` compares labels and types, never values. A node built with `init` beneath a `cycleEdges` edge, which no override reaches, elides its labeled defaults except those the mock also declares (same label and type), for each of which it passes `<Type>.SafeDIMockConfiguration().<label>` (`callSiteArgumentsForPrunedOverride(handWrittenMockDefaultParameters:)`, `MockContext.handWrittenMockDefaultParameters`), so the default is the mock's, evaluated in the struct, as for every other property of the type. Never inline the mock's default expression at the call site: it can name the type's static members or nested types, which resolve inside the struct (nested in the type's extension) but not in the mock root's extension.
- **Dependencies a hand-written mock is not passed.** A generated mock passes a dependency to the hand-written mock's argument with the same label (`resolveBuilderArguments`, `generateReturnArgumentList`). A mock merged in from a `mockOnly` declaration may have no argument for some of the production declaration's dependencies (`Instantiable.dependenciesNotPassed(to:)`, which never lists a `@Forwarded` one: it is an argument of the type's `Instantiator`). `createMockTypeDescriptionToScopeMapping` gives every property built with that mock a scope whose instantiable declares only the rest (`Scope.dependenciesLeftOut` records what was removed), so the dependency is not built, received, promoted, or offered as an override, and the mock declares no value it never uses. A dependency left out is built after all when the tree of a dependency the mock is passed receives its label, which is known only from the scopes, so the mapping is built again until nothing more is found. A mock that returns one of the type's additional types builds only properties of that type; the others are built with `init` from the complete scope, so one concrete type can have two scopes. The mock root's own instantiable is filtered to the dependencies of its scope, or a dependency its scope does not build would surface as a flat `mock()` parameter.
- **Hand-written `mock` vs. generated `mock()`.** A type whose `mock()` this module generates (`generateMock: true` or `additionalMocksToGenerate`) must not also have a hand-written method named `mock`, wherever it is declared. The macro enforces this within one declaration; `DependencyTreeGenerator.generateMockCode` enforces it across declarations and modules (a `mockOnly` pair) when it creates mock roots, by name only — no signature analysis, because a `mockOnly` extension's mock defaults every parameter, so even "distinguishable" pairs leave `Type.mock()` ambiguous. Do not work around such pairs at the call site (e.g. coerced function references). `Instantiable.mockDeclarationLocation` locates the diagnostic and must travel with `mockInitializer` through every merge.
- Names bound for receivers are tracked by label and then type: the disambiguation maps (`[String: [TypeDescription: String]]`) – `flatParameterDisambiguationMap` for renamed flat parameters, overrides, and sibling bindings, `lazilyInstantiatedBindingNames`, and `uncoveredDependencyNames` – give the name a receive of that label and type is handed.
- A receiver whose label was disambiguated is rebound to the disambiguated name (`emitReceiverBindings`), found by its declared type and then its unwrapped type, since an `onlyIfAvailable` receive of `x: X?` is fulfilled by a disambiguated `x: X`. A receive the node passes `nil` (`MockParameterNode.unavailableProperties`) is not rebound: the name may not be declared yet.

- `#SafeDIConfiguration` is always read from the current module only, never dependent modules
- **Received erased types.** `generateMockCode`'s `erasedToConcreteTypeMap` lets a mock root promote a received type no `@Instantiable` fulfills (e.g. `AnyService`) by building the concrete type an `@Instantiated(fulfilledByType:, erasedToConcreteExistential: true)` property of that exact property type names, in any module. It is keyed by the full property type, because a receiver matches by type, so an `ErasedInstantiator<(), AnyService>` erasure never counts toward `AnyService`. A type that erasures give more than one concrete type is left out of the map, and its receivers become required flat `mock()` parameters: picking one would depend on dictionary iteration order. Production never consults the map — production receivers get the value from an ancestor.
- **An `@Instantiated` dependency the mock cannot build is still declared.** `Scope.propertiesToDeclare`, which `ScopeGenerator` and the received-property walk (`ScopeDeclarations`) both read, includes `Scope.instantiatedDependenciesNotGenerated`: the type's `@Instantiated` dependencies no scope builds, which `mock()` takes as parameters. A receive of one beneath its type is therefore subtracted there, as production subtracts it, instead of reaching the mock root as a second parameter. Emission hands those receivers the parameter's final name where it enters the type's builder function, or the mocked type's whole tree for its own (`routingReceives(of:toParametersNamed:in:)`, beside `removingRenames`), and a receiver rebinds a parameter named apart. A receiver that is not beneath the type, such as its sibling, receives from above the mocked type and keeps a parameter of its own. A promoted sibling of the mocked type receives the mocked type's own such dependency by value, as its own created properties are one instance, and a receive of its `LazilyInstantiated` is wrapped around the parameter (`lazilyInstantiatedReceivedProperties` admits an instance in `mockedTypeUncoveredProperties`), never taken as a wrapper parameter or override. The instance of a wrapper the mocked type instantiates and the mock cannot build provides only that wrapper (`isProvidedByTreeByValue`): a promoted sibling's receive of the other wrapper kind takes the instance as a parameter or an override, as the mock builds a wrapper of each kind beside one it builds. That asymmetry is production's: a wrapper declaration provides itself and its instance only, so production rejects a receive of the other kind beneath it, and such a receive can only come from another declaration – another instance – while a promoted sibling's same-kind or by-value receive gets the mocked type's own property, as a receive beneath that declaration does. A promoted dependency stands for one built above the mocked type, so `createMockRootScopeGenerator` validates each promoted scope's tree for hidden received dependencies with the walk an additional mock's tree gets, rooted at that scope with its tree's received properties bound, so that the mocked type's own declarations hide nothing in it; a tree that passes is validated once across mock roots (`promotedScopesValidatedForHiddenReceives`), and one that fails is walked by every mock root that promotes it, so the errors reported never depend on the order mock roots are created in. Production never has such a dependency: `validateReachableTypeDescriptions` rejects it before scopes are built.
- **What a tree node provides.** One definition decides whether a scope provides a property to the scopes beneath it, so they do not receive it from its ancestors: `ScopeGenerator.provides(_:declaredProperties:forwardedProperties:)`. The scope declares or forwards the exact property, or, for an optional property, its unwrapped form, and a lazily instantiated property is declared (and forwarded) together with the by-value property of its instance (`declaredLazilyInstantiatedInstanceProperty`). `generateMockRootCode` drops a received property from its parameters and overrides only when its tree provides it by that definition, or when a promoted node's optional property is the receive's optional form, since a mock binds a node it builds to a non-optional value. A same-label node of any other type provides nothing: the receive stays a flat parameter or override, named apart from the root's tree bindings by label and type (`user_Draft`). Never match a received property to a tree node by label alone.
- **`onlyIfAvailable` overrides are keyed by label and type.** `generateMockRootCode` makes one `OnlyIfAvailableOverride` per `onlyIfAvailable` received property that no forwarded property or required receive covers and the tree does not provide (the mock root's own `x: X?` is handed a promoted `x: X`), even when a root tree node shares its label with another type: handing that node over is wrong (a promoted `editor: Editor` passed to its own `editor: Draft?`). `onlyIfAvailableOverrides(for:namedAfter:namesInMockScope:reservedNames:)` names the field and the binding by the bare label unless the label is a forwarded, default-valued, or uncovered-`@Instantiated` parameter, a root tree binding name, or another override's label; those are named by `identifierSafeNames` from the optional type (`user_Draft`). A flat received parameter or root alias that shares an override's name is still the one renamed, so mocks without such a clash are unchanged. A renamed override joins the flat renames in the receivers' disambiguation map, and `removingRenames(hiddenByDeclarationsOf:parameters:from:)` drops a rename wherever a nested scope declares or forwards that property (or its non-optional form), so such a receiver resolves to the closest declaration, as in production. The mock root's own renamed receive is rebound to its label at the root scope, unless the root binds that label already (to a node it promotes for another receiver); the root is then passed the renamed binding directly through the return's disambiguation map. Only promotion creates these clashes: when the mocked type's own tree hides the label, `HiddenReceivedProperty` rejects it before generation.
- **Values reaching a `@Sendable` builder function are taken as `@Sendable` autoclosures and called inside it.** A `@Sendable` builder cannot capture a value whose type is not `Sendable`, and SafeDI cannot tell whether a type is, so a labeled default-valued parameter of a type whose `SafeDIMockConfiguration` is `@Sendable`-typed (`MockContext.sendableConfigurationTypeNames`) is stored as `@Sendable () -> T` behind an `@autoclosure` init parameter and read as `field()` at every construction site (`resolveBuilderArguments`), with a closure literal default parenthesized (`(() -> Void)? = ({})`, `autoclosureDefault`), since Swift reads a bare one as the autoclosure itself, and a dependency the mock cannot build that a type inside such a builder instantiates (`UncoveredParameter.isSendableAutoclosure`) is a `@autoclosure @escaping @Sendable () -> T` parameter of `mock()`, read into `__safeDI_<name>` before any builder function and bound as `let <name> = __safeDI_<name>()` at the top of each scope that instantiates it (`sendableAutoclosureBindings`), so the value is created once per construction as in production and the receivers beneath read that binding. Mocks that no `Sendable` wrapper reaches are unchanged.
- When a mockOnly and a non-mockOnly coexist for the same type, `resolveSafeDIFulfilledTypes` merges them. The `(false, true)` and `(true, false)` branches handle opposite processing orders. Any cross-cutting concern (tracking sets, stale clearing) must be applied to both branches or order-dependent bugs will surface only on CI.

### Validation boundaries

Validation is split between the macro and the plugin based on available context:

- **Macro validation** (compile-time, local context only): The macro sees only the single decorated type or extension. Any error that can be determined from local context belongs here — missing `init`/`instantiate()`, invalid parameter combinations (`mockOnly + generateMock`), mock method signature issues, an optional `@Instantiated` property type (`X?`, `X!`, `Optional<X>`, `Instantiator<X>?`, `Instantiator<X?>`; `InjectableMacro`), and the access levels generated code can never use: `private` or `fileprivate` on the type, its construction initializer, its `instantiate()`, or its hand-written mock method, since generated code is in a file of its own (each with a fix-it that deletes the modifier; `Initializer.isValid` applies the same rule, so an `internal` or `package` initializer is selected for construction). These produce fix-its in the IDE. Whether any other access level suits the module that constructs the type is the tool's to judge (see "Access between modules"). Code generation test fixtures never declare an optional `@Instantiated` property, since the macro rejects one. Generation matches a type's names as `String`s, so the macro (`InstantiableVisitor`) rejects, without a fix-it, two names of one declaration that SafeDI matches by name (dependency labels, alias fulfilling names, and parameter names of initializers, `instantiate(…)`, and hand-written mocks) that are equal as `String`s but differ in UTF-8 bytes, which Swift reads as two names, as well as an `instantiate(…)` dependency parameter named `_`. The warning at a dependency type that names a type nested in the decorated declaration unqualified or through `Self` collects nested types from every `#if` clause and exempts a nested `@Instantiable` type exactly where `TypeDescription.qualifyingInstantiatedType(within:amongInstantiableTypes:)` qualifies it, as SafeDITool does. Its fix-it qualifies with every enclosing type from `context.lexicalContext`, and must also rewrite the same-named parameters of initializers and hand-written mocks and an alias’s `ofType:` argument, or the declaration stops matching its dependencies.
- **Plugin warnings** (build-time, full context): `DependencyTreeGenerator.generateWarnings()` runs after the tree has generated. It reports a `LazilyInstantiated` property that is instantiated whenever the type declaring it is created, because a type created along with that one reads its instance by value. `InstantiationAnalysis` reads the scopes `rootScopeGenerators` built and validated (`validatedScopes`), is type-level, and is memoized per `Scope`: a type’s creation reads what its own required by-value receives and aliases read, plus what its constant children and its instantiated-with-owner lazily instantiated children read, minus every label the type declares. A read of a renamed wrapper's instance is followed through every renaming the type declares (`propertyRead(by:)`) back to the property it starts from. An `onlyIfAvailable` receive is deliberately never a reader: whether it reads the instance or is passed `nil` depends on sibling ordering, which only `ScopeGenerator` knows, and a warning about a dependency that is not instantiated would be worse than a missing one.
- **Plugin validation** (build-time, full context): The plugin (`SafeDITool generate`) sees all modules' types. Errors that require cross-type knowledge belong here — unfulfillable dependencies, received dependencies hidden by a closer ancestor's property with the same label (generated code passes dependencies by label), a rename whose `fulfilledByDependencyNamed:` label its own type instantiates, forwards, or renames to with a type other than its `ofType:` (`renamesContradictingOwnProperties`: the rename refers to that property, so `ofType:` must name its type exactly, optionality included, or a `LazilyInstantiated` property's instance type; recorded in the hidden-label walk and thrown before unfulfillable and hidden properties, which it explains, and checked again in `validateChildrenDoNotRequireEachOther` for the trees of dependencies a mock promotes, which that walk does not reach; both declarations are on one type, but the check stays in the plugin by ruling), dependency cycles, a `@Sendable` builder function that would capture an `Instantiator`, `ErasedInstantiator`, or `LazilyInstantiated` declared outside it (`ScopeGenerator.nonSendableWrapperCaptures`, which walks the generator trees as code generation does, so a dependency passed `nil` is not reported; a receiver is reported once for each chain that reaches it, so the root a diagnostic names never depends on name order), duplicate type declarations, duplicate mock providers, a `mockOnly` hand-written `mock` on a type whose `mock()` is generated, the seam errors (`DependencyTreeGeneratorError.SeamError.Kind`: two receives of one label with different types, a tier that cannot take a required parameter, a hand-written initializer a generated tier would redeclare, a reached seam whose module's `.safedi` names a dependency this run lacks, signatures that do not settle, a seam's tree reaching a declaration its callers cannot see), an `additionalMocksToGenerate` entry of the selected configuration that names no `@Instantiable` type (`SafeDIConfiguration.validateAdditionalMocksToGenerate`, judged against the concrete types mock generation matches entries to, unioned with the `ModuleInfo.instantiableTypeNamesInAnyClause` of this module and its dependent modules, so an entry naming a type declared only in an inactive clause is accepted and its file written without code, as "Conditional compilation" describes; entries of configurations in inactive clauses are planned by `scan` and written without code, never judged).
- **Access between modules** (build-time, `SafeDITool generate`): every construction `generate` emits must compile in the module it emits it in (the `emittingModule`: `ModuleInfo.moduleName`/`packageName`, the module's own files – the manifest's `mockScopedFilePaths`, or else the input files (CSV and `--include`), never a file reached through `additionalDirectoriesToInclude` – and whether a recorded file can be read). A construction is a production root or a type its tree instantiates, built with its initializer or `instantiate()`, a type a mock builds, with its hand-written mock where `mockReturnTypeIsCompatible` says the mock builds it with that, a mock root, and the hand-written mock a `mock()` calls for a forwarded parameter's default. The declarations it relies on (`Instantiable.accessNeeds(constructingWithMockMethod:)`) – the types enclosing the type in its file, the type, and the method, each with the level it has by itself, or an extension a declaration that spells no modifier takes its level from, and, for a type an extension declares – one declared inside it, or the type of an `@Instantiable` extension – the declaration of the extended type in the extension's module and those enclosing it in its file (`extendedTypeAccessNeeds`, which `Construction` stores, so the check and the decision to generate another module's root read the same needs, as do `constructsOnlyPublicDeclarations` and the construction comments): its own `@Instantiable` declaration outside every extension, or else its plain declaration, which `FileVisitor` records outside every `#if` block and every extension (`PlainTypeDeclaration`; a namespace inside `#if` or inside an extension, or one in another module than the extension, is left to the compiler), `ModuleInfo.plainTypeDeclarations` carries attributed to modules as instantiables are, and `ExtendedTypeDeclarations` looks up by module name, preferring one in the extension's file – must each satisfy `AccessLevel.required(toConstructFrom:declaredIn:isOwnFile:)`: `internal` for a declaration in an own file or the same module, `package` within one package, `public` across packages, and `packageUnverified` (`package` accepted, and the construction line ends in a comment saying so, `Scope.ConstructionComments`, as does the line of a forwarded `mock()` parameter whose default calls a hand-written mock, after its comma, `MockContext.forwardedParameterMockDefaultComments`) when either package is unknown. Effective access (`AccessReachability.swift`): a declaration's spelled level, or, when it spells none and is directly inside an extension, the extension's (`fileprivate` for `private`), capped by each enclosing type; a member defaults to `internal` in a type whatever its level and to its extension's level in an extension (`AccessDeclaration.isExtension`); an extension caps nothing, spelled or not, as in Swift, which only warns at a member more permissive than its extension, so the type an extension-based `@Instantiable` declares is taken to be `open` (its own access is unknown) and its methods have the levels they have by themselves. A failure is `inaccessibleConstructions`, one error per declaration to widen, in source order, once however many constructions, roots, or mock roots need it (`InaccessibleConstruction.merging`, which keeps the construction with the earliest reference, then the one whose type is declared first, so an error at a reference names the type that reference constructs and root order changes nothing); in a mock's tree the fix also suggests a public mock of the outermost `public` type another module declares on the path, one with neither a hand-written nor a public mock (`Construction.publicMockCandidate`): at the declaration with one fix-it (replace the modifier, or insert one where the declaration begins) when its file can be read, else at the first reference in source order in this module, naming the declaring module. Production runs it in `rootScopesThisModuleGenerates`, before any generator exists, since creating one starts generating code; a root declared outside the module's own files is generated only when every construction in its tree is `public`/`open` and no scope of its seam-world tree carries a `seamCall`, else it is withheld (`rootsGeneratedOnlyByTheirModule`, each with the reason that chooses its comment: a non-public construction first, else the first seam call met in a declaration-order depth-first walk of the tree, never `constructions`' dictionary order): its file holds the header and a comment saying why, and nothing is reported (the declaring module, if it runs SafeDI, generates and reports it). Mocks run it in `createMockRoot`. Nothing runs when every declaration any generated code could construct is `public` or `open` (`constructsOnlyPublicDeclarations`).
- **Reject nonsense shapes.** A shape only a confused user would write gets an error, never generator support.
- **The macro prevents; the plugin trusts.** A shape decidable from one declaration gets a macro diagnostic (the rename check under "Plugin validation" stays in the plugin by ruling), and the tool never re-checks what the macro rejects. Where it relies on a macro check to keep from trapping, it reports a plain error instead, as the next rule describes.
- **Never a trap on what the macro rejects.** Every build runs `generate` before the compiler expands the macro, so where the tool relies on a macro check to keep it from trapping, input the macro rejects gets a short plain error at the declaration that points at the macro's rule: no fix-it, which the macro keeps for the IDE, and no copy of the macro's validation. `validateDependencyLabelsAreDistinct` is such a check: generation keys a declaration's dependencies by label, so a declaration two of whose dependency labels `String` equates is reported at the later one when a production root's tree (its reachable types), a generated seam's tree (and the foreign seams it calls, checked before any seam signature is computed), or a mock root's tree (the scopes its mock root scope reaches, promoted ones included) builds it – two `instantiate(…)` parameters named `_`, names encoded differently, and one dependency declared in each clause of an `#if` only the compiler decides, which the macro accepts. A declaration no tree reaches traps nowhere, so it is not reported: a shape that works must not become an error. Tests of these errors are the one exception to fixtures the macro accepts.

### Serialization

`scan`'s cache (`<manifest>.safediScanCache`, a `CachedScannedModuleInfo`) and `.safedi` module info files (a `ModuleInfo`) are written in SafeDITool's own binary format, by hand rather than through `Codable` (`BinaryCoding.swift`, `BinaryCodableModels.swift`, `BinaryFile.swift`, all in `SafeDITool`, never `SafeDICore`). These files are **regenerated every build** — there is no cross-version deserialization. Do not add backward-compatibility decoding logic. A header (magic, format version, schema fingerprint, body length, checksum) rejects any other file: an unreadable scan cache is a cache miss and a fresh parse, and an unreadable `.safedi` is an error naming the file. `BinaryFile.schemaDescription` and `BinaryLayout.description` spell every stored type and field type with `String(reflecting:)`, so the module names `SafeDITool` and `SafeDICore` are part of `schemaFingerprint`: every build of the tool must name its modules that way (the SwiftPM targets, the prebuilt binaries, and `module_name` on the Bazel `swift_binary` and `swift_library`), or its `.safedi` files are unreadable to the others, and no test catches it, because `swift test` cannot see a Bazel build. The plugin-read `SafeDIToolManifest` stays JSON.

When a stored type changes, keep its coder in step:
- Each `BinarySchemaMember` writes its fields in initializer order and reads them back through that initializer, with each field's type choosing how it is read. A field whose type is not `BinaryCodable` fails to compile; so does an enum case the writer's exhaustive `switch` does not handle, and a tag the reader's `switch` does not handle.
- `binaryLayout` is what `BinaryFile.schemaFingerprint` covers: for a struct, each field it writes, in write order, as a `BinaryLayoutField` whose key path fixes the field's type, plus `unwrittenProperties`, the stored properties not written under their own name (`Dependency.asInstantiatedType`, `UnorderedEquatingCollection.set`, `Instantiable.instantiableTypes`, written as `concreteInstantiable` and `additionalInstantiables`, and `Property`'s stored hash, which is never written because hashing is seeded per process: a decoded `Property` goes through `Property.init(label:typeDescription:)`, which computes it again); for an enum, each tag's associated values, in declaration order, which is also the order written and read. A file written by a SafeDITool whose types write other fields, fields of other types, or the same fields in another order is therefore never read. `SafeDIToolBinaryFileTests` compares each struct's layout against `Mirror`, so a new stored property fails until it is listed, written, and read, and writes each field and associated value in turn with a value distinct from the rest (`BinarySample`), so a layout whose order or types differ from what the coder writes and reads fails too. A new stored type must join `BinaryFile.schemaMembers` and conform to `BinarySample` in the tests.
- A `BinaryReader` reads type descriptions nested at most `BinaryReader.maximumNestingDepth` (128) deep, so the writer notes a deeper one and `BinaryFile` refuses to write a file that holds it, naming the instantiable whose declaration names it, or the outermost type of a plain type declaration (`BinaryFileWriteError`): `scan` then writes no cache, and `generate` fails rather than write a `.safedi` dependents cannot read. Do not describe the deep type itself in such an error: spelling a type recurses as deeply as it nests, which exhausts a task's stack in a debug build.
- `executeSafeDIToolTest` checks, for every fixture that runs scan, that the cache reads back exactly what scan wrote (`reflectedDescription`, which sees private fields and spellings `==` ignores, and compares strings by their UTF-8 bytes, because `String`'s `==` calls canonically equivalent spellings equal while Swift compares identifiers byte for byte; the writer's string table keys strings by those bytes for the same reason), so a field the coder drops fails whichever tests give it a value.
- `Codable` conformances stay: the `dump` subcommand prints either file as JSON through them.

## Determinism

Everything SafeDI produces must be identical on every run over the same inputs: generated code, diagnostics (their text, their order, and which one is reported first), fix-its, output file names, and the bytes of manifests, `.safedi` files and caches.

- Swift seeds hashing per process, and `Scope` hashes by object identity, so the order of a `Set` or `Dictionary` changes between runs — for scopes, even under a fixed hash seed. A task group's results arrive in completion order. None of these orders may reach output.
- When code chooses among candidates or emits a list, use declaration order, source path order, or a sorted order. Never use first-found or last-write-wins over an unordered collection.
- When a choice is genuinely ambiguous, report an error or apply a stated tie-break. Do not pick silently.
- Sorting only on the failure path is fine, and keeps the success path cheap: visit everything, and keep the candidate that sorts first only when there is something to report.
- A test of choice-making code needs enough candidates that a wrong order fails on nearly every run: twenty or more, or a permutation of six. A fixture with one candidate cannot catch this class of bug.

## Code Style

- **Compare for meaning through a projection.** A comparison for meaning (settling, the callers' view, a guard hash) uses an explicit projection, never the synthesized `==` or hash of a type that carries diagnostic payload.
- **No abbreviations.** Use `dependency` not `dep`, `parameter` not `param`, `declaration` not `decl`. Everywhere: variables, functions, tests, comments, commits.
- **No `default` or `case _` in switch statements when all cases are knowable.** Enumerate all cases explicitly for compile-time safety.
- **Use `for ... where` for simple boolean filters** instead of `guard ... else { continue }` inside the loop body.
- **Use `guard` for early exits**, not `if condition { continue/return }`.
- **No early return from bare `if`.** If an `if` branch returns, the non-returning path must be in an explicit `else` clause. Never fall through after `if { return }`.
- **Test names follow `method_expectation_conditionUnderTest`** pattern (e.g., `mock_disambiguatesAllParameters_whenThreeChildrenShareSameLabel`).
- **No traps in shipped code.** A validated tree, and the code generated from it, never crash. Code under `Sources` and `Plugins` uses none of the traps `SourceRuleTests` (below) fails on, except at a site whose waiver states the invariant that keeps it from trapping on any input, including input the macro rejects ("Never a trap on what the macro rejects").
- **`SourceRuleTests` enforces source rules.** It fails on a trap in `Sources` or `Plugins` (a force unwrap, in an expression or a key path, an implicitly unwrapped optional or `init!`, `unsafelyUnwrapped`, `try!`, `as!`, `fatalError`, `precondition`, `preconditionFailure`, `assert`, `assertionFailure`, `Dictionary(uniqueKeysWithValues:)`, `Dictionary(dictionaryLiteral:)`, or a dictionary literal whose keys are not distinct literals), on `try?` under `Sources/SafeDICore/Generators`, on `__safeDI_` in a literal in `Sources` outside `ReservedName.swift`, on a lone backtick literal in `Sources` outside `IdentifierSpellingExtensions.swift`, and on an error type declared under `Sources/SafeDICore` that `ErrorReportingSite.byErrorType` does not list with the code that reports it. A safe site is waived by a comment on its line or on the lines just above it, `// safedi-source-rule: allow <rule> — <the invariant that makes it safe>`; a waiver that names no rule, gives no reason, or waives no site fails the test.
- **No new `@unchecked Sendable`.** The compiler proves the concurrency safety of SafeDI's own code (`Sources` and `Plugins`; a test fixture's types are input); disentangle the state instead. Only a tiny low-level primitive may be unchecked.
- **An actor's `lazy var` initializer reaches nothing isolated through a closure.** In an actor, a `lazy var` whose initializer contains a closure or a local function that calls an isolated method or reads an isolated property fails to compile with Xcode 26's Swift 6.2 ("actor-isolated default value in a actor-isolated context"), although Linux's Swift 6.2 and Swift 6.4 accept it. Keep the value in a stored optional instead, filled on first use by an isolated method that returns it.
- **Build long arrays and strings with sequential appends.** A long expression that joins arrays or strings with `+` and contains ternaries makes Linux's Swift 6.2 time out type-checking it. Declare a `var` and append each part, with an `if` where a ternary chose a part.

## Testing Philosophy

- **TDD**: Write failing tests first, then fix.
- **One behavior per test method.** Each test verifies one behavior, but may use multiple assertions to fully validate it (e.g., checking both the count and content of output). Do not test unrelated behaviors in the same method.
- **No tautological tests.** Tests must exercise real code paths with real input. Never use test helpers that rewrite input before processing — the test content should be exactly what production code would see. Tests should verify input code → output code.
- **Test through the pipeline**, not direct model construction. Mock tests use `executeSafeDIToolTest` which parses real Swift source through the full visitor → generator pipeline.
- **Full `==` output comparison.** Never use `.contains()` for mock output. Compare the complete expected string.
- **Verify updated test expectations compile.** When updating expected output in generator tests, review the new expected code to confirm it would compile as valid Swift. Check that variable references resolve to the correct scope, types match (no optional where non-optional expected), and all referenced variables have bindings. Do not blindly update expected output to match actual — the actual output may itself be buggy.
- **Code generation tests should only test paths where the macro would not emit an error**, except tests of the plain errors "Never a trap on what the macro rejects" describes. Test inputs must be valid under `@Instantiable` macro validation — every `mockOnly: true` type needs a `mock()` method (or `customMockName` method), mock method names on the same type must not collide (and a `mockOnly` mock paired with a generated mock must use `customMockName`, or generation errors), and production types need `init` or `instantiate()`.
- **Test titles must be observably verified.** When a test title says "prefers X over Y", the assertion must verify X is used — not just that the test doesn't crash. Add a parent type with `generateMock: true` that instantiates the type under test, and assert the full mock output shows X's method name.
- **If code can't be covered by a test with real parsed input, remove the code.** Dead branches and defensive fallbacks for structurally unreachable paths should not exist.
- **"Structurally unreachable" claims need a failing test.** Before removing defensive branches on the grounds that they can't be reached, write a test that tries to reach them with valid input. If the test can't be written, cite the specific rejection (file:line) and the input shape it rejects — a structural argument alone is not evidence. Structural arguments are easy to get wrong: e.g., `erasedToConcreteExistential: true` does NOT imply a constant property type, so "erased + cycle is rejected as constant" was wrong and cost a round trip when the branches had to be restored.
- **Document a deliberate gap; don't pin it.** A deliberate difference between sibling code paths gets a comment at both sites and a rule in this file, not a test that pins the non-behavior.
- **Test fixture file naming controls processing order.** Files parse in parallel, so completion order is random; `ModuleInfo(_:)` therefore orders a module's file scans by path, so its instantiables are in source file path order, keeping each file's top-to-bottom declaration order, and its imports and mock imports are sorted and deduplicated, so the `.safedi` file `generate` writes is the same bytes every run; upstream `.safedi` module info is already in that order, and `loadSafeDIModuleInfo` returns the dependent modules in the path order of their `.safedi` files, whatever order the caller lists them in or the parallel reads finish in, so the combined list `resolveSafeDIFulfilledTypes` sees is deterministic without a second sort. `executeSafeDIToolTest` names fixture files by extracting the type name from `@Instantiable` in the source content, so those names decide the order. When testing ordering-sensitive behavior (e.g., which of the two mockOnly merge branches runs), pick names that sort the way you need, and be aware that an `extension MyService` file falls back to `"File"`. A configuration-only snippet also falls back to `File.swift`, so it exercises `parseModule`'s fallback path; pass `swiftFileContentByFilePath` (e.g. `["SafeDIConfiguration.swift": …]`) to name a fixture explicitly when the file name matters.
- **Tests must not depend on where the checkout lives.** The suite runs from checkouts under `/Users`, under `/tmp` (reached as `/private/tmp`), and through other symbolic links. Build an expected path by the rule the contract under "File path spelling" gives its consumer — for example the project root as the test handed it to `scan`, made absolute, joined with the file's path inside it, for `additionalInputFiles` — never from `currentDirectoryPath` or `NSTemporaryDirectory()` compared with a normalized path, and test a symbolic link by creating one, as `SafeDIToolPathSpellingTests` does.

## Graph fuzzer

`SafeDIToolGraphFuzzerTests` (support code in `Tests/SafeDIToolTests/Helpers/GraphFuzzer.swift`) generates random graphs of `final class` `@Instantiable` types from a seed (a quarter of them also with one extension-based type whose `instantiate(…)` has default-valued parameters, decided after the rest of the graph so the other types of a seed's graph do not depend on it), with its own SplitMix64 generator so a seed names the same graph on every machine. The oracle runs each graph through `executeSafeDIToolTest` twice in the test process and accepts only two outcomes: the tool reports an error, or the fixture and the generated code compile (`swiftc -emit-object`, as `verifyGeneratedCodeCompiles` does) and the compile the graph passed reports no warning that only its generated code draws (`warningsOnlyGeneratedCodeDraws`, the verifier's filter). Generated code that does not compile or draws such a warning (`generatedCodeDrawsWarning`), a fixture that does not compile on its own (a fuzzer defect), and two runs that differ are failures; a crash kills the test process. The two runs share the process's hash seed, so the long run also runs the `SafeDITool` executable in two processes for every 50th seed and compares them. The oracle also runs each graph under every `GraphFuzzerRenaming` – reversing the order of its type names, of its labels, of its file names, and of all three at once, each a pure rename of single-digit indices (`i` to `9 - i`, files prefixed `F<99 - rank>_`) – and requires, once the renaming is undone textually, the same verdict, the same diagnostics in any order, and byte-identical generated files (`renamedGraphDiffers`). It compares the suggestions a diagnostic lists ("Did you mean one of …") in any order too: the order inside a message is presentation and changes nothing a user does. It catches output that depends on which of several equals SafeDI meets first in name order, which two identical runs cannot see. The reversals keep every type name's `S<seed>_` prefix, which sorts after `ErasedInstantiator<`, `Instantiator<`, and `LazilyInstantiated<` and before the `Sendable` wrappers (a digit sorts before `e`), so no reversal changes whether `x: X` or `x: Instantiator<X>` sorts first. A fifth renaming therefore moves type names across wrapper names (`movesTypeNamesAcrossWrapperNames`): it replaces the prefix's `S` with `A`, which sorts before every wrapper's name, or `Z`, which sorts after every one, chosen per seed by each name's kind and index (`T3`, `AnyT3`, `Value`; a type and its `Protocol` move together), wherever the name appears. A quarter of graphs end with a motif drawn after the graph's own types and before the extension-based type (types 7 to 9, so other graphs draw as before) whose output SafeDI must choose for: a lazy cycle of mocked types, promoted siblings that receive each other only if available, one label received as an instance and as an instantiator, several independently invalid roots, or two types in two files that fulfill one protocol. The four reversals cost about 60% more corpus time, and the move is one more run of the tool per graph. Graphs compile together, kept apart by a per-seed type-name prefix (`S<seed>_`), in one `swiftc` invocation per module role: every graph in one module, with the seam's module of every graph split across modules (`GraphFuzzerModule`), compiles as `FuzzFeature` in package `shop`; then the split graphs' same-package callers (`FuzzApp`, `shop`) and other-package callers (`FuzzOther`, `other`), each against the modules before it, a graph that fails in one module left out of the later ones. Every fuzzer compile passes `-package-name`. A graph's wrappers are all `Sendable`, all not, or – in a quarter of graphs – mixed at random, so a `Sendable` builder's subtree can receive a `LazilyInstantiated` declared outside it; a mixed graph's types are `@unchecked Sendable`, and its types that are not `@Instantiable` (the extended type among them) are `Sendable`, so receiving one by value inside a `@Sendable` builder function is never what fails. The oracle compiles in the Swift 6 language mode, where such a capture is an error rather than a warning. A type no root reaches sometimes receives `items` as a wrapper of the graph's `Value` type, which is not `@Instantiable` and which nothing provides, with the wrapper chosen for each receive, so a mock's tree receives one label as several wrappers its mock cannot build. A type no root reaches also sometimes instantiates a constant of a type that is not `@Instantiable` (`addingDependenciesMocksCannotBuild`), which its mock takes as a parameter, and a pass drawn after every other base pass, with its own generator (`addingReceiversOfDependenciesMocksCannotBuild`), now and then gives a type built beneath that owner – one it instantiates, or now and then one that type instantiates – a receive of the constant, required or only if available, which the mock must pass that same parameter (`dependencyMockCannotBuildReceivedBeneathItsOwner`). With a generator of its own, the pass also now and then makes an owner with `generateMock: true` receive a type of the graph that receives the constant by value or as its `LazilyInstantiated` or `SendableLazilyInstantiated`, required or only if available; a mocked owner's mock builds that type beside it and must wrap the parameter it takes rather than take the wrapper (`dependencyMockCannotBuildReceivedLazilyBesideItsMockedOwner`). In a mixed graph the owner now and then lazily instantiates the constant as one wrapper while that type receives the other kind, which the mock must make from an instance it takes (`dependencyMockCannotBuildLazilyInstantiatedReceivedAsOtherKindBesideItsMockedOwner`), and now and then the type instead instantiates a type of the graph under the constant's label above a receiver of the constant, which the tool must reject as hidden. The oracle checks that rule in every accepted graph: a generated `mock()` takes a `LazilyInstantiated` or `SendableLazilyInstantiated` parameter only for a property the mocked type forwards or instantiates (`mockTakesWrapperParameterForReceive`). Types also receive the erased instantiators an ancestor instantiates, with exactly the type it declares, and some forward one. A tenth of graphs end with a chain of aliases through an `onlyIfAvailable` alias (`addingAliasChains`, a pass with its own generator, so every other graph is drawn as before): a second alias, required or `onlyIfAvailable`, of an `onlyIfAvailable` alias a type declares or is given, on that type or on one it instantiates, now and then a third, and usually a receive of the last on a type beneath it. The second pass never aliases an optional property, so no other graph has such a chain unless `addingSiblingAliasChains`, below, draws one; a receiver that requires the last alias needs every alias created, so the first alias's fulfilling property must be built before it, which the rest of the graph can make a cycle (`aliasOfOnlyIfAvailableAlias`). That pass draws the first alias's source from the properties provided above every path to its host, never one built around it, so it never draws the sibling cycle PRs 472 and 481 fixed. A last pass with its own generator (`addingSiblingAliasChains`, three rolls in ten, about 170 corpus graphs) draws that cycle: a scope – a root, or a type on every path to the chain – instantiates `x: X` as a constant and another type `B` without an instantiator; `B`, or a type a few such steps beneath it that each step dominates, declares an `onlyIfAvailable` alias of `x`, mostly spelled with its optional form (`ofType: X?.self`, `aliasOfOptionalFormOfProperty`); now and then one or two aliases of that alias follow, required or `onlyIfAvailable`, on the same type or on a type beneath it, so that the chain crosses scopes; usually a type beneath the last alias's type receives it, mostly required, or a required alias of it on the same type does instead; and usually `X` receives `b`, so that `b` must be built before `x` while the chain needs `x` first, which the tool must reject through the chain (`fixture_makesSiblingsTypeReceiveTheOtherSibling_forSeed4224`). A type beneath another is a child it dominates, judged from the declarations rather than from `dominators` (a root now and then declares a property the other roots lack, which the graph's edges do not hold), or, where it has none, which is most often, a new type only it instantiates (`Link0`, `Link1`, …), so a receiver is not rejected merely because another path from a root reaches it without the alias. Without the receive of `b`, the chain must be built after `x`, which the compiled output shows (seeds 731 and 2420, in the smoke batch; 2420's chain passes through a child scope).

- **Every pull request.** `ci.yml` fuzzes each corpus whole – the base corpus, seeds `0..<corpusSeedCount`, the seam corpus, seeds `0..<seamCorpusSeedCount` drawn with `generateDependencyTree`, and the public mock corpus, seeds `0..<publicMockCorpusSeedCount` drawn with `generateMockPublic` – on every pull request and push to main that changes more than Markdown. "Build and Test on Linux" packages its test bundle; "Fuzz Dependency Graphs on Linux" shards download it and run the long run over parts of a corpus (the matrix names each shard's corpus and features), with batches running concurrently on every core; and "Check Graph Fuzzer Corpus on Linux" combines the shards' reports per corpus, failing when a corpus has no report. A shard fails, naming the seeds in its summary, when a graph fails, a known issue goes stale, the run reports a problem with itself (a changed corpus, an invalid known-issue list, a harness error), the process crashes, or no graph runs. The combine job fails when a shard is missing or reported any of those, when the shards do not cover the corpus exactly once, or when the seeds the tool accepted differ from the pins (`corpusAcceptedSeedCount`, and `corpusAcceptedSeedsSum`, a `GraphFuzzerSeedSetSum` whose parts add up across shards). The oracle takes any error the tool reports as a valid rejection, so a tool change that makes it accept or reject other graphs must update those pins deliberately. The fixed seeds make every failure deterministic, so it belongs to the change that caused it. Measured: the shards add about 3¼ minutes after "Build and Test on Linux", cold or warm, since they run its bundle instead of building; each base shard fuzzes 2500 seeds in about 2¼ minutes, and the seam shard its 1000; the public mock shard's 1000 take 2 to 4 minutes on an eight-core Mac, not yet measured on CI.

- **Multi-module partition.** The oracle also runs every graph that declares no seam and no public mock – each of the base corpus's – split across modules through both multi-module integrations of `executeSafeDIToolMultiModuleTest`, `.moduleInfo` (Bazel's and Tuist's flow: `generate --combined-output --module-info-output --compiler-receives-input-paths-unchanged --module-name --package-name` per module, reading the listed dependencies' `.safedi`) and `.swiftPackagePlugin` (the SwiftPM plugin's: one CSV per module holding its files and its transitive dependencies' files, the module's own mock-scoped, with the target graph beside it, `scan` while planning and then `generate` with the manifest, one file per root and per mock), without compiling, and requires the same results (`integrationsDiffer`). `GraphFuzzerPartition` (`Tests/SafeDIToolTests/Helpers/GraphFuzzerMultiModule.swift`) is a pure function of the graph – it draws nothing from the seed, so `corpusFixtureHash` and the accepted-seed pins are unchanged by it, and `smokeAndKnownIssuePartitionHash` and `corpusPartitionHash` pin the partition itself, so a change to it is deliberate. Each file refers to the types it names (instantiated, received, forwarded, aliased, erased to, named by `fulfilledByType:`, the graph's `Value` and protocol types, the extended class), each name is declared in one file, and Tarjan's algorithm over that reference graph, visiting files in order, lists the strongly connected components after those they refer to (a lazy cycle through instantiators is one component, so its types share a module; the roots come last). The components are dealt out, contiguously in that order, to `Alpha`, `Beta`, `Gamma`, `Delta` – as many as `GraphFuzzerHash` of the fixture's text chooses, one to four, so single-module graphs stay in the corpus (1322, 1282, 1280 and 1116 of the 5000 graphs get one to four) – so every reference points into the same or an earlier module. A module's `dependencies` are every module whose declarations its `generate` must read, the modules its files refer to and, through them, theirs: what a Bazel user lists in `safedi_compile`'s `deps`, since a `.safedi` holds only its own module's declarations, so a tree reaching a declaration two modules down needs that module listed (`multiModuleTest_throwsErrorForGrandparentDeclaration_whenModuleInfoListsOnlyTheDirectDependency`); the plugin lists the transitive closure's files itself, so both integrations read the same declarations. Every file keeps its name and content, with an `import` line per module it refers to before it, and the module and package names hold no digit, so the renamings leave them alone. The property compares module by module in dependency order (`GraphFuzzerMultiModuleOutcome.difference`): a module both generate must have the same generated units, each byte for byte, the same imports in its generated files and the same warnings; a module the module-info integration rejects must be rejected with the same diagnostics, in any order, by the plugin. A unit is one generated extension, keyed as the plugin names the file it writes (`<Type>+SafeDI.swift`, `<Type>+SafeDIMock.swift`, `<Type>+SafeDIMockConfiguration.swift` for a `SafeDIMockConfiguration` struct wherever the plugin places it), with the `#if` the mock condition wraps it in, and with every path under the fixture root reduced to `<fixture-directory>/…` (`GraphFuzzerGeneratedModule`): the combined file's joined bodies and the plugin's per-file outputs reduce to the same units, and a `#sourceLocation` directive differs between the integrations only in the fixture root's spelling (the plugin's resolved root against the CSV's path under `--compiler-receives-input-paths-unchanged`). It runs in the smoke batch, which must split graphs into one, two, and three or more modules and reject some split ones, and over the corpus in the long run, whose report counts the graphs at each module count (`partitions`) and notes each differing graph (`multimodule`). ## Common Pitfalls

- The input CSV written by plugins includes ALL swift files (target + dependencies). Mock scoping requires passing `mockScopedSwiftFiles` separately — only the target's own files.
- **Which module declares a file is not "own" versus "other".** The SwiftPM plugin's CSV also lists files of no target of the package being built – every source of the SafeDI path dependency, and swift-syntax checkout files nested under `Sources/VersionMarkerModules/`, which slip past the `checkouts` check – so membership comes only from `PluginTargetGraph`, which lists those targets too, and is `nil` (unknown) for any file no target lists, never this module. The graph lists each target's files spelled by the code that spells the CSV, so `generate` matches a declaration's file by exact string and never compares spellings: change one spelling and the other in `inputSwiftFilePaths(of:relativeTo:)` together. The plugin declares the CSV and the sidecar as inputs of its `generate` command and writes each only when what it holds changes (`writeIfChanged(_:to:)`), so a change to the targets that changes no Swift file reruns `generate`, and a plan that changes nothing does not. The sidecar is written in the package path of `SafeDIGenerateDependencyTree.swift` only: the Xcode project plugin has no package information, so its runs know no module, and a SafeDITool older than the sidecar ignores it. A sidecar that exists but does not decode is an error (`UnreadableTargetGraphError`), not a silent unknown.
- **Attributes for generated declarations are resolved once.** The `@Instantiable` macro has two overloads: one takes `generatedInitializerAttributes:` and `mockAttributes:`, the other `generatedAttributes:` (no default, which is what selects it), so no declaration spells `generatedAttributes` beside either. `InstantiableVisitor` resolves them into `Instantiable.generatedInitializerAttributes` and `Instantiable.mockAttributes` (`generatedAttributes` when given, else the specific argument), and generators read only those fields, never the macro's arguments. Each is written verbatim before its generated declaration's modifiers, on the same line (`@MainActor public convenience init()`, `@MainActor static func mock(`); a new kind of generated initializer reads `generatedInitializerAttributes`, and a new kind of generated mock `mockAttributes`. A `mockOnly` declaration merged into a production declaration contributes neither: `mergedWithMockProvider` copies only the hand-written mock's fields.
- **Names generated code introduces are reserved** (`ReservedName`, the one place they are spelled: `ScopeGenerator` emits them from its constants, and the macro checks against them). - **Seams: holes, builders, fills.** In a seam's tree as the seam map builds it, an `@Instantiated` property whose instantiated type (`Dependency.asInstantiatedType`) no production declaration the map holds fulfills (none, or only `mockOnly`) is `Scope.PropertyToGenerate.hole`, unless its spelling is one no nominal type can be (`DependencyTreeGenerator.canBeHole`, by spelling: a closure, tuple, array, dictionary, metatype, `Void`, optional, opaque or attributed type stays `noInstantiableFound`; a typealias of a closure is a hole, which only hand-written code fills). A hole is a build site, a node of the seam's generator tree (`ScopeGenerator(holeProperty:…)`), never a type: a property built at k sites is k holes, each with its own builder and scope struct, never grouped, intersected or merged; a cycle-closing scope builds nothing and so holds no site. `SeamSignature.holes` is kept apart from `parameters`, so a builder is never receivable in its own seam's tree, and every reader of `parameters` is unchanged; every tier takes every builder, after the parameters, in builder-label order, and a hole whose tier access is narrower than a tier is `tierOmitsBuilder`, once per declaration, explained by `SeamAccessExplanation` as a required parameter's omission is, with the builder's remedy (`ParameterKind.builder`) in a pass-through's place. A builder's tier access is `TypeAccessProof`'s over the property's type, the hole's owner admitting its module, with a passed-up builder's scope struct counting as the type of the seam that declares it, capped at the seam's type; a field's access is the proof of its type, the declaring type admitting its module, capped the same way (a pass-through keeps its parameter's); each keeps the proof's cause (`Hole.accessCause`, `Field.accessCause`), which `fieldNotReadable` explains with the shared formatter too. `SeamBuilderParameters.swift` computes the holes from the seam root's generator tree, in this order: sites in generation order (`buildSites`, which walks only subtrees whose `containsBuildSite` holds, ordering each scope's children with `orderedChildrenComputedAfresh`, the order generation will use), then each site's fields, then names; `SeamSignature` hashes the guard from the result. A label is a field exactly when its nearest declaration on the site's path – the seam's parameters, then each path scope's forwarded properties and children; an uncreated `onlyIfAvailable` alias is a declaration but never a field – is bound before the site; a nearer declaration bound later hides a farther bound one (`UncarriedDeclaration`), since Swift would bind the farther one. Each `@Sendable` builder function on the path (`buildsInSendableFunction`) starts a stage: the seam calls each stage but the last just before declaring that function (`SeamHoles.stageCalls(at:)`), binding the returned `@Sendable` function, and calls the last at the site. A builder is always `@escaping` and returns the property's declared type; a builder is also `@Sendable` where the seam's tree passes it on from inside a `@Sendable` builder function, a passed-up one or its own handed to a call that re-enters the seam. A sibling that depends on a carrier and is declared after a later carrier is built after it: a fill reading it is reported (`FillFinding.Kind.declarationBoundAfterSite`), a deliberate gap a finer order could close later. A caller's seam leaf gets `Scope.holeArguments`: `.fill` where its declarations hold a production fulfiller (`fulfillingInstantiable(of:in:)`), else `.passUp`, which a seam's tree turns into a builder parameter of its own per inner site, shared by every call, and which in a root's tree is `unfilledHoles`, reported at the root's dependency with a note at the hole where its file is readable. A hole is identified by its site (`scopeSeamType`, `sitePath`), which a passed-up hole keeps; a seam never takes a site it already takes, and a call that presents one passes the seam's builder by its internal name (`SeamHoles.hole(taking:)`); `SettledContent.Hole` carries a hole's hidden labels, which only accumulate, so a cycle of seams settles. A fill (`ScopeGenerator(fill:key:child:)`) declares the fields as its properties, so a receive they provide is not received from the call's enclosing scopes; its child is the fulfiller's scope built with the stack the seam whose tree holds the site has at the site (`Hole.fillPropertyStack`, the owner's stack, which inside a seam's own fill is the filled seam's), never the filler's path, while a value it takes from the caller's scope is available as to a pass-through of the call, so one the caller's path is still building is passed `nil`; a site inside a seam's own fill carries every field of the filled seam's struct, which the fill binds: a repeat of the hole's property closes on the fill's own builder function, and a repeat of a property of the seam's path is reported (`FillFinding.Kind.closesCycleInSeamTree`), never a rebuild. A fill is keyed by the site it fills; a call inside it of the seam that holds the site, or of a seam that passes the site up, passes the fill, and a fill is never declared inside itself. A fill passed to such a call reads the outer call's values, so a label declared on the path from the fill's root to the calling scope hides every read the fill resolves from the caller's scope (`FillFinding.Kind.declarationBoundOnPathToReenteringCall`, as `boundByPassingUpSeam` hides the labels a passing-up seam binds); the set is per fill, computed in `findingsOfFill`. A fill a `@Sendable` function that does not enclose it refers to is `@Sendable` (`referencedFillKeys`, `sendableFillKeys`, like `buildsInSendableFunction` for cycle closers). Before generation `validateFills` (`DependencyTreeGeneratorError.fillFindings`) reports each receive in a fill's tree that a field does not give inline's value – the nearest declaration of its label is bound after the site (`declarationBoundAfterSite`, which also covers a label a passing-up seam binds on a path to its call of the inner seam, inside the seams and fills on that path included: `boundByPassingUpSeam`), the field is at an access the filler cannot read (`fieldNotReadable`), or held only optionally while the receive requires it (`fieldHeldOnlyOptionally`), or a scope of the fill declares its label on the path to a call that re-enters the fill (`declarationBoundOnPathToReenteringCall`) – and each cycle closed on the seam's path (`closesCycleInSeamTree`), keyed by kind and location; its membership test runs on the filler's generator tree, where a seam is a leaf, while the cycle walk below inlines every seam; and `rootScopeGenerators` walks, for cycles only, every foreign seam with holes from its own root over the validated scopes (`validateCyclesFromRootsOfForeignSeamsWithHoles`), which reports the seam's own cycle diagnostic where a fill would close a constant cycle the filler's walk closes earlier. `validateReachableTypeDescriptions` reports a missing fulfiller only outside every seam's tree (the fills this module generates for foreign seams entered), and a hole in a seam this run generates (`generatedSeamTypes`) while its module is unnamed (`currentModule.moduleName == nil`) is `holesInSeamsOfUnnamedModule`; a seam in neither `generatedSeams` nor `foreignSeams` — an added directory, a file no target lists — is built inline by every tree and has no hole. The guard hashes, after the parameters, each hole's builder label, builder type without `any`, tier access and every field of every stage (label, type without `any`, access); with no hole the input is unchanged. A wrapper whose instance type is optional (`LazilyInstantiated<X?>`) offers no by-value form, wherever it is declared. `Instantiable.forwardedReceivableProperties` and `DependencyTreeGenerator.propertiesToDeclare(in:)` are the only places that list a type's forwarded and declared properties with their by-value forms; use them rather than filtering `dependencies` again. `orderedPropertiesToGenerate`'s `siblingIndexByProperty` maps each lazily instantiated sibling's by-value property to that sibling too, unless another sibling declares that property itself, and the pairwise fallback applies the same rule so that both paths build the same set.
- **Validation maps a wrapper to the constant with the same optionality.** `Property.asValidatedForDependencyCycles` turns `x: LazilyInstantiated<X>?` into `x: X?`, not `x: X`: an `onlyIfAvailable` receive of the wrapper inside the tree it builds must not equal the stack entry, or a tree the constant twin accepts (the receiver is passed `nil`) is rejected as a cycle. `TypeDescription.lazilyInstantiatedInstanceType` is the generic argument as spelled (`any Service`), which is what a by-value receiver must match; `asInstantiatedType` normalizes it for the scope lookup. Validation’s instantiation stacks (`propertyStack`, `instantiationStack`, `ReceivableAlias.declaringInstantiationStack`) hold the mapped constants, while `receivableProperties`, `createdProperties`, `providedProperties` and `boundProperties` hold properties as declared, plus the by-value form of each wrapper. Map a declared property before comparing it with a stack, and never before looking it up in one of those sets. Generation differs: `Scope.createScopeGenerator`’s `childPropertyStack` keeps the declared wrapper and adds its by-value form, so `isPropertyUnavailable` passes `nil` for an `onlyIfAvailable` receive of either form inside the tree the wrapper builds, in production and mock generation alike.
- **A mock's parameters never mention `LazilyInstantiated`.** Adopting it on an owner must not change the generated `mock()` of an unchanged receiver. `createMockRootScopeGenerator` treats a dependency received both ways as one: it promotes the wrapper once whenever any receiver requires the wrapper or its instance, optional or not, and skips the by-value form and its optional form, also when the mock root declares the wrapper itself, and counts neither among the properties the mock is passed (`mockParameters`, which `childrenRequiringEachOther` takes as forwarded, so an `onlyIfAvailable` alias of either would count as always created). A required `x: LazilyInstantiated<X>`, or a required `x: X` or `x: X?` that no forwarded property fulfills (above), promotes `x: LazilyInstantiated<X>`; a required `x: LazilyInstantiated<X>?` beside none of them is promoted as itself, like any optional form whose non-optional form nothing requires. An `onlyIfAvailable` receive of the wrapper is then passed the node the mock builds, so no entry for the dependency is typed `LazilyInstantiated`; only a receive of the other wrapper kind, beside a promoted one, still is (above). A dependency the mock cannot build is classified in `generateMockRootCode` by its by-value form (`receivedParameterProperties`), so it is a `T` parameter or a `T?` override; the mock then binds `<label>_lazilyInstantiated` and passes that name to the types that receive the wrapper, and to aliases of it (`lazilyInstantiatedBindingNames`, threaded beside the flat-parameter rename map; the root's own receive goes through `returnDisambiguationMap`). `removingRenames(hiddenByDeclarationsOf:parameters:from:)` prunes `lazilyInstantiatedBindingNames` wherever it prunes that map, so a receiver below a nested scope that declares the wrapper – an `@Instantiated` child, an alias, or a builder's forwarded parameter – is passed that closest declaration, as in production. It is never rebound under the dependency's label: only one of the two bindings that share that label is renamed, so a rebinding inside a builder function would hide the instance parameter from the by-value receivers built there, which have no rename of their own to rebind. A by-value receiver of a wrapper renamed by sibling disambiguation rebinds the wrapper under its label, and an alias of its instance reads `.instance` from the renamed binding directly (`disambiguatedLazilyInstantiatedBinding`). `erasedToConcreteTypeMap` is keyed by both forms' types, and promotion falls back from a wrapper to the erasure of its instance (`concreteTypeErased(to:)`), so the wrapper is buildable whenever its instance is — also when the wrapper is optional, or when only a constant declares the erasure — and `mockReturnTypeIsCompatible` is asked about the instance type. `mockCanBuild` treats a lazily instantiated property as it does a constant: a mock has no values to forward, so it cannot lazily instantiate a type with `@Forwarded` properties, and `mock()` takes that dependency’s instance. A forwarded lazily instantiated property fulfills receives of itself, of its optional form, and of its instance beneath the mock root (`isFulfilledByForwardedProperty`), so neither `lazilyInstantiatedReceivedProperties` nor the by-value parameter set includes them; mapping such a receive to its by-value form first would lose that the wrapper is forwarded, and the mock would take a second value and ignore the forwarded one.
- **`TypeDescription ==`/`hash` ignore `any` at every depth.** `any P` equals `P`, `(any P)?` equals `P?`, `Instantiator<any P>` equals `Instantiator<P>`, and `(any P).Type` is treated as `P.Protocol` (not `P.Type`, which is `any P.Type`). `some P` stays distinct. Sets and dictionaries keyed by `TypeDescription` or `Property` therefore merge the two spellings, keeping whichever was inserted first, while `asSource`/`asIdentifier` keep each declaration's own spelling. `<` compares the spelling without `any` first, then the full spelling as a deterministic tiebreak, so two spellings of one type are equal under `==` but ordered under `<` (determinism was chosen over the Comparable contract). Any new map or set keyed by a type's spelling string (`asSource`) instead of `TypeDescription` must normalize `any` the same way, or it will miss matches `==` makes.
- **Diagnostics are chosen by source location, never by name order.** Every root (production, `generateMock` type, mock root, mock root's child trees) reports the first error its own walk finds, and `DependencyTreeGeneratorError.reportingAll(of:)` joins them in source order (`SourceDiagnostic.joiningInSourceOrder`), so renaming a type never changes which error appears or where. Two rules keep that true: a memo shared across roots (`ChildrenRequiringEachOtherValidation.validatedScopes`, `walkedAliasFulfillingProperties`) keeps only walks that completed — an entry from a walk that threw must be dropped, or a later root would skip the work and the reported set would depend on root order; and where one of several candidates must be picked (which promoted child a mock root validates first, which received property names a sibling, which reader a warning names), pick by declaration location or declaration order (`inOrderTheMockTreeFirstReceives` orders a mock root's promoted children by where its tree first receives them, for generation and validation alike), not by label or type-name order. The rename-invariance fuzzer oracle (#464) checks this class end to end.
- **`erasedToConcreteExistential: true` is orthogonal to the property's `PropertyType`.** The flag controls whether SafeDI wraps the concrete in the property's existential type at the call site; it does not determine whether the property itself is constant or lazy. The four combinations:

  | Decorator + property | `Property.PropertyType` | `isConstant` | Can close an accepted cycle? |
  |----------------------|-------------------------|--------------|------------------------------|
  | `@Instantiated let x: Concrete` | `.constant` | `true` | No — `throwIfInvalidCycle` rejects. |
  | `@Instantiated let x: Instantiator<T>` | `.instantiator` | `false` | Yes. |
  | `@Instantiated(erasedToConcreteExistential: true) let x: AnyProto` | `.constant` | `true` | No — `throwIfInvalidCycle` rejects. |
  | `@Instantiated(erasedToConcreteExistential: true) let x: ErasedInstantiator<A, AnyP>` | `.erasedInstantiator` | `false` | Yes. |

  When reasoning about whether an erased node can appear on a pruned back-edge, check `propertyType.isConstant` — don't short-circuit on the erasure flag.
