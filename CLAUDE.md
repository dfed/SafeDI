# SafeDI — Claude Code Guidelines

## Documentation

The core documentation is `Documentation/Manual.md`. Read it before making changes to understand SafeDI's API, macros, configuration options, and mock generation. The manual is the source of truth for user-facing behavior — if you change behavior, update the manual.

## Build & Test

```bash
swift build --traits sourceBuild   # Build all targets
swift test --traits sourceBuild    # Run all tests
./CLI/lint.sh                      # SwiftFormat — must pass before every push
swift test --traits sourceBuild --enable-code-coverage  # Coverage report
```

The `sourceBuild` trait is required for local development to compile SafeDITool from source. Without it, the plugin uses the prebuilt binary from the artifact bundle.

Always lint before pushing. Always run the full test suite after changes — don't rely on filtered runs alone.

### CI

- Every CI job runs on a Linux runner unless it genuinely needs macOS: Xcode or `xcodebuild`, an Apple platform SDK, the Xcode project plugin, or the macOS release binaries and their notarization. Linux runners scale; macOS runners are the scarce resource that pull requests and publishes queue on.
- A job on a `macos-*` runner states why in a comment in the workflow.
- New Linux jobs use the same container and setup as the existing Linux test job ("Build and Test on Linux" in `ci.yml`).

## Architecture

SafeDI is a compile-time dependency injection framework for Swift. It uses Swift macros (`@Instantiable`, `@Instantiated`, `@Received`, `@Forwarded`) to declare dependency graphs, then generates initializer code and mock methods via a build tool plugin.

### Key modules

| Module | Role |
|--------|------|
| `SafeDICore` | Models (`TypeDescription`, `Property`, `Instantiable`, `Dependency`), visitors (`FileVisitor`, `InstantiableVisitor`), generators (`ScopeGenerator`, `DependencyTreeGenerator`) |
| `SafeDIMacros` | Swift macro implementations (`@Instantiable`, `@Received`, etc.) |
| `SafeDITool` | CLI entry point with `scan`, `generate`, `query`, and `dump` subcommands — scans Swift files for `@Instantiable` types, builds dependency tree, generates output; `query` reports what one type needs |
| Plugins (`SafeDIGenerator`) | SPM build tool plugin that wires the tool into the build |

### Code generation flow

1. **Plugin** writes CSV of swift files → runs `SafeDITool scan` to build manifest → runs `SafeDITool generate` to produce code
2. **`SafeDITool generate`** parses all files via `FileVisitor` → builds `DependencyTreeGenerator` → generates per-root code + mock code
3. **DependencyTreeGenerator** creates `ScopeGenerator` trees → each generates its code via `generatePropertyCode`
4. **Mock generation** (`generateMockCode`) creates `mock()` static methods with `@autoclosure @escaping` parameters, `T? = nil` subtree parameters, and `MockContext` for disambiguation

### Conditional compilation

`FileVisitor` takes a `ConditionalCompilationEvaluator`; `InstantiableVisitor` takes a `ConditionalCompilationHandling`, which the macro sets to `.scanAllClauses` (the compiler already picked the active clause) and `FileVisitor` sets to `.evaluate(evaluator)`. The evaluator treats the supplied `activeCompilationConditions` as complete (a bare condition not in the set is inactive), scans every clause of platform-conditioned blocks (`os()`, `canImport()`, …), and evaluates mock-only content (`SafeDIContentDetector`) as if `mockConditionalCompilation` were active. A guarded initializer counts as SafeDI content only when `ConstructionInitializerCandidates` finds some evaluation could select it for construction — it must be able to fulfill the dependencies (bounded below by those outside every `#if` and above by those in every clause) and must not follow an unguarded initializer that fulfills them in every evaluation; initializers in `@Instantiable` extensions never count. Each evaluation that decides a block guarding SafeDI content is a `ConditionalCompilationDecision`; `generate` prepends `ConditionalCompilationDecision.compileTimeAssertions` (`#if …` / `#error`) to every generated file so the compiler rejects code generated under a condition it evaluates differently. There is no "unknown condition" state and no error at generate time: the compile-time assertion is the fail-closed mechanism. `parseModule` first parses the module's own files (`configurationFilePaths`) named `SafeDIConfiguration.swift`, chosen by path alone, and walks them to find the module's `#SafeDIConfiguration`: `SafeDIContentDetector` classifies a configuration as production content, so its `#if` blocks never depend on `mockConditionalCompilation`. The configuration found there builds the module's evaluator, every other file is read, parsed, and walked once with it, and the `SafeDIConfiguration.swift` trees are walked again from memory only when the mock condition is not the default. When no `SafeDIConfiguration.swift` holds a configuration (the fallback), every file is walked with the supplied conditions and the default `DEBUG` mock condition, which finds a configuration elsewhere; if it names another mock condition, every file that declared SafeDI content is read, parsed, and walked again — no text heuristic picks a subset. `SafeDIConfiguration.placementWarning` reports exactly that case (configuration outside `SafeDIConfiguration.swift` with a non-default mock condition) as a `SourceDiagnostic` with `.warning` severity located at the invocation (`SafeDIConfiguration.declarationLocation`, which travels in module info and scan's cache). `SafeDIConfiguration.unreadableAdditionalDirectoryWarnings` likewise warns, at the invocation, about each `additionalDirectoriesToInclude` entry of the selected configuration from which no Swift file can be read (nothing at its path, or a non-Swift file; an empty directory is fine). It judges `ParsedModule.additionalDirectories`, the `AdditionalDirectory` entries paired with the path they resolved to: scan's cache stores scan's resolution (against scan's working directory, which its freshness check also enumerates), and a fresh parse uses this run's. It is a warning, not an error, because `scan` reads every configuration's directories in every clause and a directory may exist only on some platforms. `generate` returns warnings instead of throwing them and `run()` prints them; `scan` never warns, so a build warns once per `generate`. Every syntax tree but those of `SafeDIConfiguration.swift` files is released as soon as it is walked, so memory scales with concurrency rather than module size. `scan` and `generate` both go through it, and it rejects more than one configuration in scope. `scan` records its project root in the manifest so `generate` matches configuration files by the same resolved paths.

Build tool plugins cannot read the conditions the compiler receives while they plan the build, so the `SafeDIGenerator` plugin also passes `generate` the literal arguments `--build-setting-active-compilation-conditions=[${SWIFT_ACTIVE_COMPILATION_CONDITIONS}]` and `--build-setting-other-swift-flags=[${OTHER_SWIFT_FLAGS}]` (`BuildSettingCompilationConditions`). Swift Build (Xcode and SwiftPM's `swiftbuild` backend) expands them when the command runs, and Xcode project builds expand them through the shell script that runs the command; SwiftPM's native backend passes them through literally. When both arrive expanded, their conditions plus the `-D` flags in `OTHER_SWIFT_FLAGS` *replace* the command-line and manifest conditions (Xcode reports a package's debug-configuration defines to plugins in Release too, so a union would be wrong); otherwise `generate` falls back to them. The plugin passes the options to every SafeDITool it runs, including the prebuilt binary pinned in `Package.swift` (Swift 6.2 sometimes hands the plugin that one even with the `sourceBuild` trait) and the `.safedi/` download named by `safeDIVersion` in `Plugins/Shared.swift`, so those must never name a release older than 2.1.0-rc-3, the first to accept them. Which files exist — roots, `generateMock: true` types, `additionalMocksToGenerate` entries, `#SafeDIConfiguration` files — is still decided by `scan` at planning time, but independently of any condition: `scan` plans an output for each such declaration in every clause of every `#if` block (`OutputFileDeclarations`, which `SafeDIContentDetector` collects during the walk of each block it already makes and `FileVisitor` adds for the clauses it scans), and treats the files in every configuration's `additionalDirectoriesToInclude` as inputs, parsing those only an inactive configuration lists solely to plan their roots. `generate` writes every planned output, without code (only the header and its compile-time assertions) when the declaration is inactive under its conditions, and generates the additional mocks only of the configuration it selects. It still rejects with a `ManifestError` a declaration whose file the manifest does not list (the manifest's `mockScopedFilePaths` lets it check mocks and configurations), which with superset planning means the file changed after `scan` or the manifest is hand-written. It also rejects a manifest in which two outputs name one file, which only a hand-written manifest can do: `scan` lists each additional mock once, however many times a configuration lists it. The `PluginScanner` fallback ignores `#if` and unions every configuration's arrays, so it plans the same superset. Because a cached file scan may declare a configuration in an inactive clause, `generate` parses the module afresh when a stale file declares a configuration in any clause, not just an active one; and when it parses `additionalDirectoriesToInclude` afresh it names those files as the manifest does, so their roots match its entries.

Because `generate` usually has more conditions than `scan` (always `SWIFT_PACKAGE`, `DEBUG` in debug), scan's cache keeps per-file results keyed by what each file consulted. `ScannableClauses.consultedConditions` records every bare condition a clause selection depended on (minus the mock condition for mock-only blocks, which is forced active); `FileVisitor` and `InstantiableVisitor` accumulate them only for blocks whose selection can change what they report: blocks with SafeDI content, blocks with syntax errors, and (separately, as `importOnlyConsultedCompilationConditions` with `importSegments` holding the block source) blocks that guard only imports. `FileVisitor` also collects `mockImports`: each block guarding only imports is selected again as a block guarding mock-only declarations is, and `importOnlyConsultedCompilationConditions` covers both selections. Generated mock files, `SafeDIMockConfiguration.swift`, the mock half of `--combined-output`, and module info carry `mockImports`; dependency-tree files keep `imports`, so `#if DEBUG import A #else import B #endif` still gives production code `import B`. `CachedScannedModuleInfo` (see Serialization) stores the files that consulted nothing as one `ModuleInfo` and the rest as `CachedFileScan`s; `generate` walks a file again only when a condition it consulted changed value, re-evaluates only its import segments when only those changed, and parses the whole module afresh when a walked-again file declared a configuration. Any new state a visitor collects from inside an `#if` block must either be covered by `consultedCompilationConditions` or be provably independent of the selection, or the cache becomes unsound. `OutputFileDeclarations.instantiableTypeNames`, and `ModuleInfo.instantiableTypeNamesInAnyClause`, which unions them and which scan's cache and `.safedi` carry, are such independent state: `SafeDIContentDetector` records the type of every `@Instantiable` in every clause of each block `FileVisitor` reaches, naming nested types from the enclosing type `FileVisitor` hands it, and `FileVisitor` adds the declarations outside every block, so any evaluator records the same names; `generate` uses them to tell an `additionalMocksToGenerate` entry that names a declaration these conditions leave inactive, whose file it writes without code, from one that names no type.

### Type requirements query

`SafeDITool query needs <TypeName>… --include <directory>… --module-info <file>…` reports what each named type needs: the modules whose declarations build it and its dependencies in production, its `@Forwarded` parameters, the dependencies no `@Instantiable` declaration fulfills, and what its mock needs. It exists so a focused app can be assembled from exactly the modules one feature needs. It is in beta, and `--help` and the manual say so: it was built ahead of a live use, so its options, text, and JSON may change in any release as real projects adopt it, and the JSON's `formatVersion` is `0` until the format is stable; keep the beta note and the `0` until Dan removes them, and make `1` the first stable format then. `query` is a command group with `needs` as its one subcommand, so further questions (dependents, providers) join as subcommands rather than flags. `--include` is spelled as `generate`'s, and each directory is a module (`IncludedModule`) named after its last path component, or after as many trailing components as tell it apart from the other modules (`Home/Sources`), so a `Modules/<Name>/Sources` layout works without configuration; a Swift file included directly belongs to its directory's module. `--module-info` names `.safedi` files, each a module read with `ModuleInfo(moduleInfoData:)` as `generate` reads a dependent module's (an unreadable or missing file is `QueryError.moduleInfoNotReadable`, with `BinaryFile.unreadableFileExplanation`), named after the file without `.safedi` and without the `_safedi` the Bazel macro appends (`IncludedModule.moduleName(ofModuleInfoFileNamed:)`), under the same suffix rule as directories, with the file name as spelled as the fallback when a directory's path reads the same (`Home` and `Home.safedi`), which is also what keeps the suffix loop finite. `ParsedQueryModule` reads either kind: a directory's declarations are attributed to the files found under it, spelled under the `--include` argument; a module info file's to the paths it records (`sourceFilePath`, the declaration and mock declaration locations), spelled as stored, since the writing build's spelling is all the file has. `--active-compilation-conditions` applies only to directories, and `generatedIn` reads a module info file's `configurations`. `QueryCommand.swift` parses each directory module with `parseModule` (the module's own files are its configuration files; `additionalDirectoriesToInclude` is deliberately not followed, since every module is included), rejects a file in two modules, combines the modules' instantiables in module-name order, runs them through `normalizingInstantiableTypes(of:)` and `resolveSafeDIFulfilledTypes(instantiables:)` (`InstantiableResolution.swift`, shared with `generate`, so the query sees the types exactly as `generate` does), and reports the types named in order, each once, from that one read. `DependencyTreeGenerator.requirements(forTypeNamed:generatesMock:)` builds a type's mock root exactly as `generateMockCode` builds the root of a type listed in `additionalMocksToGenerate` — the same `mockScopes(additionalMocksToGenerate:receivedPropertiesCache:)` setup and validation, with the type always listed, the same `mockRootInstantiable(for:scope:)` canonicalization, the same `createMockRoot(for:scope:…)` checks — and reads `ScopeGenerator.mockRootParameters(instantiable:)`, the classification `generateMockRootCode` emits; `generatesMock` only decides whether a hand-written method named `mock` is a collision (`createMockRoot`'s `GeneratedMockReason` is `nil` otherwise, and the root is built with that method). A mock root is a tree in which every dependency the type receives is built beside it, so the tool runs it twice: over the map with every hand-written mock removed (`Instantiable.withoutHandWrittenMock`, `mockOnly` entries dropped) for what the type needs in production, and over every declaration for what the mock needs. Which mock is decided in `query()` from the entry under the type's own key, the one `mockRootInstantiable` builds the root from (`TypeReport.Mock.Kind`): `generated` when a declaration sets `generateMock: true` or an included module's configuration lists the type (`generatedIn` names those modules, and the text says how a project without them generates the mock), `handWritten` when that entry has a hand-written mock, and `wouldBeGenerated` otherwise, so the focused app learns what the `mock()` it would generate needs — `mockOnly` modules included, which the production view strips. A hand-written method named `mock` on another entry for the type (a `mockOnly` extension whose mock returns a protocol, which `resolveSafeDIFulfilledTypes` merges only into that protocol's slot) is neither the root's mock nor compatible with generating one, so the report is `MockReport.none(NoMock)` rather than an error: the production part still prints. The mock view is computed before the production view, so a missing name is reported from the full map, with the types that fulfill that name and the types named most like it (`QueryError.noInstantiableNamed`). Neither part has a walk of its own, so the report cannot disagree with the generated mock; any new kind of `mock()` parameter must be added to `MockRootParameters`, not computed inside `generateMockRootCode` alone. The query runs exactly the checks on the path of one root, because it reaches them through `mockScopes` and `createMockRoot`, and none of the passes `generateMockCode` runs over every mock root together after its loop (`validateSendableBuildersCaptureNoNonSendableWrapper`, `validateConfigurationsAreBuiltOneWay`): those gate emitting the module's mocks and change nothing in the report, and `generate` reports them with fix-its, so a query that succeeds where `generate` would throw one of them is intended, not drift. The rule for a new check: one that decides whether a single root can be generated goes in `createMockRoot`, so both callers run it; one that needs every root at once goes after the loop, and is not added to the query. The public result is `TypeRequirements` (declarations with the file that holds each, erasures with every declaration that makes them, forwarded and required parameters with reasons); `TypeReport` in the tool attributes each file to its module (`FileAttribution`: the module's name, its `--include` or `--module-info` paths as given, and the file spelled under the `--include` argument through `NormalizedFilePath.path(under:spelled:)`, or as a module info file records it) and formats the text; `QueryReport` wraps the types under `formatVersion`, and `QueryErrorReport` prints any error as JSON with a `kind` when `--json` is set. The JSON is a contract documented in `Documentation/QueryNeeds.md`: arrays are always present, optional keys are omitted, every reason has a `reasonKind` beside its sentence, and from `1` on `formatVersion` is raised when a key is renamed, removed, or changes meaning, so a change to the shape is a change to that page and, once the format is stable, a version bump. An erasure is attributed to a module already needed when one declares it, else to the first declaring module by name, with the rest listed beside it: any one declaration suffices, and the choice must not depend on set order.

### Mock generation flow

Mock generation follows this pipeline:

1. **`generateMockCode`** builds the mock scope map via `createMockTypeDescriptionToScopeMapping` (includes ALL types, not just reachable from roots)
2. For each type with `generateMock: true`, **`createMockRootScopeGenerator`** promotes `@Received` dependencies to root-level children (except those `mockCanBuild` rejects), in the order the mock's tree first receives them (`inOrderTheMockTreeFirstReceives`), and validates for cycles
3. **`ScopeGenerator.generateMockRootCode`** builds the mock method:
   - Calls `collectMockParameterTree` to walk the dependency tree and build `MockParameterNode` trees
   - Collects flat parameters: `@Forwarded` deps, uncovered `@Instantiated` deps, `@Received` deps not in the tree
   - Generates `SafeDIOverrides` struct (if tree children exist) and the `mock()` method signature and body

The production code path (`generatePropertyCode` with `.dependencyTree`) and mock path (`.mock`) share the same `ScopeGenerator` but diverge at `generatePropertyCode`. Mock fields (`mockInitializer`, `mockReturnType`, `customMockName`) are only accessed in mock code paths — never in production paths.

### Cycle mechanisms

Multiple cycle-related mechanisms coexist — keep them distinct:

| Name | Scope | Set by / when | Role |
|------|-------|---------------|------|
| `isPropertyCycle` on a scope/node | Per-root, syntactic | `Scope.createScopeGenerator` when a property label repeats in the ancestor stack | Terminates infinite descent during a single root's walk; differs between roots for the same underlying cycle. |
| `cycleEdges` (set of `CycleEdge`) | Global | `DependencyTreeGenerator.computeCycleEdges`, alphabetical-DFS feedback arc set | Chooses a single back-edge per cycle consistently across all roots — required because shared `SafeDIMockConfiguration` structs must have one shape. Consumed by struct generation AND override-path navigation in mock bodies. Each root returns the nodes of the types its tree configures (`collectConfigurationTypes`); `generateMockCode` keeps the first root's node for each type, in alphabetical root order, and only then generates that struct (`ScopeGenerator.generateConfigurationStruct`), so no root generates a struct that is thrown away. |
| `throwIfInvalidCycle` | Shared classifier | Called from `validatePropertiesAreFulfillable` (production, and a mock root whose children require one another) and `validateMockRootScopeForCycles` (mock) | Rejects constant + partially-lazy + received-lazy cycles. Accepts fully-lazy non-received cycles (those compile as long as pruning breaks the config-struct recursion). Neither stack walk considers an `onlyIfAvailable` dependency, `@Received(onlyIfAvailable: true)` or an `onlyIfAvailable` alias (`Dependency.canCloseDependencyCycle`): generation passes it `nil` while the property it receives is built (`isPropertyUnavailable`, which in a mock matches the property still being built exactly or by its non-optional form), whatever kind of property that is — constant, `LazilyInstantiated`, or `Instantiator` — so `a: A?` under the `a: A?` it is built inside gets `nil` as it does under `a: A`, and so does an alias of `a` only if available. Both walks classify the dependency that closes a cycle with `closingReceive(of:in:)`: a required `@Received` dependency is a receive, and so is a required alias, which receives its fulfilling property — unless its scope creates that property, which the alias then refers to. Do not use `Dependency.Source.isReceived` for this; it is `false` for aliases. The classification matters only for a non-constant property: a required alias fulfilled by a `LazilyInstantiated` is mapped to the constant it stands for and rejected as a constant cycle, exactly as its constant twin is. Production's received walk agrees by another route: `Scope.requiredReceivedProperties` lists a required alias's fulfilling property, with `aliasProperty` so the error names the alias, except one the alias's scope always creates (`unconditionallyCreatedProperties`: instantiated, forwarded, or a required alias), which requires nothing of an ancestor. An alias of an `onlyIfAvailable` alias on the same scope stays listed, so the required-alias check can see whether that alias is created. A scope closing a property cycle (`isPropertyCycle`) generates none of its dependencies, so `ScopeGenerator` does not count an alias of another of its type's aliases as received there (`cycleClosingAliasProperties`); otherwise the cycle-closing scope is ordered after the alias it renames, which is ordered after the cycle-closing scope, and a chain of aliases is emitted before what it renames. |
| `validateMockRootScopeForCycles` | Mock graph | Called after `@Received` promotion in `createMockRootScopeGenerator` | Walks the post-promotion scope to catch cycles that only surface once received deps are promoted to mock-root children — through an ancestor only. For a type listed only in `additionalMocksToGenerate`, whose tree `validatePropertiesAreFulfillable` checks for hidden properties alone, it is the only cycle check. A promoted received optional property is built as its non-optional value, so a received or aliased dependency matches either form. It reports whether an `onlyIfAvailable` alias of a property still being built is declared (that alias is not created), matching the alias's fulfilling property in any of `Property.formsOnMockInstantiationStack`, as generation's `isPropertyUnavailable` does, so an alias of `x: X?` counts inside the tree that builds `x: X` or a `LazilyInstantiated<X>`; production's walk then also runs on the mock root, to report a required receive of that alias as `dependencyReceivedInSameChainItIsInstantiated` (in a mock, `formsOnStack` matches the same forms). |
| `childrenRequiringEachOther` | One scope's instantiated children | Called after `validateMockRootScopeForCycles` on the mock root, and by `validateChildrenDoNotRequireEachOther` | Cheap check, from the cached `collectReceivedProperties`, for children that require one another (C receives B while B's subtree receives C, directly, through any chain of aliases the scope declares, by requiring an `onlyIfAvailable` alias of B declared in the subtree — `requiredOnlyIfAvailableAliases`, each an `OnlyIfAvailableAliasRequirement`: the alias with its fulfilling property, and the alias properties the requirement depends on — or as `b: B?` fulfilled by the unwrapped `b: B`, decided by the same sets, so an `onlyIfAvailable` alias of `b: B?` that a receiver beneath requires counts as one of `b: B` does), which no ancestor stack shows. A receiver requires an `onlyIfAvailable` alias through any chain of aliases, as `ScopeGenerator.isRequiredByChild` and its `requiredOnlyIfAvailableAliasProperties` order them: `ScopeDeclarations.requirements(childRequiredReceived:childRequirements:)`, which the walk's `finished` and `requiredReceiver` share, lists an alias as required when a child's tree requires its property, when a required alias the scope declares is fulfilled by it (always created, whatever an enclosing scope provides), or when the last alias of a requirement — one from a child's tree, or another of the scope's own — is fulfilled by it, found to a fixed point. A requirement (`OnlyIfAvailableAliasRequirement`) is the chain of `onlyIfAvailable` aliases through which a receiver requires the last, nearest the receiver first, one entry per way an alias is required, with `requiresFulfillingProperty`: whether the receiver requires the last alias's fulfilling property where every alias is created. An alias is created only where no enclosing scope provides its property (or unwrapped form), or the mock binds it: the receiver is then handed that property, as `isProvidedByEnclosingScope` has generation do, and requires it instead — the first such alias from the receiver decides (`providedAliasIndex`), and nothing is required of the aliases beyond it. So the walk cuts a requirement at the alias whose property a scope between the child and the alias provides to the child (`ScopeDeclarations.requirements(recordedFrom:ofChild:)`, except the child being built, as the stack check does): the scope's own `onlyIfAvailable` alias with that property is required through the nearer aliases, and otherwise only the nearer aliases are kept, with `requiresFulfillingProperty` false. The check resolves what is left against the checked scope's and its enclosing scopes' provided properties (`providedProperties`, the same set `ChildrenRequiringEachOtherValidation.enclosingProvidedProperties(ofChild:of:enclosingProvidedProperties:)` threads): the child requires the first provided alias's property, which names the sibling that declares it, or its unwrapped form; where none is provided and `requiresFulfillingProperty` holds, the child requires the last alias's fulfilling property. So a provider that is a sibling emitted after the receiver's tree is a sibling cycle, whatever spelling the alias has, as it is in generation. The walk clears `requiresFulfillingProperty` where a scope declares the last alias's fulfilling property, exactly or by its unwrapped form (as `record` and ScopeGenerator's `isReceivedFromAncestors` do for a received property) — the alias is created from that scope's property, which the scope can still build after the receiver's branch — and drops the last alias where a scope forwards it, since a forwarded property is in scope wherever the alias is built and the alias is always created. A child whose tree receives itself through an alias or unwrapped requires itself; one that receives its own property directly is left to the received walk and the ancestor check, which report it. A mock root binds nothing for a property it declares itself, although promotion collects it into `allReceived`. When the chain closes on an alias of the first child, it ends with the child's own property (`@Instantiated a: A -> @Received renamedA: A -> @Received a: A`); each `onlyIfAvailable` alias in the chain adds a sentence suggesting `onlyIfAvailable: true` on the receive (`RequiredOnlyIfAvailableAlias.hint`), as the received walk's diagnostics through such an alias do. Property types do not matter: an `Instantiator` captures what its tree receives when it is created, so two sibling `Instantiator`s that receive each other cannot be ordered either. On a mock root it gates production's `validatePropertiesAreFulfillable` walk, which reports constant cycles. Running that walk on every mock root would add a received-dependency walk per node of every mock tree; on a real 250-mock-root app the check triggers it zero times. |
| `validateChildrenDoNotRequireEachOther` | Every scope of the production trees, then of each mock tree | After production's `validatePropertiesAreFulfillable` passes, and after the mock root's walk | Reports, as `aliasedDependenciesFulfillOneAnother` at the alias that closes the cycle, aliases of one scope that are fulfilled by one another (`aliasesFulfillingOneAnother`; the macro cannot see which `#if` clauses are active, so this is not a macro check), then, as `dependencyReceivedInSameChainItIsInstantiated` at the receiver found by `requiredReceiver` (the first dependency in the last child's tree that requires the closing property; a required `onlyIfAvailable` alias of it that no enclosing scope provides the property of — one `ScopeDeclarations.requirements(childRequiredReceived:childRequirements:)` lists, with no alias nearer the receiver provided either — is followed to the receiver that requires the alias, whose hint the diagnostic then carries, for each alias in the chain: on the same scope, a required alias of the alias is that receiver, and an `onlyIfAvailable` alias of it that is required in turn is followed next, and otherwise the children's trees are searched for the alias's property; when the closing property is itself the property of an `onlyIfAvailable` alias that an enclosing scope provides, the alias is followed the same way, with the enclosing property in its hint (`RequiredOnlyIfAvailableAlias.providedProperty`); the search threads the provided properties as the check does, so it stops where the walk stops and always finds a receiver), children that `childrenRequiringEachOther` finds. It catches what the received walk misses: that walk follows a received property to the scope of its type, so it never follows an `Instantiator`, and no walk covers promoted scopes' trees. Running after the walk leaves every diagnostic the walk reports unchanged. `ChildrenRequiringEachOtherValidation` threads which `onlyIfAvailable` alias properties enclosing scopes provide (restricted to the properties of the module's `onlyIfAvailable` aliases, so nearly always empty) and keys `validatedScopes` by scope and that set, which makes each scope checked once per production pass and once across all mock roots for each such set; on a mock root, the result `childrenRequiringEachOther` computed for the gate is reported directly and only the children's trees are checked again. |
| `stackPropertiesReliedOnByWalkedProperty` | Received walk in `validatePropertiesAreFulfillable` | Filled as each received property's walk returns without throwing | Memo keyed by received property (not scope: another label of the same type can reach an error the first label's walk bailed before). Stores the properties on the stack the walk relied on (bails on cycles that aren't ours, plus those passed up from skipped walks); a later visit skips the property only when its stack contains all of them, so the first error in walk order is unchanged while paths into an unrelated cycle are not re-walked. |
| `isHanded` (handed values) | Received walk in `validatePropertiesAreFulfillable`, per tree | Asked before the walk descends into a received property's scope | The walk does not follow a received property the tree is handed: one no scope in the map instantiates or renames another property to (`propertiesBuiltByAScope`, built lazily), which in a mock's tree the mock root also does not promote, because the root forwards it or `mockCanBuild` says no. Such a value comes from outside the tree (a `@Forwarded` value or a `mock()` parameter), so its type's receives are no part of the tree; a cycle through them is reported where a tree builds that type. Mocks and production follow this one rule (production's map holding only reachable types was a type-level form of it). Which branch applies is the tree's, not the pass's: the validation of mocks (`cyclesOnly`) also walks every production root's tree, and `ValidatedRootScope.isMock` is `false` for every root of the dependency tree, which receives nothing, so its mock (if any) promotes nothing and builds its production tree; the mock branch is for the trees of non-root mocked types only. Otherwise adding one unrelated `generateMock` type to a module, or `generateMock: true` to a root, could reject a production tree the production pass accepted. A mock whose parameter no caller can build is accepted, as production already accepted such a forwarded value. Over-approximates in a mock: a property forwarded inside the tree whose type the mock could build is followed, since the pre-promotion validation does not know whether the mock promotes it. |

Key consequence: if `throwIfInvalidCycle` accepts a cycle, every hop in it is non-constant (Instantiator/ErasedInstantiator-typed). Any code that assumes "a cycle node reached through a constant-typed property" is reasoning about something impossible.

**`LazilyInstantiated` is generated like an `Instantiator` and validated like a constant.** A `LazilyInstantiated` / `SendableLazilyInstantiated` property (`PropertyType.lazilyInstantiated`, `.sendableLazilyInstantiated`) is emitted as a builder function handed to its wrapper, but its instance is created at most once, so it cannot break a cycle. Every property that enters the cycle logic – in `validatePropertiesAreFulfillable` and in `validateMockRootScopeForCycles` – is first mapped through `Property.asValidatedForDependencyCycles`, which turns the wrapper into the constant it stands for. `throwIfInvalidCycle` is unchanged, and a tree is valid with the wrapper exactly when it is valid with that constant. Never classify these properties as lazy hops: generated code reads `.instance` for every by-value receiver, so a "fully lazy" cycle through them would recurse with no user code involved, creating a fresh wrapper at each level. `PropertyType.isConstant` is `false` for them, because mock generation uses it to mean "bound without a wrapper", so do not call `isConstant` on a property that has not been mapped. Cycle diagnostics show the constants; `lazilyInstantiatedDeclarations` threads the declared wrappers through validation so the message can name them.

### Mock generation specifics

- **Share logic between production and mock paths where possible.** Validation, scope population, and other shared concerns should live in common helpers rather than being duplicated between `createTypeDescriptionToScopeMapping` and `createMockTypeDescriptionToScopeMapping`. When adding validation to one path, check whether the other path needs it too.
- **Selected construction initializer.** `InstantiableVisitor.canonicalConstructionInitializer` is the single initializer SafeDI selects for construction (first init that fulfills the type's dependencies). `Instantiable.initializer` is populated from it, and mock generation emits against its signature. Validation that only matters for the path SafeDI uses (e.g., diagnosing `Self.*` in default expressions) should gate on this — walking every entry in `visitor.initializers` false-positives on unused overloads.
- **Two-layer mock return type** (extension-based `customMockName` only). When a `customMock` method returns a type different from `Self` (permitted via `fulfillingAdditionalTypes`), two concerns have to agree:
  1. **Inner closure type** (`MockParameterNode.builderClosureType`) — the type of the override closure stored in the parent's `SafeDIMockConfiguration`. Uses the property type so callers writing overrides match the receiving slot. Fixed in #251.
  2. **Outer `mock()` return type** — the generated `mock()` wrapper must return whatever the user's `customMock` returns. Fixed in #266.

  When touching extension-based types with `customMockName`, confirm both layers. `mockReturnTypeIsCompatible(withPropertyType: concreteInstantiable)` distinguishes genuine hand-written mocks from mockOnly-inherited ones.

  A mock that returns one of the type's additional types builds only properties `mockReturnTypeIsCompatible` accepts, so the type is built with its mock for some properties and with `init` for others, yet mocks generate one `SafeDIMockConfiguration` per concrete type, from the first node that needs it. `generateMockCode` therefore rejects (`validateConfigurationsAreBuiltOneWay`, a `SourceDiagnostic` at `mockDeclarationLocation`) a type whose first mock-built and first `init`-built nodes across all roots, in root order, both read a struct and differ in `MockParameterNode.configurationRequirements` (child properties, default parameters by label and type, builder parameter types). A node beneath a `cycleEdges` edge reads no overrides from its struct (its parent's struct has no field for it), so `collectConfigurationNodesByConstruction` leaves it out, and when the first node of a type is such a node built the other way, the struct is generated from the first node that reads it instead. A node that needs no struct is built from a closure typed by its property, so the shape #419 made compile, a mock that takes nothing, stays accepted, as do a mock with exactly `init`'s parameters and a mock that returns the concrete type. An extension's `instantiate(…)` plays `init`'s part: its default-valued parameters are struct fields (#452), so an `instantiate`-built node can read a struct and conflict too, and the diagnostic names the construction by `MockParameterNode.isExtensionBased`. Never emit a second struct for the same type. The struct's default-valued fields take their defaults from the hand-written mock's parameter of the same label and type (`DefaultParameter.defaultParameters(of:dependencies:)` on `mockInitializer`, matched to the dependencies of the concrete type's entry), whichever node the struct is generated from and even when no property is built with the mock in this module; `init`'s (or `instantiate(…)`'s) default applies only to a field the mock declares no default for, so `configurationRequirements` compares labels and types, never values. A node built with `init` beneath a `cycleEdges` edge, which no override reaches, elides its labeled defaults except those the mock also declares (same label and type), for each of which it passes `<Type>.SafeDIMockConfiguration().<label>` (`callSiteArgumentsForPrunedOverride(handWrittenMockDefaultParameters:)`, `MockContext.handWrittenMockDefaultParameters`), so the default is the mock's, evaluated in the struct, as for every other property of the type. Never inline the mock's default expression at the call site: it can name the type's static members or nested types, which resolve inside the struct (nested in the type's extension) but not in the mock root's extension.
- **Dependencies a hand-written mock is not passed.** A generated mock passes a dependency to the hand-written mock's argument with the same label (`resolveBuilderArguments`, `generateReturnArgumentList`). A mock merged in from a `mockOnly` declaration may have no argument for some of the production declaration's dependencies (`Instantiable.dependenciesNotPassed(to:)`, which never lists a `@Forwarded` one: it is an argument of the type's `Instantiator`). `createMockTypeDescriptionToScopeMapping` gives every property built with that mock a scope whose instantiable declares only the rest (`Scope.dependenciesLeftOut` records what was removed), so the dependency is not built, received, promoted, or offered as an override, and the mock declares no value it never uses. A dependency left out is built after all when the tree of a dependency the mock is passed receives its label, which is known only from the scopes, so the mapping is built again until nothing more is found. A mock that returns one of the type's additional types builds only properties of that type; the others are built with `init` from the complete scope, so one concrete type can have two scopes. The mock root's own instantiable is filtered to the dependencies of its scope, or a dependency its scope does not build would surface as a flat `mock()` parameter.
- **Hand-written `mock` vs. generated `mock()`.** A type whose `mock()` this module generates (`generateMock: true` or `additionalMocksToGenerate`) must not also have a hand-written method named `mock`, wherever it is declared. The macro enforces this within one declaration; `DependencyTreeGenerator.generateMockCode` enforces it across declarations and modules (a `mockOnly` pair) when it creates mock roots, by name only — no signature analysis, because a `mockOnly` extension's mock defaults every parameter, so even "distinguishable" pairs leave `Type.mock()` ambiguous. Do not work around such pairs at the call site (e.g. coerced function references). `Instantiable.mockDeclarationLocation` locates the diagnostic and must travel with `mockInitializer` through every merge.
- Names bound for receivers are tracked by label and then type: the disambiguation maps (`[String: [TypeDescription: String]]`) – `flatParameterDisambiguationMap` for renamed flat parameters, overrides, and sibling bindings, `lazilyInstantiatedBindingNames`, and `uncoveredDependencyNames` – give the name a receive of that label and type is handed.
- A receiver whose label was disambiguated is rebound to the disambiguated name (`emitReceiverBindings`), found by its declared type and then its unwrapped type, since an `onlyIfAvailable` receive of `x: X?` is fulfilled by a disambiguated `x: X`. A receive the node passes `nil` (`MockParameterNode.unavailableProperties`) is not rebound: the name may not be declared yet.
- `TypeDescription.asIdentifier` produces identifier-safe disambiguation suffixes
- `TypeDescription.simplified` strips wrappers for cleaner suffixes, with fallback on collision
- Closure-typed defaults use `@escaping T = default` (not `@autoclosure`)
- `#SafeDIConfiguration` is always read from the current module only, never dependent modules
- **Received erased types.** `generateMockCode`'s `erasedToConcreteTypeMap` lets a mock root promote a received type no `@Instantiable` fulfills (e.g. `AnyService`) by building the concrete type an `@Instantiated(fulfilledByType:, erasedToConcreteExistential: true)` property of that exact property type names, in any module. It is keyed by the full property type, because a receiver matches by type, so an `ErasedInstantiator<(), AnyService>` erasure never counts toward `AnyService`. A type that erasures give more than one concrete type is left out of the map, and its receivers become required flat `mock()` parameters: picking one would depend on dictionary iteration order. Production never consults the map — production receivers get the value from an ancestor.
- **An `@Instantiated` dependency the mock cannot build is still declared.** `Scope.propertiesToDeclare`, which `ScopeGenerator` and the received-property walk (`ScopeDeclarations`) both read, includes `Scope.instantiatedDependenciesNotGenerated`: the type's `@Instantiated` dependencies no scope builds, which `mock()` takes as parameters. A receive of one beneath its type is therefore subtracted there, as production subtracts it, instead of reaching the mock root as a second parameter. Emission hands those receivers the parameter's final name where it enters the type's builder function, or the mocked type's whole tree for its own (`routingReceives(of:toParametersNamed:in:)`, beside `removingRenames`), and a receiver rebinds a parameter named apart. A receiver that is not beneath the type, such as its sibling, receives from above the mocked type and keeps a parameter of its own. A promoted sibling of the mocked type receives the mocked type's own such dependency by value, as its own created properties are one instance, and a receive of its `LazilyInstantiated` is wrapped around the parameter (`lazilyInstantiatedReceivedProperties` admits an instance in `mockedTypeUncoveredProperties`), never taken as a wrapper parameter or override. The instance of a wrapper the mocked type instantiates and the mock cannot build provides only that wrapper (`isProvidedByTreeByValue`): a promoted sibling's receive of the other wrapper kind takes the instance as a parameter or an override, as the mock builds a wrapper of each kind beside one it builds. That asymmetry is production's: a wrapper declaration provides itself and its instance only, so production rejects a receive of the other kind beneath it, and such a receive can only come from another declaration – another instance – while a promoted sibling's same-kind or by-value receive gets the mocked type's own property, as a receive beneath that declaration does. A promoted dependency stands for one built above the mocked type, so `createMockRootScopeGenerator` validates each promoted scope's tree for hidden received dependencies with the walk an additional mock's tree gets, rooted at that scope with its tree's received properties bound, so that the mocked type's own declarations hide nothing in it; a tree that passes is validated once across mock roots (`promotedScopesValidatedForHiddenReceives`), and one that fails is walked by every mock root that promotes it, so the errors reported never depend on the order mock roots are created in. Production never has such a dependency: `validateReachableTypeDescriptions` rejects it before scopes are built.
- **What a tree node provides.** One definition decides whether a scope provides a property to the scopes beneath it, so they do not receive it from its ancestors: `ScopeGenerator.provides(_:declaredProperties:forwardedProperties:)`. The scope declares or forwards the exact property, or, for an optional property, its unwrapped form, and a lazily instantiated property is declared (and forwarded) together with the by-value property of its instance (`declaredLazilyInstantiatedInstanceProperty`). `generateMockRootCode` drops a received property from its parameters and overrides only when its tree provides it by that definition, or when a promoted node's optional property is the receive's optional form, since a mock binds a node it builds to a non-optional value. A same-label node of any other type provides nothing: the receive stays a flat parameter or override, named apart from the root's tree bindings by label and type (`user_Draft`). Never match a received property to a tree node by label alone.
- **`onlyIfAvailable` overrides are keyed by label and type.** `generateMockRootCode` makes one `OnlyIfAvailableOverride` per `onlyIfAvailable` received property that no forwarded property or required receive covers and the tree does not provide (the mock root's own `x: X?` is handed a promoted `x: X`), even when a root tree node shares its label with another type: handing that node over is wrong (a promoted `editor: Editor` passed to its own `editor: Draft?`). `onlyIfAvailableOverrides(for:namedAfter:namesInMockScope:reservedNames:)` names the field and the binding by the bare label unless the label is a forwarded, default-valued, or uncovered-`@Instantiated` parameter, a root tree binding name, or another override's label; those are named by `identifierSafeNames` from the optional type (`user_Draft`). A flat received parameter or root alias that shares an override's name is still the one renamed, so mocks without such a clash are unchanged. A renamed override joins the flat renames in the receivers' disambiguation map, and `removingRenames(hiddenByDeclarationsOf:parameters:from:)` drops a rename wherever a nested scope declares or forwards that property (or its non-optional form), so such a receiver resolves to the closest declaration, as in production. The mock root's own renamed receive is rebound to its label at the root scope, unless the root binds that label already (to a node it promotes for another receiver); the root is then passed the renamed binding directly through the return's disambiguation map. Only promotion creates these clashes: when the mocked type's own tree hides the label, `HiddenReceivedProperty` rejects it before generation.
- When a mockOnly and a non-mockOnly coexist for the same type, `resolveSafeDIFulfilledTypes` merges them. The `(false, true)` and `(true, false)` branches handle opposite processing orders. Any cross-cutting concern (tracking sets, stale clearing) must be applied to both branches or order-dependent bugs will surface only on CI.

### Validation boundaries

Validation is split between the macro and the plugin based on available context:

- **Macro validation** (compile-time, local context only): The macro sees only the single decorated type or extension. Any error that can be determined from local context belongs here — missing `init`/`instantiate()`, invalid parameter combinations (`mockOnly + generateMock`), mock method signature issues, access control, an optional `@Instantiated` property type (`X?`, `X!`, `Optional<X>`, `Instantiator<X>?`, `Instantiator<X?>`; `InjectableMacro`). These produce fix-its in the IDE. Code generation test fixtures therefore never declare an optional `@Instantiated` property. The warning at a dependency type that names a type nested in the decorated declaration unqualified or through `Self` collects nested types from every `#if` clause and exempts a nested `@Instantiable` type exactly where `TypeDescription.qualifyingInstantiatedType(within:amongInstantiableTypes:)` qualifies it, as SafeDITool does. Its fix-it qualifies with every enclosing type from `context.lexicalContext`, and must also rewrite the same-named parameters of initializers and hand-written mocks and an alias’s `ofType:` argument, or the declaration stops matching its dependencies.
- **Plugin warnings** (build-time, full context): `DependencyTreeGenerator.generateWarnings()` runs after the tree has generated. It reports a `LazilyInstantiated` property that is instantiated whenever the type declaring it is created, because a type created along with that one reads its instance by value. `InstantiationAnalysis` reads the scopes `rootScopeGenerators` built and validated (`validatedScopes`), is type-level, and is memoized per `Scope`: a type’s creation reads what its own required by-value receives and aliases read, plus what its constant children and its instantiated-with-owner lazily instantiated children read, minus every label the type declares. A read of a renamed wrapper's instance is followed through every renaming the type declares (`propertyRead(by:)`) back to the property it starts from. An `onlyIfAvailable` receive is deliberately never a reader: whether it reads the instance or is passed `nil` depends on sibling ordering, which only `ScopeGenerator` knows, and a warning about a dependency that is not instantiated would be worse than a missing one.
- **Plugin validation** (build-time, full context): The plugin (`SafeDITool generate`) sees all modules' types. Errors that require cross-type knowledge belong here — unfulfillable dependencies, received dependencies hidden by a closer ancestor's property with the same label (generated code passes dependencies by label), a rename whose `fulfilledByDependencyNamed:` label its own type instantiates, forwards, or renames to with a type other than its `ofType:` (`renamesContradictingOwnProperties`: the rename refers to that property, so `ofType:` must name its type exactly, optionality included, or a `LazilyInstantiated` property's instance type; recorded in the hidden-label walk and thrown before unfulfillable and hidden properties, which it explains, and checked again in `validateChildrenDoNotRequireEachOther` for the trees of dependencies a mock promotes, which that walk does not reach; both declarations are on one type, but the check stays in the plugin by ruling), dependency cycles, a `@Sendable` builder function that would capture an `Instantiator`, `ErasedInstantiator`, or `LazilyInstantiated` declared outside it (`ScopeGenerator.nonSendableWrapperCaptures`, which walks the generator trees as code generation does, so a dependency passed `nil` is not reported; a receiver is reported once for each chain that reaches it, so the root a diagnostic names never depends on name order), duplicate type declarations, duplicate mock providers, a `mockOnly` hand-written `mock` on a type whose `mock()` is generated, an `additionalMocksToGenerate` entry of the selected configuration that names no `@Instantiable` type (`SafeDIConfiguration.validateAdditionalMocksToGenerate`, judged against the concrete types mock generation matches entries to, unioned with the `ModuleInfo.instantiableTypeNamesInAnyClause` of this module and its dependent modules, so an entry naming a type declared only in an inactive clause is accepted and its file written without code, as "Conditional compilation" describes; entries of configurations in inactive clauses are planned by `scan` and written without code, never judged).

### Serialization

`scan`'s cache (`<manifest>.safediScanCache`, a `CachedScannedModuleInfo`) and `.safedi` module info files (a `ModuleInfo`) are written in SafeDITool's own binary format, by hand rather than through `Codable` (`BinaryCoding.swift`, `BinaryCodableModels.swift`, `BinaryFile.swift`, all in `SafeDITool`, never `SafeDICore`). These files are **regenerated every build** — there is no cross-version deserialization. Do not add backward-compatibility decoding logic. A header (magic, format version, schema fingerprint, body length, checksum) rejects any other file: an unreadable scan cache is a cache miss and a fresh parse, and an unreadable `.safedi` is an error naming the file. `BinaryFile.schemaDescription` and `BinaryLayout.description` spell every stored type and field type with `String(reflecting:)`, so the module names `SafeDITool` and `SafeDICore` are part of `schemaFingerprint`: every build of the tool must name its modules that way (the SwiftPM targets, the prebuilt binaries, and `module_name` on the Bazel `swift_binary` and `swift_library`), or its `.safedi` files are unreadable to the others, and no test catches it, because `swift test` cannot see a Bazel build. The plugin-read `SafeDIToolManifest` stays JSON.

When a stored type changes, keep its coder in step:
- Each `BinarySchemaMember` writes its fields in initializer order and reads them back through that initializer, with each field's type choosing how it is read. A field whose type is not `BinaryCodable` fails to compile; so does an enum case the writer's exhaustive `switch` does not handle, and a tag the reader's `switch` does not handle.
- `binaryLayout` is what `BinaryFile.schemaFingerprint` covers: for a struct, each field it writes, in write order, as a `BinaryLayoutField` whose key path fixes the field's type, plus `unwrittenProperties`, the stored properties not written under their own name (`Dependency.asInstantiatedType`, `UnorderedEquatingCollection.set`, `Instantiable.instantiableTypes`, written as `concreteInstantiable` and `additionalInstantiables`, and `Property`'s stored hash, which is never written because hashing is seeded per process: a decoded `Property` goes through `Property.init(label:typeDescription:)`, which computes it again); for an enum, each tag's associated values, in declaration order, which is also the order written and read. A file written by a SafeDITool whose types write other fields, fields of other types, or the same fields in another order is therefore never read. `SafeDIToolBinaryFileTests` compares each struct's layout against `Mirror`, so a new stored property fails until it is listed, written, and read, and writes each field and associated value in turn with a value distinct from the rest (`BinarySample`), so a layout whose order or types differ from what the coder writes and reads fails too. A new stored type must join `BinaryFile.schemaMembers` and conform to `BinarySample` in the tests.
- A `BinaryReader` reads type descriptions nested at most `BinaryReader.maximumNestingDepth` (128) deep, so the writer notes a deeper one and `BinaryFile` refuses to write a file that holds it, naming the instantiable whose declaration names it (`BinaryFileWriteError`): `scan` then writes no cache, and `generate` fails rather than write a `.safedi` dependents cannot read. Do not describe the deep type itself in such an error: spelling a type recurses as deeply as it nests, which exhausts a task's stack in a debug build.
- `executeSafeDIToolTest` checks, for every fixture that runs scan, that the cache reads back exactly what scan wrote (`reflectedDescription`, which sees private fields and spellings `==` ignores, and compares strings by their UTF-8 bytes, because `String`'s `==` calls canonically equivalent spellings equal while Swift compares identifiers byte for byte; the writer's string table keys strings by those bytes for the same reason), so a field the coder drops fails whichever tests give it a value.
- `Codable` conformances stay: the `dump` subcommand prints either file as JSON through them.

## Determinism

Everything SafeDI produces must be identical on every run over the same inputs: generated code, diagnostics (their text, their order, and which one is reported first), fix-its, output file names, and the bytes of manifests, `.safedi` files and caches.

- Swift seeds hashing per process, and `Scope` hashes by object identity, so the order of a `Set` or `Dictionary` changes between runs — for scopes, even under a fixed hash seed. A task group's results arrive in completion order. None of these orders may reach output.
- When code chooses among candidates or emits a list, use declaration order, source path order, or a sorted order. Never use first-found or last-write-wins over an unordered collection.
- When a choice is genuinely ambiguous, report an error or apply a stated tie-break. Do not pick silently.
- Sorting only on the failure path is fine, and keeps the success path cheap: visit everything, and keep the candidate that sorts first only when there is something to report.
- A test of choice-making code needs enough candidates that a wrong order fails on nearly every run: twenty or more, or a permutation of six. A fixture with one candidate cannot catch this class of bug.

## Code Style

- **No abbreviations.** Use `dependency` not `dep`, `parameter` not `param`, `declaration` not `decl`. Everywhere: variables, functions, tests, comments, commits.
- **No `default` or `case _` in switch statements when all cases are knowable.** Enumerate all cases explicitly for compile-time safety.
- **Use `for ... where` for simple boolean filters** instead of `guard ... else { continue }` inside the loop body.
- **Use `guard` for early exits**, not `if condition { continue/return }`.
- **No early return from bare `if`.** If an `if` branch returns, the non-returning path must be in an explicit `else` clause. Never fall through after `if { return }`.
- **Test names follow `method_expectation_conditionUnderTest`** pattern (e.g., `mock_disambiguatesAllParameters_whenThreeChildrenShareSameLabel`).

## Testing Philosophy

- **TDD**: Write failing tests first, then fix.
- **One behavior per test method.** Each test verifies one behavior, but may use multiple assertions to fully validate it (e.g., checking both the count and content of output). Do not test unrelated behaviors in the same method.
- **No tautological tests.** Tests must exercise real code paths with real input. Never use test helpers that rewrite input before processing — the test content should be exactly what production code would see. Tests should verify input code → output code.
- **Test through the pipeline**, not direct model construction. Mock tests use `executeSafeDIToolTest` which parses real Swift source through the full visitor → generator pipeline.
- **Full `==` output comparison.** Never use `.contains()` for mock output. Compare the complete expected string.
- **Verify updated test expectations compile.** When updating expected output in generator tests, review the new expected code to confirm it would compile as valid Swift. Check that variable references resolve to the correct scope, types match (no optional where non-optional expected), and all referenced variables have bindings. Do not blindly update expected output to match actual — the actual output may itself be buggy.
- **Code generation tests should only test paths where the macro would not emit an error.** Test inputs must be valid under `@Instantiable` macro validation — every `mockOnly: true` type needs a `mock()` method (or `customMockName` method), mock method names on the same type must not collide (and a `mockOnly` mock paired with a generated mock must use `customMockName`, or generation errors), and production types need `init` or `instantiate()`.
- **Test titles must be observably verified.** When a test title says "prefers X over Y", the assertion must verify X is used — not just that the test doesn't crash. Add a parent type with `generateMock: true` that instantiates the type under test, and assert the full mock output shows X's method name.
- **If code can't be covered by a test with real parsed input, remove the code.** Dead branches and defensive fallbacks for structurally unreachable paths should not exist.
- **"Structurally unreachable" claims need a failing test.** Before removing defensive branches on the grounds that they can't be reached, write a test that tries to reach them with valid input. If the test can't be written, cite the specific rejection (file:line) and the input shape it rejects — a structural argument alone is not evidence. Structural arguments are easy to get wrong: e.g., `erasedToConcreteExistential: true` does NOT imply a constant property type, so "erased + cycle is rejected as constant" was wrong and cost a round trip when the branches had to be restored.
- **Test fixture file naming controls processing order.** Files parse in parallel, so completion order is random; `ModuleInfo(_:)` therefore orders a module's file scans by path, so its instantiables are in source file path order, keeping each file's top-to-bottom declaration order, and its imports and mock imports are sorted and deduplicated, so the `.safedi` file `generate` writes is the same bytes every run; upstream `.safedi` module info is already in that order, and `loadSafeDIModuleInfo` returns the dependent modules in the path order of their `.safedi` files, whatever order the caller lists them in or the parallel reads finish in, so the combined list `resolveSafeDIFulfilledTypes` sees is deterministic without a second sort. `executeSafeDIToolTest` names fixture files by extracting the type name from `@Instantiable` in the source content, so those names decide the order. When testing ordering-sensitive behavior (e.g., which of the two mockOnly merge branches runs), pick names that sort the way you need, and be aware that an `extension MyService` file falls back to `"File"`. A configuration-only snippet also falls back to `File.swift`, so it exercises `parseModule`'s fallback path; pass `swiftFileContentByFilePath` (e.g. `["SafeDIConfiguration.swift": …]`) to name a fixture explicitly when the file name matters.
- **Tests must not depend on where the checkout lives.** The suite runs from checkouts under `/Users`, under `/tmp` (reached as `/private/tmp`), and through other symbolic links. Build an expected path by the rule the contract under "File path spelling" gives its consumer — for example the project root as the test handed it to `scan`, made absolute, joined with the file's path inside it, for `additionalInputFiles` — never from `currentDirectoryPath` or `NSTemporaryDirectory()` compared with a normalized path, and test a symbolic link by creating one, as `SafeDIToolPathSpellingTests` does.

## Graph fuzzer

`SafeDIToolGraphFuzzerTests` (support code in `Tests/SafeDIToolTests/Helpers/GraphFuzzer.swift`) generates random graphs of `final class` `@Instantiable` types from a seed (a quarter of them also with one extension-based type whose `instantiate(…)` has default-valued parameters, decided after the rest of the graph so the other types of a seed's graph do not depend on it), with its own SplitMix64 generator so a seed names the same graph on every machine. The oracle runs each graph through `executeSafeDIToolTest` twice in the test process and accepts only two outcomes: the tool reports an error, or the fixture and the generated code compile (`swiftc -emit-object`, as `verifyGeneratedCodeCompiles` does). Generated code that does not compile, a fixture that does not compile on its own (a fuzzer defect), and two runs that differ are failures; a crash kills the test process. The two runs share the process's hash seed, so the long run also runs the `SafeDITool` executable in two processes for every 50th seed and compares them. The oracle also runs each graph under every `GraphFuzzerRenaming` – reversing the order of its type names, of its labels, of its file names, and of all three at once, each a pure rename of single-digit indices (`i` to `9 - i`, files prefixed `F<99 - rank>_`) – and requires, once the renaming is undone textually, the same verdict, the same diagnostics in any order, and byte-identical generated files (`renamedGraphDiffers`). It compares the suggestions a diagnostic lists ("Did you mean one of …") in any order too: the order inside a message is presentation and changes nothing a user does. It catches output that depends on which of several equals SafeDI meets first in name order, which two identical runs cannot see. The reversals keep every type name's `S<seed>_` prefix, which sorts after `ErasedInstantiator<`, `Instantiator<`, and `LazilyInstantiated<` and before the `Sendable` wrappers (a digit sorts before `e`), so no reversal changes whether `x: X` or `x: Instantiator<X>` sorts first. A fifth renaming therefore moves type names across wrapper names (`movesTypeNamesAcrossWrapperNames`): it replaces the prefix's `S` with `A`, which sorts before every wrapper's name, or `Z`, which sorts after every one, chosen per seed by each name's kind and index (`T3`, `AnyT3`, `Value`; a type and its `Protocol` move together), wherever the name appears. A quarter of graphs end with a motif drawn after the graph's own types and before the extension-based type (types 7 to 9, so other graphs draw as before) whose output SafeDI must choose for: a lazy cycle of mocked types, promoted siblings that receive each other only if available, one label received as an instance and as an instantiator, several independently invalid roots, or two types in two files that fulfill one protocol. The four reversals cost about 60% more corpus time, and the move is one more run of the tool per graph. Graphs compile together in one `swiftc` invocation, kept apart by a per-seed type-name prefix (`S<seed>_`). A graph's wrappers are all `Sendable`, all not, or – in a quarter of graphs – mixed at random, so a `Sendable` builder's subtree can receive a `LazilyInstantiated` declared outside it; a mixed graph's types are `@unchecked Sendable`, and its types that are not `@Instantiable` (the extended type among them) are `Sendable`, so receiving one by value inside a `@Sendable` builder function is never what fails. The oracle compiles in the Swift 6 language mode, where such a capture is an error rather than a warning. A type no root reaches sometimes receives `items` as a wrapper of the graph's `Value` type, which is not `@Instantiable` and which nothing provides, with the wrapper chosen for each receive, so a mock's tree receives one label as several wrappers its mock cannot build. A type no root reaches also sometimes instantiates a constant of a type that is not `@Instantiable` (`addingDependenciesMocksCannotBuild`), which its mock takes as a parameter, and a pass drawn after every other one, with its own generator (`addingReceiversOfDependenciesMocksCannotBuild`), now and then gives a type built beneath that owner – one it instantiates, or now and then one that type instantiates – a receive of the constant, required or only if available, which the mock must pass that same parameter (`dependencyMockCannotBuildReceivedBeneathItsOwner`). With a generator of its own, the pass also now and then makes an owner with `generateMock: true` receive a type of the graph that receives the constant by value or as its `LazilyInstantiated` or `SendableLazilyInstantiated`, required or only if available; a mocked owner's mock builds that type beside it and must wrap the parameter it takes rather than take the wrapper (`dependencyMockCannotBuildReceivedLazilyBesideItsMockedOwner`). In a mixed graph the owner now and then lazily instantiates the constant as one wrapper while that type receives the other kind, which the mock must make from an instance it takes (`dependencyMockCannotBuildLazilyInstantiatedReceivedAsOtherKindBesideItsMockedOwner`), and now and then the type instead instantiates a type of the graph under the constant's label above a receiver of the constant, which the tool must reject as hidden. The oracle checks that rule in every accepted graph: a generated `mock()` takes a `LazilyInstantiated` or `SendableLazilyInstantiated` parameter only for a property the mocked type forwards or instantiates (`mockTakesWrapperParameterForReceive`). Types also receive the erased instantiators an ancestor instantiates, with exactly the type it declares, and some forward one. A tenth of graphs end with a chain of aliases through an `onlyIfAvailable` alias (`addingAliasChains`, a pass with its own generator, so every other graph is drawn as before): a second alias, required or `onlyIfAvailable`, of an `onlyIfAvailable` alias a type declares or is given, on that type or on one it instantiates, now and then a third, and usually a receive of the last on a type beneath it. The second pass never aliases an optional property, so no other graph has such a chain unless `addingSiblingAliasChains`, below, draws one; a receiver that requires the last alias needs every alias created, so the first alias's fulfilling property must be built before it, which the rest of the graph can make a cycle (`aliasOfOnlyIfAvailableAlias`). That pass draws the first alias's source from the properties provided above every path to its host, never one built around it, so it never draws the sibling cycle PRs 472 and 481 fixed. A last pass with its own generator (`addingSiblingAliasChains`, three rolls in ten, about 170 corpus graphs) draws that cycle: a scope – a root, or a type on every path to the chain – instantiates `x: X` as a constant and another type `B` without an instantiator; `B`, or a type a few such steps beneath it that each step dominates, declares an `onlyIfAvailable` alias of `x`, mostly spelled with its optional form (`ofType: X?.self`, `aliasOfOptionalFormOfProperty`); now and then one or two aliases of that alias follow, required or `onlyIfAvailable`, on the same type or on a type beneath it, so that the chain crosses scopes; usually a type beneath the last alias's type receives it, mostly required, or a required alias of it on the same type does instead; and usually `X` receives `b`, so that `b` must be built before `x` while the chain needs `x` first, which the tool must reject through the chain (`fixture_makesSiblingsTypeReceiveTheOtherSibling_forSeed4224`). A type beneath another is a child it dominates, judged from the declarations rather than from `dominators` (a root now and then declares a property the other roots lack, which the graph's edges do not hold), or, where it has none, which is most often, a new type only it instantiates (`Link0`, `Link1`, …), so a receiver is not rejected merely because another path from a root reaches it without the alias. Without the receive of `b`, the chain must be built after `x`, which the compiled output shows (seeds 731 and 2420, in the smoke batch; 2420's chain passes through a child scope).

- **Every pull request.** `ci.yml` fuzzes the whole corpus, seeds `0..<corpusSeedCount`, on every pull request and push to main that changes more than Markdown. "Build and Test on Linux" packages its test bundle; "Fuzz Dependency Graphs on Linux" shards download it and run the long run over parts of the corpus, with batches running concurrently on every core; and "Check Graph Fuzzer Corpus on Linux" combines the shards' reports. A shard fails, naming the seeds in its summary, when a graph fails, a known issue goes stale, the run reports a problem with itself (a changed corpus, an invalid known-issue list, a harness error), the process crashes, or no graph runs. The combine job fails when a shard is missing or reported any of those, when the shards do not cover the corpus exactly once, or when the seeds the tool accepted differ from the pins (`corpusAcceptedSeedCount`, and `corpusAcceptedSeedsSum`, a `GraphFuzzerSeedSetSum` whose parts add up across shards). The oracle takes any error the tool reports as a valid rejection, so a tool change that makes it accept or reject other graphs must update those pins deliberately. The fixed seeds make every failure deterministic, so it belongs to the change that caused it. Measured: the shards add about 3¼ minutes after "Build and Test on Linux", cold or warm, since they run its bundle instead of building; each fuzzes 2500 seeds in about 2¼ minutes, before the multi-module property, which adds about a quarter.
- **Ordinary suite.** Compiling generated code is what the fuzzer costs, so the ordinary suite keeps it to five small `swiftc` invocations (the smoke batch, the three of `compilationFailures_reportEachBrokenGraph…`, and the one-type probe of `results_reportIntegrationsDiffer…`) and is what `swift test` gives a developer locally. A small fixed batch (`smokeSeeds`, ten seeds) must have no failures, exercise every `GraphFuzzerFeature` (detected from the emitted source) in graphs the tool accepts, and include both accepted and rejected graphs. `compilationFailures_reportEachBrokenGraph_whenGeneratedCodeFailsToTypeCheckOrToLower` hands the oracle broken generated code. `fixture_matchesReferenceHash_forSmokeAndKnownIssueSeeds` pins the generator's output for those seeds, and the long run pins it for the whole corpus (`corpusFixtureHash`). Any generator change changes which graph every seed names, so update all four hashes (the fixture and partition hashes of the smoke and known-issue seeds and of the corpus), the accepted-seed pins, and the smoke and known-issue seeds in the same change.
- **Multi-module partition.** The oracle also runs every graph split across modules through both multi-module integrations of `executeSafeDIToolMultiModuleTest`, `.moduleInfo` (Bazel's flow: `generate --combined-output --module-info-output --compiler-receives-input-paths-unchanged` per module, reading the listed dependencies' `.safedi`; Tuist's differs only by omitting that flag) and `.swiftPackagePlugin` (the SwiftPM plugin's: one CSV per module holding its files and its transitive dependencies' files, the module's own mock-scoped, `scan` while planning and then `generate` with the manifest, one file per root and per mock), without compiling, and requires the same results (`integrationsDiffer`). `GraphFuzzerPartition` (`Tests/SafeDIToolTests/Helpers/GraphFuzzerMultiModule.swift`) is a pure function of the graph – it draws nothing from the seed, so `corpusFixtureHash` and the accepted-seed pins are unchanged by it, and `smokeAndKnownIssuePartitionHash` and `corpusPartitionHash` pin the partition itself, so a change to it is deliberate (they move with the generator and the known-issue list as well, as the fixture hashes do). The partition projects the fixture's files first (`projectedFiles(of:)`): the helper types `Value` and `Unbuildable<n>`, which the generator declares in `Root0`'s file, move into a file of their own (`S<seed>_Helpers.swift`, named explicitly), since left there every type naming them would be pulled into `Root0`'s component and a root would never be split from a type of its tree that forwards or receives them. Each file refers to the types it names (instantiated, received, forwarded, aliased, erased to, named by `fulfilledByType:`, the graph's `Value` and protocol types, the extended class), each name is declared in one file, and Tarjan's algorithm over that reference graph, visiting files in order, lists each strongly connected component after every component it refers to (a lazy cycle through instantiators is one component, so its types share a module; a root's component follows those of the types its tree names; the roots are the first files, so the types no root reaches are visited after them and their components follow the roots', and a root need not be in the last module). The components are dealt out, contiguously in that order, to `Alpha`, `Beta`, `Gamma`, `Delta` – as many as `GraphFuzzerHash` of the fixture's text chooses, one to four, so single-module graphs stay in the corpus (1313, 1240, 1229 and 1218 of the 5000 graphs get one to four) – so every reference points into the same or an earlier module. The two integrations combine declarations in different orders: `generate` lists the dependencies' `.safedi` files, read in path order, before the module's own declarations, while the plugin parses every module's files in path order (`Sources/<Module>/…`), the module's own among them; `Delta` sorts before `Gamma`, so in every four-module graph the plugin combines `Delta`'s own declarations before `Gamma`'s where the module-info integration combines them after – kept deliberately, since a real package's module directories sort arbitrarily against a Bazel build's `.safedi` paths, so a quarter of the corpus checks that nothing SafeDI generates or reports depends on that order (the corpus passing with it is the evidence). A module's `dependencies` are every module whose declarations its `generate` must read, the modules its files refer to and, through them, theirs: what a Bazel user lists in `safedi_compile`'s `deps`, since a `.safedi` holds only its own module's declarations, so a tree reaching a declaration two modules down needs that module listed (`multiModuleTest_throwsErrorForGrandparentDeclaration_whenModuleInfoListsOnlyTheDirectDependency`); the plugin lists the transitive closure's files itself, so both integrations read the same declarations. Every file keeps its name and content, with an `import` line per module it refers to before it, and the module and package names hold no digit, so the renamings leave them alone. The property compares module by module in dependency order (`GraphFuzzerMultiModuleOutcome.difference`): a module both generate must have the same generated units, each byte for byte, the combined file's imports in every one of the plugin's files (the plugin's dependency-tree and mock files import what each kind needs, which differs only through `#if`-guarded imports, which no fuzzer graph has), and the same warnings; a module the module-info integration rejects must be rejected with the same diagnostics, in any order, by the plugin. A unit is one generated extension, keyed as the plugin names the file it writes (`<Type>+SafeDI.swift`, `<Type>+SafeDIMock.swift`, `<Type>+SafeDIMockConfiguration.swift` for a `SafeDIMockConfiguration` struct wherever the plugin places it), with the `#if` the mock condition wraps it in, and with every path under the fixture root reduced to `<fixture-directory>/…` (`GraphFuzzerGeneratedModule`): the combined file's joined bodies and the plugin's per-file outputs reduce to the same units, and a `#sourceLocation` directive differs between the integrations only in the fixture root's spelling (the plugin's resolved root against the CSV's path under `--compiler-receives-input-paths-unchanged`). Two differences are the integrations' own and are normalized rather than reported: the plugin's `scan` plans a dependency-tree file for every root in its CSV, so a consumer writes each dependency's root again, which must read exactly as the declaring module's own and is then left out; and the plugin adds a build command only for a module whose manifest plans an output, so a module runs `generate` under it only when its own files declare a mock, or its own or its dependencies' files declare a root (`scan` plans every root in the CSV), and a defect its declarations alone reveal (two types fulfilling one protocol, seed 20) is reported where the first module that depends on it generates, or nowhere – the property expects those diagnostics there, requires that the module-info integration generated nothing for a module the plugin skips, and takes an unreported defect as the plugin's design; when the plugin first rejects a module that does not depend on the skipped one, nothing is compared, because `.moduleInfo` stopped at the skipped module and never ran that one. The roots the plugin writes again are `GraphFuzzerRegeneratedRoot`s (`GraphFuzzerMultiModuleProperty.removingRegeneratedRoots`, which removes only a root whose declaring module the consumer depends on). It runs in the smoke batch, which must split graphs into one, two, and three or more modules and reject some split ones, and over the corpus in the long run, whose report counts the graphs at each module count (`partitions`) and notes each differing graph (`multimodule`). Measured: the plain run adds about a quarter of the long run's CPU time (500 seeds: 290 s to 359 s of CPU), so only the graph as generated is split (`GraphFuzzerOracle.multiModuleRenamings`): each of the five renamings would add as much again.
- **Run a seed.** `SAFEDI_GRAPH_FUZZER_STARTING_SEED=<seed> SAFEDI_GRAPH_FUZZER_ITERATIONS=<count> swift test --traits sourceBuild --filter SafeDIToolGraphFuzzerTests/longRun`, or `SAFEDI_GRAPH_FUZZER_ITERATIONS=corpus` for the whole corpus, which then checks the accepted-seed pins itself. Each failure's issue prints the fixture and the compiler output. `SAFEDI_GRAPH_FUZZER_REPORT=<path>` appends progress to a file. The run also checks that no corpus graph uses a label beginning with `__safeDI_`, the prefix of generated builder functions. To explore graphs beyond the corpus, dispatch `.github/workflows/graph-fuzzer.yml` with another starting seed and count.
- **Known issues.** `knownIssues` lists every corpus seed that fails today, grouped by shape. The corpus first found six shapes, and PR 404 made the tool reject one while PRs 407 and 408 fixed the generated code of the rest. Graphs mixing `Sendable` and non-`Sendable` wrappers found two shapes, both resolved: a type below a `Sendable` builder that receives an `Instantiator` declared outside it, which the tool now rejects as it rejects a captured `LazilyInstantiated`, and a cycle through a `Sendable` builder and an `Instantiator`, whose cycle-closing scope referred to the enclosing builder function that was not `@Sendable` (see `buildsInSendableFunction`). Receiving `items` as several wrappers found two mock shapes, both fixed: a mock wrapped the instance it takes for a required `LazilyInstantiated<Value>?` by its bare label when an `Instantiator<Value>` receive of the label renamed that parameter, and a mock that promotes a received `Instantiator<A>?` read it, still being declared, through an `onlyIfAvailable` alias of `Instantiator<A>` in its own tree. Receives beside a mocked owner of a dependency its mock cannot build found two more, both open and listed: a type that receives a label as one type above a type that receives it as another, where the mock rebinds the first under the label inside the first type's builder function, and a required receive in the tree of a dependency the mock promotes that is handed the mocked type's optional `onlyIfAvailable` alias of the property. It lists the graphs whose output changes under a renaming, grouped by what changes (mock code, the mock configuration file). The mechanism's tests use known issues of their own, so they do not depend on the list. Each shape has a one-line reason and its signatures, the ways it is known to fail: compiler errors containing a given text, or a compiler crash in a generated mock (Swift 6.2 crashed on a mock shape that Swift 6.4 diagnosed). In the long run, a known seed that fails with one of its shape's signatures runs inside `withKnownIssue`; one that no longer fails is reported as stale, and one that fails any other way is reported as a new failure, so a fix's own pull request shows the entries it makes stale. Each seed is listed once, in increasing order within its shape, below `corpusSeedCount`, which `knownIssues_listEachSeedOnceInIncreasingOrder_belowCorpusSeedCount` checks. To add one, add the seed to its shape's list, or add a shape. Every failure the fuzzer finds becomes a hand-written regression test (reduced to the types that matter, with full `==` output) before its fix, and removing the entry is the last step of the fix.

## Common Pitfalls

- The input CSV written by plugins includes ALL swift files (target + dependencies). Mock scoping requires passing `mockScopedSwiftFiles` separately — only the target's own files.
- **Names generated code introduces are reserved** (`ReservedName`, the one place they are spelled: `ScopeGenerator` emits them from its constants, and the macro checks against them). Generated bodies declare builder functions `__safeDI_<label>` (and `@Sendable`-extracted locals `__safeDI_<label>__…`) next to the `let <label>` they build; the prefix keeps them out of the namespace of user labels, and it stays: any other scheme is more collision-prone and rewrites every generated file. Three kinds of exact name are reserved too, because generated code puts them in a scope with user names and cannot rename them: `safeDIOverrides` (the `mock()` parameter callers spell, which a mock parameter of that label redeclares and a body binding hides), `safeDIBuilder` (the property and initializer parameter of every `SafeDIMockConfiguration`, which a configured type's instantiated or default-parameter label redeclares, and the `if let safeDIBuilder` override binding in each construction expression, which therefore never shadows an argument), and the wrapper types generated code constructs by name (`Instantiator<T>(…)` and the other five, `Property.PropertyType.wrapperTypeName`), which a binding of that name hides. The macro tests pin that each is rejected; the evidence that each collides is in PR 410's description, because a fixture that declares one is macro-invalid and so cannot be a pipeline test. `SafeDIToolReservedNameTests` shows, with macro-valid fixtures, that the other names generated code introduces do not collide, which is what stops anyone reserving more than is needed: the `instance` closure parameter, and the generated members `SafeDIOverrides`, `SafeDIMockConfiguration`, `ForwardedProperties`, and `mock`, which a same-named property does not redeclare and which generated code never names where a binding could hide them. A new generated identifier in a scope with user names must be added to `ReservedName`, with such a test. The `@Instantiable` macro rejects every name it can see that generated code binds or refers to: property labels and `fulfilledByDependencyNamed:` names (`InstantiableVisitor`), the names of `instantiate(…)` parameters without a default value (also the visitor), and the argument labels of labeled, default-valued, non-dependency parameters of the construction initializer, `instantiate(…)` methods, and mock methods, which a mock root takes as `mock()` parameters (`validateReservedParameterLabels`, the same parameters `validateDefaultExpressions` checks). The property macros do not check, so nothing is reported twice. Only a prefixed parameter label gets a fix-it (rename the argument label to the label without the prefix, keep the parameter's name): renaming a dependency can change which dependency it fulfills or receives, because SafeDI matches by label, with no error, and an exactly reserved label has no evident replacement. `generate` does not check: SafeDI is upgraded per project at once, so every module's names have passed the macro.
- **Nested-type qualification.** `generate` qualifies each dependency's property type, `fulfilledByType:` type, and alias `ofType:` type with `TypeDescription.qualifyingInstantiatedType(within:amongInstantiableTypes:)`, and maps the initializer's arguments by the qualified property types. It qualifies only the type `asInstantiatedType` returns (`Instantiator<Service>?` → `Instantiator<Feature.Service>?`, `LazilyInstantiated<any Service>` → `LazilyInstantiated<any Feature.Service>`, so a by-value receiver of `any Service`, qualified the same way, still matches `lazilyInstantiatedInstanceType`), choosing the most qualified of `nestedOptions` that an `@Instantiable` fulfills, so a nested type wins over a top-level type of the same name, as the compiler resolves it. It also qualifies a hand-written mock's return type (`mockReturnType`, which the macro requires to be `Self` or the declaration's unqualified name, so a nested type's mock returns `Consumer`, not `Feature.Consumer`) and each of its arguments' types (`mockInitializer`), each type by itself rather than through the dependency map, because a `mockOnly` declaration has no dependencies and its mock is matched to those of the declaration it merges into. Doing it while normalizing, before `resolveSafeDIFulfilledTypes`, keeps `mockInitializer`, `mockReturnType` and `mockDeclarationLocation` together through both mockOnly merge branches. Unqualified, `mockReturnTypeIsCompatible` fails against `Feature.Consumer`, and the hand-written mock is silently skipped. Other generic arguments (an `ErasedInstantiator`'s forwarded properties) and non-instantiable types are not qualified. `replacingInstantiatedType` walks the same path through a type as `asInstantiatedType`: both read `TypeDescription.builtGeneric`, which names the built generic of each wrapper and whether its own instantiated type is read through it (`LazilyInstantiated`, whose generic may be `any Service`), so a new wrapper type is added there once.
- **No synchronous recursion per level of a tree.** A dependency tree, a chain of received dependencies, a chain of siblings that require one another, and a mock parameter tree can each be as deep as the module has types, while `generate` and the tests run on concurrency threads, whose stack is half a megabyte on Apple platforms (a debug frame of the old instantiation walk took 40 KB, so a chain of 13 overflowed). Walk them with an explicit stack that keeps the recursive visiting order, so every diagnostic and memo is unchanged (the walks of `DependencyTreeGenerator`, `Scope.createScopeGenerator`, `ScopeGenerator.orderedPropertyToGenerateIndices`), or recurse through `async` functions, whose frames the task allocates (`ScopeGenerator`'s tree walks, the mock emitter `generateMockBodyBindings`, and the mock tree walks). An object that owns the next level of a tree hands what it owns to `DeferredRelease` in its `deinit` (`Scope`, `ScopeGenerator`, `MockTreeItems`); a new owning link needs the same, or releasing a deep tree nests a deinitializer per level. `SafeDIToolDeepTreeTests` builds chains deeper than any recursion could go.
- `Property.<` sort uses type as tiebreaker (not just label) for stable ordering.
- Extension-based `@Instantiable` types use `static func instantiate(...)` instead of `init(...)`. Their `@Instantiated` dependencies are constructed by the parent scope. Each `instantiate` parameter without a default value is a `@Received` dependency (`InstantiableVisitor`); a default-valued one is not a dependency, exactly as a default-valued non-dependency `init` parameter: the production call leaves it out, a generated mock offers it as an override, and the macro gives `instantiate` the checks an initializer's default-valued parameters get (`InstantiableVisitor.instantiateFunctions`).
- When a received dependency is promoted to root scope, the producer branch must capture the root-bound value — not reconstruct the type.
- `collectReceivedProperties` returns as `onlyIfAvailable` only properties that every receiver receives only if available. A property one receiver requires and another receives `onlyIfAvailable` is required — the collision is real, because an `onlyIfAvailable` alias's fulfilling property is non-optional (`@Received(fulfilledByDependencyNamed: "x", ofType: X.self, onlyIfAvailable: true)` yields `x: X`). Treating such a property as only-if-available skips its promotion, and the required receiver is handed `X?`. `createMockRootScopeGenerator` applies the same rule across the root's tree and the promoted scopes' trees, and `ScopeGenerator.onlyIfAvailableUnwrappedReceivedProperties` applies it to each subtree, so sibling ordering and mock parameters agree with promotion.
- A received constant whose type has `@Forwarded` properties is never promoted (`mockCanBuild`): the mock has no values to forward, so the dependency stays received and `mock()` takes it as a flat parameter, as production never `@Instantiated`s such a constant. The promotion loop and the worklist that collects promoted scopes' received properties both apply the check; a worklist that walked an unpromoted scope would promote its received dependencies into unused `SafeDIOverrides` entries.
- The mock root's own aliases are bound in the mock body's top-level scope, next to the dependencies promoted to the root and the `onlyIfAvailable` override bindings — production never puts them together, because it builds a type's aliases inside the scope that builds the type. `renamingAliases` binds an alias whose label one of those top-level bindings already uses as `<label>_<simplified type's asIdentifier>`, and the rename joins the tree's disambiguation map (receivers rebind it to the label) and the return-argument map. Only a binding redeclares: an alias whose label matches a flat parameter shadows it legally and keeps its name.

- **`TypeDescription ==`/`hash` ignore `any` at every depth.** `any P` equals `P`, `(any P)?` equals `P?`, `Instantiator<any P>` equals `Instantiator<P>`, and `(any P).Type` is treated as `P.Protocol` (not `P.Type`, which is `any P.Type`). `some P` stays distinct. Sets and dictionaries keyed by `TypeDescription` or `Property` therefore merge the two spellings, keeping whichever was inserted first, while `asSource`/`asIdentifier` keep each declaration's own spelling. `<` compares the spelling without `any` first, then the full spelling as a deterministic tiebreak, so two spellings of one type are equal under `==` but ordered under `<` (determinism was chosen over the Comparable contract). Any new map or set keyed by a type's spelling string (`asSource`) instead of `TypeDescription` must normalize `any` the same way, or it will miss matches `==` makes.
- **Diagnostics are chosen by source location, never by name order.** Every root (production, `generateMock` type, mock root, mock root's child trees) reports the first error its own walk finds, and `DependencyTreeGeneratorError.reportingAll(of:)` joins them in source order (`SourceDiagnostic.joiningInSourceOrder`), so renaming a type never changes which error appears or where. Two rules keep that true: a memo shared across roots (`ChildrenRequiringEachOtherValidation.validatedScopes`, `walkedAliasFulfillingProperties`) keeps only walks that completed — an entry from a walk that threw must be dropped, or a later root would skip the work and the reported set would depend on root order; and where one of several candidates must be picked (which promoted child a mock root validates first, which received property names a sibling, which reader a warning names), pick by declaration location or declaration order (`inOrderTheMockTreeFirstReceives` orders a mock root's promoted children by where its tree first receives them, for generation and validation alike), not by label or type-name order. The rename-invariance fuzzer oracle (#464) checks this class end to end.
- **`erasedToConcreteExistential: true` is orthogonal to the property's `PropertyType`.** The flag controls whether SafeDI wraps the concrete in the property's existential type at the call site; it does not determine whether the property itself is constant or lazy. The four combinations:

  | Decorator + property | `Property.PropertyType` | `isConstant` | Can be in an accepted cycle? |
  |----------------------|-------------------------|--------------|------------------------------|
  | `@Instantiated let x: Concrete` | `.constant` | `true` | No — `throwIfInvalidCycle` rejects. |
  | `@Instantiated let x: Instantiator<T>` | `.instantiator` | `false` | Yes. |
  | `@Instantiated(erasedToConcreteExistential: true) let x: AnyProto` | `.constant` | `true` | No — `throwIfInvalidCycle` rejects. |
  | `@Instantiated(erasedToConcreteExistential: true) let x: ErasedInstantiator<A, AnyP>` | `.erasedInstantiator` | `false` | Yes. |

  When reasoning about whether an erased node can appear on a pruned back-edge, check `propertyType.isConstant` — don't short-circuit on the erasure flag.
