# SafeDI — Claude Code Guidelines

## Documentation

The core documentation is `Documentation/Manual.md`. Read it before making changes to understand SafeDI's API, macros, configuration options, and mock generation. The manual is the source of truth for user-facing behavior — if you change behavior, update the manual.

## Build & Test

```bash
swift build --traits sourceBuild   # Build all targets
swift test --traits sourceBuild    # Run all tests
./CLI/lint.sh                      # SwiftFormat — must pass before every push
swift test --traits sourceBuild --enable-code-coverage  # Coverage report
```

The `sourceBuild` trait is required for local development to compile SafeDITool from source. Without it, the plugin uses the prebuilt binary from the artifact bundle.

Always lint before pushing. Always run the full test suite after changes — don't rely on filtered runs alone.

## Architecture

SafeDI is a compile-time dependency injection framework for Swift. It uses Swift macros (`@Instantiable`, `@Instantiated`, `@Received`, `@Forwarded`) to declare dependency graphs, then generates initializer code and mock methods via a build tool plugin.

### Key modules

| Module | Role |
|--------|------|
| `SafeDICore` | Models (`TypeDescription`, `Property`, `Instantiable`, `Dependency`), visitors (`FileVisitor`, `InstantiableVisitor`), generators (`ScopeGenerator`, `DependencyTreeGenerator`) |
| `SafeDIMacros` | Swift macro implementations (`@Instantiable`, `@Received`, etc.) |
| `SafeDITool` | CLI entry point with `scan` and `generate` subcommands — scans Swift files for `@Instantiable` types, builds dependency tree, generates output |
| Plugins (`SafeDIGenerator`) | SPM build tool plugin that wires the tool into the build |

### Code generation flow

1. **Plugin** writes CSV of swift files → runs `SafeDITool scan` to build manifest → runs `SafeDITool generate` to produce code
2. **`SafeDITool generate`** parses all files via `FileVisitor` → builds `DependencyTreeGenerator` → generates per-root code + mock code
3. **DependencyTreeGenerator** creates `ScopeGenerator` trees → each generates its code via `generatePropertyCode`
4. **Mock generation** (`generateMockCode`) creates `mock()` static methods with `@autoclosure @escaping` parameters, `T? = nil` subtree parameters, and `MockContext` for disambiguation

### Conditional compilation

`FileVisitor` takes a `ConditionalCompilationEvaluator`; `InstantiableVisitor` takes a `ConditionalCompilationHandling`, which the macro sets to `.scanAllClauses` (the compiler already picked the active clause) and `FileVisitor` sets to `.evaluate(evaluator)`. The evaluator treats the supplied `activeCompilationConditions` as complete (a bare condition not in the set is inactive), scans every clause of platform-conditioned blocks (`os()`, `canImport()`, …), and evaluates mock-only content (`SafeDIContentDetector`) as if `mockConditionalCompilation` were active. A guarded initializer counts as SafeDI content only when `ConstructionInitializerCandidates` finds some evaluation could select it for construction — it must be able to fulfill the dependencies (bounded below by those outside every `#if` and above by those in every clause) and must not follow an unguarded initializer that fulfills them in every evaluation; initializers in `@Instantiable` extensions never count. Each evaluation that decides a block guarding SafeDI content is a `ConditionalCompilationDecision`; `generate` prepends `ConditionalCompilationDecision.compileTimeAssertions` (`#if …` / `#error`) to every generated file so the compiler rejects code generated under a condition it evaluates differently. There is no "unknown condition" state and no error at generate time: the compile-time assertion is the fail-closed mechanism. `parseModule` first parses the module's own files (`configurationFilePaths`) named `SafeDIConfiguration.swift`, chosen by path alone, and walks them to find the module's `#SafeDIConfiguration`: `SafeDIContentDetector` classifies a configuration as production content, so its `#if` blocks never depend on `mockConditionalCompilation`. The configuration found there builds the module's evaluator, every other file is read, parsed, and walked once with it, and the `SafeDIConfiguration.swift` trees are walked again from memory only when the mock condition is not the default. When no `SafeDIConfiguration.swift` holds a configuration (the fallback), every file is walked with the supplied conditions and the default `DEBUG` mock condition, which finds a configuration elsewhere; if it names another mock condition, every file that declared SafeDI content is read, parsed, and walked again — no text heuristic picks a subset. `SafeDIConfiguration.placementWarning` reports exactly that case (configuration outside `SafeDIConfiguration.swift` with a non-default mock condition) as a `SourceDiagnostic` with `.warning` severity located at the invocation (`SafeDIConfiguration.declarationLocation`, which travels in module info and scan's cache). `generate` returns warnings instead of throwing them and `run()` prints them; `scan` never warns, so a build warns once per `generate`. Every syntax tree but those of `SafeDIConfiguration.swift` files is released as soon as it is walked, so memory scales with concurrency rather than module size. `scan` and `generate` both go through it, and it rejects more than one configuration in scope. `scan` records its project root in the manifest so `generate` matches configuration files by the same resolved paths.

Build tool plugins cannot read the conditions the compiler receives while they plan the build, so the `SafeDIGenerator` plugin also passes `generate` the literal arguments `--build-setting-active-compilation-conditions=[${SWIFT_ACTIVE_COMPILATION_CONDITIONS}]` and `--build-setting-other-swift-flags=[${OTHER_SWIFT_FLAGS}]` (`BuildSettingCompilationConditions`). Swift Build (Xcode and SwiftPM's `swiftbuild` backend) expands them when the command runs, and Xcode project builds expand them through the shell script that runs the command; SwiftPM's native backend passes them through literally. When both arrive expanded, their conditions plus the `-D` flags in `OTHER_SWIFT_FLAGS` *replace* the command-line and manifest conditions (Xcode reports a package's debug-configuration defines to plugins in Release too, so a union would be wrong); otherwise `generate` falls back to them. The plugin passes the options to every SafeDITool it runs, including the prebuilt binary pinned in `Package.swift` (Swift 6.2 sometimes hands the plugin that one even with the `sourceBuild` trait) and the `.safedi/` download named by `safeDIVersion` in `Plugins/Shared.swift`, so those must never name a release older than 2.1.0-rc-3, the first to accept them. Which files exist — roots, `generateMock: true` types, `additionalMocksToGenerate` entries, `#SafeDIConfiguration` files — is still decided by `scan` at planning time, but independently of any condition: `scan` plans an output for each such declaration in every clause of every `#if` block (`OutputFileDeclarations`, which `SafeDIContentDetector` collects during the walk of each block it already makes and `FileVisitor` adds for the clauses it scans), and treats the files in every configuration's `additionalDirectoriesToInclude` as inputs, parsing those only an inactive configuration lists solely to plan their roots. `generate` writes every planned output, without code (only the header and its compile-time assertions) when the declaration is inactive under its conditions, and generates the additional mocks only of the configuration it selects. It still rejects with a `ManifestError` a declaration whose file the manifest does not list (the manifest's `mockScopedFilePaths` lets it check mocks and configurations), which with superset planning means the file changed after `scan` or the manifest is hand-written. The `PluginScanner` fallback ignores `#if` and unions every configuration's arrays, so it plans the same superset. Because a cached file scan may declare a configuration in an inactive clause, `generate` parses the module afresh when a stale file declares a configuration in any clause, not just an active one; and when it parses `additionalDirectoriesToInclude` afresh it names those files as the manifest does, so their roots match its entries.

Because `generate` usually has more conditions than `scan` (always `SWIFT_PACKAGE`, `DEBUG` in debug), scan's cache keeps per-file results keyed by what each file consulted. `ScannableClauses.consultedConditions` records every bare condition a clause selection depended on (minus the mock condition for mock-only blocks, which is forced active); `FileVisitor` and `InstantiableVisitor` accumulate them only for blocks whose selection can change what they report: blocks with SafeDI content, blocks with syntax errors, and (separately, as `importOnlyConsultedCompilationConditions` with `importSegments` holding the block source) blocks that guard only imports. `FileVisitor` also collects `mockImports`: each block guarding only imports is selected again as a block guarding mock-only declarations is, and `importOnlyConsultedCompilationConditions` covers both selections. Generated mock files, `SafeDIMockConfiguration.swift`, the mock half of `--combined-output`, and module info carry `mockImports`; dependency-tree files keep `imports`, so `#if DEBUG import A #else import B #endif` still gives production code `import B`. `CachedScannedModuleInfo` stores the files that consulted nothing as one `ModuleInfo` and the rest as `CachedFileScan`s; `generate` walks a file again only when a condition it consulted changed value, re-evaluates only its import segments when only those changed, and parses the whole module afresh when a walked-again file declared a configuration. Any new state a visitor collects from inside an `#if` block must either be covered by `consultedCompilationConditions` or be provably independent of the selection, or the cache becomes unsound.

### Mock generation flow

Mock generation follows this pipeline:

1. **`generateMockCode`** builds the mock scope map via `createMockTypeDescriptionToScopeMapping` (includes ALL types, not just reachable from roots)
2. For each type with `generateMock: true`, **`createMockRootScopeGenerator`** promotes `@Received` dependencies to root-level children and validates for cycles
3. **`ScopeGenerator.generateMockRootCode`** builds the mock method:
   - Calls `collectMockParameterTree` to walk the dependency tree and build `MockParameterNode` trees
   - Collects flat parameters: `@Forwarded` deps, uncovered `@Instantiated` deps, `@Received` deps not in the tree
   - Generates `SafeDIOverrides` struct (if tree children exist) and the `mock()` method signature and body

The production code path (`generatePropertyCode` with `.dependencyTree`) and mock path (`.mock`) share the same `ScopeGenerator` but diverge at `generatePropertyCode`. Mock fields (`mockInitializer`, `mockReturnType`, `customMockName`) are only accessed in mock code paths — never in production paths.

### Cycle mechanisms

Multiple cycle-related mechanisms coexist — keep them distinct:

| Name | Scope | Set by / when | Role |
|------|-------|---------------|------|
| `isPropertyCycle` on a scope/node | Per-root, syntactic | `Scope.createScopeGenerator` when a property label repeats in the ancestor stack | Terminates infinite descent during a single root's walk; differs between roots for the same underlying cycle. |
| `cycleEdges` (set of `CycleEdge`) | Global | `DependencyTreeGenerator.computeCycleEdges`, alphabetical-DFS feedback arc set | Chooses a single back-edge per cycle consistently across all roots — required because shared `SafeDIMockConfiguration` structs must have one shape. Consumed by struct generation AND override-path navigation in mock bodies. |
| `throwIfInvalidCycle` | Shared classifier | Called from `validatePropertiesAreFulfillable` (production, and a mock root whose children require one another) and `validateMockRootScopeForCycles` (mock) | Rejects constant + partially-lazy + received-lazy cycles. Accepts fully-lazy non-received cycles (those compile as long as pruning breaks the config-struct recursion). |
| `validateMockRootScopeForCycles` | Mock graph | Called after `@Received` promotion in `createMockRootScopeGenerator` | Walks the post-promotion scope to catch cycles that only surface once received deps are promoted to mock-root children — through an ancestor only. |
| `childrenRequireEachOther` | Mock root's children | Called after `validateMockRootScopeForCycles` | Cheap check, from the cached `collectReceivedProperties`, for children that require one another (C receives B while B's subtree receives C), which no ancestor stack shows. Only then is production's `validatePropertiesAreFulfillable` walk run on the mock root, to report the cycle. Running that walk on every mock root would add a received-dependency walk per node of every mock tree; on a real 250-mock-root app the check triggers it zero times. |
| Soft `onlyIfAvailable` edges in `orderedPropertiesToGenerate` | Per scope, siblings | `ScopeGenerator.orderedPropertiesToGenerate` | A required receive of a sibling always orders it first; an `onlyIfAvailable` receive does only when that does not close a sibling cycle. When it would, the receiver's subtree is generated with that sibling in `propertiesGeneratedLater` and gets `nil`, matching production's "not available" semantics. Not an error. |

Key consequence: if `throwIfInvalidCycle` accepts a cycle, every hop in it is non-constant (Instantiator/ErasedInstantiator-typed). Any code that assumes "a cycle node reached through a constant-typed property" is reasoning about something impossible.

### Mock generation specifics

- **Share logic between production and mock paths where possible.** Validation, scope population, and other shared concerns should live in common helpers rather than being duplicated between `createTypeDescriptionToScopeMapping` and `createMockTypeDescriptionToScopeMapping`. When adding validation to one path, check whether the other path needs it too.
- **Selected construction initializer.** `InstantiableVisitor.canonicalConstructionInitializer` is the single initializer SafeDI selects for construction (first init that fulfills the type's dependencies). `Instantiable.initializer` is populated from it, and mock generation emits against its signature. Validation that only matters for the path SafeDI uses (e.g., diagnosing `Self.*` in default expressions) should gate on this — walking every entry in `visitor.initializers` false-positives on unused overloads.
- **Two-layer mock return type** (extension-based `customMockName` only). When a `customMock` method returns a type different from `Self` (permitted via `fulfillingAdditionalTypes`), two concerns have to agree:
  1. **Inner closure type** (`MockParameterNode.builderClosureType`) — the type of the override closure stored in the parent's `SafeDIMockConfiguration`. Uses the property type so callers writing overrides match the receiving slot. Fixed in #251.
  2. **Outer `mock()` return type** — the generated `mock()` wrapper must return whatever the user's `customMock` returns. Fixed in #266.

  When touching extension-based types with `customMockName`, confirm both layers. `mockReturnTypeIsCompatible(withPropertyType: concreteInstantiable)` distinguishes genuine hand-written mocks from mockOnly-inherited ones.
- **Hand-written `mock` vs. generated `mock()`.** A type whose `mock()` this module generates (`generateMock: true` or `additionalMocksToGenerate`) must not also have a hand-written method named `mock`, wherever it is declared. The macro enforces this within one declaration; `DependencyTreeGenerator.generateMockCode` enforces it across declarations and modules (a `mockOnly` pair) when it creates mock roots, by name only — no signature analysis, because a `mockOnly` extension's mock defaults every parameter, so even "distinguishable" pairs leave `Type.mock()` ambiguous. Do not work around such pairs at the call site (e.g. coerced function references). `Instantiable.mockDeclarationLocation` locates the diagnostic and must travel with `mockInitializer` through every merge.
- `MockParameterIdentifier` (propertyLabel + sourceType) is the key type for tracking parameters throughout mock gen
- `resolvedParameters` tracks which deps are already bound — prevents duplicate bindings across scopes
- `parameterLabelMap` maps identifiers to disambiguated parameter names
- `TypeDescription.asIdentifier` produces identifier-safe disambiguation suffixes
- `TypeDescription.simplified` strips wrappers for cleaner suffixes, with fallback on collision
- Closure-typed defaults use `@escaping T = default` (not `@autoclosure`)
- `#SafeDIConfiguration` is always read from the current module only, never dependent modules
- **Received erased types.** `generateMockCode`'s `erasedToConcreteTypeMap` lets a mock root promote a received type no `@Instantiable` fulfills (e.g. `AnyService`) by building the concrete type an `@Instantiated(fulfilledByType:, erasedToConcreteExistential: true)` property of that exact property type names, in any module. It is keyed by the full property type, because a receiver matches by type, so an `ErasedInstantiator<(), AnyService>` erasure never counts toward `AnyService`. A type that erasures give more than one concrete type is left out of the map, and its receivers become required flat `mock()` parameters: picking one would depend on dictionary iteration order. Production never consults the map — production receivers get the value from an ancestor.
- When a mockOnly and a non-mockOnly coexist for the same type, `resolveSafeDIFulfilledTypes` merges them. The `(false, true)` and `(true, false)` branches handle opposite processing orders. Any cross-cutting concern (tracking sets, stale clearing) must be applied to both branches or order-dependent bugs will surface only on CI.

### Validation boundaries

Validation is split between the macro and the plugin based on available context:

- **Macro validation** (compile-time, local context only): The macro sees only the single decorated type or extension. Any error that can be determined from local context belongs here — missing `init`/`instantiate()`, invalid parameter combinations (`mockOnly + generateMock`), mock method signature issues, access control. These produce fix-its in the IDE.
- **Plugin validation** (build-time, full context): The plugin (`SafeDITool generate`) sees all modules' types. Errors that require cross-type knowledge belong here — unfulfillable dependencies, dependency cycles, duplicate type declarations, duplicate mock providers, a `mockOnly` hand-written `mock` on a type whose `mock()` is generated.

### Serialization

The `Instantiable` struct conforms to `Codable` and is serialized as JSON in `.safedi` module info files. These files are **regenerated every build** — there is no cross-version deserialization. Do not add backward-compatibility decoding logic (e.g., `decodeIfPresent` with defaults). The synthesized `Codable` conformance is sufficient.

## Code Style

- **No abbreviations.** Use `dependency` not `dep`, `parameter` not `param`, `declaration` not `decl`. Everywhere: variables, functions, tests, comments, commits.
- **No `default` or `case _` in switch statements when all cases are knowable.** Enumerate all cases explicitly for compile-time safety.
- **Use `for ... where` for simple boolean filters** instead of `guard ... else { continue }` inside the loop body.
- **Use `guard` for early exits**, not `if condition { continue/return }`.
- **No early return from bare `if`.** If an `if` branch returns, the non-returning path must be in an explicit `else` clause. Never fall through after `if { return }`.
- **Test names follow `method_expectation_conditionUnderTest`** pattern (e.g., `mock_disambiguatesAllParameters_whenThreeChildrenShareSameLabel`).

## Testing Philosophy

- **TDD**: Write failing tests first, then fix.
- **One behavior per test method.** Each test verifies one behavior, but may use multiple assertions to fully validate it (e.g., checking both the count and content of output). Do not test unrelated behaviors in the same method.
- **No tautological tests.** Tests must exercise real code paths with real input. Never use test helpers that rewrite input before processing — the test content should be exactly what production code would see. Tests should verify input code → output code.
- **Test through the pipeline**, not direct model construction. Mock tests use `executeSafeDIToolTest` which parses real Swift source through the full visitor → generator pipeline.
- **Full `==` output comparison.** Never use `.contains()` for mock output. Compare the complete expected string.
- **Verify updated test expectations compile.** When updating expected output in generator tests, review the new expected code to confirm it would compile as valid Swift. Check that variable references resolve to the correct scope, types match (no optional where non-optional expected), and all referenced variables have bindings. Do not blindly update expected output to match actual — the actual output may itself be buggy.
- **Code generation tests should only test paths where the macro would not emit an error.** Test inputs must be valid under `@Instantiable` macro validation — every `mockOnly: true` type needs a `mock()` method (or `customMockName` method), mock method names on the same type must not collide (and a `mockOnly` mock paired with a generated mock must use `customMockName`, or generation errors), and production types need `init` or `instantiate()`.
- **Test titles must be observably verified.** When a test title says "prefers X over Y", the assertion must verify X is used — not just that the test doesn't crash. Add a parent type with `generateMock: true` that instantiates the type under test, and assert the full mock output shows X's method name.
- **If code can't be covered by a test with real parsed input, remove the code.** Dead branches and defensive fallbacks for structurally unreachable paths should not exist.
- **"Structurally unreachable" claims need a failing test.** Before removing defensive branches on the grounds that they can't be reached, write a test that tries to reach them with valid input. If the test can't be written, cite the specific rejection (file:line) and the input shape it rejects — a structural argument alone is not evidence. Structural arguments are easy to get wrong: e.g., `erasedToConcreteExistential: true` does NOT imply a constant property type, so "erased + cycle is rejected as constant" was wrong and cost a round trip when the branches had to be restored.
- **Test fixture file naming controls processing order.** Files parse in parallel, so completion order is random; `ModuleInfo(_:)` therefore orders a module's file scans by path, so its instantiables are in source file path order, keeping each file's top-to-bottom declaration order, and its imports and mock imports are sorted and deduplicated, so the `.safedi` file `generate` writes is the same bytes every run; upstream `.safedi` module info is already in that order, so the combined list `resolveSafeDIFulfilledTypes` sees is deterministic without a second sort. `executeSafeDIToolTest` names fixture files by extracting the type name from `@Instantiable` in the source content, so those names decide the order. When testing ordering-sensitive behavior (e.g., which of the two mockOnly merge branches runs), pick names that sort the way you need, and be aware that an `extension MyService` file falls back to `"File"`. A configuration-only snippet also falls back to `File.swift`, so it exercises `parseModule`'s fallback path; pass `swiftFileContentByFilePath` (e.g. `["SafeDIConfiguration.swift": …]`) to name a fixture explicitly when the file name matters.

## Common Pitfalls

- The input CSV written by plugins includes ALL swift files (target + dependencies). Mock scoping requires passing `mockScopedSwiftFiles` separately — only the target's own files.
- `Property.<` sort uses type as tiebreaker (not just label) for stable ordering.
- Extension-based `@Instantiable` types use `static func instantiate(...)` instead of `init(...)`. Their `@Instantiated` dependencies are constructed by the parent scope.
- When a received dependency is promoted to root scope, the producer branch must capture the root-bound value — not reconstruct the type.
- `collectReceivedProperties` returns as `onlyIfAvailable` only properties that every receiver receives only if available. A property one receiver requires and another receives `onlyIfAvailable` is required — the collision is real, because an `onlyIfAvailable` alias's fulfilling property is non-optional (`@Received(fulfilledByDependencyNamed: "x", ofType: X.self, onlyIfAvailable: true)` yields `x: X`). Treating such a property as only-if-available skips its promotion, and the required receiver is handed `X?`. `createMockRootScopeGenerator` applies the same rule across the root's tree and the promoted scopes' trees.
- A mock root can list the same property twice: promotion collects a promoted scope's received properties without subtracting what the root already instantiates. `orderedPropertiesToGenerate` emits only the first child for each property; emitting both produces two identically-labeled siblings, which sibling disambiguation renames to the same `label_Type_` name — an invalid redeclaration and a duplicate `SafeDIOverrides` field.
- Promoted dependencies are siblings at the mock root, and an `onlyIfAvailable` receive deep in one sibling's subtree resolves against another sibling by Swift lexical scope. Availability therefore depends on emission order: an `onlyIfAvailable` receiver may only see siblings emitted before its subtree. Any new emission path must thread `propertiesGeneratedLater` (production `generateCode`, mock `collectMockParameterTree`) and pass `nil` for receives in it, or it will reference a `let` before its declaration. The test compile verifier compiles each test's fixtures and generated code to an object file (`-emit-object`, whole-module), so it reports SIL diagnostics as well as type errors: a nested function capturing a later local ("closure captures before it is declared") and `self` used before `self.init` in a production `init()` fail the test. `-typecheck` would miss both. It defines `DEBUG`, the test's conditions, and the module's `mockConditionalCompilation`, so generated mocks are compiled too.
- `resolvedParameters` flows through sibling accumulation AND parent-to-child descent. Both paths must be consistent.
- **`#sourceLocation` paths are compared as strings.** The compiler groups every path a module uses – each source file as it was handed to the compiler, and each `#sourceLocation` file – by file name, and warns at a directive whose file name maps to more than one path (a build error under warnings as errors). It does not resolve relative paths or symbolic links. `AliasDeclarationReferences` emits a directive for an alias only when `generate` knows the compiler’s spelling: a plugin manifest’s `projectRoot` (`SafeDIToolManifest.compilerFilePath(for:underProjectRoot:)`), unless the root is spelled differently from its `realpath(3)` resolution (`String.isResolvedFilePath`, one call per `generate`) – Xcode reports a package under `/tmp` as `/tmp/…` and hands the compiler `/private/tmp/…`, and a manifest from `scan` holds no second spelling that would reveal it – or `--compiler-receives-input-paths-unchanged` (passed by the Bazel rule). It still omits one whose file name another directive’s file or one of the module’s own files shares (`--mock-scoped-files` when `generate` scans for itself, the manifest’s `mockScopedFilePaths` otherwise, every input file under the flag), which covers a module file known under two spellings such as Xcode’s `/tmp/…` against the working directory’s `/private/tmp/…`. Every other alias gets a trailing `// Declared at <path>:<line>` comment with the path as the integration handed it (project-root-relative under a plugin). Tuist shares its build cache across machines, so nothing generated for a Tuist build, nor its `.safedi`, may hold an absolute path: its script hands `generate` `$SRCROOT`-relative paths and gets comments. Never spell a directive path with `standardizedFileURL`, which drops a leading `/private` the compiler keeps. The examples treat warnings as errors and each declares an aliased `@Received` in its root module, so CI catches a wrong spelling.
- `typeDescriptionToFulfillingInstantiableMap` is a dictionary — iterating `.values` has non-deterministic order. Any code that reduces, sorts, or builds state from `.values` must produce the same result regardless of iteration order. CI runs tests 5 times specifically to catch non-determinism.
- `resolveSafeDIFulfilledTypes` can produce multiple map entries with the same `concreteInstantiable` under different keys (e.g., a merged entry under `MyService` and an unmerged entry under `ServiceProtocol`). These entries may have different mock info. The mock scope map uses scope-reuse by `concreteInstantiable` and a deterministic sort to handle this.
- `mockInitializer` on an `Instantiable` can be inherited from a mockOnly merge — it doesn't always mean the type declared its own mock. `generateMock` is never inherited. Use `mockReturnTypeIsCompatible(withPropertyType: concreteInstantiable)` to distinguish genuine hand-written mocks from inherited ones.
- **`erasedToConcreteExistential: true` is orthogonal to the property's `PropertyType`.** The flag controls whether SafeDI wraps the concrete in the property's existential type at the call site; it does not determine whether the property itself is constant or lazy. The four combinations:

  | Decorator + property | `Property.PropertyType` | `isConstant` | Can be in an accepted cycle? |
  |----------------------|-------------------------|--------------|------------------------------|
  | `@Instantiated let x: Concrete` | `.constant` | `true` | No — `throwIfInvalidCycle` rejects. |
  | `@Instantiated let x: Instantiator<T>` | `.instantiator` | `false` | Yes. |
  | `@Instantiated(erasedToConcreteExistential: true) let x: AnyProto` | `.constant` | `true` | No — `throwIfInvalidCycle` rejects. |
  | `@Instantiated(erasedToConcreteExistential: true) let x: ErasedInstantiator<A, AnyP>` | `.erasedInstantiator` | `false` | Yes. |

  When reasoning about whether an erased node can appear on a pruned back-edge, check `propertyType.isConstant` — don't short-circuit on the erasure flag.
